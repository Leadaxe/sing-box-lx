# FEATURE 002 — XHTTP — клиентский XHTTP-транспорт

| Поле | Значение |
|------|----------|
| Тип | Продуктовая фича |
| Build-tag | `with_xhttp` |
| Состояние | ✅ live-validated против Xray; `stream-one`/`auto`+REALITY девайс-верифицированы (`v1.14.0-lx.17`). ⚠️ `packet-up`/`stream-up` за обратным прокси залипали на дайле — устранено задачей [061](../../TASKS/061-XHTTP_DIAL_DOWNLOAD_DEADLOCK/SPEC.md) — в поле с `v1.14.0-lx.30` без жалоб |

## Назначение

Транспорт XHTTP (в Xray — «splithttp»/«xhttp») для VLESS/VMess: туннель
переносится внутри обычных HTTP-запросов, чтобы на проводе выглядеть
как веб-трафик, а не как прокси-протокол.

Целевая пара — **сервер Xray, клиент наш**. Контракт задаёт Xray: расхождение
даже в мелочи (лишний сегмент пути, не тот заголовок) ломает соединение молча —
запрос проходит, данные не идут.

## Контролируемые параметры

Все — внутри блока транспорта `xhttp`.

### Основные

| Ключ | Тип | Дефолт | Смысл |
|------|-----|--------|-------|
| `mode` | `auto` · `packet-up` · `stream-up` · `stream-one` | `auto` | Как разнесены аплинк и даунлинк |
| `host` | строка | TLS SNI или адрес сервера | Значение заголовка Host |
| `path` | строка | пусто | Префикс пути запроса |
| `headers` | карта | пусто | Дополнительные заголовки на каждом запросе |

**Режимы:**

| Режим | Аплинк | Даунлинк |
|-------|--------|----------|
| `packet-up` | Последовательные POST-пакеты | Отдельный GET-поток |
| `stream-up` | Один потоковый POST | Отдельный GET-поток |
| `stream-one` | Одно двунаправленное соединение (тело запроса вверх, тело ответа вниз) | |
| `auto` | При REALITY → `stream-one`, иначе → `packet-up` (на HTTP/1.1 и HTTP/3 REALITY не бывает — всегда `packet-up`) | |

Все режимы работают на всех версиях HTTP.

### Версия HTTP

Отдельного ключа нет: версия выводится из TLS-блока внешнего протокола
по правилу Xray (`decideHTTPVersion`).

| TLS | REALITY | `tls.alpn` | Версия | Как идёт трафик |
|-----|---------|-----------|--------|-----------------|
| нет | — | — | HTTP/2 без TLS (h2c) | TCP |
| да | да | любой | HTTP/2 | TCP + REALITY |
| да | нет | пусто | HTTP/2 | TCP + TLS, ALPN `h2` |
| да | нет | два и больше элементов | HTTP/2 | TCP + TLS, ALPN как в конфиге |
| да | нет | `["http/1.1"]` | HTTP/1.1 | TCP + TLS |
| да | нет | `["h3"]` | HTTP/3 | UDP + QUIC |
| да | нет | любой другой один элемент | HTTP/2 | TCP + TLS, ALPN как в конфиге |

Элемент сравнивается точно. На HTTP/1.1 долгие запросы (download-GET,
потоковый POST) идут каждый по своему соединению с `Connection: close`,
upload-POST'ы `packet-up` переиспользуют соединения.

### Размещение идентификаторов

| Ключ | Тип | Дефолт | Смысл |
|------|-----|--------|-------|
| `session_placement` | `path` · `query` · `header` · `cookie` | `path` | Где переносится идентификатор сессии |
| `session_key` | строка | `X-Session` / `x_session` | Имя параметра при размещении не в пути |
| `seq_placement` | `path` · `query` · `header` · `cookie` | `path` | Где переносится номер пакета (только `packet-up`) |
| `seq_key` | строка | `X-Seq` / `x_seq` | Имя параметра при размещении не в пути |

### Данные аплинка

| Ключ | Тип | Дефолт | Смысл |
|------|-----|--------|-------|
| `uplink_data_placement` | `body` · `auto` · `header` · `cookie` | `auto` | Где переносится полезная нагрузка (не-`body` — только `packet-up`) |
| `uplink_data_key` | строка | `X-Data` / `x_data` | Базовое имя при переносе в заголовке/куке |

### Паддинг

| Ключ | Тип | Дефолт | Смысл |
|------|-----|--------|-------|
| `x_padding_bytes` | `"min-max"` | `100-1000` | Длина паддинга |
| `x_padding_obfs_mode` | флаг | выкл | Выкл — паддинг в Referer (как у старого Xray); вкл — настраиваемое размещение ниже |
| `x_padding_placement` | `cookie` · `header` · `query` · `queryInHeader` | `queryInHeader` | Где размещается паддинг в obfs-режиме |
| `x_padding_key` | строка | `x_padding` | Имя параметра/куки |
| `x_padding_header` | строка | `X-Padding` | Имя заголовка |
| `x_padding_method` | `repeat-x` · `tokenish` | `repeat-x` | Как генерируются байты паддинга |

### Темп аплинка (`packet-up`)

| Ключ | Тип | Дефолт | Смысл |
|------|-----|--------|-------|
| `sc_max_each_post_bytes` | `"min-max"` | `1000000-1000000` | Порог разбиения одного POST |
| `sc_min_posts_interval_ms` | `"min-max"` | `30-30` | Минимальная пауза между POST (антивсплеск) |

### Переиспользование соединений (`xmux`)

Секция `xmux` внутри блока транспорта. Действует и когда её нет — дефолты
применяются в любом случае.

| Ключ | Тип | Дефолт | Смысл |
|------|-----|--------|-------|
| `max_concurrency` | диапазон | `1-1` | Сколько потоков делят одно соединение. Взаимоисключается с `max_connections` |
| `max_connections` | диапазон | без лимита | Сколько соединений держит пул; пока пул меньше, новое соединение открывается всегда. Взаимоисключается с `max_concurrency` |
| `c_max_reuse_times` | диапазон | без лимита | Сколько раз соединение выдаётся под новый поток до вывода из пула |
| `h_max_request_times` | диапазон | `600-900` | Сколько **запросов** проходит через соединение до вывода из пула |
| `h_max_reusable_secs` | диапазон | `1800-3000` | Сколько секунд соединение остаётся пригодным |
| `h_keep_alive_period` | целое (секунды) | дефолт транспорта | Период поддерживающих пингов; отрицательное — выключить. HTTP/2 — пинги h2 (дефолт транспорта), HTTP/3 — QUIC keep-alive (дефолт 10 с), на HTTP/1.1 не действует |

**Диапазонные поля** записываются строкой `"min-max"` (`"3000-4000"`) либо
одним числом (`"4000"` = `"4000-4000"`); пустое значение — дефолт. В секции
`xmux` дополнительно принимается форма двухэлементного массива — так их пишут
конфиги, составленные под другие клиенты. **Каждый диапазон разыгрывается
один раз**, а не на каждый запрос: границы пула — при его создании, лимиты
переиспользования — при создании каждого соединения.

### Принимаются, но игнорируются

Ради симметрии с конфигами и ссылками Xray принимаются и не влияют
на поведение: `sc_max_concurrent_posts`, а также серверные
`server_max_header_bytes`, `no_sse_header`, `sc_max_buffered_posts`,
`sc_stream_up_server_secs`. Конфиг с ними не отвергается.

### Сборка

| Ручка | Значение |
|-------|----------|
| `with_xhttp` | Без тега транспорт `xhttp` отвергается при загрузке с явной ошибкой |
| `with_quic` | Нужен для HTTP/3. Без него конфиг, для которого правило даёт HTTP/3 (`tls.alpn: ["h3"]`), отвергается при загрузке. Поставляемые сборки тег содержат |

## Входы

- **Конфиг** транспорта (выше) плюс параметры внешнего протокола
  (VLESS/VMess, TLS/REALITY).
- **Поток данных** от прокси-протокола, который нужно перенести.

## Выходы

- **HTTP-запросы на сервер** — с путём, заголовками, куками и паддингом
  согласно конфигу.
- **Восстановленный двунаправленный поток** обратно в прокси-протокол.

## Data flow

**`packet-up` (аплинк и даунлинк раздельно):**

```
поток вверх → нарезка на куски (sc_max_each_post_bytes)
            → пауза между отправками (sc_min_posts_interval_ms)
            → POST: путь + идентификатор сессии + номер пакета + паддинг
                                    │
поток вниз ← отдельный GET-поток ───┘
```

**`stream-one` (одно соединение):** запрос открывается один раз, тело запроса
несёт аплинк, тело ответа — даунлинк.

## Правила и гарантии

- **В `stream-one` путь запроса не содержит идентификатора сессии.**
  Сервер маршрутизирует этот режим только при его отсутствии; лишний сегмент
  означает, что даунлинк придёт не тем протоколом и соединение развалится
  без внятной диагностики.
- **Завершающий слэш пути при этом сохраняется.** Сервер приводит свой путь
  к виду со слэшем (когда сессия или номер пакета размещены в пути — это
  умолчание) и обслуживает только запросы с таким началом пути. Отсутствие
  слэша даёт «не найдено» и зависание до таймаута, а не ошибку. Пустым
  в `stream-one` должен быть идентификатор сессии, а не слэш.
- **`auto` при REALITY выбирает `stream-one`** — так поступает Xray,
  и обратный выбор с REALITY-сервером не работает.
- **Запросы, несущие тело, помечаются как gRPC-поток** — паритет с Xray.
  Касается `stream-one` и `stream-up`; отключается `no_grpc_header`.
  Рабочая гипотеза «без пометки обратный прокси буферизует даунлинк»
  живым прогоном не подтвердилась (корнем зависания оказался слэш пути);
  пометка сохранена как соответствие эталону, не как лечение.
- **Перенос нагрузки в заголовке или куке допустим только в `packet-up`** —
  вне его конфиг отвергается с ошибкой.
- **Метод `GET` вне `packet-up` не отвергается, а заменяется на `POST`
  с предупреждением.** В остальных режимах нагрузка идёт в теле запроса,
  которого у `GET` нет; одна кривая нода подписки не должна ронять весь
  конфиг, поэтому она чинится, а не блокирует загрузку.
- **Неизвестные и серверные ключи не ломают загрузку** — принимаются
  и игнорируются.
- **Соединение не отдаётся вызывающему после ответа сервера, а сразу.**
  В режимах с раздельным даунлинком сервер придерживает нисходящий поток
  до первого пакета аплинка; ожидание ответа внутри установки соединения
  замыкает круг — обе стороны ждут друг друга.
- **Лимит переиспользования считается в запросах, а не в потоках.**
  В `packet-up` один поток порождает много запросов аплинка, поэтому счёт
  по потокам занижал бы износ соединения в разы.
- **REALITY всегда идёт по HTTP/2.** `tls.alpn` без `h2` в списке заменяется
  на `["h2"]` с предупреждением: иначе узел с `alpn: ["h3"]` по TCP
  не поднимется. У Xray ALPN из конфига до REALITY не доходит вовсе.
- **Без TLS — h2c, как раньше.** Xray здесь выбрал бы HTTP/1.1; сервер Xray
  принимает обе формы, и провод существующих конфигов не меняется.
- **Отпечаток uTLS на HTTP/3 не применяется** — паритет с Xray. Конфиг
  не падает, при загрузке пишется предупреждение; QUIC-рукопожатие идёт
  с профилем Chrome. С `disable_sni` профиль Chrome для узла выключается
  (с предупреждением): проверка сертификата важнее вида рукопожатия.
- **HTTP/3 ходит по UDP через тот же `detour`.** Если detour UDP не умеет,
  dial отвечает `HTTP/3 needs UDP to the server`; если UDP режется по пути,
  dial завершается по таймауту рукопожатия QUIC, а не висит.
- **Соединение, упершееся в лимит, выводится из пула, но не рвётся, пока
  на нём живут потоки** — закрытие откладывается до последнего из них.

## Границы

- **Только клиент.** Серверную сторону форк не реализует.
- **Паддинг вне obfs-режима намеренно минимален** — сохраняется совместимость
  со старым поведением Xray.
- **Не поддерживаются:** `downloadSettings` Xray (download по другому адресу
  или версии), `finalmask.quicParams` (параметры QUIC задаются как у Xray
  по умолчанию, контроль перегрузки — Cubic, у Xray BBR), ECH на HTTP/3
  (узел грузится, dial отвечает ошибкой), сырые pipelined upload-POST'ы
  HTTP/1.1 без чтения ответов.
- **Служебный паддинг, вставляемый сервером в `stream-up`, не вычищается** —
  если целевой сервер его шлёт, поведение нужно проверять отдельно.

## Особенности сопровождения

- **Контракт задаёт Xray.** Поведение сверяется с его исходниками
  и трекером, а не выводится из общих соображений.
- **Синтетика не заменяет живой прогон.** Дважды подряд зелёная синтетика
  скрывала неработающий в поле `stream-one` — живой прогон 2026-08-01
  вскрыл сразу два дефекта (тип контента и слэш пути) и закрыл этот долг;
  правило остаётся: новую механику принимать только после провода.
- **Стенд из голого сервера воспроизводит не всё.** Часть контракта
  адресована не серверу, а обратному прокси перед ним: сервер такие
  запросы принимает одинаково, а прокси — нет. Проверять на схеме
  с фронтом, иначе класс дефекта не виден.
- **Выбор режима при REALITY — хрупкое место**, закрытое тестом-стражем:
  ошибка здесь не диагностируется, а проявляется как неработающий даунлинк.
