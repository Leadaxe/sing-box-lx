# FEATURE 003 — AWG2 — AmneziaWG 2.0 клиентский endpoint

| Поле | Значение |
|------|----------|
| Тип | Продуктовая фича |
| Build-tag | `with_awg` |
| Состояние | ✅ Работает против живого AWG2-сервера; полный клиентский паритет — все 16 параметров обфускации, которые принимают официальные реализации (ещё 4 «advanced»-ключа в протоколе не существуют, см. задачу 031) |

## Назначение

Обфусцированный WireGuard-endpoint. Обычный WG опознаётся по сигнатуре:
фиксированные типы сообщений в первом байте, характерные размеры пакетов,
предсказуемая последовательность хендшейка. AWG2 меняет форму пакетов так,
чтобы этой сигнатуры не было — при полностью сохранённой криптографии
и семантике WireGuard.

Клиент должен сойтись с сервером **побайтово**: обфускация симметрична,
и расхождение любого параметра означает, что хендшейк не состоится вообще.

## Контролируемые параметры

Все — внутри блока endpoint'а типа `wireguard`. Покрыто **16 из 20**
параметров AmneziaWG 2.0.

### Junk-пакеты перед хендшейком

| Ключ | Тип | Дефолт | Смысл |
|------|-----|--------|-------|
| `jc` | целое | 0 (выкл) | Сколько мусорных пакетов отправить перед хендшейком |
| `jmin` | целое | 0 | Минимальный размер мусорного пакета, байт |
| `jmax` | целое | 0 | Максимальный размер, байт |

### Padding (дополнительный junk внутри сообщений)

| Ключ | Тип | Дефолт | Смысл |
|------|-----|--------|-------|
| `s1` | целое | 0 | Junk перед init-сообщением хендшейка |
| `s2` | целое | 0 | Junk перед response-сообщением |
| `s3` | целое | 0 | Junk в cookie-сообщении |
| `s4` | целое | 0 | Junk в transport-пакетах (каждый пакет данных) |

### Magic headers — подмена типов сообщений

| Ключ | Тип | Дефолт | Смысл |
|------|-----|--------|-------|
| `h1` | целое **или** `"min-max"` | штатный тип WG | Тип init-сообщения |
| `h2` | целое **или** `"min-max"` | штатный | Тип response-сообщения |
| `h3` | целое **или** `"min-max"` | штатный | Тип cookie-сообщения |
| `h4` | целое **или** `"min-max"` | штатный | Тип transport-сообщения |

Диапазонная форма `"min-max"` (AWG 2.0) означает, что значение выбирается
из интервала — так его записывают экспорты awg2-серверов.

### CPS — контролируемые последовательности пакетов

| Ключ | Тип | Дефолт | Смысл |
|------|-----|--------|-------|
| `i1`…`i5` | строка мини-языка | пусто | Пакет-приманка, отправляемый в заданный момент |

Мини-язык CPS чувствителен к регистру, **порядок значим**: последовательность
статических байтов, счётчиков, таймстампов и случайных блоков. Типичное
применение `i1` — снимок реального протокола (например, QUIC Initial),
чтобы первый пакет соединения выглядел как чужой легитимный трафик.

### Masquerade — декларативная форма `i1`

| Ключ | Значения | Обязателен | Смысл |
|------|----------|-----------|-------|
| `ip` | `quic` · `dns` · `stun` · `sip` | при любом из трёх | Под какой протокол маскируется первый пакет |
| `id` | домен | только для `quic` | Домен в приманке. Для `dns`/`sip` необязателен — без него генерируется псевдо-домен; для `stun` игнорируется |
| `ib` | `chrome` · `firefox` · `curl` | нет | Профиль клиента; принимается только вместе с `ip=quic` |

Вместо ручного составления CPS-строки пользователь называет протокол, домен
и клиент — приманка собирается за него.

`ib` выбирает **TLS-фингерпринт приманки**: `chrome` и `firefox` дают подлинный
браузерный отпечаток (JA3/JA4) настоящего браузерного рукопожатия, `curl` и
отсутствие ключа — общий отпечаток. Браузерные профили требуют сборки
с поддержкой имитации TLS; без неё они молча деградируют до общего.

Профиль `sip` — двухпакетный: приманка занимает и `i1` (INVITE), и `i2`
(ответ того же диалога), поэтому явный `i2` вместе с `ip=sip` отвергается.

### Сборка

| Ручка | Значение |
|-------|----------|
| `with_awg` | Без тега AWG-поля отвергаются при загрузке конфига с явной ошибкой — без тихого отката к обычному WG |

## Входы

- **Конфиг** — параметры выше плюс обычные поля WireGuard-endpoint'а
  (ключи, peer, адреса, MTU).
- **Трафик приложения** — то, что маршрутизируется в этот endpoint.
- **Пакеты от сервера** — включая ответы на хендшейк и transport-пакеты.

## Выходы

- **UDP-датаграммы на провод** — обфусцированные: с junk-пакетами, padding,
  подменёнными типами сообщений и приманками.
- **Расшифрованный трафик** обратно в маршрутизацию.
- **Ошибка при загрузке конфига** — если параметры несогласованы (см. гарантии).

## Data flow

**Исходящий путь:**

```
конфиг → валидация параметров → установка соединения
                                       │
        (jc пакетов размером jmin..jmax — мусор перед хендшейком)
                                       │
        init-сообщение: [s1 junk][тип из h1][полезная нагрузка]
                                       │
        приманка i1 (если задана или собрана из id/ip/ib)
                                       ▼
        transport-пакеты: [s4 junk][тип из h4][зашифрованные данные]
```

**Входящий путь:** пакет с провода → распознавание типа по magic-заголовкам →
снятие padding → штатная расшифровка WireGuard → маршрутизация.

Ключевая связь между параметрами: **`s1`–`s4` сдвигают позицию magic-заголовка**
в пакете. Отсюда весь класс пограничных случаев — параметры не независимы,
padding и заголовки читаются из одного и того же буфера.

## Правила и гарантии

- **`id`/`ip`/`ib` взаимоисключаются с явным `i1`.** Конфиг, задающий оба,
  отвергается при проверке — до старта туннеля.
- **`ip` обязателен**, если задан `id` или `ib`.
- **`jmin > jmax` отвергается при загрузке.** Инвертированный диапазон
  раньше ронял процесс в фоновой горутине; теперь это ошибка конфига.
- **Домен `id` проходит строгую проверку формата.** Это граница безопасности:
  для `dns` и `sip` домен уходит на провод внутри структуры протокола,
  и посторонние символы означали бы инъекцию.
- **Малые `s1`–`s4` (0–3) поддерживаются.** При таком padding magic-заголовок
  попадает на позиции, которые в других сценариях используются под служебные
  байты; фича гарантирует, что заголовок при этом не разрушается.
- **Обычный WireGuard не затронут.** Все обфускации активируются только
  заданными параметрами; конфиг без них ведёт себя как штатный WG.

## Границы

- **Паритет клиентской обфускации — полный.** Поддержаны все параметры, которые
  официальный AmneziaWG принимает в клиентском конфиге: `jc`/`jmin`/`jmax`,
  `s1`–`s4`, `h1`–`h4`, `i1`–`i5`, включая полный язык описания приманок.
  Профиль, экспортированный из Amnezia, переносится в конфиг без потерь, и
  туннель к серверу на официальном AmneziaWG поднимается. Сверка с официальными
  реализациями — [031](../../TASKS/031-AWG_PARITY_AUDIT_ADVANCED_SECURITY/SPEC.md).
- **`AdvancedSecurity` не поддерживается и не требуется.** Единственный параметр
  официального конфига вне списка выше. Это серверная ручка: она относится к
  разбору **входящих** подключений (сервер помечает, что клиент пришёл с
  обфускацией) и на то, что отправляет клиент, не влияет. В клиентском профиле
  смысла не имеет — [031](../../TASKS/031-AWG_PARITY_AUDIT_ADVANCED_SECURITY/SPEC.md) §5.
- **Masquerade работает только через приманки-слоты** (`i1`, плюс `i2` у профиля
  `sip`). Механизмы на основе `s1`–`s4` для этой задачи непригодны против
  целевого сценария (WARP).
- **Только клиентская сторона.** Серверную реализацию форк не делает.

## Особенности сопровождения

- **Wire-формат живёт в отдельном форке**, подключённом как submodule.
  Правки формата идут туда, и снятие наших патчей происходит бампом
  версии submodule, а не мержем ядра — см.
  [UPSTREAM_SYNC](../005-UPSTREAM_SYNC/FEATURE.md).
- **Класс дефектов здесь — «значение из конфига».** Параметр проходит
  разбор, но ломает рантайм на границе: ноль, максимум, инверсия min/max,
  пересечение padding и заголовка. Каждый новый параметр проверяй
  на границах, а не только на типичном значении.
- **Симптом расхождения — «нода не встаёт».** Обфускация симметрична,
  поэтому любая ошибка выглядит одинаково: хендшейк не проходит,
  диагностики нет. Проверка возможна только против реального сервера.
