# FEATURE: XHTTP — клиентский XHTTP-транспорт

| Поле | Значение |
|------|----------|
| Тип | Продуктовая фича |
| Build-tag | `with_xhttp` |
| Состояние | ✅ live-validated против Xray; скоуп расширяется (задача 002 — `A`) |

## Назначение

Транспорт XHTTP (в Xray — «splithttp»/«xhttp») для VLESS/VMess: туннель
переносится внутри обычных HTTP-запросов, чтобы на проводе выглядеть
как веб-трафик, а не как прокси-протокол.

Целевая пара — **сервер Xray, клиент наш**. Контракт задаёт Xray: расхождение
даже в мелочи (лишний сегмент пути, не тот заголовок) ломает соединение молча —
запрос проходит, данные не идут.

## Контролируемые параметры

Все — внутри блока транспорта `xhttp`.

### Основные

| Ключ | Тип | Дефолт | Смысл |
|------|-----|--------|-------|
| `mode` | `auto` · `packet-up` · `stream-up` · `stream-one` | `auto` | Как разнесены аплинк и даунлинк |
| `host` | строка | TLS SNI или адрес сервера | Значение заголовка Host |
| `path` | строка | пусто | Префикс пути запроса |
| `headers` | карта | пусто | Дополнительные заголовки на каждом запросе |

**Режимы:**

| Режим | Аплинк | Даунлинк |
|-------|--------|----------|
| `packet-up` | Последовательные POST-пакеты | Отдельный GET-поток |
| `stream-up` | Один потоковый POST | Отдельный GET-поток |
| `stream-one` | Одно двунаправленное соединение (тело запроса вверх, тело ответа вниз) | |
| `auto` | При REALITY → `stream-one`, иначе → `packet-up` | |

### Размещение идентификаторов

| Ключ | Тип | Дефолт | Смысл |
|------|-----|--------|-------|
| `session_placement` | `path` · `query` · `header` · `cookie` | `path` | Где переносится идентификатор сессии |
| `session_key` | строка | `X-Session` / `x_session` | Имя параметра при размещении не в пути |
| `seq_placement` | `path` · `query` · `header` · `cookie` | `path` | Где переносится номер пакета (только `packet-up`) |
| `seq_key` | строка | `X-Seq` / `x_seq` | Имя параметра при размещении не в пути |

### Данные аплинка

| Ключ | Тип | Дефолт | Смысл |
|------|-----|--------|-------|
| `uplink_data_placement` | `body` · `auto` · `header` · `cookie` | `auto` | Где переносится полезная нагрузка (не-`body` — только `packet-up`) |
| `uplink_data_key` | строка | `X-Data` / `x_data` | Базовое имя при переносе в заголовке/куке |
| `uplink_chunk_size` | `"min-max"` | зависит от размещения | Размер куска нагрузки в base64-символах |
| `uplink_http_method` | строка | `POST` | Метод запросов аплинка (`GET` — только `packet-up`) |

### Паддинг

| Ключ | Тип | Дефолт | Смысл |
|------|-----|--------|-------|
| `x_padding_bytes` | `"min-max"` | `100-1000` | Длина паддинга |
| `x_padding_obfs_mode` | флаг | выкл | Выкл — паддинг в Referer (как у старого Xray); вкл — настраиваемое размещение ниже |
| `x_padding_placement` | `cookie` · `header` · `query` · `queryInHeader` | `queryInHeader` | Где размещается паддинг в obfs-режиме |
| `x_padding_key` | строка | `x_padding` | Имя параметра/куки |
| `x_padding_header` | строка | `X-Padding` | Имя заголовка |
| `x_padding_method` | `repeat-x` · `tokenish` | `repeat-x` | Как генерируются байты паддинга |

### Темп аплинка (`packet-up`)

| Ключ | Тип | Дефолт | Смысл |
|------|-----|--------|-------|
| `sc_max_each_post_bytes` | `"min-max"` | `1000000-1000000` | Порог разбиения одного POST |
| `sc_min_posts_interval_ms` | `"min-max"` | `30-30` | Минимальная пауза между POST (антивсплеск) |

**Диапазонные поля** записываются строкой `"min-max"` (`"3000-4000"`) либо
одним числом (`"4000"` = `"4000-4000"`); пустое значение — дефолт.

### Принимаются, но игнорируются

Ради симметрии с конфигами и ссылками Xray принимаются и не влияют
на поведение: `no_grpc_header`, `sc_max_concurrent_posts`, а также серверные
`server_max_header_bytes`, `no_sse_header`, `sc_max_buffered_posts`,
`sc_stream_up_server_secs`. Конфиг с ними не отвергается.

### Сборка

| Ручка | Значение |
|-------|----------|
| `with_xhttp` | Без тега транспорт `xhttp` отвергается при загрузке с явной ошибкой |

## Входы

- **Конфиг** транспорта (выше) плюс параметры внешнего протокола
  (VLESS/VMess, TLS/REALITY).
- **Поток данных** от прокси-протокола, который нужно перенести.

## Выходы

- **HTTP-запросы на сервер** — с путём, заголовками, куками и паддингом
  согласно конфигу.
- **Восстановленный двунаправленный поток** обратно в прокси-протокол.

## Data flow

**`packet-up` (аплинк и даунлинк раздельно):**

```
поток вверх → нарезка на куски (sc_max_each_post_bytes)
            → пауза между отправками (sc_min_posts_interval_ms)
            → POST: путь + идентификатор сессии + номер пакета + паддинг
                                    │
поток вниз ← отдельный GET-поток ───┘
```

**`stream-one` (одно соединение):** запрос открывается один раз, тело запроса
несёт аплинк, тело ответа — даунлинк.

## Правила и гарантии

- **В `stream-one` путь запроса не содержит идентификатора сессии.**
  Сервер маршрутизирует этот режим только при его отсутствии; лишний сегмент
  означает, что даунлинк придёт не тем протоколом и соединение развалится
  без внятной диагностики.
- **`auto` при REALITY выбирает `stream-one`** — так поступает Xray,
  и обратный выбор с REALITY-сервером не работает.
- **Ограничения режимов проверяются:** перенос нагрузки в заголовке/куке
  и метод `GET` допустимы только в `packet-up`.
- **Неизвестные и серверные ключи не ломают загрузку** — принимаются
  и игнорируются.

## Границы

- **Только клиент.** Серверную сторону форк не реализует.
- **Паддинг вне obfs-режима намеренно минимален** — сохраняется совместимость
  со старым поведением Xray.
- **Служебный паддинг, вставляемый сервером в `stream-up`, не вычищается** —
  если целевой сервер его шлёт, поведение нужно проверять отдельно.

## Особенности сопровождения

- **Контракт задаёт Xray.** Поведение сверяется с его исходниками
  и трекером, а не выводится из общих соображений.
- **Синтетика не заменяет живой прогон.** Часть механики принята
  на юнит-тестах, и проверка против реального сервера остаётся
  открытым пунктом.
- **Выбор режима при REALITY — хрупкое место**, закрытое тестом-стражем:
  ошибка здесь не диагностируется, а проявляется как неработающий даунлинк.
