# FEATURE: DNS_GROUP — группа DNS-серверов с резервированием

| Поле | Значение |
|------|----------|
| Тип | Продуктовая фича |
| Build-tag | — (для выдачи состояния группы в UI нужен `with_lx_command`) |
| Состояние | 🔧 Переработка на TTL-модель (v2) — спроектировано, в реализации |

## Назначение

Сбой одного DNS-сервера роняет резолв целиком, даже если в конфиге есть
другие рабочие серверы: `dns.final` — сервер **по умолчанию**, а не резерв;
запрос, направленный правилом в сервер, при его сбое получает ошибку без
повторной попытки.

Фича добавляет тип DNS-сервера `group`: несколько серверов под одним тегом
со стратегией выбора. Группа встаёт всюду, где принимается тег сервера —
и в `final`, и в правилах — и закрывает оба пути одним механизмом, не трогая
схему DNS-правил.

## Контролируемые параметры

Блок в списке DNS-серверов:

```json
{
  "type": "group",
  "tag": "public",
  "servers": ["google", "cloudflare", "quad9"],
  "mode": "stable",
  "error_ttl": "2m",
  "win_ttl": "5m"
}
```

| Ключ | Тип | Дефолт | Смысл |
|------|-----|--------|-------|
| `servers` | список тегов | обязательное | Серверы группы. **Порядок не значим** ни в одном режиме |
| `mode` | `stable` · `fastest` · `parallel` | `stable` | Стратегия выбора цели, см. ниже |
| `error_ttl` | длительность | `2m` | Сколько живёт запись об ошибке сервера |
| `win_ttl` | длительность | `5m` | Сколько живёт запись о победе. **Только для `fastest`**; вне него игнорируется с предупреждением в лог |

### Сборка

Build-tag не вводится: новый тип сервера аддитивен, конфиг без `group` ведёт
себя в точности как upstream. Выдача состояния группы клиенту — часть
[OBSERVABILITY](../OBSERVABILITY/FEATURE.md), за её тегом `with_lx_command`.

## Модель: две записи с TTL

У серверов **нет состояний** (down/up/backoff не существуют). Есть две
таблицы записей, истекающих по TTL:

| Запись | Создаётся | Живёт | Дополнительно |
|--------|-----------|-------|---------------|
| **ошибка** | сбойный обмен (транспорт / таймаут / SERVFAIL) — штатный или в веере | `error_ttl` | запись ошибки **стирает живые победы** этого сервера |
| **победа** | **только** первый успешный ответ в веере (соревновательная — иначе текущий сервер самоусиливается и не переизбирается) | `win_ttl` | успешный обмен сервера **стирает его живые ошибки** (это не победа — самоусиления нет) |

**Чистый** = ноль живых ошибок. `NXDOMAIN` и пустой ответ — валидный ответ
(и победа, если пришёл первым в веере), не ошибка. Смена сети → амнистия
обеих таблиц.

## Data flow

```
             ДВЕ TTL-ЗАПИСИ (вместо состояний)
   ошибка → error_ttl          победа → win_ttl (только fastest)
   успех сервера СТИРАЕТ его живые ошибки (не победа — не самоусиление)
   ошибка сервера СТИРАЕТ его живые победы
   смена сети → амнистия обеих таблиц;  чистый = ноль живых ошибок

запрос ──► ВЫБОР ЦЕЛИ
   │  чистых нет ──► ОДНА попытка к наименее грязному, БЕЗ веера
   │                 (ничья: давность последней ошибки; полная ничья —
   │                  случайно). Это «режим выживания»: анти-шторм
   │                  на мёртвой сети, одна попытка — вся цена запроса
   │  чистые есть:
   │    stable ──── липкость прежде случайности: текущий ∈ чистых?
   │    │           остаёмся : случайный из чистых (перевыборы)
   │    fastest ─── max живых побед среди чистых; ничья — липкость,
   │    │           потом случайность; побед нет ни у кого →
   │    │           ЭТОТ запрос идёт веером-выборами (single-flight:
   │    │           фанится один, конкуренты окна — к случайному
   │    │           чистому)
   │    parallel ── веер по чистым на каждый запрос, без выбора;
   │                побед не пишет
   ▼
ОДИНОЧНЫЙ ОБМЕН с целью
   │  цель получает ПОД-ДЕДЛАЙН — половину остатка бюджета запроса:
   │  вееру ГАРАНТИРОВАН остаток (иначе цель-blackhole съедает всё
   │  и веер стартует мёртвым)
   ├─ успех ────────────────► ОТВЕТ  (+ ошибки цели стёрты)
   ▼ ошибка → запись ошибки цели
чистые остались? ── нет ──► ОШИБКА РЕЗОЛВА
   ▼ да
ВЕЕР — только по ЧИСТЫМ (без сбойнувшей цели), под ctx запроса
   ├─ первый успех ──► ОТВЕТ; победителю — победа (кроме parallel)
   └─ все сбойнули ──► ОШИБКА РЕЗОЛВА
   guard: при исчерпанном бюджете запроса ошибки участникам веера
          НЕ пишутся (травится только цель, а не вся группа)
   опоздавшие живые ответы: отбрасываются, в кеш не идут,
          но живые ошибки своего сервера стирают
```

Веер — единственный источник побед и групповых проб. Таймеров нет нигде:
нет трафика — нет активности (инвариант [ENERGY](../ENERGY/FEATURE.md)).
Ритм переизбрания `fastest` задаёт `win_ttl`: победы истекли → следующий
запрос становится веером-выборами.

## Восстановление после «всё лежит»

Сервис и стратегия восстанавливаются в разные моменты:

- **Путь 1 — смена сети** (основной): событие интерфейса → амнистия таблиц
  → все чистые → штатная работа немедленно (в `fastest` первый запрос —
  веер-выборы).
- **Путь 2 — дренаж по TTL** (сеть моргнула без события): первый запрос
  после оживления попадает к наименее грязному → успех **стирает его
  ошибки** → он чистый, липкость держит его — **ответы идут с первого
  запроса**. Остальные дренируются за `error_ttl`. В `fastest`
  задерживается только оптимальность (выбор быстрейшего) — не более чем
  на `error_ttl`; побед ни у кого нет → выборы при первом запросе после
  дренажа.

Ускоритель «успех грязного → внеочередные выборы» отвергнут: флаппер
превращает его в генератор вееров.

## Правила и гарантии

- **Сбой — это транспортная ошибка, таймаут или `SERVFAIL`.** `NXDOMAIN`
  и пустой ответ — валидные ответы: переспрашивать их у другого сервера
  значит превращать резолв в лотерею.
- **Победа только соревновательная.** Штатный успех текущего не считается —
  иначе он самоусиливается и не переизбирается никогда.
- **Анти-шторм.** Чистых нет → одна попытка к наименее грязному, веера
  запрещены. «Никогда не отказывать» сохраняется за цену одной попытки.
- **Веер только по чистым** и только под бюджетом запроса; цель получает
  половину остатка бюджета, веер — гарантированный остаток; при исчерпанном
  бюджете ошибки участникам веера не пишутся.
- **Выборы `fastest` — single-flight**: одновременно фанится один запрос,
  конкуренты окна уходят к случайному чистому. Бёрст не порождает стада
  вееров ни на холодном старте, ни на истечении `win_ttl`.
- **Группа — полноправный сервер.** Тег принимается в `final`, правилах,
  `servers` другой группы. Вложенность разрешена, циклы — ошибка загрузки.
  Внутренняя группа для внешней — один участник: одна попытка, один исход,
  одна запись; внутренний веер снаружи невидим.
- **Состав** — только серверы с реальным сетевым обменом; `fakeip`/`hosts` —
  ошибка загрузки. `servers` непуст (и `[]` — ошибка).
- **Кеш** — без изменений: кешируется только отданный группой ответ
  (кеш выше группы, ключ — тег группы); опоздавшие ответы веера в кеш
  не попадают.
- **Наблюдаемость** — через [OBSERVABILITY](../OBSERVABILITY/FEATURE.md):
  фактически ответивший участник (лист при вложенности; кеш-попадание
  и полный сбой — тег группы); трасса проб (путь групп изнутри наружу,
  хронология с исходами и rtt); признаки «запрос-с-веером» и «режим
  выживания» (без него деградация невидима в потоке); состояние группы
  по запросу (`GetDNSGroups`): режим, текущая цель, по участникам —
  чистота, живые ошибки (счёт + возраст последней), живые победы,
  последний rtt; лог решений: ошибка/веер/победитель — debug, смена
  текущего — info, «все сбойнули» — warn.

## Границы

- **Порядок `servers` не значим.** Семантика «первый — основной, остальные
  резерв, возврат к первому после выздоровления» невыразима ни в одном
  режиме — группа для равноправных серверов.
- **Per-query-ротации нет.** Случайность работает на перевыборах, не на
  каждом запросе: приватностного размазывания истории по резолверам
  и балансировки нагрузки режимы не дают (вернётся отдельным режимом,
  если понадобится — поле `mode` расширяемо).
- **Утечка имён — свойство группы, не режима.** Любой режим при сбое шлёт
  имя запроса всем чистым, `parallel` — каждым запросом. Единственная
  изоляция — не смешивать внутренние и публичные серверы в одной группе.
- **Быстрый лжец.** `fastest` меряет скорость, не качество: перехватывающий
  резолвер с мгновенными ответами — вечный победитель. Фильтрация лжецов —
  вне модели.
- **`parallel` дорог по определению**: N× трафика на каждый запрос
  и полное обнуление сна DNS-детуров ([ENERGY](../ENERGY/FEATURE.md)) —
  режим для тех, кто это осознанно покупает.
- **Таймаут цели — дорогой путь**: запрос платит долю бюджета цели, потом
  веер. Упреждающий hedged-веер (по порогу ~300ms) — возможное расширение,
  не MVP.
- **Амнистия приходит не на всех классах смен сети** — дренаж по TTL
  не редкость, а рабочая страховка; его цена — до `error_ttl`
  неоптимальности при живом сервисе.
- **Не заменяет rule-level `race`/`evaluate` upstream.** Upstream
  оркеструет запросы внутри одного резолва без памяти между запросами;
  группа — сервер с памятью (TTL-записи). Слои не пересекаются.

## Особенности сопровождения

- **SERVFAIL и DNSSEC.** Валидирующий резолвер отвечает `SERVFAIL`
  на сломанную подпись — веер на невалидирующий сервер молча обходит
  защиту. Не смешивать валидирующие и невалидирующие серверы, если DNSSEC
  важен.
- **Опоздавшие ответы веера — граница кеша.** Инвариант «кешируется только
  отданный ответ» проверять живым запуском с медленным участником.
- **Ленивая семантика — инвариант энергосбережения.** Любое «улучшение»
  с таймером (фоновые пробы, периодические выборы) — регресс.
- **Семантику списочного `servers` проверять живым запуском** (badjson
  схлопывает `[]` в nil).
- **Пустые поля наблюдаемости — состояние, а не поломка** (нет текущего
  до первого запроса, нет побед до первого веера).
