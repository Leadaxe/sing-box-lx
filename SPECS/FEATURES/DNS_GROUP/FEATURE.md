# FEATURE: DNS_GROUP — группа DNS-серверов с резервированием

| Поле | Значение |
|------|----------|
| Тип | Продуктовая фича |
| Build-tag | — (для выдачи состояния группы в UI нужен `with_lx_command`) |
| Состояние | ✅ Реализовано, проверено тестами (юниты + живой `box.New`; полевой проверки не было) |

## Назначение

Сегодня сбой одного DNS-сервера роняет резолв целиком, даже если в конфиге
есть другие рабочие серверы. `dns.final` — это сервер **по умолчанию**,
а не резервный: запрос, направленный правилом в конкретный сервер, при его
сбое получает ошибку без повторной попытки. Единственный существующий
повтор срабатывает, когда ответ пришёл, но не прошёл фильтр адресов;
сетевые ошибки, таймауты и `SERVFAIL` повтора не имеют.

Фича добавляет тип DNS-сервера `group`: несколько серверов под одним тегом
со стратегией выбора. Группа встаёт всюду, где принимается тег сервера —
и в `final`, и в правилах, — и закрывает оба пути одним механизмом,
не трогая схему DNS-правил. Форма симметрична группам outbound'ов
(`urltest` поверх узлов) — группа поверх DNS-серверов.

## Контролируемые параметры

Блок в списке DNS-серверов:

```json
{
  "type": "group",
  "tag": "public",
  "servers": ["google", "cloudflare"],
  "mode": "failover",
  "interval": "3m",
  "down_time": "30s"
}
```

| Ключ | Тип | Дефолт | Смысл |
|------|-----|--------|-------|
| `servers` | список тегов | обязательное | Серверы группы. Порядок значим: для `failover` это порядок опроса |
| `mode` | `failover` · `race` | `failover` | `failover` — по списку сверху вниз до первого ответившего; `race` — периодическая гонка всех серверов на реальном запросе, трафик идёт победителю |
| `interval` | длительность | `3m` | Минимальный возраст прошлой гонки, после которого следующий запрос запускает новую. **Только для `race`**; в `failover` игнорируется с предупреждением в лог |
| `down_time` | длительность | `30s` | Сколько сбойный сервер не опрашивается. По истечении возвращается в строй |

### Почему `interval` и `down_time` — разные поля

Это два разных смысла, нужных **одновременно**: даже в режиме `race`
сбойный сервер надо временно исключать из гонок, иначе каждая гонка
ждёт его таймаут. Одно поле с двумя значениями в зависимости от режима —
ловушка: по конфигу не понять, что означает число. Прецедент в форке:
в `urltest` поле `tolerance` игнорируется в режиме `round_robin`
с предупреждением, а для второго режима заведено отдельное `pool_tolerance`
(см. [URLTEST_BALANCE](../URLTEST_BALANCE/FEATURE.md)).

### Сборка

Build-tag не вводится. Новый тип сервера аддитивен: конфиг без `group`
ведёт себя в точности как upstream, изоляция достигается самим типом —
код группы не участвует в пути запроса, пока группа не объявлена.
Выдача состояния группы клиентскому приложению — часть
[OBSERVABILITY](../OBSERVABILITY/FEATURE.md) и живёт за её тегом
`with_lx_command`.

## Входы

- **Конфиг** — блок группы выше.
- **DNS-запросы**, адресованные тегу группы: из правил, из `final`,
  из другой группы.
- **Ответы и ошибки** серверов-участников.

## Выходы

- **DNS-ответ** одного из серверов группы; кешируется штатно, независимо
  от того, какой участник ответил.
- **Ошибка резолва**, если ответа не дал ни один опрошенный сервер.
- **Наблюдаемость**: тег **фактически ответившего** сервера в потоке
  DNS-запросов и состояние группы (победитель, рейтинг, кто в `down_time`)
  для UI — через [OBSERVABILITY](../OBSERVABILITY/FEATURE.md).

## Data flow

### `failover`

```
запрос → первый сервер списка, не отмеченный down
             │ ответ (в т.ч. NXDOMAIN, пустой) ──► ответ запроса
             │ сбой (сеть / таймаут / SERVFAIL)
             ▼
        пометить сервер down на down_time
             │
             ▼
        следующий сервер списка … (тот же цикл)
             │ весь список в down_time
             ▼
        сервер с самым давним сбоем — ровно одна попытка
             │ сбой ──► ошибка резолва; метка сбоя обновлена,
             │          следующий запрос возьмёт следующего по давности
```

### `race`

```
первый запрос после того, как прошлой гонке исполнился interval
        │
        ▼  веером на все серверы группы, не отмеченные down
первый успешный ответ ──► ответ запроса; его сервер — победитель
порядок прихода остальных ответов ──► рейтинг (запасной порядок)
опоздавшие ответы выбрасываются и в кеш не попадают
        │
между гонками: запросы идут победителю;
его сбой → следующий по рейтингу (по правилам failover)
```

Гонок по таймеру **нет**: `interval` — минимальный возраст прошлой гонки,
а не расписание. Нет трафика — нет гонок и нет фонового расхода
(требование [ENERGY](../ENERGY/FEATURE.md) к периодическим механизмам).
Запрос-гонщик ничего не теряет — он получает первый пришедший ответ,
то есть быстрее обычного.

## Правила и гарантии

- **Сбой — это транспортная ошибка, таймаут или `SERVFAIL`.**
  `NXDOMAIN` и пустой ответ — валидные ответы «домена/записи нет»,
  а не сбой: переспрашивать их у другого сервера значит получать разные
  ответы от разных резолверов и превращать резолв в лотерею.
- **Один сбой переводит сервер в `down_time`.** Просто и предсказуемо;
  цена ошибочной пометки мала — по истечении срока сервер возвращается
  в строй без каких-либо проверок.
- **Полное исчерпание не означает мгновенный отказ.** Когда все серверы
  в `down_time`, каждый новый запрос пробует ровно один сервер — тот,
  чей сбой самый давний. Неудача обновляет его метку, поэтому следующие
  запросы естественно ротируются по остальным. Цена одного запроса
  ограничена одной попыткой, а не суммой всех таймаутов.
- **Группа — полноправный сервер.** Её тег принимается везде, где
  принимается тег DNS-сервера: в `final`, в правилах, в `servers`
  другой группы.
- **Вложенность разрешена, циклы отвергаются при загрузке.** Группа,
  прямо или через цепочку ссылающаяся на себя, — ошибка конфига,
  а не зацикливание в рантайме. Внешняя группа видит внутреннюю как один
  сервер: всё её внутреннее время — одна попытка внешней.
- **В группу принимаются только серверы с реальным сетевым обменом.**
  `fakeip` и `hosts` — локальные источники, сбоить и резервироваться
  им нечем; их присутствие в `servers` — ошибка загрузки.
- **Кеш один и тот же для всех участников.** Ответ резервного сервера
  кешируется так же, как основного. В `race` кешируется **только ответ
  победителя**; опоздавшие выбрасываются — иначе в кеше окажутся
  вперемешку ответы разных резолверов.
- **`interval` вне `race` — предупреждение, не ошибка.** Значение
  игнорируется, в лог пишется предупреждение.
- **В потоке DNS-запросов — фактический сервер, не группа.** Запись
  несёт тег участника, который реально ответил; иначе диагностика
  «какой из серверов группы деградировал» невозможна.

## Границы

- **Failover последователен.** Запрос, обнаруживший сбой, платит полный
  таймаут упавшего сервера, прежде чем перейти к следующему; группа
  не переопределяет таймауты участников. Платит только «невезучий»
  запрос — последующие идут мимо помеченного сервера сразу.
  Режим `race` лишён этой платы по построению.
- **Ответы не сравниваются.** Берётся первый успешный; группа не выбирает
  «лучший» ответ по содержимому и не замечает расхождений между серверами.
- **Это не балансировщик.** Ни весов, ни распределения нагрузки;
  приоритет задаётся только порядком списка (`failover`)
  или рейтингом гонки (`race`).
- **Утечка имён.** При failover запрос уходит следующему серверу группы,
  а в `race` каждый запрос-гонщик уходит **всем** серверам сразу. Группа
  из внутреннего сервера и публичного резерва отправит внутреннее имя
  наружу. Рекомендация: не смешивать внутренние и публичные серверы
  в одной группе.
- **Параллельного режима опроса нет.** `mode: parallel` (веером на каждый
  запрос, а не раз в `interval`) — возможное расширение; поле `mode`
  заведено так, чтобы оно не потребовало переименований.
- **Не заменяет rule-level `race`/`evaluate` upstream.** Upstream 1.14
  умеет оркестровать запросы внутри одного резолва флагами правил —
  без памяти между запросами: каждый запрос платит гонку или таймаут
  заново. Группа — сервер с памятью здоровья (`down_time`, победитель
  между гонками); механизмы живут на разных слоях и не пересекаются.

## Особенности сопровождения

- **SERVFAIL и DNSSEC.** Валидирующий резолвер отвечает `SERVFAIL`
  на сломанную подпись — failover на невалидирующий сервер молча обходит
  эту защиту. Пользователю, которому важен DNSSEC, нельзя смешивать
  валидирующие и невалидирующие серверы в одной группе.
- **Опоздавшие ответы гонки — граница кеша.** Инвариант «кешируется только
  победитель» проверять живым запуском с медленным участником, а не только
  юнит-тестом: смешение ответов разных резолверов в кеше проявляется
  как редкие «не те» адреса.
- **Ленивая семантика `interval` — инвариант энергосбережения.** Гонка
  только по приходу трафика; любое «улучшение» с таймером — регресс:
  серверы за прокси-цепочками будят спящие узлы
  (см. [ENERGY](../ENERGY/FEATURE.md)).
- **Семантику списочного `servers` проверять живым запуском.** Разбор
  конфига схлопывает пустой список в «ключ не задан» — ошибка
  «`servers` обязателен» должна срабатывать и на `[]`, и юнит-тест
  на прямом разборе этого не показывает
  (грабля из [URLTEST_BALANCE](../URLTEST_BALANCE/FEATURE.md)).
- **Пустые поля наблюдаемости — состояние, а не поломка.** До первой
  гонки у группы `race` нет ни победителя, ни рейтинга — это валидное
  состояние, а не рассинхрон версий.
