# FEATURE 006 — OBSERVABILITY — канал управления и наблюдения для UI

| Поле | Значение |
|------|----------|
| Тип | Продуктовая фича (контракт с клиентским приложением) |
| Build-tag | `with_lx_command` |
| Потребитель | **LxBox** (Android-клиент) |
| Состояние | ✅ Работает на устройстве |

## Назначение

Приложению нужно показывать живое состояние ядра — узлы, правила, соединения,
DNS-запросы — и управлять им. Штатный канал для этого (REST-интерфейс
в стиле Clash) требует открытого HTTP-порта и не даёт потокового обновления.

Фича переводит управление на протокол libbox, встроенный в саму библиотеку,
и расширяет его тем, чего в нём не было: адресный опрос узлов, выдача
групп и правил, состав пула балансировки, цепочка проксирования соединения
и живой поток DNS-запросов.

## Контролируемые параметры

Конфиг-ключей у фичи нет: контракт — это набор вызовов и полей протокола.

### Сборка

| Ручка | Значение |
|-------|----------|
| `with_lx_command` | Включает расширения протокола. Без тега доступен только базовый набор вызовов |
| `with_clash_api` | REST-интерфейс. ⚠️ **Выключается только в мобильной библиотеке.** Сборки для десктопа и CLI обязаны его сохранять — ими управляют внешние панели |

### Вызовы

| Вызов | Что возвращает |
|-------|----------------|
| `URLTestOutbound` | Замер задержки **конкретного узла** (не всей группы), отменяемый |
| `GetGroups` · `GetOutbounds` | Группы и узлы для экранов выбора |
| `GetRules` | Правила маршрутизации |
| `GetPool` | Занятые слоты пула — см. [URLTEST_BALANCE](../007-URLTEST_BALANCE/FEATURE.md) |
| `GetDNSGroups` | Состояние DNS-групп: режим, победитель, рейтинг, down-участники — см. [DNS_GROUP](../013-DNS_GROUP/FEATURE.md) |
| `GetRunningConfig` | Канонический JSON конфига, из которого реально построено работающее ядро (post-override снапшот старта). Источник правды при рассинхроне профиль↔ядро; JSON отдельного узла приложение вырезает из него по тегу |
| `GetURLViaOutbound` | HTTP GET по произвольному URL **через конкретный узел** (outbound или endpoint) с возвратом тела ответа — диагностический пробник: exit-IP, гео, `warp=` и любой другой текстовый эндпоинт |
| `SubscribeDNSQueries` | Подписка на поток DNS-запросов |
| `GetChains` | Состояние каждого outbound'а `chain`: позиции, разрешённый узел, звено (состояние, соединения, MTU, что снято/переписано), счётчики — см. [CHAIN](../015-CHAIN/FEATURE.md) |

### Поля соединения

| Поле | Смысл |
|------|-------|
| `detourList` | Хвост проксирования финального узла — **отдельным полем**; основная цепочка его намеренно не включает |

### Записи потока DNS

| Поле | Смысл |
|------|-------|
| Домен, тип запроса | Что спрашивали |
| Код ответа | Результат резолва; **`-1` означает «ответа не было вовсе»** (таймаут, сетевая ошибка) — это отдельное значение, а не общий код ошибки |
| Признак сбоя и его причина | Единственный надёжный способ отличить неудачу: часть сбоев (например SERVFAIL) приходит с **реальным** кодом ответа, а не с `-1` |
| Цепочка ответов | Полный путь через промежуточные имена (CNAME) |
| Процесс-инициатор | Кто спросил |
| Сервер и его тип | Куда ушёл запрос; для группы — **фактически ответивший участник** (лист при вложенности), кеш-попадание и полный сбой несут тег группы |
| Узел | Через что ушёл; **пустое значение = напрямую** |
| Путь групп | Изнутри наружу; **пусто = запрос шёл мимо группы** — см. [DNS_GROUP](../013-DNS_GROUP/FEATURE.md) |
| Хронология проб | Опрошенные участники группы по порядку: исход (`answered`/`timeout`/`network_error`/`servfail`) и rtt; снимок на момент записи — опоздавшие ответы гонки не входят |
| Признак гонщика | Этот запрос запустил гонку группы |

## Входы

- **Запросы от приложения** — вызовы и подписки выше.
- **События ядра** — установка и закрытие соединений, DNS-запросы,
  результаты замеров.

## Выходы

- **Ответы на вызовы** и **потоки событий** в приложение.
- **Состояние соединений** с цепочкой проксирования.

## Data flow

```
приложение ──вызов/подписка──► ядро
                                 │
     события ядра (соединения, DNS, замеры)
                                 │
приложение ◄──ответ / поток──────┘
```

Обмен идёт по одному мультиплексированному каналу — отдельного сетевого
порта фича не открывает.

## Правила и гарантии

- **Пустое поле — это состояние, а не отсутствие данных.** Пустой узел
  в записи DNS означает «запрос ушёл напрямую» и является нормальным
  значением. Прежде чем искать поломку в ядре или подозревать рассинхрон
  версий библиотеки, сверься с семантикой поля.
- **Ошибки DNS попадают в поток наравне с успехами** — по признаку сбоя,
  а не по коду ответа: `-1` означает лишь «ответа не было», тогда как
  отклонённый ответ несёт свой настоящий код. Отсутствие записи означает,
  что запроса не было, а не что он не удался.
- **Замер отдельного узла отменяем**: клиент, закрывший запрос,
  останавливает и сам замер. То же верно для HTTP-пробника.
- **Для пробника ответ сервера — всегда результат, а не ошибка.** Любой
  HTTP-статус (403, 500, редирект-цепочка, упёршаяся в лимит) возвращается
  клиенту как данные; ошибкой считается только несостоявшийся обмен:
  тег не найден, dial/TLS не удался, таймаут.
- **Тело пробы ограничено.** Ядро отсекает тело по запрошенному лимиту
  с явным признаком обрезки; у лимита есть дефолт и жёсткий потолок —
  заказать неограниченную загрузку в память нельзя.
- **Проба — реальный трафик через реальный узел** (на лимитных узлах —
  расход, на спящих WG — пробуждение). Вызывается только по явному
  действию пользователя; фоновые периодические обходы узлов пробником
  запрещены на стороне клиента.
- **Цепочка проксирования и её хвост разделены** намеренно — приложение
  собирает отображение само.

## Границы

- **Перехваченные DNS-запросы не попадают в учёт соединений** — они
  обрабатываются раньше точки учёта соединений. В DNS-поток они попадают
  и составляют его основную массу (на мобильном VPN — большинство запросов):
  процесс-инициатор определяется до перехвата специально ради этого.
- **Фича не хранит историю.** Поток отдаёт события с момента подписки;
  накопление — задача приложения.
- **Переподключение подписки — обязанность клиента.** Ядро не восстанавливает
  оборванные подписки самостоятельно.
- **Пробник — только GET.** Произвольные методы и тела запросов намеренно
  не экспортируются: это диагностический инструмент, а не HTTP-клиент
  общего назначения; расширение поверхности — отдельное решение, не
  «доделка» этого вызова.
- **Ядро не интерпретирует тело пробы.** Парсинг форматов внешних сервисов
  (`cdn-cgi/trace`, гео-JSON) — сторона приложения; смена формата чужого
  сервиса не является багом ядра и не требует его релиза.
- **Пробник не отвечает на вопрос «через что я хожу сейчас».** Состояние
  туннеля целиком (реальный маршрут с правилами, sniff, выбором группы)
  проверяется обычным запросом с устройства при поднятом VPN; RPC говорит
  только о свойствах отдельного узла.

## Особенности сопровождения

- **Два набора сборки расходятся намеренно.** Мобильная библиотека
  и десктоп имеют разный состав; правка «для единообразия» ломает
  внешние панели — это уже происходило.
- **Часть жалоб «ядро молчит» — клиентские.** Замолкающий поток однажды
  оказался отсутствием переподключения на стороне приложения при полностью
  исправном ядре.
- **Регенерация протокола тянет посторонние правки** — в коммит должно
  попадать только относящееся к задаче.
- **Вызов не возвращает текст или байты напрямую.** Значение отдаётся
  объектом с геттером, даже когда наружу нужен ровно один документ.
  Прямой возврат текста разрушает мобильный процесс при каждом вызове —
  не в редком случае, а всегда; проверено полем и генерацией моста
  ([038](../../TASKS/038-GOMOBILE_STRING_RETURN_FRAME_KILL/SPEC.md)).
  Сборка и тесты этого не ловят: дефект возникает только в мобильной
  библиотеке на устройстве.
