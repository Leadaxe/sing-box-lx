# FEATURE 021 — PLUGINS — протоколы отдельной программой рядом с ядром

| Поле | Значение |
|------|----------|
| Тип | Продуктовая фича |
| Build-tag | `with_lx_plugin` (рабочее имя) |
| Состояние | Идея (2026-11-26). Работа — после пятницы 2026-11-27, решение владельца. Задач нет, кода нет; тест [§3.1 CONSTITUTION](../../CONSTITUTION.md) не пройден |

## Назначение

Пользователи регулярно просят протоколы, которых нет ни в апстриме, ни у нас. Пример — mieru:
о нём спрашивают в чате поддержки, запросы в LxBox
([#204](https://github.com/Leadaxe/LxBox/issues/204), [#216](https://github.com/Leadaxe/LxBox/issues/216))
закрыты как not planned. Тащить каждый такой протокол в ядро дорого: у каждого своя зона мержа,
свои зависимости, своя поддержка.

Фича даёт один механизм вместо N протоколов: протокол живёт в **отдельной программе — плагине**,
которую ядро запускает само. Пользователь кладёт файл плагина в каталог плагинов, записывает его в `lx.plugins.list` с суммой
файла и пишет в конфиге
`"type": "mieru"` так же, как `"type": "vless"`, и всё работает так, будто тип собран в ядре:
группы, `urltest`, пул, цепочки, `detour`, правила, статус, логи.

Плагин ничего не знает о внутренностях sing-box. Он говорит с ядром по узкому публичному протоколу
и получает от ядра уже открытые соединения. Сокеты к сети держит ядро. Плагин пишется на любом
языке, собирается и обновляется отдельно от ядра.

## Термины

- **Ядро** — sing-box-lx, процесс-хозяин.
- **Плагин** — исполняемый файл, отдельный процесс.
- **Тип плагина** — имя, которое плагин объявляет (`mieru`), и его род: `outbound`, `endpoint`
  или `inbound`. Один плагин может дать несколько типов.
- **Экземпляр** — один объект конфига с таким типом (`"tag": "mieru-nl"`).
- **Канал управления** — пара сокетов «ядро ↔ плагин», которую ядро создаёт при запуске плагина.
- **Канал пакетов** — отдельная пара сокетов на экземпляр рода `endpoint` или пакетного `inbound`.

## Общая схема

```
                   процесс ядра                                     процесс плагина
 ┌───────────────────────────────────────────────────┐          ┌─────────────────────────────┐
 │                                                   │ канал    │                             │
 │  конфиг ─► менеджер плагинов ─────────────────────┼─управл.──┼─► протокол плагинов         │
 │              │ регистрирует типы                  │          │   (рукопожатие, экземпляры, │
 │              ▼                                    │          │    статус, логи)            │
 │   роутер ─► экземпляр `mieru` ────────────────────┼── fd ────┼─► логика протокола mieru    │
 │   группы     (для ядра — обычный outbound)        │          │   (рукопожатие, шифрование, │
 │   urltest                                         │          │    кадры)                   │
 │              ┌────────────────────────────────────┼◄─DIAL────┤                             │
 │              ▼ сервисы ядра для плагина           │          │                             │
 │   outbound / detour ─► сеть                       │── fd ───►│  поток к серверу mieru      │
 └───────────────────────────────────────────────────┘          └─────────────────────────────┘
```

Ядро держит всё, что касается сети и маршрутизации. Плагин занят только преобразованием данных.

## Контролируемые параметры

### Откуда запускаются плагины

Плагины лежат в **каталоге плагинов**. Ядро запускает только файлы из него. Задаётся каталог двумя
способами:

| Ключ | Что задаёт | По умолчанию |
|---|---|---|
| переменная окружения `LX_PLUGINS_DIR` | каталог плагинов, заданный стороной, которая запускает ядро | нет |
| `lx.plugins.dir` (корень конфига) | каталог плагинов из конфига | нет |
| `lx.plugins.list[]` | записи о плагинах: по одной на файл | нет |
| `lx.plugins.list[].file` | **обязательный.** Имя файла в каталоге плагинов, по шаблону `lx-plugin-*` | — |
| `lx.plugins.list[].sha256` | **обязательный.** Сумма SHA-256 файла; ядро сверяет её перед каждым запуском, несовпадение — ошибка старта | — |
| `lx.plugins.list[].args`, `env` | аргументы и окружение запуска | нет |
| `lx.plugins.list[].restart` | `always` / `never` | `always` |
| переменная окружения `LX_PLUGINS=off` | выключить плагины, что бы ни было в конфиге | включены |
| build-tag `with_lx_plugin` | есть ли механизм в сборке | обсуждается: в `LX_TAGS` и в AAR |

Правила каталога:

1. Задана `LX_PLUGINS_DIR` — это каталог. `lx.plugins.dir` из конфига тогда может указывать только
   внутрь него; путь наружу — ошибка старта. Так запускающая сторона (лаунчер, LxBox, `lxd`,
   init-скрипт) закрепляет каталог, и чужой конфиг не запустит программу из другого места.
2. `LX_PLUGINS_DIR` не задана — действует `lx.plugins.dir`. Это режим для того, кто сам пишет свой
   конфиг и запускает ядро из CLI.
3. Не задано ни то, ни другое — плагинов нет; тип плагина в конфиге — ошибка «unknown type» с
   подсказкой про каталог.

4. **Имя файла — всегда по шаблону** `lx-plugin-*` (`.exe` на Windows), в том числе в
   `list[].file`; имя с `/` или `..` — ошибка старта. Без этого правила конфиг
   с `dir: "/bin"`, `file: "sh"` и `args` запускал бы что угодно, в том числе на `sing-box check`.

Конфиг бывает чужим (удалённый профиль, присланный JSON), а `sing-box check` тоже запускает плагин.
С правилом 4 чужой конфиг может запустить только файл, который кто-то уже положил на диск под
именем `lx-plugin-*`. Сторона, которая грузит чужие конфиги, дополнительно закрепляет каталог
через `LX_PLUGINS_DIR`.

5. **Каждый плагин записан явно.** Ядро запускает только файлы из `lx.plugins.list`, и только если
   сумма совпала. Каталог не обходится, файлы без записи не запускаются. Запись без `file` или без
   `sha256` — ошибка старта.

**Откуда ядро знает типы.** Ядро запускает каждый плагин из списка, и плагин сам называет свои типы
в `MANIFEST`. Один файл может дать несколько типов; процесс при этом один. Два плагина с одним типом
— ошибка старта. Плагин из списка, чьи типы в конфиге не встретились, всё равно запускается и
проходит рукопожатие: так ошибка в списке видна сразу, а не при первом использовании.

```json
"lx": { "plugins": {
  "dir": "/opt/sing-box/plugins",
  "list": [ { "file": "lx-plugin-mieru",
              "sha256": "9f2c…e41a" } ]
} }
```

Порядок поиска типа: встроенные типы → плагины. Встроенный тип плагин не переопределяет:
совпадение имени — ошибка старта.

### Объект экземпляра

Тип плагина пишется там же, где встроенные:

```json
{
  "type": "mieru", "tag": "mieru-nl",
  "detour": "o-ru",                          ← ключ ядра
  "bind_interface": "wwan0",                 ← ключ ядра
  "server": "nl.example.com",                ← ключи плагина
  "port_range": "2012-2022",
  "transport": "TCP",
  "username": "u", "password": "p"
}
```

- **Ключи ядра** — `type`, `tag` и ключи соединения, как у `direct` (`detour`, `bind_interface`,
  `routing_mark`, `connect_timeout`, `domain_resolver`, …). Их разбирает ядро, плагин их не видит.
  Через них работают цепочки (перезапись `detour`, [FEATURE 015](../015-CHAIN/FEATURE.md)) и всё
  остальное, что ядро делает с соединениями.
- **Ключи плагина** — всё остальное. Ядро передаёт их плагину как есть; плагин проверяет их и
  отвечает ошибками с путём ключа. Набор ключей mieru выше — иллюстрация, он принадлежит плагину.
- Плагин может сослаться на другой outbound ядра по тегу. Какие ключи — ссылки, плагин объявляет
  в манифесте; ядро проверяет, что тег есть, и учитывает ссылку в порядке старта.

*Предположения, не сверенные с кодом* (проверяются в PLAN первой задачи): что парсер опций ядра
позволяет тип «ключи соединения + остальное сырым JSON» (сейчас типы разбираются строго по
структуре); что перезапись `detour` цепочками ([SPEC 165](../../TASKS/165-CHAIN_DETOUR_REWRITE/SPEC.md))
берёт `detour` через общий интерфейс ключей соединения и поэтому подхватит тип плагина.

## Входы

- Конфиг: `lx.plugins`, объекты экземпляров.
- `LX_PLUGINS_DIR`, `LX_PLUGINS`; каталог плагинов и файлы в нём.
- Трафик от роутера: соединения и пакеты, которые маршрутизация отправила в экземпляр.
- От плагина: запросы на соединения, потоки и пакеты к роутеру, статус, логи.
- События ядра: смена сети, пауза и пробуждение ([FEATURE 008](../008-ENERGY/FEATURE.md)),
  перезагрузка конфига.

## Выходы

- Обычный outbound / endpoint / inbound для всего ядра.
- Статус экземпляра по тегу — унарный `GetPluginStatus(tag)`, как статусы WG и MASQUE.
- Логи плагина в логе ядра с префиксом тега.
- Счётчики, присланные плагином (байты и ошибки по его соединениям к серверу), — в статусе.
- Понятные ошибки старта: нет файла, каталог вне `LX_PLUGINS_DIR`, сумма не та, версия протокола
  плагинов не та, плагин отверг опции.

## Data flow

### Запуск

```
ядро                                              плагин
  │ читает конфиг: какие типы неизвестны
  │ для каждой записи `lx.plugins.list`: сверяет sha256 файла
  │ создаёт пару сокетов, запускает файл ───────────►  (fd 3 = канал управления)
  │ ◄──────────────────────────────────────────────── HELLO: версия протокола, имя, версия плагина
  │ ◄──────────────────────────────────────────────── MANIFEST: типы, роды, сети, ключи-ссылки
  │ сверяет версию, регистрирует типы
  │ разбирает конфиг целиком
  │ CHECK(тип, ключи плагина) ─────────────────────►
  │ ◄──────────────────────────────────────────────── OK | ошибки с путями ключей
  │ CREATE(экземпляр, тег, ключи) ─────────────────►
  │ START ─────────────────────────────────────────►
  │ ◄──────────────────────────────────────────────── READY
  ▼ ядро стартует дальше
```

Плагин запускается до разбора конфига: парсеру нужно знать тип. Поэтому конфиг читается в два
прохода: сначала только `lx.plugins` и имена типов, затем полный разбор. `sing-box check` и проверка
конфига в LxBox тоже запускают плагин, но только до `CHECK`.

### Outbound: соединение к цели

```
 приложение ─► роутер ─► экземпляр `mieru` (ядро)
                              │ NEW_CONN(цель, сеть, метаданные) + fd клиентской стороны
                              ▼
                          плагин: «нужен поток к серверу mieru»
                              │ DIAL(через свой detour | outbound по тегу, адрес сервера)
                              ▼
               ядро открывает соединение через outbound / detour ─► сеть
                              │ DIAL_RESULT: fd потока к серверу | класс ошибки
                              ▼
                          плагин гонит данные между двумя fd по своему протоколу
```

Обе стороны плагин видит как обычные сокеты. Ядро копирует данные между настоящим соединением и
своим концом пары сокетов. Для UDP fd клиентской стороны датаграммный, у каждой датаграммы короткий
заголовок с адресом назначения: одна UDP-сессия ходит к разным адресам.

### Endpoint (L3-туннель)

Endpoint получает трафик двумя путями, как WG-endpoint сейчас: пакеты прямо из TUN и соединения
от роутера, когда трафик пришёл не из TUN (например, из `mixed`). Соединения нужно превратить в
L3-пакеты стеком TCP/IP. Где живёт этот стек — развилка:

| | Стек в плагине | Стек в ядре |
|---|---|---|
| Через границу | пакеты TUN + соединения (`NEW_CONN` с fd) | только пакеты |
| Ядро | ничего своего | свой стек в переходнике, больше кода за тегом |
| Плагин | несёт свой стек (например, gVisor — Apache-2.0) | проще |
| Линия апстрима 1.15 | не зависит | апстрим 1.15 убрал gVisor — стек ядра под вопросом |

Черновик исходит из «стек в плагине»: ядро остаётся тоньше и не зависит от судьбы gVisor в апстриме.
Плагин без своего стека объявляет в `MANIFEST` «только пакеты»: тогда ядро на соединения от роутера
в этот endpoint отвечает ошибкой, а трафик в него идёт только из TUN.

```
 TUN   ─► роутер ─► экземпляр (ядро) ══ канал пакетов (батчи) ══► плагин
 mixed ─► роутер ─► экземпляр (ядро) ── NEW_CONN + fd ──────────► стек плагина ─► пакеты
                                                                    │ шифрование, кадры
                           ┌── DIAL(через outbound / detour) ◄─────┤
                           ▼                                        │
         ядро держит соединение к серверу ─► сеть                   │
                           кадры ◄═══════ fd соединения ═══════════╯
```

### Inbound (сервер)

```
 сеть ─► слушатель ядра (адрес, порт, TLS) ─► ACCEPT: fd соединения ─► плагин
                                                                         │ рукопожатие, расшифровка
            ┌────────────────────────────────────────────────────────────┤
            ▼ потоковый вариант (прокси-протокол)                         ▼ пакетный вариант (VPN)
   ROUTE_CONN(цель, пользователь) + fd                         стек плагина ─► ROUTE_CONN по
   ─► роутер ядра ─► правила ─► outbound                       потокам ─► роутер ─► правила ─► outbound
```

Слушает ядро. Ключи ядра у inbound-типа — стандартные ключи слушателя (`listen`, `listen_port`,
`tcp_fast_open`, `tcp_multi_path`, `udp_timeout`, …) и необязательный стандартный блок `tls`
входящего TLS. Блок `tls` разрешён, только если плагин объявил это в `MANIFEST`: протоколы со своим
TLS-подобным рукопожатием его не берут. Мультиплексирование — забота плагина. Плагин получает уже
принятые (и, при блоке `tls`, расшифрованные) соединения.
Для пакетного варианта та же развилка про стек: в плагине — каждый поток к роутеру идёт через
`ROUTE_CONN` своим fd; в ядре — плагин отдаёт пакеты, ядро разбирает их само. Выбор — по замеру.

## Каналы и передача данных

| Что | Как | Почему |
|---|---|---|
| Управление | пара сокетов, унаследована при запуске (fd 3) | нет пути в файловой системе, чужой процесс не подключится |
| Поток (TCP-подобный) | отдельный fd на поток | управление потоком делает ОС, медленный поток не тормозит остальные |
| Датаграммы одного соединения к серверу | отдельный fd, границы датаграмм сохранены | — |
| Пакеты L3 | канал пакетов на экземпляр, батчи | одна запись на много пакетов |

**Батчи без таймера.** Запись забирает всё, что сейчас стоит в очереди. Если в очереди один пакет,
он уходит сразу, задержки нет. Под нагрузкой батч набирается сам из пакетов, которые и так ждали.
Таймеры сборки батча запрещены: они поднимают пинг.

**Отдача настоящего сокета.** Если соединение к серверу идёт через чистый `direct` без обёрток,
ядро отдаёт плагину сам сокет — уже с `bind_interface`, `routing_mark` и `protect()` на Android.
Остаётся одна граница вместо двух, работает offload ОС. Если в пути есть что-то, что трогает байты
(`impair`, прокси-протокол, TLS ядра, хоп цепочки), сокет не отдаётся: плагин пошёл бы мимо
обёртки, и она молча перестала бы работать.

**Бюджет fd.** Отдельный fd на поток — это +2 fd в ядре и +1 в плагине на соединение. На роутерах
лимит открытых файлов поднимается при запуске (`lxd`, init-скрипт) и проверяется под нагрузкой.
Если упрётся — мультиплексирование потоков в одном канале с окнами; это запасной вариант, он
сложнее.

**Общая память** — возможная замена канала пакетов, если замер покажет, что батчей мало: оба
процесса отображают один кусок памяти с кольцом ячеек и будят друг друга, только когда кольцо было
пустым. Протокол плагинов от этого не меняется.

**Windows.** fd передаётся дублированием хендла в процесс плагина; канал управления — AF_UNIX или
пара анонимных каналов. Детали — в PLAN.

## Сообщения протокола плагинов (смысл, не формат)

| Направление | Сообщение | Смысл |
|---|---|---|
| П → Я | `HELLO` | версия протокола, имя и версия плагина |
| П → Я | `MANIFEST` | типы, роды, поддержка TCP/UDP, какие ключи — ссылки на outbound |
| Я → П | `CHECK` / `CREATE` / `START` / `CLOSE` | жизненный цикл экземпляра |
| Я → П | `NEW_CONN` | новое соединение в экземпляр, с fd и метаданными (цель, сеть, inbound, пользователь) |
| П → Я | `DIAL` → `DIAL_RESULT` | открыть соединение через свой `detour` или outbound по тегу; fd или класс ошибки |
| Я → П | `ACCEPT` | принятое соединение слушателя inbound |
| П → Я | `ROUTE_CONN` / `ROUTE_PACKET_CONN` | отдать поток или UDP-сессию роутеру ядра |
| П → Я | `RESOLVE` → ответ | DNS через DNS ядра |
| П → Я | `STATUS` | состояние и счётчики экземпляра |
| П → Я | `LOG` | уровень, текст |
| Я → П | `NETWORK_CHANGED`, `PAUSE`, `RESUME` | события сети и энергосбережения |
| обе | `PING` / `PONG` | проверка, что сторона жива |

Классы ошибок — закрытый список, который понимают пул и `urltest`: таймаут, отказ, недоступно,
отказ авторизации, ошибка протокола, плагин недоступен.

Формат сообщений канала управления — protobuf с префиксом длины: в проекте уже есть свой конвейер
protobuf, а у авторов плагинов он есть на любом языке. Каналы данных — без protobuf, как в таблице
каналов.

**Версия протокола** — `major.minor` в `HELLO`. Ядро принимает плагин с тем же `major`; `minor`
растёт при добавлении сообщений и возможностей, плагин и ядро пользуются пересечением возможностей
из `HELLO`/`MANIFEST`. Смена `major` — несовместимое изменение, ядро называет обе версии в ошибке. SDK для авторов плагинов — отдельный репозиторий
под пермиссивной лицензией, без кода sing-box и sing: плагину не нужно ничего импортировать из ядра.

## Правила и гарантии

### Состояния плагина

```
           запуск              HELLO + MANIFEST         все START ок
  нет ───────────► старт ─────────────────► готов ────────────────► работает
                     │ нет HELLO за 5 с /       ▲                      │ процесс умер /
                     │ версия не та /           │ CREATE всех           │ нет PONG 10 с /
                     │ опции отвергнуты         │ экземпляров заново    │ битое сообщение
                     ▼                          │                      ▼
              ошибка старта ядра       перезапуск ◄──────────────── упал
              (fail-fast)              через 1, 2, 4 … 30 с
```

1. **Первый старт — fail-fast.** Файла нет, каталог вне `LX_PLUGINS_DIR`, сумма не та, нет `HELLO`
   за 5 с, версия протокола не та, опции отвергнуты — ядро не стартует, ошибка называет тег и
   причину.
2. **Падение после старта не роняет ядро.** Экземпляры плагина сразу отвечают на новые соединения
   ошибкой класса «плагин недоступен», открытые соединения закрываются. Группы, `urltest` и пул
   уходят на другие узлы по своим обычным правилам.
3. **Перезапуск** с задержками 1, 2, 4 … 30 с; счётчик сбрасывается после 60 с без падений. После
   перезапуска ядро заново создаёт все экземпляры с теми же опциями. Состояние сессий внутри
   плагина теряется. `restart: never` — экземпляры остаются в состоянии «плагин недоступен».
4. **Остановка:** `CLOSE` всем экземплярам, 2 с на выход, затем принудительное завершение.
5. **Плагин не переживает ядро.** Закрылся канал управления — плагин обязан выйти. Если ядро убито
   и не успело ничего сказать, канал закрывает ОС.
6. **Перезагрузка конфига:** экземпляры пересоздаются; процесс переиспользуется, если файл и его
   сумма не изменились.
7. **Ядро проверяет каждое сообщение** (длины, границы, известные id). Нарушение — разрыв с
   плагином, как при падении.
8. **Счётчики соединений** для пользователя (лаунчер, LxBox, Clash API) ядро считает само, на
   стороне роутера; плагин не может их подделать или потерять. Счётчики соединений к серверу при
   отданном настоящем сокете приходят из `STATUS` плагина.
9. **Доверие:** плагин работает с правами ядра. Это код, который пользователь положил в каталог
   плагинов; ядро его не изолирует. `sha256` защищает от подмены файла.

Правила 2, 3 и 6 — логика с состоянием: до кода пишется ALGORITHM.md ([SPECS/README §3а](../../README.md)).

### Стыковка с остальным ядром

| Механизм | Что происходит |
|---|---|
| Группы, `urltest`, пул, самовосстановление пула | экземпляр — обычный outbound; ошибки дозвона приходят классами |
| Цепочки ([FEATURE 015](../015-CHAIN/FEATURE.md)) | `detour` — ключ ядра; перезапись цепочки действует на него как на любой узел (предположение, см. выше) |
| `impair` ([FEATURE 020](../020-IMPAIR/FEATURE.md)) | плагин ходит через `impair` по тегу; настоящий сокет в этом случае не отдаётся |
| Энергосбережение ([FEATURE 008](../008-ENERGY/FEATURE.md)) | `PAUSE` / `RESUME` плагину |
| Наблюдаемость ([FEATURE 006](../006-OBSERVABILITY/FEATURE.md)) | `GetPluginStatus(tag)`, логи с префиксом тега |
| Android (LxBox) | см. раздел «Android» ниже |
| Роутеры | статические бинари плагинов в каталоге плагинов; `lxd` или init-скрипт задаёт `LX_PLUGINS_DIR` и поднимает лимит fd |

## Android

На Android плагины вкомпилированы в APK приложения. Набор плагинов фиксируется при сборке APK:
пользователь файлы не кладёт, каталог и переменные окружения ему не нужны. `LX_PLUGINS_DIR` и `lx.plugins.dir` на Android не действуют: каталог — тот, куда APK положил
плагины. Записи `lx.plugins.list` с `file` и `sha256` обязательны и здесь; их пишет приложение при
сборке APK, а не пользователь.

Протокол плагинов при этом тот же, что на десктопе и роутерах: плагин собирается как отдельная
программа и упаковывается в APK. Приложение знает свои плагины и сообщает ядру, где они лежат и
какие типы дают. Сокеты держит ядро, `protect()` уже сделан.

Проверить спайком до первой задачи: запуск программы из APK на целевых версиях Android и живучесть
дочернего процесса (ограничения Android 12+ на дочерние процессы). Если не пройдёт — на Android
второй загрузчик в процессе ядра с теми же сообщениями (см. «Границы»).

## Тестовый плагин `plugtest`

Для проверки механизма нужен протокол без своей сложности. В репозитории будет плагин-заглушка
`plugtest` — отдельная программа, стенды в `lx-test/`. Он даёт три типа:

| Тип | Род | Что делает |
|---|---|---|
| `plugtest` | `outbound` | открывает через ядро поток к своему серверу, первым кадром шлёт цель, дальше гонит байты |
| `plugtest` | `inbound` | принимает поток, читает цель, отдаёт поток роутеру через `ROUTE_CONN` |
| `plugtest-l3` | `endpoint` | заворачивает L3-пакеты из TUN в кадры по одному соединению к серверу `plugtest`; в `MANIFEST` — «только пакеты», своего стека нет. Серверная сторона для него и проверка стека в плагине — второй задачей |

Провод `plugtest` — без шифрования и рукопожатия:

```
поток:      [2 байта длина][цель: "tcp|udp host:port"]  затем байты как есть
датаграмма: [2 байта длина][цель]  [2 байта длина][данные]   — на каждую датаграмму
L3-кадр:    [2 байта длина][IP-пакет]
```

Ручки заглушки — чтобы проверять правила жизненного цикла, а не протокол:

| Ключ | Что делает |
|---|---|
| `crash_after` | процесс плагина падает через N соединений или N секунд |
| `hang_after` | плагин перестаёт отвечать на `PING` |
| `reject_options` | `CHECK` отвечает ошибкой по указанному ключу |
| `dial_error` | `DIAL` на сервер отвечает заданным классом ошибки |
| `bad_message` | плагин шлёт битое сообщение |
| `delay` | задержка ответа на `HELLO` / `READY` |

Стенд — loopback в одном конфиге: `mixed` → `plugtest` (outbound) → `plugtest` (inbound) →
`direct` → локальный эхо-сервер. Тот же стенд с `impair` в `detour` проверяет, что настоящий сокет
не отдаётся, а с цепочкой — что перезапись `detour` подхватывает тип плагина.

## Цена в форке (оценка для теста [§3.1](../../CONSTITUTION.md) (а3))

- Вставки в апстримные файлы: регистрация типов плагинов в `include/registry.go` (по одной на
  реестр за маркером `// lx:`) и ранний запуск плагинов до разбора конфига в местах, где конфиг
  читается (CLI, libbox, `lxd`). Точный список — в PLAN первой задачи.
- `GetPluginStatus` — по §3.6 (несколько строк в `.proto` и регенерация).
- Остальное — новые пакеты за тегом `with_lx_plugin`.
- Альтернатива для сравнения: каждый запрошенный протокол (mieru и следующие) — отдельной фичей в
  ядре со своей зоной мержа и зависимостями.

## Границы

- Плагин не получает доступ к внутренностям ядра (роутер, кеш, память) — только сообщения из таблицы.
- Встроенные типы не переопределяются.
- Плагин не открывает сетевые сокеты сам. Технически ему никто не мешает, но тогда петля через TUN,
  цепочки, `protect()` и mark — его забота, ядро это не поддерживает.
- Загрузка плагина в процесс ядра (Go `plugin`, dll) — вне скоупа. Если понадобится, это второй
  загрузчик с теми же сообщениями.
- Изоляция плагина (песочница, отдельный пользователь) — вне скоупа.
- iOS — вне скоупа.

## Решения черновика

Приняты в черновике без отдельного обсуждения (2026-11-26); пересматриваются на ревью фичи.

1. **Стек TCP/IP для endpoint и пакетного inbound — в плагине.** Ядро остаётся тоньше и не зависит
   от судьбы gVisor в апстриме 1.15. Стек в ядре — вариант на будущее, если замер на сервере покажет,
   что поток-на-fd через `ROUTE_CONN` дорог.
2. **Каждый плагин записан в `lx.plugins.list` с обязательными `file` и `sha256`** (решение
   владельца 2026-11-26). Каталог не обходится; типы плагин называет сам в `MANIFEST`.
3. **Управление — переменные окружения и конфиг** (`LX_PLUGINS_DIR`, `LX_PLUGINS`, `lx.plugins`).
   Отдельных настроек в лаунчере и LxBox фича не требует; им достаточно задать переменную при
   запуске ядра.
4. **Формат канала управления — protobuf с префиксом длины.**
5. **Android — плагины вкомпилированы в APK**, набор фиксируется при сборке, пользователь файлы не
   кладёт. Отдельный APK-плагин — вне
   первой версии.
6. **Версия протокола — `major.minor`**, совместимость по `major`, возможности по пересечению.
7. **Ключи слушателя inbound — стандартные ключи слушателя ядра** + блок `tls` по разрешению
   плагина.
8. **Язык — русский.** Английская версия с русской копией — вместе с публикацией SDK для внешних
   авторов плагинов.
