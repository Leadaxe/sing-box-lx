# FEATURE: MASQUE_WARP — outbound MASQUE (CONNECT-IP)

| Поле | Значение |
|------|----------|
| Тип | Продуктовая фича |
| Build-tag | — собственного нет, но нужны апстрим-теги `with_quic` (+`with_gvisor`): без них тип `masque` в конфиге отвергается с ошибкой «QUIC не собран» |
| Состояние | ✅ Реализовано |

## Назначение

Outbound типа `masque` — туннель по протоколу MASQUE в варианте **CONNECT-IP**
([RFC 9484](https://www.rfc-editor.org/rfc/rfc9484)), переносящий IP-пакеты
внутри HTTP-соединения. Основной сценарий — Cloudflare WARP.

Вариант с IP-пакетами выбран сознательно: WARP работает именно так, вариант
с переносом отдельных UDP-датаграмм для этой задачи непригоден.

⚠️ Не путать с полями `id`/`ip`/`ib` в [AWG2](../AWG2/FEATURE.md) —
там «masquerade» означает совсем другой механизм.

## Контролируемые параметры

Внутри блока outbound'а типа `masque`.

| Ключ | Тип | Дефолт | Смысл |
|------|-----|--------|-------|
| `profile` | `cloudflare` · `standard` | `cloudflare` | Набор умолчаний и поведения: WARP либо обычный сервер по RFC |
| `network` | `h3` · `h2` | `h3` | **Транспорт**: `h3` — поверх QUIC (UDP), `h2` — поверх TCP |
| `network_list` | `tcp` · `udp` | оба | **Протоколы L4**, которые пускаются в туннель |
| `server`, `server_port` | адрес | — | Точка подключения |
| `private_key`, `public_key` | base64 | — | Ключи; обязательны для профиля `cloudflare` |
| `ip` | адрес с маской | — | Локальный адрес туннеля (IPv4); без маски трактуется как одиночный |
| `ipv6` | адрес с маской | — | Локальный адрес туннеля (IPv6) |
| `uri` | строка | по профилю | Адрес запроса на установку туннеля |
| `sni` | строка | по профилю | Имя сервера для TLS |
| `mtu` | целое | 1280 | MTU внутреннего стека |
| `idle_timeout` | длительность | 5m | Простой, после которого туннель усыпляется; отрицательное — не усыплять |
| `keep_alive_period` | длительность | 30s | Период поддержания соединения (для `h3`); отрицательное — выключить |
| `skip_cert_verify` | флаг | выкл | Отключение проверки ключа сервера — только для отладки |

⚠️ **`network` здесь означает не то же, что в других outbound'ах.**
Обычно `network` выбирает `tcp`/`udp`; тут он выбирает транспорт `h3`/`h2`,
а список L4-протоколов задаётся отдельным `network_list`. Значение `"tcp"`
в `network` отвергается сразу.

Требуется хотя бы один из `ip` / `ipv6`.

⚠️ **Фрагментация UDP разрешена по умолчанию** — в отличие от обычных
outbound'ов, где исходящая датаграмма помечается «не фрагментировать».
Туннель по своей природе добавляет к каждому пакету заголовки инкапсуляции,
и при вложении (masque внутри другого туннеля) внешняя датаграмма штатно
перерастает MTU: с запретом фрагментации она молча пропадала бы вместо
разбиения. Явный `udp_fragment: false` возвращает запрет —
см. [HOTFIXES](../HOTFIXES/FEATURE.md), запись 028.

## Входы

- **Конфиг** (выше) и **ключи**, полученные при регистрации на стороне
  клиентского приложения.
- **Трафик**, маршрутизируемый в этот outbound.

## Выходы

- **HTTP-соединение к серверу** (поверх QUIC либо TCP), несущее
  IP-пакеты туннеля.
- **Расшифрованный трафик** обратно в маршрутизацию.

## Data flow

```
конфиг + ключи → установка HTTP-соединения (h3 или h2)
               → запрос CONNECT-IP → туннель установлен
                          │
трафик приложения → внутренний IP-стек → IP-пакеты → в туннель
                          │
        простой дольше idle_timeout → туннель усыпляется
        следующее обращение        → туннель восстанавливается
```

## Правила и гарантии

- **Ключи не добываются ядром.** Регистрация выполняется приложением,
  ядро получает готовые ключи из конфига.
- **Туннель усыпляется при простое** и восстанавливается по обращению —
  ресурсы неактивного туннеля не удерживаются.
- **Отмена запроса на установку соединения работает**: попытка подключения
  прекращается вместе с отменой, а не висит до собственного тайм-аута.
- **`network: "tcp"` — ошибка**, а не молчаливая подмена смысла.

## Границы

- **`h3` не проходит через HTTP-прокси в цепочке проксирования.**
  HTTP-прокси переносит только TCP, а `h3` работает поверх UDP.
  В такой схеме нужен `network: "h2"` — при профиле `cloudflare`
  и MTU не больше 16000.
- **Проверка сертификата заменена сверкой ключа** — обычные TLS-опции
  сюда не выносятся: набор ALPN определяется транспортом, а ослабление
  проверки не соответствует модели WARP.
- **Поведение профиля `cloudflare` определяется реальным сервисом** —
  синтетический стенд его не воспроизводит.

## Особенности сопровождения

- **Проверять на реальном WARP.** Профиль завязан на поведение конкретного
  сервиса, а не на текст RFC.
- **Отмена операций — не мелочь.** Игнорирование отмены на этапе установки
  соединения давало зависание навсегда; это была самая дорогая находка
  аудита ([AUDITS](../AUDITS/FEATURE.md)).
- **Вложенность требует внимания к размеру пакетов** — см.
  [HOTFIXES](../HOTFIXES/FEATURE.md).
