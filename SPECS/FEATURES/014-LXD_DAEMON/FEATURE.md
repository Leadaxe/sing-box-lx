# FEATURE: 014 — LXD_DAEMON

Headless-демон `lxd`: ядро живёт **внутри процесса демона**, а управляющий
gRPC-канал принадлежит процессу — и потому переживает любую смену конфига и
любой битый конфиг. Фундамент удалённого управления серверными (и в
перспективе локальными) ядрами из лаунчера.

## 1. Назначение

`sing-box run` перезапускается по SIGHUP целиком: канал управления умирает
вместе с инстансом, а фатально-битый конфиг оставляет хост без управления.
`lxd` разрывает эту связку: долгоживущий процесс держит управляющий канал
поднятым **всегда**, а смена конфига — это подмена ядра-объекта внутри
процесса. Управление доступно ровно тогда, когда оно нужнее всего — когда
data-plane лежит.

Потребители: лаунчер (удалённые серверы — фаза 1; локальный режим — фаза 2),
`grpcurl`/инструменты, дашборды. Протокол — тот же, что у Android-линии
(CommandClient): всё, что дорабатывается для мобильной наблюдаемости,
сервер получает автоматически, и наоборот.

## 2. Контролируемые параметры

| Ручка | Тип / дефолт | Значение |
|---|---|---|
| `lxd` | сабкоманда (голая) | запуск демона |
| `-c <файл>` | путь, **необязателен** | seed-конфиг: используется, только когда нет last-good; без него демон стартует пустым (IDLE); каталоги `-C` не поддерживаются |
| `--config-force <файл>` | путь | **всегда** бутиться с этого файла, поверх last-good; после успешного старта он становится last-good |
| `--run` | флаг | форсит подъём ядра независимо от памяти run-состояния |
| `--listen` | `host:port`, дефолт `127.0.0.1:9091` | адрес управляющего канала (обе плоскости) |
| `--tls` | флаг | включить mTLS с регистрацией клиентов; без него — h2c (loopback-only) |
| `--secret` | строка, дефолт пусто | Bearer обеих плоскостей; **пусто = аутентификация выключена**; виден в `ps` |
| `--secret-file` | путь | читать Bearer из файла `0600` (предпочтительно перед `--secret`) |
| `--state-dir` | путь, дефолт `lxd-state` (сервис — абсолютный `<support>/state`) | каталог состояния: last-good, кандидат, pending, was_running, серверная пара, доверенные клиенты |
| `--service` | `install` \| `install-user` \| `uninstall` \| `print` | установка службой (см. ниже) |
| `--purge` | флаг | с `--service=uninstall` — снести и state-каталог |
| `client add [--name] / list / remove <тег>` | подкоманды | регистрация/просмотр/отзыв доверенных клиентов у живого демона |
| build-tag | `with_lx_command` | без тега сабкоманды нет |

**Admin-плоскость (REST, тот же порт, что gRPC):** `POST /admin/apply`
(тело = конфиг, 200 / 422 невалидный / 500 сбой или провал старта +`rolled_back`),
`POST /admin/rollback` (на last-good, 404 если нет), `POST /admin/start` и
`POST /admin/stop` (жизнь ядра отдельно от конфига), `GET /admin/config`
(активный конфиг), `GET /admin/status` (`status: idle|started|fatal`, sha
активного и last-good, `last_error`, `interrupted_apply`), `POST /admin/enroll`
(регистрация клиента по одноразовому коду — единственный маршрут до доверия).

**mTLS (`--tls`):** демон сам себе CA — на первом старте самоподписывает
серверную пару (стабильный отпечаток в state-dir); при нуле клиентов печатает
приглашение `адрес#отпечаток#код`. Клиент пинит сервер по отпечатку,
регистрируется одноразовым кодом (сгорает после одного клиента, без TTL —
не подобрать); клиентский пин требуется на **обеих** плоскостях.

**Служба (`--service`):** `install` — системный LaunchDaemon (root, для сервера,
TUN, до логина); `install-user` — пользовательский LaunchAgent (без sudo,
десктоп-UX); оба переносят текущую командную строку (минус `--service`) в plist,
абсолютизируя пути, и сами создают каталоги; `print` — сухой прогон plist;
`uninstall` (+`--purge`) — снять службу (и опц. state). macOS реализовано,
Linux/Windows — заглушки.

Дорожная карта ручек (не реализовано): confirm/dead-man, история версий
(content-addressed), SRS-хранилище, reverse-proxy внутреннего Clash API,
Linux/Windows-служба (systemd `LoadCredential=`), scoped-токены.

## 3. Входы / Выходы

**Входы:** конфиг-файл на диске (читается на старте и по SIGHUP; JSONC
допустим — ядро толерантно); SIGHUP = перечитать и применить; SIGINT/SIGTERM =
корректное завершение; gRPC-вызовы `daemon.StartedService` (полный протокол,
включая lx-RPC наблюдаемости: пул балансировщика, правила, DNS-поток и т.д.).

**Выходы:** работающий data-plane согласно конфигу; поток статусов
(STARTED/STOPPING/STARTING/FATAL с текстом ошибки) — один стрим видит все
переходы без переподключения; логи ядра в кольцевом буфере канала и на stderr.

## 4. Data flow

```
конфиг-файл ──чтение──► демон ──строкой──► подмена box-инстанса in-process
     ▲                    │                        │
   SIGHUP                 │ канал (gRPC) ЖИВЁТ     ▼
                          │ поверх подмен      data-plane
 клиент ◄── статусы/RPC ──┘
```

Порядок старта жёсткий: **сначала** управляющий listener, **потом** ядро.

## 5. Правила и гарантии

- Управляющий канал поднимается до первого запуска ядра и не закрывается
  при смене/провале конфига; смена конфига не рвёт соединения и стримы.
- **Пайплайн применения** (REST и SIGHUP — один вход, применения
  сериализуются): кандидат стейджится на диск → валидация **сабпроцессом**
  (`check` самим бинарём, таймаут; паника валидации не убивает демон;
  отказ = 422, работающий инстанс не тронут) → подмена инстанса → last-good
  переписывается **только после успешного старта**; провал старта (bind/tun —
  то, что проверка без Start не ловит) вызывает **автооткат** на last-good.
- **Источник конфига на старте**: last-good → seed-файл (`-c`, если дан
  явно; первый успешный старт записывает его как last-good) → пусто (IDLE).
  Кандидат не загружается на старте никогда; прерванный процессной смертью
  apply помечается в статусе (`interrupted_apply`).
- Статус `fatal` означает «инстанса нет»; после успешного отката статус
  `started`, а причина провала остаётся в `last_error` информационно.
- Аутентификация обеих плоскостей — Bearer; REST сравнивает секрет
  constant-time. Шифрования канала пока нет — слушать не-loopback без
  внешней защиты нельзя.

## 6. Границы

- Не заменяет Clash API: если конфиг содержит `experimental.clash_api`,
  он работает как обычно внутри инстанса.
- Не супервизор самого себя: смерть процесса лечит systemd/launchd/SCM.
- Не менеджер парка ядер: один демон — одно ядро.
- Android/gomobile не затрагивает (другая точка входа).
- Версии конфигов, откат, доставка SRS, TLS, admin-RPC — впереди
  (дорожная карта фичи), скелет их сознательно не содержит.

## 8. Особенности сопровождения

- Контракт `daemon.StartedService` — общий с Android-линией и десктопным
  демоном апстрима; его семантика меняется апстримом без semver. Смена
  семантики применения конфига заденет и нас — ловится сборкой и
  сквозным прогоном.
- Применение убивает старый инстанс **до** парсинга нового — «проверь до
  убийства» (как SIGHUP-путь `sing-box run`) и автооткат должны строиться
  поверх, в admin-плоскости.
- Сабкоманда регистрируется собственным файлом через `init()` — правок в
  апстримных файлах нет; при мержах апстрима конфликтов не даёт.
- В релизных сборках тег `with_lx_command` уже включён; без тега пакет
  собирается пустым (стаб) — обе стороны проверяются CI.
