# FEATURE: 014 — LXD_DAEMON

Headless-демон `lxd`: ядро живёт **внутри процесса демона**, а управляющий
gRPC-канал принадлежит процессу — и потому переживает любую смену конфига и
любой битый конфиг. Фундамент удалённого управления серверными (и в
перспективе локальными) ядрами из лаунчера.

## 1. Назначение

`sing-box run` перезапускается по SIGHUP целиком: канал управления умирает
вместе с инстансом, а фатально-битый конфиг оставляет хост без управления.
`lxd` разрывает эту связку: долгоживущий процесс держит управляющий канал
поднятым **всегда**, а смена конфига — это подмена ядра-объекта внутри
процесса. Управление доступно ровно тогда, когда оно нужнее всего — когда
data-plane лежит.

Потребители: лаунчер (удалённые серверы — фаза 1; локальный режим — фаза 2),
`grpcurl`/инструменты, дашборды. Протокол — тот же, что у Android-линии
(CommandClient): всё, что дорабатывается для мобильной наблюдаемости,
сервер получает автоматически, и наоборот.

## 2. Контролируемые параметры

| Ручка | Тип / дефолт | Значение |
|---|---|---|
| `lxd run` | сабкоманда | запуск демона |
| `-c <файл>` | путь, ровно один (дефолт `config.json`) | конфиг ядра; каталоги `-C` не поддерживаются |
| `--listen` | `host:port`, дефолт `127.0.0.1:9091` | адрес управляющего канала |
| `--secret` | строка, дефолт пусто | Bearer-секрет канала; **пусто = аутентификация выключена** (только для loopback) |
| build-tag | `with_lx_command` | без тега сабкоманда отсутствует |

Дорожная карта ручек (не реализовано): mTLS канала, admin-плоскость
(apply/confirm/rollback/история версий), SRS-хранилище, reverse-proxy
внутреннего Clash API, рабочий каталог состояния, установка системной
службой (`service install`), scoped-токены.

## 3. Входы / Выходы

**Входы:** конфиг-файл на диске (читается на старте и по SIGHUP; JSONC
допустим — ядро толерантно); SIGHUP = перечитать и применить; SIGINT/SIGTERM =
корректное завершение; gRPC-вызовы `daemon.StartedService` (полный протокол,
включая lx-RPC наблюдаемости: пул балансировщика, правила, DNS-поток и т.д.).

**Выходы:** работающий data-plane согласно конфигу; поток статусов
(STARTED/STOPPING/STARTING/FATAL с текстом ошибки) — один стрим видит все
переходы без переподключения; логи ядра в кольцевом буфере канала и на stderr.

## 4. Data flow

```
конфиг-файл ──чтение──► демон ──строкой──► подмена box-инстанса in-process
     ▲                    │                        │
   SIGHUP                 │ канал (gRPC) ЖИВЁТ     ▼
                          │ поверх подмен      data-plane
 клиент ◄── статусы/RPC ──┘
```

Порядок старта жёсткий: **сначала** управляющий listener, **потом** ядро.

## 5. Правила и гарантии

- Управляющий канал поднимается до первого запуска ядра и не закрывается
  при смене/провале конфига.
- Битый конфиг (на старте или по SIGHUP) **не роняет демон**: статус FATAL
  с текстом ошибки, канал отвечает, следующий SIGHUP с исправленным конфигом
  восстанавливает работу.
- Смена конфига не рвёт клиентские соединения и стримы канала.
- Провал применения оставляет data-plane остановленным до следующего
  успешного применения (семантика ядра: старый инстанс закрывается до сборки
  нового). Автооткат — зона admin-плоскости, в скелет не входит.
- Аутентификация — Bearer-метаданные каждого вызова; шифрования канала пока
  нет — слушать не-loopback без внешней защиты нельзя.

## 6. Границы

- Не заменяет Clash API: если конфиг содержит `experimental.clash_api`,
  он работает как обычно внутри инстанса.
- Не супервизор самого себя: смерть процесса лечит systemd/launchd/SCM.
- Не менеджер парка ядер: один демон — одно ядро.
- Android/gomobile не затрагивает (другая точка входа).
- Версии конфигов, откат, доставка SRS, TLS, admin-RPC — впереди
  (дорожная карта фичи), скелет их сознательно не содержит.

## 8. Особенности сопровождения

- Контракт `daemon.StartedService` — общий с Android-линией и десктопным
  демоном апстрима; его семантика меняется апстримом без semver. Смена
  семантики применения конфига заденет и нас — ловится сборкой и
  сквозным прогоном.
- Применение убивает старый инстанс **до** парсинга нового — «проверь до
  убийства» (как SIGHUP-путь `sing-box run`) и автооткат должны строиться
  поверх, в admin-плоскости.
- Сабкоманда регистрируется собственным файлом через `init()` — правок в
  апстримных файлах нет; при мержах апстрима конфликтов не даёт.
- В релизных сборках тег `with_lx_command` уже включён; без тега пакет
  собирается пустым (стаб) — обе стороны проверяются CI.
