# FEATURE: VLESS_ENCRYPTION — пост-квантовый слой внутри VLESS

| Поле | Значение |
|------|----------|
| Тип | Продуктовая фича |
| Build-tag | — |
| Состояние | 🆕 **Спроектировано, не реализовано** |

## Назначение

Слой шифрования **внутри VLESS**, устойчивый к атаке «сохранить сейчас,
расшифровать потом»: трафик, записанный сегодня, не должен вскрываться
квантовым компьютером в будущем.

Такие конфигурации сейчас не работают **ни в одном клиенте на базе sing-box** —
зазор общий для всей экосистемы; серверы Xray и клиенты mihomo их уже
поддерживают.

⚠️ Это **не** пост-квантовый обмен ключами REALITY. Слой живёт над VLESS
и с механизмами самого REALITY не связан.

## Контролируемые параметры

Одно поле в блоке outbound'а типа `vless`.

| Ключ | Тип | Дефолт | Смысл |
|------|-----|--------|-------|
| `encryption` | строка спецификации | пусто = слой выключен | Параметры пост-квантового слоя; значение `none` также означает «выключен» |

### Формат строки

```
mlkem768x25519plus.<вид>.<0rtt|1rtt>[.<паддинг>][.<задержка>].<ключ>[.<ключ>…]
```

| Сегмент | Значения | Смысл |
|---------|----------|-------|
| Схема | `mlkem768x25519plus` | Единственная поддерживаемая; должна совпасть с серверной |
| Вид | `native` · `xorpub` · `random` | Как слой выглядит на проводе: как обычный TLS 1.3, с замаскированными открытыми ключами, либо полностью случайно |
| Режим | `0rtt` · `1rtt` | Переиспользовать сохранённый билет либо каждый раз выполнять полное согласование |
| Паддинг, задержка | блоки `вероятность-от-до` | Форма трафика; **только для `1rtt`** |
| Ключи | base64 | Открытые параметры сервера |

## Входы

- **Конфиг** — строка спецификации и обычные параметры VLESS.
- **Поток данных** прокси-протокола.
- **Открытые ключи сервера** из строки спецификации.

## Выходы

- **Согласование и зашифрованный поток** к серверу.
- **Ошибка при загрузке конфига** с указанием неверного сегмента строки.

## Data flow

```
строка спецификации → разбор по сегментам → параметры слоя
                                │
      согласование ключей (пост-квантовое + классическое)
                                │
   выбранный вид определяет, как согласование выглядит на проводе
                                │
поток VLESS → шифрование слоем → внешний транспорт (TLS/REALITY/XHTTP…)
```

Режим `0rtt` позволяет пропустить полное согласование при повторном
подключении; `1rtt` всегда выполняет его целиком и допускает настройку
формы трафика.

## Правила и гарантии

- **Неразобранная строка отвергается при проверке конфига** — с указанием
  сегмента, где ошибка. Молчаливого отключения слоя быть не должно:
  иначе пользователь считает трафик защищённым, а он не защищён.
- **Схема должна совпасть с серверной** — иначе соединение не установится.
- **Паддинг и задержка применимы только к `1rtt`** — в режиме `0rtt`
  они не имеют смысла и должны отвергаться.
- **Пустое значение и `none` эквивалентны** — слой выключен, поведение
  штатное.

## Границы

- **Пост-квантовые механизмы самого REALITY — вне скоупа.**
- **Только клиентская сторона.**
- **Внешних зависимостей фича не добавляет** — используется криптография
  из стандартной библиотеки.

## Особенности сопровождения

- **Единственный симптом любой ошибки — «не подключается».** Слой либо
  сходится с сервером побайтово, либо нет; промежуточной диагностики
  крипто-согласование не даёт.
- **Проверка возможна только против эталонного сервера.** Синтетические
  тесты подтверждают разбор строки, но не совместимость согласования.
- **Проверять в связке с внешними слоями** — с REALITY и с транспортом
  [XHTTP](../XHTTP/FEATURE.md), потому что реальные конфигурации
  используют их вместе.
