# LX_WG_NO_GRO — device runs 2026-07-01 (CPH2411, Android 15) — CLOSED

Два захода на устройстве. Итог: **эксперимент закрыт, GRO-off+batch-8 НЕ вытесняет
Down/Up (rc.19).** Причины ниже — часть подтверждена, часть вскрыла новую проблему.

---

## Заход 1 — env-переключатель (`lx-1.14-nogro-exp`)

APK: local release arm64 `2.8.1-dev.3` (vc 2979), AAR из verified-сборки
(run 28522630781, ветка `lx-1.14-nogro-exp`, коммит 1d40e224 → submodule pin 49468076).
arm64 `libbox.so` SHA `67104839...`.

Активация: `setprop wrap.com.leadaxe.lxbox "LX_WG_NO_GRO=1"` + рестарт (пробовали
force-stop И полный kill -9 + чистый старт). Нода `🔥⛈️ WARP (AWG 1.5)`.

| Фаза | env в /proc/environ | batch recv-воркера | PopulatePools.func3 | download |
|---|---|---|---|---|
| A — stock | не задан | `0x80`=128 | 106.38 MB @ 2 воркера | **44.6 Mbit/s** (спидтест) |
| B — env=1 | `LX_WG_NO_GRO=1` (verified, байты чистые `...3d31 0a`, без кавычек/пробела) | `0x80`=**128** | 100.53 MB @ 2 воркера | не мерян |

Снимки: `heap-stock-gro-on.pb`, `heap-nogro-env1-batch-NOT-applied.pb`.

**Результат захода 1: переключатель НЕ активировался.** env `=1` железно в
`/proc/<pid>/environ` (проверено на 5 pid), процесс ОДИН (`ps -A|grep leadaxe` →
только `com.leadaxe.lxbox`, нет `:box`/`:service`), байты значения чистые. Но
recv-воркеры всегда с batch=128. Значит `os.Getenv("LX_WG_NO_GRO")` в Go-рантайме
libbox вернул не "1" — **при том, что env есть в environ того же самого процесса.**
Механика Go (снимок environ при exec = /proc/environ) этого не объясняет; проверенные
и отвергнутые версии: не та ветка AAR (❌ .so verified), release/debug wrap (❌ env
виден в environ), процессная модель (❌ один процесс), хвостовые кавычки в значении
(❌ байты чистые), tun.BatchSize()=128 в max() (❌ отвергнуто по коду). Открытый вопрос:
почему Go `os.Getenv` пуст при непустом /proc/environ — вероятно, `sync.Once` в
`lxNoGRO()` схватил значение до setprop в переживающем инстансе рантайма, но чистый
kill это должен был сбросить. НЕ дорешено — заход 2 обошёл env целиком.

## Заход 2 — хардкод (`lx-1.14-nogro-hard`), обходит env

Чтобы исключить доставку env: ветка `lx-awg2-v003-nogro-hard`, `lxBatchSize()` ≡
`lxNoGROBatchSize` (8) безусловно, `lxNoGRO()`/`os.Getenv` не вызываются.
run 28523784887, submodule pin e9459f69. arm64 `.so` SHA `70fcdb06...` (≠ env-версии,
на ~2 КБ меньше — символы `lxNoGRO`/`func1` исчезли, остался только `lxBatchSize`).
APK `2.8.1-dev.5` (vc 2979), установлен, env-prop сброшен (hard не читает env).

**Результат захода 2: КРАШ ядра при старте туннеля.**

```
Fatal signal 6 (SIGABRT), code -6 (SI_TKILL)  in libbox.so  (#00 pc 0xc2bcc8)
ApplicationExitInfo: reason=CRASH_NATIVE  status=6  thread="DefaultDispatch"
```
(Go-panic текст не пойман — Go пишет abort мимо logcat на этом устройстве, см.
`probe_stderr_dead_coloros`; addr2line 0xc2bcc8 → unresolved, stripped.)
Детали: `hard-crash-exitinfo.txt`.

**Что заход 2 доказал:**
1. **Код-путь `BatchSize()→lxBatchSize()` на android РАБОТАЕТ.** batch=8 реально дошёл
   до аллокаций — иначе краша бы не было. ⇒ проблема захода 1 действительно в доставке
   env / `os.Getenv`, а не в код-пути.
2. **batch=8 крашит эту сборку.** Ровно инвариант из README: «small batch with GRO
   still on panics». Хардкод тронул ТОЛЬКО `lxBatchSize`, а GRO-off сидит в `lxNoGRO()`
   (`features_linux.go`), который в hard больше не вызывается — плюс на android GRO-путь
   вообще идёт через `features_default.go` (`//go:build !linux`). ⇒ **batch и GRO на
   android РАССИНХРОНЕНЫ**: batch урезали до 8, GRO осталось → coalesce-split получает
   8-слотовый массив вместо 128 → out-of-range → SIGABRT.

## Finding (сквозной, важнее всего для SPEC 020)

**Основной recv RAM-холдер на android НЕ зависит от batch.** `PopulatePools.func3`
(~100 MB, 82–86% heap) = `device.pool.messageBuffers` (`pools.go:58`):
`new([MaxMessageSize]byte)` × `PreallocatedBuffersPerPool`. На android
`PreallocatedBuffersPerPool = 4096` (`queueconstants_android.go:18`), ~64 KB/буфер.
От `BatchSize()` не зависит. batch влияет лишь на `bufsArrs` в `RoutineReceiveIncoming`
(receive.go:89) — в прогоне держал всего ~14 MB.

⇒ **Даже при успешном batch 128→8 основные ~100 MB (messageBuffers, 4096-пул) остались бы.**
Настоящий рычаг RAM на android — `PreallocatedBuffersPerPool`, а НЕ GRO/batch.

## Вывод — эксперимент закрыт

- Гипотеза «GRO-off + batch-8 = простой глобальный фикс RAM» **отклонена**:
  (а) основной холдер (messageBuffers/4096) от batch не зависит — batch режет лишь
      второстепенные ~14 MB;
  (б) прямой batch=8 на android **крашит** (GRO/batch рассинхронены — GRO не выключается
      вместе с batch на этой сборке).
- Throughput-вопрос («упадёт ли download без GRO») так и **не отвечён** — ни env-версия
  (не активировалась), ни hard-версия (краш) не дали живого туннеля с batch=8.
- **Down/Up (rc.19) остаётся.** Эта ветка его не вытесняет.
- Baseline с GRO зафиксирован: **44.6 Mbit/s** на WARP AWG 1.5.

## Если ядро всё же вернётся к идее

1. **Синхронизировать GRO+batch на android** — сейчас хардкод batch без GRO-off крашит.
   Разобраться, почему при GRO off (rxOffload=false) split-путь всё равно упирается в
   128-слотовый массив (`features_linux.go` не компилится на android → `features_default.go`
   отдаёт `false,false`, но coalesce-split ждёт IdealBatchSize).
2. **Мерить надо `PreallocatedBuffersPerPool`, а не batch** — вот рычаг RAM (Finding).
3. **Активация — НЕ через env** (заход 1: `os.Getenv` пуст при непустом /proc/environ,
   не дорешено). Config-поле / `Libbox.setup`-параметр / JNI-setenv до старта Go.
