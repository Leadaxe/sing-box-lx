## 1. Проблема

Наша реализация AmneziaWG покрывает **16 параметров**: `Jc/Jmin/Jmax`, `S1–S4`,
`H1–H4`, `I1–I5`. Этого достаточно для подключения к обычному AWG2-серверу.

Более поздний слой «advanced security» апстрима `amneziawg-go` добавляет ещё
**четыре параметра таймированного junk**:

- **`Itime`** — период (секунды), с которым клиент шлёт junk-пакеты в установившемся
  туннеле (не только перед хендшейком).
- **`J1`, `J2`, `J3`** — CPS-описания содержимого этих периодических junk-пакетов
  (тот же мини-язык `<b ...>`/`<r ...>`/`<c ...>`/`<t>`, что и у `I1–I5`).

Сейчас их **нет ни на одном слое**:

| Слой | Файл | Что есть | Чего нет |
|------|------|----------|----------|
| Конфиг sing-box | `option/wireguard_awg.go` | `jc…i5` | `j1/j2/j3/itime` |
| Обвязка → UAPI | `transport/wireguard/device_awg.go` | форматирует `jc=…i5=…` | `j*`/`itime` |
| Подмодуль UAPI | `device/uapi.go` | `case "jc"`…`case "i5"` | `case "j1..j3"/"itime"` |
| Подмодуль send | `device/send.go`, `device/timers.go` | I-CPS перед init (синхронно) | периодическая отправка по таймеру |

**Следствие для пользователя:** к серверу, где включён `Itime`/`J1-J3` как
**обязательный** уровень маскировки, наш клиент не сойдётся по хендшейку. Если
это опциональная серверная надстройка — туннель выживает, но без этого слоя.

Цель фичи — закрыть зазор до **полного набора AWG2** (20 параметров), чтобы
«произвольный AWG2-сервер» стал буквальным, а не «обычный AWG2-сервер».

## 2. Архитектура (актуальное состояние — как будет устроено)

Фича встраивается в **уже существующие** механизмы, не строит их с нуля.

### 2.1 Содержимое junk — переиспользование `obfChain`

`J1/J2/J3` — это тот же CPS-мини-язык, что и `I1–I5`. Он полностью реализован:
`device/obf.go` (`type obf interface`, `obfChain`, `newObfChain`) + семейство
генераторов `obf_bytes.go`, `obf_rand.go`, `obf_randchars.go`, `obf_randdigits.go`,
`obf_timestamp.go`, `obf_datasize.go`, `obf_datastring.go`, `obf_data.go`.

**Вывод:** для `J1-J3` новый парсер НЕ нужен. Каждый `J*` строится тем же
`newObfChain(spec)`, что и `I*`. Это ключевое отличие от «порта с нуля».

### 2.2 Отправка по расписанию — новый таймер рядом с keepalive

Периодической отправки junk в установившемся туннеле сейчас нет: I-CPS шлётся
синхронно перед `SendHandshakeInitiation` (`send.go:134-140`).

`Itime` требует **периодического таймера на peer**. Каркас готов:
`device/timers.go` (224 стр.) уже держит `persistentKeepalive *Timer` на
`time.AfterFunc` — это прямой образец. `Itime`-таймер:

- заводится при `Itime>0` и хотя бы одном непустом `J*`;
- по срабатыванию собирает пакет(ы) из `J1-J3` через их `obfChain.Obfuscate` и
  шлёт `peer.SendBuffers`, затем перевзводится на `Itime` секунд;
- гейтится `peer.timersActive()` (как keepalive) — не тикает при down/suspend,
  что важно для [[SPECS/020-MULTI_WG_IDLE_BUFFER_HEAT]] (не будить спящие WG).

### 2.3 UAPI-ключи в подмодуле

`device/uapi.go` (get + set): четыре новых `case` по образцу `jc`/`i1`:
- `itime` → `strconv.Atoi`, хранить в новом поле `device.junk.itime` (struct
  `junk` в `device.go:98`, сейчас `{min,max,count}` → добавить `itime int` +
  срез собранных `j []*obfChain`).
- `j1/j2/j3` → `newObfChain(value)`, сложить в тот же срез.

### 2.4 Схема конфига и обвязка (LX-слой)

- `option/wireguard_awg.go`: 4 поля — `Itime uint32 json:"itime"`,
  `J1/J2/J3 string json:"j1..j3"`. Валидация junk уже централизована в
  [[SPECS/008-AWG_JUNK_PARAM_VALIDATION]] — расширить её (Itime без J* и наоборот
  = ошибка; верхняя граница Itime как у остальных числовых).
- `transport/wireguard/device_awg.go`: `writeStr("j1", …)` × 3 и `sendf`-строка
  `itime=` — механически по образцу `i1..i5` (там уже есть `writeStr`).
- `IsSet()` в `wireguard_awg.go`: добавить новые поля в проверку.

## 3. Зона касания upstream

- **Подмодуль** (`device/uapi.go`, `device/device.go`, `device/timers.go` или
  новый `device/junk-timer.go`, `device/send.go`) — **это LX-прививка на
  sagernet-базе, не форк официального amneziawg-go**. `J1-J3`/`Itime` в апстриме
  amnezia реализованы в другой кодовой структуре — **не cherry-pick**, а порт
  логики в нашу `obf`/`timers` архитектуру. Изменения ограничены junk-подсистемой,
  hot-path шифрования не трогается.
- **LX-репо** (`option/`, `transport/wireguard/`) — обычный LX-слой.
- Тег сборки — существующий `with_awg` (новые ключи так же гейтятся; без тега
  UAPI отверг бы `j1/itime`).

## 4. Критерии приёмки

1. Конфиг с `{"itime":N,"j1":"<b 0x…>"}` парсится; невалидные комбинации
   (`Itime` без `J*`; `J*` без `Itime`) дают ошибку с именем поля.
2. `device_awg.go` эмитит `itime=`/`j1..j3=` в IpcSet; UAPI подмодуля принимает
   их без `IpcErrorInvalid`.
3. Периодическая отправка: в установившемся туннеле junk-пакеты уходят каждые
   `Itime` сек (проверяемо счётчиком tx / pcap на стенде).
4. Таймер не тикает на down/suspended peer (регресс к
   [[SPECS/020-MULTI_WG_IDLE_BUFFER_HEAT]] — не будить спящие WG).
5. **Живой хендшейк с реальным AWG2-сервером, у которого включены `Itime`/`J1-J3`**
   — туннель поднимается и держит трафик (главный критерий, стендовый).
6. Существующие AWG-конфиги без новых полей ведут себя идентично (backward-compat).
7. `gofmt`/`lx-check` чистые; junk-параметры остаются в наборе `with_awg`.

## 5. Оценка объёма

| Слой | Файлы | Характер | LOC (порядок) |
|------|-------|----------|---------------|
| Схема конфига | `option/wireguard_awg.go` | +4 поля, IsSet, валидация | ~30–50 |
| Обвязка → UAPI | `transport/wireguard/device_awg.go` | +4 строки по образцу i1..i5 | ~15–25 |
| UAPI подмодуля | `device/uapi.go` | +4 `case` (get+set) | ~40–60 |
| junk-state | `device/device.go` | `junk` struct: +`itime`, +`[]*obfChain` | ~10 |
| **Таймер отправки** | `device/junk-timer.go` (new) + врезка в `timers.go`/`send.go` | **новая логика** — сборка пакета из J-chains + периодический `time.AfterFunc` + гейт `timersActive` | ~80–140 |
| Тесты | `option/*_test.go`, `device/*_test.go` | парс/валидация + регресс на таймер | ~60–100 |

**Итого ~250–400 LOC.** Профиль риска — **не равномерный**:

- **Дёшево и предсказуемо (~60% строк):** конфиг, обвязка, UAPI-ключи, состояние.
  Всё по прямому образцу `I1-I5` — тот же CPS-парсер (`obfChain`), тот же паттерн
  проброса. Это «ещё 4 поля» уровня [[SPECS/005-AWG2_RANGED_MAGIC_HEADERS]].
- **Дорого и рискованно (~§2.2, новый таймер):** периодическая отправка junk —
  единственный **новый механизм**. Каркас (`timers.go`, `persistentKeepalive`)
  снижает риск, но врезка в send-loop требует стенда: гонки с хендшейком/keepalive,
  корректное гашение на suspend (иначе регресс к SPEC 020), поведение при роуминге.

Разбивка на PLAN/TASKS — при переводе в статус O. Ориентир: LX-слой (конфиг+UAPI)
— 1 подход; таймер+стендовая верификация — отдельный, основной по трудозатратам.

## 6. Открытые вопросы

- **Точная семантика `Itime` в апстриме:** период между пакетами vs jitter-окно;
  один пакет за тик или последовательность `J1→J2→J3`. Требует сверки с
  `amnezia-vpn/amneziawg-go` перед PLAN (не по памяти — по коду апстрима).
- **Нужна ли фича практически:** есть ли у целевой аудитории форка серверы с
  включённым `Itime`/`J1-J3`, или это «для полноты паритета». От ответа зависит
  приоритет (полный паритет vs реальный кейс — ср. [[SPECS/024-RUNTIME_LOOP_GUARD]],
  отложенную до воспроизводимого кейса).
