## 1. Состояние решений

## 2. Логика апстрима

Тип — **endpoint** `masque-client` (и парный `masque-server`). Один endpoint держит один туннель.

### 2.1 Сборка

`protocol/masque/client.go`, `NewClientEndpoint`:

1. Выбор версии HTTP: `version` 0 означает 3; без сборки с QUIC дефолт тихо становится 2.
2. Keepalive по умолчанию 10 с. `InitialPacketSize` QUIC = `mtu + 51`, то есть 1331 при `mtu` 1280.
3. Дайлер с `ResolverOnDetour`; `authority` берётся из заголовка `Host`, иначе из адреса сервера
   (порт 443 опускается).
4. Общий HTTP-клиент `transport/http` с блоком `tls` как есть.
5. Клиент туннеля `transport/masque.Client` и описание устройства `transport/device`.

### 2.2 Жизненный цикл

| Событие | Что происходит | Где |
|---|---|---|
| `Start`, стадия Initialize | Создаётся устройство (внутренний стек или системный TUN). Оно одно на всю жизнь endpoint'а | `protocol/masque/client.go`, `Start` |
| `Start`, стадия PostStart | Запускается фоновый цикл подключения | `transport/masque/client.go`, `loop` |
| Цикл | `connect()` → сеанс → по завершении пауза с backoff 1 с → 1 мин; после успешного сеанса backoff сбрасывается | `loop`, `connect` |
| Смена сети | `InterfaceUpdated` → `RestartSession`: текущий сеанс отменяется, соединения HTTP-клиента сбрасываются | `protocol/masque/client.go:214` |
| `on_demand` | Endpoint не считается используемым сам по себе. Учёт ссылок усыпляет его (`Suspend`), когда на него не ссылается маршрутизация либо устройство на паузе, и будит при первом dial или пакете (`Resume`) | `route/reference.go:173-181`, `:254-265` |
| Dial при неготовом туннеле | Без `on_demand` — сразу ошибка `endpoint is not ready yet`. С `on_demand` — пробуждение и ожидание готовности до `C.TCPTimeout` | `waitReady` |

Открытые соединения переживают переподключение туннеля, если адрес не сменился: стек не
пересоздаётся.

### 2.3 Открытие туннеля

`connect()` зовёт `httpClient.OpenTunnel(ctx, upgradeToken, path)` с таймаутом `C.TCPTimeout`.
Порядок попыток — в `transport/http/tunnel_client.go`, `openTunnel`:

| Шаг | Условие входа | Запрос | Что считается поводом идти дальше |
|---|---|---|---|
| HTTP/3 | h3 собран и не помечен сломанным | Extended CONNECT, `:protocol` = токен, `Capsule-Protocol: ?1` | Только `ErrHTTP3Unavailable`: отказ UDP-сокета, QUIC-хендшейка или открытия потока |
| HTTP/2 | есть TLS, h2 не помечен неподдерживаемым | CONNECT с заголовком `:protocol` | Только отсутствие `SETTINGS_ENABLE_CONNECT_PROTOCOL` у сервера |
| HTTP/1.1 | всегда последним | `GET` с `Connection: Upgrade`, `Upgrade: <токен>` | — |

Пометки:

- h3 после отказа помечается сломанным на 5 с, затем срок удваивается до 5 мин. Сброс — при успехе
  и при `ResetConnections` (смена сети).
- «h2 без Extended CONNECT» — липкий флаг до `ResetConnections`.
- `disable_version_fallback` запрещает все переходы.
- Ответ принимается только с кодом 200 (h3, h2) или 101 (h1).
- Чтение ответа на h3 привязано к контексту (`context.AfterFunc` с `CancelRead`/`CancelWrite`).

### 2.4 Сеанс

`transport/masque/client.go`, `connect`, и `session.go`:

1. Клиент шлёт `ADDRESS_REQUEST`: любой IPv4 (`0.0.0.0/32`, id 1) и любой IPv6 (`::/128`, id 2).
2. Если заданы `advertise_routes`, шлёт `ROUTE_ADVERTISEMENT`.
3. Два цикла чтения: датаграммы (если поток их умеет) и капсулы.
4. `ADDRESS_ASSIGN` → адрес применяется к устройству, устройство запускается, сеанс становится
   готовым, в лог уходит `assigned <адреса>`.
5. `ROUTE_ADVERTISEMENT` от сервера → список маршрутов; пакеты вне его получают ICMP no-route.
6. `ADDRESS_REQUEST` от сервера → отказ (назначение с неопределённым адресом).
7. Неизвестные типы капсул пропускаются.

**Готовность наступает только после шага 4.** До неё исходящие пакеты отбрасываются молча.

### 2.5 Пакеты

| Направление | Путь |
|---|---|
| Из стека в туннель | Проверка адресата по маршрутам → для пересылаемых пакетов уменьшение hop limit → датаграмма QUIC. Если датаграмма не помещается: ICMP Packet Too Big с фактическим пределом; предел ниже 1280 — сеанс рвётся. Если поток датаграммы не умеет — капсула DATAGRAM в потоке |
| Из туннеля в стек | Проверка адресата по своим адресам и объявленным маршрутам; чужой адресат → ICMP no-route обратно в туннель |

На h2 и h1 датаграмм нет, пакеты идут капсулами внутри TCP-потока.

### 2.6 Стек

`transport/device`: собственный TCP/IP-стек `sing-tun` либо системный TUN (`system: true`,
`name`). TCP, UDP и ICMP. Настройки UDP NAT (`udp_mapping`, `udp_filtering`, `udp_nat_max`,
`udp_timeout`). Endpoint двунаправленный: соединения, пришедшие из туннеля, отдаются в роутер.
gVisor в 1.15 не используется.

## 3. Логика наша

Тип — **outbound** `masque`. Реализация: `protocol/masque/outbound.go`, `transport/masque/`.

### 3.1 Сборка

1. Профиль (`cloudflare` по умолчанию, `standard`) задаёт токен протокола, заголовок для h2,
   URI и SNI по умолчанию, пиннинг.
2. TLS: самоподписанный клиентский сертификат на 24 часа генерируется из `private_key` при
   каждом старте; подлинность эндпоинта — сверка его ECDSA-ключа с `public_key`, цепочка не
   проверяется; SNI по умолчанию `www.cloudflare.com`.
3. Для h2 TLS идёт через общий слой `common/tls` — отсюда фрагментация ClientHello, в том числе
   автоматическая при диале через `detour`.
4. QUIC: `InitialPacketSize` 1242, keepalive 30 с, датаграммы включены. Объявляется устаревшая
   настройка `SETTINGS_H3_DATAGRAM_00` (0x276).
5. `UDPFragmentDefault = true`: внешнему сокету разрешена фрагментация (028).

### 3.2 Жизненный цикл

| Событие | Что происходит |
|---|---|
| Старт ядра | Ничего: туннель ленивый |
| Первый dial | Под мьютексом сборки создаётся gVisor-стек, открывается туннель, запускаются два насоса пакетов и, если задан `idle_timeout`, сторож простоя |
| Простой дольше `idle_timeout` | Туннель, стек и насосы разбираются; следующий dial собирает заново |
| Смерть туннеля | Разбирается всё, включая стек: открытые соединения рвутся. Причина один раз пишется в лог |
| Смена сети | Не обрабатывается. h3 замечает её по idle-timeout QUIC, h2 — по TCP keepalive |
| Повторные попытки | Фонового переподключения и backoff нет: каждая попытка — следствие чьего-то dial |

### 3.3 Открытие туннеля

| `vhttp` | Поведение |
|---|---|
| `h3` | QUIC → ожидание SETTINGS → Extended CONNECT с `:protocol` = `cf-connect-ip` → ответ 2xx → анонс маршрута по умолчанию |
| `h2` | TCP + TLS → HTTP/2 вручную на `Framer`: преамбула, SETTINGS, **обычный** CONNECT (`:method`, `:authority`) с заголовками `cf-connect-proto: cf-connect-ip`, `pq-enabled: false`, `capsule-protocol: ?1`, пустым `user-agent` |
| `auto` (дефолт) | h3 в отдельной горутине; через 3 с от поднятого UDP-сокета либо по ранней ошибке — h2. Победитель запоминается. Отказ запомненного h2 сбрасывает память и пробует h3 в той же попытке (108) |

Отличие от апстрима: поводом уйти с h3 служит **любой** исход, включая молчание сервера после
успешного QUIC-хендшейка.

### 3.4 Сеанс и пакеты

- Адрес туннеля берётся из конфига (`ip`, `ipv6`). `ADDRESS_ASSIGN` разбирается и сохраняется, к
  стеку не применяется. `ADDRESS_REQUEST` мы не шлём.
- `ADDRESS_REQUEST` от сервера и неизвестный тип капсулы обрывают поток.
- Шлём `ROUTE_ADVERTISEMENT` на весь IPv4 и IPv6.
- ICMP: только Packet Too Big с фиксированным 1280. TTL ≤ 1 отбрасывается без ответа.
- Только TCP и UDP (`network_list`); ICMP через туннель не ходит.

```bash
# отпечаток ключа эндпоинта для certificate_public_key_sha256
base64 -d <<< "$PUBLIC_KEY" | openssl dgst -sha256 -binary | base64
```

## 6. Швы

Шов — место, где наша правка входит в апстримный файл. Объём — оценка по чтению кода.

### Ш1. Токен протокола

| | |
|---|---|
| Что | WARP ждёт `:protocol = cf-connect-ip`, по RFC — `connect-ip` |
| Где | Константа `upgradeToken` в `transport/masque/session.go:17`, единственное использование — `transport/masque/client.go:166` |
| Правка | Поле токена в `ClientOptions`, подстановка в строке 166. Нижний слой `transport/http` токен уже принимает параметром |
| Объём | 6–10 строк |
| Серверная сторона | Не трогаем: `protocol/masque/server.go` регистрирует туннель под ключом `connect-ip` |
| Риск | Низкий |

### Ш2. Статический адрес

| | |
|---|---|
| Что | Адрес WARP выдаётся при регистрации устройства, а не капсулой |
| Где | `transport/masque/client.go`: отправка `ADDRESS_REQUEST` в `connect` (строки 185–188), готовность в `handleAddressAssign` и `updateConfiguration` |
| Правка | Если задан `address`: не слать `ADDRESS_REQUEST`, сразу вызвать `updateConfiguration` с адресами из конфига; пришедший `ADDRESS_ASSIGN` с другим адресом писать в лог предупреждением и не применять |
| Объём | 15–25 строк |
| Риск | Средний: неизвестно, что делает WARP в ответ на `ADDRESS_REQUEST` и шлёт ли `ADDRESS_ASSIGN` сам |
| Может не понадобиться | Если Э1 покажет, что WARP присылает `ADDRESS_ASSIGN` с адресом регистрации |

### Ш3. Обычный CONNECT на HTTP/2

| | |
|---|---|
| Что | На h2 WARP ждёт обычный CONNECT без `:protocol`, `:scheme`, `:path`; тип туннеля передаётся заголовком `cf-connect-proto`. `SETTINGS_ENABLE_CONNECT_PROTOCOL` он не объявляет |
| Где | `transport/http/tunnel_client.go`, `openTunnelHTTP2` (заголовок `:protocol` ставится всегда); `transport/http/client_h2.go`, `roundTripHTTP2` |
| Правка | Ветка «туннель обычным CONNECT»: форма запроса уже есть в `connectHTTP2`, поверх неё заголовок `Capsule-Protocol` и заголовки профиля |
| Объём | 10–20 строк |
| Риск | Средний: файл общий для HTTP-прокси, апстрим правит его активно. Штатный клиент `x/net/http2` может отказаться вести обычный CONNECT как двунаправленный поток — наша реализация ради этого ведёт h2 вручную |
| Без шва | Клиент получает отказ на h2 и уходит на h1, где WARP туннель не поднимает; в логе видна ошибка h1, а не причина |

### Ш4. Фолбэк при молчании после QUIC-хендшейка

| | |
|---|---|
| Что | Эндпоинт завершает QUIC-хендшейк и не отвечает на CONNECT. Наш полевой случай: блокировка по SNI и прокси-хоп, пропускающий только TCP |
| Где | `transport/http/client_h3.go`, `openStream`: ошибка после отправки запроса оборачивается в `HTTP/3 CONNECT`, а не в `ErrHTTP3Unavailable`; `tunnel_client.go`, `openTunnel` |
| Правка | Считать истечение срока ожидания ответа поводом для перехода на h2; срок — 3 с, как сейчас |
| Объём | 10–30 строк |
| Риск | Средний: меняет поведение общего клиента. Ограничить туннельным путём, HTTP-прокси не трогать |
| Без шва | Цикл повторяет h3 с backoff до 1 мин и на h2 не уходит |

## 7. Особенности и узкие места

### 7.1 Особенности WARP

| Особенность | Следствие |
|---|---|
| Не объявляет поддержку Extended CONNECT ни на h3, ни на h2 | На h3 апстрим этого не проверяет; на h2 штатный клиент отказывает — шов Ш3 |
| Свой токен `cf-connect-ip` | Шов Ш1 |
| Адрес выдаётся при регистрации | Шов Ш2 |
| Подлинность — по ключу эндпоинта, имя в сертификате не совпадает с SNI | `certificate_public_key_sha256` пропускает проверку цепочки — конфигом выразимо |
| Клиентский сертификат — самоподписанный из ключа регистрации | Сейчас выпускается на 24 часа при каждом старте. Примет ли WARP долгоживущий — не проверено |
| Имя эндпоинта в SNI режется DPI | SNI задаёт приложение; дефолта в ядре больше не будет |
| URI запроса — `https://cloudflareaccess.com` без пути | У апстрима путь обязан начинаться с `/`. Какой `:path` уходит у нас при пустом пути и важен ли он WARP — не проверено |
| С некоторых выходных адресов QUIC игнорируется без отказа | Шов Ш4 |

### 7.2 Особенности апстримной реализации

| Особенность | Следствие |
|---|---|
| Без `ADDRESS_ASSIGN` сеанс жив, но не готов; в логе об этом ничего | Отказ выглядит как таймаут dial. При испытаниях смотреть строку `assigned` |
| Код ответа строго 200 | Если WARP отвечает другим 2xx, нужен ещё один шов |
| Ошибка h2 про Extended CONNECT распознаётся по тексту (`extended connect not supported`) | Хрупко: смена текста в `x/net` молча отключит фолбэк на h1 |
| Флаг «h2 без Extended CONNECT» липкий до смены сети | После одного отказа h2 не пробуется |
| `InitialPacketSize` = `mtu + 51` | На путях с малым MTU первый пакет QUIC может не пройти. Задавать `initial_packet_size` явно |
| `on_demand` + dial: ожидание готовности до `C.TCPTimeout` | Первый запрос после сна платит полный подъём туннеля, как у нас |
| Без `on_demand` туннель поднимается на старте ядра | N узлов WARP в группе — N живых туннелей и N keepalive каждые 10 с |
| `DialEarly` под мьютексом клиента | Сброс соединений при смене сети ждёт конца хендшейка |
| Запись первых капсул до регистрации отмены | Заблокированная запись не прерывается ни сном, ни рестартом сеанса |
| Источник входящих пакетов не проверяется | Как и у нас |

### 7.3 Усыпление: таймер против учёта ссылок

| | `idle_timeout` (наш) | `on_demand` (апстрим) |
|---|---|---|
| Повод уснуть | нет трафика дольше срока | на узел не ссылается маршрутизация либо устройство на паузе |
| Узел выбран в группе, трафика нет | уснёт | не уснёт |
| Узел не выбран | уснёт по таймеру | уснёт сразу |
| Пауза устройства | не учитывается | усыпляет |

Для одиночного WARP как узла по умолчанию `on_demand` не усыпит туннель никогда, кроме паузы
устройства. Разница по батарее неизвестна, нужен замер (этап Э7). Если замер покажет проигрыш,
таймер простоя возвращается отдельным слоем поверх `Suspend`/`Resume`.

### 7.4 Узкие места, общие для обеих

- **TCP внутри TCP на h2 и h1.** Потеря одного сегмента задерживает все пакеты туннеля; два
  механизма повторной отправки мешают друг другу. h2 — запасной путь, не основной.
- **Фрагментация внешнего UDP.** С lx.8 на Linux и Android `UDPFragmentDefault` снимает DF явно.
  У `masque` по h3 он оставлен, хотя QUIC рассчитан на DF. После переноса решить заново: апстрим у
  своих QUIC-протоколов флаг убрал.
- **Холодный первый dial.** QUIC-хендшейк, CONNECT, стек: короткий таймаут `urltest` помечает
  свежий узел мёртвым на первой пробе.
- **TCP-only-хоп в `detour`.** h3 через него не проходит и отказа не даёт. Без Ш4 узел не поднимется.

### 7.5 Что меняется для пользователя

- Узел переезжает из `outbounds` в `endpoints`.
- Конфиги, написанные руками (роутеры с `lxd`), приложения не перегенерируют. Нужен либо один
  релиз с алиасом старого типа и предупреждением, либо таблица миграции в нотах.
- Через туннель начинает ходить ICMP.
- Соединения переживают переподключение туннеля.

## 8. Программа и методика испытаний

### 8.1 Цель

Установить, поднимает ли апстримный клиент туннель к WARP, какие швы для этого необходимы, и не
хуже ли результат нашей реализации по работоспособности, устойчивости и расходу энергии.

### 8.2 Объекты

| Обозначение | Что это |
|---|---|
| Н | Наше ядро `v1.14.2-lx.8`, outbound `masque` |
| А0 | Апстримное ядро из `upstream/testing` без правок |
| А1…А5 | А0 с наложенными швами по одному, в порядке Ш1, Ш2, Ш3, Ш4, Ш5 |
| Ц | Целевая сборка: ветка `lx` на базе 1.15 со всеми нужными швами |

### 8.3 Стенды

| Стенд | Состав | Для чего |
|---|---|---|
| С1 | Mac, прямой выход в сеть. Отдельный каталог с `upstream/testing` (обычный `git worktree`, форк-сабмодули ему не нужны), сборка с `with_quic`. Конфиг: `mixed`-inbound → узел WARP. Ключи и адреса реальной регистрации | Э1–Э5 |
| С2 | С1 плюс `tcpdump` на внешнем интерфейсе и `SSLKEYLOGFILE` для расшифровки QUIC и TLS в Wireshark | Снятие провода |
| С3 | С1 с `detour` узла через HTTP-прокси (TCP-only-хоп) | Ш4 |
| С4 | Android-устройство, LxBox с AAR из сборки Ц | Э6, Э7 |
| С5 | Пара А0: `masque-server` и `masque-client` на loopback | Контроль: швы не ломают работу по RFC |

Ограничения стендов, известные по прошлым работам:

- Лаунчер на Mac забирает маршрут по умолчанию в свой `utun` — на время испытаний выключать либо
  привязывать проверочный трафик к физическому интерфейсу.
- Эмулятор Android сетевые дефекты вендорского ядра не воспроизводит: С4 — только реальное
  устройство.
- Синтетический сервер поведение WARP не воспроизводит: вывод «работает с WARP» делается только
  на живом WARP.
- Один ключ регистрации у двух одновременно работающих клиентов даёт «хендшейк есть, данных
  нет». Н и А запускать по очереди либо на разных регистрациях.

### 8.4 Проверка работоспособности

Единая для всех этапов:

```bash
curl -s -x socks5h://127.0.0.1:12345 https://www.cloudflare.com/cdn-cgi/trace
```

Признак успеха — `warp=on` и адрес Cloudflare в `ip=`. Дополнительно: UDP через туннель
(DNS-запрос на 1.1.1.1 через SOCKS5 UDP), загрузка файла 100 МБ без обрыва.

### 8.5 Этапы

| Этап | Что делаем | Что фиксируем | От чего зависит дальнейшее |
|---|---|---|---|
| **Э0. Эталон провода** | Н на С2, подъём туннеля по h3 и по h2 | Расшифрованный обмен: заголовки запроса, код ответа, SETTINGS сервера, какие капсулы и в каком порядке шлёт WARP, размер первого пакета | Даёт образец, с которым сравниваются А |
| **Э1. Апстрим без правок** | А0 на С2, конфиг 5.3 без `profile` и `address` | Дошёл ли CONNECT, код ответа, пришёл ли `ADDRESS_ASSIGN` и с каким адресом, реакция на `ADDRESS_REQUEST`, строка `assigned` в логе | **Нужны ли Ш2 и Ш5; нужен ли шов на код ответа** |
| **Э2. Швы по одному** | А1…А5 на С1, h3 | После какого шва появляется `warp=on` | Минимальный набор швов для h3 |
| **Э3. HTTP/2** | `version: 2`, с Ш3 и без | Форма запроса на проводе против эталона Э0; не уходит ли клиент на h1; держит ли штатный клиент двунаправленный поток на обычном CONNECT | Реализуем ли Ш3 на штатном клиенте или h2 придётся вести вручную |
| **Э4. Фолбэк** | С3, `version: 3`, с Ш4 и без | Время от dial до `warp=on`; что в логе; возврат на h3 после снятия хопа | Срок ожидания в Ш4 |
| **Э5. Жизненный цикл** | Обрыв сети на 30 с; смена Wi-Fi ↔ мобильная; простой 10 мин; выключение ядра при живом туннеле | Переживают ли соединения переподключение; время восстановления; время `Close`; утечки горутин (`pprof`) | Сравнение с Н по тем же сценариям |
| **Э6. Устройство** | С4: работа час, пауза и пробуждение, вложение WG и AWG поверх узла WARP, узел WARP в группе `urltest` | `warp=on` после каждого события; трафик вложенного туннеля; поведение в группе | Готовность к выпуску |
| **Э7. Энергия и память** | С4, ночь простоя и час нагрузки, Н против Ц, `on_demand` включён и выключен | Расход батареи, RSS, число пробуждений | Возвращать ли таймер простоя |
| **Э8. Контроль RFC** | С5 до и после швов | Тесты апстрима `test/masque_test.go`; туннель по h3, h2, h1 | Швы не меняют поведение без `profile` |

### 8.6 Критерии

| Критерий | Порог |
|---|---|
| Подъём туннеля к WARP по h3 | `warp=on` в 10 запусках из 10 |
| Подъём по h2 | `warp=on` в 10 из 10 при `version: 2` |
| Фолбэк через TCP-only-хоп | `warp=on` не позже 5 с от первого dial |
| Восстановление после смены сети | не позже 10 с, открытые соединения живы |
| Выключение ядра при зависшем пути | `Close` не дольше 5 с |
| Утечки | число горутин после 50 циклов подъёма и сна равно исходному |
| Вложенный WG или AWG поверх WARP | трафик идёт, загрузка 100 МБ без обрыва |
| Энергия | Ц не хуже Н более чем на 10 % за ночь простоя |
| Контроль RFC | тесты апстрима зелёные на сборке со швами |

### 8.7 Порядок записи результатов

Результаты каждого этапа — в `TEST_RESULTS.md` этой задачи: дата, коммиты Н и А, конфиг без
ключей, команда, вывод, вывод по этапу. Дампы провода в репозиторий не кладутся: в них ключи
сеанса и адреса регистрации. Отрицательный результат записывается так же подробно, как
положительный.

### 8.8 Что можно сделать до выхода 1.15

Э0 и Э1. Они не требуют ни одной нашей правки в апстримном коде и отвечают на главный вопрос:
один ключ добавляем или два, и нет ли несовпадения, которого не видно по коду. Результат не
устаревает от перезаливки `testing`, пока апстрим не менял обмен капсулами.

1. Повторить Э0 и Э1 на актуальном апстриме.

## 11. Границы

- Серверная сторона (`masque-server`) берётся апстримная без швов; WARP-профиль на сервере не нужен.
- Дефекты апстримной реализации, не мешающие WARP (U1, U2, U5 из 107), не чиним: вклад в апстрим
  невозможен, а держать правки ради них дороже дефектов.
- Открытые дефекты нашей реализации (107 §6, кроме исправленных в 108) не чиним: они уходят вместе
  с кодом.
- CONNECT-UDP и HTTP-прокси апстрима в эту задачу не входят.
