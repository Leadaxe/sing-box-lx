## 1. Вопрос

«Мы все фишки AWG реализовали или не все?» — требовался ответ, проверяемый по
первоисточнику, а не по памяти.

## 2. Ответ: паритет по обфускации полный — 16 из 16

У AmneziaWG **нет нормативной спецификации** (нет RFC, нет whitepaper — в отличие
от WireGuard). Протокол задан реализациями, поэтому «истина» = пересечение
официальных реализаций. Сверка по трём независимым источникам:

| Источник | Роль | Набор параметров обфускации |
|---|---|---|
| `amneziawg-tools` `src/config.c` | что пользователь пишет в `.conf` (ближайшее к спеке конфига) | `Jc Jmin Jmax` · `S1–S4` · `H1–H4` · `I1–I5` · `AdvancedSecurity` |
| `amneziawg-linux-kernel-module` `src/uapi/wireguard.h` | netlink-контракт | `WGDEVICE_A_{JC,JMIN,JMAX,S1..S4,H1..H4,I1..I5}` · `WGPEER_A_ADVANCED_SECURITY` |
| **наш форк** (3 слоя: `option/` → `device_awg.go` → `device/uapi.go`) | — | `jc jmin jmax` · `s1–s4` · `h1–h4` · `i1–i5` |

**Вывод: все 16 параметров обфускации AWG у нас реализованы**, сквозной цепочкой
конфиг → UAPI → устройство. CPS-мини-язык `I1–I5` совпадает 1:1 — те же 8 тегов
(`b, d, ds, dz, r, rc, rd, t`), сверено с `obfBuilders` апстрима.

Формально в наборе есть ещё `AdvancedSecurity`, но это **серверное** поле,
неприменимое к клиенту (§5) — по клиентской части паритет **полный**.

**Интроспекция тоже полная.** Get-путь `device/uapi.go` отдаёт все 16 параметров,
включая `i1..i5` — они эмитятся циклом `sendf("i%d=%s", …)` (`uapi.go:144-148`), а не
отдельными `sendf("i1=…")`, поэтому при аудите грепом по литералам их легко
не заметить. Проверено живым прогоном `IpcSet` → `IpcGet`, а не грепом:
`device/lx_ipcget_awg_test.go` (`TestIpcGetReportsAWGParams`) — пинит все 16 ключей
в выводе и отсутствие незаданных слотов (`i2`/`i4`).

## 3. Чего в AWG НЕТ (отозванные гипотезы)

Фиксируется, чтобы не переоткрывать.

**`J1`, `J2`, `J3`, `Itime` — не существуют.** Ни в `amneziawg-go`, ни в
`amneziawg-tools`, ни в ядерном модуле. Исходная версия этой спеки описывала их
как «поздний слой advanced security» — это была ошибка памяти, не подтверждённая
кодом.

**«Advanced»-ключи из ветки `master` `amneziawg-go`** —
`header_protection_key`, `content_padding_addition`, `rekey_after_time`,
`rekey_timeout`, `reject_after_time`, `keepalive_timeout`,
`max_handshake_attempts` — **не часть AWG**:

- `amneziawg-tools` их не отправляет (проверено `config.c`/`set.c`/`setconf.c` —
  ни одного упоминания) ⇒ пользователь не может их задать, в `.conf` их нет;
- ядерный модуль их не знает (нет netlink-атрибутов).

Это неreleased разработка Go-ветки. Реальный AWG-сервер их не потребует — иначе он
был бы несовместим с официальным клиентом и с ядерным модулем. **Методический
вывод: `master` одной реализации ≠ протокол.** Сверять — по `amneziawg-tools`
(пользовательский набор) с кросс-проверкой ядерным модулем.

Часть этих ключей (`rekey_after_time`, `keepalive_timeout`,
`max_handshake_attempts`) — вообще локальные тайминги WireGuard, вынесенные в
настройку: они не согласуются с пиром и на совместимость не влияют.

## 4. Практический ответ про совместимость

К **любому серверу на официальном AmneziaWG** (Go-реализация или ядерный модуль,
выпущенные версии) наш клиент подключается: полный набор обфускации на месте.

Оговорка, не связанная с набором: всё это работает под тегом сборки `with_awg`;
без него UAPI подмодуля отвергнет `jc/i1/…` как неизвестные ключи
(`transport/wireguard/device_awg.go:34`).

## 5. `AdvancedSecurity` — серверное поле, вне scope клиента

Единственный параметр официальных реализаций, которого у нас нет. **Реализовывать
нечего:** вопреки названию, это не переключатель обфускации, а серверная сущность.

### 5.1 Device-level — не задаётся пользователем вообще

`wg->advanced_security` выводится автоматически: установка **любого**
junk-параметра по netlink ставит его в `true` (`netlink.c:780+`, 10+ одинаковых мест):

```c
if (info->attrs[WGDEVICE_A_JC]) {
	wg->advanced_security = true;
	wg->jc = nla_get_u16(info->attrs[WGDEVICE_A_JC]);
}
```

В `false` не выставляется **нигде**; отдельного device-атрибута для него нет.
Смысл ровно один: «на этом устройстве заданы AWG-параметры». У нас этот факт и так
известен по наличию параметров в конфиге, и на нём же держится
[[SPECS/TASKS/008-AWG_JUNK_PARAM_VALIDATION]] (у нас валидация безусловная — строже,
чем гейт `device.c:562`, который в модуле пропускает проверки при выключенном флаге).

### 5.2 Peer-level — про ВХОДЯЩИЕ соединения, роль сервера

Вычисляется при разборе **приходящего** handshake initiation (`noise.c:601`):

```c
bool advanced_security = wg->advanced_security &&
	mh_validate(SKB_TYPE_LE32(skb), &wg->headers[MSGIDX_HANDSHAKE_INIT]);
...
peer->advanced_security = advanced_security;          // noise.c:633
```

`mh_validate` проверяет magic header **пришедшего** пакета. То есть это запись факта
«данный пир прислал нам обфусцированный хендшейк» — так сервер различает AWG- и
обычных WG-клиентов на одном интерфейсе; значение уходит в
`wg_genl_mcast_peer_unknown(...)` (уведомление о неизвестном пире).

В `.conf` (`[Peer] AdvancedSecurity = true`) поле нужно **серверу**, чтобы заранее
пометить конкретного клиента как AWG. Показательно и расположение секций:
все 16 параметров обфускации — в `[Interface]`, а `AdvancedSecurity` —
единственный в `[Peer]` (`config.c:587`, ветка `ctx->is_peer_section`).

### 5.3 Почему клиенту это не нужно

- На **send-пути отсутствует** — в `send.c`/`receive.c` не встречается вообще.
  Наша отправка от него не зависит ни в каком варианте.
- В клиентском конфиге `[Peer]` описывает **сервер**; клиент не разбирает входящие
  initiation в этой роли и не рассылает уведомления о неизвестных пирах.
- Форк client-focused ([[fork-is-client-focused]]) — серверная сторона вне scope.

**Вывод:** это не зазор в паритете. Клиентская часть AWG у нас полная.

## 6. Критерии приёмки

Задача исследовательская — критерий один: ответ получен и обоснован ссылками на
код трёх реализаций (§2–§5). Выполнено, кода менять не требуется.

Побочный результат, закреплённый тестом: `device/lx_ipcget_awg_test.go`
(`TestIpcGetReportsAWGParams`) — round-trip `IpcSet` → `IpcGet` по всем 16 ключам.

## 7. Открытые вопросы

Нет. Оба прежних вопроса закрыты кодом, живой стенд не потребовался:

- ~~Нужен ли `AdvancedSecurity` практически?~~ — нет: серверное поле, §5.
- ~~Есть ли аналог флага в выпущенных `amneziawg-go`?~~ — вопрос снят вместе с
  предыдущим; в UAPI ветки `master` его нет, а клиенту он не нужен в принципе.
- ~~Расхождение get-пути (`i1..i5` не отдаются нашим UAPI)~~ — **закрыто, расхождения
  не было**: параметры отдаются циклом `i%d=`, подтверждено живым round-trip-тестом
  (см. §2). Ложная находка от грепа по литералам `sendf("i1=`.
