# SPEC: 121 — MASQUE_AUTO_MEMORY_TTL

**Фича:** [009-MASQUE_WARP](../../FEATURES/009-MASQUE_WARP/FEATURE.md)

| Поле | Значение |
|------|----------|
| Тип | B (bug) — `vhttp: auto` после одного быстрого отказа h3 парковал узел на h2 до рестарта или отказа h2 |
| Статус | I (implemented) — 2026-10-09: код, юниты, прогон на живом WARP с GL ([IMPLEMENTATION_REPORT.md](IMPLEMENTATION_REPORT.md)) |
| Ветка | `lx` |
| Build-tag | нет (lx-файл `protocol/masque/outbound.go`) |
| Источник | Наблюдение на стенде [120](../120-PATH_MTU_ALIGN/IMPLEMENTATION_REPORT.md): ~25 % подъёмов h3-туннеля к WARP падают сразу с `PROTOCOL_VIOLATION (remote)`, повтор проходит |
| Связано | [074](../074-MASQUE_VHTTP_AUTO/SPEC.md) (память режима), [108](../108-MASQUE_UNBOUNDED_WAITS/SPEC.md) (сброс памяти при отказе h2) |

Память h2 в `auto` — окно по лестнице: первая победа h2 помнится 1 с (на деле — «следующий
подъём снова пробует h3»), каждая следующая победа h2 берёт следующую ступень — 10 с, 30 с,
5 мин, 10 мин (верхняя повторяется), победа h3 возвращает на первую. Быстрый отказ h3 и тишина идут по одному правилу.

## 1. Проблема

Память режима из 074 придумана под один отказ — эндпоинт или TCP-only-хоп перед ним **молча
глотает QUIC**: ошибки нет, есть 3 с тишины, и платить их на каждом подъёме незачем. 108
добавил обратный ход только при отказе самого h2.

На живом WARP есть другой класс: сервер принимает QUIC, отвечает SETTINGS и закрывает
соединение на CONNECT-IP с `PROTOCOL_VIOLATION` без причины — за ~70 мс, сериями по 2–3 подъёма,
затем снова работает (стенд GL, 2026-10-09: 3 из 12 подъёмов, не зависит от `InitialPacketSize`).
Для `auto` это выглядело как «h3 упал → h2 победил → запомнить h2»: один такой сбой уводил узел
на TCP до рестарта процесса или до отказа h2 — молча, при живом h3.

## 2. Поведение

| Событие | Память | Окно |
|---|---|---|
| h2 победил (h3 молчал 3 с **или** отказал быстро — `PROTOCOL_VIOLATION`, `connection refused`, …) | h2 до истечения окна | текущая ступень: 1 с → 10 с → 30 с → 5 мин → 10 мин (ступень за каждую победу h2, верхняя повторяется) |
| Подъём по запомненному h2 | та же запись | окно **не продлевается**: отсчёт от фолбэка, h3 пробуется не чаще раза за окно |
| Окно истекло | сбрасывается на чтении, Info «remembered h2 expired after …; trying h3 first again» | следующий подъём — h3 → h2; если h2 снова победил, следующая ступень |
| h3 победил (сразу или поздно, после отказа h2) | h3 без окна | лестница возвращается на первую ступень: следующая победа h2 снова получит 1 с |
| Отказ запомненного h2 | сбрасывается немедленно (108) | ступень не трогается |
| Отмена вызывающим | ничего (074) | — |

Что это даёт: один случайный отказ h3 стоит ровно один туннель на h2 — следующий подъём
снова на h3. Канал, где h3 закрыт постоянно, за 4 подъёма сходится к пробе h3 раз в 10 мин (цена пробы —
3 с тишины на том подъёме). Ступеней мало намеренно: при молчащем h3 каждая ступень короче
периода пересоздания туннеля стоит одну 3-секундную пробу (при `idle_timeout: 5m` — 4 пробы
за ~20 мин, при ×2 с 0.1 с было бы 12 за час). С выключенным `idle_timeout` (дефолт) подъём туннеля —
редкое событие, и в обоих случаях расход незаметен.

## 3. Требования

1. Победа h2 записывается с окном по лестнице `autoH2MemoryLadder` = 1 с, 10 с, 30 с, 5 мин,
   10 мин: первая победа — первая ступень, каждая следующая — следующая, верхняя повторяется;
   по истечении память сбрасывается на чтении, следующий подъём начинает с h3.
2. Подъём по запомненному h2 окно не продлевает.
3. Победа h3 помнится без окна и возвращает лестницу на первую ступень.
4. Отказ запомненного h2 (108), отмена вызывающим (074) и остальное поведение `auto` не
   меняются. Outbound без проводки лестницы (юниты) помнит h2 без окна, как до 121.

## 4. Границы

- **Повтор h3 на быстрый отказ в той же попытке** (вместо ухода на h2) не делается здесь:
  отдельное решение после исследования причины.
- **Ступень не персистентна** между процессами и сбрасывается `Close()`.
- **Причина `PROTOCOL_VIOLATION`** не исследуется: гипотезы — разные бэкенды за anycast
  `162.159.198.2`, 0-RTT (`quic.DialEarly`), наша h3-специфика (`0x276`, пустой `User-Agent`).
  Программа опытов — в [IMPLEMENTATION_REPORT 120](../120-PATH_MTU_ALIGN/IMPLEMENTATION_REPORT.md).
- Режим `vhttp: h3` (пин) не затрагивается: быстрый отказ там остаётся ошибкой dial'а.
