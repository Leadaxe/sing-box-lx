# SPEC 033 — DNS-группа: тип `group`, режим failover

**Фича:** [DNS_GROUP](../../FEATURES/DNS_GROUP/FEATURE.md)

| Поле | Значение |
|------|----------|
| Тип | F (feature) |
| Статус | C (complete) |
| Ветка | `lx-1.14` (атомарные коммиты по зонам, пререлиз следом) |
| Связанные | [[SPECS/TASKS/034-DNS_GROUP_RACE]] · [[SPECS/TASKS/035-DNS_GROUP_OBSERVABILITY]] |

## 1. Проблема

Сбой DNS-сервера роняет резолв целиком: `dns.final` — сервер по умолчанию,
а не резерв; запрос, направленный правилом в сервер, при его сбое получает
ошибку без повтора. Полное поведение и контракт —
в [FEATURE.md](../../FEATURES/DNS_GROUP/FEATURE.md); эта задача реализует
тип `group` с режимом `failover` и `down_time`. Режим `race` — задача 034,
атрибуция фактического сервера в DNS-потоке — задача 035.

## 2. Архитектура

Новый пакет `dns/transport/group` — составной DNS-транспорт.

- **Регистрация** — штатный реестр (`dns.RegisterTransport[option.GroupDNSServerOptions]`),
  константа `C.DNSTypeGroup = "group"`, одна строка проводки
  в `include/registry.go`. Build-tag не вводится (обоснование в FEATURE.md,
  прецеденты: MASQUE_WARP, VLESS_ENCRYPTION).
- **Зависимости.** Адаптер создаётся `dns.NewTransportAdapter(C.DNSTypeGroup, tag,
  options.Servers)` — теги участников уходят в `Dependencies()`. Менеджер
  транспортов даёт за это бесплатно: топологический порядок старта
  (участники стартуют раньше группы), отлов циклов на старте
  (`circular server dependency`, включая группу-в-группе) и защиту
  участников от удаления.
- **Резолв участников** — в `Start(StartStateStart)`, по образцу
  `route/rule/rule_item_preferred_by_dns.go`: менеджер из контекста →
  `Transport(tag)` → ошибка `DNS server not found: <tag>` при отсутствии.
  Там же валидация состава: участник с типом `fakeip` или `hosts` —
  ошибка старта (локальные источники, резервировать нечего).
- **Exchange (failover)** — последовательный обход участников не в down-состоянии,
  на базе готового хелпера `dns/transport/exchange_strategy.go`
  (`ExchangeSequential` + `accept`-хук) либо эквивалентного цикла:
  - **сбой** = ошибка обмена (сеть/таймаут) или ответ/`RcodeError`
    с `SERVFAIL`. `NXDOMAIN` и пустой ответ — валидные ответы, отдаются
    как есть;
  - один сбой → участник помечается down на `down_time` (метка = время сбоя);
  - все участники down → одна попытка через участника с самой давней меткой;
    сбой обновляет метку (естественная ротация), ошибка уходит наверх;
  - дедлайн запроса — внешний (ctx от `dns.Client`, дефолт `C.DNSTimeout`);
    группа таймауты участников не переопределяет.
- **Состояние** — mutex + карта «тег → время последнего сбоя». Ничего
  не тикает: down-состояние проверяется лениво при обращении
  (инвариант ENERGY: нет трафика — нет активности).
- **Кеш** — выше транспорта, ключ = тег группы (`dns/client.go`,
  `dnsCacheKey{... transportTag}`): участники под кешем, кешируется только
  то, что группа вернула. Отдельного кода не требует — зафиксировать тестом
  поведения не нужно, это упстрим-слой.
- **`Reset()`** — фан-аут не нужен: менеджер сбрасывает все транспорты сам
  (`dns/router.go ResetNetwork`), группа сбрасывает только своё
  down-состояние.
- **Конфиг** — `option.GroupDNSServerOptions{Servers []string; Mode string;
  Interval badoption.Duration; DownTime badoption.Duration}`.
  Валидация в конструкторе: `servers` непустой (⚠️ badjson схлопывает `[]`
  в nil — проверка ловит оба случая одной ошибкой), `mode` ∈ {`failover`,
  `race`} (дефолт `failover`), `interval` при `mode: failover` —
  предупреждение в лог, игнорируется; `down_time` дефолт 30s.
  В этой задаче `mode: race` принимается схемой, но конструктор возвращает
  ошибку «mode race is not implemented yet» — чтобы 033 была выпускаемой
  отдельно; 034 заменяет ошибку реализацией.

## 3. Разграничение с upstream `race`/`evaluate` (тест §3.1(а2))

Upstream (коммит `5d744ada`, 1.14) добавил **rule-level** оркестровку:
действия `evaluate` с тегами ответов и флаги `race`/`speculative` на правилах.
Это композиция **запросов внутри одного резолва**, без памяти между
запросами: каждый запрос либо гонит все ветки заново (N× трафика на каждый
запрос), либо последовательно платит полный таймаут упавшей ветки.

Группа — **составной сервер с памятью здоровья**: `down_time` (сбойный
участник исключается для последующих запросов), победитель между гонками,
ленивый `interval`. Ни одно из этих свойств правилами не собирается —
у правил нет состояния между запросами. Плюс группа работает в `final`
и вложении, где rule-actions неприменимы. Это не переупаковка удобнее,
а другое поведение → а2 проходит. Слои не конфликтуют и не пересекаются
кодом: upstream-механика живёт в `dns/router.go` (правила), группа —
транспорт под менеджером.

Всё остальное — новые файлы `dns/transport/group/*`. Конфликт при ребейзе
возможен только как контекстный (соседние строки), содержательный — нет.

## 5. Критерии приёмки

- Юнит-тесты пакета (фейковые участники-транспорты):
  - failover по порядку списка; первый ответивший останавливает обход;
  - `SERVFAIL` (и ответом, и `RcodeError`) → переход к следующему;
    `NXDOMAIN` и пустой ответ → отдаются, обход не продолжается;
  - один сбой → down; в течение `down_time` участник не опрашивается;
    по истечении — опрашивается снова;
  - все down → ровно одна попытка через самого давнего; сбой ротирует;
  - `servers` пуст/`[]`/nil → ошибка; `fakeip`/`hosts` в составе → ошибка
    старта; неизвестный тег → ошибка старта;
  - цикл группа→группа→группа — ошибка старта менеджера (интеграционный
    тест через `TransportManager`).
- Живой `box.New` тест: конфиг с группой из двух udp-серверов принимается;
  `servers: []` отвергается (не прямой Unmarshal — правило badjson).
- `go build ./...` (без тегов) и `go build -tags "$LX_TAGS минус badlinkname/naive"`,
  `go vet`, `gofmt -l` по lx-файлам — чисто.
- `./sing-box check` на конфиге с группой в `final` и в правиле.

## 6. Вне скоупа

Режим `race` (034), атрибуция в DNS-потоке (035), RPC состояния группы
(отложено до запроса LxBox, см. 035), `mode: parallel` (расширение
по FEATURE.md).
