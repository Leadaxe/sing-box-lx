# SPEC: 144 — MTU_ALIGN_STREAM_BOUNDARY

**Фича:** [015-CHAIN](../../FEATURES/015-CHAIN/FEATURE.md)

| Поле | Значение |
|------|----------|
| Тип | B (bug) — `lx.mtu_align` зажимает IP-туннель ниже 1280 через ограничение, которого на пути нет; внутри туннеля пропадает IPv6 |
| Статус | N (new) |
| Ветка | `lx` |
| Build-tag | — (пакет `common/lxmtu`, как и 120 — всегда в сборке) |
| Источник | Полевой разбор владельца 2026-10-31, CPH2411, LxBox 2.25.18-rc.2, ядро `1.14.3-lx.24-rc.2` |
| Связано | [120](../120-PATH_MTU_ALIGN/SPEC.md) (модель ёмкости — меняется §2.1, §2.2), [073](../073-CHAIN_OUTBOUND/SPEC.md) (звенья `chain` выравниваются тем же пакетом) |

Выравнивание MTU из 120 получает три поправки. Узел, который сам доставляет датаграмму
целиком (поток или своя нарезка с пересборкой), обрывает ёмкость: ограничения под ним наверх
не идут. IP-туннель не опускается ниже 1280. У AmneziaWG в накладные входит паддинг `s4`.
Минимум по группе (120 §2.5) остаётся как есть.

## 1. Проблема

### 1.1 Полевой случай

Конфиг: WG-endpoint «🔗 Warp chain» (AWG 1.5 к WARP `162.159.192.181:4500`, `mtu` 1280,
адреса IPv4 + IPv6) с `detour: "Warp relay"`. `Warp relay` — selector примерно на 150 узлов
(vless, trojan, hysteria2, vmess, `direct-out`); выбран `direct-out`. DNS: `strategy: prefer_ipv6`.

URLTest узла на `https://www.gstatic.com/generate_204` даёт `-1` (таймаут 5 с), стабильно.
A/B на устройстве, 4G, один конфиг, меняется только `detour`:

| `detour` | IPv6 `[2606:4700:4700::1111]` | IPv4 `1.1.1.1` | `gstatic` |
|---|---|---|---|
| нет | 111–122 мс | 115–120 мс | 275–346 мс |
| `direct-out` | 258 мс | 96 мс | 299 мс |
| `Warp relay` | `-1` | 99 мс | `-1` |

Лог ядра в третьем случае:

```
lx: mtu_align: 🔗 Warp chain mtu 1280 → 1220 clamped (detour 🏠 Home server[wireguard] mtu 1280 via vpn-2 via 🏴 🇩🇪 Germany, Frankfurt am Main | [BL] via Warp relay − 60 ipv4)
```

### 1.2 Механизм

1. Один член `Warp relay` — vless + XHTTP — ходит через `detour: vpn-2`, а в `vpn-2` есть WG
   «🏠 Home server» с `mtu` 1280. По 120 §2.1 vless «с `detour`» транзитивно отдаёт ёмкость
   detour'а; группа берёт минимум; получается 1280, и «🔗 Warp chain» зажимается до
   1280 − 60 = 1220.
2. Ограничения на самом деле нет: WG-пакеты WARP идут в vless байтами TCP-потока. TCP поверх
   Home server сам берёт MSS по его 1280 и режет поток на сегменты; на той стороне поток
   собирается обратно. Пакет любого размера доходит целиком.
3. gvisor не поднимает IPv6 на канале с MTU меньше 1280 (`calculateNetworkMTU` →
   `ErrInvalidEndpointState`, [ipv6.go](../../../submodules/gvisor/pkg/tcpip/network/ipv6/ipv6.go)).
   IPv6-соединения внутри «🔗 Warp chain» висят без ошибки, IPv4 работает.
4. `prefer_ipv6` отдаёт домену AAAA первым, WG-endpoint диалит адреса по очереди
   (`N.DialSerial`), первая IPv6-попытка съедает весь таймаут URLTest. Приложения в TUN
   не замечают: у них Happy Eyeballs откатывается на IPv4.

Зажим ниже 1280 хуже, чем отсутствие `lxmtu`: без него внешние пакеты резались бы на
IPv4-фрагменты и проходили, а с ним IPv6 внутри туннеля пропадает целиком.

### 1.3 Недосчёт `s4`

`TunnelOverhead` считает AmneziaWG как WireGuard: 32 + IP/UDP. В AWG 2.0 перед каждым
транспортным пакетом идёт паддинг `s4`, и внешний пакет больше на `s4` байт. Под датаграммным
ограничением верхний туннель получает `mtu` на `s4` больше, чем влезает. `h1`–`h4` размер не
меняют; `jc`/`jmin`/`jmax`, `s1`–`s3`, I1–I5 относятся к хендшейку и в расчёт данных не входят.

## 2. Поведение

### 2.1 Ёмкость узла (заменяет таблицу 120 §2.1)

Граница — узел, который доставляет датаграмму сверху целиком сам, без IP-фрагментации
под собой. Над границей ёмкость `∞`, что бы ни лежало ниже. Свой собственный размер пакета
граница при этом выравнивает по своему `detour`, как сейчас (QUIC-узлы — §2.2 из 120).

| Класс | Узлы | Ёмкость наверх |
|---|---|---|
| Граница: поток | `vless`, `vmess`, `trojan` (любой транспорт), `anytls`, `trusttunnel`, `tuic` с `udp_relay_mode: quic`, `shadowsocks` / `socks` / `naive` с `udp_over_tcp`, любой узел с `multiplex` | ∞ |
| Граница: своя нарезка | `hysteria`, `hysteria2`, `tuic` с `udp_relay_mode: native` (режут сообщение больше датаграммы на куски и собирают на сервере — `fragUDPMessage` в sing-quic) | ∞ |
| Пропускающие датаграммы | `shadowsocks` (UDP), `socks` (UDP ASSOCIATE) | `capacity(detour)` минус свой заголовок; без `detour` — ∞ |
| IP-туннели | `wireguard` (endpoint и legacy outbound), `masque`, `tailscale`, `openvpn-client`, `openconnect` | эффективный `mtu` (после выравнивания и пола §2.2) |
| Группы | `selector`, `urltest` | min по членам, рекурсивно (без изменений) |
| `chain` как цель `detour` | — | ∞ + предупреждение (без изменений) |
| Физическая сеть | `direct` | ∞ |
| Без UDP | `http`, `ssh`, `tor`, `shadowtls` | ∞ |

Предупреждение для `tuic` native из 120 («может терять крупные датаграммы») снимается: по
коду sing-quic он их режет, а не теряет.

Нужно подтвердить по коду до реализации (§6):

- `trusttunnel` и `anytls` несут UDP потоком во всех режимах;
- `vless` с `packet_encoding: xudp` поверх QUIC-транспорта идёт стримами, не датаграммами;
- размер заголовка `shadowsocks` (по методу) и `socks` для вычитания.

### 2.2 Пол 1280 для IP-туннелей

IP-туннель не опускается ниже 1280, минимального MTU IPv6:

- `limit` ≥ 1280 — поведение 120 без изменений;
- `limit` < 1280, значение задано или дефолтное ≥ 1280 — эффективный `mtu` = 1280, в лог
  Warn: путь уже, чем нужно туннелю, внешние пакеты будут резаться на фрагменты;
- явный `mtu` < 1280 в конфиге не повышается (ни один режим не повышает значения, 120 §2.3).

Пол не касается `initial_packet_size` QUIC-узлов: у них свой кламп [1200, 1452] (120 §2.2).

### 2.3 Накладные AmneziaWG

Для WG-узла с заданным `s4`: накладные = 32 + `s4` + IP/UDP. Без `s4` — как сейчас.

### 2.4 Наблюдаемость

Строка решения (120 §4) называет причину пола:

```
lx: mtu_align: <tag> mtu 1280 → 1280 floor (detour <reason> − <overhead> <fam>; limit <N> below IPv6 minimum, packets will be fragmented)
```

Причина зажима через границу в строку не попадает: граница даёт ∞, решения нет.

## 3. Требования

1. Ёмкость считается по таблице §2.1; узел класса «граница» не передаёт ёмкость своего
   `detour` наверх.
2. Пропускающие датаграммы вычитают свой заголовок из ёмкости `detour`.
3. IP-туннель не получает эффективный `mtu` ниже 1280 от выравнивания (§2.2).
4. Накладные WG учитывают `s4` (§2.3).
5. Звенья `chain` идут через тот же расчёт и получают те же поправки.
6. Режимы, `except`, минимум по группе, кламп QUIC — без изменений.
7. Апстримные файлы не трогаются.

## 4. Критерии приёмки

1. Юнит: конфиг §1.1 (WG 1280 → selector из vless с `detour` на группу с WG 1280 и
   `direct`) — эффективный `mtu` верхнего WG = 1280, решения нет.
2. Юнит: WG 1408 → WG 1408 напрямую — верхний 1348 (поведение 120 сохраняется).
3. Юнит: WG → WG 1280 — верхний 1280 и Warn с `floor`.
4. Юнит: WG поверх hysteria2 поверх WG 1280 — верхний WG без изменений; hysteria2 получает
   свой `initial_packet_size` как раньше.
5. Юнит: WG поверх shadowsocks поверх WG 1408 — ёмкость 1408 минус заголовок ss.
6. Юнит: AWG с `s4: 20` поверх WG 1408 — верхний 1408 − 60 − 20 = 1328.
7. Юнит: группа из vless и hysteria2 поверх WG 1280 — оба члена граница, ёмкость группы ∞.
   Группа из vless и WG 1340 — ёмкость 1340.
8. Устройство: конфиг §1.1 без правок, сборка с фиксом — URLTest на `gstatic` и на
   `[2606:4700:4700::1111]` через «🔗 Warp chain» с `detour: "Warp relay"` проходит, в логе
   нет строки `clamped` для этого узла.

## 5. Границы

- Динамический MTU при переключении селектора не делаем (решение владельца 2026-10-31):
  живые TCP сохраняют MSS, QUIC фиксирует размер при создании клиента, нужен хук на смену
  выбора по всей цепочке. Вернуться при живом случае.
- TUN-инбаунд в расчёт не входит: TCP от приложений ядро открывает заново со своим MSS,
  размер UDP задаёт приложение.
- Зажим WG поверх WG остаётся: в диапазоне от 1280 до дефолта он убирает двойные пакеты
  фрагментов, ниже 1280 его останавливает пол.

## 6. Риски

- Неверная классификация узла как границы снимет нужный зажим — вернётся фрагментация
  (и потеря IPv6-фрагментов у WARP). Поэтому список §2.1 подтверждается по коду каждого
  протокола до реализации, неизвестный тип остаётся в классе «пропускающие».
- Пол 1280 на реально узком датаграммном пути означает фрагменты. По IPv4 они проходят;
  внешние IPv6-фрагменты к WARP не проверялись.
