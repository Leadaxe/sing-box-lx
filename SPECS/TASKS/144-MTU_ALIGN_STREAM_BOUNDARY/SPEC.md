# SPEC: 144 — MTU_ALIGN_STREAM_BOUNDARY

**Фича:** [015-CHAIN](../../FEATURES/015-CHAIN/FEATURE.md)

| Поле | Значение |
|------|----------|
| Тип | B (bug) — `lx.mtu_align` зажимает IP-туннель ниже 1280 через ограничение, которого на пути нет; внутри туннеля пропадает IPv6 |
| Статус | I (implemented) — код и юниты 2026-10-31 (§7); на устройстве не прогонялось |
| Ветка | `lx` |
| Build-tag | — (пакет `common/lxmtu`, как и 120 — всегда в сборке) |
| Источник | Полевой разбор владельца 2026-10-31, CPH2411, LxBox 2.25.18-rc.2, ядро `1.14.3-lx.24-rc.2` |
| Связано | [120](../120-PATH_MTU_ALIGN/SPEC.md) (модель ёмкости — меняется §2.1, §2.2), [073](../073-CHAIN_OUTBOUND/SPEC.md) (звенья `chain` выравниваются тем же пакетом) |

Выравнивание MTU из 120 получает три поправки. Ёмкость наверх несут только IP-туннели и
группы; любой другой узел — граница, что бы ни лежало под его `detour`. IP-туннель с IPv6
внутри не опускается ниже 1280. У AmneziaWG в накладные входит паддинг `s4`. Минимум по
группе (120 §2.5) остаётся как есть.

## 1. Проблема

### 1.1 Полевой случай

Конфиг: WG-endpoint «🔗 Warp chain» (AWG 1.5 к WARP `162.159.192.181:4500`, `mtu` 1280,
адреса IPv4 + IPv6) с `detour: "Warp relay"`. `Warp relay` — selector примерно на 150 узлов
(vless, trojan, hysteria2, vmess, `direct-out`); выбран `direct-out`. DNS: `strategy: prefer_ipv6`.

URLTest узла на `https://www.gstatic.com/generate_204` даёт `-1` (таймаут 5 с), стабильно.
A/B на устройстве, 4G, один конфиг, меняется только `detour`:

| `detour` | IPv6 `[2606:4700:4700::1111]` | IPv4 `1.1.1.1` | `gstatic` |
|---|---|---|---|
| нет | 111–122 мс | 115–120 мс | 275–346 мс |
| `direct-out` | 258 мс | 96 мс | 299 мс |
| `Warp relay` | `-1` | 99 мс | `-1` |

Лог ядра в третьем случае:

```
lx: mtu_align: 🔗 Warp chain mtu 1280 → 1220 clamped (detour 🏠 Home server[wireguard] mtu 1280 via vpn-2 via 🏴 🇩🇪 Germany, Frankfurt am Main | [BL] via Warp relay − 60 ipv4)
```

### 1.2 Механизм

1. Один член `Warp relay` — vless + XHTTP — ходит через `detour: vpn-2`, а в `vpn-2` есть WG
   «🏠 Home server» с `mtu` 1280. По 120 §2.1 vless «с `detour`» транзитивно отдаёт ёмкость
   detour'а; группа берёт минимум; получается 1280, и «🔗 Warp chain» зажимается до
   1280 − 60 = 1220.
2. Ограничения на самом деле нет: WG-пакеты WARP идут в vless байтами TCP-потока. TCP поверх
   Home server сам берёт MSS по его 1280 и режет поток на сегменты; на той стороне поток
   собирается обратно. Пакет любого размера доходит целиком.
3. gvisor не поднимает IPv6 на канале с MTU меньше 1280 (`calculateNetworkMTU` →
   `ErrInvalidEndpointState`, [ipv6.go](../../../submodules/gvisor/pkg/tcpip/network/ipv6/ipv6.go)).
   IPv6-соединения внутри «🔗 Warp chain» висят без ошибки, IPv4 работает.
4. `prefer_ipv6` отдаёт домену AAAA первым, WG-endpoint диалит адреса по очереди
   (`N.DialSerial`), первая IPv6-попытка съедает весь таймаут URLTest. Приложения в TUN
   не замечают: у них Happy Eyeballs откатывается на IPv4.

Зажим ниже 1280 хуже, чем отсутствие `lxmtu`: без него внешние пакеты резались бы на
IPv4-фрагменты и проходили, а с ним IPv6 внутри туннеля пропадает целиком.

### 1.3 Недосчёт `s4`

`TunnelOverhead` считал AmneziaWG как WireGuard: 32 + IP/UDP. В AWG 2.0 перед каждым
транспортным пакетом идёт паддинг `s4` (`send.go` форка), и внешний пакет больше на `s4` байт.
Под датаграммным ограничением верхний туннель получал `mtu` на `s4` больше, чем влезает.
`h1`–`h4` размер не меняют; `jc`/`jmin`/`jmax`, `s1`–`s3`, I1–I5 относятся к хендшейку и в
расчёт данных не входят.

### 1.4 Почему не перепаковка на входе в туннель

Masque и WG несут IP-пакет верхнего узла как одну датаграмму; на другом конце — чужой сервер
(WARP, чужой WG), который ждёт один пакет в одной датаграмме. Единственная «перепаковка» —
IP-фрагментация, и она уже делается gvisor'ом: по IPv4 фрагменты проходят (каждый пакет
едет двумя), по IPv6 WARP их теряет (120 §1.1). Источник больших пакетов — quic-go внутри
hysteria2 или стек верхнего WG; обратного сигнала к ним нет (сокет на netstack, ICMP и DF не
действуют), размер задаётся при создании. Отсюда выравнивание заранее — единственный путь.

Полный отказ от `lxmtu` рассматривался и отвергнут (2026-10-31): он откатывает дефолт
«hysteria2 через WARP на IPv6-сервер работает» (issue #37, с lx.14) и контракт звеньев
`chain` из 073 §3.5, а hysteria2 через WARP на IPv6 снова висит без строки в логе.

## 2. Поведение

### 2.1 Ёмкость узла (заменяет таблицу 120 §2.1)

Одно правило: ёмкость наверх несут только IP-туннели и группы. Любой другой узел — граница
с ёмкостью `∞`, что бы ни лежало под его `detour`. Классификация по протоколам не ведётся:
новый тип из апстрима автоматически граница.

| Класс | Узлы | Ёмкость наверх |
|---|---|---|
| IP-туннели | `wireguard`, `masque`, `tailscale`, `openvpn-client`, `openconnect` | эффективный `mtu` (после выравнивания и пола §2.2) |
| Группы | `selector`, `urltest` | min по членам, рекурсивно (без изменений) |
| `chain` как цель `detour` | — | ∞ + предупреждение (без изменений) |
| Всё остальное | прокси любого типа, `direct` | ∞ |

Чем это оплачено. Потоковые прокси (`vless`, `vmess`, `trojan`, `anytls`, `trusttunnel`,
`tuic` в `quic`, UoT, `multiplex`) доставляют датаграмму верхнего узла целиком, TCP под ними
сам берёт MSS; `hysteria`, `hysteria2`, `tuic` в `native` режут и собирают сами
(`fragUDPMessage` в sing-quic). У них ∞ по существу. `shadowsocks` и `socks` с UDP и
собственным `detour` на туннель пропускают ограничение датаграммами — этот транзит больше
не выравнивается (§5), явный `mtu` у верхнего туннеля остаётся выходом. Предупреждение для
`tuic` native из 120 снято: по коду sing-quic он режет, а не теряет.

Свой собственный размер граница при этом выравнивает по своему `detour`, как сейчас
(QUIC-узлы — 120 §2.2).

### 2.2 Пол 1280 для IP-туннелей с IPv6

IP-туннель, несущий IPv6 внутри, не опускается ниже 1280, минимального MTU IPv6. Несущий
IPv6: WG-endpoint с IPv6-префиксом в `address`; `masque` всегда (CONNECT-IP выдаёт оба
семейства). Туннель только с IPv4 внутри опускается как раньше: gvisor отказывает только
IPv6-endpoint'у, а фрагменты по IPv4 проходят.

- `limit` ≥ 1280 — поведение 120 без изменений;
- `limit` < 1280 у туннеля с IPv6 — предел поднимается до 1280; значение, которое в итоге
  выше `limit` (дефолт, опущенный до 1280; явное 1280), получает Warn: путь уже, чем нужно
  туннелю, внешние пакеты будут резаться на фрагменты;
- явный `mtu` < 1280 в конфиге не повышается (ни один режим не повышает значения, 120 §2.3)
  и предупреждения не получает: он влезает.

Пол не касается `initial_packet_size` QUIC-узлов: у них свой кламп [1200, 1452] (120 §2.2).

### 2.3 Накладные AmneziaWG

Для WG-узла с заданным `s4`: накладные = 32 + `s4` + IP/UDP. Без `s4` — как сейчас.

### 2.4 Наблюдаемость

Причина решения (120 §4) показывает `s4` и пол:

```
lx: mtu_align: wg-exit mtu 1408 → 1328 (default) (detour wg-in[wireguard] mtu 1408 − 80 ipv4 (s4 20))
lx: mtu_align: wg-exit mtu 1408 → 1280 (default) (detour wg-in[wireguard] mtu 1280 − 60 ipv4; floor 1280)
lx: mtu_align: wg-exit mtu 1280 is above the path: detour wg-in[wireguard] mtu 1280 − 60 ipv4; floor 1280 leaves 1220 bytes, below the IPv6 minimum 1280; outer packets will be fragmented
```

Причина зажима через границу в строку не попадает: граница даёт ∞, решения нет.

## 3. Требования

1. Ёмкость считается по таблице §2.1; узел не-туннель и не-группа не передаёт ёмкость
   своего `detour` наверх.
2. IP-туннель с IPv6 внутри не получает эффективный `mtu` ниже 1280 от выравнивания (§2.2).
3. Накладные WG учитывают `s4` (§2.3).
4. Звенья `chain` идут через тот же расчёт и получают те же поправки.
5. Режимы, `except`, минимум по группе, кламп QUIC — без изменений.
6. Апстримные файлы не трогаются.

## 4. Критерии приёмки

1. Юнит: конфиг §1.1 (WG 1280 с IPv4 + IPv6 → selector из vless с `detour` на группу с WG
   1280 и `direct`) — эффективный `mtu` верхнего WG = 1280, решения нет.
2. Юнит: WG 1408 → WG 1408 напрямую — верхний 1348 (поведение 120 сохраняется).
3. Юнит: WG с IPv6-адресом → WG 1280 — верхний 1280, решение с `floor`, Warn; тот же WG
   только с IPv4 — 1220 без Warn; явный 1200 — остаётся, без Warn.
4. Юнит: hysteria2 → vless → masque — hysteria2 не выравнивается, решений нет.
5. Юнит: WG поверх shadowsocks / socks с `detour` на masque — не выравнивается (§5).
6. Юнит: AWG с `s4: 20` поверх WG 1408 — верхний 1408 − 60 − 20 = 1328, причина с `(s4 20)`.
7. Юнит: группа из vless и hysteria2 поверх WG 1280 — ёмкость группы ∞, hysteria2 сам
   выровнен по своему туннелю. Группа из vless и WG 1340 — ёмкость 1340.
8. Юнит: masque 1280 поверх WG 1340 — остаётся 1280 с Warn (пол), hysteria2 над ним 1232.
9. Юнит (`chain`, карта опций): `s4` в накладных; пол по `address`; tuic native без
   предупреждения.
10. Устройство: конфиг §1.1 без правок, сборка с фиксом — URLTest на `gstatic` и на
    `[2606:4700:4700::1111]` через «🔗 Warp chain» с `detour: "Warp relay"` проходит, в логе
    нет строки `clamped` для этого узла. **Не прогнано.**

## 5. Границы

- Транзит ограничения через `shadowsocks` / `socks` с UDP и собственным `detour` на туннель
  не выравнивается (решение владельца 2026-10-31): ради него нужна таблица классов на все
  протоколы с проверкой по коду на каждом синке, а в поле такой конфиг не встречался.
  Выход — явный `mtu` у верхнего туннеля.
- Динамический MTU при переключении селектора не делаем (решение владельца 2026-10-31):
  живые TCP сохраняют MSS, QUIC фиксирует размер при создании клиента, нужен хук на смену
  выбора по всей цепочке. Вернуться при живом случае.
- TUN-инбаунд в расчёт не входит: TCP от приложений ядро открывает заново со своим MSS,
  размер UDP задаёт приложение.
- Зажим WG поверх WG остаётся: в диапазоне от 1280 до дефолта он убирает двойные пакеты
  фрагментов, ниже 1280 его останавливает пол у туннелей с IPv6.

## 6. Риски

- Пол 1280 на реально узком датаграммном пути означает фрагменты. По IPv4 они проходят;
  внешние IPv6-фрагменты к WARP не проверялись.
- Критерий 10 на устройстве не прогнан: подтверждение из поля впереди.

## 7. Реализация

Апстримных файлов ноль.

- `common/lxmtu/graph.go`: `capacityOf` — ветка «любой узел с `detour`» (`detourCapacity`) и
  предупреждение tuic native удалены, всё, что не туннель и не группа, — `Unlimited`;
  `alignOf` — `s4` через `tunnelPadding`, пол через `FloorIPv6` + `carriesIPv6`
  (WG — IPv6-префикс в `address`, masque — всегда), Warn `FloorWarning` при эффективном
  значении выше предела пути.
- `common/lxmtu/table.go`: `IPv6MinimumMTU`, `TunnelOverhead(type, server, padding)`,
  `OverheadText`, `FloorIPv6`, `FloorWarning`.
- `common/lxmtu/map.go` (`chain`): то же по карте опций — `mapPadding`, `mapCarriesIPv6`.
- `protocol/chain/mtu.go`: `leafCapacity` без ветки tuic native.
- Тесты: `common/lxmtu` (`TestResolverProxyBoundary` с полевым случаем §1.1,
  `TestResolverFloor`, `TestResolverAWGPadding`, `TestAlignMap` дополнен), пре-пасс
  `box_lx_mtu_test.go` (транзитивные случаи переписаны под границу), `protocol/chain`
  `TestChainMTU` зелёный без правок.
