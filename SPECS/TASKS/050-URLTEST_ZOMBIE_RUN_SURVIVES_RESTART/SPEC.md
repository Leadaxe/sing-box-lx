# SPEC: 050 — URLTEST_ZOMBIE_RUN_SURVIVES_RESTART

**Фича:** [HOTFIXES](../../FEATURES/004-HOTFIXES/FEATURE.md)

| Поле | Значение |
|------|----------|
| Тип | B (bug) — неотменяемая блокировка в связке XHTTP-транспорта, VLESS-encryption и urltest-прогона |
| Статус | O (open) — все три уровня в дереве, red/green проверен откатом фикса, `-race` чистый. Остаток: живой XHTTP-узел + device-верификация по `dumpStacks()` |
| Ветка | `lx` |
| Base | `137890db7` (v1.14.0-lx.20-rc.3) |
| Связанные | Полевой дамп LxBox 2026-08-04 (Android arm64, ядро `1.14.0-lx.17-rc.3`, подписка на 2806 узлов); код фичей [002 XHTTP](../../FEATURES/002-XHTTP/FEATURE.md), [007 URLTEST_BALANCE](../../FEATURES/007-URLTEST_BALANCE/FEATURE.md), [012 VLESS_ENCRYPTION](../../FEATURES/012-VLESS_ENCRYPTION/FEATURE.md) |

**Touches:** реестр HOTFIXES (новая строка). Промисы фич 002/007/012 не меняются — их поведение на живых узлах остаётся прежним, добавляется только отменяемость.

## Why

**URL-тест, застрявший на полуживом узле `vless + xhttp + encryption`, не
завершается никогда и переживает полную остановку ядра.** Остановленное ядро
продолжает держать горутины прогона и весь массив outbound'ов, по которому шёл
тест; каждый следующий запуск добавляет новое поколение зомби.

### Фактура

Дамп с устройства (Android arm64, ядро `1.14.0-lx.17-rc.3`), снят через 40 с
после успешного полного цикла Stop → Start:

- живы **два групповых прогона от прошлых сессий** — `URLTestGroup.testNodes`,
  заблокированные на `batch.Wait()` возрастом **100 и 43 минуты**, каждый по
  2806 узлов. В конфиге на момент дампа 592 узла: этих списков в текущей
  сессии нет, они остались от прежней подписки;
- их удерживают **6 горутин на одном и том же стеке** — `io.(*pipe).write` ←
  `v2rayxhttp.(*streamConn).Write` ← `vless/encryption.(*ClientInstance).Handshake`
  ← `vless.(*vlessDialer).DialContext` ← `urltest.URLTest`. Возраст 25–98 минут.
  Две из них запущены одиночным `URLTestOutbound` (RPC), четыре — групповым
  `testNodes.func1`;
- три поколения зомби (≈100 мин / ≈43 мин / текущее) — накопление с каждым
  перезапуском, не разовая аномалия;
- в том же дампе 5 OOM-снимков: memory 396–428 МБ, heap inuse 153–168 МБ,
  goroutines 285–397;
- пользователь сообщает «утерялся пинг» — группа, чей `batch.Wait()` не
  возвращается, результаты замеров не публикует;
- перезапуск VPN (полный Stop → Started в логе клиента) зомби **не убрал**;
  помог только ребилд конфига.

Все шесть зависших хендшейков — на узлах VLESS с транспортом `xhttp` и слоем
`encryption` (`mlkem768x25519plus`). Группа: `type: urltest`, `interval: 3m`,
`balancer.pool_tolerance > 0` — то есть путь `balancePoolTolerant`, тестирующий
**все** члены группы.

## Механизм

Три независимых дефекта, наложившись, дают наблюдаемую картину. Каждый из них
сам по себе не смертелен — смертельна их комбинация.

### Уровень 1 — заблокированный `Write` физически неотменяем

`dialStreamOne` возвращает conn **немедленно**, а `RoundTrip` уходит в отдельную
горутину ([`transport/v2rayxhttp/conn.go:51`](../../../transport/v2rayxhttp/conn.go)).
Тело запроса — это `io.Pipe`: запись в него разблокируется, только когда
`RoundTrip` начнёт читать тело (то есть когда TCP/TLS/h2-хендшейк прошёл и
сервер начал читать), либо когда pipe закроют.

Если узел полуживой — TCP принят, но h2 не поднялся, или сервер не читает тело —
`RoundTrip` висит, из pipe никто не читает, `streamConn.Write` блокируется
навсегда. И прервать эту блокировку нечем:

```go
func (c *streamConn) SetDeadline(t time.Time) error      { return os.ErrInvalid }
func (c *streamConn) SetWriteDeadline(t time.Time) error { return os.ErrInvalid }
```
[`transport/v2rayxhttp/conn.go:186`](../../../transport/v2rayxhttp/conn.go)

У conn нет дедлайнов вообще. Тот же паттерн у `splitConn` (stream-up).

### Уровень 2 — ctx не доходит до места блокировки

Выше по стеку — `ClientInstance.Handshake(conn)`
([`protocol/vless/encryption/client.go`](../../../protocol/vless/encryption/client.go)):
чистый `net.Conn`-API **без `context.Context`**, внутри — цикл фрагментированного
паддинга с `conn.Write(clientHello[:l])` и `time.Sleep` между фрагментами. Ctx
туда не передаётся и не проверяется.

Вызывается он из `vlessDialer.DialContext` через `wrapEncryption(conn)`
([`protocol/vless/lx_encryption.go:25`](../../../protocol/vless/lx_encryption.go)) —
уже **после** того, как conn создан. Поэтому `testCtx` с `C.TCPTimeout`
([`protocol/group/urltest.go:599`](../../../protocol/group/urltest.go)) ограничивает
только фазу диала: к моменту хендшейка отмена ctx не влияет ни на что, потому что
никто не закрывает conn по `ctx.Done()`.

Отсюда важное следствие: **одиночный `URLTestOutbound` тоже виснет навсегда**,
хотя его ctx безупречен — per-call gRPC-контекст с явным таймаутом
([`daemon/started_service_command_lx.go:68`](../../../daemon/started_service_command_lx.go),
это сознательное решение SPEC 015 §3.6). Отменять просто некому.

### Уровень 3 — `Close()` группы не трогает идущий прогон

`URLTestGroup.Close()` ([`protocol/group/urltest.go:409`](../../../protocol/group/urltest.go))
делает ровно три вещи: гасит ticker, снимает pause-callback, закрывает `g.close`.
Он **не отменяет `g.ctx`** и никак не связан с горутинами идущего прогона.
Канал `g.close` читает только `loopCheck` — цикл тикера; прогон, уже идущий
внутри `CheckOutbounds` → `balancePoolTolerant` → `testNodes`, про этот канал
не знает.

Сама горутина прогона порождена в `PostStart` как `go g.CheckOutbounds(false)` —
без WaitGroup, без регистрации, без возможности дождаться или прервать.
`testNodes` висит на `b.Wait()`, который ждёт **все** задачи batch: одна вечная
задача = вечный `Wait`. При `batch.WithConcurrencyNum(10)` шесть зомби из десяти
слотов означают, что прогон по 2806 узлам не продвинется в принципе.

Мелочь того же места: batch создаётся на `ctx` (аргумент функции), а задачи
внутри используют `g.ctx` — рассогласование, вторичное по отношению к главному
дефекту, но чинится тем же изменением.

### Как складывается наблюдаемая картина

| Наблюдение | Уровень |
|---|---|
| Горутины висят 25–98 минут | 1 — блокировку нечем прервать |
| Одиночный RPC-тест виснет вопреки корректному ctx | 2 — отмена не доходит |
| «Утерялся пинг» у группы | 3 — `testNodes` не возвращает результат до `Wait` |
| 396–428 МБ / зомби держат 2806 outbound'ов | 3 — прогон не отпускает ссылки |
| Перезапуск ядра не лечит, лечит только ребилд конфига | 3 — `Close()` прогон не отменяет |
| Три поколения зомби | 3 — каждый Start плодит новое, старое не умирает |

## Требования

**R1. У XHTTP-conn работают дедлайны.** `streamConn` и `splitConn` реализуют
`SetDeadline`/`SetWriteDeadline`/`SetReadDeadline` вместо `os.ErrInvalid`:
истёкший дедлайн прерывает висящий `Write` (и `Read`) ошибкой, а не держит
горутину. Это корневое требование — без него никакой слой выше не способен
ограничить блокировку.

**R2. Отмена диал-контекста рвёт повисший хендшейк.** Пока `dialStreamOne` /
`dialStreamUp` не отдали рабочий conn наверх, отмена ctx диала закрывает pipe и
освобождает горутину. Хендшейк `encryption`, идущий поверх такого conn, при
отмене завершается ошибкой.

*Форма механизма изменена [SPEC 077](../077-XHTTP_DIAL_CTX_CONTRACT/SPEC.md)
(2026-09-02):* сторож `watchDialContext` снят. `DialContext` сам не
возвращается, пока HTTP-слой не принял тело запроса, и отмена ctx диала до
этого завершает **сам dial** ошибкой контекста (pipe разорван, conn наверх не
отдаётся, слот пула возвращён) — хендшейку просто не на чем повиснуть. После
возврата dial-контекст на conn не влияет (контракт `net.Dialer`); повисший
после подъёма хендшейк ограничивают дедлайны R1.

**R3. `Close()` группы отменяет идущий прогон.** После `URLTestGroup.Close()`
горутины `testNodes` этой группы завершаются; они не остаются в дампе стеков
следующей сессии и не удерживают массив outbound'ов.

**R4. Живые узлы не деградируют.** Дедлайны и отмена не срабатывают на
нормальных узлах: успешный `stream-one` / `stream-up` / `packet-up` работает как
раньше, долгие фоновые соединения не рвутся по дедлайну диала.

## Критерии приёмки

1. **Стенд-репро (red/green).** Фиктивный XHTTP-сервер, который принимает TCP,
   но не читает тело запроса. До фикса: `urltest.URLTest` по такому узлу висит
   бесконечно, горутина остаётся после закрытия box. После: тест завершается
   ошибкой в пределах таймаута, горутина уходит. Узлы пользователя для этого
   не нужны.
2. **Отмена по ctx.** Отмена контекста, переданного в `URLTest`, прерывает тест,
   застрявший в фазе `encryption`-хендшейка, — а не только в фазе диала.
3. **Диагностический критерий с поля** (сформулирован владельцем дампа): после
   цикла Stop → Start в `dumpStacks()` **не остаётся горутин
   `URLTestGroup.testNodes` от предыдущей сессии**. Сейчас их две, возрастом
   100 и 43 минуты.
4. **Регрессия на живом узле.** `go test ./...` зелёный; XHTTP-узел
   (`stream-one` с REALITY, `packet-up`) проходит URL-тест и держит трафик как
   до фикса.
5. **Память.** На стенде с зависшими узлами RSS после Stop возвращается к
   базовому уровню — массив outbound'ов освобождается.

## Пост-релизные находки в зоне дедлайнов (2026-08-24, полевой разбор SPEC 074)

QUIC-хендшейк поверх xhttp-хопа, которому эндпоинт не отвечает, вскрыл два слоя
в `readDeadline` (`transport/v2rayxhttp/conn.go`) — оба видимы только когда
истечение дедлайна совпадает с активным закрытием со стороны потребителя
(quic-go зовёт `SetReadDeadline` из `Transport.Close` на своём dial-пути):

1. **Дедлок «колбэк под замком» — ИСПРАВЛЕН.** `expireLocked` вызывал
   `onExpire` (закрытие h2-тела) под удерживаемым `access`-мьютексом; закрытие
   блокировалось, и на замке вставали `stop()` и `set()` других потребителей —
   дамп горутин показал три горутины во взаимном ожидании, хендшейк висел
   20–90 с вместо бюджета. Фикс: `expireLocked` лишь помечает и отдаёт флаг,
   колбэк выполняется вне замка (`runOnExpire`). Прогон `-race` чистый.

2. **`transportResponseBody.Close` блокируется сам по себе — ОТКРЫТО.**
   `x/net/http2` завершает `Close` ожиданием `<-cs.donec`, который не закроется,
   пока не выйдет write-цикл request-body — а в stream-one это наш бесконечный
   upload-пайп с заблокированным Read (в апстриме рядом честный
   `TODO: Acquiring this mutex can block indefinitely`). По доктрине этого SPEC
   «рвать пайп с читающей половины» правильное направление — на expiry рвать
   соединение/writer, а не вежливо закрывать тело; требует аккуратного прохода
   по инвариантам R1–R3, впопыхах не делается. Потребитель (MASQUE `auto`,
   SPEC 074) от этого зависания отвязан архитектурно — решение здесь перестало
   быть блокером и делается в свой темп.

## Границы

- **Не меняем error-модель `URLTestOutbound`** (Variant B, SPEC 015 §3.6):
  таймаут остаётся полем `error` в ответе, не транспортной gRPC-ошибкой.
- **Не трогаем протокол `encryption`** — провод SPEC 032 остаётся байт-в-байт;
  добавляется только внешняя отменяемость поверх него.
- **Не меняем семантику `pool_tolerance`** и вообще логику выбора узлов
  (фича 007): чинится живучесть прогона, не его алгоритм.
- **Не вводим глобальный дедлайн на все соединения XHTTP** — дедлайн ставится
  на фазу теста/диала, длинные пользовательские соединения не ограничиваем.
