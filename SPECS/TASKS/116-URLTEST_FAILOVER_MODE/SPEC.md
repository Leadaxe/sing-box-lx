## 1. Назначение

У `urltest` было два режима и один флаг, который менял смысл одного из них.
`least_test` каждый `interval` меряет все узлы и переезжает на более быстрый.
`passive_check` поверх него пропускал циклы проб, пока через выбранный узел
шёл трафик, и тем самым **неявно** превращал least_test в «держимся за
рабочий узел»: другие узлы не мерились, переключений не было, цифры задержек
в UI устаревали. Энергетическая ручка и политика выбора оказались склеены в
одном флаге, и пользователь, включавший флаг ради тишины радио, получал
другую политику выбора, не заявленную нигде, кроме комментария в коде.

Решение владельца 2026-10-07: политика выбора живёт в `mode`, а
`passive_check` удаляется целиком. Три режима:

| `mode` | Выбор | Переключение | Что пробуется каждый `interval` |
|---|---|---|---|
| `least_test` (по умолчанию) | самый быстрый | как только кто-то быстрее на `tolerance` | все узлы |
| `round_robin` | пул живых | ротация по пулу | члены пула (лениво) |
| **`failover`** | самый быстрый на момент выбора | **только при отказе текущего**; следующий — снова самый быстрый | **только текущий узел** |

`least_test` остаётся честным: пробы ходят, выбор гонится за скоростью.
`failover` даёт то, что раньше получалось побочно, но явно и дёшево: одна
проба в `interval` вместо N, остальные узлы спят (SPEC 020), выбор стабилен.

## 2. Семантика `mode: failover`

### 2.1 Выбор

- **Первый выбор** — после первого полного прогона проб (старт группы):
  узел с минимальной задержкой среди ответивших, **без** `tolerance`.
  До первого результата действует апстримный холодный старт: первый узел
  списка, поддерживающий сеть.
- **Следующий выбор** (после отказа текущего) — снова самый быстрый среди
  живых по свежему полному прогону. Порядок в списке `outbounds` роли не
  играет (решение владельца 2026-10-07: «следующего выбираем по скорости,
  а не по порядку»).
- **TCP и UDP** держатся раздельно, как в апстриме (`selectedOutboundTCP` /
  `selectedOutboundUDP`); обычно это один и тот же узел.

### 2.2 Удержание

Пока текущий узел жив, группа его не меняет, даже если другой узел стал
быстрее. Возврата на «бывший лучший» по его оживлению нет.

Периодический тик (`interval`) пробует **только текущие узлы** (TCP-выбор и,
если отличается, UDP-выбор). Ответил — history обновлена, в UI у текущего
узла свежая задержка, выбор не меняется. Остальные узлы не пробуются, их
history стареет; это согласованная цена, в UI их задержки не актуальны.

### 2.3 Отказ текущего и переезд

Отказом считается любое из двух:

1. **Проба текущего не ответила** — history удалена, тик немедленно делает
   полный прогон по всем узлам и выбирает самый быстрый из ответивших.
   Переезд идёт через `performUpdateCheck`: `interrupt_exist_connections`
   действует как в апстриме.
2. **Боевой дайл класса «путь мёртв»** — машинерия SPEC 054 без изменений:
   штраф, один fallback-дайл через лучшего кандидата (по штрафам ↑, затем по
   задержке ↑ — то есть самый быстрый из нештрафников), успех переносит выбор
   на него без `Interrupt`. Аварийный режим и клапан тотальных штрафов
   (force-прогон не чаще раза в 2 минуты) действуют как в least_test.

После переезда новый узел становится удерживаемым: тик пробует его одного.

### 2.4 Ручной тест

`URLTest` группы из UI, CLI (`sing-box api group urltest <tag>`) или Clash
API всегда `force`: полный прогон по всем узлам и **перевыбор самого
быстрого**. Это единственный штатный способ вернуть группу на лучший узел,
пока текущий жив, и он же обновляет задержки всех узлов в UI.

### 2.5 Поля конфига

- `mode: failover` — новое допустимое значение; константа
  `C.URLTestModeFailover`.
- `balancer` с `failover` — **ошибка старта**, как и с `least_test`.
- `tolerance` в `failover` **не действует** (переключений «по скорости»
  нет); ненулевое значение даёт предупреждение при старте, по образцу
  `round_robin`.
- `url`, `interval`, `idle_timeout`, `interrupt_exist_connections` — как в
  апстриме. `idle_timeout` гасит тикер при простое группы; гейт достижимости
  SPEC 020 пропускает циклы недостижимой группы.

### 2.6 Энергия (связка SPEC 020)

Активная failover-группа будит один узел в `interval`, а не N. Узлы вне
выбора не получают проб, поэтому при включённом idle-suspend засыпают по
своим порогам и спят, пока текущий жив. Полный прогон (отказ, ручной тест,
клапан SPEC 054) будит всех — это редкое событие по определению режима.

### 2.7 Наблюдаемость

Протокол не меняется. `GetGroups`/`GetOutbounds` показывают текущий узел как
выбранный; задержка у него свежая, у остальных — на момент последнего
полного прогона. Clash API то же.

## 3. Удаление `passive_check`

Флаг удаляется целиком, без периода совместимости (решение владельца
2026-10-07: флаг никто не внедрил; в LxBox и лаунчере поддержки не было,
лаунчер добавил её в рабочей копии 2026-10-07 и откатит по этой спеке).

- `option.URLTestOutboundOptions.PassiveCheck` удаляется. Разбор конфига
  строгий, поэтому конфиг с ключом `passive_check` **не стартует** с ошибкой
  неизвестного поля. Это заявленное поведение, не дефект.
- Из `protocol/group` уходят: `passiveCheck` на `URLTest`/`URLTestGroup`,
  `passiveOK`, `markPassiveAlive`, `passiveFresh`,
  `selectedPassivelyConfirmed`, шов в `DialContext`, пропуск цикла в
  `urlTest`, пропуск подтверждённых слотов в `balancePoolFirstLive`, штамп в
  `penaltyFailoverDial`, предупреждение про `pool_tolerance > 0`, тесты
  флага.
- Документация: раздел `passive_check` из SPEC 019 переезжает в
  `SPECS/TASKS/019-URLTEST_MODE_STICKY/HISTORY.md` с обоснованием удаления
  и ссылкой сюда; упоминания в SPEC 054, FEATURE 007/008, README (оба
  языка), `docs-lx/lx-config{,.ru}.md`, `docs-lx/lx-energy{,.ru}.md`,
  `docs/configuration/outbound/urltest.md` переписываются под три режима.
  Исторические файлы (`docs-lx/releases/*`, `lx-changelog.md`, SPEC 020,
  RESEARCH 052) не трогаются.

## 4. Критерии приёмки

Юнит-тесты `protocol/group` (lx-файл тестов):

1. **Удержание.** failover, два живых узла, текущий медленнее — тик не меняет выбор.
2. **Одна проба.** За тик пробуется только текущий узел (счётчик проб по тегам).
3. **Переезд по пробе.** Текущий перестал отвечать — тик делает полный прогон и выбирает самого быстрого из живых; `interrupt_exist_connections` уважается.
4. **Переезд по дайлу.** Отказ «путь мёртв» через SPEC 054 переносит выбор на самого быстрого нештрафника; дальше тик пробует уже его.
5. **Нет возврата.** Бывший лучший ожил — выбор не меняется, пока текущий жив.
6. **Ручной тест.** `URLTest` (force) пробует всех и перевыбирает самого быстрого.
7. **Холодный старт.** До первого результата — первый узел списка; после первого прогона — самый быстрый.
8. **UDP.** UDP-выбор держится отдельно и переезжает по своему отказу.
9. **Конфиг.** `balancer` с `failover` — ошибка; ненулевой `tolerance` — предупреждение; `passive_check` в конфиге — ошибка разбора.
10. **round_robin и least_test** не меняют поведения: существующие тесты пакета зелёные после удаления `passive_check`.

Сборка `make -f Makefile.lx` целей lx под полным набором тегов и `go vet`
пакета; `gofmt` lx-файлов. Полевая проверка — через лаунчер после rc.
