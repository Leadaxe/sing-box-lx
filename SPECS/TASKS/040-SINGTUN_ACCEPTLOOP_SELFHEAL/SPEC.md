## Why

В system-стеке sing-tun весь новый TCP из TUN проходит через локальный
TCP-listener (`stack_system.go` `start()`: bind на адрес TUN, эфемерный порт,
`s.tcpPort`) и NAT-переписывание. Приёмная петля (`stack_system.go:370-384`):

```go
conn, err := listener.Accept()
if err != nil {
	return          // ← любая ошибка: петля молча умирает НАВСЕГДА
}
```

Если listener закрывается «из-под» стека (LxBox и libbox живут в одном
Android-процессе — общее пространство fd; чужой close по переиспользованному
номеру бьёт в Go-сокет), петля выходит **без единой строчки лога**, а стек
продолжает жить: `tunLoop` NAT-переписывает каждый новый SYN на кешированный
`s.tcpPort` мёртвого листенера, ядро ОС отвечает RST, RST де-НАТится обратно
приложению. Итог: **весь новый TCP — мгновенный `ECONNREFUSED` (~16 мс) до
рестарта VPN**; UDP/QUIC/DNS живут (listener-free путь), QUIC-приложения
маскируют поломку, браузер на не-QUIC сайтах мёртв.

Фактура с живого устройства (OnePlus CPH2411, Android 15, ядро
v1.14.0-lx.17-rc.3, LxBox 2.18.2-dev.13, 2026-07-31):

- goroutine-дамп сломанного состояния: `tunLoop`/`TCPNat`/`UDPNat` живы,
  `acceptLoop` отсутствует; после лечащего рестарта — присутствует;
- скан портов на адресе TUN: listener-сокета нет (закрыт);
- `ListenOverflows=0, ListenDrops=0` — SYN до сокета не доходят вовсе;
- поломка совпадает с окном быстрого рестарта VPN (Stopping→Started 600 мс);
- **репро**: серия быстрых `reconnect` (интервал ~4-5 с): 108 рестартов →
  3 поломки (итерации 8, 8, 22), затем 78 подряд чистых — вероятность
  кластеризуется на «грязном» процессе (fd-churn/GC), отсюда плавающий
  характер (§047: «каждый цикл деградации короче»).

Верифицированный воркфлоу-аудит Go-стороны (14 агентов, 2026-07-31):
внутри sing-tun/sing-box/LX-дельты закрывателя listener'а **нет**;
рестарт-путь daemon (`StartOrReloadService`/`CloseService`) строго
последователен и чист. Триггер — на Java-границе AAR (LxBox), приоритетный
подозреваемый — protect-путь (голый int fd каждого исходящего сокета уходит
в Kotlin `protect()`). Уточнение механики: голый чужой `close(fd)` НЕ будит
горутину, запаркованную в netpoll `Accept` (она осталась бы видна в дампе) —
раз петля исчезла, `Accept` вернул реальную ошибку: `ErrNetClosing`
(закрытие через Go-объект с тем же poll.FD) либо `EBADF`/`ENOTSOCK`
(close/переиспользование в момент активного `accept4`). Поэтому лог патча
обязан сохранять текст ошибки — errno называет путь убийства.

Ядровая половина бага — **молчаливая невосстановимость**: единичный внешний
сбой превращается в перманентный отказ TCP. Это чиним здесь; триггер чинится
на стороне LxBox.

Второй воркфлоу-аудит (Kotlin-сторона LxBox, 14 агентов, 2026-07-31): все
16 статических сценариев закрытия переиспользованного fd **опровергнуты**
чтением кода — триггер статикой не доказывается. План поимки — динамический,
на устройстве: `android_fdsan_set_error_level(FATAL)` (abort со стеком
нарушителя при чужом close) + логирование номеров fd (pfd в `openTun`,
listener при bind в Go) на репро-серии. Warn-лог этого патча (errno) — ядровая
половина той же инструментировки. Задача — в репо LxBox.

## What to build

Форк sing-tun сабмодулем (`submodules/sing-tun` на upstream-ревизии
`2d9b8aed5fe2` + `replace` в go.mod, по образцу wireguard-go) с патчем
самолечения `acceptLoop`:

1. **Штатное закрытие остаётся тихим**: `System.Close()` выставляет флаг до
   закрытия листенеров; петля, увидев флаг, выходит без шума (текущее
   поведение).
2. **Нештатная ошибка `Accept`** (флаг не выставлен):
   - warn-лог с полным текстом ошибки (errno различает
     `use of closed network connection` / `EBADF` / `ENOTSOCK` — называет
     путь убийства) и портом умершего листенера;
   - пересоздание листенера на том же адресе (`inet4Address:0` /
     `inet6Address:0`), обновление `tcpPort`/`tcpPort6`; замена безопасна
     относительно конкурентного чтения порта в `dispatchIPv4/6` и
     NAT-переписывании (`tunLoop` — другая горутина);
   - warn-лог о восстановлении (старый и новый порт); петля продолжает
     работу с новым листенером;
   - счётчик восстановлений (атомарный) — телеметрия; тикает ⇒ триггер в
     обвязке всё ещё жив.
3. **Отказ пересоздания** (bind не удался после ретраев): error-лог, петля
   завершается — не хуже текущего поведения; остаточный health-сигнал.

Существующие NAT-сессии, направленные на умерший порт, добиваются RST'ом —
приемлемо (единичные); новые SYN идут на новый порт.

## Acceptance criteria

- [ ] red/green: тест в форке sing-tun — поднять минимальный System-стек,
      закрыть listener «из-под» стека (минуя `System.Close`), новое
      TCP-соединение через стек: на upstream-ревизии `2d9b8aed5fe2` красный
      (refused навсегда), с патчем — зелёный (восстановление, соединение
      проходит);
- [ ] штатный останов: `System.Close()` не порождает warn/error-логов
      восстановления (регрессия);
- [ ] neighbours untouched: дифф форка против upstream `2d9b8aed5fe2` —
      только файлы патча; ядро собирается с `replace` без иных изменений;
- [ ] verification grade: **device** (pending: требует сборки AAR и
      установки LxBox) — серия быстрых `reconnect` ≥100 итераций: TCP-проба
      зелёная на каждой итерации ЛИБО в логах ядра warn «accept loop died …
      recreated» и TCP-проба зелёная сразу после; fingerprint: OnePlus
      CPH2411 / Android 15;
- [ ] запись в реестре HOTFIXES (FEATURE 004) с условием снятия: апстрим
      делает acceptLoop устойчивым (или заменяет механику system-стека).
