# SPEC 034 — DNS-группа: режим `race`

**Фича:** [DNS_GROUP](../../FEATURES/DNS_GROUP/FEATURE.md)

| Поле | Значение |
|------|----------|
| Тип | F (feature) |
| Статус | C (complete) |
| Ветка | `lx-1.14` |
| Связанные | [[SPECS/TASKS/033-DNS_GROUP_SERVER]] · [[SPECS/TASKS/035-DNS_GROUP_OBSERVABILITY]] |

## 1. Проблема

Failover (033) статичен: порядок опроса задан списком и не учитывает
фактическую скорость серверов. Режим `race` выбирает самый быстрый сервер
замером на **реальном запросе**, без синтетического трафика и без таймеров.
Контракт — [FEATURE.md](../../FEATURES/DNS_GROUP/FEATURE.md), раздел
Data flow / `race`.

## 2. Архитектура

Всё внутри пакета `dns/transport/group` (новый файл), схема конфига
готова в 033 — эта задача заменяет ошибку конструктора на реализацию.

- **Триггер гонки — ленивый.** При `Exchange`: если возраст последней гонки
  ≥ `interval` (или гонки ещё не было) — этот запрос становится гонщиком.
  Одновременные кандидаты сериализуются флагом «гонка уже идёт» под
  мьютексом: гонит один, остальные обслуживаются текущим победителем
  (или, до первой гонки, ждут её результат).
- **Фан-аут.** Запрос-гонщик уходит всем участникам не в down-состоянии
  параллельно. Готовый `ExchangeRace` из `dns/transport/exchange_strategy.go`
  НЕ используется — он отменяет проигравших, а гонке нужен полный порядок
  прихода. Свой фан-аут:
  - каждому участнику — горутина с контекстом, **отвязанным от запроса**
    (`context.WithoutCancel` + собственный таймаут `C.DNSTimeout`):
    ответ вызывающему уходит по первому успеху, а отставшие доигрывают
    в фоне и достраивают рейтинг;
  - первый **успешный** ответ (не сбой по классификатору 033; `NXDOMAIN` —
    успех) → ответ запроса, его участник — победитель;
  - порядок прихода успешных ответов → рейтинг; сбойные участники
    помечаются down (метка 033);
  - все сбойнули → ошибка запроса (агрегат), рейтинг пуст, время гонки
    всё равно фиксируется (следующая гонка не раньше `interval`,
    межгоночные запросы работают по правилам «все down» из 033).
- **Между гонками.** Запросы идут победителю. Его сбой → down + переход
  к следующему в рейтинге, не находящемуся в down; рейтинг исчерпан →
  правила 033 (порядок списка / самый давний down).
- **Ответы проигравших выбрасываются** — не возвращаются и, как следствие
  (кеш выше группы, ключ = тег группы), не кешируются. Достройка рейтинга
  в фоне результат запроса не меняет.
- **Состояние:** победитель, рейтинг (срез тегов), время последней гонки —
  под тем же мьютексом, что down-карта. `Reset()` сбрасывает и гоночное
  состояние (смена сети обесценивает замеры).

## 3. Критерии приёмки

- Юнит-тесты (фейковые участники с управляемыми задержками):
  - первая гонка: ответ = первый успешный; медленные достраивают рейтинг
    в фоне; повторный запрос до `interval` идёт ТОЛЬКО победителю;
  - запрос после `interval` запускает новую гонку; параллельные кандидаты
    не порождают вторую гонку одновременно;
  - сбойный участник гонки уходит в down и не участвует в следующей
    до истечения `down_time`;
  - сбой победителя между гонками → следующий по рейтингу;
  - `NXDOMAIN` от самого быстрого — валидный ответ гонки;
  - все сбойнули → ошибка, повторная гонка не раньше `interval`;
  - отставший ответ не меняет уже отданный результат (нет гонок данных —
    прогон с `-race`).
- Нет таймеров/тикеров: простой без трафика не порождает ни одного
  обмена (инвариант ENERGY) — проверяется тестом на фейках (нулевая
  активность участников без входящих запросов).
- DoD как в 033 (build ± теги, vet, gofmt, `sing-box check` с `mode: race`).

## 4. Вне скоупа

`mode: parallel` (гонка на каждый запрос), настройка домена-гонщика
(не нужен — гонка на реальном запросе), атрибуция в потоке (035).
