# SPEC: 061 — XHTTP_DIAL_DOWNLOAD_DEADLOCK

**Фича:** [XHTTP](../../FEATURES/002-XHTTP/FEATURE.md)

| Поле | Значение |
|------|----------|
| Тип | B (bug) — баг в фиче 002, в клиентском дайле с самого её появления ([002](../002-XHTTP_CLIENT_TRANSPORT/SPEC.md)) |
| Статус | I (implemented) — корень воспроизведён на проводе и устранён, регрессионный тест зелёный; **девайс-верификация открыта** |

Не ждать ответ на download-запрос внутри дайла. `packet-up` и `stream-up` должны отдавать соединение вызывающему сразу, иначе клиент и сервер ждут друг друга: сервер придерживает нисходящий поток до первого uplink-пакета, а мы придерживали первый uplink до нисходящего потока.

Build-tag: `with_xhttp`. Scope: **client-only**.

---

## 1. Проблема

Жалоба (2026-08-11): узел VLESS+XHTTP за CDN VK не поднимается на нашем ядре. Тот же конфиг на том же устройстве работает в NekoBox+ (тест 100 мс) и в v2rayN на десктопе.

Наблюдаемое в LxBox: пинг узла `-1`, в логе ядра —

```
open connection to … using outbound/vless[⚡ xhttp for CDN VK]:
v2ray-xhttp: unexpected download status: 504 Gateway Timeout
```

Путь трафика у пользователя: **CDN VK → nginx → Xray (3x-ui)**. Конфиг узла: `mode=packet-up`, `path=/upload/`, сессия в заголовке `X-Upload-Token`, seq в query `chunk_id`, паддинг `tokenish` в `queryInHeader`, `uplink_http_method=GET`, ALPN `h2,http/1.1`, uTLS `firefox`.

### 1.1 Корень: встречное ожидание в дайле

В `packet-up` сессия состоит из двух половин: download — GET, чей ответ и есть нисходящий поток; upload — отдельные запросы, по одному на запись.

Xray не отвечает на download-GET сразу: пока в сессию не пришёл первый uplink-пакет, слать вниз нечего, и ответ удерживается открытым.

Наш `dialPacketUp` делал зеркально противоположное — вызывал `RoundTrip` на download **синхронно** и проверял `StatusCode`, прежде чем вернуть `net.Conn` наверх:

```go
downResp, err := c.transport.RoundTrip(downReq)   // ждём ответ...
if downResp.StatusCode != http.StatusOK { … }
return &packetConn{reader: downResp.Body, …}, nil // ...и только теперь можно писать
```

Первый uplink не мог уйти, пока не пришёл download-ответ; download-ответ не мог прийти, пока не ушёл первый uplink. Обе стороны стояли. `dialStreamUp` имел ту же форму и ту же болезнь.

### 1.2 Откуда `504`, а не зависание

Сам дедлок молчалив — он бы висел до таймаута. `504 Gateway Timeout` дорисовывал обратный прокси перед Xray: зависший запрос упирался в его upstream-таймаут. Поэтому симптом выглядел как отказ сервера, хотя сервер был исправен.

Следствие для диагностики: **на прямом соединении с Xray, без прокси, баг проявляется иначе** — не `504`, а зависание до таймаута URLTest. Это объясняет, почему класс жалоб привязался именно к конфигурациям за CDN/nginx.

### 1.3 Почему у эталонного клиента работает

`sing-box-extended` (ядро NekoBox+) возвращает управление из `OpenStream` сразу после установки соединения — по `httptrace.GotConn`, — а HTTP-ответ разбирает асинхронно в горутине; читатель блокируется на `WaitReadCloser` до появления тела. Первый uplink уходит немедленно, сервер разблокируется, нисходящий поток открывается.

Разошлась только последовательность дайла. Сверка конфигурации транспорта нашего ядра (`/config/running` через Debug API LxBox) с бинарным профилем узла в NekoBox+ дала совпадение всех полей: путь, режим, размещения сессии и seq, параметры паддинга, метод uplink, диапазоны, ALPN, отпечаток.

### 1.4 Что причиной **не** является

Проверено и отброшено по ходу разбора — зафиксировано, чтобы версии не возвращались:

- **ALPN.** Сервер согласует `h2` при оффере `h2,http/1.1`. Наш транспорт всегда HTTP/2, и здесь это совпало с реальностью. (Отдельный риск сохраняется — см. §5.)
- **uTLS-отпечаток `firefox`.** Проходит. Ранние RST на пробах были rate-limit'ом CDN на IP тестовой машины: после паузы тот же отпечаток соединяется, а без паузы отбиваются и `chrome`, и остальные.
- **`xmux`.** В форке не реализован и в конфиг ядра не попадает, но на дайл не влияет: у эталонного клиента мультиплексор живёт **над** транспортом. Совместимость с `xmux` — отдельная задача [059](../059-XHTTP_XMUX/SPEC.md).
- **Конфигурация nginx у пользователя.** Ручные пробы `/upload/` дают `405` на POST и `400` на GET, но это нормальная реакция на запрос, не похожий на настоящую xhttp-сессию, а не признак неработающего `proxy_pass`.

## 2. Доказательство

Стенд: h2c-сервер, воспроизводящий контракт Xray — ответ на download удерживается до первого uplink того же сеанса; в роли upstream-таймаута прокси — `504` по истечении ожидания.

| Режим | До фикса | После фикса |
|---|---|---|
| `packet-up` | дайл не возвращается, затем `504` | conn отдан сразу; после первой записи приходит нисходящий поток |
| `stream-up` | то же | то же |

Красно-зелёный переход воспроизводим: `transport/v2rayxhttp/dial_deadlock_test.go`, оба режима, с `-race`.

Полевое подтверждение до фикса: на устройстве пользователя узел даёт `-1` и `504` в логе ядра, тогда как NekoBox+ на том же конфиге и в той же сети — 100 мс.

## 3. Требования

- Дайл `packet-up` и `stream-up` возвращает `net.Conn` **не дожидаясь** ответа на download-запрос; `RoundTrip` выполняется в горутине.
- Reader соединения связывается поздно: до его появления `Read` ждёт, а не обращается к `nil`. Ошибка download доставляется тому же `Read` вместо тела.
- `Close` до появления ответа не трогает несвязанное тело и не роняет клиент; повторный `Close` не закрывает тело дважды.
- Read-дедлайн в `packetConn` — рабочий (прежде `os.ErrInvalid`): при несвязанном reader закрывать нечего, и только дедлайн способен освободить залипший `Read`.
- `stream-one` не затрагивается: там тело запроса и так стримится, а ответ уже разбирался асинхронно.

## 4. Критерии приёмки

- Регрессионный тест против сервера, удерживающего download до первого uplink: дайл завершается, запись проходит, нисходящий поток приходит — в обоих режимах.
- Тесты пакета зелёные с `-race`.
- **Полевая проверка (открыта):** узел за CDN VK в LxBox с новым AAR — туннель, URL-тест, реальный трафик.

## 5. Границы

- Только клиент; серверная сторона XHTTP в форке не реализуется.
- `xmux` не реализуется здесь — задача [059](../059-XHTTP_XMUX/SPEC.md).
- **Известное ограничение, вне этой задачи:** транспорт всегда `http2.Transport`, тогда как ALPN уходит на провод из конфига. Если сервер выберет `http/1.1`, дозвона не будет. На этом узле не проявляется — сервер отвечает `h2`.
