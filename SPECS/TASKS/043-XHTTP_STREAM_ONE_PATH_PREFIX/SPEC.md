# SPEC: 043 — XHTTP_STREAM_ONE_PATH_PREFIX

**Фича:** [XHTTP](../../FEATURES/002-XHTTP/FEATURE.md)

| Поле | Значение |
|------|----------|
| Тип | B (bug) — баг в фиче 002, внесён задачей [011](../011-XHTTP_STREAM_ONE_DOWNLINK/SPEC.md) |
| Статус | C (complete) — корень воспроизведён на проводе, устранён, **девайс-верифицирован**; отгружен в `v1.14.0-lx.17` |

Восстановить завершающий слэш в пути `stream-one`. Без него запрос не проходит префиксную проверку XHTTP-сервера, получает 404 и висит до таймаута — а вместе с ним не работает `mode:auto` при REALITY, то есть типовой конфиг из подписок.

Build-tag: `with_xhttp`. Scope: **client-only**.

---

## 1. Проблема

Жалоба (2026-08-01): 14 XHTTP-нод подписки мертвы на нашем ядре. Те же ноды на том же устройстве, в той же сети, той же подпиской поднимаются в стороннем клиенте (NekoBox+) за 34–36 мс.

Наблюдаемое: дозвон открывается, ядро логирует `outbound connection to …` и молчит — ни ошибки, ни успеха. Соединение висит до таймаута URLTest.

### 1.1 Корень: сервер отбрасывает путь без слэша

XHTTP-сервер нормализует **свой** путь и сверяет с ним каждый запрос по префиксу:

```go
s.path = options.GetNormalizedPath()             // "/api/v1/feed/"
if !strings.HasPrefix(request.URL.Path, s.path) {
    writer.WriteHeader(http.StatusNotFound)      // 404
}
```

`GetNormalizedPath()` добавляет завершающий `/`, когда сессия или seq размещены в пути — а это значение по умолчанию. То есть сервер, настроенный на `/api/v1/feed`, обслуживает `/api/v1/feed/…` и отвергает `/api/v1/feed`.

Наш клиент в `stream-one` слэш **срезал**: `trimBarePathSlash` в `applyMeta`. На провод уходило `POST /api/v1/feed` → префикс не совпадал → 404 → зависание.

### 1.2 Почему это выглядело как «сломан auto»

`mode:auto` при REALITY разворачивается в `stream-one` (у нас, у Xray и у NekoBox одинаково — сверено с Xray v26.7.28 и NekoBox-ядром `starifly/sing-box@7567ef41`). У нод из жалобы REALITY включён на всех, поэтому `auto` вёл ровно в сломанную ветку.

`packet-up` при этом работал: его путь продолжается в `/<sessionId>`, префикс совпадает. Отсюда наблюдение «`packet-up` живой, `auto` мёртвый», которое ошибочно указывало на разрешение режима.

### 1.3 Откуда взялся срез

Задача [011](../011-XHTTP_STREAM_ONE_DOWNLINK/SPEC.md) чинила реальный баг — `stream-one` слал `<path>/<sessionId>`, из-за чего сервер уходил в stream-down-ветку. Вместе с sessionId был убран и слэш, по посылке «сервер ждёт точный голый путь». Посылка неверна: пустым должен быть **sessionId**, а слэш — часть нормализованного пути. 011 принималась на синтетике, живой прогон оставался открытым TODO, и юнит-тесты закрепили ошибочное ожидание.

## 2. Доказательство

Стенд: HTTP/2-сервер с той же префиксной проверкой, что у Xray/NekoBox; наш клиент дозванивается напрямую.

| | путь на проводе | вердикт сервера |
|---|---|---|
| `stream-one` до фикса | `/api/v1/feed` | `REJECT 404 — lacks prefix "/api/v1/feed/"` |
| `stream-one` после фикса | `/api/v1/feed/` | `ACCEPT` |
| `packet-up` (не менялся) | `/api/v1/feed/<uuid>/0` | `ACCEPT` |

Красно-зелёный переход воспроизводим.

---

## 3. Требования

- В `stream-one` путь несёт завершающий `/` ровно при том же условии, что у Xray: сессия **или** seq размещены в пути (значение по умолчанию).
- При размещении сессии вне пути (header/query/cookie) путь уходит на провод как настроен — слэш не добавляется и не срезается.
- sessionId в `stream-one` по-прежнему **не** отправляется: пустой sessionId — то, по чему сервер выбирает двунаправленную ветку (достижение 011 сохраняется).
- `packet-up` и `stream-up` не затрагиваются.

## 4. Критерии приёмки

- Регрессионный тест: путь `stream-one` совпадает с нормализованным префиксом сервера для `/api/v1/feed`, `/api/v1/feed/` и `/`.
- Конфиг `mode:auto` + REALITY из реальной подписки поднимается без правок пользователем.
- Полевая проверка: XHTTP-ноды подписки отвечают на URLTest.

## 5. Границы

- Только клиент; серверная сторона XHTTP в форке не реализуется.
- `downloadSettings` (третья ступень `auto` → `stream-up`) не поддерживается, как и раньше.
- Hysteria2-ноды той же подписки мертвы независимо от ядра (UDP/QUIC режется каналом — подтверждено: в стороннем клиенте без туннеля они тоже в тайм-ауте). К фиче 002 отношения не имеет.
