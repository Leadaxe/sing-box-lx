# SPEC: 161 — HTTP_CONNECT_OUTAGE_LEAK

**Фича:** [HOTFIXES](../../FEATURES/004-HOTFIXES/FEATURE.md)

| Поле | Значение |
|------|----------|
| Тип | B (bug) — неограниченное ожидание ответа HTTP CONNECT при отказе прокси |
| Статус | I (implemented) — тесты под `-race`, сборки и стенд со Squid зелёные ([PR #73](https://github.com/Leadaxe/sing-box-lx/pull/73)) |
| Ветка | `lx` |
| Источник | [issue #74](https://github.com/Leadaxe/sing-box-lx/issues/74), [PR #73](https://github.com/Leadaxe/sing-box-lx/pull/73). Воспроизведение на официальном `v1.14.4-lx.33` |

## Проблема и границы доказательства

HTTP-прокси принимает TCP и CONNECT, но не отвечает. Обычный маршрутизируемый
трафик не имеет срока ожидания CONNECT: таймаут TCP закончился при установке
сокета, а таймаут urltest распространяется только на пробы. Закрытие SOCKS-клиента
не прерывает заблокированный `http.ReadResponse` ядра. Повторные попытки удерживают
горутины, сокеты, буферы и стеки без предела.

Локальный стенд, три волны по 256 запросов с закрытием клиента через 150 мс и
ожиданием 20 с после каждой: горутины 12 → 268 → 524 → 780, fd
10 → 522 → 1034 → 1546; RSS 77 956 → 126 324 KiB. Профиль показывает
`sing/protocol/http.Client.DialContext` → `http.ReadResponse`.
Все процессы стенда ограничены cgroup 512 MiB, без swap и без TUN.

Немедленный HTTP 503 — другой случай: 16 000 отказов не дали накопления ресурсов,
после восстановления успешны 200/200 запросов. Отказ с немедленным
503 и отсутствие ответа CONNECT — разные режимы, их результаты учитываются
раздельно.

## Контракт

- Ожидание HTTP CONNECT после установки нижележащего соединения ограничено
  `constant.TCPTimeout` (15 с), включая запись запроса и чтение неполного ответа.
- Более ранняя отмена/дедлайн вызывающего по-прежнему прерывает запрос.
- Истечение сторожа возвращает `CONNECT handshake timeout` с
  `os.ErrDeadlineExceeded`. Ответы прокси и ошибки вызывающего сохраняют причину.
- При отказе или таймауте сокет закрывается; при успехе сторож снимается.
- Исход попытки решает один атомарный переход между сторожем и завершением
  CONNECT. Вызывающий получает либо туннель, который сторож уже не закроет,
  либо таймаут без соединения; если ответ пришёл, когда сторож уже закрывал
  сокет, соединение не возвращается.
- Новый таймаут не передаётся в `detour` и не меняет время жизни успешного
  транспорта, исходный контекст и `connect_timeout` нижележащего дайлера.
- HTTP-заголовки, авторизация и уже прочитанные байты туннеля сохраняются.
- Новых JSON-полей, build-tag, зависимостей и изменений UI нет.

## Реализация

Логика — в `protocol/http/handshake_lx.go`. В апстримном
`protocol/http/outbound.go` два помеченных места (`// lx: SPEC 161`):

- в конструкторе — блок перед литералом `Outbound`, который оборачивает
  нижележащий дайлер в `httpHandshakeDialerLx`; апстримная строка
  `Dialer: detour` не правится;
- в `DialContext` — вызов `dialHTTPWithHandshakeTimeoutLx` вместо прямого
  `h.client.DialContext`.

`dialHTTPWithHandshakeTimeoutLx` кладёт состояние попытки в значение контекста
и вызывает HTTP-клиент из `sing`. Клиент зовёт обёртку дайлера; та дозванивается
нижележащим дайлером с исходным контекстом и только после его возврата ставит
таймер, закрывающий соединение. Когда клиент вернулся, функция отмечает
попытку завершённой, останавливает таймер и обнуляет ссылку на него: `detour`
может держать контекст дозвона всё время жизни сессии, и сокет через него
удерживаться не должен. Обёртка, вызванная без состояния в контексте,
возвращает соединение как апстрим, без сторожа.

Порог — переменная пакета `httpConnectHandshakeTimeoutLx`, по умолчанию
`constant.TCPTimeout`; ключа конфига нет, тесты её сокращают.

## Приёмка

`TestLxHTTPConnectOutage` на реальном loopback TCP проверяет зависший CONNECT,
неполный ответ, раннюю отмену и дедлайн, 503, освобождение сокета и успешное
соединение через `detour` после бюджета хендшейка.
`TestLxHTTPConnectWatchdogRace` отвечает на параллельные CONNECT в пределах
нескольких миллисекунд вокруг истечения сторожа и проверяет исход каждой
попытки по контракту выше. lx-ci запускает пакет под `-race`. Стенд с реальным HTTP-прокси сравнивает накопление горутин и fd при
контролируемом отказе и проверяет восстановление трафика.
Сборки выполняются с закреплёнными в HEAD сабмодулями, без пользовательских
изменений их рабочих копий. Живой VPN и бинарь бандла не затрагиваются.

## Основание принятия

Дефект воспроизведён на стенде с живым сервером — Squid 6.12 с приостановленным
ACL-помощником. По CONSTITUTION §3.1 это воспроизведение в реальной практике.

С пользовательской установки данных нет. Сообщение из чата лаунчера, с которого
начался issue #74, показывает немедленные ответы 503 — другой режим, без
накопления ресурсов; утечку на той установке эта правка может не закрывать.

## Условие снятия

Удалить оба помеченных места и lx-обёртку, когда используемый `sagernet/sing` либо upstream
sing-box ограничит HTTP CONNECT, закрывая сокет при отказе и сохраняя время жизни
успешного туннеля. Перед удалением прогнать этот же регрессионный тест и стенд.
