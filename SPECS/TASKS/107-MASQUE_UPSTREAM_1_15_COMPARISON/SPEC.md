# SPEC: 107 — MASQUE_UPSTREAM_1_15_COMPARISON

**Фича:** [RESEARCH](../../FEATURES/011-RESEARCH/FEATURE.md) · предмет — [MASQUE_WARP](../../FEATURES/009-MASQUE_WARP/FEATURE.md)

| Поле | Значение |
|------|----------|
| Тип | Q (question/исследование) |
| Статус | C (complete) — 2026-09-28 |
| Вопрос | Апстрим в 1.15 добавил свой MASQUE. Заменяет ли он наш outbound, чем реализации отличаются и что делать с нашей до перехода на 1.15 |
| Срез апстрима | `upstream/testing` = `710d7c715` (`v1.15.0-alpha.9`); MASQUE пришёл коммитом `a23874fd8` в `alpha.7` |
| Срез нашего кода | `lx` = `1b735351d` (номера строк ниже — на этом коммите) |
| Связано | [108](../108-MASQUE_UNBOUNDED_WAITS/SPEC.md) — три дефекта из этого разбора, исправлены; [074](../074-MASQUE_VHTTP_AUTO/SPEC.md); [028](../028-NESTED_TUNNEL_UDP_FRAGMENT/SPEC.md) |

## 1. Ответ

1. **Апстримный клиент наш не заменяет.** С Cloudflare WARP он из коробки не работает:
   мешают три места в коде (§4), остальное выражается конфигом.
2. **Как транспорт апстримная реализация сильнее**: жизненный цикл, сетевой стек,
   соответствие RFC 9484/9297 (§5).
3. **Наша сильнее в том, ради чего писалась**: WARP, обход блокировки по SNI,
   детекция молчания после успешного QUIC-хендшейка.
4. **Пути совпадают**, имена типов в конфиге — нет (§3). До перехода на 1.15 коллизии
   нет: наша база — `upstream/stable`.
5. **Дефекты нашей реализации**, найденные по дороге, — в §6. Три дают зависание без
   ошибки и исправлены в [108](../108-MASQUE_UNBOUNDED_WAITS/SPEC.md).

Способ перехода на 1.15 владельцем не утверждён; варианты и рекомендация — в §8.

## 2. Что сделал апстрим

Два **endpoint**-типа, `masque-client` и `masque-server`: CONNECT-IP по RFC 9484 поверх
HTTP/1.1, HTTP/2 и HTTP/3 с фолбэком версий.

| Свойство | Значение |
|---|---|
| Ключи клиента | `server`, `server_port`, `username`, `password`, `path`, `headers`, `version` (1/2/3, дефолт 3), `disable_version_fallback`, `tls`, `advertise_routes`, `system`, `name`, `mtu` (дефолт 1280), `on_demand`, поля UDP NAT, HTTP/2 или QUIC, dial |
| Стек | внутренний либо системный TUN (`system`) |
| Направление | двунаправленный: входящие потоки отдаются в роутер |
| Основа | новый общий `transport/http` (переписанный HTTP-прокси, CONNECT-UDP) и новый `transport/device` |

В той же пачке 1.15 (32 коммита поверх `stable`, 335 файлов, +20k/−5.5k) для нас дороже
самого MASQUE:

| Коммит | Чем задевает |
|---|---|
| `305b22d7f` Remove dependency on gVisor, `7c4f940be` Add go TUN stack | Переписаны `transport/wireguard/device_stack*`, wireguard-go поднят до v0.0.8. Наш masque-outbound стоит на gVisor-стеке из `transport/wireguard`, AWG — на форк-сабмодуле |
| `1ca62ca8b` Rewrite HTTP proxy protocol | Основа апстримного MASQUE; задевает `protocol/http` |
| `b248ad5d6` Fix outbound group resolution and interruption for nested groups | Зона наших задач 064 и 084 |

## 3. Коллизия путей

| Путь | У нас | У апстрима | Состояние |
|---|---|---|---|
| `option/masque.go` | `MASQUEOutboundOptions` | `MASQUEClientEndpointOptions`, `MASQUEServerEndpointOptions` | снята: наш файл — `option/masque_lx.go` (`1b735351d`) |
| `test/masque_test.go` | один тест разбора опций | сквозные тесты | снята: наш файл — `test/masque_lx_test.go` |
| `protocol/masque/` | `outbound.go` и тесты | `client.go`, `endpoint.go`, `server.go` | один Go-пакет, файлы разные |
| `transport/masque/` | `masque.go`, `client_h2.go`, `profile.go`, `request.go`, `connectip/` | `capsule.go`, `client.go`, `icmp.go`, `pool.go`, `server.go`, `session.go`, `template.go` | один Go-пакет, файлы разные |

Тип в конфиге: у нас outbound `masque`, у апстрима endpoint `masque-client` /
`masque-server` — конфиги не пересекаются. Грубая сверка идентификаторов в общих
пакетах столкновений не нашла; полный пробный мерж с 1.15 не делался.

## 4. Почему апстримный клиент не работает с WARP

| Точка | Где у апстрима | Что нужно WARP | Объём шва |
|---|---|---|---|
| Токен протокола | `transport/masque/session.go:17` — константа `connect-ip` | `cf-connect-ip` | 6–10 строк |
| Готовность сеанса | `transport/masque/client.go:336-397` — только после ADDRESS_ASSIGN | адреса статические, из регистрации | 15–25 строк |
| HTTP/2 | `transport/http/client_h2.go:82-84` — без `SETTINGS_ENABLE_CONNECT_PROTOCOL` отказ и уход на HTTP/1.1 | обычный CONNECT без `:protocol`/`:scheme`/`:path` | 10–20 строк |
| `SETTINGS_H3_DATAGRAM_00` (0x276) | `transport/http/client_h3.go:72` — не объявляется | по нашему коду объявляется | 1–3 строки |
| Заголовки `cf-connect-proto`, `pq-enabled` | — | на h2 | 0, поле `headers` |
| URI и authority | путь `/.well-known/masque/ip/*/*/`, authority = адрес сервера | `https://cloudflareaccess.com` | 0, `path` + `headers.Host` |
| Пин ключа эндпоинта | `tls.certificate_public_key_sha256` | пин ECDSA-ключа | 0, sha256 от DER нашего `public_key` |
| Клиентский сертификат | `tls.client_certificate` / `client_key`, готовый PEM | самоподписанный из ключа регистрации | 0, но серт готовится снаружи |

Проверку Extended CONNECT на h3 апстрим не делает (идёт через `OpenRequestStream`),
шов там не нужен.

**Не проверено на проводе:** шлёт ли WARP ADDRESS_ASSIGN и как отвечает на
ADDRESS_REQUEST; примет ли долгоживущий клиентский сертификат; обязателен ли
`pq-enabled`; нужна ли настройка 0x276. Апстримный клиент против WARP не запускался.

Чего апстримным конфигом не выразить: дефолтный нейтральный SNI, автоматическую
фрагментацию ClientHello при диале через detour (задача 060), `profile`,
`idle_timeout` по таймеру простоя.

## 5. Сравнение по осям

| Ось | Наша | Апстрим | Сильнее |
|---|---|---|---|
| Жизненный цикл | Ленивый подъём на первом dial, сборка под одним мьютексом; фонового переподключения и backoff нет; смена сети не обрабатывается; смерть туннеля закрывает стек и рвёт все соединения | Фоновый цикл с backoff 1 с → 1 мин; смена сети перезапускает сеанс; устройство создаётся один раз и переживает переподключение; `on_demand` усыпляет по ссылкам маршрутизации, не по таймеру | апстрим |
| Сетевой стек | gVisor из `transport/wireguard`; только tcp и udp; 3–4 копии на исходящий пакет, на h2 три копии и две аллокации на входящий | `transport/device`; ICMP; системный TUN; буферы из пула с headroom, запись капсул пачкой; настройки UDP NAT | апстрим |
| Капсулы | ADDRESS_ASSIGN разбирается, к стеку не применяется; ADDRESS_REQUEST и неизвестный тип обрывают поток | Шлёт ADDRESS_REQUEST, на запрос сервера отвечает отказом, неизвестные типы пропускает, маршруты валидирует по RFC | апстрим |
| ICMP и MTU | Только Packet Too Big с фиксированным 1280; TTL ≤ 1 отбрасывается без ответа | no-route, hop-limit, Packet Too Big с фактическим пределом; фолбэк с датаграмм на капсулы | апстрим |
| Фолбэк h3 → h2 | 3 с по настенному таймеру от поднятого UDP-сокета; срабатывает на любой отказ h3, включая молчание после CONNECT | 5 с (дефолт quic-go); только на отказ до отправки CONNECT; h3 помечается сломанным на 5 с → 5 мин и перепроверяется, сброс при смене сети; есть h1 | смешанно |
| TLS под WARP | Ключи регистрации напрямую, сертификат генерируется при старте, нейтральный SNI, автофрагментация | Общий блок `tls` | наша |
| Диагностика | Причина смерти туннеля и фолбэк в логе; причина разрыва на уровне капсул теряется | Причина конца каждого сеанса в логе; фолбэк версий и отсутствие ADDRESS_ASSIGN не видны | смешанно |
| Тесты | Юниты на граничные случаи фолбэка, teardown, пин, капсулы; сквозного теста нет | Сквозные self-to-self на h3/h2/h1, маршруты, PTB, backoff; юнитов нет | апстрим |

## 6. Находки в нашей реализации

Номера строк — на `1b735351d`. «Проверено» значит прочитано в коде; сценарий, при
котором дефект срабатывает, в ряде случаев предположение — помечено.

| # | Находка | Где | Состояние |
|---|---|---|---|
| N1 | Неизвестный тип капсулы и ADDRESS_REQUEST от сервера обрывают поток; RFC 9297 §3.2 требует неизвестные типы игнорировать | `transport/masque/connectip/connectip.go:239-243`, `:256-257` | открыто |
| N2 | Ошибка чтения потока подменяется на закрытие, в лог уходит «use of closed network connection» вместо причины | `connectip.go:113-121` | открыто |
| N3 | `Close()` на h2 берёт мьютекс записи до закрытия сокета; за зависшей записью ждёт таймаута TCP, с ним — разбор сеанса и `Outbound.Close()`. Порядок вызовов проверен, зависшая запись — предположение | `transport/masque/client_h2.go:303-311` | **исправлено, 108** |
| N4 | На h2 нет учёта окна потока пира, клиентских PING и read-deadline: мёртвый путь обнаруживается только TCP keepalive | `client_h2.go:227-294` | открыто |
| N5 | Победа h2 в `auto` необратима: запомненный h2 при отказе не пробует h3 до рестарта процесса | `protocol/masque/outbound.go:575-581`, `:677-685` | **исправлено, 108** |
| N6 | `ReadResponse` на h3 не привязан к контексту: при молчании сервера после хендшейка dial держит мьютекс сборки, в `auto` течёт горутина с QUIC-соединением | `transport/masque/masque.go:113` | **исправлено, 108** |
| N7 | Аллокация и копия до 1280 байт на каждый исходящий пакет ради редкого Packet Too Big | `connectip.go:381-388` | открыто |
| N8 | QUIC-соединение при закрытии не получает `CloseWithError`: `http3.Transport.Close()` не закрывает соединение, отданное через `NewClientConn`; серверная сессия, вероятно, живёт до своего idle-timeout | `outbound.go:886-899`, `masque.go:37-47` | открыто |
| N9 | Комментарий обещает пустой User-Agent, но на h3 quic-go его выкидывает, на h2 пустое поле уходит | `transport/masque/request.go:21-22` | открыто |
| N10 | Мьютекс сборки удерживается на всё время установки туннеля; backoff нет, при мёртвом сервере каждый dial платит полную попытку | `outbound.go:425-480` | открыто |
| N11 | Смена сети не обрабатывается: h3 переживает её через idle-timeout QUIC, h2 — через TCP keepalive | — | открыто |
| N12 | Если сервер назначит адрес, отличный от конфига, пакеты молча отбрасываются стеком | `outbound.go:435-440` | открыто |
| N13 | TTL ≤ 1 без ICMP Time Exceeded, traceroute через туннель пуст | `connectip.go:434-437`, `client_h2.go:478-481` | открыто |

Открытые находки не планируются к исправлению до решения о пути на 1.15: большинство
(N1, N2, N4, N7, N11, N12, N13) уходит вместе с транспортом, если WARP-профиль
пересаживается на апстримный.

## 7. Находки в апстримной реализации

| # | Находка | Где |
|---|---|---|
| U1 | ADDRESS_REQUEST и маршруты пишутся до регистрации закрытия потока по контексту; заблокированная запись не прерывается ни Suspend, ни Restart | `transport/masque/client.go:185-195` |
| U2 | `DialEarly` идёт под мьютексом клиента; сброс соединений при смене сети ждёт конца хендшейка | `transport/http/client_h3.go:76-104` |
| U3 | Молчание после успешного QUIC-хендшейка не считается отказом h3: фолбэка на h2 нет, цикл повторяет h3 с backoff. Это наш полевой случай блокировки по SNI | `transport/http/client_h3.go:145` |
| U4 | Без ADDRESS_ASSIGN сеанс жив, но не готов; ни лога, ни таймаута | `transport/masque/client.go:222-247` |
| U5 | Буфер и копия на каждый пакет в записи endpoint'а, захват мьютекса на каждую пачку при `on_demand` | `protocol/masque/client.go:278-289` |

Общее с нами: адрес источника входящих пакетов не проверяется.

Контрибуция в апстрим невозможна; U3 и U4 — то, что придётся закрывать своим слоем при
пересадке на их транспорт.

## 8. Варианты для перехода на 1.15

| Вариант | Что это | Цена | Оценка |
|---|---|---|---|
| A. WARP-профиль поверх апстримного транспорта | Тип `masque` и его ключи остаются; транспорт, стек, TLS и фолбэк версий — апстримные; свои — три шва из §4 и детекция молчаливого CONNECT (U3) | Швы в чужих файлах, активно правимых в альфе; перенос `idle_timeout` на `on_demand` или отдельным слоем | рекомендуется, после стабилизации 1.15 |
| B. Жить параллельно | Развести пакеты по путям (`protocol/masque` → свой каталог), обе реализации в дереве | Дешевле на первом мерже; ~4,5 тыс. строк своей дельты остаются, каждая правка апстримного стека (gVisor снят) требует адаптации нашего outbound | запасной |
| C. Отказаться от своего | Только апстримный `masque-client` | WARP перестаёт работать | отвергнут |

## 9. Как проводилось

- Чтение апстрима через `git show upstream/testing:<path>`, нашего — в рабочем дереве;
  quic-go читался из кэша модулей (`v0.61.0-sing-box-mod.7`).
- Находки N1, N3, N5 перепроверены по строкам вторым проходом.
- Живых прогонов не было: ни апстримного клиента против WARP, ни сквозного сравнения
  производительности. Выводы о копиях и аллокациях — по коду, без замера.
