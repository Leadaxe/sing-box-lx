**Фича:** [014-LXD_DAEMON](../../FEATURES/014-LXD_DAEMON/FEATURE.md)

| Связано | [127](../127-LXD_INFO_PLATFORM/SPEC.md) (`platform`, `init_system`, `service` — окружение команд), [129](../129-LXD_UPDATE/SPEC.md) (`sing-box lxd update` — штатная команда `update`), [057](../057-LXD_MTLS_SERVICE/SPEC.md) (гейт операторских маршрутов), [066](../066-LXD_CLIENT_IDENTITY/SPEC.md) (имена клиентов для аудита), [100](../100-LXD_ROOT_OWNED_BINARY/SPEC.md) (граница «клиент не исполняет код») |

Админ при установке перечисляет в `daemon.json` именованные команды — `"commands":
{"update": "/usr/bin/sing-box lxd update"}`. Клиент (лаунчер) видит список с текстом команд
и их последним результатом и запускает команду **по имени** — ничего своего он передать не
может. Команда выполняется под пользователем демона (root) отдельным detached-процессом,
вывод и код выхода сохраняются в state-dir и переживают рестарт демона. Нет ключа — нет
ручки. Модель — `sudoers` с `Cmnd_Alias … NOPASSWD`: тот, у кого есть root на хосте,
перечисляет, что именно разрешено сетевому клиенту.

## 1. Проблема

Демон под root управляет сетевой конфигурацией, читает логи и ресурсы, но не исполняет код —
это граница SPEC 100: служба запускается только из root-owned копии, чтобы никто, кто может
подменить файл или держит клиентский сертификат, не получил root. Из-за этого всё, что
исполняет код на машине — обновить ядро, перезапустить службу, — лаунчер делает по SSH
ключами оператора, и окно Service на половину состоит из подсказок «сделайте руками».

Отвергнуто:

- **«Загрузи бинарь/скрипт и выполни»** — ломает границу 100: украденный клиентский
  сертификат или скомпрометированный лаунчер = root-шелл на роутере.
- **То же за флагом `daemon.json`** (`allow_exec`) — opt-in не меняет сути: пока включён,
  mTLS-канал равен root, а выключить его можно только тем SSH, который он должен был заменить.
- **Аргументы от клиента к команде** (версия, URL) — инъекция; с первым же аргументом
  модель «админ перечислил, что можно» рушится. Вариативность живёт в тексте команды: две
  команды `update` и `update-rc` вместо одной с параметром.
- **Подписанное самообновление как единственный путь** — не отвергнуто, но это другая
  задача ([129](../129-LXD_UPDATE/SPEC.md)); обобщённая ручка нужна и для перезапуска,
  `reboot`, `logread` и прочего, что админ сочтёт нужным.
- **Отдельный, более строгий гейт для `commands`** (только сертификат при `tls:true`, только
  loopback при `tls:false`) — решение владельца 2026-10-12: барьер однороден, без исключений
  по маршрутам. Если настроен mTLS — он везде, если Bearer — везде; `apply` под root делает не
  меньше.
- **Исход команд во flash** (`<state_dir>` на OpenWrt — overlay): каждый запуск писал бы лог во
  flash. Файлы — рядом с логом демона (на роутере tmpfs); «последний исход с момента загрузки»
  для кнопки достаточно.

## 2. Поведение

### 2.1 Ключ `daemon.json`

```jsonc
"commands": {
  "update":    "/usr/bin/sing-box lxd update",
  "update-rc": "/usr/bin/sing-box lxd update --prerelease",
  "restart":   "/etc/init.d/sing-box-lxd restart"
}
```

| Правило | Значение |
|---|---|
| Имя | `^[a-z0-9][a-z0-9_-]{0,31}$` — безопасно в URL и имени файла; иначе демон не стартует с ошибкой, называющей имя |
| Текст | непустая строка; исполняется `/bin/sh -c "<текст>"` как есть, без подстановок |
| Отсутствие ключа / пустой объект | маршрутов `/admin/commands*` нет вовсе (как `/admin/resources` без стора) |
| Старый демон | верхний уровень `daemon.json` читается `json.Unmarshal` без `DisallowUnknownFields` — демон до 128 ключ молча игнорирует и стартует; клиент видит отсутствие ручки по `404` |
| Платформы | unix (linux, darwin) одним кодом; Windows — ключ принимается с предупреждением в лог, маршрутов нет (`/bin/sh`, `setsid` — unix). Первая цель и живая проверка — Linux/OpenWrt |

Смена набора команд = правка файла + рестарт службы, как у всех ключей.

### 2.2 REST (операторские маршруты, гейт ровно как у `/admin/apply` — решение владельца, см. §1)

| Маршрут | Ответ |
|---|---|
| `GET /admin/commands` | `{"commands": [<command>, …]}` — по именам, отсортированы |
| `POST /admin/commands/{name}` | `202` + `<command>` в состоянии `running`; `404` — имени нет в конфиге; `409` + `<command>` — уже выполняется; `400 "commands take no input"` — непустое тело: контракт «клиент ничего не передаёт» проверяется кодом, не документацией |
| `GET /admin/commands/{name}` | `<command>` с хвостом лога; `404` — имени нет |

`<command>`:

```jsonc
{
  "name": "update",
  "command": "/usr/bin/sing-box lxd update",   // текст — клиент показывает его до клика
  "state": "idle" | "running" | "done" | "lost",
  "started_at": "2026-10-11T18:02:11Z",         // "" если не запускалась
  "finished_at": "2026-10-11T18:02:40Z",        // "" пока running / lost
  "exit_code": 0,                                // null пока нет
  "client": "launcher",                          // имя клиента по сертификату; "operator" при Bearer
  "log": "update: installed 1.14.3-lx.15 …"      // хвост ≤ 64 КиБ; только в GET по имени
}
```

Текст команды отдаётся клиенту намеренно: клиент — аутентифицированный оператор, и
лаунчер показывает, что именно выполнится и чем кончилось в прошлый раз.

### 2.3 Исполнение

- **Detached.** Демон порождает `/bin/sh -c 'exec >"$LXD_CMD_LOG" 2>&1; /bin/sh -c "$LXD_CMD";
  echo $? >"$LXD_CMD_EXIT"'` с `Setsid`, stdin `/dev/null`, cwd `/`. Процесс в своей сессии:
  рестарт службы (а `update` именно это и делает) убивает демон, но не команду. Код выхода
  пишет обёртка, а не демон, — поэтому результат есть и когда демона уже нет.
- **Файлы** в `<dirname(log_file)>/commands/` — рядом с логом демона (на роутере `/tmp`, tmpfs:
  без износа flash); при запуске без `log_file` (терминал) — `<state_dir>/commands/`. Новых
  маршрутов под них нет: лог отдаётся только внутри `<command>` в `GET` по имени.
  `<name>.json` (демон пишет **до** запуска: `started_at`, `pid`, `client`), `<name>.log` (вывод),
  `<name>.exit` (код выхода; `finished_at` = его mtime).
  Состояние выводится из файлов, не из памяти: `.json` без `.exit` и живой `pid` → `running`;
  `.json` без `.exit` и мёртвый `pid` → `lost` (демон или команду убили до завершения);
  `.exit` есть → `done`. Новый `POST` перезаписывает все три.
- **Окружение** — окружение демона плюс: `LXD_PLATFORM`, `LXD_VERSION`, `LXD_INIT_SYSTEM`
  (из 127), `LXD_STATE_DIR`, `LXD_BIN` (путь работающего бинаря с раскрытыми симлинками),
  `LXD_CLIENT` (кто запустил — то же имя, что в аудите; `operator` при Bearer);
  `PATH`, если пуст, — `/usr/sbin:/usr/bin:/sbin:/bin` (под procd окружение минимальное).
  Значения — от демона, не из запроса; команда получает факты о хосте, не вход клиента.
- **Один экземпляр на имя**; разные имена параллельно. Таймаут — ответственность админа
  (`timeout 600 …`); демон команд не убивает, в том числе при своём Close (они detached).
- **Лог** пишется командой напрямую в файл, без буферов демона; `GET` отдаёт хвост 64 КиБ.
  Каталог `commands/` чистится от файлов имён, которых больше нет в конфиге, при старте.
- **Релиз** — вместе со 127 и 129 одним тегом (решение владельца): лаунчеру для окна Service
  без SSH нужны все три.

### 2.4 Аудит

Каждый `POST` — строка Info в лог демона: `lxd: command update started by launcher (pid 4242)`;
завершение демон не отслеживает (его может не быть), но `GET` после рестарта показывает исход.

### 2.6 Чего не делать

- Никаких параметров, тела запроса, подстановок `{…}` в текст команды.
- Не убивать команды (`DELETE`) — detached-процесс с правами root останавливает админ.
- Не хранить историю запусков — только последний исход.
- Апстримных файлов не трогать.

## 3. Критерии приёмки

- Табличный тест валидации имён и текста (`daemonconfig_test.go`): допустимые имена, `A`,
  `-x`, 33 символа, пустой текст — демон не стартует с ошибкой, называющей имя.
- Тест исполнения на фейковой команде (`sh -c 'echo hi; exit 3'`): `POST` → `202 running`,
  `.json` до запуска; затем `GET` → `done`, `exit_code: 3`, `log` = `hi\n`; второй `POST` во
  время `sleep` → `409`; после «перезапуска» контроллера над тем же state-dir состояние
  читается из файлов; `.json` без `.exit` с мёртвым pid → `lost`.
- Тест: команда переживает `Close()` контроллера (detached), `.exit` появляется после.
- Тест маршрутов: без ключа — `404` на все три; имя не из конфига — `404`; непустое тело —
  `400`; `client` = имя по сертификату; гейт — тот же тест-набор, что у `/admin/apply`.
- Окружение: тест проверяет `LXD_PLATFORM`, `LXD_STATE_DIR`, `LXD_BIN`, `LXD_CLIENT` и дефолтный
  `PATH` через `env`-команду; каталог исхода — рядом с `log_file`, без него — в state-dir.
- Существующие тесты 057/066/103 зелёные; `go vet` по lx-файлам чистый на darwin/linux/windows.
- Ручная проверка владельцем после тега: на роутере `"commands": {"echo": "echo $LXD_PLATFORM"}`
  → `POST` → `GET` показывает `linux-arm64`, `exit_code: 0`.

## 4. Потребитель (для справки, в объём ядра не входит)

Лаунчер, окно Service: `GET /admin/commands` → список кнопок с текстом команды и прошлым
исходом; `404` → раздел скрыт с подсказкой «добавьте `commands` в daemon.json»; нет `update`
в списке — кнопка Update неактивна с той же подсказкой. После `POST` — опрос `GET` раз в
секунду; обрыв соединения при `update` — ожидаем, переподключение и сверка `version` в
`/admin/info`. Коллекция рецептов (готовые `commands` под procd/systemd) — на стороне лаунчера.
