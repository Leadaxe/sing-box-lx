При выборе узла `round_robin` пропускает слот, чей узел известно мёртв (последняя проба
провалилась и стёрла его history), и берёт живой слот того же пула. Состав пула и
раскладка слотов не меняются. Если живых слотов в пуле нет — выбор как раньше.

## 1. Проблема

Конфиг из отчёта:

```json
{
  "type": "urltest",
  "tag": "auto",
  "outbounds": ["ru-7f6da9614", "shadowtls-shadowsocks-inf6da9614", "wh", "shadowtls-shadowsocks-inee53d308"],
  "interval": "3667ms",
  "mode": "round_robin",
  "balancer": { "pool": 3, "pool_tolerance": 700, "sticky_hash": ["none"] }
}
```

Физически серверов два: `ru-7f6da9614` (vless без mux) и `shadowtls-shadowsocks-inf6da9614`
(ss + shadowtls, h2mux) стоят на одном IP, `wh` и `shadowtls-shadowsocks-inee53d308` — на
другом. Сервер моргает на 10–20 с, и оба его узла умирают разом.

Пул по SPEC 019 меняет жильца слота только на живой узел вне пула; живого кандидата нет —
мёртвый остаётся в слоте («пул не пустеет»). Выбор узла берёт жильца слота без проверки
живости, а ошибка дайла пул не трогает. Пока простой длится, мёртвый слот получает свою
долю новых соединений:

| Пул | Раскладка при простое сервера 1 | Доля новых соединений в мёртвый сервер |
|-----|--------------------------------|------------------------------------------|
| 4 из 4 | оба узла сервера 1 в пуле, запасных нет | 1/2 |
| 3 из 4, оба узла сервера 1 в пуле | один слот получает запасной узел сервера 2, второй остаётся мёртвым | 1/3 |
| 3 из 4, в пуле один узел сервера 1 | запасной — второй узел сервера 1, тоже мёртвый | 1/3 |

При этом живые узлы в пуле есть всегда, пока жив хотя бы один сервер.

## 2. Поведение

Только `mode: round_robin`. `least_test` и `failover` не меняются.

**Мёртвый слот** — тег слота резолвится в узел, и в history URL-тестов нет записи под его
реальным тегом (`RealTag`: для вложенной группы — её текущий лист; так же history читает
`GetPool`). Нерезолвимый тег считается мёртвым. Остальные слоты — живые.

1. **Номер слота** считается как сейчас: счётчик (`sticky_hash: ["none"]`) или
   `hash(key) % pool`. Счётчик растёт на 1 за соединение, как сейчас.
2. **В пуле нет живых слотов** → выбор как сейчас, `slot[номер]`. Это холодный старт
   (истории нет ни у кого) и тотальный простой (SPEC 019: ротация по последним известным,
   дайлы падают, восстановление само).
3. **С закреплением.** Живой `slot[номер]` → его узел: ключи живого слота не двигаются
   никогда, строгий ноль переездов SPEC 019 сохраняется. Мёртвый `slot[номер]` → `j`-й
   живой слот в порядке слотов, `j = (hash / pool) % число живых`: ключи мёртвых слотов
   расходятся по живым поровну, по остатку хеша, независимому от номера слота. «Первый
   живой по кругу» не годится: при `[живой, мёртвый, мёртвый, живой]` последний получал бы
   3/4 ключей. При неизменном наборе живых слотов один ключ всегда попадает на один узел.
   Узел ожил → его ключи возвращаются на него со следующего нового соединения, без
   переходного состояния.
4. **Без закрепления.** Ротация идёт только по живым слотам в порядке слотов: `k`-й живой,
   `k = счётчик % число живых`. Все слоты живы → последовательность совпадает с нынешней.
   «Следующий живой» здесь не годится: при пуле из 4 с двумя мёртвыми подряд соседний
   живой получал бы 3/4 соединений.
5. **Пул не меняется.** Выбор слота не трогает раскладку, `onChange` (кэш достижимости
   SPEC 020), References (SPEC 109), `ActiveTags`. Состав пула по-прежнему меняет только
   дотест.
6. **Сеть.** Узел выбранного слота не поддерживает сеть соединения → fallback
   `Select(network)`, как сейчас (SPEC 019 «Узел слота не поддерживает network»). Проверка
   живости от сети не зависит, как и планирование пула.
7. **Наблюдаемость.** `Now()` показывает фактически выбранный узел. `GetPool` не меняется:
   у мёртвого слота `delay = 0`, то есть слот с нулём в UI пропускается, пока в пуле есть
   живые.
8. **Ошибка дайла** в `round_robin` по-прежнему не трогает ни пул, ни history.

### 2.1 Источник сигнала

Своего состояния нет, читается общая history:

- **Дотест пула** каждый тик пробует членов пула с `force` (`pool_tolerance: 0` — членов
  пула, при нехватке живых ещё и кандидатов; `> 0` — все узлы). Запись стирается в момент
  провала конкретной пробы, а не в конце прогона, поэтому пропуск начинается раньше, чем
  дотест перепишет слоты.
- **Ручные тесты** — тест группы, clash API `/proxies/{name}/delay` и `/group/{name}/delay`,
  RPC демона `URLTestOutbound` и `URLTest` — пишут и стирают ту же запись. Успешный
  оживляет узел.
- **Другие группы с тем же узлом** — их пробы; дайл-ошибка в `least_test` стирает запись
  (апстрим); провал fallback-дайла SPEC 054 тоже.
- **Цена общего сигнала.** Ручной тест задержки с коротким `timeout` (clash API
  `/proxies/{name}/delay`, RPC `URLTestOutbound`), который не успел, или отказ дайла /
  fallback-дайла `least_test`-группы с тем же узлом стирает запись и выводит узел из
  ротации `round_robin` до ближайшего дотеста пула — не дольше `interval` плюс время пробы:
  члены пула пробуются каждый тик. Это осознанный компромисс: свой сигнал живости ради
  этого потребовал бы состояния. Пользовательская документация говорит об этом явно.
- **Отменённая проба** (закрытие группы) запись не стирает.
- **Штрафы SPEC 054** к `round_robin` не применяются и сигналом не служат. Новых счётчиков
  и таймеров нет.
- **Возраст записи** не учитывается. У членов пула при работающем тикере запись не старше
  одного прогона; при остановленном (`idle_timeout`, гейт SPEC 020) — последняя известная.

### 2.2 Холодный старт и первый прогон

- До первого ответа пробы истории нет → п. 2 → как сейчас: слоты — первые `pool` по
  конфигу.
- Тёплая история (процесс не выгружался) → пул засеян по ней, узлы живы → пп. 3–4 с первого
  соединения.
- **Первый прогон.** Пробы отвечают не одновременно. Пока ответила часть пула, слоты без
  ответа (ещё не измерены, а не мертвы) тоже пропускаются, и их доля уходит на ответивших —
  до конца их проб, не дольше таймаута пробы 15 с. Это перекос распределения, не отказ;
  отличать «не измерен» от «мёртв» потребовало бы нового состояния.

### 2.3 Задержка реакции

Пропуск начинается, когда проба мёртвого узла провалилась: до ближайшего тика (не больше
`interval`, в отчёте 3,667 с) плюс время провала пробы:

- RST или недостижимость — ожидается быстрее остальных; на устройстве не подтвердилось:
  с `reject with tcp reset` окно было те же ~15–20 с, что с `drop` (не разбиралось);
- чёрная дыра без mux — TCP connect timeout узла, 5 с по умолчанию (`connect_timeout`);
- mux-сессия на внешне живом TCP — до таймаута пробы, 15 с.

На роутере (пул 3 из 4, `interval` 3,667 с) обход начинался через ~15–20 с простоя. Для
простоя в 10–20 с фикс закрывает хвост окна или не успевает вовсе. Узел
возвращается в ротацию в пределах одного прогона после возврата сервера: прогон с мёртвым
узлом длится до таймаута, а буферизованный тик стартует сразу за ним. Пауза SPEC 125
(`tickTooSoon`) этому не мешает: она читает `lastTickRunEnd`, который пишет только
`testNodesTick`, а пути пула зовут `testNodes(…, true)` и отметку не ставят.

Более быстрый сигнал — отказы боевых дайлов, как в SPEC 054, — вне задачи: он противоречит
инварианту SPEC 019 «ошибка дайла пул не трогает» и требует состояния. Отдельная задача —
по решению владельца.

**Энергия.** Проб не прибавляется. Проверка живости — чтение history в памяти, не больше
двух проходов по слотам за соединение.

### 2.4 Отвергнуто

- **Сжимать пул в планировании** — убирать мёртвого жильца без замены в `planTolerantPool`,
  `planFirstLivePool` и `balancePoolFirstLive`. Число слотов перестаёт быть постоянным,
  `hash(key) % pool` меняется у всех ключей при каждом сжатии и обратном росте: массовые
  переезды закрепления дважды за простой. Нарушаются инварианты SPEC 019 «пул не пустеет» и
  «живой жилец не меняет индекс слота»; без этого остаётся дырявый слот, а это тот же
  пропуск в выборе. Каждое изменение — `setSlots` → инвалидация кэша достижимости SPEC 020,
  выпавший узел теряет References SPEC 109 и его простаивающие соединения закрываются.
  Срабатывает только в конце прогона, после всех проб и добора, — позже, чем стирается
  history.
- **Fallback `Select(network)` вместо соседнего слота.** Весь перенаправленный трафик уходит
  в один узел, и он может быть вне пула: не в References (SPEC 109) и не в `ActiveTags`
  (SPEC 020, может спать). На холодном старте свёл бы весь трафик в первый узел конфига.
- **Перебор соседей при несовместимости по сети** — нет, правило SPEC 019 не меняется.

## 3. Критерии приёмки

- Без закрепления, пул `[a,b,c,d]`, `b` и `d` мертвы: соединения только на `a` и `c`,
  поровну.
- Без закрепления, все живы: последовательность выбора совпадает с выбором без проверки
  живости.
- С закреплением, пул `[a,b,c,d]`, `b` и `c` мертвы (подряд): ключи живых слотов — на тех
  же узлах; ключи мёртвых — на `a` и `d` примерно поровну, каждый ключ одинаково при
  повторах; раскладка слотов не изменилась.
- Узел снова жив: его ключи на нём со следующего соединения, ключи живых слотов не
  двигались.
- Все мертвы: выбор совпадает с нынешним, с закреплением и без.
- Холодный старт (пустая history): выбор как сейчас; пустой пул — fallback.
- Узел слота, выбранного пропуском, не поддерживает сеть — fallback.
- `balancePoolFirstLive` на httptest-фикстуре SPEC 019: мёртвый член без запасного остаётся в
  своём слоте, `selectBalanced` его не выбирает; внешние `DeleteURLTestHistory` /
  `StoreURLTestHistory` (как у clash API) включают и снимают пропуск.
- Существующие тесты `protocol/group` зелёные, `go vet` и `gofmt` чисто.
