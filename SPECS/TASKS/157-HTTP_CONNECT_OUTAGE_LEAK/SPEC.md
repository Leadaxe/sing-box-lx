# SPEC: 157 — HTTP_CONNECT_OUTAGE_LEAK

**Фича:** [HOTFIXES](../../FEATURES/004-HOTFIXES/FEATURE.md)

| Поле | Значение |
|------|----------|
| Тип | B (bug) — неограниченное ожидание ответа HTTP CONNECT при отказе прокси |
| Статус | I (implemented) — регрессионный тест, race, сборки и локальный стенд зелёные; полевая проверка ожидается |
| Ветка | `lx` |
| База | `4dbee51ca`; воспроизведение на официальном `v1.14.4-lx.33` |

## Проблема и границы доказательства

HTTP-прокси принимает TCP и CONNECT, но не отвечает. Обычный маршрутизируемый
трафик не имеет срока ожидания CONNECT: таймаут TCP закончился при установке
сокета, а таймаут urltest распространяется только на пробы. Закрытие SOCKS-клиента
не прерывает заблокированный `http.ReadResponse` ядра. Повторные попытки удерживают
горутины, сокеты, буферы и стеки без предела.

Локальный стенд, три волны по 256 запросов с закрытием клиента через 150 мс и
ожиданием 20 с после каждой: горутины 12 → 268 → 524 → 780, fd
10 → 522 → 1034 → 1546; RSS 77 956 → 126 324 KiB. Профиль показывает
`sing/protocol/http.Client.DialContext` → `http.ReadResponse`.
Все процессы стенда ограничены cgroup 512 MiB, без swap и без TUN.

Немедленный HTTP 503 — другой случай: 16 000 отказов не дали накопления ресурсов,
после восстановления успешны 200/200 запросов. Отказ с немедленным
503 и отсутствие ответа CONNECT — разные режимы, их результаты учитываются
раздельно.

## Контракт

- Ожидание HTTP CONNECT после установки нижележащего соединения ограничено
  `constant.TCPTimeout` (15 с), включая запись запроса и чтение неполного ответа.
- Более ранняя отмена/дедлайн вызывающего по-прежнему прерывает запрос.
- При отказе или таймауте сокет закрывается; при успехе сторож снимается.
- Новый таймаут не передаётся в `detour` и не меняет время жизни успешного
  транспорта, исходный контекст и `connect_timeout` нижележащего дайлера.
- HTTP-заголовки, авторизация и уже прочитанные байты туннеля сохраняются.
- Новых JSON-полей, build-tag, зависимостей и изменений UI нет.

## Приёмка

Один интеграционный тест на реальном loopback TCP проверяет зависший CONNECT,
неполный ответ, раннюю отмену, 503 и работу успешного соединения после бюджета
хендшейка. Тест должен ловить исходный дефект. Повтор стенда показывает отсутствие
накопления горутин/fd после трёх волн; здоровый трафик восстанавливается.
Сборки выполняются с закреплёнными в HEAD сабмодулями, без пользовательских
изменений их рабочих копий. Живой VPN и бинарь бандла не затрагиваются.

## Условие снятия

Удалить швы и lx-обёртку, когда используемый `sagernet/sing` либо upstream
sing-box ограничит HTTP CONNECT, закрывая сокет при отказе и сохраняя время жизни
успешного туннеля. Перед удалением прогнать этот же регрессионный тест и стенд.
