# TEST_PLAN 060 — прогон 2026-08-12: авто-фрагментация ClientHello под `detour`

> Это план и результаты **прежнего механизма** задачи — разреза ClientHello по умолчанию под
> `detour` (описан в [HISTORY.md](HISTORY.md)). Проверка `lx.sniff_guard` — в
> [SPEC.md](SPEC.md) §6. Записи используют язык гипотезы того времени («сломанное плечо»,
> «PMTU-дыра»): факты верны, причина — сниффинг SNI на релее, см. HISTORY §1.2. Ссылки на «§3»
> ниже ведут в прежнюю спеку, сохранённую в HISTORY.

## Стенд

Локальный `sing-box run` с раздельными mixed-инбаундами (по одному на каждое проверяемое
плечо), нижние плечи с `bind_interface: en0` — иначе стенд уходит в боевой TUN и даёт
ложные таймауты (эта ошибка уже была допущена при первичной диагностике).

**Нужен заведомо сломанный узел.** PMTU-дыра — свойство конкретного хостера, а не протокола:
на момент baseline ломались FI/SE, работали GB/FR. Перед прогоном сломанность
подтверждать замером порога (см. ниже), а не памятью.

### Подтверждение сломанности плеча

Через SOCKS-инбаунд, смотрящий в проверяемое плечо, снять TLS-хендшейк к цели с ClientHello
двух размеров (варьируется длиной `sni`/паддингом):

| ClientHello | здоровое плечо | сломанное плечо |
|---|---|---|
| ~1488 B | OK | OK |
| ~1511 B | OK | висит → EOF (12–17 с) |

## Baseline (снят 2026-08-12, до реализации)

Цель — WARP endpoint `162.159.199.118:8443`, `network: h2`, `sni: www.google.com`.

| плечо | результат |
|---|---|
| VLESS сам по себе | ✅ `ip=66.234.150.226` |
| masque h2 напрямую (en0) | ✅ `warp=on` |
| masque h2 через detour(VLESS-FI, сломанный) | ❌ `tls handshake: EOF` за 17 с |
| masque h3 через detour | ✅ `warp=on`, 4/4 |
| `VLESS(DE-2) detour VLESS(FI)` | ❌ `EOF` за 1.9 с |

Эффект фрагментации через то же сломанное плечо (штатный `tf.NewConn`):

| режим | результат |
|---|---|
| без фрагментации | ❌ FAIL, 12 с |
| `fragment` | ✅ OK, 0.6 с |
| `record_fragment` | ✅ **OK, 0.1 с** |
| оба | ✅ OK, 0.6 с |

Post-handshake через сломанное плечо: прикладные записи 200 B … 64 КБ проходят мгновенно
⇒ фрагментация нужна только на хендшейке.

## Что проверить после реализации

1. **Основной сценарий (был сломан)**: `masque h2 + detour(сломанный узел)` БЕЗ ручных
   флагов — туннель поднимается, `warp=on`, хендшейк < 1 с.
2. **Второй протокол**: `VLESS detour VLESS(сломанный узел)` без флагов — поднимается.
   Это то, что отличает 060 от точечного фикса в masque.
3. **Регресс прямого пути**: те же outbound'ы БЕЗ `detour` — работают как в baseline,
   фрагментация НЕ включена (проверять фактом, напр. размером первой записи на проводе,
   а не только успехом коннекта).
4. **Явное перекрытие сильнее авто**:
   - `record_fragment: false` + detour → падение возвращается (авто не должно быть
     неотключаемым);
   - `record_fragment: true` без detour → фрагментация включена.
5. **Отличие «не задано» от «явно false»** — проверять живым `box.New`/декодом конфига,
   а не чтением структуры: badjson схлопывает пустые значения (прецедент известен).
6. **Цепочки**: detour через несколько звеньев и `default_outbound` — поведение
   соответствует решению по §3 открытому вопросу 2.
7. **QUIC не задет**: masque h3 + detour, hysteria2/tuic — без изменений относительно baseline.
8. **Сквозной трафик**: 5 МБ через detour-туннель; сравнить со строкой baseline
   (эталон: `http=200`, ~1 с на здоровом плече).
9. **Регресс-набор**: `go test -race` по `common/tls`, `protocol/vless`, `protocol/masque`;
   `gofmt -l`, `go vet`.

## Риск ложно-зелёного

Если проверять только на здоровом плече, все пункты пройдут независимо от реализации.
Пункты 1, 2 и 4 обязаны выполняться **на подтверждённо сломанном узле** — иначе прогон
ничего не доказывает.

## RESULTS (2026-08-12)

### Целевой сценарий — был сломан, стал рабочим

WARP `162.159.199.118:8443` (h2, `sni: www.google.com`) через VLESS-FI с подтверждённой
PMTU-дырой, **без единого флага в конфиге**:

| | до | после |
|---|---|---|
| h2 напрямую (регресс) | ✅ `warp=on` | ✅ `warp=on`, 0.3 с |
| h2 + detour(FI) | ❌ FAIL, 15.2 с | ✅ **`warp=on`, 0.4 с** |
| h2 + detour + явный `record_fragment` | ✅ 0.3 с | ✅ 0.3 с |

### Матрица: все живые VLESS × оба направления

19 живых узлов подписки, по 2 комбинации на узел = **38 связок**:
`MASQUE detour VLESS` и `VLESS detour MASQUE`.

| проверка | результат |
|---|---|
| связность (`cdn-cgi/trace`) | **38/38 OK**, ни одного FAIL |
| крупные данные (5 МБ каждой связке) | **38/38 OK**, ровно 5 000 000 B, 0 обрывов |

Времена 5 МБ: 0.7–7.6 с типично (медленные узлы — свойство узла, не фрагментации);
единственный выброс 19.2 с — 🇳🇱 в направлении MASQUE-over-VLESS.

Семантика подтверждена: `MASQUE-over-VLESS` → `warp=on` (выход через Cloudflare),
`VLESS-over-MASQUE` → `warp=off` и IP VLESS-узла (наружу смотрит VLESS, WARP несёт его
трафик). Это ожидаемо и означает, что цепочки собираются в правильном порядке.

Узлы FI/SE, на которых связка не поднималась вообще, теперь работают в обе стороны —
включая сквозные 5 МБ.

### Юнит-тесты

`common/tls/detour_fragment_lx_test.go`: прямой путь не тронут; detour включает
`record_fragment`; явный `record_fragment` сохраняется; явный `fragment` НЕ апгрейдится;
`fragment_fallback_delay` не затирается.

### Статика и сборка

`make -f Makefile.lx lx-build`, сборка без `with_quic` (stub-путь), `go vet`, `gofmt -l` —
чисто. `go test -race` по `common/tls`, `protocol/masque`, `protocol/vless`, `option` — зелено.

# Прогон 2026-11-13 — `lx.sniff_guard`, loopback-стенды SPEC §6

Стенд — `lx-test/sniffguard/` (`stand.sh`, `gen.py`, README). Всё на `127.0.0.1`, без TUN, pf и
внешних адресов. Сниффер — Xray `26.7.28` (собран из кеша модулей Go, снимок 2026-09-01; спека
сверялась с `c456141` от 2026-11-11) со `sniffing` `destOverride: ["http","tls","quic"]`,
`routeOnly: false`. sing-box — из рабочего дерева на `6504471ea` под полным `LX_TAGS`. Серверы —
sing-box на loopback: trojan + TLS, hysteria2, tuic. Маскировочный SNI — `decoy.invalid`
(не резолвится: подмена назначения даёт быстрый отказ, наружу ничего не уходит).

Стенд A «релей»: узел через `detour` → vless → Xray. Стенд B «прямой путь»: pf нет, сниффер

**Расхождения с ожиданием.**

- `fragment` на прямом пути защищает. Апстримный `writeAndWaitAck` при ACK быстрее 20 мс сам
  выдерживает `fragment_fallback_delay` (500 мс), это больше бюджета Xray. FEATURE и SPEC
  исправлены.
- hysteria2/tuic со стартом `clean`: первое соединение висит до таймаута, второе новое
  соединение идёт с приманкой и проходит, но метка оставалась `clean` — успех засчитывался
  только при следующем новом соединении, а живое соединение его не открывало. Переход появился
  после принудительного переподключения. Исправлено тем же днём: успех засчитывается, когда
  соединение прожило 30 с. Повторный прогон после правки: первое соединение hysteria2 падает за
  15 с, второе проходит с приманкой, через 31 с в логе `quic path detour relay: clean -> suspect`
  без нового соединения; tuic на том же релее после этого проходит с первого раза.
