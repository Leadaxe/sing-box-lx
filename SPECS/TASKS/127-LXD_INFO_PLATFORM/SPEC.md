# SPEC: 127 — LXD_INFO_PLATFORM

**Фича:** [014-LXD_DAEMON](../../FEATURES/014-LXD_DAEMON/FEATURE.md)

| Поле | Значение |
|------|----------|
| Тип | F (feature) — демон сообщает о себе платформу, релизный ассет, init-систему хоста и свой статус службы |
| Статус | I (implemented) — 2026-10-11, дизайн согласован с владельцем; ручная проверка на роутере и Mac — после тега |
| Ветка | `lx` |
| Build-tag | `with_lxd` (lx-файлы `lxd/initsystem*.go`, `lxd/admin.go`, `lxd/service_linux.go`) |
| Источник | Лаунчер, SPEC 161 (окно Service): запись машины «Home» хранила `linux/amd64`, роутер — aarch64; кнопка «Download core» скачала бы чужой бинарь. Init-систему (procd/systemd) лаунчер сейчас просит выбрать руками |
| Связано | [057](../057-LXD_MTLS_SERVICE/SPEC.md) (`/admin/info`), [068](../068-LXD_HOST_TELEMETRY/SPEC.md) (`/admin/host`: `os_id`, `arch` по uname), [100](../100-LXD_ROOT_OWNED_BINARY/SPEC.md) (`executable` в info, self-check по ppid/XPC_SERVICE_NAME), [103](../103-LXD_WINDOWS_SERVICE/SPEC.md) (контекст службы SCM) |

`GET /admin/info` получает платформенную карточку из пяти полей: `goos`, `goarch` — из
`runtime`; `platform` — суффикс релизного ассета для платформы этого бинаря
(`linux-armv7`, `linux-mipsle-softfloat`), то есть что качать для этой машины;
`init_system` — что за init на **хосте** (`procd` / `systemd` / `openrc` / `launchd` /
`scm`, `""` — не распознан); `service` — запущен ли **этот процесс** под ним как служба.
Лаунчер по этим полям сам выставляет платформу записи машины, выбирает рецепт
обслуживания и убирает ручной выбор.

## 1. Проблема

Лаунчер строит конфиг и рецепты обслуживания (скачать ядро под машину, перезапустить
службу, прочитать лог) по полям записи машины `goos/goarch` и по init-системе, которую
пользователь выбирает в окне. Оба значения — догадки:

- `goos/goarch` вводятся руками при добавлении машины; дефолт `linux/amd64`. У владельца
  запись роутера так и осталась `amd64` при реальном `aarch64`.
- init-систему демон не сообщает вовсе; `/admin/host` отдаёт `os_id` («openwrt») и `arch`
  по uname («aarch64»), но это телеметрия с другим кэшем, а `arch` требует таблицы
  uname → GOARCH на стороне клиента (`aarch64`→`arm64`, `x86_64`→`amd64`, `armv7l`→`arm`,
  mips с softfloat не различим). Бинарь, который уже работает, знает свою платформу
  точно — `runtime.GOOS/GOARCH`.

Отвергнуто:

- **Вычислять init по путям из паспорта** (`/etc/sing-box-lxd/state` + `/tmp/lxd.log` ⇒
  OpenWrt) — эвристика по чужим дефолтам, на кастомной раскладке врёт молча.
- **Брать `os_id`/`arch` из `/admin/host`** — см. выше: отдельный кэш (обновляется по
  своему интервалу и не на всех платформах), uname-строка вместо GOARCH, init всё равно
  неизвестен.
- **Одно поле `init_system` = «init, если служба, иначе `""`»** (первая редакция этой
  спеки). Смешивает два вопроса — что за init на хосте (свойство машины, от него зависят
  все рецепты) и запущен ли процесс под ним (свойство процесса). Склейка теряет самый
  частый ручной сценарий: демон в терминале на systemd-хосте отдавал бы `""`, и лаунчер
  не отличил бы «init неизвестен» от «systemd есть, службы нет» — а рецепт «установить
  службу» нужен именно тут. И прячет единственную эвристику (`ppid == 1` на linux) в
  поле, по которому строятся рецепты.
- **Только `goos`/`goarch` для скачивания.** Матрица `lx-release.yml`: `linux-armv7`,
  `linux-mipsle-softfloat`, `linux-mips-softfloat` — `GOARCH=arm`/`mips` ассет не называют,
  нужны `GOARM`/`GOMIPS`; проблема «softfloat не различим», из-за которой отвергнута
  таблица uname, вернулась бы в новом виде на основном парке OpenWrt-роутеров.
- **Свой детектор init для `/admin/info` отдельно от `detectInit` рецепта `--service`.**
  Два детектора с разными ответами на одном хосте (`--service=install` печатает одно,
  паспорт говорит другое) — баг, который лаунчер не объяснит. Детектор один.

## 2. Поведение

### 2.1 Поля `/admin/info`

| Ключ | Значение |
|------|----------|
| `goos` | `runtime.GOOS` |
| `goarch` | `runtime.GOARCH` |
| `platform` | суффикс релизного ассета `lx-release.yml` для платформы бинаря: `<goos>-<goarch>`; для `arm` — `<goos>-armv<GOARM>` (`linux-armv7`); для `mips`/`mipsle` (`mips64`/`mips64le`) — `-<GOMIPS>` (`-<GOMIPS64>`): `linux-mipsle-softfloat`; `windows/386` — `windows-386-legacy-windows-7` (единственный ассет 386, SPEC 004). Настройки — из `debug.ReadBuildInfo().Settings`, они записаны в бинарь всегда, дефолты включая |
| `init_system` | init **хоста**: `procd` / `systemd` / `openrc` / `launchd` / `scm` / `""` |
| `service` | `true` — этот процесс запущен под `init_system` как служба |

Поля всегда присутствуют (`""` / `false` — «не знаю», не отсутствующий ключ). Остальной
ответ без изменений. `/admin/host` не трогается. Соглашение об именах ассетов живёт в
этом репо рядом с workflow и меняется вместе с ним — поэтому реализовано здесь один раз,
а не таблицей в каждом клиенте.

### 2.2 Определение `init_system` и `service`

Считается один раз при старте демона (как `executable`; ppid после переусыновления
меняется, нужен снимок «кто меня запустил»), чистая функция от окружения, без сетевых и
дорогих вызовов:

| Платформа | `init_system` | `service` |
|---|---|---|
| windows | всегда `scm` | контекст службы SCM (тот же признак, что `serviceContext` самопроверки, SPEC 103 §2.11) |
| darwin | всегда `launchd` | `ppid == 1` и `XPC_SERVICE_NAME != ""` (LaunchAgent `install-user` тоже служба: у агента `XPC_SERVICE_NAME` задан) |
| linux | общий детектор хоста (ниже): `procd` / `systemd` / `openrc` / `""` | `init_system != ""` и `ppid == 1` |
| прочие | `""` | `false` |

**Детектор linux** — один для рецепта `--service` (`detectInit`, `service_linux.go`) и для
паспорта: сначала `/proc/1/comm` (живой pid 1 — `systemd` → `systemd`, `procd` → `procd`;
OpenWrt-userland под systemd — машина systemd), файловые пробы — только когда pid 1 не
говорит ничего (контейнер со спрятанным procfs, `init` sysvinit под openrc):
`/etc/openwrt_release` → `procd`; каталог `/run/systemd/system` (= `sd_booted()`) →
`systemd`; каталог `/run/openrc` → `openrc`; иначе `""`. `/run` — tmpfs, chroot его не
подделает; `/sbin/openrc` не признак — установленный ≠ работающий. Для рецепта `openrc`
читается как «неизвестный init» (рецепта нет).

`service` на windows и darwin точен (SCM и launchd сами маркируют свои процессы), на
linux — эвристика: `ppid == 1` — туда ставят службы systemd, procd и openrc, но туда же
попадает осиротевший `nohup sing-box lxd &`. Поэтому это отдельное поле: ошибка в нём
не портит `init_system`, по которому строятся рецепты. Контейнер без init — `""`/`false`;
запуск руками на роутере — `procd`/`false`.

## 3. Критерии приёмки

- Табличные тесты чистых функций: `detectLinuxInit` (pid 1 бьёт файловые метки, пробы
  как fallback, openrc под sysvinit, контейнер без признаков → `""`); `detectInitSystem`
  (все строки таблицы §2.2: `service` отдельно от `init_system`, запуск руками на
  procd/systemd-хосте → init назван, `service=false`); `releasePlatform` (имена ассетов
  матрицы, `GOARM` вида `7,softfloat`, `windows/386`).
- Тесты `/admin/info` (`admin_test.go`) проверяют все пять полей; без карточки — `""`/`false`,
  ключи есть.
- Тесты рецептов `service_linux_test.go` зелёные на общем детекторе; 057/100/103 зелёные;
  `go vet` по lx-файлам чистый на darwin/linux/windows/прочих.
- Ручная проверка владельцем после тега: на роутере `curl … /admin/info` →
  `"goos":"linux","goarch":"arm64","platform":"linux-arm64","init_system":"procd","service":true`;
  на Mac со службой — `darwin`/`arm64`/`darwin-arm64`/`launchd`/`true`; при запуске
  `sing-box lxd` руками в терминале — `init_system` назван, `service:false`.

## 4. Потребитель (для справки, в объём ядра не входит)

Лаунчер (SPEC 161 follow-up): при каждом паспорте, если `goos/goarch` непусты и
отличаются от записи машины — запись обновляется (с записью в лог), платформа в строке
машины и в окне Service берётся из паспорта; «Download core» качает ассет по `platform`.
`init_system` непустой — селектор в шапке окна Service скрывается, рецепты строятся по
нему; при `service:false` в рецептах уместен шаг «установить службу». `init_system` пустой
— селектор остаётся. Минимальная версия ядра для этого — тег, в который войдёт 127.
