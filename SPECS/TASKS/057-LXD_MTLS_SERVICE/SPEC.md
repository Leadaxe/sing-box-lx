## Why

Дизайн-сессия с владельцем (2026-08-08) зафиксировала CLI-контракт демона и
модель доступа. Скелет (055) + apply (056) давали локальный loopback-канал без
шифрования; для удалённого сервера нужен взаимно-аутентифицированный канал,
регистрация клиентов по модели WG-пиров, управление жизнью ядра отдельно от
конфига и восстановление состояния после рестарта. Плюс — установка демона
системной службой одной командой.

## Design (владельца, 2026-08-08)

**CLI-контракт.** Демон — голая команда `sing-box lxd` (не `run`): порт вшит
(`--listen`, дефолт `127.0.0.1:9091`), `-c` необязателен. Управление клиентами —
`sing-box lxd client add|list|remove`.

**Источник конфига и запуск.** `--config-force <файл>` — всегда бутиться с него;
иначе last-good; иначе `-c`-затравка; иначе idle. `--run` форсит подъём ядра;
без него запуск определяет память run-состояния (`was_running` в state-dir:
«1»/«0», **отсутствие файла = свежий state** — интент ни разу не записывался,
и при наличии конфига ядро стартует: контракт 056 «`-c` на чистом хосте
бутится» жив). Апстрим-модель boxdd: рестарт восстанавливает «как было»;
явный `/admin/stop` пишет «0» и переживает рестарты, успешный apply и
автооткат пишут «1».

**start/stop.** `/admin/start` и `/admin/stop` управляют жизнью ядра, не трогая
демон и канал; stop пишет «stopped» в память (рестарт не поднимет ядро).

**mTLS + регистрация.** Демон — сам себе CA (`--tls`): на первом старте
самоподписывает серверную пару (ECDSA P-256, стабильный отпечаток в state-dir;
IO-ошибка чтения пары или ключ-без-серта = отказ старта, тихая перегенерация
запрещена — она молча инвалидирует все пины). TLS-конфиг анонсирует ALPN
`h2, http/1.1` — без `h2` gRPC-плоскость поверх TLS недостижима для
grpc-клиентов. Нет зарегистрированных клиентов → печатает приглашение
`адрес#отпечаток#код`, **только в интерактивный терминал** (stdout-TTY): под
службой код в персистентный лог не пишется (лог 0644 переживает бес-TTL-код;
в лог идёт подсказка про `client add`). Лаунчер пинит сервер по отпечатку из
строки, генерит свою клиентскую пару, `POST /admin/enroll` с кодом → сервер
пинит клиентский серт. Код одноразовый (сгорает после регистрации одного
клиента), без TTL (не подобрать — `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`, 3 группы
по 4). Все плоскости (admin-REST и gRPC-наблюдение) требуют пиннингованного
клиентского серта; enroll — единственный маршрут до доверия, за одноразовым
кодом. Операторские маршруты (`/admin/clients`, `/admin/client-code`,
`/admin/client-remove`) — сознательное исключение из пина для CLI на самом
хосте: **loopback-only** (RemoteAddr) + Bearer; минт кода = выдача доверия и из
сети недоступен. `client add [--name]` минтит новый код у живого демона (день
N, без рестарта; метка оператора побеждает имя, предложенное клиентом при
enroll), `list`/`remove` — просмотр и отзыв.

**Секрет.** ⚠️ Абзац ниже — исходный замысел, **отменён ревизией** «daemon.json
— дом демона»: `--secret-file`, env и `--secret` удалены полностью, секрет
живёт только в daemon.json, а Bearer — операторский мандат, не второй фактор
поверх пина. Оставлено для истории решения.

~~`--secret-file` (0600) → env `SING_BOX_LXD_SECRET` → argv-флаг
`--secret` (виден в ps); сравнение constant-time. Bearer — второй фактор
поверх пина. В службу `--secret` не переносится: plist мир-читаем, поэтому
install/install-user/print с `--secret` **отказывают** с подсказкой про
`--secret-file` (молчаливое разоружение службы запрещено).~~

**Служба.** `--service=install|install-user|uninstall|print`. `install` —
системный LaunchDaemon (root, для сервера: TUN, до логина, `/Library/…`);
`install-user` — пользовательский LaunchAgent (без sudo, десктоп-UX как у
обычных .app, `~/Library/…`, `gui/<uid>`). Обе роли переносят командную строку
демона (минус `--service`) в plist (`RunAtLoad`+`KeepAlive` = launchd-аналог
`Restart=always`), **абсолютизируя все пути** (state-dir/config-force/`-c`) — иначе
launchd-юнит с cwd `/` крэш-циклит на относительном `--state-dir`; дефолтный
state-dir службы = `<support>/state` (абсолютный). install сам создаёт каталоги
лога/состояния (`0700` — внутри серверный ключ, доверенные клиенты, last-good).
`print` — сухой прогон plist (системный scope). `uninstall` снимает любой
найденный scope (сначала user, потом system; системный без root отбивается с
подсказкой про sudo) и по умолчанию **оставляет** state (клиенты/last-good/
ключи — чтобы переустановка сохранила enrollment), печатая подсказку про
`--purge`; `--purge` сносит support-каталог (кастомный `--state-dir` вне
support-каталога не трогается). Non-interactive (без Y/N) — uninstall идёт из
скриптов/сервиса без TTY. Linux/Windows — заглушки.

## Verification

- Юниты (зелёные): пайплайн apply/rollback (056), store (атомарность,
  pending/was_running, ReadFile-ошибка ≠ отсутствие файла), admin-auth.
- Сборка ± тег (стаб без тега пуст), gofmt, go vet чисты.
- Сквозное mTLS-демо на macOS (сборка `1.14.0-lx.23-lxd3`, порт 19092):
  голый старт → idle; plain-HTTP отбит; приглашение напечатано; пин сервера по
  отпечатку совпал; enroll по коду + клиентский серт; без серта → «client
  certificate not trusted»; повторный enroll тем же кодом → «no active
  enrollment code» (сгорел); apply/stop по mTLS, канал жив после stop; память
  run-состояния (stop→рестарт idle; `--run`→started); приглашение не печатается
  при наличии клиента; `client list/add/remove` через живой демон;
  сухой прогон даёт корректный plist (командная строка → ProgramArguments; на
  момент прогона он вызывался как `--service=print`, ныне
  `--service=install --dry-run`).
- **Служба device-verified на macOS (обе роли):** `install-user` без sudo →
  launchd `state = running`, `runs = 1`, `never exited`, порт слушается,
  приглашение в логе; `KeepAlive` перезапустил после `kill -9` (новый pid);
  `uninstall` без `--purge` оставил state + подсказку, с `--purge` снёс каталог.
  Системный `install` (sudo, владельцем): первый прогон **поймал крэш-цикл**
  (`runs=5`, `last exit code=1`, `mkdir lxd-state: read-only file system` —
  относительный state-dir резолвился в `/`); после фикса абсолютных путей —
  `state = running`, `runs = 1`, `never exited`, pid от root, порт 19093 LISTEN,
  приглашение в логе, `uninstall --purge` снял plist и вычистил каталог.

## Из ревью 056 (внесено в этот же код)

Bootstrap под `applyAccess` (гонка с первым apply); shutdown под мьютексом +
буфер сигналов 4 (потеря SIGTERM); ошибки стора → отдельный исход `applyError`
(500, не 422); `setFatal` чистит active (config не отдаёт мёртвый конфиг);
ReadFile различает «нет файла» от IO-ошибки; http.Server с таймаутами
(ReadHeader/Idle); мёртвый тест temp-файлов починен.

## Из ревью 055–057 (multi-agent, 2026-08-08; внесено следом)

Закрыто по подтверждённым находкам: операторские маршруты стали loopback-only
(critical: минт кода был достижим из сети в обход пина); ALPN `h2` в
TLS-конфиге (gRPC поверх mTLS был мёртв — подтверждено пробой, согласованный
ALPN пуст); приглашение не пишется в лог службы (код без TTL оседал в
мир-читаемом `lxd.log`); install с `--secret` отказывает (секрет молча
выбрасывался из plist); свежий state с явным `-c` бутится без `--run`
(гейт `was_running` делал seed мёртвым, `/admin/start` отвечал 404;
`was_running` теперь тристейт «1»/«0»/нет файла); IO-ошибка чтения серверной
пары не перегенерирует отпечаток; инфраструктурные сбои валидатора → 500, не
422; автооткат пишет `was_running=1`; `client add --name` доезжает до enroll;
env-канал секрета `SING_BOX_LXD_SECRET`; teardown симметричен на обоих путях
(serve-error и сигнал) + `closed`-флаг контроллера; support-каталог службы
0700; подсказка sudo при uninstall системного scope; `-C` отбивается явно.
Тестовый долг: HTTP-контракты всех admin-маршрутов, tlsca (стабильность
отпечатка), plist/абсолютизация путей, store/clients-инварианты, интеграционный
`TestControlPlaneSurvivesBrokenApply` на реальном ядре; тесты lxd включены в
lx-ci (go test -race, vet, gofmt-фильтр покрывает `lxd/`).

## Ревизия модели владения (2026-08-09): daemon.json — дом демона

Проблема исходной модели: Bearer-секрет — учётные данные ДЕМОНА — жил в
каталоге клиента (`bin/daemon/secret` лаунчера, передавался через
`--secret-file` в plist). Инверсия владения: переустановка/удаление лаунчера
ломала службу при следующем старте, лаунчер писал секрет внутрь собственного
.app-бандла, секрет «принадлежал» одному клиенту.

Новая модель — демон полностью самодостаточен в своём state-dir:

- **`<state-dir>/daemon.json`** (0600, атомарная запись) — базовые настройки
  демона: `listen`, `tls`, `secret`, лимиты ротации лога
  (`log_max_size_mb`/`log_max_backups`/`log_max_age_hours`). Plist вырождается
  в `sing-box lxd --state-dir <dir>`; смена настроек = правка файла + рестарт
  службы, не переустановка.
- **Ровно один источник истины (ревизия 2026-08-10, финал):
  connection-флагов НЕ СУЩЕСТВУЕТ.** `--listen`/`--tls`/`--secret`/
  `--secret-file` и env-секрет удалены полностью — вопрос «кто побеждает»
  невозможен по построению. daemon.json есть → он и только он; файла нет →
  фиксированные dev-дефолты (plain h2c на 127.0.0.1:9091, без секрета),
  файл неявно не создаётся. `--service=install` решает всё сам: адрес —
  существующий из файла (реинсталл не двигает канал под сопряжёнными
  клиентами) либо первый свободный loopback-порт с 19091; mTLS — всегда;
  секрет — существующий либо генерируется. В конце install печатает
  сводку: адрес канала, админ-секрет, путь к daemon.json, команду
  перезапуска службы и одноразовое приглашение. Boot-параметры
  (`-c`/`--config-force`/`--run`) остаются флагами. `client`-сабкоманды
  читают только daemon.json (без файла — ошибка: безфайловый dev-демон
  работает plain без реестра клиентов, `client …` против него бессмыслен).
- **Секрет генерирует демон** (`--service=install` при отсутствии), реинсталл
  сохраняет существующий. Клиенты секрет НЕ знают и не хранят.
- **Аутентификация разведена по ролям:** доверенный клиентский сертификат —
  ПОЛНЫЙ мандат mTLS-плоскости (admin + gRPC, Bearer поверх не требуется;
  Bearer без серта пиновую зону НЕ открывает). Bearer — операторский мандат
  loopback-маршрутов (`client-code`/`clients`/`client-remove`) и единственный
  гейт plain-h2c (dev). gRPC-интерцептор секрета при TLS отключён — пин серта
  уже стоит в h2c-обёртке.
- **`GET /admin/info`** — паспорт демона: `version`, `state_dir`, `listen`,
  `tls`, `fingerprint`, `pid`, `uptime_seconds`, `log_path`. Клиенты берут
  пути отсюда вместо хардкода (лаунчер: каталог для `cache_file`).
- **Bootstrap сопряжения:** `--service=install --tls` после старта службы
  минтит одноразовое приглашение через operator-маршрут (install под root
  знает секрет из daemon.json) и печатает в stdout — терминал оператора или
  захват привилегированного вызова лаунчера; в лог службы не попадает, код
  сгорает на первом enroll. Пере-сопряжение: `sudo sing-box lxd client add`
  — без флагов находит state-dir установленной службы (system → user) и
  берёт listen/tls/secret из её daemon.json.

### Лог демона: демон владеет файлом и ротирует его (2026-08-11)

launchd `StandardOutPath` — вечный append (наблюдался рост до 39 МБ за
~1.5 суток на info-логах ядра), `newsyslog.conf` не умеет пути с пробелами
(`/Library/Application Support/…`), а user-scope он не покрывает вовсе.
Поэтому ротация — in-process, одинаковая для обеих областей установки:

- На старте, если stdout — **не терминал** (служба), демон переоткрывает
  `<support>/lxd.log` и dup2-ит его на fd 1/2: в ротацию попадает ВСЁ —
  свой лог, лог ядра, паники рантайма. Plist не меняется: launchd-редирект
  на тот же путь остаётся аварийным каналом для вывода до перехвата
  (существующие установки получают ротацию без переустановки). В терминале
  (dev) лог остаётся на экране; безфайловый dev-запуск файла не заводит.
- Фоновый тикер (раз в минуту): ротация по возрасту файла и по размеру;
  сдвиг поколений `lxd.log.1…N`, хвост за `log_max_backups` удаляется;
  удалённый из-под демона файл пересоздаётся. Rename догоняют открытые
  дескрипторы — конкурентные писатели ничего не теряют.
- Дефолты «≈сутки истории»: 24 ч возраст, 1 бэкап, 20 МБ страховочный
  потолок; ключи daemon.json (0 = дефолт, «безлимита» нет).
- darwin (dup2) и linux (dup3 — на arm64 dup2 нет); Windows — заглушка
  (rename открытого файла там и не работает; ждёт Windows-службы).

### `--service` на linux: только печать рецепта (2026-08-11)

**Принцип: на linux `--service` ТОЛЬКО ПЕЧАТАЕТ.** Всё, что меняет диск —
unit/init-скрипт, `daemon.json`, удаление state — выполняет оператор. launchd
— один вендор с одним API; linux — зоопарк (systemd, OpenWrt/procd,
контейнеры без обоих), и неверная догадка, мутирующая `/etc`, хуже точной
распечатки. У read-only нет полусостояний: рецепт, не применяемый частично,
не оставит хост между двумя конфигурациями.

- **Детект init:** `/proc/1/comm` — главный судья (кто реально рулит машиной,
  а не что лежит на диске); фолбэки — `/etc/openwrt_release` и
  `/run/systemd/system` (та же проверка, что в `sd_booted()`; `/run` — tmpfs,
  chroot не подделает). Пути вынесены в переменные — тесты подменяют корень.
- **install/print** печатают: ссылку на нужный раздел
  [docs-lx/lxd-daemon.md](../../../docs-lx/lxd-daemon.md) (якорь по
  обнаруженному init), явное «NOTHING was installed», затем шаги — дом демона
  + `daemon.json`, unit/init-скрипт, команды включения, шаг сопряжения.
  `print` идентичен install по построению.
- **Секрет на экран не попадает никогда:** в рецепте стоит
  `$(head -c 32 /dev/urandom | xxd -p -c 64)` — генерится при выполнении, не
  оседает ни в скроллбеке, ни в логе ssh-сессии.
- **uninstall** печатает шаги снятия; `--purge` печатает `rm -rf`, а НЕ
  удаляет: в state лежат реестр клиентов и серверный ключ.
- **Дефолтные дома:** procd — `/etc/sing-box-lxd/state` (на OpenWrt `/var` —
  tmpfs, `/etc` — персистентный overlay), systemd — `/var/lib/…`, user-scope —
  XDG `~/.local/state/…`. Для procd рецепт дополнительно предупреждает про
  износ NAND без extroot и про `/etc/sysupgrade.conf`.
- В общей ветке install (`cmd/sing-box`) появился гейт
  `lxd.ServiceInstallIsAdvisory`: где установщик только печатает, там нельзя
  ни материализовать daemon.json, ни минтить инвайт (демон ещё не запущен).

### Отложено (план, не реализовано)

- Ротация секрета с консоли (`lxd secret rotate`) и серверной пары
  (`lxd identity rotate` — инвалидирует пины всех клиентов, печатает свежее
  приглашение).
- Дебаг-дампы по запросу в `<state-dir>/debug/` (goroutine dump, pprof .pb —
  как в Android-приложении).
- Audit-лог админ-доступа (`<state-dir>/logs/admin_access.log`: время,
  клиент/loopback, маршрут, результат).
