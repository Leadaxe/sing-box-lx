# SPEC: 097 — LAZY_WG_DEVICE_BUILD

**Фича:** [ENERGY](../../FEATURES/008-ENERGY/FEATURE.md)

| Поле | Значение |
|------|----------|
| Тип | F (feature) — WG/AWG-устройство собирается при первом дайле, а не на старте ядра; потолок одновременно собранных устройств; состояние endpoint'а в наблюдаемости |
| Статус | N (new) — заведена по решению владельца 2026-09-24, кода нет |
| Ветка | `lx` |
| Build-tag | `with_lx_idle_suspend` (тот же, что у SPEC 020 — механизм тот же) |
| Связано | [020](../020-MULTI_WG_IDLE_BUFFER_HEAT/SPEC.md) (уровни сна, `resumeOnDial`, `Rebuild`/`Teardown` — переиспользуются целиком), [030](../030-FAST_BOX_SHUTDOWN/SPEC.md) (закрытие endpoint'ов), [019](../019-URLTEST_MODE_STICKY/SPEC.md) (пробы urltest будят endpoint'ы), [096](../096-NAIVE_ENGINE_POOL/SPEC.md) (тот же класс для naive), LxBox 519 (профиль на эмуляторе 2026-09-24) |

## 1. Проблема

Профиль LxBox на эмуляторе (11 WG/AWG-endpoint'ов, ядро lx.8): каждый endpoint держит ≈17.5 МБ с момента старта — пулы wireguard-go на 11 устройств заняли 192 МБ, 93 % кучи, утечки нет, зависимость линейная. Причина — не `PopulatePools` (WaitPool ленивый), а стартовые батчи горутин `RoutineReadFromTUN` и `RoutineReceiveIncoming`: по 128 буферов на 64 КБ (на Android `MaxSegmentSize` = 64 КБ ради GRO, SPEC 010), для v4- и v6-бинда, выделяются сразу при `Start`. Подписка с десятком AWG-узлов на probe-сессии LxBox (лимит 150 МБ) — кандидат на OOM. Старт ядра при этом платит сборку всех устройств последовательно (на Mac 0.10 с на 11 узлов; на больном хосте — десятки секунд, см. LxBox 519).

Уменьшать буферы нельзя: 64-КБ сегменты питают GRO на Android (SPEC 010). Параллельный старт не уменьшает сумму и делает пик памяти одновременным. Остаётся не строить устройства, которые никто не использует.

## 2. Решение

### 2.1 Холодный старт в состоянии «торн-даун»

SPEC 020 уровень 3 уже описывает endpoint без устройства: `torndown = true`, `idleAsleep = true`, а `resumeOnDial` по первому дайлу делает `Rebuild()` + `Start(false)` + `Start(true)`. Задача — прийти в это состояние сразу на старте: `Start(StartStateStart/PostStart)` для endpoint'а под `with_lx_idle_suspend` не собирает устройство, а помечает endpoint как усыплённый уровня 3 с меткой «никогда не поднимался». Первый дайл (пользовательский или проба urltest) собирает устройство ровно как пробуждение после сна.

Что сохраняется без изменений: резолв `detour` на стадии Start (SPEC 029 — он не требует устройства), `InitializeDetour`, регистрация pause-колбэков (перенести в момент сборки, как при `Rebuild`), поведение `Close` над торн-даун endpoint'ом (уже идемпотентно, SPEC 020/070).

### 2.2 Потолок одновременно собранных устройств

Одного ленивого старта мало: urltest пробует все узлы группы сразу после старта, и все устройства всё равно собираются — пик тот же, только позже. Поэтому второй механизм — **бюджет собранных устройств**: не больше N устройств живут одновременно. Дайл, которому нужно собрать (N+1)-е, сначала разбирает самое давно неиспользуемое усыплённое устройство (по `IdleSince`), а если все N заняты живыми соединениями — ждёт освобождения или собирается сверх бюджета с предупреждением (выбор — §5). Пробы urltest под бюджетом идут очередью, а не веером: замер группы из K узлов становится длиннее (K/N сборок последовательно), зато память ограничена.

Ключ: `lx.wg.build_max` (целое, 0 = без потолка = сегодняшнее поведение) в корневом блоке `lx` ([098](../098-LX_ROOT_CONFIG_BLOCK/SPEC.md)). Дефолт — 0; LxBox выставляет для probe-сессий по лимиту памяти.

### 2.3 Состояние endpoint'а в наблюдаемости

Сегодня состояния сна SPEC 020 наружу не отдаются (в `daemon/*.proto` полей нет). Добавить в `GetOutbounds`/`ChainInfo`-ответы поле состояния endpoint'а: `never_built` / `building` / `up` / `asleep` (уровень 1–2) / `torn_down` (уровень 3), плюс `idle_since`. Это состояние, а не ошибка (`empty-observability-field-is-state-not-bug`); приложение показывает «узел не поднят» и не пугает пользователя таймаутом.

## 3. Границы

- Провод WG/AWG не меняется; буферы wireguard-go не меняются.
- Без `with_lx_idle_suspend` поведение прежнее (устройства на старте).
- `lx.wg.build_max` действует только на WG/AWG-endpoint'ы; MASQUE, naive, chain-звенья — вне объёма (naive — SPEC 096).
- Хендшейк: первый дайл через свежесобранное устройство платит сборку + рукопожатие (у доменных peer'ов — апстримный фикс `96b004bab` в lx.10 должен убрать 5-секундную задержку первого хендшейка, сверить прогоном lx.10).

## 4. Критерии приёмки

1. Юниты: старт с `with_lx_idle_suspend` не создаёт устройства (счётчик `NewDevice` = 0), первый дайл создаёт ровно одно, параллельные дайлы — одно; `Close` до первого дайла чист; бюджет N: (N+1)-я сборка разбирает самое старое усыплённое устройство; пробы urltest на K узлах при бюджете N дают не больше N живых устройств одновременно.
2. Замер на эмуляторе (конфиг из LxBox 519, 11 endpoint'ов): Native/Go heap после старта и после «проверки на всех серверах» при `lx_wg_build_max: 3` против сегодняшних 192 МБ; время старта до `tunnel=connected`.
3. Прогон по раннбуку §1.4: туннель, DNS, urltest, WG/AWG-узлы, стоп/старт ×3, смена сети.
4. Наблюдаемость: LxBox отличает «не поднят» от «мёртв» по полю состояния.

## 5. Решения владельца (открытые)

- Дефолт `lx_wg_build_max`: 0 (как сегодня) или, например, 4 на мобильных.
- Поведение при исчерпании бюджета живыми соединениями: ждать освобождения (ограниченно, с таймаутом дайла) или собрать сверх бюджета с предупреждением.
- Решено 2026-09-24 ([098](../098-LX_ROOT_CONFIG_BLOCK/SPEC.md)): отдельный ключ `lx.wg.lazy_build` (дефолт `false`), требует `lx.wg.idle_suspend`; ключи 097 парсятся в 098, действуют с 097.
