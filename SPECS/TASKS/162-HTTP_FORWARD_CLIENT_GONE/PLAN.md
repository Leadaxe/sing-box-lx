# План

Реализация — на `lx-1.15` после перехода. Перед началом сверить номера строк
ниже с текущим `upstream/testing`: ветку перезаливают, `forward.go` молодой
(два коммита).

## Алгоритм

Приём сервера `net/http` (`connReader.startBackgroundRead`) поверх уже
имеющегося буфера клиента `c.reader`. На каждый `serveForward` создаётся
объект сторожа.

1. **Старт.** Только когда запись запроса к узлу вернулась без ошибки
   (горутина `forward.go:93-99`): тело прочитано, `c.reader` больше никто не
   читает, гонки с `bufio.Reader` нет. Одинаково для запросов с телом и без.
2. **Проверка дедлайнов.** Перед стартом `c.conn.SetReadDeadline(time.Time{})`;
   ошибка — соединение без дедлайнов (труба, часть `detour`), не сторожить.
3. **Горутина** делает `c.reader.Peek(1)`:
   - байт есть — пришёл следующий запрос, клиент жив; выйти, байт остаётся
     в буфере;
   - таймаут — это наша остановка или дедлайн апстрима (`forward.go:183`);
     тихо выйти;
   - конец потока или сброс — отметить «клиент ушёл» и закрыть оба конца
     трубы к узлу. Поле `c.upstream` горутина не трогает.
4. **Остановка.** `defer` в `serveForward` и явно перед `relayUpgrade`:
   `SetReadDeadline` в прошлое, дождаться горутину, сбросить дедлайн.
   `bufio.Reader` отдаёт ошибку таймаута один раз и остаётся рабочим. Если
   горутина не вышла за 1 с (соединение принимает дедлайн, но не исполняет),
   закрыть `c.conn`.
5. **Клиент ушёл.** В ветке ошибки `readResponse` (`forward.go:105`): если
   отмечено — `closeUpstream()` и `return requestClose, net.ErrClosed`.
   502 не пишется, `finishConnection` логирует на debug (`server.go:144`).
6. **Ответы 1xx** — сторож живёт через весь цикл чтения и через стриминг тела
   ответа, с записью в `c.conn` не пересекается.
7. **Жёсткий разрыв.** Чтобы соединение через узел закрылось, а не только
   получило `CloseWrite`, `upstreamConn` хранит серверную сторону трубы
   (`server_h2.go:260`), и закрытие идёт по обеим.

## Размещение

Логика — новый `transport/http/forward_watch_lx.go` (~70 строк), без
build-тега. Вставки `// lx: SPEC 162` в апстримные файлы:

| Вставка | Место | Строк |
|---|---|---|
| поле серверной стороны трубы в `upstreamConn` | `forward.go:20-29` | 1 |
| заполнение поля в `newUpstreamConn` | `server_h2.go:262-269` | 1 |
| создание сторожа и `defer stop()` | после `forward.go:91` | 2 |
| `watch.start()` при успешной записи запроса | горутина `forward.go:93-99` | 1–3 |
| проверка «клиент ушёл» | `forward.go:105` | 3 |
| `watch.stop()` перед `relayUpgrade` | перед `forward.go:138` | 1 |
| жёсткий разрыв в HTTP/2 и HTTP/3 (по решению владельца) | `server_h2.go:193` | 1 |

Входы `protocol/http` и `protocol/mixed` не трогаются.

Зона конфликта при синке: `transport/http/forward.go` и `server_h2.go`.
Вставки однострочные; при рефакторинге апстрима сломается компиляция, а не
поведение.

## Тесты

Тестов у апстрима в пакете нет, модуль `test/` у нас не собирается — новый
`transport/http/forward_watch_lx_test.go`: loopback TCP и фейковый `Handler`,
который держит серверную сторону трубы и молчит.

- GET, клиент закрылся → чтение серверной стороны вернуло ошибку за ≤200 мс,
  502 не записан. Red без вставок.
- Keep-alive: два запроса подряд, второй обслужен.
- Pipelining: второй запрос отправлен до ответа на первый и не потерян.
- POST 1 МБ: закрытие клиента после тела → разрыв.
- Upgrade: закрытие до 101 → разрыв.
- Клиент по TLS (`tls.Server` поверх loopback).
- Соединение без дедлайнов: сторож не стартует, запрос проходит.
- Всё под `-race`; пакет — строкой в `.github/workflows/lx-ci.yml`.

Стенд на loopback (путь трафика Mac не задевается): сервер принимает
соединение и игнорирует FIN; ядро с `mixed` + `direct`;
`curl -x … --max-time 2 http://…`; соединение к серверу закрыто.
