## 0. TL;DR

`vhttp` принимает третье значение — `auto`: h3-нога стартует в своей горутине, и
если за 3 с не вернулась — стартует h2, **не дожидаясь возврата h3**. Победивший
режим запоминается (таймаут платит только первый туннель процесса), поздний успех
проигравшей ноги закрывается в фоне. Фиксированные `h3`/`h2` — ровно как раньше.

Ключевое решение — **отвязанный fallback**: вызывающий никогда не ждёт возврата
ноги. Полевой прогон показал, что застрявшая h3 может сидеть в чужом cleanup-коде
минутами (quic-go `Transport.Close` → блокирующийся `transportResponseBody.Close`
из `x/net/http2`, см. находки в [[SPECS/TASKS/050-URLTEST_ZOMBIE_RUN_SURVIVES_RESTART]]),
и «заставить ногу быстро вернуться» — борьба с кодом, который мы не контролируем.
Решение по таймеру, а не по возврату, закрывает весь класс: и найденные
зависания, и будущие.

## 1. Проблема (полевой разбор 2026-08-24)

MASQUE-выход к Cloudflare WARP **молча не поднимался** через часть промежуточных
узлов. Стенд на живых узлах (три способа выхода, шесть замеров) показал:

| Проба | через vless/TCP (Финляндия) | через vless/xhttp (Швейцария) |
|---|---|---|
| UDP DNS → 1.1.1.1:53 | ✅ 0.09 с | ✅ 0.28 с |
| QUIC → www.google.com:443 | ✅ хендшейк 253 мс | ✅ хендшейк 695 мс |
| QUIC → WARP `162.159.198.2` | отвечает (CRYPTO_ERROR за 125 мс) | ❌ тишина 30 с |
| QUIC → WARP `.198.1` / `.197.2` | — | ❌ тишина |

**Вывод:** UDP и QUIC через оба узла ходят (Google отвечает), а Cloudflare
**игнорирует QUIC с выходного IP** части хостеров. Отказа при этом нет — есть
тишина: хендшейк висит до дедлайна вызывающего (десятки секунд), и наружу это
выглядит как «MASQUE не работает», без единой строки, объясняющей почему.

Ручной обход — переставить узел на `vhttp: h2` — работает всегда (TCP:443
Cloudflare принимает отовсюду; замер той же цепочки на h2: 205 мс), но требует
знать про дыру и держать два узла-близнеца.

## 2. Контракт

```json
{ "type": "masque", "tag": "warp", "profile": "cloudflare", "vhttp": "auto", … }
```

| Значение `vhttp` | Поведение |
|---|---|
| `h3` | только QUIC — пин на одну ногу |
| `h2` | только TCP — как раньше |
| **`auto`** (дефолт с v2) | h3 в отдельной горутине; через 3 с (или по её ранней ошибке) — h2; победитель запоминается; поздний успех ноги закрывается |

Правила:

- **Отвязка, а не потолок.** Решение о fallback принимает wall-clock-таймер в
  `connect()`; нога дополнительно несёт бюджет на сам QUIC-хендшейк (не на
  UDP-сокет — тот может легально долго подниматься через detour/цепочку), и там,
  где контексты уважаются, возвращает чистую ошибку раньше таймера → h2 стартует
  немедленно. Дедлайн вызывающего не трогается.
- **Застрявшая нога не держит дозвон.** Если h3 не вернулась к таймеру, она
  бросается: её единственный результат дочитывает фоновая горутина, поздний
  успех закрывается. Цена — до одной зомби-горутины на процесс на клинически
  застрявшем пути (память режима не даёт ходить в h3 повторно); это горутина,
  которая точно так же висела бы и без `auto`.
- **h2 упал, а брошенная h3 ещё жива** — её результат ждётся (лучшего
  предложить нечего): медленный-но-живой путь спасает дозвон и запоминает h3.
- **Отмена вызывающим — не вердикт h3.** Если `ctx` умер снаружи, fallback не
  делается и ничего не запоминается: пользователь просто отменил дозвон.
- **Память по процессу.** Первый успешный режим запоминается (atomic) и пробуется
  первым в следующих туннелях; после `Close`/рестарта — заново с h3.
- **Обе ошибки в отчёте.** Если упали обе ноги, ошибка несёт и h3, и h2 — иначе
  «h2 failed» скрывает, почему ушли с h3.
- **`standard`-профиль:** h2 там не реализован, поэтому `auto` вырождается в h3
  с предупреждением в лог (а не в ошибку старта).
- **Потолок MTU h2 (`maxH2MTU`) применяется и к `auto`** — иначе fallback был бы
  заведомо нерабочим; проверка на старте, как для явного h2.
- **TLS:** для `auto` готовятся оба клиента (ALPN `h3` и `h2`), поэтому переход
  стоит один дозвон, а не пересборку outbound'а. Предупреждение «фрагментация
  игнорируется на h3» для `auto` не выдаётся — h2-нога её использует.

## 3. Почему таймаут 3 с

Из полевых замеров: рабочий h3-хендшейк укладывается в 250–700 мс даже через два
прокси-хопа, а отфильтрованный путь не отвечает вовсе. 3 с уверенно отделяют
«медленно, но работает» от «никогда», не отнимая h3 у медленных, но живых путей.
Константа `autoH3Timeout` в коде; юнит держит её в диапазоне 1–10 с.

## 4. Критерии приёмки

1. h3 застряла НАВСЕГДА (игнорирует ctx и бюджет — как quic-go в чужом cleanup)
   → дозвон уходит в h2 за ~бюджет, не дольше. ✅ `TestAutoFallsBackWhenH3StuckForever`
2. Висящий-но-отзывчивый h3 → h2 по таймеру/бюджету; бюджет не тратится на
   подъём UDP-сокета через detour. ✅ `TestAutoFallsBackWhenH3Hangs`,
   `TestAutoBudgetCoversHandshakeNotSocketDial`
3. Рабочий h3 → h2 не дозванивается вовсе. ✅ `TestAutoKeepsH3WhenItWorks`
4. Поздний успех брошенной h3 закрывается, не течёт. ✅ `TestAutoLateH3WinnerIsClosed`
5. h2 упал, поздняя h3 добежала → используется и запоминается.
   ✅ `TestAutoH2FailureWaitsForLateH3`
6. Отмена вызывающим → ошибка, без fallback и записи в память.
   ✅ `TestAutoDoesNotFallBackOnCallerCancellation`
7. Обе ноги упали → в ошибке обе причины. ✅ `TestAutoReportsBothLegsOnTotalFailure`
8. Фиксированный `vhttp` → прежнее поведение. ✅ `TestFixedNetworkNeverFallsBack`
9. После fallback следующий дозвон стартует сразу с h2. ✅ `TestRememberedLegIsTriedFirst`
10. Память потокобезопасна (`-race`). ✅ `TestRememberNetworkIsRaceFree`
11. Неизвестное `vhttp` отвергается с перечислением трёх вариантов; `mtu` >
    `maxH2MTU` при `auto` — ошибка старта.
12. Живой стенд: глухой h3 через xhttp-хоп → «h3 handshake exceeded 3s …
    abandoned» и «h2 tunnel established» на 3.30 с; быстрая пин-ошибка h3 →
    h2 немедленно. ✅ прогон 2026-08-24.

## 5. Намеренно не делаем

- **Happy-eyeballs (одновременный старт обеих ног).** Удваивает хендшейки в
  каждом дозвоне ради единиц секунд один раз за процесс. Отвязанный fallback
  даёт ту же устойчивость без гонки: h2 стартует только когда h3 не уложилась.
- **Персистентная память режима между запусками** — состояние сети меняется;
  повторная проба h3 на старте стоит 3 с однократно.
- **Автовыбор эндпоинта/перерегистрация WARP** — это про пиннинг ключа и anycast,
  отдельная тема (см. §1: через другой выход CF отдаёт другой ключ).
