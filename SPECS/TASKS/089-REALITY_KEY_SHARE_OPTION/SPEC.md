# SPEC: 089 — REALITY_KEY_SHARE_OPTION

**Фича:** [REALITY](../../FEATURES/017-REALITY/FEATURE.md) (противовес [083](../083-REALITY_MLKEM_KEYSHARE/SPEC.md) в той же линии; в реестре [HOTFIXES](../../FEATURES/004-HOTFIXES/FEATURE.md) — строка «что сторожить»)

| Поле | Значение |
|------|----------|
| Тип | F (feature) — опция `tls.reality.key_share` (`hybrid` / `classical`): по-узловой выбор, нести ли в REALITY ClientHello гибридный key share `X25519MLKEM768`. [083](../083-REALITY_MLKEM_KEYSHARE/SPEC.md) сняла апстримный фильтр целиком, а сети, где двухсегментный ClientHello теряется, требуют способа вернуть классическое приветствие на конкретном узле |
| Статус | D (done, device-verified) — выпущено в `v1.14.1-lx.4`; полевой прогон репортёра LxBox #142 2026-09-18 (Android, мобильная сеть, серверные pcap): `classical` 24/24 и 20/20, `hybrid` 50/50 |
| Ветка | `lx` |

## Why

Полевой отчёт 2026-09-17 (Telegram → LxBox #142): на одном мобильном операторе REALITY-узлы с `fp=chrome` не поднимаются — TCP установлен, ~1,8 КБ ClientHello висит в `Send-Q` и ретранслируется, ответа нет, через 15 с таймаут. Те же узлы в Husi на апстримном sing-box 1.14.0 работают. Репортёр через Debug API сменил только отпечаток на `edge` — узлы ожили.

Механика: после [083](../083-REALITY_MLKEM_KEYSHARE/SPEC.md) `chrome`/`firefox`/`safari` шлют гибрид `X25519MLKEM768` (+1216 байт), ClientHello = 1720/1885/1533 байта и уходит двумя TCP-сегментами; апстрим гибрид вырезает, у него 594 байта и один сегмент. Где-то на пути репортёра двухсегментное приветствие к этим адресам теряется. **Что именно там срабатывает — не доказано**: второй телефон того же оператора работает, провод работает, Chrome на том же телефоне шлёт тот же гибрид на обычные сайты и не ломается; Happ на Xray-клиенте у репортёра тоже не проходит. Xray [#6256](https://github.com/XTLS/Xray-core/issues/6256) описывает ровно этот симптом (1892 байта → 1448 + 444, middlebox молча теряет; 516 байт проходят) и закрыт как not planned.

Ядро не может выбрать за пользователя: новые Xray-серверы (≥ v26.9.8) без гибрида отвергают клиента, а эта сеть с гибридом его теряет. Выбор должен быть у узла. `fp=edge` даёт тот же эффект, но как побочный: это обещание «выгляжу как Edge 85», а не «не шлю ML-KEM», и LxBox вешает на такой узел предупреждение.

## Опция

`tls.reality.key_share` — строка, три значения:

| Значение | Поведение |
|---|---|
| `""` (не задано) | Как несёт отпечаток: `chrome`/`firefox`/`safari` — гибрид, `edge`/`ios`/`android`/`360`/`qq` — только X25519. Текущее поведение 083, ничего не меняется. |
| `"classical"` | `X25519MLKEM768` вырезается из `supported_groups` и `key_share` — тот самый апстримный фильтр, но по выбору узла. ClientHello `chrome` = 594 байта. Работает только с Xray < v26.9.8. |
| `"hybrid"` | Гибрид обязателен: если отпечаток его не несёт, `prepareClientHello` возвращает ошибку `reality key_share "hybrid": fingerprint Edge 85 carries no X25519MLKEM768 key share` — вместо тихого `reality verification failed`, неотличимого от чужого ключа. На отпечатке с гибридом ничего не меняет. |

Любое другое значение — ошибка при построении outbound'а (`unknown reality key_share: classic (expected "hybrid" or "classical")`): опечатка не должна молча становиться дефолтом.

```json
"tls": {
  "enabled": true,
  "server_name": "www.example.com",
  "utls": { "enabled": true, "fingerprint": "chrome" },
  "reality": { "enabled": true, "public_key": "…", "short_id": "0123abcd", "key_share": "classical" }
}
```

Почему строка с тремя значениями, а не булево `hybrid_key_share`:

- пустое значение обязано оставаться «как у отпечатка» — иначе пересборка конфига в приложениях (`badjson` схлопывает отсутствующее поле в дефолт) превратит политику отпечатка в политику ядра;
- `hybrid` нужен как проверка: ядро не может добавить гибрид в `edge`, но может сказать об этом словами при первом рукопожатии;
- имя `key_share` — терминология TLS (расширение так и называется); `key_exchange` из #142 шире и путается с шифросьютами.

## Как реализовано

В `prepareClientHello` (общий с 088) после первого `BuildHandshakeState()`:

- `classical` — `common.Filter` по `SupportedCurvesExtension.Curves` и `KeyShareExtension.KeyShares`, затем второй `BuildHandshakeState()`: пресет применяется один раз (`clientHelloBuildStatus == BuildByUtls`), второй вызов только перемаршаливает hello из отфильтрованных расширений. Это ровно порядок апстрима до 083. `KeyShareKeys.Ecdhe` остаётся — `AuthKey` считается по нему, как и раньше (контракт 083: сначала `Ecdhe`, при nil — `MlkemEcdhe`). У Firefox 148 (reuse одного ключа в обеих записях, 086) после фильтра остаётся классическая запись с тем же ключом.
- `hybrid` — `realityHelloCarriesHybridShare(uConn)`: есть ли `X25519MLKEM768` в `KeyShareExtension` (проводной факт, который проверяет сервер). Нет — ошибка с именем и версией отпечатка.
- Валидация значения — в `newRealityClient`, до построения; `Clone()` переносит поле (outbound'ы клонируют TLS-конфиг на каждый dial).

## Требования

- **R1.** `""` не меняет ClientHello ни для одного отпечатка (страж 083/086/087 + `TestLxRealityKeyShareDefaultKeepsHybrid`).
- **R2.** `classical` убирает `X25519MLKEM768` из обоих расширений, оставляет ровно одну запись `X25519` (32 байта), и `Ecdhe` совпадает с ней; сырой hello короче 1184 байт (в него физически не помещается ML-KEM-ключ), гибридный — не короче 1216. Два независимо собранных hello друг с другом не сравниваются: у Chrome-пресета GREASE-ECH случайного размера, разница плавает (первый вариант стража на этом упал в полном прогоне).
- **R3.** `hybrid` на `edge` — ошибка с текстом про отпечаток; на `chrome` — без изменений.
- **R4.** Неизвестное значение отвергается в `newRealityClient`; `Clone()` сохраняет политику.

## Критерии приёмки

1. Стражи R1–R4 в `common/tls/reality_client_lx_test.go` зелёные (`-tags with_utls -ldflags "-checklinkname=0"`). ✅ 2026-09-17
2. `make -f Makefile.lx lx-build` полным `LX_TAGS`. ✅
3. `classical` против Xray < v26.9.8 → 204; против Xray ≥ v26.9.8 → `reality verification failed` (ожидаемо, документировано). ⏳ стенд — как в 083 §2
4. Проводка в приложениях и прогон на сети репортёра #142 через LxBox. ⏳ «Остаток»

## Границы

- **Не автофолбэк.** «Гибрид, при таймауте — классика» не делаем: репортёр отмечает, что сеть после первого гибридного пролёта примерно минуту не пропускает соединения к тому же серверу, так что фолбэк без запомненного выбора не спасёт; и он не отличим от обычного таймаута сервера.
- **Не ответ для новых серверов в такой сети.** `classical` на Xray ≥ v26.9.8 = отказ сервера. Там остаются [088](../088-REALITY_FRAGMENT_BYPASS/SPEC.md) (если DPI не собирает сегменты) и `detour`.
- Ядро отпечаток по-прежнему не подменяет ([083 §5](../083-REALITY_MLKEM_KEYSHARE/SPEC.md#5-границы)); `key_share` — про содержимое приветствия, не про его форму.
- Серверная сторона REALITY не трогается.

## Остаток

- **LxBox / лаунчер:** по-узловое поле `key_share` в модели узла (переживает обновление подписки, пересборку, экспорт/импорт), UI с предупреждением «отключает постквантовую защиту и не работает с новыми Xray-серверами», проводка в `tls.reality.key_share`. Критерии приёмки #142 в части приложения — там.
- Стенд по 083 §2 для критерия 3.
- Полевой прогон на сети репортёра: `classical` (ожидаемо = его `edge`) и `record_fragment` (088) на одном узле.

## Условие снятия

Не хотфикс, а опция — снимать нечего. Что сторожить на мерже: фильтр `X25519MLKEM768` в `reality_client.go` должен стоять **только** под `case C.RealityKeyShareClassical`; безусловный фильтр апстрима, если он вернётся при мерже, уронит `TestLxRealityKeyShareDefaultKeepsHybrid` и стражи 083/086/087. Если апстрим заведёт свою опцию того же смысла (issue SagerNet#4520 без реакции) — переехать на его имя, оставив `key_share` алиасом на один релиз.
