# TEST_PLAN 062 — конфиг masque к стандарту, с алиасами

## Принцип

Проверяем **схему и её разрешение**, а не поведение туннеля (оно в SPEC 021).
Главный риск — тихая потеря настройки: пользователь задал поле, оно проигнорировано,
и он узнаёт об этом только по неработающему узлу.

Поэтому каждый пункт проверяет не «конфиг принялся», а **что именно доехало до дайла**.
Способ: `log.level: debug` печатает `establishing h3 tunnel to … (sni=…)` — по этой
строке видно фактический SNI. Для остальных полей — живой `box.New` + проверка
собранного `*tls.Config`.

## 1. Матрица разрешения старое/новое

Для каждой пары (`sni` ↔ `tls.server_name`, `skip_cert_verify` ↔ `tls.insecure`,
`fragment*` ↔ `tls.fragment*`, `network` ↔ `transport`):

| случай | ожидание |
|---|---|
| только новое | работает, warning'ов нет |
| только старое | работает, **есть** `deprecated.Report` |
| оба, совпадают | работает, берётся новое, warning'а о конфликте нет |
| оба, противоречат | **fail-fast** с внятной ошибкой, ядро не стартует |

⚠️ Случай «оба совпадают» обязателен: наивная реализация может считать любое
одновременное присутствие конфликтом и ломать рабочие конфиги на переходный период.

## 2. Обратная совместимость (главное)

1. **Боевой конфиг из снапшота LxBox** (со старыми именами: `sni`, `network: "h3"`,
   `network_list`) — поднимается **без правок**, узлы работают.
2. **Живой WARP** на старом синтаксисе: h3 и h2 → `warp=on`.
3. **Живой WARP** на новом синтаксисе (`tls.server_name`, `transport`) → `warp=on`.
4. Оба синтаксиса дают **идентичный** `*tls.Config` (сравнить `ServerName`,
   `InsecureSkipVerify`, `NextProtos`, наличие `VerifyConnection`).

## 3. Предупреждения на неприменимое

| задано | ожидание |
|---|---|
| `tls.alpn` | warning + игнор; ALPN остаётся выведенным из транспорта |
| `tls.ech` / `kernel_tx` / `kernel_rx` / `reality` | warning + игнор |
| `fragment` или `record_fragment` при `transport: h3` | warning, туннель поднимается |

Проверять **фактом**, а не только текстом в логе: после `tls.alpn: ["http/1.1"]`
в `NextProtos` должно остаться `["h3"]`/`["h2"]`, иначе игнор не сработал.

## 4. Декод (badjson)

Проверять живым `box.New`/декодом конфига, а не чтением структуры — прецедент известен
(badjson схлопывает пустые значения):

- `"tls"` отсутствует vs `"tls": {}` — различаются ли, и не падает ли второе;
- `"tls": {"server_name": ""}` — явная пустая строка не должна молча подменяться дефолтом
  профиля (пустой SNI на WARP не работает, см. SPEC 021 — ожидание: либо ошибка, либо
  дефолт, но осознанно и задокументированно);
- `transport: ""` — эквивалент «не задано».

## 5. Регресс SPEC 021 / 060

- дефолтный SNI (`www.cloudflare.com`) применяется, когда не задано ни `sni`, ни
  `tls.server_name` — 4 прогона на живом WARP;
- авто-`record_fragment` под detour (SPEC 060) продолжает включаться и через новый блок;
- pinning: подменённый `public_key` → внятная ошибка, а не успешный коннект;
- `go test -race` по `option`, `protocol/masque`, `transport/masque`, `common/tls`;
- `make -f Makefile.lx lx-build`, `gofmt -l`, `go vet`.

## 6. Риск ложно-зелёного

Если проверять только «ядро стартовало», пройдут все пункты независимо от реализации:
конфиг может распарситься, а поле — потеряться. Пункты 1, 2.4 и 3 обязаны сверять
**фактическое значение**, доехавшее до `*tls.Config` или до строки дайла.

Отдельно: тесты на живом WARP требуют канала, где h3 вообще работает (SPEC 021
§SNI эндпоинта — при cf-SNI он молчит). Перед прогоном убедиться, что baseline-конфиг
с нейтральным SNI даёт `warp=on`, иначе провал теста ничего не значит.
