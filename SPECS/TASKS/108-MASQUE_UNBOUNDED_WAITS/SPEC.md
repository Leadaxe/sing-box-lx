# SPEC: 108 — MASQUE_UNBOUNDED_WAITS

**Фича:** [MASQUE_WARP](../../FEATURES/009-MASQUE_WARP/FEATURE.md)

| Поле | Значение |
|------|----------|
| Тип | B (bug) — три ожидания без предела в masque-outbound: узел зависает без ошибки |
| Статус | I (implemented) — 2026-09-28: код и юнит-тесты в дереве; на живом WARP не прогонялось |
| Ветка | `lx` |
| Источник | Находки N3, N5, N6 исследования [107](../107-MASQUE_UPSTREAM_1_15_COMPARISON/SPEC.md) |
| Связано | [074](../074-MASQUE_VHTTP_AUTO/SPEC.md) (`vhttp: auto`), [022](../022-LX_DEEP_AUDIT/SPEC.md) (тот же класс: CONNECT на h2 без контекста) |

## 1. Поведение

| Ситуация | Поведение |
|---|---|
| `vhttp: auto`, запомнен h2, h2 перестал подниматься | Память сбрасывается, в той же попытке пробуется h3. h3 поднялся — запоминается h3. Оба отказали — ошибка несёт обе причины, следующий dial начинает с h3 |
| То же, dial отменён вызывающим | h3 не пробуется, память сохраняется: отмена не вердикт о ноге |
| `vhttp: h2` задан явно | h3 не пробуется никогда |
| Закрытие h2-туннеля при зависшей записи | `Close()` возвращается сразу: сокет закрывается, зависшая запись получает ошибку |
| Закрытие h2-туннеля без зависшей записи | Перед закрытием уходит `RST_STREAM`, запись ограничена одной секундой |
| Сервер принял QUIC-соединение и не ответил на CONNECT-IP | Ожидание ответа обрывается по контексту dial; в `auto` брошенная h3-нога завершается вместе со своим соединением |
| Ответ на CONNECT-IP получен, позже контекст dial отменён | Туннель не затрагивается |

## 2. Дефекты

### 2.1 Победа h2 в `auto` была необратимой

`auto` запоминает ногу, на которой поднялся туннель, чтобы таймаут h3 платился один
раз. Ветка запомненного h2 при отказе возвращала ошибку и не трогала память: после
смены сети на такую, где TCP закрыт, а UDP открыт, узел отказывал на каждом dial до
рестарта процесса. Обратная ситуация (запомнен h3, он отказал) работала: общий путь
`auto` идёт h3 → h2.

Исправление: отказ запомненного h2 не при отмене вызывающим сбрасывает память и
передаёт управление общему пути `auto`, который в этой попытке h2 повторно не
пробует. Настенный таймер фолбэка при этом выключен — падать уже некуда, и медленный
h3 ждут до ответа или до отмены dial; собственный бюджет хендшейка ноги действует.

### 2.2 `Close()` на h2 ждал писателя

Запись пакета держит мьютекс записи на всё время `Write`, у которого нет дедлайна.
`Close()` брал тот же мьютекс, чтобы послать `RST_STREAM`, и только потом закрывал
сокет. На пути, который перестал принимать данные, `Close()` вставал в очередь за
зависшей записью до таймаута TCP в ядре; за ним стояли разбор сеанса и
`Outbound.Close()`, а dial'ы получали мёртвый сеанс.

Исправление: `Close()` ставит дедлайн записи и берёт мьютекс только если он свободен
(`TryLock`). `RST_STREAM` на соединении с единственным потоком — вежливость: занятый
мьютекс означает, что запись идёт, и её освобождает закрытие сокета.

### 2.3 `ReadResponse` на h3 без контекста

`http3.RequestStream.ReadResponse` контекст не принимает. Если эндпоинт завершил
хендшейк QUIC, отвечает на keepalive и молчит на CONNECT, ожидание длилось, пока живо
соединение. При `vhttp: h3` это держало мьютекс сборки туннеля — все dial узла ждали.
В `auto` фолбэк срабатывал по таймеру, но брошенная h3-нога оставалась висеть вместе
с QUIC-соединением.

Исправление: на время чтения ответа к контексту привязана отмена потока (`CancelRead`
и `CancelWrite`); после получения ответа привязка снимается.

## 4. Границы

- Запись пакета на h2 по-прежнему без дедлайна: зависшая запись освобождается
  закрытием туннеля, а не сама. Обнаружение мёртвого пути на h2 (PING, read-deadline,
  учёт окна) — находка N4, не здесь.
- `CloseWithError` для QUIC-соединения — находка N8, не здесь.
- Смена сети как событие не обрабатывается (N11): сброс памяти `auto` происходит по
  факту отказа ноги.
