# Статус пиров WG/AWG: руководство для потребителей

**Задача:** [SPEC 114](SPEC.md) · **Фича:** [OBSERVABILITY](../../FEATURES/006-OBSERVABILITY/FEATURE.md)

Для кого: LxBox (libbox/gomobile), лаунчер и любой клиент `lxd` (gRPC), оператор сервера (CLI `sing-box api`). Нужна сборка ядра с `with_lx_command`; на сборке без тега вызов `GetWireGuardStatus` отвечает `Unimplemented`.

## 1. Где брать данные

| Канал | Вызов | Что читать |
|---|---|---|
| gRPC (`lxd`, `services: [{type: "api"}]`) | `GetWireGuardStatus(WireGuardStatusRequest{tag})` → `WireGuardEndpointStatus` | `endpointState`, `idleSinceSeconds`, `peers[]` |
| libbox (Android, Apple) | `CommandClient.GetWireGuardStatus(tag)` → `*WireGuardEndpointStatus` | `EndpointState`, `IdleSinceSeconds`, `Peers()` → `PeerStatusIterator` |
| CLI | `sing-box api peers [тег]` (`--url` или `BOX_API_URL`, `--secret` или `BOX_API_SECRET`) | таблица `ENDPOINT STATE PEER ADDRESS HANDSHAKE RX TX` |

Список узлов для экрана по-прежнему даёт `GetOutbounds`: у WG/AWG-узла там `endpointState` и `idleSinceSeconds`, пиров там нет. Окно одного узла зовёт `GetWireGuardStatus(tag)` и получает состояние, простой и пиров одним ответом. Ошибки: `NotFound` — тега нет, `InvalidArgument` — не WG/AWG, `FailedPrecondition` — сервис не запущен, `Unimplemented` — ядро без `with_lx_command` или старше lx.12-rc.2 (в этом случае показывайте узел по `endpointState` без пиров).

Поля пира:

| gRPC / libbox | Тип | Значение |
|---|---|---|
| `publicKey` / `PublicKey` | string | base64-ключ пира, тот же, что `public_key` в конфиге |
| `endpoint` / `Endpoint` | string | `ip:port`; пусто, пока адрес неизвестен |
| `lastHandshakeUnix` / `LastHandshakeUnix` | int64 | Unix-секунды последнего хендшейка; `0` — хендшейка не было |
| `rxBytes`, `txBytes` / `RxBytes`, `TxBytes` | int64 | принятые и отправленные байты устройства, включая служебные |

Только pull: потоки `SubscribeOutbounds`/`SubscribeGroups` статус пиров не несут. Вызов не будит спящий узел и не собирает несобранный.

## 2. Как понять, есть ли связь

Ядро не выносит вердикт «подключён». Его выводит потребитель по трём сигналам: `endpointState`, `lastHandshakeUnix` и изменение `rxBytes` между двумя опросами.

Опора — тайминги WireGuard. Ключ сессии живёт до 180 с (`reject_after_time`). Пока идёт трафик, хендшейк повторяется каждые ~120 с (`rekey_after_time`). Без трафика хендшейк не повторяется: тихий, но исправный пир через 3 минуты выглядит так же, как пропавший, — до следующего пакета.

`age = now − lastHandshakeUnix` (при `lastHandshakeUnix > 0`):

| Условие | Показывать | Почему |
|---|---|---|
| `peers` пуст | по `endpointState` из того же ответа: «не поднят» / «спит» / «выключен» | устройства нет — см. §3.6 |
| `lastHandshakeUnix == 0` | «ещё не подключался» | хендшейка не было ни разу с момента сборки устройства |
| `age ≤ 180 с` | «на связи» | сессия действует |
| `age > 180 с`, rx растёт | «на связи» | редкий случай гонки опроса и rekey; доверять росту rx |
| `age > 180 с`, rx стоит | «нет активной сессии (последний хендшейк N мин назад)» | либо пир просто молчит, либо пропал; ядро различить не может |

Если у AWG-endpoint'а заданы `reject_after_time` / `rekey_after_time` (числом или диапазоном `"min-max"`), берите верхнюю границу `reject_after_time` вместо 180 с.

Чтобы тихий пир не выглядел пропавшим, на одной из сторон нужен `persistent_keepalive_interval`. Keepalive — это трафик, поэтому хендшейк будет обновляться каждые ~2 минуты, пока пир жив.

## 3. Сценарии

### 3.1 Сервер: кто из клиентов сейчас подключён

Конфиг вида «один endpoint, много пиров без `address`, `listen_port` задан».

```bash
BOX_API_URL=127.0.0.1:9090 sing-box api peers
```

```
wg-server  up  RIpg…A1Eo  85.12.34.56:41022  42s ago   1.20 MB  340 KB
wg-server  up  Xk3d…9fQa  -                  never     0 B      0 B
```

Первый клиент на связи, второй ни разу не подключался с момента старта сервера. Для UI то же самое: пройти `peers` и применить таблицу §2.

### 3.2 Сервер: откуда пришёл клиент

`endpoint` у пира без `address` — это адрес, с которого пришёл его последний проверенный пакет:

- сменил сеть (Wi-Fi → LTE) — адрес обновится после первого пакета из новой сети;
- за NAT/CGNAT — внешний адрес NAT, порт часто случайный;
- через detour/relay/MASQUE — адрес промежуточного узла;
- после отключения клиента адрес остаётся: это последний известный адрес, а не «клиент сейчас там». Показывать его только вместе с возрастом хендшейка.

### 3.3 Клиент: карточка WG/AWG-узла

На экране узла: «хендшейк N с назад» и признак из §2. У клиентского endpoint'а с одним пиром достаточно `peers[0]`. `endpoint` здесь почти всегда равен адресу сервера из конфига; если адрес доменный — это резолвленный IP.

### 3.4 Клиент: хендшейк не проходит

Признаки: `endpointState = up`, `txBytes` растёт между опросами, `lastHandshakeUnix` остаётся `0` (или старым), `rxBytes` не растёт. Клиент шлёт инициации, ответа нет. Причины: сервер недоступен, неверный ключ, несовпадение AWG-параметров (`jc`/`s1–s4`/`h1–h4`) с сервером, блокировка по пути. Такой узел стоит показать как «сервер не отвечает», а не «таймаут соединения».

### 3.5 Трафик по пирам

`rxBytes`/`txBytes` — накопленные значения, включая служебный трафик. Скорость — разность двух опросов, делённая на интервал.

Счётчики обнуляются при пересборке устройства (сон уровня 3 `torn_down`, ленивая сборка SPEC 097). Если новое значение меньше прежнего, считайте его новой базой, а не отрицательной скоростью. При обычном сне (`asleep`) счётчики сохраняются.

### 3.6 Спящий, выключенный, несобранный узел

| `endpointState` | `peers` | Что показывать |
|---|---|---|
| `never_built` | пусто | «не поднят» — устройство соберёт первое соединение через узел |
| `building` | пусто | «поднимается» |
| `up` | есть | по §2 |
| `asleep` | есть | «спит»; время хендшейка — с момента до сна, при пробуждении будет новый хендшейк |
| `torn_down` | пусто | «спит» (память освобождена) |
| `disabled` | есть или пусто | «выключен вручную» (SPEC 106) |
| `down` | пусто | «остановлен» |

Не опрашивайте узел пробой (`URLTestOutbound`, `GetURLViaOutbound`) только ради статуса: проба будит спящий узел и тратит трафик. Статус пиров ничего не будит.

### 3.7 Имена пиров

Имён в ядре нет. Потребитель строит таблицу `publicKey → имя` из своего же конфига (у сервера — список клиентов) и показывает имя вместо ключа. Ключ сравнивается строкой base64 как есть.

### 3.8 Сопоставление с логами ядра

wireguard-go пишет в лог `peer(xxxx…yyyy)`: символы 0–3 и 39–42 base64-ключа (в логе sing-box — в нижнем регистре). CLI `api peers` сокращает ключ так же. В UI сокращение пригодится, если показываете логи рядом со статусом.

### 3.9 Несколько пиров в одном endpoint'е

Пиры идут в порядке конфига, и этот порядок стабилен между опросами. Идентифицируйте пира по `publicKey`, а не по индексу: после перезагрузки конфига с другим набором пиров индексы сдвинутся.

## 4. Частота опроса

Вызов дешёвый, но не бесплатный: дамп UAPI под мьютексом устройства. Ориентир — раз в 1–5 с, пока окно узла открыто, и без опроса в фоне. Вызов адресный — один endpoint на запрос; список всех WG/AWG-узлов берите из `GetOutbounds` по непустому `endpointState`.

## 5. Чего нет

- Вердикта «подключён» — только сырые данные (§2).
- Истории: накопление и графики делает потребитель.
- Статуса пиров Tailscale: для него `GetTailscaleStatus` / `sing-box api tailscale peers` (SPEC 115).
- Пиров в `GetOutbounds` и в потоке `SubscribeOutbounds`: поле `GroupItem.peers` было только в rc.1 и удалено.
