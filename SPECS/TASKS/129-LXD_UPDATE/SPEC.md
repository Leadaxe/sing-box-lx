`sing-box lxd update` — отдельный процесс, который сам узнаёт свой путь, версию, ассет и
init хоста, берёт у GitHub `SHA256SUMS` последнего stable-релиза, потоком скачивает архив
своей платформы прямо в `<бинарь>.new` на той же файловой системе, сверяет сумму, проверяет
новый бинарь (`version`, `check` на текущем конфиге), подменяет атомарно (старый — хардлинком),
перезапускает службу через init и откатывает, если новая служба не поднялась. Код по сети не
скачивается — только архив с проверкой суммы. Админ включает кнопку одной строкой:
`"commands": {"update": "/usr/bin/sing-box lxd update"}`.

## 1. Проблема

Обновить ядро на роутере = SSH, инсталлятор или руки: скачать нужный ассет (угадав
платформу), сверить сумму, остановить службу, подменить файл, запустить, убедиться. Лаунчер
хотел бы кнопку, 128 даёт механизм запуска, но саму процедуру кто-то должен уметь надёжно.

Отвергнуто:

- **Shell-скрипт в репо, установленный инсталлятором на хост** — зоопарк busybox / uclient-fetch /
  `ca-bundle`; правка логики требует переустановки; знание платформы и init дублирует то, что
  ядро уже знает.
- **Скрипт с raw-ветки GitHub (`wget … | sh`)** — root исполняет содержимое URL на момент
  клика; ветка меняется без ритуала релиза; `| sh` исполняет обрывок.
- **Скрипт как ассет релиза + локальный бутстрап** — доверие то же, что к бинарю, и логика
  обновляется релизом; но это по-прежнему shell на зоопарке хостов и строка в `daemon.json`,
  которую админ не прочитает. Единственный его плюс — починить сломанный апдейтер без
  обновления — признан слабым: путь обновления проверяется на стенде до тега.
- **Временный архив в `/tmp`** — tmpfs = RAM роутера, 20 МБ архив + 20 МБ распаковка.
  Потоковая распаковка одной записи сразу в целевой каталог.
- **Копия старого бинаря `.old`** — на 16-МБ overlay двух копий не будет; хардлинк стоит
  ноль байт и даёт тот же откат.

## 2. Поведение

### 2.1 Команда

```
sing-box lxd update [--dry-run] [--prerelease] [--no-restart] [--service <name>] [--state-dir <dir>]
```

| Флаг | Смысл |
|---|---|
| `--dry-run` | шаги 1–3 (кто я, что доступно, место) — печать и выход; ничего не меняется. Для диагностики по SSH и для `"check-update": "… lxd update --dry-run"` в лаунчере |
| `--prerelease` | целевой релиз — новейший по API (`releases?per_page=1`), включая rc; по умолчанию — `releases/latest` (stable) |
| `--no-restart` | остановиться после подмены (шаг 5); службу перезапускает админ |
| `--service` | имя службы для restart/health (`/etc/init.d/<name>`, `systemctl … <name>`); дефолт `sing-box-lxd` |
| `--state-dir` | как у `lxd` — где `last_good.json` для `check`; дефолт как у демона |

Только Linux (`runtime.GOOS`); на других платформах — отказ с подсказкой (macOS:
`sudo <новый бинарь> lxd --service=install`; Windows: установщик лаунчера). Не root — отказ
сразу. Вывод — строки `update: …` в stdout, ошибки — `update: ERROR: …` в stderr; коды:
`0` — обновлено или уже актуально, `1` — ничего не изменено, `2` — откат выполнен.

### 2.2 Шаги

1. **Кто я.** Путь бинаря — `os.Executable()` + `EvalSymlinks` (это и есть файл для замены);
   версия — `constant.Version`; ассет — `releasePlatform(...)` (127); init — `detectInit` (127).
   Остатки `.new`/`.old` от упавшего прошлого запуска удаляются.
2. **Что доступно.** `GET https://github.com/Leadaxe/sing-box-lx/releases/latest/download/SHA256SUMS`
   (с `--prerelease`: тег из API, затем `releases/download/<tag>/SHA256SUMS`). Строка
   `<sha256>  sing-box-<ver>-<platform>.tar.gz` даёт версию, имя и сумму; нет строки для
   платформы → `ERROR: no asset for <platform>`. Бинарь, упакованный UPX (`packedWithUPX`:
   `UPX!` в первых 4 КиБ файла), ищет `sing-box-<ver>-<platform>.upx.tar.gz` — релизный CI
   кладёт такие копии для linux-arm64 и linux-mipsle-softfloat, и роутер с маленьким overlay
   остаётся на сжатом ядре; копии нет (шаг UPX в CI необязательный) — строка
   `no UPX-packed copy in this release, falling back to the plain binary` и обычный архив. Сравнение версий: upstream semver, затем
   `lx.N`, затем `rc.M` (без rc новее, чем с rc). Равно → `already up to date`, выход 0.
   Доступная старше установленной → `ERROR: installed <v> is newer than <v'>` (hint про
   `--prerelease`), выход 1 — даунгрейда нет.
3. **Место.** `statfs` каталога бинаря: свободно ≥ размер текущего бинаря × 1.1; иначе
   `ERROR: need N KiB free beside <path>, have M`. Размер нового бинаря до скачивания
   неизвестен, поэтому та же проверка повторяется на шаге 4 по размеру из tar-заголовка записи
   `sing-box`, до записи первого байта: обычный бинарь вместо упакованного в 4–5 раз больше.
4. **Скачивание потоком.** `GET releases/download/v<ver>/<asset>` → `TeeReader` в sha256 →
   `gzip` → `tar`: единственная запись `sing-box` пишется в `<бинарь>.new` (`0755`, тот же
   каталог ⇒ та же ФС). Прогресс — в лог, не чаще раза в секунду (`progressInterval`):
   `update: downloading <asset>: 3.2 / 14.1 MiB (23%)`, итог из `Content-Length` (нет —
   только байты); чаще нет смысла — лог отдаётся хвостом, лаунчер опрашивает раз в секунду,
   а `\r` в файле не работает. Сумма сжатого потока сверяется с `SHA256SUMS` **после** записи; не
   сошлась — `.new` удалён, выход 1. Таймаут всего скачивания 10 мин, HTTP-клиент —
   стандартный Go (без зависимости от `wget`/`ca-bundle`-вариантов; корневые сертификаты
   системы, на OpenWrt — `ca-bundle`, который требует инсталлятор). Прокси — стандартные
   `HTTPS_PROXY`/`ALL_PROXY`/`NO_PROXY` из окружения (`http.ProxyFromEnvironment`): там, где
   GitHub недоступен, админ пишет `"update": "HTTPS_PROXY=socks5://127.0.0.1:2080 /usr/bin/sing-box
   lxd update"` через локальный inbound ядра; своего флага нет.
5. **Проверка до подмены.** `<бинарь>.new version` (запускается на этом CPU) и, если есть
   `<state_dir>/last_good.json`, `<бинарь>.new check -c last_good.json` (новая версия
   принимает текущий конфиг); файла нет (демон ещё ничего не применял) — строка
   `no applied config, skipping check`, не отказ. Падение → `.new` удалён, выход 1. Работающий демон всё это
   время не затронут.
6. **Подмена.** `link(бинарь, бинарь.old)`; `rename(бинарь.new, бинарь)`. Атомарно, без
   `ETXTBSY`; процесс демона живёт на старом inode.
7. **Перезапуск.** `procd` → `/etc/init.d/<service> restart`; `systemd` → `systemctl restart
   <service>`; init не распознан или `--no-restart` → `unlink(.old)`, печать «binary replaced,
   restart the service yourself», выход 0. **Сама команда restart завершилась с ошибкой**
   (юнит назван иначе, init-скрипта нет) — то же: бинарь исправен, откатывать нечего, `unlink(.old)`,
   выход 0 с текстом ошибки restart; откат — только в шаге 8, когда restart прошёл, а служба не
   держится. Здесь умирает демон, породивший команду (128 —
   detached, апдейтер жив).
8. **Здоровье и откат.** До 15 с ждём, что init считает службу работающей (`/etc/init.d/… running`
   / `systemctl is-active`), затем ещё 3 с проверяем, что она держится (respawn-цикл под procd
   виден как мигание). Не держится → `rename(.old, бинарь)`, повторный restart, `ERROR: <ver>
   did not come up, rolled back to <old>`, выход 2.
8b. **Ядро внутри демона.** «running» у init — это процесс демона, не ядро: демон, проигравший
   гонку за TUN (§2.6), стоит с управляющим каналом и без VPN. Поэтому после шага 8 апдейтер
   опрашивает `GET /admin/status` нового демона раз в секунду до 20 с (демон сам ретраит
   занятое устройство 10 с, запас — на медленный старт роутера). `started` → `core started`,
   `unlink(.old)`, `done: <ver> is running`, выход 0. `fatal` — окончательный ответ сразу
   (демон уже отретраил и сдался): `ERROR: <ver> is up but the core did not start:
   <last_error>, rolled back to <old>`, откат по правилам шага 8, выход 2; `idle` все 20 с —
   то же с текстом `still idle after 20s`. Пробы без ответа (демон недостижим, `401` на
   секрете) — **не вердикт**: init говорит, что процесс жив, а недостижимость админ-плоскости
   может быть нашей же конфигурацией; печатается `core status unknown (<ошибка>); the service
   is running, not rolling back`, выход 0. Пробы нет вовсе — строка `core status not checked:
   <почему>` и выход 0 по шагу 8: нет state-dir / `daemon.json`; `listen` не на loopback
   (демон слушает только LAN-адреса — операторский маршрут требует loopback-пира;
   `0.0.0.0`/`::` → `127.0.0.1`/`::1`); run-state записан как `stopped` (ядро остановлено
   оператором, `idle` штатно). Адрес, секрет и `tls` — из `daemon.json` state-dir'а, как у
   `lxd client`. Для этого `GET /admin/status` стал ещё и **операторским маршрутом**: без
   сертификата с loopback-пира — Bearer-секрет; с доверенным сертификатом или не с loopback
   — прежний пин (удалённый клиент без сертификата по-прежнему получает `401`).

### 2.3 `sing-box version` и `--help`

- `sing-box version` печатает секцию lxd — через один `// lx:`-хук в `cmd_version.go`
  (`versionExtraLx`), тело в lx-файле под `with_lxd`:
  ```
  Platform: linux-arm64          ← релизный ассет (127), под него качать ядро
  Init: procd                    ← init хоста (127)
  ```

  Без `with_lxd` секции нет; `Update:` — только на Linux, где команда работает; `Platform:`
  полезен и оператору, который качает руками.
- `sing-box lxd --help` и `sing-box lxd update --help`: подкоманда с флагами выше и абзац
  про `commands` в `daemon.json` (128) со ссылкой на `docs-lx/lxd-daemon.md`.

### 2.6 Гонка рестарта под procd (живой прогон 2026-10-12)

`/etc/init.d/sing-box-lxd restart` под procd запускает новый процесс раньше, чем старый
освободил TUN: ядро держит интерфейс, пока не закрыт старый fd, и `TUNSETIFF` нового ядра
получает `EBUSY` на несколько секунд раньше срока. На RouteRich (lx.15-test128 → lx.16):
12:59:47 старый процесс отпускает `lxd-tun0`, 12:59:50 новый демон уже пишет `boot from
last-good; staying up — … open tun: TUNSETIFF: device or resource busy`, 12:59:52 `lxd-tun0`
удалён; шаг 8 видел `running` у procd и честно вернул `done`, VPN лежал ~80 с до ручного
`restart`. Два исправления в ядре:

- **Ретрай старта на `EBUSY` (демон, `bootstrap`).** Окно старого демона — секунды, поэтому
  загрузка повторяет весь `StartOrReloadService` каждые 500 мс до 10 с, пока ошибка — «device
  busy» (`errors.Is(err, EBUSY)` по цепочке причин; текст `device or resource busy` —
  страховка для сплющенной ошибки). Упавший старт закрывает инстанс, между попытками ничего
  не течёт. Любая другая ошибка окончательна сразу — плохой конфиг от ожидания не улучшится.
  Только загрузка: REST-apply идёт при уже закрытом старом инстансе этого же процесса, ждать
  некого. Чинит и обычный `restart`, не только update. Первая попытка логируется `WARN lxd:
  boot: device busy (the previous instance is still shutting down?), retrying for up to 10s`.
- **Шаг 8b** (выше): апдейтер ждёт `started` у `/admin/status`, `fatal` → откат.

Живой прогон lx.17 → lx.18 (RouteRich, 2026-10-13) оба исправления прошёл до конца и
откатился: ядро держал не старый демон, а сам `update` — порождённый через `commands`
(128), он унаследовал копию fd `lxd-tun0` (sing-tun открывает TUN без `CLOEXEC`), и
интерфейс жил, пока `update` ждал в шаге 8b; ретрай демона на 10 с короче этого ожидания.
Остановка ядра изнутри `update` не помогла бы — копия fd уже у него. Исправление в 128 §2.3:
демон ставит `FD_CLOEXEC` перед порождением. Переход с lx.17/lx.18 на версию с фиксом через
кнопку невозможен (порождает старый демон): один раз `stop` → `update` → `start` из
лаунчера или `lxd update` по SSH.

Лаунчер со своей стороны после возвращения демона сверяет `CoreStatus` и при не-`started`
показывает «обновлено, но ядро не запустилось: <ошибка>» вместо зелёного `done`.

## 3. Критерии приёмки

- Табличные тесты чистых функций: разбор `SHA256SUMS` (строка своей платформы среди соседних,
  отсутствие, мусор); сравнение версий (`1.14.3-lx.15` < `1.14.3-lx.16`, `lx.16-rc.2` < `lx.16`,
  `1.14.3-lx.20` < `1.15.0-lx.1`); имя ассета → версия.
- Тест потоковой распаковки на синтетическом `.tar.gz` с несколькими записями: в `.new`
  попадает только `sing-box`, сумма сверяется после записи, несовпадение удаляет `.new`.
- Тест подмены/отката на temp-каталоге с фейковыми `exec` и init: `link`+`rename`, успех →
  `.old` удалён; «служба не поднялась» → исходный inode на месте, выход 2; «restart сам упал» →
  новый бинарь остаётся, выход 0; `--no-restart`; `--service` подставляется в команды init.
- Тест `--dry-run`: ничего не создано; тест «уже актуально» и «установленная новее».
- `sing-box version` с `with_lxd` содержит `Platform:`; без тега — не содержит
  (`cmd_schema_lx_test.go`-стиль).
- Ретрай `EBUSY`: два `EBUSY` подряд → третья попытка успешна, две паузы; сплющенный текст
  ретраится; другая ошибка — одна попытка без паузы; отказ паузы (shutdown) возвращает
  busy-ошибку; через `bootstrap` демон оказывается `running` после одного `EBUSY`.
- Шаг 8b: `idle, idle, started` → выход 0 и `core started`; `fatal` → выход 2, бинарь старый,
  текст с `last_error`; `idle` всё окно → выход 2 `still idle after 20s`; проба недостижима →
  выход 0 и `core status unknown`; пробы нет → `core status not checked: <почему>`.
  `loopbackAdminAddress`: `127.0.0.1`/`0.0.0.0`/`[::]`/`:port`/multi → loopback-адрес,
  только-LAN → пусто; `coreProbe` при run-state `stopped` — без пробы с причиной.
- `/admin/status` операторским маршрутом: loopback + секрет без сертификата → 200; неверный
  секрет → 401; удалённый пир без сертификата → 401 `client certificate not trusted` (пин).
- `go vet` на darwin/linux/windows; существующие тесты `lxd` зелёные.
- Живой прогон владельцем до тега: роутер на lx.N-1 → кнопка/`POST /admin/commands/update`
  → `GET` показывает `done: … is running`, `/admin/info.version` новая; повторный запуск →
  `already up to date`; `--dry-run` печатает ассет `linux-arm64`.

## 4. Потребитель (для справки, в объём ядра не входит)

Лаунчер: кнопка Update = `POST /admin/commands/update` (128); «Проверить обновления» =
`check-update` с `--dry-run`, строка «installed … available …» из лога. Коллекция рецептов
предлагает именно эти две строки `commands` для procd и systemd.
