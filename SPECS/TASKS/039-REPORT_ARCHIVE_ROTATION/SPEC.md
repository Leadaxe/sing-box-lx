# SPEC: 039 — REPORT_ARCHIVE_ROTATION

**Фича:** [HOTFIXES](../../FEATURES/004-HOTFIXES/FEATURE.md)

| Поле | Значение |
|------|----------|
| Тип | B (bug) — баг апстрима, чиним у себя |
| Статус | C (complete) |
| Ветка | `lx` |
| Связанные | [[SPECS/TASKS/020-MULTI_WG_IDLE_BUFFER_HEAT]] (OOM-репорты как инструмент разбора) |

Архивы отчётов апстрима — `files/oom_reports` и `files/crash_reports` — растут
**без ограничения**: каждое событие создаёт новую папку, старые не удаляются никогда.
Один повторяющийся сбой съедает диск пользователя пачками по ~750 КБ.

Замер на устройстве (OPPO CPH2411, 2026-07-27):

```
575 отчётов, 427 МБ в files/oom_reports    ← за 19 дней (2026-06-27 .. 07-15)
 10 отчётов, 2.4 МБ в files/crash_reports
```

Пик — 94 отчёта за один день (06 июля). Ни один не был удалён.

Фикс: перед записью нового отчёта архив подрезается до последних `N` папок и `M` МБ.
Отгружен в `v1.14.0-lx.17-rc.2`.

## 1. Причина

`WriteReport` (OOM) и `archiveCrashReport` (crash) устроены одинаково: создать каталог,
получить свободное имя через `nextAvailableReportPath`, записать. Шага удаления старого
нет ни в одном из двух путей.

Отчёт тяжёлый: OOM-снапшот несёт два pprof-профиля (`heap.pb`, `allocs.pb` — по ~580 КБ),
`goroutine.pb`, `block.pb`, `go.log` и копию конфига (~105 КБ). Отсюда цена роста: сотни
МБ за считанные недели при регулярном сбое.

Апстрим предоставляет экспорт отчётов наружу (`CreateZipArchive`, age-шифрование), но
удаление отдаёт на откуп клиенту, а клиент чистит только то, что выгрузил. Всё, что не
выгружено, лежит вечно.

## 2. Фикс

`pruneReports(dir, keepCount, keepBytes)` в `experimental/libbox/report.go` — общем файле
обоих путей, поэтому одна функция закрывает и OOM, и crash. Вызов вставлен **перед**
`nextAvailableReportPath` в оба места.

Лимиты (константы там же):

| Лимит | Значение | Смысл |
|---|---|---|
| `maxReportCount` | 32 | обычно срабатывает первым: 32 × ~750 КБ ≈ 24 МБ |
| `maxReportBytes` | 64 МБ | страховка от нескольких аномально жирных отчётов |

Действуют оба; удаление идёт, пока не выполнены сразу оба условия. Подрезка до
`keepCount-1`, чтобы после записи нового отчёта в архиве было ровно `keepCount`,
а не `keepCount+1` каждый раз.

### Порядок удаления — по mtime, НЕ по имени

Имена отчётов выглядят сортируемыми (`2006-01-02T15-04-05`), но при коллизии
`nextAvailableReportPath` добавляет суффикс `-1..-1000`, и лексикографический порядок
ломается: `…-05-2` сортируется **после** `…-05-10`. Сортировка по имени удаляла бы не те
папки. Поэтому порядок — по времени модификации; папки с нечитаемым mtime считаются
самыми старыми и удаляются первыми.

### Best-effort

Ротация работает на пути записи краша/OOM, то есть в уже деградировавшем процессе.
Любая ошибка (нечитаемый каталог, отказ удаления) — пропуск, а не возврат ошибки:
потерять один отчёт лучше, чем потерять тот отчёт, ради которого всё писалось.
Отсутствующий каталог — no-op: подрезка вызывается и до первой записи.

Файлы, не являющиеся каталогами, не трогаются и в бюджет не считаются — в каталоге
отчётов может лежать посторонний файл.

## 3. Зона касания upstream

Все три файла — **чистый upstream** (`98b2ecd7`, `4bccd6fa`, `53e87a7e`; наших коммитов
в них не было). Поэтому вставки помечены `// lx:begin report-rotation` / `// lx:end`:

| Файл | Вставка |
|---|---|
| `experimental/libbox/report.go` | `pruneReports` + `reportDirSize` + константы лимитов |
| `experimental/libbox/oom_report.go` | одна строка вызова в `WriteReport` |
| `experimental/libbox/log.go` | одна строка вызова в `archiveCrashReport` |

Логика записи отчёта, формат, имена и экспорт наружу не изменены — добавлено только
удаление старого.

**Условие снятия:** апстрим введёт свою ротацию архивов отчётов (любой из двух). Тогда
наш вызов и функция удаляются, лимиты берутся апстримные. До тех пор фикс держим —
см. реестр в [HOTFIXES](../../FEATURES/004-HOTFIXES/FEATURE.md).

## 4. Критерии приёмки

- [x] Ротация вызывается на обоих путях — OOM и crash.
- [x] Оба лимита независимы: превышение любого удаляет старые отчёты.
- [x] Порядок удаления — по mtime; регрессионный тест ловит сортировку по имени
      на суффиксных именах (`…-05-2` новее `…-05-10`).
- [x] Посторонние файлы в каталоге не удаляются и не учитываются в бюджете.
- [x] Отсутствующий каталог — no-op, каталог не создаётся.
- [x] `go build ./...` и `-tags with_lx_command`, `gofmt -l` — зелёные.
- [ ] Полевая проверка: после выпуска убедиться, что архив на устройстве держится
      в пределах лимита (сейчас там 575 отчётов, накопленных до фикса).

## 5. Остаток

**Накопленные 427 МБ фикс не удаляет сам** — подрезка срабатывает только при записи
следующего отчёта, а OOM-события на устройстве прекратились 15 июля. Существующий архив
либо уберётся при первом же новом отчёте, либо его нужно вычистить вручную/из клиента.
