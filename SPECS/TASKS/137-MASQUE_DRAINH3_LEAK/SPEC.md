## 1. Симптом

Демон `lxd` на роутере через несколько дней работы съедает оба ядра при нулевом
трафике; весь сегмент за TUN'ом (игры, звонки) получает джиттер. Снятие узлов из
конфига и рестарт ядра кнопкой лаунчера не помогают: каждое такое действие — ещё
один apply внутри того же процесса. Освобождает только рестарт процесса.

Снято через `/admin/memory`, `/admin/pprof/heap`, `/admin/pprof/goroutine` (SPEC 068):

| Показатель | До рестарта процесса | После (тот же конфиг, 2 мин) |
|---|---|---|
| `heap_inuse_bytes` | 227 МБ при `GOMEMLIMIT=200MiB`, idle 16 КБ | 108 МБ, idle 56 МБ |
| `num_gc` | 1 964 328 за 6,2 дня (≈ 3,7/с) | 29 |
| `gc_pause_total_ns` | 1056 с | 11 мс |
| CPU по ядрам | 98 % / 95 % | 7,9 % / 5,1 % |

Куча стоит у мягкого лимита, сборщик работает непрерывно на своём потолке 50 %
CPU — это и есть «одно ядро постоянно». Верхушка `inuse_space` (190,6 МБ):

```
39.31MB  sing-tun.newTCPGROTable
32.69MB  sing-tun.newUDPGROTable
27.13MB  wireguard-go/device.(*Device).PopulatePools.func3
 8.16MB  sing-tun.(*ForwardDispatcher).insertEntry
 7.35MB  sing-tun.(*TCPNat).Lookup
```

Один `NativeTun` выделяет одну TCP- и одну UDP-таблицу GRO (≈ 1 МБ и ≈ 0,8 МБ) —
в куче около сорока TUN'ов, а живой `BatchRead`-цикл один. Остальные — закрытые
TUN'ы предыдущих Box'ов. Самая большая группа горутин:

```
61 @ … masque.(*Outbound).connect.func2.1  protocol/masque/outbound.go:661   (outcome := <-h3Done)
```

Ни одного кадра `connectH3` в дампе нет: ноги, которые эти горутины «дренируют»,
давно вернулись.

## 2. Причина

`connect()` в `auto` запускает h3-ногу отвязанно (SPEC 074) и забирает её
единственный результат из `h3Done` (буфер 1) в первом `select`. Если нога
отказала до таймера фолбэка, `h3Returned = true`, и управление уходит на h2.
Ветка победы h2 безусловно вызывала `drainH3()`:

```go
h2Closer, h2Conn, h2Err = connectH2(ctx)
if h2Err == nil {
    drainH3()             // результат уже забран выше — горутина ждёт пустой канал вечно
```

Замыкание дренажа держит `o`; `o.ctx` — контекст Box'а, через него реестр
сервисов: inbound-менеджер → TUN (GRO-таблицы sing-tun), менеджер endpoint'ов →
WG-устройства с приёмными пулами, роутер → NAT-таблицы и rule-set'ы. `Box.Close()`
эту горутину не трогает — она не слушает ни контекст, ни сигнал закрытия, — и
после каждой пересборки внутри процесса (lxd apply, Stop/Start из лаунчера,
смена профиля в libbox) старый Box остаётся достижимым для GC.

Частота: к WARP примерно четверть подъёмов h3 падает сразу с
`PROTOCOL_VIOLATION` (SPEC 121), а истечение окна h2 снова пробует h3 — утечка
набегает и внутри одного Box (горутина на подъём), и между Box'ами (мёртвый Box
на apply). Зависание роутера 25.09 с пиком кучи 326 МБ, после которого был
выставлен `GOMEMLIMIT`, — вероятно, оно же.

Код с `6105c7a5b` (SPEC 074); затронуты `v1.14.0-lx.27` и позже.

## 3. Исправление

`drainH3()` вызывается только когда нога ещё не отвечала (`!h3Returned`). Две
другие точки вызова — ветки `ctx.Done()` — стоят до потребления результата и
корректны. Блок помечен `// lx: SPEC 137`; остальная логика `auto` (таймер,
память режима, ожидание поздней ноги при отказе h2) не меняется.

## 4. Проверка

- `TestAutoFastH3FailureThenH2LeavesNoGoroutine` (`auto_vhttp_lx_test.go`): h3
  отказывает мгновенно, h2 поднимается; после возврата `connect` число горутин с
  кадром `masque.(*Outbound).connect.func` возвращается к исходному в пределах 2 с.
  До правки: `FAIL … 1 goroutine(s) of connect() still parked`; после — `ok`,
  `-race` зелёный.
- Сборка под `LX_TAGS` проходит.
- Полевая проверка после выката: на роутере после серии apply `heap_inuse` не
  растёт ступенями по 40–70 МБ, в `/admin/pprof/goroutine` нет группы
  `connect.func2.1`. На момент записи не прогнано.

Тест на «закрытый Box собирается GC после apply» не писался: он требует живого
Box с TUN'ом. Если после выката куча продолжит расти — искать вторую цепочку
удержания тем же способом (§1), а не возвращаться к masque.

## 5. Границы

- `GOMEMLIMIT` в инсталляторе OpenWrt (RAM/3) и `GOGC=50` не трогаются: лимит
  был правильным, упиралась в него утечка.
- Базовая куча свежего процесса с полным конфигом владельца ≈ 110 МБ, из них
  75 МБ — приёмные пулы четырёх WG-устройств (два WireGuard, Tailscale, masque),
  по ≈ 19 МБ на устройство. Это штатный размер (SPEC 020; усыпление
  `with_lx_idle_suspend` — только мобильные сборки), не часть этого дефекта.
- DTLS-ретраи openconnect и userspace-стек Tailscale, с которых началось
  расследование, в верхушку кучи не входят и к симптому отношения не имеют.

## 6. Как увидеть в следующий раз

Через лаунчер (`POST /remote/machines/{id}/raw/rest`) или по SSH на loopback:

- `GET /admin/memory` — `heap_inuse_bytes` у лимита при `heap_idle_bytes ≈ 0`
  и `num_gc`, растущий на единицы в секунду, = GC-спираль;
- `GET /admin/pprof/goroutine?debug=1` — группа с `connect.func` и счётчиком в
  десятки = эта утечка; группа другого кадра = другая цепочка;
- `GET /admin/pprof/heap` → `go tool pprof -top -sample_index=inuse_space`:
  GRO-таблицы sing-tun кратно больше 2 МБ при одном живом TUN = в куче мёртвые
  Box'ы, независимо от того, кто их держит.
