**Touches:** только пакет `lxd/` — новые файлы `clientinfo.go` (сборка карты,
кеш, метки), `clientinfo_linux.go` + `clientinfo_stub.go` (платформенные

Единственное заимствование из ядра — вызов **`route.ReloadLeaseFiles`**
([route/neighbor_resolver_lease.go:39](../../../route/neighbor_resolver_lease.go))
как библиотечной функции. **Ядро не правится**: ни `route/`, ни `adapter/`,
ни proto, ни `InboundContext`.

## Why

Инспектор соединений показывает `Client: 192.168.20.238:50558`. Для одного
устройства это читается, для домашней сети из пятнадцати — нет: чтобы понять,
кто именно качает 4.9 МБ с `81.27.242.141`, оператор держит карту адресов в
голове или лезет в веб-морду роутера.

`processInfo` тут не работает по построению: он ищет процесс в **локальной**
таблице сокетов, а соединение Wi-Fi-клиента открыл чужой хост — процесса на
машине с ядром нет. Для трафика из сети нужен другой источник имени.

Демон крутится **на самом роутере** (решение владельца), а роутер — та сторона,
которая имена и раздаёт: DHCP-сервер знает `IP → MAC → hostname` (устройство
представилось в DHCP option 12), а hostapd знает, через какой SSID клиент
подключён. Обе таблицы лежат на том же хосте. Остаётся отдать их наружу.

## Design

### Граница: обвязка, а не ядро

Ядро не трогается вовсе — решение владельца. Технически можно было бы вывести
в proto уже посчитанные `SourceMACAddress`/`SourceHostname`
([route.go:537-553](../../../route/route.go)) и научить neighbor-резолвер не
выбрасывать ifindex, но это правки в апстримных файлах горячего пути, ради
данных, которые справочник отдаёт снаружи.

Цена решения — **у клиента со статическим IP не будет `name`**: DHCP-имя берётся
из лизов, а его там нет. Всё остальное достаётся снаружи: `mac` и `iface` — из
`/proc/net/arp`, `port` — из `bridge fdb`, `ssid` — из ubus. То есть такой
клиент опознаётся по MAC и сегменту, а человеческое имя ему даёт ручная метка
оператора.

### Эндпоинт

```
GET /admin/clients-info
```

```json
{
  "clients": {
    "192.168.20.238": {
      "name": "iPhone-Vasya",
      "mac": "be:ab:bd:ec:70:40",
      "ssid": "LexVPN2G",
      "iface": "phy0-ap1",
      "port": "",
      "source": "lease+arp+wireless"
    },
    "192.168.20.51": {
      "name": "NAS", "mac": "dc:a6:32:de:ad:be", "ssid": "",
      "iface": "br-lan", "port": "lan2",
      "source": "lease+arp+bridge"
    },
    "192.168.20.77": {
      "name": "Телевизор", "mac": "", "ssid": "", "iface": "", "port": "",
      "source": "label"
    }
  },
  "sources": ["/tmp/dhcp.leases", "arp", "bridge", "ubus"],
  "updated_unix": 1755087234
}
```

**Справочник, а не поле в событии.** Имя не летит в каждом соединении: это
горячий путь, а имя меняется раз в часы. UI тянет карту раз в минуту, кеширует
и подставляет сам по `source`-адресу соединения. `SubscribeConnections` не
трогается.

**Поля.** `name` и `mac` — от кого и чьё устройство. `iface` — интерфейс
подключения (`phy0-ap1` у Wi-Fi, `br-lan` у проводного): для роутера с
VLAN/гостевой сетью это ответ на «из какого сегмента пришёл». `ssid` — только
для Wi-Fi. `port` — физический порт моста (`lan2`) для проводного клиента:
`iface` говорит «в каком сегменте», `port` — «в какую розетку воткнут».

**`source` — обязательное поле.** Оператор должен видеть, какой источник
сработал: когда устройство «переименовалось» или потеряло имя, вопрос всегда
один. Пример: клиент был `iPhone-Vasya` из лизов, лиз истёк — с
`source: "label"` видно, что осталась только ручная метка, а DHCP-запись
протухла. Плюс это подсказка, что чинить: пусто `ssid` при `source: "lease"` —
значит ubus не ответил либо интерфейс не Wi-Fi.

**Пустое поле — валидное состояние, а не ошибка.** Пустая строка = «этот
источник о клиенте ничего не сказал».

### Провайдеры: контракт один, реализации платформенные

Форма ответа платформо-независима; меняется только то, чем поля заполнены.

| Провайдер | Платформа | Даёт | Механизм |
|---|---|---|---|
| lease | любая | `name`, `mac` | `route.ReloadLeaseFiles` — готовая функция |
| arp | linux | `mac`, `iface` (мост) | чтение `/proc/net/arp` |
| bridge | linux | `port` (физический порт) | `bridge fdb show`, внешний процесс |
| wireless | linux (OpenWrt) | `ssid`, `iface` (AP) | `ubus call`, внешний процесс |
| label | любая | `name` | файл в state-dir |

Порядок вызова = приоритет: `lease` → `arp` → `bridge` → `wireless` → `label`.
`wireless` идёт после `arp` намеренно: для Wi-Fi-клиента ARP даёт мост
(`br-lan`), а ubus уточняет до конкретного AP-интерфейса (`phy0-ap1`) — более
точный источник перезаписывает менее точный.

Конфликт `mac` между лизом и ARP разрешается в пользу ARP: лиз мог не истечь
после того, как устройство сменило MAC, а таблица соседей отражает того, кто
отвечает на этот IP сейчас. На рандомизированных MAC случай не гипотетический.

**Оформление — тот же паттерн, что уже принят в `lxd/`**: одноимённые
package-private функции + build-теги, **без интерфейса** (интерфейсы в этом
пакете заведены под тестируемость — `reloader`, `statsSource`, — а не под
платформу). То есть буквально как `currentRSS()` / `peakRSS()` из SPEC 065:

```go
// clientinfo_linux.go   //go:build with_lxd && linux
func enrichARP(clients map[string]*clientEntry) bool
func enrichBridge(clients map[string]*clientEntry) bool
func enrichWireless(clients map[string]*clientEntry) bool

// clientinfo_stub.go    //go:build with_lxd && !linux
func enrichARP(_ map[string]*clientEntry) bool      { return false }
func enrichBridge(_ map[string]*clientEntry) bool   { return false }
func enrichWireless(_ map[string]*clientEntry) bool { return false }
```

Возврат `bool` = «источник отработал» — попадает в `sources` ответа. Стаб
возвращает `false` молча: вне Linux этих таблиц нет, и это состояние, а не сбой
(тот же принцип, что `rssUnsupported`, — «значения нет», а не «платформа не
та»). `false` возвращает и Linux-реализация, когда источник недоступен на этом
хосте (нет `/proc/net/arp`, нет бинаря `bridge`/`ubus`) — одна ветка у клиента
покрывает оба случая, ровно как у `currentRSS()`.

Слияние — по образцу `ReloadLeaseFiles`: карта передаётся провайдерам как
**аккумулятор**, каждый дописывает свои поля, отсутствующий источник молча
пропускается. Приоритет задан порядком вызова, метки идут последними и
перекрывают всё.

### ARP-провайдер: `/proc/net/arp`

Тот же класс операции, что чтение лизов — файл, не процесс:

```
IP address     HW type  Flags  HW address         Mask  Device
192.168.20.51  0x1      0x2    dc:a6:32:de:ad:be  *     br-lan
```

Даёт `IP → MAC + iface`. Колонка `Device` — мост (`br-lan`), а не физический
порт; для «из какого сегмента пришёл» этого достаточно, порт уточняет
bridge-провайдер.

**Побочно чинит дыру со статическими IP.** Клиент, которого нет в лизах, здесь
появится: получит `mac` и `iface`, а `mac` — это ключ к метке оператора. То
есть устройство со статикой перестаёт быть голым адресом, хотя `name` из DHCP
у него по-прежнему нет.

Ограничение честное: ARP-запись живёт, пока идёт трафик, и только для соседей в
одном L2-сегменте. Устройство молчит несколько минут — запись протухает, и
клиент выпадает из этого источника (оставаясь в lease/label).

Фильтруем по `Flags`: `0x0` — неполная запись (ARP-запрос без ответа), MAC там
`00:00:00:00:00:00`. В карту такие не идут.

### Bridge-провайдер: `bridge fdb show`

Уточняет `MAC → физический порт` для проводных клиентов:

```
dc:a6:32:de:ad:be dev lan2 master br-lan
```

Внешний процесс, та же дисциплина, что у ubus (см. ниже): `LookPath`, таймаут,
отсутствие бинаря = провайдер вернул `false`, а не ошибку.

Записи с флагами `permanent`/`self` пропускаем — это адреса самого моста, не
клиентов. Порт пишется в отдельное поле `port`, а `iface` от ARP не
перезаписывается: это разные уровни (сегмент vs розетка), и оба полезны.

Для Wi-Fi-клиента fdb покажет AP-интерфейс (`phy0-ap1`) — то же, что даст
ubus, но менее информативно, поэтому `wireless` идёт последним и уточняет.

### Wireless-провайдер: ubus

Полевой замер владельца на живом роутере (10 запусков уложились в интервал
меньше разрешения таймера busybox) снял вопрос стоимости: на частоте раз в
минуту накладные расходы неизмеримы. Из трёх опробованных источников выбран
**ubus**, и не по скорости, а по составу данных:

```
ubus list                          → перечень объектов hostapd.*  (интерфейсы не хардкодим)
ubus call hostapd.phy0-ap1 get_status  → {"ssid": "LexVPN2G"}
ubus call hostapd.phy0-ap1 get_clients → {"clients": {"be:ab:bd:ec:70:40": {...}}}
```

Два вызова на интерфейс дают готовую связку `MAC → {ssid, iface}`;
`iw station dump` не нужен. Отвергнуты: `iwinfo` (даёт только SSID, за
клиентами всё равно идти в другое место, и это разбор текста вместо JSON) и
UCI `/etc/config/wireless` (секция называется `wireless.vpn_2g`, а интерфейс —
`phy0-ap1`; связь возникает при старте hostapd и в файле её нет, плюс UCI
показывает желаемое, а не поднятое).

**Через `ubus call`, а не через сокет напрямую.** Бинарный ubus-протокол
потребовал бы своей реализации или новой зависимости ради двух вызовов раз в
минуту. `ubus call` отдаёт JSON — разбирается штатным `encoding/json`. Демон
уже умеет `exec` тем же паттерном: валидация конфига идёт через
`exec.CommandContext` с таймаутом ([lxd/apply.go:44-73](../../../lxd/apply.go)).
Если однажды упрёмся в производительность или отсутствие бинаря — замена
источника локальна, формат ответа не изменится.

Дисциплина вызова — по образцу `execSelfCheck`: `exec.CommandContext` с
таймаутом (2 с на вызов), отсутствие бинаря через `exec.LookPath` (нет `ubus` —
провайдер возвращает `false`, не ошибку), разбор ошибки `CombinedOutput` +
`strings.TrimSpace`.

### Метки оператора

Файл `<state_dir>/client-labels.json`:

```json
{"192.168.20.77": "Телевизор", "be:ab:bd:ec:70:40": "Рабочий ноут"}
```

Ключ — IP **или** MAC. MAC устойчивее: устройство переедет на другой адрес и
метка переедет с ним; при совпадении обоих выигрывает MAC.

⚠️ **Оговорка про MAC-рандомизацию.** iOS и Android по умолчанию подставляют
приватный MAC на каждую сеть и меняют его при перезабытии/перепривязке — на
стенде владельца все клиенты именно такие (`be:ab:…`, `6a:b8:…`, `ae:c4:…`).
Метка по MAC для таких устройств отвяжется ровно тогда, когда оператор этого
не ждёт. Для них надёжнее метка по IP при фиксированной DHCP-резервации.

```
PUT    /admin/clients-info/labels/{key}   тело = {"name": "..."}
DELETE /admin/clients-info/labels/{key}
```

Запись атомарна (tmp + fsync + rename, как `resourceStore.writeAtomic`).
Ключ обязан парситься как IP или MAC, иначе 400 — в путь файла он не попадает
никогда, но мусорные ключи засоряют карту.

### Пути лизов и кеш

Дефолт — тот же список, что у апстрима (`defaultLeaseFiles`,
[route/neighbor_resolver_linux.go:23](../../../route/neighbor_resolver_linux.go)):
`/tmp/dhcp.leases` (OpenWrt, первым), `/var/lib/dhcp/dhcpd.leases`,
`/var/lib/dhcpd/dhcpd.leases`, `/var/lib/kea/kea-leases4.csv`,
`/var/lib/kea/kea-leases6.csv`. Берутся существующие и непустые. Формат
определяется по имени файла внутри `parseLeaseFile`; неизвестный суффикс —
dnsmasq/odhcpd.

Переопределение — в `daemon.json`, рядом с `log_max_size_mb` (единственный
источник настроек демона, флагов у команды нет по построению):

```json
{"dhcp_lease_files": ["/etc/custom/leases"]}
```

**Кеш 60 секунд.** Лизы читаются с диска, ubus запускает процесс — обе операции
дешёвые, но не бесплатные, а клиент может опрашивать часто. Тот же приём, что
у `/admin/memory` в SPEC 065, только TTL длиннее: данные меняются раз в часы.
`fswatch` не заводим — карта строится по запросу, а не держится постоянно.

## Out of scope

- **Правки ядра** — вывод `SourceMACAddress`/`SourceHostname` в proto,
  сохранение ifindex в neighbor-резолвере, `IP_PKTINFO` на listener'е. Решение
  владельца: всё на уровне внешней обвязки.
- **neighbor-резолвер ядра** как источник — потребовал бы правок
  `route/neighbor_resolver_*`. Его практическая польза (MAC для статических IP)
  закрыта ARP-провайдером, читающим ту же таблицу из `/proc/net/arp` снаружи.
- **Вендор по OUI** — таблица весит мегабайты и требует обновления; MAC
  отдаётся сырым, резолв вендора остаётся клиенту.
- **mDNS / reverse DNS** — второй сетевой опрос со своими таймаутами ради
  случая, который на роутере закрыт лизами.
- **Сигнал/RSSI из `get_clients`** — живёт секундами, а карта кешируется на
  минуту: цифра будет несвежей и вводящей в заблуждение. Для «кто откуда
  пришёл» не нужен.
- **Накопительный учёт трафика по клиенту** — отдельная задача: нужны
  счётчики, переживающие закрытие соединений, и решение о хранении/обнулении.
  Здесь только идентификация.
- **Windows** — стаб (`ssid`/`iface` пусты). lxd на Windows и так заглушка:
  служба не реализована, ротация лога тоже.

## Acceptance

- [x] `GET /admin/clients-info` на OpenWrt с непустым `/tmp/dhcp.leases`
  возвращает записи с `name`, `mac`, `source: "lease"`; имена совпадают с
  `cat /tmp/dhcp.leases`.
- [x] Wi-Fi-клиент получает `ssid` и `iface: "phy0-ap1"`; SSID совпадает с
  `ubus call hostapd.<iface> get_status`. Приоритет соблюдён: `iface` от ubus
  перезаписал мост, который дал ARP.
- [x] ARP-провайдер: клиент, активно ходящий в сеть, получает `mac` и `iface`;
  значения совпадают со строкой из `cat /proc/net/arp`. Записи с `Flags 0x0`
  (неполные, MAC `00:00:00:00:00:00`) в карту не попадают.
- [x] Клиента нет в лизах (статический IP) → `name` пуст, но `mac`/`iface` из
  ARP заполнены; ручная метка по этому MAC даёт ему имя.
- [ ] Bridge-провайдер: проводной клиент получает `port` (`lan2`), совпадающий
  с `bridge fdb show`; записи `permanent`/`self` (адреса самого моста)
  отфильтрованы. **Полевая проверка невозможна на стенде владельца — проводных
  клиентов нет; закрывается юнит-тестом на подставном выводе.**
- [ ] Проводной клиент: `ssid` пуст, остальные поля заполнены — пустое поле не
  ломает ответ и не мешает другим источникам. **Там же: без полевой проверки.**
- [x] Нет `ubus`/`bridge` в системе (`LookPath` не нашёл) → ручка отвечает 200
  с тем, что дали остальные источники; отсутствующий не значится в `sources`;
  в лог не сыплется ошибка.
- [x] Нет файлов лизов → пустой `clients`, пустой `sources`, статус **200**
  (не 404, не 500) — демон может стоять и не на роутере.
- [x] Ручная метка перекрывает имя из лиза; метка по MAC переживает смену IP
  устройством; при совпадении IP- и MAC-метки выигрывает MAC.
- [x] `PUT`/`DELETE` меток пишут атомарно; мусорный ключ (не IP и не MAC) →
  400, файл не тронут.
- [x] Повторный запрос внутри 60 с не перечитывает файлы и не запускает `ubus`
  (кеш) — проверяется через тестовый seam, а не по времени.
- [x] Истёкшие лизы в карту не попадают (тест на подставном файле с прошедшим
  `expiry` — отрабатывает апстримный парсер).
- [x] Маршруты за mTLS-пином (без сертификата → 401) и **не** на операторском
  loopback-only пути — как вся плоскость наблюдаемости.
- [x] Ядро не поднято (`idle`/`fatal`) → ручка продолжает отвечать: она не
  зависит от инстанса вовсе.
- [x] Сборка без тега `with_lxd` и на не-Linux (стабы `enrichARP`,
  `enrichBridge`, `enrichWireless`) не ломается; `gofmt` чист; юниты зелёные.
- [x] Полевая проверка на живом OpenWrt-роутере с реальными Wi-Fi-клиентами.
