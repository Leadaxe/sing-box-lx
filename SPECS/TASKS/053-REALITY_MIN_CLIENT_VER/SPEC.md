# SPEC: 053 — REALITY_MIN_CLIENT_VER

**Фича:** [HOTFIXES](../../FEATURES/004-HOTFIXES/FEATURE.md)

| Поле | Значение |
|------|----------|
| Тип | B (bug) — протухшая константа апстрима, жива в upstream на момент фикса |
| Статус | I (in progress) — фикс в дереве, собран; полевой прогон против живого Xray ≥ v26.7.11 не делался |

Xray-сервер начиная с v26.7.11 по умолчанию требует клиента версии ≥ 26.3.27.
Апстримный sing-box объявляет в REALITY-рукопожатии зашитую с 2023 года версию
`1.8.1` и потому **тихо** отбрасывается — без ошибки, подменой на камуфляжный сайт.
Фикс — объявлять ровно требуемый минимум `26.3.27`.

Build-tag: нет (правка безусловна, внутри `with_utls`). Scope: **client-only**.

---

## 1. Проблема

REALITY передаёт версию клиента в первых трёх байтах `SessionId` ClientHello.
Апстримный sing-box пишет туда константу:

```go
hello.SessionId[0] = 1
hello.SessionId[1] = 8
hello.SessionId[2] = 1
```

Это версия sing-box 1.8.1, зашитая в [common/tls/reality_client.go](../../../common/tls/reality_client.go)
коммитом `fe053e26b` (декабрь 2023) и с тех пор не обновлявшаяся: файл целиком
апстримный, ни одной lx-правки в его истории нет.

### 1.1 Что изменилось на стороне Xray

Коммит `af7eb68` (RPRX, 2026-07-11) в `infra/conf/transport_security.go` добавил
дефолт для незаданного `minClientVer`:

```go
} else {
    config.MinClientVer = []byte{26, 3, 27} // change it at your own risk: ...
}
```

Первый релиз с этим дефолтом — **v26.7.11** (v26.6.27 его ещё не несёт).
Порог `26.3.27` — это последняя невыпущенная-как-prerelease версия Xray, то есть
операторы обновлённых серверов получают отсечку **без явного действия с их стороны**.

До коммита незаданный `minClientVer` оставлял `config.MinClientVer == nil`, и первая
же клауза сравнения делала проверку вакуумно-истинной — то есть проверки не было вовсе.

### 1.2 Механика сравнения

Проверка в `XTLS/REALITY/tls.go` (функция `Server()`) — не побайтовая: три байта
пакуются в одно целое хелпером `Value()` (`26<<16|3<<8|27` = 1704731) и сравниваются
целиком:

```go
if (config.MinClientVer == nil || Value(hs.c.ClientVer[:]...) >= Value(config.MinClientVer...)) &&
    (config.MaxClientVer == nil || Value(hs.c.ClientVer[:]...) <= Value(config.MaxClientVer...)) &&
    (config.MaxTimeDiff == 0 || time.Since(hs.c.ClientTime).Abs() <= config.MaxTimeDiff) &&
    (config.ShortIds[hs.c.ClientShortId]) {
    hs.c.conn = conn
}
```

Два следствия, важных для нас:

- сравнение **`>=`**, а не строгое `>`: клиент, объявляющий ровно `26.3.27`,
  проходит. Объявлять больше требуемого незачем;
- наш `1.8.1` = 67585 против порога 1704731 — мимо с огромным запасом.

### 1.3 Почему симптом выглядит не как отказ

Версия — одно из четырёх AND-условий, и единственный их эффект это присваивание
`hs.c.conn = conn`. При провале любого условия сервер не закрывает соединение,
а прозрачно проксирует его на `config.Dest` — настоящий камуфляжный сайт с его
настоящим сертификатом. Это сделано намеренно, чтобы пробер не мог отличить
REALITY-сервер по форме отказа.

Отсюда форма жалобы: рукопожатие «удаётся», ошибки нет, но трафик уходит
на чужой сайт. На клиенте это видно только как `uConn.Verified == false`
(в терминах апстрима — «received real certificate (potential MITM or redirection)»),
и неотличимо от неверного shortId, разъехавшихся часов или чужого публичного ключа.

### 1.4 Зона поражения

Все REALITY-клиенты форка без исключения: `SessionId[0..2]` пишется в одном
месте (`common/tls/reality_client.go`), общем для всех протоколов поверх REALITY
(VLESS, trojan, vmess, XHTTP-поверх-REALITY). Внешнее условие — сервер Xray
≥ v26.7.11 с незаданным `minClientVer`. Затронуты все клиенты экосистемы
одинаково: mihomo закрыл это той же правкой (`wiktorbgu/mihomo-mikrotik@d8231b3`,
sed по трём тем же строкам).

## 2. Доказательство

- Line-cited контракт сервера: `XTLS/REALITY/tls.go` (`Value()` + четвёрка условий),
  `Xray-core/infra/conf/transport_security.go` (дефолт из `af7eb68`).
- Дефолт присутствует в теге `v26.7.11` и отсутствует в предыдущем `v26.6.27`.
- Наш объявляемый `1.8.1` — прямым чтением файла; история файла подтверждает,
  что константа апстримная и не обновлялась с 2023.
- Полевого прогона против живого обновлённого сервера **нет** — стенда с Xray
  ≥ v26.7.11 у форка нет. Это остаток задачи.

## 3. Требования

- REALITY-клиент объявляет версию `26, 3, 27` — ровно порог, не выше.
- Правка безусловная: отдельной ручки в конфиг не вводим (см. Границы).
- Совместимость со старыми серверами сохраняется: они либо не сверяют версию
  вовсе (`minClientVer` не задан → nil), либо сверяют с порогом ниже нашего.
- Минимальный дифф: три константы + маркер `// lx:` с причиной и ссылкой на
  апстрим-коммит, чтобы правка не потерялась на мерже.

## 4. Критерии приёмки

- Сборка `go build -tags with_utls ./common/tls/` зелёная.
- `grep` по `SessionId\[0\]` даёт ровно одно место — правка не разъехалась по дереву.
- Field: VLESS+REALITY-узел на сервере Xray ≥ v26.7.11 с незаданным `minClientVer`
  ходит (до фикса — подмена на dest-сайт). **Не выполнено**, нужен стенд.

## 5. Границы

- Серверная сторона REALITY (`common/tls/reality_server.go`) вне scope: форк
  client-focused, отсечка живёт на сервере и его настройками не управляем.
- Ручку в конфиг (объявляемая версия) не вводим: значение диктуется чужим
  порогом, а не пользовательским выбором, и осмысленных альтернатив у него нет.
- Реальную версию форка сюда не подставляем: поле сравнивается с чужим порогом
  как число, а не идентифицирует наш билд. Совпадение с версией Xray — свойство
  протокола, а не подделка identity.
- Обратной проверки (клиент → версия сервера) в REALITY не существует: полей
  `ServerVer`/`MinServerVer` в `XTLS/REALITY` нет, объявленный `26.3.27` ничего
  не ломает встречно.

## 6. Условие снятия

Апстрим sing-box сам поднимет константу в `common/tls/reality_client.go`
(или начнёт брать её из версии билда) — тогда наш патч снимается.

**Проверять на каждом мерже апстрима**: файл апстримный и активно трогается
(`kTLS`, `ECH`, `TLS spoof` — все от 世界), поэтому конфликт вероятен, а тихий
откат правки встречным изменением — тем более. Дополнительный риск: порог на
стороне Xray может подняться ещё раз, и тогда потребуется новый бамп трёх байт —
автоматически это не отслеживается, сигналом будут жалобы вида «REALITY-узел
не ходит, ошибки нет».
