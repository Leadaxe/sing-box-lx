# SPEC 159 — замена набора правил, на который ссылается конфиг

**Фича:** [014-LXD_DAEMON](../../FEATURES/014-LXD_DAEMON/FEATURE.md)

| Поле | Значение |
|------|----------|
| Тип | B (bug) — гуард B2 из [SPEC 063](../063-LXD_RESOURCE_STORE/SPEC.md) не давал обновить набор правил на машине, пока её конфиг на него ссылается |
| Статус | I (implemented) — код, юниты и живой прогон на macOS 2026-11-23; на Linux/OpenWrt не проверено |
| Источник | Роутер владельца, демон 1.14.4-lx.35, 2026-11-23: лаунчер (его SPEC 185) при Deploy заливает обновлённые `.srs`, демон отвечает 409. Решения владельца 2026-11-23: чинить в демоне; проверка + замена; прежнюю копию держать, пока новая не запустится хоть раз; занятым не-наборам оставить 409 |
| Build-tag | `with_lxd` |

## 1. Проблема

`PUT /admin/resources/{name}` отбивался 409, если `/resources/<name>` встречается в активном
конфиге или в last-good. Остановка ядра не помогает: last-good на диске продолжает ссылаться
на файл. Обновлённый набор правил не доезжал до машины никогда.

Гуард берёг одно: конфиг, на который демон может откатиться, должен подняться. Новый набор
под прежним именем этому не мешает, пока ядро способно его загрузить.

## 2. Решение

### 2.1. Ответы `PUT` для занятого имени

| Имя | Что произошло | Ответ |
|---|---|---|
| `.srs` / `.json` | байты те же, что на диске | **200**, ничего не меняется |
| `.srs` / `.json` | не загружается ядром (проверка до подмены) | **422**, файл прежний |
| `.srs` / `.json` | работающее ядро перечитало новый набор | **200**, `"replace": "confirmed"` |
| `.srs` / `.json` | работающее ядро не приняло набор за 10 с | **422**, файл возвращён прежний |
| `.srs` / `.json` | подтвердить некому | **200**, `"replace": "pending"` |
| другое расширение | — | **409**, как в SPEC 063 |

`DELETE` занятого имени — 409, как раньше. Свободное имя пишется без проверки и без копии,
как раньше: конфиг, который начнёт на него ссылаться, проверит `apply`.

### 2.2. Проверка до подмены

`checkRuleSetContent` (`lxd/resource_check.go`) проходит тот же путь, что
`LocalRuleSet.reloadFile`: декодирование (`srs.Read` для `.srs`, `PlainRuleSetCompat` для
`.json`), `Upgrade()`, сборка каждого правила через `rule.NewHeadlessRule`. Формат — по
расширению, как у ядра без явного `format`. Набор с правилом, которое не строится (плохое
регулярное выражение), на диск не попадает.

Проверка не знает одного: примет ли набор конкретный конфиг. DNS-роутер отвергает некоторые
наборы для некоторых правил и при старте, и при перечитывании на ходу. Это решает только
ядро — отсюда прежняя копия.

### 2.3. Прежняя копия

Перед подменой текущие байты откладываются в `resources/.prev-<name>` (скрыт из списка,
через REST недостижим). Копия живёт, пока ядро не подтвердило новый набор, и хранит всегда
последнюю подтверждённую версию: повторная заливка неподтверждённого набора её не затирает.

**Ядро работает и грузит этот файл.** Демон находит в активном конфиге наборы `type: local`
с этим путём, подписывается на их обновление (`RegisterCallback`) и после подмены ждёт. Ядро
перечитывает файл само (`fswatch` → `reloadFile`); успешная перезагрузка вызывает подписчиков.
Все наборы отозвались — копия удаляется, `confirmed`. За 10 с не отозвались — прежние байты
возвращаются на место, 422; причина отказа ядра — в его логе (`reload rule-set <tag>: …`).

**Подтвердить некому** — ядро остановлено, либо на файл ссылается только last-good, либо
путь в конфиге записан не так, как его отдаёт демон. Копия ждёт (`pending`):

- первый удавшийся старт ядра (`apply`, `start`/`rollback`, загрузка демона) удаляет все
  копии — что бы ни лежало на диске, ядро с этим поднялось;
- первый неудавшийся старт возвращает все копии на место до следующей попытки:
  - `apply` → откат на last-good идёт уже по прежним байтам. Откат выполняется и тогда, когда
    применяемый конфиг совпадает с last-good, а различались только ресурсы (раньше — fatal);
  - `start`/`rollback` и загрузка демона → одна повторная попытка по прежним байтам.

Копии переживают перезапуск демона: загрузка идёт по той же схеме.

### 2.4. Решения

- **Подтверждение через подписку, не через правку апстрима.** `RegisterCallback` — штатный
  интерфейс `adapter.RuleSet`; файлы `route/rule` не тронуты.
- **Таймаут → отказ, а не «pending».** Если ядро не приняло набор на ходу, с ним не поднимется
  и следующий старт; отказ на `PUT` задевает один набор, а не весь `apply`. Цена: на машине,
  где слежение за файлом не завелось (`watch rule-set file` в логе ядра), замена на ходу
  отвечает 422 — там набор меняется при остановленном ядре.
- **Неудавшийся старт возвращает все копии разом,** не разбираясь, какой набор виноват:
  неподтверждённое не должно участвовать в откате. Потерянное обновление клиент увидит по
  sha256 в списке и зальёт снова.
- **Блокировка.** Проверка, подмена и ожидание идут под `applyAccess`: `apply` не вклинится
  между подменой и подтверждением. Тело запроса читается до захвата.

### 2.5. Windows-пути в проверке занятости

`resourceReferenced` искал в тексте конфига `/resources/<name>`. Конфиг с родными
Windows-путями содержит `\\resources\\<name>` (обратный слэш, экранированный в JSON), и имя
считалось свободным: гуард SPEC 063 на Windows не срабатывал, а замена шла мимо проверки и
прежней копии. Теперь разделители перед сравнением приводятся к `/` (`referencesResource`).
Найдено задачей `test-windows` в lx-ci.

## 3. Клиент (лаунчер)

Признак возможностей не вводится. `PUT` как раньше:

- 200 — набор на машине; `replace: confirmed` — ядро уже работает по нему, `pending` — вступит
  в силу со стартом ядра, поле отсутствует — имя свободно или байты те же;
- 409 — демон до этой задачи либо файл не набор правил: набор остаётся прежней версии;
- 422 — набор не годится (текст в `error`): показать пользователю, считать необновлённым.

Запрос может длиться до 10 с.

## 4. Проверка

- `lxd/resource_check_test.go` — таблица `checkRuleSetContent`, замена под активным конфигом
  и под last-good, битый набор (422, байты прежние), свободное имя без проверки.
- `lxd/resource_replace_test.go`:
  - `TestReplaceConfirmedByRunningCore` / `TestReplaceRefusedByRunningCore` — настоящий
    `rule.LocalRuleSet` со слежением за файлом: принятый набор матчит новые домены, отвергнутый
    (валидатор DNS-правил) возвращён на диск, в памяти прежние правила;
  - `TestPendingReplaceConfirmedByStart`, `TestPendingReplaceRevertedByFailedStart`,
    `TestApplyRevertsPendingReplaceAndFallsBack`, `TestBootRevertsPendingReplace` — судьба
    копии на каждом пути старта;
  - `TestResourceStoreKeepsOldestPrevious`, `TestCheckRuleSetContentBuildsRules`,
    `TestReplaceSameBytesIsNoop`.
- `lxd/resources_test.go`: занятый `geoip.db` — 409, не меняется;
  `TestResourceReferencedByWindowsPath` — путь с `\\` и с `/`.
- `go test -race -tags with_lxd ./lxd/` ✅; сборка `cmd/sing-box` под `LX_TAGS` ✅.
- Живой прогон на macOS 2026-11-23 (бинарь из `lx` под `LX_TAGS`, отдельный `lxd` на
  loopback: mixed-вход, `direct`, два локальных набора — в правиле маршрута и в DNS-правиле):
  - годный набор при работающем ядре → `confirmed` за 0,11 с, запрос через прокси сразу идёт
    по новым правилам, копии нет;
  - набор с `ip_cidr` под DNS-правило (проверку демона проходит) → ядро пишет
    `reload rule-set d: Legacy Address Filter Fields in DNS rules is deprecated…`, 422 через
    10 с, на диске прежние байты, ядро работает;
  - ядро остановлено → `pending`, `.prev-a.srs` лежит; `start` → копия удалена, правила новые;
  - `pending` + `apply` конфига, не стартующего из-за занятого порта → `rolled_back: true`,
    прежние байты на месте, last-good поднялся по ним.
- `GOOS=windows go vet -tags with_lxd ./lxd/` ✅; сами тесты на Windows идут только в lx-ci.
- Не проверено: Linux/OpenWrt (слежение за файлом через inotify) и роутер владельца.

## 5. Не в scope

- Версионирование ресурсов (B3 из SPEC 063): копия одна и живёт только до подтверждения.
- Замена занятых файлов других типов.
- Обрезанный хвост `.srs`, до которого декодер не дочитывает: ядро такой файл читает.
