# SPEC: 081 — AWG_RECEIVE_INDEX_FIRST_CLASSIFICATION

**Фича:** [AWG2](../../FEATURES/003-AWG2/FEATURE.md)

| Поле | Значение |
|------|----------|
| Тип | B (bug) — ловушка референса на приёме, унаследованная портом AWG 2.0 и 3.x |
| Статус | **C** (complete) — red/green e2e, решение владельца 2026-09-05 |
| Подмодуль | `submodules/wireguard-go` (ветка `lx-awg2-v005`), `device/receive.go` |
| Связанные | [[SPECS/TASKS/080-AWG3_HEADER_PROTECTION_TIMINGS]] (§6 — где ловушка описана) · [[SPECS/TASKS/005-AWG2_RANGED_MAGIC_HEADERS]] · [[SPECS/TASKS/026-AWG_MAGIC_VS_RESERVED_CLEAR]] |

Приёмник классифицирует датаграмму как **transport по живому receiver index** до
того, как handshake-кандидаты получат шанс присвоить её по одному лишь слову типа.
Правка чисто приёмная: провод не меняется, совместимость с любым сервером
сохраняется.

---

## 1. Проблема / контекст

Референсный приёмник amneziawg-go (`DeterminePacketTypeAndPadding`) пробует виды
сообщений в порядке init → response → cookie → transport. Handshake-кандидат
принимается по двум признакам: размер (`== S_k + size_k`, а при `random_trailers` —
`> S_k + size_k`) и слово типа на смещении `S_k` в диапазоне `H_k`. Содержимое
transport-пакета на смещении `S1` — шифротекст, то есть случайные 4 байта, и при
широком диапазоне `H1` они в него попадают с вероятностью `ширина/2³²`.

Два проявления:

- **AWG2, точный размер.** Data-датаграмма ровно `S1 + 148` байт (или `S2 + 92`,
  `S3 + 64`) пробуется как init/response/cookie. У экспортов AWG2 с диапазонами
  вроде `43613244-384550127` это ≈8 % таких пакетов. Совпадение размера возможно, когда
  `(S_k + size_k − S4 − 32)` кратно 16 (выравнивание plaintext), например `s1=28,
  s4=0` или `s1=44, s4=0`; при `s1=55, s4=12` (экспорт AWG3) — невозможно без
  добавок 3.x.
- **AWG 3.1, `random_trailers`.** Условие размера ослаблено до `>`, и под проверку
  попадает **каждый** data-пакет длиннее `S1 + 148`; с широким `H1` — те же ≈8 %
  потерь на всём крупном трафике. Экспорты AWG3 держат `h1–h4 = 1..4`, где ложное
  совпадение 2⁻³², поэтому в их конфигурации ловушка не стреляет.

Присвоенный пакет обрезается до размера handshake, уходит в очередь хендшейков, не
проходит MAC1 и отбрасывается. Потеря — на **нашем приёме** (downlink). Uplink
классифицирует приёмник сервера, до него правка не доезжает.

Порт SPEC 080 перенёс порядок референса 1:1 и задокументировал ловушку как свойство
протокола. Владелец решил закрыть нашу половину.

## 2. Цель

Data-пакет, адресованный одному из наших живых ключей, никогда не присваивается
handshake-кандидатом, независимо от размера и ширины `H1–H3`. Всё, что принималось
раньше, принимается и теперь; на провод ничего не меняется.

## 3. Решение

`device/receive.go`, маркер `lx: SPEC 081`:

- Keystream шифра заголовка берётся для байт 0..8 (было 0..4): слово типа **и**
  receiver index. Дальнейший XOR по видам сообщений продолжается с байта 8 —
  keystream последовательный, сумма та же.
- Новый первый кандидат `classifyTransportByIndex`: `len ≥ S4 + 32`, размаскированное
  слово типа на смещении `S4` ∈ `H4`, размаскированный receiver index (смещение
  `S4 + 4`) находится в `indexTable` **с живым keypair** → transport, размер не
  проверяется на равенство. Найденная запись таблицы передаётся дальше — второго
  lookup нет.
- Промах → референсный порядок `DeterminePacketTypeAndPadding` без изменений.
  Поэтому набор принимаемых пакетов — надмножество прежнего.

Обратный риск — настоящий init/response присвоен как transport — требует
одновременно попадания слова типа в `H4` и совпадения индекса с живым ключом:
`(ширина H4 / 2³²) × (живых индексов / 2³²)`, при одиночном `h4` ≈ 2⁻⁶⁴, при самом
широком — порядка 10⁻¹⁰; такой пакет не пройдёт AEAD, хендшейк повторится через
`rekey_timeout`. Стоимости: один `indexTable.Lookup` (RLock) на handshake-датаграмму
(редко); у transport-датаграмм lookup просто переехал раньше.

## 4. Критерии приёмки — выполнено

`device/awg_classify_index_first_lx_test.go` (`TestAWGDataPacketOfInitSizeNotClaimedByWideH1`):
пара устройств, `s1=44`, `s4=0`, `h1=5-4294967295` (любое случайное слово типа — «init»),
`h2/h3/h4 = 2/3/4`; после установления сессии 160-байтный IP-пакет даёт data-датаграмму
ровно `44 + 148 = 192` байт (перехват провода пинит размер и тип 4 в открытом виде).

| | Результат |
|---|---|
| Референсный порядок (до правки) | RED — пакет не доставлен за 20 с в обе стороны |
| С правкой | GREEN — доставлен A→B и B→A |
| `go test ./device ./conn`, `-race` по AWG-тестам | зелёные; SPEC 080 e2e (AWG3 с трейлерами и шифром заголовка) не изменился |

## 5. Вне скоупа

- **Uplink** — приёмник сервера на референсе. Полная защита от комбинации
  `random_trailers` × широкие `h1–h4` по-прежнему только конфигом; предупреждение в
  доках остаётся, с пометкой, что наша сторона закрыта.
- Cookie-reply-кандидат и handshake-кандидаты по-прежнему принимаются по слову типа
  без проверки MAC1 на стадии классификации (порядок референса сохранён).
