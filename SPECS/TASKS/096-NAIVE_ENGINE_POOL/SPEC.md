## 1. Как устроено сейчас

Апстримный `protocol/naive/outbound.go` на каждый naive-outbound создаёт `cronet.NaiveClient`, а `Start(StartStateStart)` зовёт `client.Start()`: поднимается движок Cronet — инициализированный сетевой стек Chromium (сетевой поток, `URLRequestContext`, резолвер с кешем, пулы сокетов, кеши TLS/H2/QUIC-сессий). При `insecure_concurrency: N` движков на узел N (по одному на пул соединений), кроме iOS: там `singleEngine`, один движок и N пулов, разведённых заголовком `-network-isolation-key` на каждом стриме.

Что привязано к движку на старте (cronet-go `startEngine`): dialer TCP/UDP (колбэки в наш sing-box-dialer с `detour`), DNS-override на локальный сокет, который обслуживает наш резолвер, пакет доверенных CA, включение QUIC и congestion control, окна QUIC/HTTP2, лимиты пула сокетов. Что живёт на стриме: URL сервера, `-connect-authority` (цель), `proxy-authorization`, `-force-quic`, `Padding`, `-network-isolation-key`. То есть сам сервер naive в движок **не** зашит: один движок может обслуживать разные серверы.

`DialEarly` умеет ждать `started`: дайл до `Start()` не падает, а блокируется до старта. Это делает ленивый старт возможным без правок cronet-go.

Оценка стоимости (§4 — замер): 2–5 МБ кучи на движок в покое, 3–8 МБ под трафиком; код `libcronet` один на процесс. Для сравнения замеренная цена WG/AWG-endpoint'а — 17.5 МБ (стартовые батчи, SPEC 020 / профиль LxBox 519).

## 2. Проблема

1. Подписка из K naive-узлов поднимает K движков на старте ядра независимо от того, пойдёт ли через них трафик; при `insecure_concurrency: N` — K×N движков на Android и десктопе.
2. Старт ядра платит инициализацию всех движков последовательно (та же сумма, что у WG-endpoint'ов).
3. В probe-сессии LxBox (лимит 150 МБ) naive-узлы складываются с WG-пулами.

По оценке выигрыш — десятки мегабайт на десятке узлов, не сотни; это и есть повод сначала измерить (§4), потом делать.

## 3. Варианты

### A. Единый движок на узел на всех платформах (iOS-приём)

`cronet.NaiveClientOptions.TestForceSingleEngine = true` в нашем `NewOutbound`. Один движок и N изолированных пулов вместо N движков. Правка — одна строка в апстримном файле (маркер `// lx: SPEC 096`) или lx-файл с обёрткой конструктора. Выигрыш только у узлов с `insecure_concurrency > 1`; цена — общий сетевой поток на N пулов (у апстрима на iOS так и живёт). Риск: имя опции говорит «Test…», апстрим может её переименовать — страж-тест на компиляцию.

### B. Ленивый старт движка при первом дайле

`Start(StartStateStart)` не зовёт `client.Start()`; `DialContext`/`ListenPacket` делают это под `sync.Once` (или по CAS), ошибка старта возвращается дайлу и сбрасывает `Once`, чтобы следующий дайл повторил. `Close()` останавливает клиента и в незапущенном состоянии (проверить, что `NaiveClient.Close` из `clientStateCreated` корректен; по коду `Start` из закрытого состояния отвечает `net.ErrClosed`).

Даёт: неиспользуемые узлы не стоят ничего, старт ядра не платит за движки. Не даёт: узлы, которые пробует urltest, всё равно получают движок; после первого дайла движок живёт до остановки ядра. Цена: первый запрос через свежий узел ждёт инициализацию движка (сотни миллисекунд); первый замер urltest у такого узла длиннее. Наблюдаемость: `GetOutbounds`/статус узла должен отличать «движок не поднят» от ошибки — состояние, не сбой (по образцу `empty-observability-field-is-state-not-bug`).

Правка — только `protocol/naive/outbound.go` (апстримный файл, маркеры) и, при желании, lx-файл с обёрткой; cronet-go не трогается.

### C. Усыпление движка по простою (уровень 3 SPEC 020 для naive)

Тик idle-suspend (`route/reachability_lx.go`) видит только `adapter.IdleSuspendable` endpoint'ы. Расширение: naive-outbound реализует тот же интерфейс, по простою зовёт `client.Close()` (Shutdown/Destroy движка) и пересоздаёт клиент при следующем дайле. Полный аналог уровня 3 для WG: цена — пересоздание движка при пробуждении, поверх B. Требует, чтобы `NaiveClient` можно было создать заново из тех же опций — конструктор чистый, можно хранить `NaiveClientOptions`. Тик сегодня итерирует `Endpoints()`, для outbound'ов нужен второй список — это правка lx-кода тика, без апстрима.

Делать только если замер покажет, что движок в покое дорог; иначе B достаточно.

### D. Общий движок на группу узлов (форк cronet-go)

`NaiveClient` владеет движками и внешний не принимает; апстрим-контрибуции закрыты; копировать клиент нельзя (правило владельца) — значит пятый форк-сабмодуль `cronet-go-lx` (чистые Go-биндинги, `libcronet` пересобирать не нужно). В нём:
- «профиль движка» = хеш параметров уровня движка (CA-bundle, QUIC/CC/окна, H2-окна, лимиты пула); узлы с одинаковым профилем делят один движок;
- dialer-колбэк движка — диспетчер по адресу назначения (host:port сервера) к dialer'у владеющего outbound'а (его `detour`); резолвер — диспетчер по имени сервера к DNS-опциям узла;
- пулы узлов разводятся `-network-isolation-key` (приём iOS);
- CA объединяются в один bundle на профиль — корень узла A становится доверенным для узла B (назвать в доке);
- неразводимый случай: два узла с одним host:port сервера и разными `detour` — им отдельные движки (fallback на профиль «свой движок»).

Выигрыш — (K−1) движков на профиль; по оценке десятки мегабайт на десяток узлов. Цена — форк, диспетчеры, новый класс гонок при закрытии узла (движок жив, пока жив хоть один узел профиля), правка `.gitmodules`/CI. **Не делать без замера, который покажет, что A+B недостаточно.**

## 4. Замер (условие для решения)

Отложен владельцем 2026-09-24 до появления живого naive-сервера (на машине и у стороны приложений его нет; фикстуры LxBox — заглушки). Методика: эмулятор, один AAR, `adb shell dumpsys meminfo <пакет>` (Native Heap PSS и TOTAL PSS — память Cronet нативная, pprof ядра её не видит), контроль без naive; три конфига на одном узле — (1) один узел, (2) тот же с `insecure_concurrency: 4`, (3) четыре узла; по два замера — после старта и после минуты трафика. (2)−(1) = цена трёх движков одного узла, (3)−(1) = цена трёх узлов.

Пороги для решения (предложение): движок < 3 МБ в покое — делать только B; 3–8 МБ — A+B; > 8 МБ или probe-сессии упираются в лимит — обсуждать C и D.

## 5. Границы

- Провод naive не меняется ни в одном варианте: те же CONNECT-стримы, заголовки, padding.
- Новых ключей конфига в A/B нет; C переиспользует `lx_idle_suspend`; D — без ключей (профиль вычисляется).
- Сервер (inbound naive) не затрагивается.
- Локально на darwin naive не поднять (нет `libcronet`), стенд — только эмулятор или CI-сборка darwin с CGO.

## 6. Критерии приёмки (для варианта, который утвердит владелец)

1. Замер §4 до и после: память в покое и под трафиком, старт ядра с K naive-узлами.
2. Юниты: ленивый старт стартует движок ровно один раз при параллельных дайлах; ошибка старта отдаётся дайлу и не залипает; `Close` до первого дайла не паникует и не течёт.
3. Прогон на эмуляторе: naive-узел под urltest в selector'е, переключения, стоп/старт ×3, `insecure_concurrency: 4` (для A).
4. Наблюдаемость: узел без поднятого движка виден как состояние, не как ошибка.
