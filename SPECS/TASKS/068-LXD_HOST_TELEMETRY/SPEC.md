# SPEC: 068 — LXD_HOST_TELEMETRY

**Фича:** [LXD_DAEMON](../../FEATURES/014-LXD_DAEMON/FEATURE.md)

| Поле | Значение |
|------|----------|
| Тип | F (feature) — телеметрия **хоста**, на котором крутится демон: CPU, память, температура, диски, дескрипторы и сетевые интерфейсы |
| Статус | C (complete) — **DEVICE-VERIFIED**: полевой прогон на живом OpenWrt-роутере (MT7981) подтверждён владельцем 2026-08-13. Юниты зелёные под `-race` (включая Linux-парсеры на подставном `/proc`), живой прогон на macOS |
| Ветка | `lx` |
| Base | `b291fd5fc` |
| Связанные | [SPEC 065](../065-LXD_OBSERVABILITY_PLANE/SPEC.md) (плоскость наблюдаемости — тот же mux, тот же пин, тот же паттерн кеша; `/admin/memory` про **процесс**, эта спека про **хост**), [SPEC 066](../066-LXD_CLIENT_IDENTITY/SPEC.md) (тот же приём платформенных провайдеров и «пустое поле = состояние»), [SPEC 067](../067-LXD_BUILD_TAG_SPLIT/SPEC.md) (тег `with_lxd`), [FEATURE 014](../../FEATURES/014-LXD_DAEMON/FEATURE.md) |

**Touches:** только пакет `lxd/` — новые файлы `hostinfo.go` (форма ответа,
кеш, дельты), `hostinfo_linux.go`, `hostinfo_darwin.go`, `hostinfo_stub.go`
(платформенные читатели), `hostinfo_net.go` и `hostinfo_exec.go` (общее для
`linux || darwin`: «паспорт» интерфейса, запуск внешних процессов, список
псевдо-ФС) и маршруты в [lxd/admin.go](../../../lxd/admin.go). Из
`clientinfo_linux.go` в `hostinfo_exec.go` переехал `runProvider` — он
понадобился обеим платформам.
**Ядро не правится.** Внешних зависимостей не добавляется: на darwin
счётчики интерфейсов читаются через `golang.org/x/net/route`, который уже в
`go.mod` (тянется транзитом через `http2`, которым демон и так пользуется).

## Why

`/admin/memory` (SPEC 065) показывает память **процесса**. Когда роутер с
256 МБ ОЗУ начинает тормозить, этого мало: непонятно, упёрлось ли железо, и
если да — во что. Оператор идёт по SSH и смотрит `top`, `free`, `df` руками —
то есть ровно то, ради устранения чего заводилась плоскость наблюдаемости.

Три сценария, которые ручка закрывает:

- **«Роутер тормозит»** — CPU в полке, или память кончилась, или одно ядро
  занято при трёх свободных (на четырёхъядерном MT7981 среднее это прячет).
- **«Apply перестал работать»** — кончилось место на разделе со state-dir.
  Симптом неочевидный: ядро живо, конфиг не пишется.
- **«Новые соединения не открываются»** — упёрлись в лимит файловых
  дескрипторов. В логе `too many open files` либо вообще ничего, при
  нормальных CPU и памяти.

## Design

### Две ручки

```
GET /admin/host             железо и ОС: cpu, memory, thermal, disk, fd
GET /admin/host/interfaces  сетевые интерфейсы со счётчиками
```

Разделены потому, что интерфейсов на роутере десяток и обновляются они чаще,
чем модель железа. Одна ручка с `?include=` отвергнута: параметр, который в
99% случаев не указывают, — это сложность без применения.

Обе — на том же mux, за тем же mTLS-пином, что вся плоскость наблюдаемости
(SPEC 065), и **не** на операторском loopback-пути: смысл в том, чтобы
лаунчер читал их удалённо. Обе отвечают независимо от того, поднято ли ядро.

**Массив, а не объект по имени** — порядок значим: UI показывает `wan` и
`br-lan` первыми, а не по алфавиту. **Отдаются все интерфейсы**, включая `lo`
и down (решение владельца): «wan лёг» — ровно то, что оператор хочет увидеть,
а фильтрация мусора вроде `ifb0` — задача UI, который знает, что показывает.

`mac: ""` у туннельного интерфейса и `addresses: []` у AP-интерфейса в мосту —
валидные состояния, не ошибки (тот же принцип, что в SPEC 066).

### Счётчики против производных: дельты и `interval_seconds`

`/proc/stat` и `/proc/net/dev` отдают **монотонные счётчики**, а не проценты и
не скорости. Проценты считаются как дельта между двумя замерами, поэтому
демон хранит предыдущий замер и рядом с производным числом отдаёт
`interval_seconds` — интервал, за который оно посчитано. Без него `12.4%` за
5 секунд и за час выглядят одинаково, а значат разное.

**Первый запрос после старта демона** отдаёт `usage_percent: null`,
`per_core_percent: null`, `interval_seconds: 0` — считать не от чего, и
подставлять ноль нельзя: он читается как «простаивает».

Сырые счётчики отдаются **вместе** с производными, не вместо: счётчик
переживает всё, скорость удобна, но врёт при разрывах. Клиент выбирает сам.

### Кеш

TTL **2 секунды** — короче, чем у справочника клиентов (60 с), потому что
данные меняются постоянно; длиннее, чем у `/admin/memory` (200 мс), потому что
чтение `/proc` дороже и опрос идёт под графики. Тот же приём: `now()` как
тестовый шов, чтобы юниты проверяли throttle, а не гонялись со временем.

Замер под кешем **обновляет базу дельт**. Отсюда следствие, которое надо
знать: `interval_seconds` — это интервал между последними двумя **фактическими**
замерами, а не между запросами клиента.

### Платформенные читатели

Тот же паттерн, что в SPEC 065/066: одноимённые package-private функции +
build-теги, **без интерфейса**.

```go
// hostinfo_linux.go   //go:build with_lxd && linux
// hostinfo_darwin.go  //go:build with_lxd && darwin
// hostinfo_stub.go    //go:build with_lxd && !linux && !darwin
func numCPU() int
func readStaticInfo() staticInfo                     // модель, ОС, ядро, арх
func readUptimeSeconds() int64
func readLoadAverage() (*float64, *float64, *float64)
func readCPUTicks() ([]cpuTicks, bool)               // [0] = агрегат, дальше ядра
func readMemory() memoryInfo
func readThermal() *thermalInfo                      // nil = датчиков нет
func readMounts() []mountInfo
func markStateDirMount(mounts []mountInfo, stateDir string)
func readFD() fdInfo
func readInterfaces() []rawInterface
```

Читатели возвращают **сырьё**, а не готовый ответ: проценты и скорости
считает общая часть, потому что для них нужен предыдущий замер, а он живёт в
кеше. `readCPUTicks` отдаёт тики (`(ticks, ok)`, где `ok=false` = источника на
платформе нет), `readInterfaces` — счётчики; преобразование в `cpuInfo` и
`interfaceInfo` платформы не касается.

Три файла делят два общих: `hostinfo.go` (форма, кеш, дельты) и
`hostinfo_net.go` + `hostinfo_exec.go` под `linux || darwin` — «паспорт»
интерфейса через `net.Interfaces()`, запуск внешних процессов и список
псевдо-ФС одинаковы на обеих платформах, дублировать их незачем.

Источники по платформам:

| Данные | Linux | macOS |
|---|---|---|
| CPU-тики | `/proc/stat` | ❌ (нужен Mach API) |
| load average | `/proc/loadavg` | `sysctl vm.loadavg` |
| память | `/proc/meminfo` | `sysctl hw.memsize` + `vm_stat` |
| температура | `/sys/class/thermal/*` | ❌ (нужен SMC/IOKit → CGO) |
| диски | `/proc/self/mounts` + `statfs` | `getfsstat` |
| дескрипторы | `/proc/self/fd`, `/proc/sys/fs/file-nr` | `getrlimit`, `sysctl kern.num_files` |
| интерфейсы | `/proc/net/dev` | `x/net/route`, `NET_RT_IFLIST2` |
| модель | `/proc/device-tree/model`, `/tmp/sysinfo/model` | `sysctl hw.model` |

**Форма ответа одна на все платформы; недоступное поле = `null`.** Клиент не
разбирает `os` перед чтением — просто проверяет `null`.

Когда клиенту нужно знать платформу — например, отличить «здесь термодатчиков
не бывает» от «датчик молчит», — для этого есть **три машиночитаемых поля**, и
они отвечают на разные вопросы:

| Поле | Уровень | Вопрос |
|---|---|---|
| `os_family` | ядро, сисколлы | «есть ли тут `/proc`» |
| `os_id` | дистрибутив | «есть ли тут `ubus`» |
| `os_id_like` | совместимость | «это форк чего-то знакомого?» |

Строка `os` — человеческая, её формат задаёт дистрибутив, и парсить её клиент
не должен.

`os_id` и `os_id_like` берутся из `ID` и `ID_LIKE` в `/etc/os-release`.
**Именно поэтому `os-release` читается первым, а `openwrt_release` — только
запасной**: у стандартного файла есть машиночитаемые ключи, которых у второго
нет вовсе, и его `PRETTY_NAME` чище. На роутере владельца это видно наглядно:

```
/etc/os-release:      NAME="RouteRich"  ID="openwrt"  ID_LIKE="lede openwrt"
                      PRETTY_NAME="RouteRich 24.10.5"
/etc/openwrt_release: DISTRIB_DESCRIPTION='RouteRich 24.10.5 r29087-… RR-3.9.0'
```

Форк называет себя `RouteRich`, но `ID` честно говорит `openwrt` — то есть
клиент, сопоставляющий человеческую строку, платформу бы не опознал, а по
`os_id` опознаёт. `ID_LIKE` нужен для форков, которые ставят собственный `ID`
(например `immortalwrt`) и называют базу только там; отдаётся массивом, потому
что в стандарте это список через пробел, и резать строку каждому клиенту
незачем.

Вне Linux `/etc/os-release` нет, поэтому `os_id` — константа (`macos`,
`windows`): поле заполнено везде, где платформа вообще известна, и отдельной
ветки клиенту не нужно. `os_id_like` при этом пустой массив, **не** `null`. Это прямое следствие
решения владельца «берём что можем, чего не можем — не отдаём».

Отдельного списка `unsupported` **нет** (моя рекомендация, принята по
умолчанию): UI рисует прочерк одинаково и для «платформа не умеет», и для
«датчик молчит», а различать их нужно один раз — при отладке, где хватает
знания платформы из поля `os`.

### macOS: счётчики интерфейсов 32-битные

Проверено на живой машине: `NET_RT_IFLIST2` отдаёт `if_data64`, где **пакеты и
ошибки 64-битные и точны** (сверено с `netstat -ib` до единицы), а **байтовые
счётчики фактически 32-битные** — переполняются каждые 4 ГБ. Это поведение
ядра, а не дефект разбора: значения сходятся с `netstat` по модулю 2³².

Решение (моя рекомендация, принята по умолчанию): **демон доращивает байтовые
счётчики до 64 бит**, накапливая дельты с учётом переполнения. Состояние под
это уже есть — предыдущий замер хранится ради скоростей, добавляется одно поле
на интерфейс.

Границы, которые надо назвать честно:

- счётчик стартует с нуля при перезапуске демона (он «свой», а не системный);
- если между замерами прошло больше 4 ГБ трафика, переполнение незаметно и
  дельта теряется — при TTL 2 с это ~17 Гбит/с, вне досягаемости стенда;
- на Linux доращивание не нужно и не применяется — `/proc/net/dev`
  64-битный.

Альтернативы отвергнуты: отдавать усечённое значение → график обрывается в
ноль каждые 4 ГБ (на Wi-Fi это часы); отдавать `null` → macOS теряет то, что
достаётся почти даром.

### Сводные поля

`max_celsius` и `max_used_percent` — рядом с массивами, чтобы UI показывал
одно число и разворачивал по клику, а каждый клиент не писал свой `max()`.

**`max_used_percent` считается только по записываемым ФС** (моя рекомендация,
принята по умолчанию). На OpenWrt корень `squashfs` read-only и всегда 100%:
без фильтра сводка вечно красная, а индикатор, который всегда красный, — это
индикатор, на который перестают смотреть. Флаг `read_only` при этом остаётся в
каждой записи, так что полная картина видна.

### state-dir среди маунтов

Раздел, на котором лежит state-dir, помечается `holds_state_dir: true`, а сам
путь отдаётся отдельным полем `state_dir_path`. **Дублирующей записи не
создаётся** — это одна ФС, и вторая запись ломала бы и сумму по `total_bytes`,
и сводку.

Ищется сравнением **device id** из `statfs` по state-dir с маунтами, **не по
префиксу пути**: на OpenWrt `/etc` — симлинк в оверлей, и `/etc/sing-box-lx/state`
не начинается с `/overlay`, хотя физически там и лежит.

Край: если совпадения нет (bind-mount, экзотическая ФС, гонка при чтении),
`holds_state_dir` не появляется ни на одной записи, а `state_dir_path`
остаётся единственным указателем. Это лучше, чем выдумывать запись.

### Что выяснилось при реализации

Четыре вещи, которых не было в исходном дизайне и которые нашлись только на
живом прогоне — записаны, чтобы следующий читатель не «чинил» их обратно.

**`struct loadavg` на darwin — 24 байта, не 32.** Три `fixpt_t` (по 4 байта)
плюс паддинг до выравнивания `long`, который лежит на смещении **16**.
Первая реализация читала масштаб с 24 и молча отдавала `null` во всех трёх
полях. Смещения сверены `offsetof`-пробником по SDK-заголовкам этой машины.

**`/dev/fd` на darwin не читается через `os.ReadDir`.** Нужен
`os.Open` + `Readdirnames`; `ReadDir` возвращал пустой результат, и `fd.open`
был `null` при живом источнике. Открытие каталога само занимает дескриптор —
он вычитается.

**Псевдо-ФС нужно фильтровать и на macOS.** `devfs` попадал в `mounts[]` с
`used_percent: 100` и утаскивал за собой `max_used_percent`. Список псевдо-ФС
переехал в общий файл и пополнился darwin-именами (`devfs`, `ctlfs`,
`fdesc`).

**`syscall.Utsname` разной знаковости на ARM.** `Release` — это `[]int8` на
arm64 и amd64, но `[]uint8` на 32-битном arm. Хелпер с сигнатурой под один из
типов компилируется на части Linux-целей и падает на остальных: релизная
сборка `linux-armv7` слегла именно на этом, пройдя при этом на arm64. Хелпер
сделан дженериком `[T ~int8 | ~uint8]`. Урок общий: у `syscall`-структур
типы полей зависят от архитектуры, и одной кросс-сборки под arm64 мало —
проверять надо всю релизную матрицу.

**`runProvider` переехал из `clientinfo_linux.go` в общий
`hostinfo_exec.go`.** Он понадобился darwin-читателю памяти (`vm_stat`), а
второй копии быть не должно — дисциплина запуска внешних процессов (LookPath,
таймаут, «нет бинаря = состояние, не ошибка») у всех провайдеров одна.

## Out of scope

- **История и графики.** Хранить временные ряды на роутере с 256 МБ и флешкой
  — отдельная задача со своим устройством хранения и ротацией. Ручка отдаёт
  «сейчас», историю копит клиент.
- **Пороги и алерты** («температура выше 80 — предупредить»). Это политика,
  её место в UI, а не в демоне.
- **Per-process telemetry хоста** (кто ест CPU). Это `top` по сети — другой
  масштаб задачи и другая приватность.
- **Windows** — стаб, все поля `null`. Демон там и так неполон: службы нет,
  ротации лога нет (SPEC 067 — Win7-сборка вообще собирается без `with_lxd`).
- **Управление** (сбросить счётчики, поднять интерфейс). Ручка только читает.
- **Мост в Clash API / Prometheus.** Формат — наш JSON; экспортеры, если
  понадобятся, живут на стороне клиента.

## Acceptance

- [x] `GET /admin/host` на живом OpenWrt возвращает непустые `cpu`, `memory`,
  `disk`, `fd`; `model` совпадает с `cat /tmp/sysinfo/model`, `uptime_seconds`
  — с первым числом `/proc/uptime`.
- [x] `per_core_percent` длиной ровно `cores`; при нагрузке на одно ядро
  (`while :; do :; done`) в массиве видно одно высокое значение, а не ровное
  среднее.
- [x] Первый запрос после старта демона: `usage_percent: null`,
  `per_core_percent: null`, `interval_seconds: 0`. Второй (после TTL) — числа.
- [x] `memory.used_percent` считается от `available_bytes`; при заполненном
  page cache процент **не** скачет к 100 (проверяется на подставном
  `/proc/meminfo` с большим `Cached`).
- [x] `thermal.zones` совпадает с `for z in /sys/class/thermal/thermal_zone*/;
  do cat $z/type $z/temp; done`; `max_celsius` = максимум по массиву.
  Термозон нет → `thermal: null` (не пустой массив).
- [x] `disk.mounts` не содержит псевдо-ФС (`proc`, `sysfs`, `cgroup`,
  `devtmpfs`, `debugfs`); `holds_state_dir: true` стоит ровно на одной записи
  и совпадает с разделом из `df <state-dir>`.
- [x] `max_used_percent` игнорирует read-only ФС: на OpenWrt со `squashfs` в
  корне (100%) сводка показывает максимум по записываемым, а флаг `read_only`
  у корня выставлен.
- [x] `fd.open` растёт при открытии соединений и возвращается назад;
  `fd.limit` совпадает с `ulimit -n` процесса.
- [x] `GET /admin/host/interfaces` перечисляет **все** интерфейсы, включая
  `lo` и down; счётчики совпадают с `/proc/net/dev`.
- [x] Скорости: при заведомой нагрузке `rx_bytes_per_second` ненулевой и
  правдоподобен; на простаивающем интерфейсе — ноль, а не мусор.
- [x] macOS: ответ приходит с заполненными `memory`, `disk`, `fd`,
  `load_*`, `uptime_seconds`, `model`; `thermal: null`, `usage_percent: null`,
  `per_core_percent: null` — и это **не** 500 и не пустой ответ.
- [x] macOS: `/admin/host/interfaces` отдаёт пакеты и ошибки, совпадающие с
  `netstat -ib`; байтовые счётчики доращены — после прокачки >4 ГБ значение
  продолжает расти, а не обнуляется.
- [x] Кеш: два запроса внутри TTL не перечитывают `/proc` (проверяется через
  тестовый шов, не по времени).
- [x] Маршруты за mTLS-пином (без сертификата → 401) и **не** на операторском
  loopback-пути.
- [x] Ядро не поднято (`idle`/`fatal`) → обе ручки продолжают отвечать.
- [x] Сборка без тега `with_lxd` и на платформе без реализации (стаб) не
  ломается; `gofmt` чист; `go vet` чист; юниты зелёные под `-race`.
