# Демон lxd: что это и как настроить

Практическое руководство оператора: что такое `sing-box lxd`, зачем он нужен, как
ставится на macOS и какие есть подходы на Linux. English version —
[lxd-daemon.md](lxd-daemon.md).

---

## 1. Что это и зачем

`sing-box lxd` — **демон, который хостит ядро sing-box внутри себя** и выставляет
долгоживущий канал управления. Ключевое отличие от `sing-box run`:

- **Канал переживает reload.** У `run` смена конфига = рестарт процесса: клиент
  (лаунчер) теряет соединение, стримы статусов и наблюдаемости рвутся. У lxd
  слушающий порт принадлежит демону, а не box-инстансу: apply подменяет ядро
  «под» живым сервером, клиент видит переходы STARTED/STOPPING/… одним стримом
  без переподключения.
- **Демон доступен именно тогда, когда данные не ходят.** Канал управления
  поднимается ДО ядра: битый или отсутствующий конфиг оставляет демон на связи —
  чинить конфиг можно по тому же каналу, который нужен как раз при лежащем
  data-plane.
- **Конфиг с гарантиями.** `POST /admin/apply` валидирует кандидата
  (`sing-box check` собственным бинарником), при провале старта откатывается на
  последний рабочий конфиг (**last-good**), помнит прерванный apply и
  run-намерение (`was_running`) через рестарты и ребуты.
- **Удалённое управление с доверием.** mTLS: демон — сам себе CA, клиенты
  регистрируются одноразовым инвайтом и дальше опознаются по сертификату.

Типовые роли: локальный движок для лаунчера на том же маке (канал переживает
reload'ы) и **удалённый узел** — например, ядро на роутере/сервере, которым
лаунчер управляет по сети.

Один порт несёт две плоскости:

| Плоскость | Протокол | Что даёт |
|---|---|---|
| наблюдаемость | gRPC `daemon.StartedService` | статусы, логи, группы/urltest, DNS-поток, соединения — общий протокол с Android-линейкой |
| администрирование | REST `/admin/*` | apply / rollback / start / stop / config / status / info, enrollment клиентов |

## 2. Быстрый старт (dev, без установки)

```bash
sing-box lxd --state-dir lxd-state -c config.json
```

Без `daemon.json` действуют **dev-дефолты**: plain h2c на `127.0.0.1:9091`, без
секрета, без mTLS и без реестра клиентов. Лог — на экран. `-c` — необязательный
seed: используется только пока нет last-good; без него демон стартует пустым
(IDLE) и ждёт первый apply.

Проверка:

```bash
curl -s http://127.0.0.1:9091/admin/status
```

## 3. daemon.json — настройки демона

Живёт в `<state-dir>/daemon.json` (0600). **Единственный** источник
connection-настроек: у команды нет флагов `--listen/--tls/--secret` по
построению — вопрос «файл или флаг» не существует. Нет файла → dev-дефолты;
файл никогда не создаётся неявно (его пишет `--service=install` на macOS или
редактор оператора).

| Ключ | Дефолт | Значение |
|---|---|---|
| `listen` | `127.0.0.1:9091` | адрес канала (обе плоскости); строка `"host:port"` либо `{"address": [...], "port": N}` для нескольких адресов — см. ниже |
| `tls` | `false` | mTLS с регистрацией клиентов; `false` = plain h2c, только loopback/dev |
| `secret` | пусто | Bearer операторских маршрутов; единственный гейт при `tls: false` (пусто = аутентификации нет) |
| `log_max_size_mb` | `20` | ротация лога: страховочный потолок размера |
| `log_max_backups` | `1` | сколько старых поколений (`lxd.log.1…N`) хранить |
| `log_max_age_hours` | `24` | ротация по возрасту файла |

Дефолты ротации дают «≈сутки истории»; 0/отсутствие ключа = дефолт,
«безлимита» нет намеренно. Смена любых настроек = правка файла + рестарт службы,
не переустановка.

### 3.1. listen: один адрес или несколько

У `listen` две формы с одним смыслом — адреса, на которых поднимается
управляющий канал. Обе плоскости (gRPC и admin REST) одинаково доступны на
каждом из них.

```jsonc
"listen": "127.0.0.1:19091"                                  // один адрес
"listen": {"address": ["192.168.10.1", "127.0.0.1"], "port": 19091}  // несколько
```

Вторая форма нужна потому, что одного адреса часто действительно мало: демон,
доступный и с LAN-интерфейса, **и** с loopback, одним биндом не выражается.
`0.0.0.0` — не решение: он заодно выставляет наружу все остальные интерфейсы
хоста, включая те, на которых слушать не планировали.

Что важно знать:

- **Всё или ничего.** Если хоть один адрес не поднялся (опечатка или интерфейс
  ещё не сконфигурен), демон завершается с ошибкой, называющей адрес. Так
  исключён режим «поднялся наполовину»: снаружи здоров, но недоступен ровно
  там, где нужен. Если адрес появляется поздно (мост или туннель настраивается
  после загрузки), запускать службу после этого интерфейса.
- **Первый адрес — рекламируемый.** Инвайты регистрации, локальный клиент и
  сводка установки указывают на первую запись — ставьте первым тот адрес, на
  который должны ходить лаунчеры.
- **Маски не поддерживаются.** `192.168.10.1/32` отвергается: ядро биндит один
  адрес, а не диапазон, поэтому маска лишь заставила бы файл обещать то, чего
  демон не делает. Ограничение того, *кому* можно подключаться, — задача
  файрвола.
- Строковая форма не изменилась и продолжает работать: существующие
  `daemon.json` править не нужно, одиночный адрес и записывается строкой.

## 4. Ключи командной строки

| Ключ | Значение |
|---|---|
| `--state-dir <dir>` | дом демона: daemon.json, last-good, run-state, реестр клиентов, ключи (дефолт `lxd-state`) |
| `-c <файл>` | seed-конфиг (строго один файл; каталоги `-C` не поддерживаются) |
| `--config-force <файл>` | всегда бутиться с этого файла, поверх last-good |
| `--run` | поднять ядро независимо от записанного run-состояния |
| `--service install\|install-user\|uninstall` | установка службой (см. разделы ОС) |
| `--purge` | с `uninstall` — снести и state-каталог |
| `--dry-run` | с `--service` — показать, что было бы сделано, ничего не меняя |
| `client add [--name <метка>]` | сминтить одноразовый инвайт для нового клиента |
| `client list` / `client remove <имя-или-отпечаток>` | просмотр / отзыв доверенных клиентов |

Сабкоманда существует только в сборках с тегом `with_lxd`.

## 5. Безопасность: кто чем аутентифицируется

- **Клиент (лаунчер)** — доверенным сертификатом, полученным при enrollment.
  Сертификат — полный мандат обеих плоскостей; Bearer клиенту не нужен и секрета
  он не знает.
- **Оператор (человек с шеллом на хосте)** — Bearer-секретом из daemon.json на
  **loopback-only** маршрутах (`client add/list/remove`). Минт инвайта = выдача
  доверия, поэтому из сети эти маршруты недоступны в принципе.
- **Enrollment** — единственный маршрут до доверия: одноразовый код
  (`адрес#отпечаток-сервера#код`), сгорает на первом использовании; клиент пинит
  сервер по отпечатку.
- При `tls: false` (dev) весь гейт — Bearer; без секрета аутентификации нет —
  поэтому plain-режим только на loopback.

## 6. Логи

Под службой (stdout — не терминал) демон **сам владеет** файлом
`<support>/lxd.log`: перехватывает stdout/stderr процесса (в файл попадает всё,
включая лог ядра и паники) и ротирует по возрасту/размеру с лимитами из
daemon.json. При ручном запуске в терминале лог остаётся на экране, файл не
трогается. Путь к логу и state-dir клиент узнаёт из `GET /admin/info` — ничего
хардкодить не нужно. Реализовано на macOS и Linux; на Windows — нет (как и
служба).

**Каналов лога два, и несут они разное.** gRPC-поток `SubscribeLog` несёт лог
**ядра** — то, что пишет работающий инстанс. Строки самого демона (`lxd: …`,
ошибки бутстрапа, паники) идут в stdout/stderr, то есть в `lxd.log`. Разница
важна ровно тогда, когда всё сломалось: если ядро не поднялось, стримить
нечего, а причина лежит в файле. `GET /admin/logs?tail=N` отдаёт его хвост по
сети — удалённому клиенту не нужен shell на хосте:

```bash
curl -s --cert client.pem --key client.key -k \
  "https://server:9091/admin/logs?tail=500"
```

## 7. macOS — автоматическая установка

Единственная платформа с полным `--service`. Две области:

```bash
sudo sing-box lxd --service=install    # системный LaunchDaemon: root, старт до логина, TUN
sing-box lxd --service=install-user    # LaunchAgent: без sudo, старт при логине, десктоп-UX
```

Install делает всё сам:

1. создаёт `…/Application Support/sing-box-lxd/` (0700) и `state/` внутри;
2. **материализует daemon.json**: существующий адрес сохраняется (реинсталл не
   двигает канал из-под сопряжённых клиентов), иначе первый свободный
   loopback-порт от 19091; `tls` — всегда; секрет — существующий или генерируется;
3. пишет plist (`com.leadaxe.sing-box-lxd`) и бутстрапит службу; plist вырожден
   до `sing-box lxd --state-dir <dir>` — все настройки в daemon.json;
4. печатает сводку: адрес канала, админ-секрет, путь daemon.json, команду
   рестарта — и **одноразовый инвайт** для сопряжения лаунчера.

Пути: system — `/Library/Application Support/sing-box-lxd/`, user —
`~/Library/Application Support/sing-box-lxd/`. Лог — `lxd.log` рядом со `state/`.

Прочее:

```bash
sing-box lxd --service=install --dry-run  # показать plist и что произойдёт, ничего не трогая
sing-box lxd --service=uninstall          # снять службу; state сохраняется
sing-box lxd --service=uninstall --purge  # снять службу и снести state (клиенты, ключи, last-good)
sing-box lxd --service=uninstall --dry-run --purge   # показать, что было бы удалено
sudo sing-box lxd client add --name mac-book   # новый инвайт на живом демоне (state-dir найдётся сам)
```

## 8. Linux — подходы к настройке

**Принцип: на Linux `--service` ТОЛЬКО ПЕЧАТАЕТ.** Всё, что меняет диск —
unit/init-скрипт, `daemon.json`, удаление state — выполняет оператор своими
руками. Почему: launchd — один вендор с одним API, а linux — зоопарк (серверы с
systemd, роутеры на OpenWrt/procd, контейнеры без того и другого), и неверная
догадка, мутирующая `/etc`, хуже точной распечатки. У read-only нет и
полусостояний: рецепт, который никогда не применяется частично, не может
оставить хост между двумя конфигурациями.

Поэтому `--service=install` определяет init-систему и печатает готовый к
вставке рецепт — дом демона, `daemon.json`, unit/init-скрипт, команды включения
и шаг сопряжения — со ссылкой на соответствующий раздел этого документа.
`--service=uninstall` так же печатает шаги снятия; `--purge` печатает команду
`rm -rf`, а не выполняет её. `--dry-run` принимается и ничего не меняет — на
Linux любое действие и так лишь печать.

Сам демон на Linux полноценен: mTLS, apply/rollback, ротация лога — всё
работает; кросс-сборка `GOOS=linux GOARCH=arm64` (статический бинарник,
musl-совместим) проверена. Секрет на экран не попадает никогда: рецепт
генерирует его на месте через `$(head -c 32 /dev/urandom | xxd -p -c 64)`, так
что он существует только внутри `daemon.json` на хосте.

Ниже — то, что этот рецепт печатает, если удобнее делать руками.

### 8.1. Общая часть (любой init)

```bash
mkdir -p /var/lib/sing-box-lxd/state        # OpenWrt: /etc/sing-box-lxd/state — см. 8.3
cat > /var/lib/sing-box-lxd/state/daemon.json <<EOF
{
  "listen": "127.0.0.1:19091",
  "tls": true,
  "secret": "$(head -c 32 /dev/urandom | xxd -p -c 64)"
}
EOF
chmod 700 /var/lib/sing-box-lxd /var/lib/sing-box-lxd/state
chmod 600 /var/lib/sing-box-lxd/state/daemon.json
```

> ⚠️ **На OpenWrt/busybox `xxd` нет** — подстановка выше даст **пустой** секрет
> без единой ошибки, а `"secret": ""` при `tls: true` означает канал управления
> без аутентификации. Там генерировать `$(openssl rand -hex 32)` (openssl на
> OpenWrt почти всегда есть) — и **проверять записанное** (`grep secret
> daemon.json`), а не полагаться на выход команды. Рецепт `--service=install`
> уже печатает правильный генератор под каждый init.

Для управления с другой машины `listen` — LAN-адрес (например
`192.168.10.1:19091`), либо объектная форма, если рядом нужен и loopback
(`{"address": ["192.168.10.1", "127.0.0.1"], "port": 19091}`) — см. 3.1. mTLS
обязателен, наружу порт не открывать файрволом без необходимости. Операторские
команды (`client add`) всё равно выполняются только на самом хосте.

### 8.2. systemd (обычный сервер/десктоп)

`/etc/systemd/system/sing-box-lxd.service`:

```ini
[Unit]
Description=sing-box-lx daemon
After=network-online.target
Wants=network-online.target

[Service]
ExecStart=/usr/local/bin/sing-box lxd --state-dir /var/lib/sing-box-lxd/state
Restart=always
RestartSec=2

[Install]
WantedBy=multi-user.target
```

```bash
systemctl daemon-reload
systemctl enable --now sing-box-lxd
```

stdout под systemd — не терминал, поэтому демон сам заберёт лог в
`/var/lib/sing-box-lxd/lxd.log` и будет ротировать; journald получит только
ранний вывод до перехвата.

### 8.3. OpenWrt / procd (роутеры)

Особенности платформы:

- `/var` — tmpfs, умирает на ребуте → state-каталог держать в персистентном
  месте: `/etc/sing-box-lxd/state` (overlay) или extroot (`/root/…`).
- На роутерах **без extroot** лог рядом со state будет писаться в NAND-overlay —
  износ; с extroot проблемы нет. Дефолтные лимиты ротации (20 МБ × 2 файла)
  ограничивают ущерб, но лучше extroot.

**Заливка бинарника.** На OpenWrt часто нет sftp-server, поэтому `scp`/`rsync`
не работают. Рабочий способ — поток через ssh (качать и распаковывать архив
лучше на рабочей машине, не на роутере — там может не быть места под tar):

```bash
ssh root@HOST 'cat > /root/sing-box' < sing-box            # распакованный бинарь
ssh root@HOST 'chmod +x /root/sing-box && /root/sing-box version'
```

Брать **статическую** сборку (`GOOS=linux`, musl-совместима) и убедиться в этом
до запуска: `file sing-box` должен показать `statically linked` под нужную
архитектуру — динамический бинарь под glibc на musl-роутере не стартует. В выводе
`version` проверить тег `with_lxd` — без него нет ни `lxd`, ни `client`.

`/etc/init.d/sing-box-lxd`:

```sh
#!/bin/sh /etc/rc.common
START=95
USE_PROCD=1

start_service() {
    procd_open_instance
    procd_set_param command /root/sing-box lxd --state-dir /etc/sing-box-lxd/state
    procd_set_param respawn
    procd_set_param stdout 1
    procd_set_param stderr 1
    procd_close_instance
}
```

```bash
chmod +x /etc/init.d/sing-box-lxd
/etc/init.d/sing-box-lxd enable
/etc/init.d/sing-box-lxd start
```

`sysupgrade -b` не забирает ни init-скрипт, ни state, ни бинарник — дописать
пути в `/etc/sysupgrade.conf`, иначе прошивка-апгрейд снесёт установку.

Как поднять поверх демона отдельный VPN-Wi-Fi (Wi-Fi → мост → tun → firewall с
fail-closed) — [openwrt-vpn-ssid-ru.md](openwrt-vpn-ssid-ru.md).

### 8.4. Чего на Linux нет

- Автоматической установки — по принципу, а не по недоделке (см. выше): рецепт
  печатается, выполняет его оператор.
- Self-update — обновление бинарника это «доставить файл + рестарт службы».

## 9. Сопряжение клиента (одинаково на всех ОС)

1. На хосте демона: `sing-box lxd client add --name <метка>` (на macOS с
   системной службой — под sudo). Печатается одноразовый инвайт
   `адрес#отпечаток#код`.
2. Инвайт вставляется в лаунчер: тот пинит сервер по отпечатку, регистрируется
   кодом (`POST /admin/enroll`), получает доверие по своему сертификату. Код
   сгорает.
3. Проверка/отзыв: `client list`, `client remove <имя-или-отпечаток>`.

**Грабли сопряжения по сети** (проверено на роутере — три неудачные попытки):

- **Операторские команды (`client add/list/remove`) работают только с
  loopback.** По сети демон отвечает `403 operator routes are loopback-only`:
  минт инвайта = выдача доверия, поэтому наружу этот маршрут закрыт. Если
  `listen` указывает на **один** LAN-адрес, loopback не слушается вовсе и
  команда не выполнится ниоткуда. Решение — объектная форма listen с обоими
  адресами (`{"address": ["192.168.10.1", "127.0.0.1"], "port": 19091}`, см.
  3.1); держать `0.0.0.0` только ради этого не нужно и небезопасно.
- **Код живёт в памяти процесса, не в state-dir.** Любой рестарт демона между
  `client add` и вводом кода в лаунчер убивает enrollment: клиент получит
  `enroll: no active enrollment code`. Порядок строгий: выставить listen →
  рестарт службы → **выпустить код** → ввести в лаунчере → и только потом менять
  что-либо ещё.
- **Адрес в инвайте берётся из `listen`.** Если listen — loopback или
  объектная форма, в лаунчере адрес надо заменить на реально достижимый
  (`192.168.10.1:19091`); отпечаток и код оставить как есть. После успеха
  доверие лежит в `clients.json` и переживает рестарт демона и ребут хоста.

## 10. Админ-REST (справочно)

| Маршрут | Что делает |
|---|---|
| `POST /admin/apply` | тело = конфиг; 200 применён / 422 невалиден / 500 сбой (+`rolled_back`) |
| `POST /admin/rollback` | откат на last-good (404 — нечего) |
| `POST /admin/start` · `POST /admin/stop` | жизнь ядра отдельно от конфига (stop запоминается) |
| `GET /admin/config` | активный конфиг |
| `GET /admin/status` | `idle\|started\|fatal`, sha активного/last-good, `last_error`, `interrupted_apply` |
| `GET /admin/info` | паспорт: версия, state_dir, listen, tls, отпечаток, pid, uptime, log_path |
| `POST /admin/enroll` | регистрация клиента по одноразовому коду |
| `GET /admin/resources` · `PUT`/`GET`/`DELETE /admin/resources/{имя}` | файлы, на которые **ссылается** конфиг (`.srs`, geo-базы): список с sha256, заливка, выгрузка, удаление; 409, пока на имя ссылается активный или last-good конфиг |
| `GET /admin/memory` | память процесса: heap/stack/sys, горутины, GC и **два** числа RSS — `rss_current_bytes` и `rss_peak_bytes` (сырые байты; пик не убывает, поэтому отдаётся отдельно от текущего) |
| `GET /admin/stats` | uptime **ядра**, `uplink_total`/`downlink_total`, активные соединения — всё `null` (статус всё равно 200), когда ядра нет |
| `GET /admin/logs?tail=N` | хвост `lxd.log` — лог самого **демона**, которого нет в gRPC-потоке (тот несёт лог ядра) |
| `GET /admin/pprof` | профили со счётчиками; `block`/`mutex` показывают `enabled:false`, пока не задан rate |
| `GET /admin/pprof/{имя}` | `heap`, `allocs`, `goroutine`, `threadcreate`, `block`, `mutex` — отдаются мгновенно из того, что рантайм копит и так; `?debug=2` у `goroutine` = дамп стеков |
| `GET /admin/pprof/profile?seconds=N` | CPU-профиль — вот он **пишет** N секунд (дефолт 30, максимум 120); параллельный запрос получает 409 |
| `GET /admin/pprof/trace?seconds=N` | runtime trace, правила записи те же |
| `POST /admin/pprof/block?rate=N` · `POST /admin/pprof/mutex?fraction=N` | включение/выключение двух lock-профилей (`0` = выкл); не сохраняется, после рестарта сброшено |
| `GET /admin/clients-info` | справочник IP → устройство: `name`, `mac`, `ssid`, `iface`, `port`, `source` по каждому клиенту, о котором знает хост; отвечает и когда ядро не поднято |
| `PUT`/`DELETE /admin/clients-info/labels/{ключ}` | собственное имя клиента от оператора; ключ — IP или MAC (иначе 400) |
| `GET /admin/host` | **машина**, на которой крутится демон: CPU (по ядрам), память, термозоны, диски, дескрипторы — в отличие от `/admin/memory`, который про процесс |
| `GET /admin/host/interfaces` | все сетевые интерфейсы с сырыми счётчиками и посчитанными скоростями |

SIGHUP демону = перечитать файл конфига (`--config-force`/`-c`) и применить через
тот же apply-пайплайн с валидацией и откатом.

## 10a. Имена устройств в локальной сети

Инспектор соединений с записью `192.168.20.238:50558` читается, пока устройство
одно, и бесполезен, когда их пятнадцать. `GET /admin/clients-info` — таблица,
которая превращает адреса в устройства. Это **справочник, а не поле в
соединении**: имена меняются раз в часы, поэтому клиент тянет карту раз в
минуту и сам сшивает её с адресами источников. Поток соединений не трогается.

```bash
curl -s .../admin/clients-info
```

```json
{
  "clients": {
    "192.168.20.238": {"name": "iPhone-Vasya", "mac": "be:ab:bd:ec:70:40",
                       "ssid": "LexVPN2G", "iface": "phy0-ap1", "port": "",
                       "source": "lease+arp+wireless"},
    "192.168.20.51":  {"name": "NAS", "mac": "dc:a6:32:de:ad:be", "ssid": "",
                       "iface": "br-lan", "port": "lan2",
                       "source": "lease+arp+bridge"}
  },
  "sources": ["lease", "arp", "bridge", "wireless"],
  "updated_unix": 1755087234
}
```

Карту наполняют пять провайдеров, каждый следующий уточняет предыдущего:

| Провайдер | Заполняет | Откуда |
|---|---|---|
| `lease` | `name`, `mac` | DHCP-лизы (`/tmp/dhcp.leases` и обычные пути дистрибутивов) |
| `arp` | `mac`, `iface` | `/proc/net/arp` — закрывает и клиентов со статическим IP, которых нет в лизах |
| `bridge` | `port` | `bridge fdb show` — в какую розетку воткнут проводной клиент |
| `wireless` | `ssid`, `iface` | `ubus call hostapd.*` на OpenWrt; уточняет `br-lan` до конкретной точки доступа |
| `label` | `name` | ваши собственные метки, последнее слово |

`source` есть в каждой записи намеренно: когда устройство теряет имя, вопрос
всегда один — какой источник замолчал. Одинокое `"source": "label"` означает,
что DHCP-лиз протух. **Пустое поле — состояние, а не ошибка**: у проводного
клиента нет `ssid`, а вне Linux последние три провайдера молчат целиком (ручка
всё равно отвечает — лизами и метками).

`processInfo` эту задачу не решает: он ищет процесс в **локальной** таблице
сокетов, а соединение клиента из сети открыл вообще другой хост.

Метки принадлежат вам и переживают рестарт (`<state_dir>/client-labels.json`):

```bash
curl -X PUT -d '{"name":"Телевизор"}'   .../admin/clients-info/labels/192.168.20.77
curl -X PUT -d '{"name":"Рабочий ноут"}' .../admin/clients-info/labels/be:ab:bd:ec:70:40
curl -X DELETE .../admin/clients-info/labels/192.168.20.77
```

Метка по MAC переезжает вместе с устройством на другой адрес — но современные
телефоны подставляют случайный MAC на каждую сеть и меняют его при
переподключении, поэтому для них **надёжнее метка по IP при фиксированной
DHCP-резервации**.

Карта кешируется на 60 секунд; запись метки видна сразу. Лизы ищутся в обычных
местах, переопределяются в `daemon.json`:

```json
{"dhcp_lease_files": ["/etc/custom/leases"]}
```

## 10b. Телеметрия хоста

`/admin/memory` описывает **процесс** демона. Когда начинает тормозить сам
роутер, этого мало — `GET /admin/host` описывает **машину**:

```bash
curl -s .../admin/host
curl -s .../admin/host/interfaces
```

На что отвечает:

| Секция | Что говорит |
|---|---|
| `cpu` | `usage_percent` и `per_core_percent` — одно ядро в полке при трёх свободных среднее прячет. `load_1/5/15` достаются от ядра даром |
| `memory` | `used_percent` считается от `available_bytes`, а не от `free_bytes`: роутер держит почти всю память в page cache, и процент от free кричит «занято» при реально свободных 120 МБ |
| `thermal` | все датчики массивом `zones[]` плюс `max_celsius` для одного индикатора. `null`, когда датчиков нет |
| `disk` | `mounts[]` с флагами `read_only` и `holds_state_dir`. `max_used_percent` **игнорирует read-only ФС** — корень squashfs на OpenWrt вечно занят на 100%, а всегда красный индикатор перестают замечать |
| `fd` | открытые дескрипторы демона и лимит, плюс системные. Упереться в любой из них — это «новые соединения не открываются» без единой понятной строки в логе |

**Проценты требуют двух замеров.** `usage_percent` — это дельта между двумя
чтениями `/proc/stat`, поэтому первый запрос после старта отдаёт `null` и
`interval_seconds: 0`: ноль читался бы как «простаивает», а это другое
утверждение. `interval_seconds` говорит, за какое окно посчитан процент —
12.4% за пять секунд и за час значат разное.

**Кеш 500 мс.** Ручку можно опрашивать до 2 раз в секунду — каждый ответ
будет свежим. Чаще смысла нет: вернётся тот же снимок с тем же
`updated_unix`. И помните, что проценты — это дельта между двумя замерами:
более короткое окно делает число **шумнее**, а не точнее, поэтому для гладкого
графика усредняйте на клиенте, а не опрашивайте чаще.

**Счётчики и скорости вместе.** У интерфейсов есть и сырой `rx_bytes`, и
`rx_bytes_per_second`: счётчик переживает рестарты и разрывы, скорость удобна,
но на разрывах врёт. Графики строить по счётчику, читать глазами — скорость.

Отдаются все интерфейсы, включая `lo` и лежачие: «wan лёг» — ровно то, что
нужно увидеть. Фильтрация — задача UI.

**Платформу читать из машиночитаемых полей, а не из строки `os`** — та
человеческая, и её формат задаёт дистрибутив:

| Поле | Пример | Отвечает на |
|---|---|---|
| `os_family` | `linux` | есть ли тут `/proc` (ядро, сисколлы) |
| `os_id` | `openwrt` | есть ли тут `ubus` (дистрибутив) |
| `os_id_like` | `["lede","openwrt"]` | форк чего-то знакомого? |

Разница не теоретическая: роутер RouteRich называет себя `RouteRich`, но
`ID` в `/etc/os-release` у него `openwrt` — сопоставление по человеческой
строке платформу бы не опознало. `os_id_like` нужен для форков, которые ставят
собственный `ID` и называют базу только там. Вне Linux `os_id` — константа
(`macos`, `windows`), а `os_id_like` — пустой массив, не `null`.

**Вне Linux форма ответа та же, недоступные поля — `null`.** На macOS это
термодатчики (нужен CGO) и проценты CPU (Mach API), а память, диски,
дескрипторы и load average работают. Клиент проверяет `null`, а не разбирает
поле `os`.

## 11. Диагностика неисправного демона

Всё ниже идёт через обычный управляющий порт за обычным клиентским
сертификатом — никакого второго, неаутентифицированного debug-порта открывать
не нужно. (Собственный `experimental.debug.listen` ядра как раз такой порт и
поднимает, вообще без аутентификации; на сервере, доступном из сети, им
пользоваться нельзя.)

**Есть ли вообще проблема** — достаточно дёшево, чтобы опрашивать регулярно:

```bash
curl -s .../admin/memory   # горутины и heap во времени говорят об утечках
curl -s .../admin/stats    # uptime ядра, трафик, живые соединения
```

Неуклонно растущие `goroutines` или `heap_inuse_bytes` — подпись утечки.
Смотреть надо на `rss_current_bytes`, а не на `rss_peak_bytes`: пик — это
отметка максимума за всю жизнь процесса, вниз она не возвращается.

**Демон завис** — самый быстрый ответ, причём мгновенный:

```bash
curl -s ".../admin/pprof/goroutine?debug=2" > stacks.txt
```

Все горутины со стеками, ровно как в дампе при панике: то, что застряло, там
видно.

**Демон ест CPU** — эта ручка пишет, поэтому занимает столько, сколько попросишь:

```bash
curl -s ".../admin/pprof/profile?seconds=30" > cpu.pb.gz
go tool pprof -top sing-box cpu.pb.gz
```

**Растёт память** — снять heap дважды с интервалом в час и сравнить:

```bash
curl -s .../admin/pprof/heap > heap-1.pb.gz
# … через час …
curl -s .../admin/pprof/heap > heap-2.pb.gz
go tool pprof -base heap-1.pb.gz sing-box heap-2.pb.gz
```

Учти: `heap`, `allocs`, `goroutine` и `threadcreate` — **снимки**. Рантайм ведёт
их непрерывно, поэтому GET возвращается за миллисекунды и уже покрывает всю
жизнь процесса. Включать заранее ничего не надо, и фонового налога от того, что
эти маршруты доступны, нет.

**Подозрение на конкуренцию за локи** — единственный случай, который нужно
сперва включить, потому что его учёт не бесплатен:

```bash
curl -s -X POST ".../admin/pprof/mutex?fraction=100"
# … дать поработать под нагрузкой …
curl -s .../admin/pprof/mutex > mutex.pb.gz
curl -s -X POST ".../admin/pprof/mutex?fraction=0"     # выключить обратно
```

Аргументом `go tool pprof` указывай тот бинарь, который реально работает —
символизация происходит на твоей машине, потому демон и не отдаёт `/symbol`.
