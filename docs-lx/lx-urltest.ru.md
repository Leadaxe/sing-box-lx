# sing-box-lx — режимы выбора узла в urltest

> EN: [lx-urltest.md](lx-urltest.md) · Фича: [URLTEST_BALANCE](../SPECS/FEATURES/007-URLTEST_BALANCE/FEATURE.md)

Upstream `urltest` всегда выбирает узел с наименьшей задержкой. sing-box-lx добавляет ещё два
режима:

| `mode` | Выбор | Переключение | Что проверяется каждый `interval` |
|---|---|---|---|
| `least_test` (по умолчанию) | самый быстрый | когда другой быстрее на `tolerance` или подключение через текущий не удалось | все узлы |
| `round_robin` | пул живых узлов | соединения раскладываются по пулу | только пул |
| `failover` | самый быстрый на момент выбора | только когда текущий отказал или стал вдвое медленнее остальных; дальше снова самый быстрый | только текущий узел |

Поля `url`, `interval`, `idle_timeout` и `interrupt_exist_connections` работают как в апстриме.
Выбирайте адрес пробы `url`, который узлы не блокируют: узел, не пропускающий его — отказом или
молчанием, — группа считает мёртвым, даже если через него ходит другой трафик, как и апстрим.
Поля `mode` и `balancer` работают в любой сборке; состояние пула для интерфейса (`GetPool`,
[§8](lx-observability.ru.md)) — в сборке с `with_lx_command`.

## 1. Общие поля

| Ключ | Тип | По умолчанию | Значение |
|------|-----|--------------|----------|
| `mode` | string | `least_test` | `least_test` — самый быстрый узел, как в апстриме; `round_robin` — пул; `failover` — держаться за рабочий узел до отказа. `least_connection` — ошибка загрузки: `round_robin` и так распределяет соединения поровну |
| `balancer` | object | — | параметры `round_robin`; с другим `mode` — ошибка старта. Поля — в [§3](#3-round_robin--пул-со-sticky-привязкой) |

## 2. least_test — самый быстрый узел

Каждый `interval` группа проверяет все узлы и переходит на другой, как только он быстрее текущего
больше чем на `tolerance` мс (по умолчанию `50`). Так же работают upstream и группа без `mode`.

Форк добавляет реакцию на отказы. Если подключение через узел упало с ошибкой «путь мёртв» —
таймаут, хост недоступен, отказ в подключении к прокси-узлу, — узел получает штраф, а соединение
один раз открывается через лучший из остальных узлов. Если это удалось, группа переходит на этот
узел, а открытые соединения остаются на месте. Штраф снимается, когда узел снова ответит. У
`direct` и туннелей (WireGuard, AWG, Tailscale) отказ в подключении считается ответом сайта и
штрафа не даёт.

## 3. round_robin — пул со sticky-привязкой

`round_robin` раскладывает соединения по пулу из нескольких живых узлов. Каждый `interval`
проверяется только пул, а не все узлы, поэтому режим подходит для списков из сотен узлов. Узел
выбирается один раз на соединение; UDP/QUIC-сессия остаётся на своём узле. Upstream-поле
`tolerance` здесь не действует, вместо него — `pool_tolerance`; если задан `tolerance`, а
`pool_tolerance` нет, при старте выводится предупреждение.

### Поля `balancer`

| Ключ | Тип | По умолчанию | Значение |
|------|-----|--------------|----------|
| `pool` | int | `3` | сколько узлов в пуле. `0` или опущено — `3`; отрицательное — ошибка. Узлов в пуле не больше, чем в `outbounds` |
| `pool_tolerance` | int (мс) | `0` | `0` — пул заполняется живыми узлами без сравнения задержек, проверка останавливается, найдя `pool` живых и запас `max(⌈pool/2⌉, 1)`; режим для больших списков. `> 0` — проверяются все узлы, в пуле держатся `pool` самых быстрых; узел из пула меняется, только когда узел снаружи быстрее его больше чем на `pool_tolerance` мс |
| `sticky_hash` | string[] | `["process","domain"]` | из чего собирается ключ привязки (см. [Привязка по слот-хешу](#привязка-по-слот-хешу)): `process`, `domain`, `source_ip`, `dest_ip`, `dest_port`. Опущено или `[]` — значение по умолчанию. Отключает привязку только `["none"]` |

> ⚠️ `"sticky_hash": []` не отключает привязку. Декодер конфига sing-box читает пустой массив
> как опущенное поле, то есть как `["process","domain"]`. Отключает привязку `["none"]`; `none`
> вместе с другим компонентом — ошибка.

Число слотов не меняется: слот мёртвого узла остаётся пустым, пока не найдётся живая замена, а
живые узлы остаются в своих слотах. Пока в пуле есть живой узел, новые соединения обходят пустой
слот: его sticky-ключи поровну расходятся по живым узлам и возвращаются, когда слот снова занят;
без привязки ротация идёт по живым. Узел в карантине обходится так же. Отказ соединения запускает
[самовосстановление](#самовосстановление-пула).

Живым или мёртвым узел делает общая история его проверок. Поэтому из ротации до ближайшей
проверки пула (не дольше `interval` плюс время пробы) узел выводят и ручной тест задержки с
коротким таймаутом, который не успел (Clash API `/proxies/{name}/delay`, `URLTestOutbound`), и
неудачное подключение группы `least_test` через тот же узел.

### Привязка по слот-хешу

Ключ потока привязан не к узлу, а к номеру слота: `slot[hash(key) % pool]`. Когда узел в слоте
меняется, замена встаёт в тот же слот. Поэтому ключи остальных слотов остаются на своих узлах, и
их соединения не переоткрываются. При `pool_tolerance > 0` плановая проверка может сменить живой
узел слота на более быстрый — в этом смысл режима; ключи слота переходят к новому узлу.

По умолчанию ключ — процесс и домен назначения. `domain` — домен из исходного запроса, он остаётся
и после того, как роутер разрешил домен в IP. Для доменного трафика держите `domain` в ключе:
`dest_ip` до разрешения пуст, и ключ только из `source_ip`/`dest_ip`/`dest_port` посадит все
такие потоки одного источника на один слот.

### Самовосстановление пула

Пул восстанавливается после сбоя узла, не дожидаясь `interval`.

Плановая проверка обходит узлы раз в `interval`, и на большом списке это долгий процесс: между
двумя проверками часто проходит 10–15 минут. Для живого трафика это слишком редко: узел, умерший
сразу после проверки, получал бы свою долю новых соединений до следующей. Поэтому у группы
`round_robin` есть механизмы восстановления, которые работают от самих соединений. Сбой одного
узла не роняет соединения: то, что не открылось через мёртвый узел, открывается через соседний, а
узел меняется на живой, не дожидаясь проверки. Сайт, закрытый для одного узла, уходит на другой
узел пула, а остальной трафик остаётся на своих узлах по sticky-привязке.

Одна ошибка ничего не решает: молчание, отказ узла или уход клиента дают только повтор через
другой слот, пробу узла и счёт. Узел вычёркивается, только когда промолчал на собственной пробе,
а контрольный узел в той же проверке ответил. Если не ответил никто, вывода нет и пул не
меняется. После вычёркивания слот пуст, пока нет замены, и в него встаёт только узел, ответивший
на свою пробу. Замену ищут среди узлов вне пула, живые узлы пула при этом не трогаются.

Плановая проверка при `pool_tolerance: 0` ищет живых не только на пул, но и на запас
`max(⌈pool/2⌉, 1)` узлов. Узлы запаса трафик не несут, но на замену берутся первыми, поэтому
слот обычно заполняется за доли секунды.

Пока не отвечает никто, проверки становятся реже. Если опрошены все кандидаты и ни один не ответил,
пауза между проверками растёт: 15 → 30 → 60 → 120 с. Любой ответ пробы или сигнал платформы
(пробуждение, смена сети) возвращает её к 15 с, а соединение, открытое во время длинной паузы,
даёт одну внеочередную проверку. На всё ядро одновременно идёт не больше 16 проб
самовосстановления, и узел с одним URL пробы проверяется одной пробой для всех групп.

Если группы `round_robin` вложены друг в друга (одна — `detour` узла другой или её член),
соединение повторяет только внешняя группа, и повторы не умножаются.

Настраивать нечего: поведение включено всегда, ключей конфига нет.

#### Что видит приложение при сбое узла

| Что случилось | Что делает группа | Что видит приложение |
|---|---|---|
| Узел пула умер между проверками: процесс сервера остановлен, машина недоступна | Соединение, не открывшееся через узел, повторяется через другой слот, узел получает пробу. Промолчал при ответившем контроле — вычёркивается, при отказе в подключении меньше чем за секунду; слот получает замену | Ни одного упавшего соединения. Если недоступна машина, а не процесс, первое соединение ждёт отказа и идёт в повтор; с пятой секунды ожидания новые соединения обходят слот |
| Узел принимает соединение и молчит | Через 5 с новые соединения обходят его слот, узел получает пробу. Примерно через 41 с от начала молчания узел вычёркивается и заменяется. Соединения, ещё открывающиеся через него, повторяются через другой узел; открытые соединения, ждущие первого байта, закрываются | Соединения, попавшие в узел за первые 5 с, теряются; закрытое соединение приложение повторяет |
| Сайт недоступен через один узел: гео-ограничение, сайт не пускает адрес узла | Явный отказ от узла или сайта — соединение сразу повторяется через другой слот, и сайт переходит на следующий слот. Обрыв без кода или молчание сайта дольше 15 с — сайт переходит со второго такого случая на том же узле, если между ними узел отвечал другим сайтам. Ответ SOCKS «general failure» и уход клиента до ответа сайт не переносят. Остальные сайты остаются на своих узлах | При явном отказе — ничего; иначе первый запрос может упасть (см. ограничения), следующие идут через другой узел |
| Узел отвечает на пробу, но рвёт заметную долю соединений | Узел с долей отказов от 5 % и больше удвоенной медианы пула уходит в карантин: его слот обходится и получает замену до следующей плановой проверки или смены сети. Так же в карантин уходит узел, вычеркнутый дважды между плановыми проверками. Плановая проверка карантинные узлы пробует всегда | Меньше упавших соединений |
| Пропала своя сеть: сон устройства, смена Wi-Fi или мобильной сети, обрыв у провайдера | По пробам группа «сеть лежит» не выводит: раз не ответил никто, никто и не вычёркивается. Пробуждение, смена сети или скачок часов больше 10 с замораживают группу на 15 с: повтор через другой слот работает, выводов и записей нет | После возврата сети пул тот же, что до обрыва |

Где это заметно:

- пул с редкой проверкой (`interval` от 10 минут) — сервер, упавший между проверками, не забирает
  свою долю соединений до следующей проверки, а заменяется сразу;
- сайт, закрытый для одного узла (например, по гео-признаку), открывается через другой и
  сохраняет выбор;
- телефоны и ноутбуки — после сна и смены сети пул не теряют.

Ограничения:

- Так восстанавливается только `mode: round_robin`. У `least_test` и `failover` остаются штраф и
  запасное подключение по ошибкам «путь мёртв» ([§2](#2-least_test--самый-быстрый-узел)).
- Первый запрос к сайту, закрытому для узла без явного отказа, может упасть. Через VLESS, Trojan,
  VMess и Shadowsocks такой отказ виден только после открытия соединения, поэтому группа его не
  повторяет — повторяет приложение, а сайт переходит на другой узел со второго отказа.
- На узлах, которые массово закрывают соединения без ответа, сайты изредка переезжают лишний раз.
- Узел, который на половину проб отвечает дольше 15 с, вычёркивается как молчащий.
- Если запас вычеркнут или пуст, в большой группе с маленьким пулом поиск замены может занять
  минуты.
- Сайт остаётся на новом слоте до перезапуска ядра. Таблица держит 1024 ключа, при переполнении
  вытесняется самый старый. Сайт, закрытый через все узлы пула, возвращается на свой слот до
  следующей проверки или смены сети.
- Без sticky-привязки (`sticky_hash: ["none"]`) сайты не сдвигаются; мёртвые и карантинные узлы
  обходятся и так.
- UDP покрыт частично: неоткрывшийся поток повторяется, мёртвый узел вычёркивается и для UDP, но
  отказы UDP не сдвигают ключи и не идут в счёт карантина.
- Смена сети, о которой платформа не сообщила (в том числе Modern Standby на Windows), может один
  раз вычеркнуть живой узел. Он возвращается сам на ближайшей замене или проверке.
- На открытии каждого соединения есть небольшая добавочная работа. Скорость загрузки и отдачи —
  на уровне сборки без самовосстановления; разница видна только в синтетическом прогоне из тысяч
  очень коротких соединений подряд ([замеры](../SPECS/TASKS/138-URLTEST_RR_SKIP_DEAD_SLOT/IMPLEMENTATION_REPORT.md)).

Состояние показывает `sing-box api group pool <tag>` (сборка с `with_lx_command`): таблица слотов
со `STATE` (`live`/`dead`/`quarantined`), `CONNECTIONS` и `FAILURES`, а также сдвинутые ключи,
проблемы в адресе и заморозка:

- `quarantined` — узел рвёт соединения чаще остальных или дважды вычеркнут; новые соединения его обходят до следующей
  проверки или смены сети;
- сдвинутый ключ — сайт, закрытый для своего узла, переведён на следующий узел пула;
- проблема в адресе — сайт не открылся ни через один узел пула и вернулся на свой узел до
  следующей проверки или смены сети;
- заморозка — 15 с после пробуждения устройства, смены сети или скачка часов группа не делает
  выводов; повтор через другой слот работает.

То же несёт `GetPool` демона: по слоту `quarantined`, `connections` и `confirmedFailures`, по
группе `shiftedKeys`, `markedKeys`, `frozen` и `frozenSeconds`. В libbox поля группы приходят
через `GetPoolState` ([§8](lx-observability.ru.md)). Список соединений
показывает узел, через который соединение пошло, в том числе после повтора. Все правила — в
[SPEC 138](../SPECS/TASKS/138-URLTEST_RR_SKIP_DEAD_SLOT/SPEC.md), точные определения и константы —
в [ALGORITHM.md](../SPECS/TASKS/138-URLTEST_RR_SKIP_DEAD_SLOT/ALGORITHM.md).

### Пример — urltest с round_robin

```jsonc
{
  "type": "urltest",
  "tag": "auto",
  "outbounds": ["proxy-a", "proxy-b", "proxy-c", "proxy-d", "proxy-e"],
  "interval": "15m",
  "mode": "round_robin",
  "balancer": {
    "pool": 3,
    "pool_tolerance": 0,
    "sticky_hash": ["process", "domain"]   // ["none"] чтобы отключить sticky-привязку
  }
}
```

Для большого списка узлов меньше всего проверок даёт `pool_tolerance: 0`, небольшой `pool` и
`interval` побольше.

Статус: равномерная ротация проверена локально (10/10/10 с выключенной sticky-привязкой) и на
устройстве, на реальном пуле из нескольких узлов. Равномерность по доменам на устройстве — 0.95+.

📖 [Справочник полей](../docs/configuration/outbound/urltest.md): каждое поле и компоненты ключа
привязки.

## 4. failover — держаться до отказа

**Выбор.** Группа берёт самый быстрый узел на момент выбора, без `tolerance`; порядок в списке
`outbounds` роли не играет.

**Удержание.** Пока узел работает, группа остаётся на нём, даже если другой стал быстрее. Каждый
`interval` проверяется только этот узел: одна проба вместо проверки всех.

**Деградация.** Если узел ответил больше чем вдвое медленнее самого быстрого из остальных узлов
той же сети (по их последней задержке), он сразу проверяется ещё раз. Если снова больше 2×,
группа проверяет все узлы и переходит на самый быстрый, только если тот больше чем в 1,5 раза
быстрее; иначе остаётся: просела сеть, а не узел. Ключа конфига нет.

**Отказ.** Два вида:

- узел не ответил на пробу → группа проверяет все узлы и переходит на самый быстрый живой;
- подключение через узел упало с ошибкой «путь мёртв» → штраф и одно запасное подключение, как в
  [least_test](#2-least_test--самый-быстрый-узел); группа переходит на запасной узел, открытые
  соединения остаются на месте.

После перехода группа держится за новый узел.

**Ручной тест.** Тест группы из UI, CLI (`sing-box api group urltest <tag>`) или Clash API
проверяет все узлы и выбирает самый быстрый. Только так группа возвращается на самый быстрый
узел, пока текущий жив.

**Что не действует.** `tolerance` игнорируется, при старте выводится предупреждение. `balancer`
даёт ошибку старта.

В UI задержки невыбранных узлов показаны на момент последней проверки всех узлов.

### Пример — urltest с failover

```jsonc
{
  "type": "urltest",
  "tag": "auto",
  "outbounds": ["proxy-a", "proxy-b", "proxy-c", "proxy-d", "proxy-e"],
  "url": "https://www.gstatic.com/generate_204",
  "interval": "15m",
  "mode": "failover"
  // tolerance не задаётся: переключений «по скорости» нет (ненулевое значение — предупреждение)
  // balancer не задаётся: с failover это ошибка старта
}
```

Когда выбирать: держаться за один рабочий узел важнее, чем всегда быть на самом быстром, —
например, мобильные профили. Сколько проб это экономит — в [lx-energy.ru.md §6](lx-energy.ru.md#6-пробы-urltest-будят-спящих-поэтому-их-ограничивают-пять-механизмов).

## 5. Сравнение и выбор режима

| Что важнее | Режим |
|---|---|
| минимум переключений и одна проба в `interval` | `failover` |
| распределение нагрузки по нескольким узлам | `round_robin` |
| всегда самый быстрый узел ценой проверки всех узлов | `least_test` |

По энергии: `least_test` будит все узлы каждый `interval`, `round_robin` — только пул (при
`pool_tolerance: 0`), `failover` — один узел; подробнее в [lx-energy.ru.md §6](lx-energy.ru.md#6-пробы-urltest-будят-спящих-поэтому-их-ограничивают-пять-механизмов).
