# Протоколы семейства Xray — как они устроены и как поддержаны в sing-box-lx

> 🌐 English version: **[lx-protocols-explained.md](lx-protocols-explained.md)**.

Современный стек VPN-протоколов, устойчивых к посредникам, задаёт Xray:
REALITY, Vision, XHTTP и постквантовый слой VLESS `encryption`
(`mlkem768x25519plus`) придуманы и развиваются там, а серверы в подписках —
это серверы Xray. Ванильный sing-box покрывает этот стек частично и с
отставанием: чего-то нет вовсе, что-то есть, но против актуального
Xray-сервера уже не работает. `sing-box-lx` закрывает этот зазор на
клиентской стороне.

Документ отвечает на три вопроса по каждому протоколу: **как он устроен** —
зачем существует, что делает с байтами на проводе и почему именно так;
**как сделана его поддержка в форке** — где живёт код и какие решения
приняты; **чем это отличается от ванильного sing-box** — сводная таблица
в [§7](#7-отличия-от-ванильного-sing-box). Там же — почему базовый движок
всё-таки sing-box, а не сам Xray ([§7.1](#71-почему-база--sing-box-а-не-xray)).
Поля, дефолты и тексты ошибок здесь не перечисляются — для этого есть
[lx-config.ru.md](lx-config.ru.md) (обзор по фичам) и
[lx-protocols-transports.ru.md](lx-protocols-transports.ru.md) (справочник
параметров). Текущее состояние каждой области — в спеках фич:
[017-REALITY](../SPECS/FEATURES/017-REALITY/FEATURE.md),
[002-XHTTP](../SPECS/FEATURES/002-XHTTP/FEATURE.md),
[012-VLESS_ENCRYPTION](../SPECS/FEATURES/012-VLESS_ENCRYPTION/FEATURE.md).

Для кого: разработчик ядра или клиента, который впервые открывает
`common/tls/reality_client.go`, `transport/v2rayxhttp/` или
`protocol/vless/encryption/` и хочет понимать, что читает. Знание TLS на
уровне «есть ClientHello, есть сертификат» предполагается.

Врезки в тексте помечены по типу:

- ⚠️ — ловушка: то, что ломается молча и не объясняет себя;
- 🔀 — отличие от ванильного sing-box;
- 🧭 — итог, который стоит запомнить, если не читать раздел целиком;
- 📖 — нормативный источник.

# 0. Картина целиком: слои и угрозы

Одно исходящее соединение VLESS в ядре проходит через стопку слоёв. Сверху
вниз, от данных приложения к сети:

```
данные приложения (чаще всего — чужой TLS к целевому сайту)
        │
        ▼
VLESS ─── flow: xtls-rprx-vision        (§3)  убирает двойное шифрование
   └── encryption: mlkem768x25519plus   (§5)  постквантовое шифрование нагрузки
        │
        ▼
transport ── tcp (нет блока) / ws / grpc / httpupgrade / xhttp   (§4)
        │
        ▼
tls ── std / utls (отпечаток) / reality                           (§1, §2)
        │
        ▼
TCP или QUIC → сеть
```

Каждый слой отвечает на своего посредника. Посредников три, и они разные:

| Посредник | Как действует | Какой слой отвечает |
|---|---|---|
| **Пассивный классификатор** (DPI) смотрит на форму трафика: длины пакетов, ритм, SNI, набор шифров в ClientHello, характерные последовательности | Сетевое оборудование на пути, в реальном времени | отпечаток uTLS (§1), Vision (§3), XHTTP (§4), паддинг везде |
| **Активная проверка сервера** подключается к серверу сама и смотрит, что тот ответит | По списку адресов, выделенных классификатором | REALITY (§2) |
| **Запись трафика с расшифровкой в будущем** квантовым компьютером | Кто угодно с большим диском | VLESS `encryption` (§5), гибридный key share в TLS (§1.3) |

> 🧭 **Запомнить:** REALITY и VLESS `encryption` **не заменяют друг
> друга**. REALITY отвечает за то, чтобы сервер вообще принял соединение и чтобы
> проверяющий ничего не нашёл. `encryption` отвечает за то, чтобы записанный
> трафик нельзя было вскрыть потом. Общий у них только математический
> примитив ML-KEM-768 + X25519.

# 1. Фундамент: TLS, ClientHello и отпечаток

## 1.1 Что видно в ClientHello

TLS 1.3 шифрует почти всё, кроме первого сообщения клиента. ClientHello идёт
открытым текстом и несёт:

- **SNI** — имя сервера, к которому клиент хочет подключиться;
- **список шифров** и **расширений** в определённом порядке;
- **supported_groups** — какие кривые клиент умеет для обмена ключами;
- **key_share** — публичные половинки для одной или нескольких из этих
  групп, чтобы сервер мог ответить сразу;
- **session id** — 32 байта, в TLS 1.3 не несут смысла и заполняются
  случайно ради совместимости с TLS 1.2;
- **random** — 32 случайных байта.

Для DPI это визитная карточка. Набор и порядок полей у каждой библиотеки
свой, и по нему отличают Chrome от Firefox, а Go-программу от любого
браузера.

## 1.2 Отпечаток и uTLS

Стандартная `crypto/tls` Go шлёт ClientHello, который не похож ни на один
браузер. Библиотека uTLS умеет собирать приветствие по пресету: `chrome`,
`firefox`, `safari`, `edge`, `ios` и так далее. Ключ `tls.utls.fingerprint`
выбирает пресет.

> ⚠️ Ядро **не подменяет** отпечаток молча ни при каких условиях: что
> попросили, то и ушло (правило фичи [017](../SPECS/FEATURES/017-REALITY/FEATURE.md)).
> Узел с пресетом без гибридного шара на новом Xray-сервере умирает у нас
> так же, как у самого Xray-клиента, и это не дефект ядра (§1.3, §2.6).

У нас uTLS — форк-сабмодуль `Leadaxe/utls-lx` поверх `metacubex/utls`. Форк
нужен из-за §1.3: два из трёх пресетов с гибридным key share принесены нами.

## 1.3 Гибридный key share и размер приветствия

С 2024 года браузеры шлют в `key_share` две записи: классическую X25519 и
гибридную **X25519MLKEM768**, где к 32 байтам X25519 приписано 1184 байта
публичного ключа ML-KEM-768 (о нём §5.2). Цель — постквантовая защита
обмена ключами самого TLS.

Для устойчивости к посредникам это имеет два следствия.

1. **Отпечаток без гибрида больше не похож на браузер.** Пресеты `edge`,
   `ios`, `android`, `360`, `qq` несут только X25519 — таких приветствий
   живые браузеры уже не шлют. Гибрид есть у `chrome`, `firefox`, `safari`.
2. **Приветствие выросло втрое**: у `chrome` 1720 байт вместо 594. Оно не
   влезает в один TCP-сегмент и уходит двумя. Некоторые сети второй сегмент
   теряют, и рукопожатие никогда не завершается.

> 🔀 **Только в sing-box-lx:** по-узловой ключ `tls.reality.key_share` ([SPEC 089](../SPECS/TASKS/089-REALITY_KEY_SHARE_OPTION/SPEC.md)): `classical`
> вырезает гибрид и возвращает односегментное приветствие, `hybrid` требует
> гибрид и падает с понятной ошибкой на пресете, где его нет, пустое значение
> оставляет то, что несёт отпечаток. Зачем это нужно именно для REALITY —
> в §2.6.

## 1.4 Фрагментация

Цель фрагментации — не дать классификатору увидеть SNI одним куском.
Оборудование, которое сопоставляет открытый текст с шаблоном, обычно смотрит
на каждый пакет по отдельности и не собирает TCP-поток; если имя сервера
разрезано между пакетами, шаблон не срабатывает.

**Как это сделано в Xray: вручную.** Фрагментация — свойство outbound-а
`freedom` (`settings.fragment`) или элемента `finalmask.tcp`. Пользователь
задаёт три числа: какие пакеты резать (`packets: "tlshello"` или диапазон
номеров), на куски какой длины (`length: "100-200"`) и с какой паузой между
кусками (`interval` / `delay: "10-20"` мс), в новой форме ещё `maxSplit`.
Длины берутся случайно из диапазона **без оглядки на содержимое**: куда
попадёт граница относительно SNI — дело случая, и при неудачном диапазоне
имя может целиком уйти в один кусок. Паузы фиксированные: слишком короткая
— ядро ОС склеит куски обратно в один сегмент, слишком длинная — каждое
рукопожатие тормозит. Подбор под конкретную сеть идёт перебором.

**Как это сделано в sing-box: по содержимому.** Пакет
`common/tlsfragment` (апстримный, с 1.12) разбирает первый пакет как
ClientHello и находит в нём расширение SNI. Имя сервера делится на метки
без публичного суффикса (для `www.example.com` это `www` и `example`), и
**внутри каждой метки** выбирается случайная точка разреза. Так ни один
кусок не содержит имя целиком и даже ни одну значимую метку целиком, в
какой бы сети это ни работало. Ручных длин нет: границы определяет
структура приветствия.

Дальше два режима, их можно включать по отдельности или вместе:

- **`tls.fragment`** — каждый кусок уходит отдельным TCP-сегментом с
  выключенным алгоритмом Нейгла. После каждого сегмента ядро **ждёт
  подтверждения ACK** от сервера, читая состояние сокета (`TCP_INFO` на
  Linux, аналоги на Apple и Windows), и только потом шлёт следующий. Это
  гарантирует, что куски не склеятся ни в ядре ОС, ни на пути, и при этом
  пауза ровно такая, какая нужна сети, а не выбранная наугад. Если ACK
  пришёл быстрее 20 мс, цель считается локальной или прозрачным прокси, и
  ядро переходит на фиксированную паузу `fragment_fallback_delay` (по
  умолчанию 500 мс); то же на платформах без доступа к состоянию сокета.
  Цена — задержка на столько круговых обходов, сколько получилось кусков,
  поэтому апстрим советует включать режим только для имён, про которые
  известно, что они фильтруются.
- **`tls.record_fragment`** — те же точки разреза, но каждый кусок
  оборачивается в **собственную TLS-запись** с заголовком, и все записи
  уходят одной TCP-записью. Пакет один, пауз нет, задержки нет. Работает
  против классификатора, который разбирает TLS-записи по одной и ждёт
  SNI в первой; не работает против того, кто собирает поток. Это первое,
  что стоит пробовать.

Оба режима трогают только первый пакет соединения; трафик после
рукопожатия не меняется. У Xray аналога `record_fragment` как отдельного
режима нет: нарезка на TLS-записи получается лишь побочно, когда граница
куска совпала с границей записи.

### Вложенные протоколы: почему ClientHello теряется и что делает ядро

Отдельный случай, ради которого фрагментация в `sing-box-lx` включается
сама. Когда один протокол заворачивается в другой — outbound диалит через
`detour`, звено `chain` ходит через предыдущее звено, VLESS едет внутри
WireGuard или MASQUE — наш ClientHello уходит **внутри** чужого туннеля.
Нижнее плечо пересылает его дальше от своего имени, и у пути за тем
сервером свой MTU, обычно меньше, чем у нас, потому что туннель съел часть
кадра своими заголовками.

Пока первый пакет маленький, это незаметно. Гибридный ClientHello после
[SPEC 083](../SPECS/TASKS/083-REALITY_MLKEM_KEYSHARE/SPEC.md) весит
1,5–1,9 КБ и уходит двумя TCP-сегментами; на части нижних плеч он уже не
помещается. ICMP *Fragmentation Needed* от промежуточного маршрутизатора
до нас не доходит — он адресован серверу нижнего плеча, а не клиенту
внутри туннеля. Пакет просто исчезает. Снаружи это `tls handshake: EOF`
через 12–17 секунд без единой подсказки; воспроизводится голым `curl` через
то же плечо, то есть причина в пути, а не в ядре.

> 🧭 **Запомнить:** обойти это нельзя ничем, кроме фрагментации первой записи, потому что
> именно в ClientHello лежит всё, без чего вложенное соединение не
> установить: SNI, по которому сервер выбирает сертификат, `key_share`,
> без которого не вывести ключи, и, как показано в §2.3, секрет REALITY в
> session id. Урезать приветствие тоже нельзя: отпечаток браузера (§1.2) и
> требование гибридного шара (§2.6) задают его размер.

> 🔀 **В ванильном sing-box такой механики нет.** Там `fragment` и
> `record_fragment` — ручные ключи, и ядро не знает, что outbound диалит
> через другой outbound: ClientHello под `detour` уходит целиком, как и
> напрямую, и на плече с меньшим MTU соединение молча не поднимается.
> Пользователь должен сам догадаться, что дело в размере первого пакета, и
> сам включить фрагментацию на каждом узле, который ходит через туннель.
> К REALITY-узлам в ванили это не поможет даже вручную — см. ниже про
> [SPEC 088](../SPECS/TASKS/088-REALITY_FRAGMENT_BYPASS/SPEC.md).

Поэтому `sing-box-lx` делает это сам
([SPEC 060](../SPECS/TASKS/060-TLS_FRAGMENT_AUTO_ON_DETOUR/SPEC.md),
обзор — [lx-config §9](lx-config.ru.md#9-автоматическая-фрагментация-clienthello-под-detour-spec-060)):

- При сборке TLS-клиента outbound получает признак «диалю через detour».
  Если он стоит, а пользователь не задал ни `fragment`, ни
  `record_fragment`, ядро включает **`record_fragment`**
  (`applyDetourFragmentDefault` в `common/tls/client.go`). Выбран именно
  он: разрез по TLS-записям без пауз, и каждая запись заведомо меньше
  любого разумного MTU. Замер через сломанное плечо: без фрагментации
  отказ за 12 с, `fragment` — 0,6 с, `record_fragment` — 0,1 с.
- Дефолт применяется **до** того, как опции увидит конкретный движок,
  поэтому стандартный клиент, uTLS и REALITY получают его одинаково.
  Для REALITY это заработало только с
  [SPEC 088](../SPECS/TASKS/088-REALITY_FRAGMENT_BYPASS/SPEC.md): до неё
  REALITY-клиент строил uTLS-соединение на голом сокете, и фрагментация,
  включая явную, на нём молча не действовала. Апстрим sing-box так и живёт.
- **Явное значение в конфиге всегда сильнее.** `fragment: true` не
  апгрейдится до `record_fragment`: если выбран разрез по пакетам, это
  остаётся выбором пользователя.
- **Только рукопожатие.** Трафик после него не трогается, постоянного
  налога на туннель нет.
- **`h3`/QUIC не затронут**: там нет TLS поверх TCP, а QUIC сам держит
  Initial ниже порога.
- **Вложенные цепочки покрыты автоматически**: у каждого звена
  [`chain`](../SPECS/FEATURES/015-CHAIN/FEATURE.md) свой `detour`, у
  [MASQUE](../SPECS/FEATURES/009-MASQUE_WARP/FEATURE.md) по `h2` через
  detour — тот же путь.

> ⚠️ **Известное ограничение:** явный `"record_fragment": false` неотличим от
> «не задано», поэтому под `detour` дефолт всё равно включится. Способа
> диалить через detour вообще без фрагментации сейчас нет; чтобы сменить
> режим, ставят `"fragment": true`. Задача живёт в реестре
> [004-HOTFIXES](../SPECS/FEATURES/004-HOTFIXES/FEATURE.md): это заплатка на
> поведение пути, не фича протокола, и у неё есть условие снятия.

Поможет ли фрагментация в сети, которая теряет большой первый пакет
**без** туннеля, — свойство той сети; второй рычаг там —
`key_share: classical` (§1.3).

## 1.5 Пример: Xray и sing-box-lx

Обычный VLESS + TLS на голом TCP, без REALITY: отпечаток браузера, ALPN и
фрагментация ClientHello. У Xray фрагментация существует в двух формах,
и обе сводятся у нас к одному блоку `tls`.

Xray, новая форма (`finalmask`, Xray ≥ 25.x):

```jsonc

  "settings": {
    "vnext": [{
      "address": "example.com",

    "network": "tcp",
    "security": "tls",
    "tlsSettings": {
      "serverName": "example.com",
      "fingerprint": "chrome",
      "alpn": ["h2", "http/1.1"],
      "allowInsecure": false
    },
    "finalmask": {
      "tcp": [{
        "type": "fragment",
        "settings": { "packets": "tlshello", "length": "20-40", "delay": "3-10", "maxSplit": "3-6" }

    }
  }
}
```

ходит через `sockopt.dialerProxy`):

```jsonc

    "protocol": "vless",

      "network": "tcp",

      "tlsSettings": { "serverName": "example.com", "fingerprint": "chrome" },

```

sing-box-lx — один outbound для обеих форм:


# 2. REALITY

## 2.1 Какую проблему решает

Классический VLESS + TLS требует домен и сертификат на самом сервере. Это
даёт посреднику три зацепки:

- в сертификате виден свежий домен, выписанный на дешёвый VPS;
- SNI в ClientHello сопоставляется с IP-адресом, и адрес попадает в список;
- активная проверка: посредник сам подключается, получает сертификат и
  видит пустой сайт-заглушку.

ECH закрыл бы первые две зацепки, но ECH нужен DNS-записью и поддержкой у
сервера, а третью он не закрывает вовсе.

## 2.2 Идея: чужой сайт как прикрытие

REALITY (RPRX, Xray 1.8, 2023) убирает сертификат с сервера. Сервер
притворяется чужим большим сайтом — в Xray это `dest` и `serverNames`,
например `www.microsoft.com`. Любой, кто подключается и не предъявил
секрет, получает **настоящий** TLS-ответ этого сайта: сервер просто
пробрасывает байты туда и обратно. Для проверяющего сервер неотличим от
прокси перед Microsoft.

Свой клиент предъявляет секрет так, чтобы снаружи ClientHello оставался
обычным браузерным приветствием к этому же сайту.

## 2.3 Как сервер узнаёт своих: session id

Секрет прячется в поле **session id** ClientHello — те самые 32 байта,
которые в TLS 1.3 всё равно случайны. Клиент (`common/tls/reality_client.go`)
собирает их так:

```
байты  0..2   версия клиента REALITY (у нас 26.3.27)
байт   3      резерв
байты  4..7   unix-время, секунды
байты  8..15  short_id (8 байт из конфига)
байты 16..31  тег AES-GCM
```

Первые 16 байт шифруются AES-GCM. Ключ выводится так:

1. Клиент берёт **эфемерную** X25519-пару, которую uTLS уже сгенерировал для
   `key_share` этого приветствия. Отдельного ключа нет: тот же публичный
   ключ, что уходит в `key_share`, сервер использует и для TLS, и для
   проверки секрета.
2. ECDH этого приватного ключа с `tls.reality.public_key` сервера даёт
   общий секрет.
3. HKDF-SHA256 с солью `random[0..20]` и меткой `REALITY` превращает его в
   `AuthKey`.
4. AES-GCM с ключом `AuthKey`, nonce `random[20..32]` и всем сырым
   ClientHello как associated data запечатывает 16 байт в 32.

Снаружи session id по-прежнему выглядит случайным. Сервер, зная свой
приватный ключ и публичный из `key_share`, повторяет шаги 2–4, расшифровывает
блок и проверяет: версия не ниже `minClientVer`, время в допуске
`maxTimeDiff`, `short_id` в списке.

## 2.4 Два исхода рукопожатия

```
ClientHello ──► сервер REALITY
                   │
         session id расшифровался, время и short_id сошлись?
                   │
        ┌── да ────┴──── нет ───┐
        ▼                       ▼
  сервер сам завершает     сервер пробрасывает всё
  TLS временным            на dest; клиент говорит
  сертификатом под         с настоящим сайтом
  AuthKey (§2.5)           и получает настоящие
        │                  страницы
        ▼                       │
  прокси-соединение             ▼
                        «reality verification failed»
```

> ⚠️ Правый исход — главное свойство REALITY и одновременно его главная ловушка
> для диагностики. Сервер **никогда не сообщает**, почему отверг клиента:
> протухшие часы, не тот `short_id`, устаревшая версия, неподходящий
> `key_share` — всё заканчивается одинаково, страницей чужого сайта. Для
> клиента это выглядит как ошибка проверки сертификата.

## 2.5 Как клиент проверяет сервер

Свой сервер отвечает временным сертификатом с публичным ключом ed25519.
Подпись этого сертификата — не настоящая подпись, а `HMAC-SHA512(AuthKey,
публичный ключ)`. Обычный TLS-клиент такой сертификат отверг бы, но обычный
клиент сюда не попадёт: он не знает `AuthKey`.

Наш клиент в `VerifyPeerCertificate` (`realityVerifier`) делает две вещи:

1. Если первый сертификат в цепочке ed25519 и его подпись совпадает с
   HMAC — это свой сервер, соединение помечается `verified`.
2. Иначе цепочка проверяется как обычная, по SNI. Если она **валидна** —
   значит, клиент разговаривает с настоящим сайтом-прикрытием: сервер его
   отверг (или между ними кто-то стоит). Прокси-данные в такое соединение не
   уходят; наружу это та самая `reality verification failed`.

Чтобы отвергнутый клиент не выделялся на фоне браузеров, Xray-клиент после
этого ходит по сайту-прикрытию (spider). У нас этот обход есть в упрощённом
виде: один GET с User-Agent отпечатка и случайной cookie; полноценный
`spiderX` намеренно не реализован.

## 2.6 Что в нашем ядре иначе, чем в апстриме

> 🔀 **В ванили иначе.** Сервер REALITY развивается вместе с Xray и
> периодически ужесточает, какое приветствие он считает своим. Апстрим
> sing-box за этим не успевает, и узлы из подписок уходят на сайт-прикрытие
> молча.

Фича 017 держит клиентскую сторону совместимой:

- **Гибридный key share обязателен для Xray ≥ v26.9.8** ([SPEC 083](../SPECS/TASKS/083-REALITY_MLKEM_KEYSHARE/SPEC.md)).
  Коммит `XTLS/REALITY@8cdf7bf` отвергает ClientHello без
  `X25519MLKEM768` перед `X25519`. Апстрим sing-box сам вырезал этот шар
  из приветствия (костыль под старый uTLS), поэтому каждый его узел на новом
  сервере умирает. Мы шлём то, что несёт пресет, и считаем `AuthKey` по
  **тому же ключу, что выберет сервер**: чистый X25519, если он есть в
  `key_share`, иначе X25519-часть гибрида. Порядок выбора повторяет
  серверный код Xray.
- **Гибрид стоит перед классическим и ровно один раз** в `key_share` и
  `supported_groups` — правило приёма сервера; страж-тест держит его для всех
  трёх пресетов.
- **Версия клиента** в session id — ровно требуемый минимум ([SPEC 053](../SPECS/TASKS/053-REALITY_MIN_CLIENT_VER/SPEC.md));
  сервер с `minClientVer` отсекает клиентов ниже порога.
- **`key_share: classical | hybrid`** ([SPEC 089](../SPECS/TASKS/089-REALITY_KEY_SHARE_OPTION/SPEC.md), §1.3) — для сетей, которые
  теряют двухсегментное приветствие. Классика работает только с Xray
  < v26.9.8; автофолбэка между режимами нет, потому что отказ сервера от
  потери в сети не отличим без второй попытки, а сеть после потери
  ~минуту не пропускает соединения к тому же адресу.
- **Фрагментация действует и на REALITY** ([SPEC 088](../SPECS/TASKS/088-REALITY_FRAGMENT_BYPASS/SPEC.md)).

Вне фичи: постквантовые **подписи** сертификата REALITY (`mldsa65Seed` /
`mldsa65Verify` в Xray) и `spiderX`. Конфиг с такими полями ядро не
принимает.

## 2.7 Типичные отказы

| Симптом | Причина |
|---|---|
| `reality verification failed` на всех узлах одной подписки | Сервер обновился до Xray ≥ v26.9.8, а клиент шлёт приветствие без гибрида: пресет `edge`/`ios`/`android` или `key_share: classical` |
| То же на одном узле, остальные живы | Не тот `short_id` или `public_key`; часы клиента ушли больше `maxTimeDiff` |
| Рукопожатие висит до таймаута, ошибки нет | Сеть потеряла второй сегмент гибридного ClientHello. Лечится `key_share: classical` (старый сервер) или `record_fragment` / `detour` (новый) |
| Работает на Wi-Fi, не работает в мобильной сети | Та же потеря сегмента; мобильные сети режут чаще |

# 3. Vision

## 3.1 Проблема TLS-в-TLS

Почти весь трафик пользователя и так зашифрован TLS. Внутри туннеля VLESS
поверх TLS или REALITY получается TLS внутри TLS. Снаружи это обычное
TLS-соединение, в котором первые записи после рукопожатия повторяют
**форму** второго рукопожатия: ClientHello, ServerHello с сертификатом,
Finished. Их длины и ритм характерны, и DPI их узнаёт, не расшифровывая
ничего.

Первые поколения XTLS (`xtls-rprx-origin`, `direct`, `splice`) решали это
радикально: после того как внутренний TLS установился, внешнее шифрование
отключалось вовсе, и внутренние записи шли по проводу как есть. Скорость
была отличная, но снаружи стали видны настоящие длины внутренних записей,
и в 2022 году эту схему научились отличать. RPRX её закрыл.

## 3.2 Как работает Vision

Поток `flow: xtls-rprx-vision` делает то же самое аккуратнее. Реализация —
в `sing-vmess`, апстримной зависимости; у нас своего кода Vision нет.

1. **Паддинг рукопожатия.** Первые пакеты соединения, где внутри идёт
   чужое TLS-рукопожатие, Vision дополняет до случайной длины. Снаружи
   ClientHello, сертификат и Finished внутреннего соединения не
   различимы.
2. **Прямой проброс после рукопожатия.** Как только Vision увидел, что
   внутренний TLS 1.3 установился, он перестаёт перешифровывать его
   записи вторым слоем. Внешнее соединение продолжает жить, но данные
   внутри него уходят напрямую в нижний слой. Для этого Vision нужен
   доступ к «сырому» соединению под внешним TLS — отсюда ограничения §3.3.
3. **Splice на сервере.** Сервер делает то же в обратную сторону и на
   Linux отдаёт копирование ядру ОС. Процессор почти не тратится.

> 🧭 **Итог:** скорость выше, чем у двойного шифрования, и отпечатка TLS-в-TLS нет.

## 3.3 С чем Vision сочетается

Vision нужно соединение, которое он умеет распаковать до сырого слоя.
`sing-vmess` держит реестр таких типов (`tlsRegistry`):

- стандартный `tls.Conn`, uTLS и REALITY поверх **голого TCP** — да;
- WebSocket, gRPC, HTTPUpgrade, XHTTP поверх TLS — **нет**: между Vision и
  сырым слоем стоит транспорт, пробрасывать некуда. С такими узлами `flow`
  должен быть пуст;
- **VLESS `encryption` поверх любого транспорта — да** ([SPEC 105](../SPECS/TASKS/105-VISION_OVER_VLESS_ENCRYPTION/SPEC.md)). Слой
  шифрования (`*encryption.CommonConn`) играет для Vision роль «TLS»: он
  зарегистрирован в том же реестре через `go:linkname`, и прямой проброс
  идёт в соединение под шифрованием. Это повторяет Xray, где для Vision
  поверх `encryption` транспорт любой, включая XHTTP.

Vision бессмыслен для трафика, который сам не зашифрован: такие соединения
просто остаются под внешним слоем целиком.

# 4. XHTTP

## 4.1 Зачем нужен ещё один HTTP-транспорт

Транспорт решает, как байты прокси-соединения упаковать в сеть. Когда IP
сервера напрямую недоступен, единственный путь — через посредника: CDN или
обратный прокси. Посредник понимает только HTTP, поэтому туннель должен выглядеть как
HTTP-запросы.

WebSocket и gRPC это умеют, но у каждого свой изъян: WebSocket опознаётся
по заголовку `Upgrade` и живёт одним долгим соединением, gRPC требует
HTTP/2 по всей цепочке и несёт характерные заголовки. XHTTP (Xray, конец
2024, наследник SplitHTTP) выглядит как набор обычных GET и POST, которые
CDN пропускает не задумываясь.

> ⚠️ Контракт транспорта задаёт Xray: наш клиент работает против Xray-сервера,
> и расхождение даже в мелочи ломает соединение молча — запрос проходит,
> данные не идут (фича [002](../SPECS/FEATURES/002-XHTTP/FEATURE.md)). Реализация — `transport/v2rayxhttp/`.

## 4.2 Два направления и три режима

Ключевая идея XHTTP: аплинк и даунлинк — **разные HTTP-запросы**.

```
packet-up / stream-up
  клиент ──GET /path/<session>──────────► сервер     даунлинк: долгий ответ,
         ◄── поток байтов вниз ────────            как бесконечная загрузка

  клиент ──POST /path/<session>/<seq>──► сервер     аплинк (packet-up):
         ──POST /path/<session>/<seq+1>►            куски по порядку
  или
  клиент ──POST /path/<session> (поток)► сервер     аплинк (stream-up):
                                                     одно тело без конца

stream-one
  клиент ──POST /path ───────────────► сервер       одно соединение:
         ◄── тело ответа = даунлинк ──              тело запроса вверх,
         ── тело запроса = аплинк ───►              тело ответа вниз
```

| Режим | Когда | Цена |
|---|---|---|
| `packet-up` | За CDN, который буферизует тела запросов и не умеет потоковый аплинк. Самый проходимый | Каждый кусок — отдельный запрос с заголовками; выше задержка и накладные расходы |
| `stream-up` | Посредник пропускает потоковые тела | Два долгих запроса на соединение |
| `stream-one` | Напрямую на сервер, обычно под REALITY | Нужен HTTP/2 и отсутствие буферизации |
| `auto` | Дефолт: при REALITY → `stream-one`, иначе → `packet-up` | — |

Сервер склеивает направления по идентификатору сессии (§4.4). Что это
даёт сверх проходимости: направления можно пустить **разными путями**
— в Xray за это отвечает `downloadSettings`. У нас этого поля **нет**:
даунлинк всегда идёт туда же, куда аплинк.

## 4.3 Версия HTTP выводится, а не задаётся

Отдельного ключа нет; версия вычисляется из блока `tls` по правилу Xray
(`decideHTTPVersion`, [SPEC 104](../SPECS/TASKS/104-XHTTP_HTTP_VERSION_PARITY/SPEC.md)):

- без TLS — HTTP/1.1 по TCP;
- REALITY — всегда HTTP/2; `alpn` без `h2` заменяется на `["h2"]` с
  предупреждением, потому что REALITY поверх QUIC не бывает;
- TLS с `alpn: ["h3"]` — HTTP/3 по QUIC/UDP;
- TLS с `alpn: ["http/1.1"]` — HTTP/1.1;
- всё остальное — HTTP/2.

HTTP/3 иногда проходит там, где TCP душат, и наоборот. Это единственный
рычаг выбора между TCP и UDP для XHTTP.

## 4.4 Сессия, нумерация, паддинг

- **Идентификатор сессии** по умолчанию — сегмент пути после `path`.
  В `stream-one` его **нет**: сервер маршрутизирует этот режим ровно по
  отсутствию сегмента. `session_placement` переносит его в query,
  заголовок или cookie.
- **Номер пакета** (`seq`) нужен только `packet-up`: сервер собирает куски
  по порядку, потому что POST-ы через CDN приходят как попало.
- **X-Padding** — случайное число байт из диапазона `x_padding_bytes`,
  приписанное к каждому запросу: в query, заголовок или cookie по
  `x_padding_placement`. Без него запросы одной длины выдавали бы структуру
  туннеля.
- `sc_max_each_post_bytes` и `sc_min_posts_interval_ms` задают размер
  куска и паузу между POST-ами: тюнинг ритма под конкретный CDN.
- Запросы с телом помечаются заголовком gRPC-потока — паритет с Xray;
  `no_grpc_header` убирает пометку, если посредник на неё ругается.

## 4.5 xmux: пул соединений как у браузера

Браузер держит к сайту несколько HTTP/2-соединений и время от времени
открывает новые. Одно HTTP/2-соединение, живущее часами и гоняющее сотни
потоков, на браузер не похоже.

`xmux` описывает пул: сколько соединений держать (`max_connections`),
сколько потоков пускать в одно (`max_concurrency`), после скольких
запросов или секунд соединение закрыть и открыть заново
(`h_max_request_times`, `h_max_reusable_secs`, `c_max_reuse_times`), как
часто слать keepalive (`h_keep_alive_period`). Значения можно задавать
диапазоном, и каждое соединение получает свой случайный лимит.

Лимит переиспользования у нас считается **в запросах, а не в потоках**:
в `packet-up` один поток порождает десятки POST-ов, и счёт по потокам
занижал бы износ соединения в разы ([SPEC 059](../SPECS/TASKS/059-XHTTP_XMUX/SPEC.md)). При серии отказов пул
размыкается (breaker, [SPEC 076](../SPECS/TASKS/076-XHTTP_XMUX_BREAKER/SPEC.md)), чтобы не долбить мёртвый сервер
сотнями запросов.

## 4.6 Грабли, на которых соединение молчит

Все они — из полевых разборов (задачи [043](../SPECS/TASKS/043-XHTTP_STREAM_ONE_PATH_PREFIX/SPEC.md), [061](../SPECS/TASKS/061-XHTTP_DIAL_DOWNLOAD_DEADLOCK/SPEC.md), [094](../SPECS/TASKS/094-XHTTP_LOCAL_CLOSE_NOT_FAILURE/SPEC.md), [104](../SPECS/TASKS/104-XHTTP_HTTP_VERSION_PARITY/SPEC.md)). Общее у них
одно: HTTP-запрос проходит, ошибки нет, данных нет.

- **Лишний сегмент пути в `stream-one`** — сервер отдаёт даунлинк другим
  протоколом, соединение разваливается без диагностики.
- **Потерянный завершающий слэш** — сервер приводит путь к виду со слэшем
  и обслуживает только такое начало; без слэша «не найдено» и зависание до
  таймаута.
- **Явный `packet-up` или `stream-up` против REALITY-сервера** — Xray на
  `auto` при REALITY берёт `stream-one`, и сервер, настроенный под эту
  пару, другого режима не ждёт.
- **Ожидание ответа сервера при установке соединения** — в режимах с
  раздельным даунлинком сервер придерживает GET до первого пакета аплинка;
  если клиент ждёт ответ на GET, прежде чем слать POST, обе стороны ждут
  друг друга ([SPEC 061](../SPECS/TASKS/061-XHTTP_DIAL_DOWNLOAD_DEADLOCK/SPEC.md)). Соединение отдаётся вызывающему сразу.
- **Локальное закрытие не считается отказом** ([SPEC 094](../SPECS/TASKS/094-XHTTP_LOCAL_CLOSE_NOT_FAILURE/SPEC.md)): когда соединение
  закрывает наш собственный клиент, читатель даунлинка видит
  `context.Canceled`, и ядро не должно считать это падением узла.

# 5. VLESS encryption: постквантовый слой

## 5.1 Угроза: записать сейчас, расшифровать потом

Вся асимметричная криптография в TLS держится на двух задачах: разложение
на множители (RSA) и дискретный логарифм на эллиптических кривых (X25519,
ECDSA, Ed25519). Алгоритм Шора на достаточно большом квантовом компьютере
решает обе. Симметричные шифры страдают меньше: алгоритм Гровера лишь вдвое
уменьшает эффективную стойкость, и AES-256 остаётся безопасным.

Такого компьютера пока нет. Но трафик можно записать сегодня и вскрыть,
когда он появится. Для VPN-трафика это не теоретическая угроза: записывать
его дёшево, а срок давности у содержимого долгий. Именно это и называется **harvest now, decrypt later**.

## 5.2 Что такое ML-KEM и зачем гибрид

В августе 2024 года NIST утвердил постквантовые стандарты:

- **ML-KEM** (FIPS 203, бывший Kyber) — обмен ключами на решётках.
  Уровни 512, 768, 1024. Публичный ключ ML-KEM-768 — 1184 байта,
  шифртекст — 1088 байт. Это *инкапсуляция*: отправитель по чужому
  публичному ключу получает общий секрет и шифртекст, получатель
  восстанавливает секрет своим приватным ключом. Обмена «ключ на ключ», как
  в Диффи-Хеллмане, нет.
- **ML-DSA** (FIPS 204, бывший Dilithium) — подпись на решётках. Для
  обмена ключами не нужна; в Xray она подписывает сертификат REALITY, у нас
  не реализована (§2.6).

Новым алгоритмам не доверяют полностью: их математику проверяли недолго.
Поэтому везде используют **гибрид**: X25519 и ML-KEM-768 одновременно,
общий секрет выводится из обоих. Чтобы вскрыть соединение, нужно сломать
и то, и другое. Так устроен X25519MLKEM768 в TLS (§1.3), и так устроен
`mlkem768x25519plus`.

## 5.3 Где живёт слой

```
VLESS-клиент (заголовок, UUID, команда, Vision)
        │
        ▼
encryption.CommonConn ── mlkem768x25519plus          ◄── этот слой
        │
        ▼
транспорт: tcp / ws / grpc / xhttp
        │
        ▼
tls: может быть, а может и не быть
```

`protocol/vless/outbound.go` оборачивает транспортное соединение в
`*encryption.CommonConn` до того, как VLESS-клиент начинает писать. Слой
не зависит ни от TLS, ни от REALITY: такие узлы часто приходят с
`security=none`, потому что внешний TLS им не нужен — шифрование уже
внутри.

> 🧭 **Зачем, если есть TLS.** TLS можно снять посредником: CDN терминирует
> его у себя и видит нагрузку открытой. Внутренний слой проходит сквозь
> посредника нетронутым и доходит до сервера.

Серверная половина (`decryption` в Xray) намеренно не портирована: форк
клиентский. Реализация клиента — `protocol/vless/encryption/`, разбор
строки — `protocol/vless/lx_encryption.go`.

> 🔀 **В ванили иначе.** Симптом, который слой лечит: сервер с `decryption` молча рвёт обычный
> VLESS. Транспорт поднимается (WS отвечает `101`, gRPC шлёт SETTINGS), после
> чего пир закрывает соединение без единой строки в логе. До [SPEC 032](../SPECS/TASKS/032-VLESS_ENCRYPTION_MLKEM768/SPEC.md) такие
> узлы не работали ни в одном клиенте на базе sing-box.

## 5.4 Рукопожатие: два ключа, один секрет

В строке конфига после режима идут **публичные ключи сервера**: X25519
(32 байта) или ML-KEM-768 (1184 байта), один или несколько. Это
долгоживущие ключи, их называют **NFS** — non-forward-secret: они не
меняются от соединения к соединению, и их компрометация в будущем опасна.
Поэтому они используются только для первого шага.

```
клиент                                            сервер
  │
  │ 1. по каждому NFS-ключу сервера:
  │    X25519  → ECDH с эфемерной парой → nfsKey
  │    ML-KEM  → инкапсуляция → nfsKey + шифртекст
  │    (relay = публичный ключ или шифртекст)
  │
  │ 2. эфемерная PFS-пара на это соединение:
  │    ML-KEM-768 (1184 байта) + X25519 (32 байта)
  │
  │──── IV · relays · AEAD(nfsKey){PFS-публичные ключи} · паддинг ────►
  │
  │                               3. сервер инкапсулирует на PFS-ключи,
  │                                  отвечает своими PFS-половинками
  │◄─── AEAD(nfsKey){PFS-ответ} · билет · паддинг ─────────────────────
  │
  │ 4. pfsKey = ML-KEM-секрет (32) ‖ X25519-секрет (32)
  │    unitedKey = pfsKey ‖ nfsKey
  │    AEAD(unitedKey) — рабочий шифр соединения
  │
  │═══ дальше поток VLESS, запись за записью ═══════════════════════════
```

- **NFS-ключ** защищает первый пакет и аутентифицирует сервер: кто не
  владеет приватной половиной, не прочитает PFS-обмен и не ответит.
- **PFS-ключи** (perfect forward secrecy) эфемерны: новая пара на каждое
  соединение, после него выбрасывается. Записанный трафик не вскрыть даже
  тем, кто потом получит приватный NFS-ключ сервера.
- Оба обмена гибридные: и NFS, и PFS содержат ML-KEM-768 и X25519. Рабочий
  ключ зависит от всех четырёх секретов.
- AEAD — AES-GCM, если у процессора есть аппаратный AES, иначе
  ChaCha20-Poly1305.

## 5.5 0-RTT и билеты

Режим `1rtt` — полное рукопожатие выше на каждом соединении: один
круговой обход до первых данных.

Режим `0rtt` позволяет его пропустить при повторном подключении. В ответе
сервер присылает **билет** (16 байт) и срок его жизни в секундах. Клиент
запоминает билет вместе с `pfsKey`. Следующее соединение в пределах срока
несёт билет вместо PFS-обмена, и сервер по билету восстанавливает тот же
`pfsKey`; данные идут сразу за первым пакетом. Билет переиспользуется, пока
не истёк срок, но NFS-шаг (§5.4, п. 1) выполняется заново на каждом
соединении, поэтому `unitedKey` у каждого соединения свой. Защита от
повтора первого пакета — на сервере.

> 🧭 **Цена 0-RTT:** несколько соединений делят один `pfsKey`, пока билет жив.
> Полевая форма у серверов, которые встречались, — `native.0rtt`.

## 5.6 Вид на проводе и паддинг

Второй сегмент строки задаёт, как слой выглядит снаружи:

- `native` — записи оформлены как TLS 1.3 `application_data`; без внешнего
  TLS трафик выглядит как TLS, поверх TLS — как TLS внутри TLS (тут Vision,
  §3.3);
- `xorpub` — то же, но relays первого пакета дополнительно замаскированы
  потоковым шифром от публичного ключа сервера: публичный ключ X25519 и
  шифртекст ML-KEM имеют узнаваемую структуру, а после XOR выглядят как
  случайные байты;
- `random` — сверх `xorpub` всё соединение оборачивается в `XorConn`:
  потоковый шифр от `unitedKey` накладывается на каждую запись, и
  TLS-подобных заголовков снаружи не остаётся — поток полностью случайный.

Паддинг и задержки (`100-111-1111.75-0-111`: вероятность, от, до) добавляют
к первому пакету случайные байты и шлют их **кусками с паузами** — чтобы
рукопожатие не имело постоянной длины и ритма. Сервер тоже может слать
свой паддинг медленно. Это имеет смысл только для `1rtt`: в `0rtt`
рукопожатия нет, и паддинг отвергается при проверке конфига.

Неразобранная строка — ошибка на `check`, с указанием сегмента. Молчаливого
отключения слоя нет: иначе пользователь считал бы трафик защищённым, когда
он не защищён.

## 5.7 Популярные заблуждения

- **«Это постквантовый REALITY».** Нет. REALITY защищает рукопожатие TLS и
  выбор сервером своих; `encryption` защищает нагрузку. Их включают вместе
  или порознь, друг от друга они не зависят.
- **«У меня `chrome` с X25519MLKEM768, значит трафик уже постквантовый».**
  Гибридный key share в ClientHello (§1.3) защищает ключ внешнего TLS,
  который CDN терминирует у себя. `encryption` защищает ключ внутреннего
  слоя, который доходит до сервера. Примитив один, ML-KEM-768, ключи и слои
  разные.
- **«С `encryption` Vision не нужен».** Нужен по той же причине, что и
  поверх TLS: внутри туннеля всё равно едет чужое TLS-рукопожатие, и его
  форму видно. Vision поверх `encryption` работает на любом транспорте
  (§3.3).
- **«`security=none` в ссылке означает, что узел не шифрован».** Означает
  только, что внешнего TLS нет. Если в ссылке есть `encryption`, шифрование
  живёт внутри VLESS (§5.3).

## 5.8 Пример: Xray и sing-box-lx

VLESS + `encryption` поверх WebSocket без внешнего TLS — типичный узел из
подписки, у которого `security=none`, потому что шифрование уже внутри.

Xray:

```jsonc
{
  "protocol": "vless",
  "settings": {
    "vnext": [{
      "address": "203.0.113.20",
      "port": 80,
      "users": [{
        "id": "00000000-0000-0000-0000-000000000000",
        "encryption": "mlkem768x25519plus.native.0rtt.<base64url ML-KEM-768 key>"
      }]
    }]
  },
  "streamSettings": {
    "network": "ws",
    "security": "none",
    "wsSettings": { "path": "/ws" }
  }
}
```

sing-box-lx:

```jsonc
{
  "type": "vless",
  "tag": "pq-ws",
  "server": "203.0.113.20",
  "server_port": 80,
  "uuid": "00000000-0000-0000-0000-000000000000",
  "encryption": "mlkem768x25519plus.native.0rtt.<base64url ML-KEM-768 key>",
  "transport": { "type": "ws", "path": "/ws" }
}
```

| Xray | sing-box-lx | Где описано |
|---|---|---|
| `users[].encryption: "mlkem768x25519plus…"` | `encryption` — плоское поле рядом с `uuid` | [lx-config §6](lx-config.ru.md#6-vless-encryption--пост-квантовый-слой-spec-032), §5.4–§5.6 |
| `users[].encryption: "none"` или пусто | поле отсутствует, пусто или `"none"` | слой выключен, §5.6 |
| `security: "none"` | блока `tls` нет | внешний TLS не нужен, §5.3 |
| `security: "tls"` / `"reality"` | `tls` как в §2.8 | два независимых слоя, §5.7 |
| `users[].flow: "xtls-rprx-vision"` | `flow` | работает поверх `encryption` на любом транспорте, §3.3 |
| `network: "ws"` + `wsSettings` | `transport.type: "ws"` + `path` | [WebSocket](../docs/configuration/shared/v2ray-transport.md#websocket); любой транспорт, включая `xhttp` (§4.7) |
| серверный `decryption` | нет | не портирован, §5.3 |

> ⚠️ Строка `encryption` переносится **дословно**: сегменты вида, режима,
> паддинга и ключи у обоих ядер одинаковы, перевода имён нет. Билдер
> клиента, который теряет это поле при сборке конфига, оставляет узел
> мёртвым без единой строки в логе.

> 📖 Нормативное описание — [VLESS outbound в документации Project X](https://xtls.github.io/config/outbounds/vless.html).

# 6. Как слои складываются

| Комбинация | Работает | Замечание |
|---|---|---|
| VLESS + Vision + REALITY, голый TCP | да | классическая связка, скорость максимальная |
| VLESS + Vision + обычный TLS, голый TCP | да | REALITY не обязателен для Vision |
| VLESS + Vision + ws / grpc / xhttp | **нет** | транспорт между Vision и TLS; `flow` должен быть пуст |
| VLESS + XHTTP + REALITY | да | `auto` → `stream-one`, всегда HTTP/2 |
| VLESS + XHTTP + TLS через CDN | да | `packet-up`, `h3` по желанию |
| VLESS + `encryption` + любой транспорт, без TLS | да | `security=none`; шифрование внутри |
| VLESS + `encryption` + Vision + любой транспорт | да | [SPEC 105](../SPECS/TASKS/105-VISION_OVER_VLESS_ENCRYPTION/SPEC.md); Vision пробрасывает в слой под шифрованием |
| VLESS + `encryption` + REALITY | да | два независимых слоя, два гибридных обмена |
| `multiplex` sing-box + Vision | нет | Vision не умеет мультиплексировать |
| `multiplex` sing-box + XHTTP | не нужно | у XHTTP свой `xmux` |
| `tls.reality` + `tls.ech` | нет | REALITY подменяет рукопожатие целиком |

Типовые стеки, от простого к осторожному:

1. **Прямой доступ к серверу.** VLESS + Vision + REALITY на `chrome`.
   Против активной проверки сервера и TLS-в-TLS. Гибридный key share уже в
   пресете.
2. **IP сервера напрямую недоступен.** VLESS + XHTTP `packet-up` + TLS через CDN.
   Без Vision (нельзя), с `xmux`. Если сервер требует `encryption` —
   добавить, внешний TLS при этом можно снять.
3. **Максимум.** VLESS + `encryption` + Vision + XHTTP + REALITY.
   Постквантовая защита нагрузки и внешнего рукопожатия, Vision убирает
   TLS-в-TLS, XHTTP даёт форму веб-трафика, REALITY закрывает
   активную проверку.

# 7. Отличия от ванильного sing-box

## 7.1 Почему база — sing-box, а не Xray

Если протоколы задаёт Xray, а форк вечно его догоняет, естественный
вопрос: почему не взять Xray целиком? Ответ в том, что Xray и sing-box —
вещи разного класса.

**Xray — ядро протоколов.** Его сильная сторона — VLESS, REALITY, Vision,
XHTTP и всё, что описано в этом документе. Вокруг них — минимум: маршрутизация
по доменам и IP, простой DNS, outbound-ы для VMess, Trojan, Shadowsocks,
WireGuard. TUN-стека, пригодного для мобильного клиента, в Xray нет:
приложения на нём ставят рядом отдельный tun2socks и сами сшивают его с
`VpnService`, жизненным циклом и статистикой.

**sing-box — платформа.** Протоколы — одна из её частей наряду с:

- **TUN-стеком** (системным и gVisor) с полным жизненным циклом интерфейса,
  маршрутами, авто-detect интерфейса по умолчанию;
- **движком маршрутизации** с правилами по процессу, пакету, домену, rule-set
  из удалённых источников, сниффингом протоколов;
- **DNS-движком** с несколькими серверами, стратегиями и правилами;
- **протоколами, которых в Xray нет и не будет**: endpoint-ы WireGuard и
  AmneziaWG, Tailscale, MASQUE и WARP, Hysteria2, TUIC, ShadowTLS, SSH, naive;
- **`libbox`** — готовым биндингом для Android и iOS с жизненным циклом
  сервиса, CommandClient для статистики и управления, прямой интеграцией с
  `VpnService`.

Клиенту, которому нужны одновременно VLESS-подписки, WireGuard и AmneziaWG,
WARP и Tailscale в одном процессе и одном TUN, Xray не подходит как база
в принципе: половину этого пришлось бы написать с нуля.

**Дельта асимметрична.** Клиентские половины Xray-протоколов — это транспорт
(`transport/v2rayxhttp/`), слой шифрования (`protocol/vless/encryption/`) и
несколько швов в TLS-клиенте. Это десятки файлов, которые ложатся в
архитектуру sing-box с её реестрами транспортов и outbound-ов за
build-тегами. Обратное — принести в Xray платформу sing-box — не
подъёмно и никому не нужно. Поэтому порт идёт в сторону sing-box, а Xray
остаётся **эталоном**: нормативный источник для каждого протокола — его
исходники, не документация ([lx-reference-cores.ru.md](lx-reference-cores.ru.md)).

> 🧭 **Цена выбора** честно видна в этом документе: протоколы меняются на стороне
> Xray, и каждое ужесточение сервера (§2.6) форк обязан догнать, иначе узлы
> из подписок умирают молча. Это постоянная работа, а не разовый порт.

## 7.2 Как устроена дельта форка

Весь downstream-код живёт либо в своих файлах, либо в швах апстримных
файлов с пометкой `// lx`, за build-тегами. Сборка без тегов — апстрим
байт в байт. Каждый релиз `upstream/stable` вливается в течение дней;
у хотфиксов апстримных багов есть условие снятия (реестр
[004-HOTFIXES](../SPECS/FEATURES/004-HOTFIXES/FEATURE.md)). Там, где
апстримная зависимость не даёт нужного, она заменяется форк-сабмодулем —
для этого документа это `utls-lx` (§1.2).

## 7.3 Сводка по протоколам

«Ванильный» — SagerNet/sing-box на версии из `upstream.version`.

| Что | Ванильный sing-box | sing-box-lx | Где |
|---|---|---|---|
| **XHTTP** | Транспорта нет: только `ws`, `grpc`, `httpupgrade`, `http`, `quic`. Узел с `xhttp` не загружается | Нативный транспорт `xhttp` за `with_xhttp`: все режимы, версия HTTP по правилу Xray, `xmux`, паддинг, размещение сессии | §4, [002](../SPECS/FEATURES/002-XHTTP/FEATURE.md) |
| **REALITY: гибридный key share** | Вырезает `X25519MLKEM768` из приветствия (костыль под старый uTLS, [SagerNet/sing-box#4520](https://github.com/SagerNet/sing-box/issues/4520)). Против Xray ≥ v26.9.8 каждый узел уходит на сайт-прикрытие | Шлёт то, что несёт пресет; `AuthKey` по тому ключу, который выберет сервер | §2.6, [083](../SPECS/TASKS/083-REALITY_MLKEM_KEYSHARE/SPEC.md) |
| **REALITY: версия клиента** | Устаревшая константа; сервер с `minClientVer` отсекает | Ровно требуемый минимум | [053](../SPECS/TASKS/053-REALITY_MIN_CLIENT_VER/SPEC.md) |
| **REALITY: `key_share`** | Поля нет | `classical` / `hybrid` по узлу — для сетей, теряющих двухсегментное приветствие | §1.3, [089](../SPECS/TASKS/089-REALITY_KEY_SHARE_OPTION/SPEC.md) |
| **REALITY: фрагментация** | `fragment` / `record_fragment` обходят REALITY стороной | Действуют и на REALITY; под `detour` `record_fragment` включается сам | §1.4, [088](../SPECS/TASKS/088-REALITY_FRAGMENT_BYPASS/SPEC.md), [060](../SPECS/TASKS/060-TLS_FRAGMENT_AUTO_ON_DETOUR/SPEC.md) |
| **Отпечатки uTLS** | `metacubex/utls`: гибридный шар только у `chrome` | Форк `utls-lx`: плюс `firefox` (Firefox 148) и `safari` (Safari 26.3) с гибридом | §1.2, [086](../SPECS/TASKS/086-UTLS_FORK_FIREFOX148/SPEC.md), [087](../SPECS/TASKS/087-UTLS_SAFARI_26_3/SPEC.md) |
| **Vision** | Есть (`sing-vmess`), только поверх TLS/REALITY на голом TCP | То же, плюс поверх VLESS `encryption` на любом транспорте | §3.3, [105](../SPECS/TASKS/105-VISION_OVER_VLESS_ENCRYPTION/SPEC.md) |
| **VLESS `encryption`** | Нет; поле отвергается как неизвестное, узлы с ним мертвы во всей экосистеме sing-box | Клиентская половина `mlkem768x25519plus`: все виды, `0rtt`/`1rtt`, паддинг | §5, [012](../SPECS/FEATURES/012-VLESS_ENCRYPTION/FEATURE.md) |
| **VLESS `decryption`** (сервер) | Нет | Нет, намеренно: форк клиентский | §5.3 |
| **ML-DSA-65 в REALITY**, `spiderX` | Нет | Нет, вне фичи | §2.6 |
| **XHTTP `downloadSettings`** | Нет транспорта | Нет поля: даунлинк идёт тем же путём, что аплинк | §4.2 |

> 🔀 **Общий знаменатель:** ванильный sing-box достаточен для REALITY-сервера на
> старом Xray и для WS/gRPC через CDN. Любая подписка с XHTTP, с
> `encryption` или с сервером на Xray ≥ v26.9.8 в нём молча не работает —
> без строки в логе, потому что REALITY отказы не объясняет, а сервер с
> `decryption` просто закрывает соединение.

# 8. Глоссарий

| Термин | Что значит |
|---|---|
| **Посредник** | Любое оборудование между клиентом и сервером, которое смотрит на трафик или вмешивается в него: классификатор, обратный прокси, CDN |
| **DPI** | Deep packet inspection: оборудование, которое классифицирует трафик по форме и содержимому, не имея ключей |
| **Активная проверка сервера** | Посредник сам подключается к серверу из списка и смотрит на ответ |
| **SNI** | Server Name Indication, имя сервера в открытом ClientHello |
| **Отпечаток (fingerprint)** | Набор и порядок полей ClientHello, по которому узнают библиотеку или браузер |
| **uTLS** | Библиотека, собирающая ClientHello по пресету браузера |
| **key_share** | Расширение ClientHello с публичными половинками обмена ключами |
| **X25519** | Классический обмен ключами на эллиптической кривой; 32-байтные ключи |
| **ML-KEM-768** | Постквантовая инкапсуляция ключа (FIPS 203, бывший Kyber); ключ 1184 байта, шифртекст 1088 |
| **ML-DSA-65** | Постквантовая подпись (FIPS 204, бывший Dilithium); у нас не реализована |
| **Гибрид** | Два обмена ключами разной природы с одним выведенным секретом |
| **PFS** | Perfect forward secrecy: компрометация долгоживущих ключей не вскрывает прошлый трафик |
| **NFS-ключ** | Долгоживущий публичный ключ сервера в строке `encryption` |
| **0-RTT / 1-RTT** | Сколько круговых обходов до первых данных: ноль с билетом, один при полном рукопожатии |
| **AuthKey** | Ключ REALITY, выведенный из ECDH эфемерного ключа клиента и публичного ключа сервера |
| **short_id** | 8 байт в session id REALITY, по которым сервер отбирает клиентов |
| **dest / сайт-прикрытие** | Настоящий сайт, которым REALITY-сервер отвечает чужим |
| **TLS-в-TLS** | Вложенное рукопожатие внутри туннеля, видимое DPI по длинам записей |
| **Splice** | Копирование между сокетами в ядре ОС без прохода через процесс |
| **CDN** | Посредник, терминирующий TLS и пробрасывающий HTTP на сервер |
| **xmux** | Пул HTTP-соединений XHTTP с лимитами переиспользования |
