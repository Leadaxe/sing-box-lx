AmneziaWG (AWG) — это WireGuard, у которого изменена форма пакетов на
проводе при полностью сохранённой криптографии. Протокол задаёт проект
Amnezia: референсная реализация — `amneziawg-go`, серверы в экспортах
`vpn://` и `.conf` — тоже их. Ванильный sing-box AWG не поддерживает и
поддерживать отказался; `sing-box-lx` несёт клиентскую половину в
форк-сабмодуле `wireguard-go`.

Документ отвечает на три вопроса: **как устроен** каждый слой AWG — зачем
существует и что делает с байтами; **как сделана поддержка в форке** — где
живёт код и какие решения приняты; **чем это отличается от ванильного
sing-box** и от референса. Поля, дефолты и тексты ошибок здесь не
перечисляются — для этого есть
[protocols-transports §2](protocols-transports.ru.md#2-amneziawg-203x-awg2-awg3)
(справочник параметров) и [lx-config §2](lx-config.ru.md#2-amneziawg-203x-awg2-awg3)
(обзор). Текущее состояние области — спека фичи
[003-AWG](../SPECS/FEATURES/003-AWG/FEATURE.md).

Для кого: разработчик ядра или клиента, который открывает
`submodules/wireguard-go/device/` или `option/wireguard_awg.go` и хочет
понимать, что читает. Знание WireGuard на уровне «есть хендшейк, есть
транспортные пакеты» предполагается.

# 0. Картина целиком: три слоя поверх WireGuard

WireGuard — быстрый и простой UDP-туннель с образцовой криптографией. Его
единственная слабость против посредника — **узнаваемость**: протокол
никогда не проектировался скрытным, и классификатор опознаёт его по
первому же пакету (§1). AmneziaWG добавляет поверх него обфускацию в три
слоя, каждый следующий включает предыдущий:

| Слой | Что добавляет | Ключи |
|---|---|---|
| **AWG 1.x** | Мусорные пакеты перед хендшейком, паддинг перед сообщениями, подмена типов сообщений | `jc` `jmin` `jmax`, `s1` `s2`, `h1`–`h4` одиночные |
| **AWG 2.0** | Пакеты-приманки, имитирующие чужой протокол; паддинг транспортных пакетов; типы сообщений диапазоном | `i1`–`i5`, `s3` `s4`, `h1`–`h4` как `"min-max"`, сахар `id` `ip` `ib` |
| **AWG 3.x** | Шифр заголовка каждого пакета, паддинг содержимого, случайные хвосты, рандомизированные тайминги | `header_protection_key`, `content_padding_addition`, `random_trailers`, `disable_cookies`, диапазонные тайминги |

Криптография WireGuard (Noise IK, Curve25519, ChaCha20-Poly1305) не
трогается ни одним слоем. AWG не делает туннель «надёжнее» — он делает
его **непохожим на WireGuard**.

Стопка слоёв в ядре, сверху вниз:

```
трафик приложения
        │
        ▼
endpoint wireguard ── обычные поля: ключи, address, mtu, peers
   └── AWG-поля на корне endpoint
        │
        ▼
device форка wireguard-go ── обфускация при отправке, снятие при приёме
        │
        ▼
UDP → сеть  (или другой outbound через detour)
```

> 🧭 **TL;DR:** AWG — это WireGuard, у которого на проводе нет ни одной
> узнаваемой черты: ни типа сообщения, ни размера, ни ритма. Внутри —
> тот же WireGuard. Клиент и сервер должны сойтись **побайтово** по всем
> параметрам обфускации: они не согласуются, а задаются.

# 1. Почему WireGuard опознаётся

Классификатору не нужно ломать шифр. Ему хватает формы:

- **Первый байт** каждого пакета — тип сообщения: `1` для handshake
  initiation, `2` для response, `3` для cookie reply, `4` для транспорта.
  За ним три нулевых байта. Четыре слова на весь протокол.
- **Размеры хендшейка** фиксированы: initiation — 148 байт, response —
  92, cookie — 64. Пара UDP-датаграмм 148 → 92 на новый адрес — это
  сигнатура сама по себе.
- **Транспортные пакеты** выровнены по 16 байтам, keepalive — ровно 32.
- **Ритм**: новый хендшейк каждые 120 секунд, повтор через 5, keepalive по
  таймеру.

Все четыре признака лежат в открытой части пакета или в его метаданных.
Классификатор, который их знает, помечает поток за один пакет, без
состояния. Именно поэтому AWG работает с каждым из них по отдельности:
junk и паддинг ломают размеры, magic-заголовки — тип, AWG3 — ритм и
остаток энтропии.

# 2. AWG 1.x: junk, паддинг, magic-заголовки

## 2.1 Junk-пакеты перед хендшейком

`jc` случайных датаграмм размером от `jmin` до `jmax` байт уходят на адрес
сервера **до** handshake initiation. Содержимое случайное, сервер их
молча выбрасывает. Смысл — чтобы первым пакетом потока не был
148-байтный initiation, а классификатор, считающий состояние по первым
N пакетам, увидел шум.

## 2.2 Паддинг S1–S4

Перед сообщением вставляются случайные байты: `s1` перед initiation,
`s2` перед response, `s3` перед cookie reply, `s4` перед **каждым
транспортным пакетом**. Приёмник знает размер паддинга из своего конфига
и просто пропускает его. Размеры сообщений перестают быть 148/92/64, а
транспорт — кратным 16.

`s4` стоит особняком: он платится на каждом пакете данных и съедает MTU
(§5). `s3` на MTU не влияет: cookie reply — редкое служебное сообщение.

## 2.3 Magic-заголовки H1–H4

Тип сообщения — 4-байтное слово — заменяется на значение из конфига:
`h1` вместо `1`, `h2` вместо `2`, и так далее. Приёмник сравнивает первое
слово после паддинга со своими `h1`–`h4` и так узнаёт тип. В AWG 2.0 каждое
значение может быть **диапазоном** `"min-max"`: на каждое сообщение
выбирается случайное число из него, приёмник проверяет попадание в
интервал. Четыре интервала не должны пересекаться, иначе тип не
восстановить — ядро отвергает такой конфиг на загрузке.

## 2.4 Почему параметры не независимы

Паддинг и заголовок читаются из одного буфера: `s1` сдвигает позицию
magic-слова в пакете. Отсюда целый класс пограничных случаев, пойманных в
форке: при малых `s1`–`s4` (0–3 байта) magic-слово попадает на позиции,
которые в других путях заняты служебными байтами, и его легко затереть
([SPEC 026](../SPECS/TASKS/026-AWG_MAGIC_VS_RESERVED_CLEAR/SPEC.md));
`s4` сдвигал пакет вправо в буфере, выделенном без запаса под паддинг, и
первый же пакет данных ронял процесс
([SPEC 025](../SPECS/TASKS/025-AWG_TRANSPORT_PADDING_OVERRUN/SPEC.md)).

> ⚠️ Обфускация симметрична: любое расхождение параметра с сервером даёт
> один и тот же симптом — «нода не встаёт», без диагностики. Особый случай
> — расхождение по `s4`: хендшейк **проходит** (`s1`/`s2` сошлись), а
> данные не ходят в обе стороны, потому что приёмник режет транспортные
> пакеты по своему `s4`. Выглядит как проблема маршрутизации, а не
> обфускации.

# 3. AWG 2.0: приманки и диапазоны

## 3.1 CPS: I1–I5 и мини-язык

Controlled Packet Sequence — до пяти пакетов, которые инициатор шлёт
перед хендшейком в заданном порядке. В отличие от junk, их содержимое не
случайно, а **описано** строкой мини-языка:

| Тег | Выдаёт |
|---|---|
| `<b 0xHEX>` | статические байты |
| `<c>` | счётчик |
| `<t>` | метка времени |
| `<r N>` | N случайных байт |
| `<rc N>` / `<rd N>` | N случайных символов / цифр |

Так в `i1` кладут снимок реального протокола — STUN Binding Request, QUIC
Initial, DNS-запрос — чтобы первый осмысленный пакет потока выглядел как
чужой легитимный трафик. Строки регистрозависимы, порядок тегов значим;
сервер шлёт их не из конфига, а повторяет то, что пришло от клиента.

## 3.2 Порядок на проводе

По коду графта (`device/send.go`, `SendHandshakeInitiation`):

```
i1 → i2 → … → i5        приманки, по порядку, только заданные
jc × [jmin..jmax]       junk-датаграммы
[s1 junk][h1][initiation]
        ◄── [s2 junk][h2][response]
[s4 junk][h4][transport]  …  далее каждый пакет данных
```

Приманки идут **до** junk, не после: смысл приманки — быть первым
пакетом, который увидит классификатор.

## 3.3 Сахар маскировки id / ip / ib

Писать QUIC Initial тегами `<b 0x…>` руками нереально, а снимок одного
пакета у всех пользователей одинаков и сам становится сигнатурой. Поэтому
форк, по аналогии с WireSock Secure Connect, принимает декларацию: `ip` —
протокол приманки (`quic`, `dns`, `stun`, `sip`), `id` — домен, `ib` —
профиль клиента (`chrome`, `chrome-full`, `firefox`, `curl`), и собирает
`i1` сам — для `quic` заново на каждый хендшейк, со свежими DCID и раскладкой
([SPEC 009](../SPECS/TASKS/009-WIRESOCK_MASQUERADE_PROFILES/SPEC.md)).

Профиль `quic` — QUIC Initial, в котором лежит **целый** ClientHello с
отпечатком выбранного браузера, а фреймы внутри разложены так, как это
делает его стек. `chrome` — Chrome 155 без постквантового key_share, один
пакет 1250 байт, ClientHello порезан на 2–11 CRYPTO-фреймов с PING и
PADDING вразброс, как делает Chrome (`QuicChaosProtector`). `chrome-full` —
тот же Chrome 155 с X25519MLKEM768: ClientHello ~1,9 КБ в одном Initial
больше MTU, который IP-слой режет на два фрагмента. `firefox` и `curl` —
один CRYPTO-фрейм плюс PADDING. Порядок фреймов роли не играет (проверено в
поле); играет роль, что весь ClientHello уехал одним QUIC-пакетом —
размазанный по нескольким Initial, как у настоящего Chrome с ML-KEM, он
на пути к WARP давится. Это единственный профиль, доказанный против
живого DPI на устройстве.

> ⚠️ `id` **уходит на провод**: как SNI в QUIC, как QNAME в DNS, как host в
> SIP. Домен должен быть правдоподобным и разрешённым, не маяком VPN.
> `id`/`ip`/`ib` взаимоисключимы с явным `i1`: конфиг с обоими
> отвергается.

## 3.4 Почему QUIC, а не DNS или STUN

Все четыре профиля — корректные пакеты своих протоколов. Но на устройстве
в живой сети прошёл только `quic`; `dns`, `stun` и `sip` упёрлись в
таймаут. Причина не в качестве пакета, а в **аномалии назначения**:
классификатор ждёт DNS, STUN и SIP на их обычных адресах, а запрос к
дата-центровому IP на нестандартный порт сам по себе подозрителен. QUIC к
любому адресу и порту — норма, потому что так ведёт себя HTTP/3.

Отсюда рекомендация справочника: для Cloudflare WARP — `ip=quic`,
`id=<популярный домен>`, `ib=chrome`. Остальные профили оставлены для
посредников, которые проверяют только правильность формы.

# 4. AWG 3.x: шифр заголовка, паддинг содержимого, тайминги

AWG2 ломает размеры и типы, но заголовок пакета остаётся **низкоэнтропийным**:
после паддинга лежит magic-слово из узкого диапазона, receiver index и
счётчик, которые растут монотонно. Классификатор с состоянием может
это заметить. AWG 3.0 и 3.1 (amneziawg-go v3.0 и v3.1, лето 2026)
закрывают остаток
([SPEC 080](../SPECS/TASKS/080-AWG3_HEADER_PROTECTION_TIMINGS/SPEC.md)).

## 4.1 Защита заголовка

`header_protection_key` — 32-байтный ключ ChaCha20, которым шифруется
заголовок каждого пакета: тип, receiver index, счётчик. Nonce для шифра
берётся из **первых 12 байт паддинга** того же сообщения — поэтому каждый
из `s1`–`s4` обязан быть не меньше 12, и конфиг с ключом при коротком
паддинге отвергается. На проводе остаются только случайные байты до самого
AEAD.

## 4.2 Паддинг содержимого и случайные хвосты

- `content_padding_addition` — добавка нулей **внутрь** AEAD каждого пакета
  данных вместо выравнивания по 16. Снаружи зашифрована, поэтому неотличима
  от данных; размер пакета перестаёт коррелировать с размером нагрузки.
- `random_trailers` — случайный по длине случайный хвост после
  handshake-сообщений и, по тому же правилу, внутри пакетов данных.

Обе добавки ограничены «UDP-окном»: самой большой датаграммой, которую путь
уже проносил. Бюджет MTU (§5) они не меняют, но и не уменьшают
необходимость держать `mtu` на значении сервера.

## 4.3 Тайминги и cookie

Пять таймингов WireGuard (`rekey_after_time` 120, `rekey_timeout` 5,
`reject_after_time` 180, `keepalive_timeout` 10, `max_handshake_attempts`
18) и `persistent_keepalive_interval` пира задаются диапазоном и
перевыбираются при каждом взводе. Ритм перестаёт быть константой.
`disable_cookies` убирает cookie-обмен под нагрузкой: у него узнаваемая
форма, и клиенту он не нужен.

## 4.4 Что обязано совпасть с сервером

AmneziaWG различает **серверные** параметры (значение одинаково на обоих
концах, иначе хендшейка нет) и **клиентские** (локальное поведение,
серверу безразлично). В AWG3 серверный только `header_protection_key`.
Остальные клиентские — но копировать их из экспорта сервера всё равно
стоит: они подобраны вместе, и бессмысленная пара вроде
`rekey_after_time` выше `reject_after_time` заставит туннель дёргаться.

> 🧭 **TL;DR:** AWG1 прячет размеры и типы, AWG2 добавляет приманку и
> диапазоны, AWG3 шифрует всё, что ещё оставалось читаемым, и рандомизирует
> время. Побайтовое совпадение с сервером требуют `jc`/`jmin`/`jmax`,
> `s1`–`s4`, `h1`–`h4`, `i1`–`i5` и `header_protection_key`.

# 5. MTU: куда уходят байты

Это самый частый источник отказов AWG, и он не похож на отказ обфускации.

**Что происходит.** `s4` добавляет junk перед **каждым** транспортным
пакетом. Пакет данных на проводе = IP/UDP (28) + WireGuard (32) + `s4` +
нагрузка. Если нагрузка взята по обычному для WireGuard MTU, пакет
становится длиннее пути, ОС отвергает датаграмму, и в логе появляется:

```
peer(…) - received handshake response
peer(…) - failed to send data packets: write udp4 …: sendmsg: message too long
```

Хендшейк прошёл — его размер от `mtu` не зависит. Данные не ходят.
Снаружи это «VPN подключился, сайты не открываются».

**Бюджет** против 1500-байтного пути:

```
mtu ≤ 1500 − 28 (IP/UDP) − 32 (WireGuard) − s4
```

При `s4 = 60` это 1380. Amnezia рекомендует клиенту **1280**: запас на
PPPoE, мобильные сети и вложенные туннели.

**Что ядро делает само.**

- Если `mtu` не задан, а `s4` есть, дефолт становится **1280** вместо
  обычных для WireGuard 1408.
- Если `mtu` задан явно и не влезает в бюджет, ядро пишет предупреждение
  при старте. Считается против консервативных 1492 (PPPoE), поэтому может
  сработать на несколько байт ниже Ethernet-потолка. Туннель всё равно
  поднимается: предупреждение рекомендательное.
- Внешний сокет **не форсит DF** ([SPEC 028](../SPECS/TASKS/028-NESTED_TUNNEL_UDP_FRAGMENT/SPEC.md)):
  негабаритная датаграмма IP-фрагментируется, а не дропается. Это и даёт
  работать вложенным туннелям — AWG через `detour` поверх другого WG или
  MASQUE, где внешняя датаграмма негабаритна рутинно. Явный
  `"udp_fragment": false` возвращает старое поведение. Правильный `mtu` всё
  равно предпочтительнее: фрагментация — страховка.
- В цепочке [`chain`](../SPECS/FEATURES/015-CHAIN/FEATURE.md) MTU
  туннельных звеньев понижается автоматически.

`jmax` тоже держат ниже path MTU: junk-пакет длиннее MTU фрагментируется,
и узкие пути потом роняют фрагменты.

> 🔀 В ванильном sing-box ничего из этого нет, потому что нет `s4`: MTU
> WireGuard-endpoint там по умолчанию 1408 и не проверяется, DF на внешнем
> сокете форсится. Конфиг AWG, механически перенесённый в ваниль, даже если
> бы она его приняла, упёрся бы в `message too long` на первом пакете
> данных.

> 🧭 **TL;DR:** шум `s4` съедает MTU на каждом пакете данных. Хендшейк
> проходит, данные нет. Ядро дефолтит `mtu` в 1280, предупреждает о
> переборе и разрешает IP-фрагментацию для вложенных туннелей.

# 6. Как это сделано в форке

## 6.1 Два слоя: графт и проброс

Обфускация живёт **не в sing-box**, а в форке `wireguard-go`
([Leadaxe/wireguard-go-awg2-lx](https://github.com/Leadaxe/wireguard-go-awg2-lx),
сабмодуль `submodules/wireguard-go`, `replace` в `go.mod`). Это трёхсторонний
графт: обфускация `amneziawg-go` перенесена поверх `sagernet/wireguard-go`,
на котором стоит sing-box. Вся правка замкнута в `device/`: десять новых
файлов (генератор magic-заголовков, CPS-цепочки, junk, кодеки) и шесть
изменённых (состояние AWG в `device.go`, вставка обфускации в `send.go`,
снятие в `receive.go`, UAPI). `conn/` и `tun/` взяты из апстрима без
изменений.

sing-box только **пробрасывает параметры**: поля на корне endpoint
(`option/wireguard_awg.go`) читаются, валидируются и уходят в device через
UAPI, как обычные ключи WireGuard. Контракт `transport/wireguard` ↔ device
не меняется; конфиг без единого AWG-поля — обычный WireGuard-endpoint,
**байт в байт как в апстриме**. Build-тег `with_awg`; без него AWG-поле
даёт явную ошибку загрузки, а не тихий откат к чистому WireGuard, который
свёл бы обфускацию на нет.

Форк-сабмодуль — часть дельты: снятие наших патчей при обновлении
референса идёт бампом версии сабмодуля, не мержем ядра
([005-UPSTREAM_SYNC](../SPECS/FEATURES/005-UPSTREAM_SYNC/FEATURE.md)).
Текущий порт — amneziawg-go v3.1 (`b5928ef`, 2026-08-28), байт-совместимый
по раскладке nonce, порядку классификации и правилам паддинга.

Инвариант графта — `MessageEncapsulatingTransportSize = 8`, запас перед
каждой датаграммой, как в апстриме. Его однажды обнулили, и перестал
подниматься Tailscale, который сидит на том же форке
([SPEC 112](../SPECS/TASKS/112-TAILSCALE_DIRECT_PATH_SEND_HEADROOM/SPEC.md)).

## 6.2 Валидация: класс «значение из конфига»

Главный класс дефектов AWG — параметр проходит разбор, но ломает рантайм
на границе: ноль, максимум, инверсия диапазона, пересечение паддинга и
заголовка. В референсе такие вещи валидируются по одному полю; в форке
правило — **валидировать комбинации**, и на загрузке, а не в фоновой
горутине:

- `jmin > jmax` — ошибка конфига, а не паника генератора на первом
  хендшейке ([SPEC 008](../SPECS/TASKS/008-AWG_JUNK_PARAM_VALIDATION/SPEC.md));
- длины CPS без границ — отрицательная давала выход за slice, огромная —
  OOM ([SPEC 025](../SPECS/TASKS/025-AWG_TRANSPORT_PADDING_OVERRUN/SPEC.md));
- диапазон `h` на всю ширину `uint32` — переполнение и паника генератора;
- пересечение диапазонов `h1`–`h4` — `headers must not overlap`;
- `header_protection_key` при любом `s1`–`s4` < 12 — отказ с именем поля,
  и при загрузке, и при частичном обновлении через UAPI, когда ключ уже
  стоит, а паддинг сужают;
- `id`/`ip`/`ib` вместе с `i1`, `id` без `ip`, `ib` не при `quic` — отказ
  с текстом; домен `id` проходит строгую LDH-проверку, потому что уходит в
  текст SIP и в DNS QNAME — это граница инъекции.

Дословные тексты — в
[справочнике §2.9](protocols-transports.ru.md#29-ошибки-валидации-дословно).

## 6.3 Приём: классификация пакетов

С `random_trailers` приёмник обязан пробовать как handshake-сообщение
любую датаграмму **длиннее** `s1`+148 / `s2`+92 / `s3`+64 — по слову типа.
При одиночных `h1`–`h4` ложное совпадение случается с вероятностью 2⁻³²;
при широких диапазонах AWG2 — ширина/2³² на **каждый** пакет данных, который
затем не проходит MAC и теряется. Референс так и живёт.

Форк классифицирует иначе
([SPEC 081](../SPECS/TASKS/081-AWG_RECEIVE_INDEX_FIRST_CLASSIFICATION/SPEC.md)):
датаграмма, у которой за словом типа транспорта стоит один из **наших
живых receiver index**, считается данными до любых handshake-кандидатов.
Downlink пакеты так не теряет. Провод не меняется, поэтому uplink зависит
от приёмника сервера, и совет остаётся: не сочетать `random_trailers` с
широкими диапазонами `h1`–`h4`.

## 6.4 Все пути отправки

Пакет данных уходит в device не одним путём: чтение из TUN, инжекция из
стека gVisor (`InputPacket`), приоритетное сообщение, keepalive. Референс
обфусцирует основной путь; в форке AWG3-обёртка применяется ко всем,
включая первый батч после старта, прочитанный до того, как конфиг
применился — он переносится под актуальный паддинг, а не уезжает в старой
раскладке.

> 🔀 Отличия от референса amneziawg-go, которых нет в его клиенте:
> валидация комбинаций на загрузке (§6.2), классификация по receiver index
> (§6.3), обфускация на всех путях отправки (§6.4), сахар `id`/`ip`/`ib` с
> фрагментированным QUIC Initial (§3.3), дефолт и проверка MTU (§5). Всё
> остальное — побайтовый паритет: 16 параметров AWG2 и 9 ключей AWG3.

# 8. Позиция апстрима

У SagerNet/sing-box по AmneziaWG **прямой отказ**, того же рода, что по
XHTTP ([xray-protocols-explained §4.8](xray-protocols-explained.ru.md#48-позиция-апстрима)).

- Запрос [SagerNet/sing-box#4045](https://github.com/SagerNet/sing-box/issues/4045)
  (AmneziaWG 2.0, 2026-04-14) закрыт мейнтейнером как `not planned`
  2026-04-30 с единственным комментарием, отсылающим автора к Hiddify и
  Karing. Аргументов по существу нет.
- Расширить WireGuard-endpoint снаружи нельзя: апстримный
  `sagernet/wireguard-go` не имеет точек подключения для обфускации, а
  sing-box подключает его как обычную зависимость. Отсюда форк-сабмодуль и
  `replace` в `go.mod`.

Это одна из двух транспортных фич, с которых форк начался
([CONSTITUTION](../SPECS/CONSTITUTION.md)): вливать их обратно некуда,
поэтому форк постоянный.

> 🔀 Серверную половину форк не делает намеренно: сервер — это
> `amneziawg-go` или `amneziawg-linux-kernel-module` от Amnezia, и
> клиентский форк sing-box ему не конкурент. Серверный `AdvancedSecurity` по
> той же причине не нужен.

# 9. Популярные заблуждения

- **«AWG шифрует надёжнее WireGuard».** Нет. Криптография та же до байта:
  Noise IK, Curve25519, ChaCha20-Poly1305. AWG меняет только форму пакетов
  на проводе. Шифр заголовка AWG3 защищает метаданные от классификатора, а
  не нагрузку от взлома.
- **«Достаточно включить `jc`, остальное по желанию».** Junk и приманки —
  конфигурация, а не согласование: всё, что задано на сервере, должно
  стоять у клиента с теми же значениями. Пропущенный `s4` — хендшейк
  пройдёт, данные нет.
- **«MTU как у WireGuard, 1420».** `s4` съедает его на каждом пакете. При
  `s4 = 60` потолок 1380, рекомендация 1280 (§5).
- **«`h1`–`h4` скрывают всё, что нужно».** В AWG2 заголовок остаётся
  низкоэнтропийным: receiver index и счётчик читаются. Их прячет только
  `header_protection_key` в AWG3 (§4.1).
- **«Клиенту нужен `AdvancedSecurity`».** Это серверная ручка разбора
  входящих подключений; на то, что шлёт клиент, она не влияет.
- **«Профиль `dns` или `stun` безопаснее `quic`, пакет ведь честнее».**
  Решает не качество пакета, а аномалия назначения (§3.4): на устройстве
  прошёл только `quic`.
- **«Без `with_awg` AWG-поля просто проигнорируются».** Нет: конфиг с
  AWG-полем в такой сборке отвергается с явной ошибкой. Тихий откат к
  чистому WireGuard означал бы туннель без обфускации под видом
  обфусцированного.

# 10. Типичные отказы

| Симптом | Причина | Куда смотреть |
|---|---|---|
| Хендшейк не проходит, в логе ничего | Любой серверный параметр не совпал: `jc`/`jmin`/`jmax`, `s1`–`s4`, `h1`–`h4`, `i1`–`i5`, `header_protection_key` | сверить с экспортом сервера побайтово, §4.4 |
| `received handshake response`, затем `message too long` | `mtu` выше бюджета при заданном `s4` | §5: `mtu ≤ 1500 − 60 − s4`, лучше 1280 |
| Хендшейк есть, данные не ходят, ошибок нет | `s4` не совпал с сервером; или `allowed_ips` верхнего туннеля не покрывает адреса | §2.4; `allowed_ips: ["0.0.0.0/0", "::/0"]` |
| `headers must not overlap` при загрузке | Диапазоны `h1`–`h4` пересекаются или не заданы все четыре | §2.3 |
| `… is too short for header_protection_key` | Какой-то из `s1`–`s4` меньше 12 | §4.1 |
| `AmneziaWG (awg) support is not included in this build` | Сборка без `with_awg` | §6.1 |
| Работает напрямую, не работает через `detour` | Негабаритная внешняя датаграмма; проверить, не стоит ли `udp_fragment: false` | §5, [SPEC 028](../SPECS/TASKS/028-NESTED_TUNNEL_UDP_FRAGMENT/SPEC.md) |
| Downlink теряет пакеты при `random_trailers` | Широкие диапазоны `h1`–`h4` на сервере-референсе | §6.3: сузить диапазоны |
| `id/ip/ib masquerade conflicts with an explicit i1` | Заданы и сахар, и `i1` | §3.3: оставить одно |

# 11. Глоссарий

| Термин | Что значит |
|---|---|
| **Посредник** | Любое оборудование между клиентом и сервером, которое смотрит на трафик или вмешивается в него |
| **Классификатор (DPI)** | Оборудование, помечающее поток по форме пакетов без ключей |
| **Сигнатура WireGuard** | Тип в первом байте, размеры 148/92/64, кратность 16, ритм хендшейков |
| **Junk** | Случайные датаграммы перед хендшейком (`jc`, `jmin`, `jmax`) |
| **Паддинг S1–S4** | Случайные байты перед сообщением; `s4` — перед каждым пакетом данных |
| **Magic-заголовок** | Подменённое слово типа сообщения, одиночное или диапазоном |
| **CPS** | Controlled Packet Sequence: приманки `i1`–`i5` из мини-языка тегов |
| **Приманка (decoy)** | Пакет в форме чужого протокола, отправленный первым |
| **Сахар маскировки** | `id`/`ip`/`ib`: декларация приманки вместо строки `i1` |
| **Защита заголовка** | ChaCha20-шифр заголовка каждого пакета, nonce из паддинга (AWG3) |
| **UDP-окно** | Самая большая датаграмма, которую путь уже проносил; ограничивает паддинг содержимого и хвосты |
| **Серверный параметр** | Обязан совпасть на обоих концах, иначе хендшейка нет |
| **Бюджет MTU** | `1500 − 28 − 32 − s4`; рекомендация 1280 |
| **Графт** | Перенос обфускации amneziawg-go поверх sagernet/wireguard-go в форк-сабмодуле |
| **UAPI** | Текстовый интерфейс конфигурации device WireGuard, через который sing-box передаёт параметры |
| **Receiver index** | Идентификатор сессии в пакете данных; по нему форк классифицирует приём |
