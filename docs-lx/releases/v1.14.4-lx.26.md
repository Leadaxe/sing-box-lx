A DNS `group` can now carry a `hosts` server in front of its network members: names from the hosts list are answered locally and never reach the network, every other name goes to the group's servers as before. An outbound or endpoint address can be a local name with an IPv4 and an IPv6 address, the family picked by `strategy`, while the same resolver keeps serving the rest of the config, subscriptions included. MTU alignment no longer clamps a WireGuard or MASQUE tunnel through a proxy member of a `detour` group, and never below 1280 when the tunnel carries IPv6: a WARP tunnel over a large subscription selector gets its IPv6 back.

DNS-группа `group` теперь может нести сервер `hosts` перед сетевыми участниками: имена из списка hosts отвечаются локально и в сеть не уходят, остальные имена идут серверам группы как раньше. Адрес outbound или endpoint может быть локальным именем с IPv4 и IPv6, семейство выбирает `strategy`, а тот же резолвер продолжает обслуживать остальной конфиг, включая подписки. Выравнивание MTU больше не зажимает туннель WireGuard или MASQUE через прокси-участника группы в `detour` и никогда ниже 1280, если туннель несёт IPv6: у туннеля WARP над большим селектором подписки возвращается IPv6.

## 🆕 What's new

### 🏠 DNS group: a `hosts` server in front of the network members

- Outbound and endpoint server addresses resolve through `domain_resolver`, which goes straight to the server and bypasses DNS rules, so neither a `predefined` rule action nor a `server: hosts` rule reaches them. A `hosts` server as the resolver answers NXDOMAIN for every name it does not list, and a `hosts` server inside a group's `servers` was rejected at start.
- New optional group key `hosts`: tags of `hosts`-type servers, asked before the group chooses a target, in key order. A hit is an A or AAAA query for a name the server knows, answered NOERROR: that answer is returned as is and no network member is asked. An entry with only the other address family is a hit too: an IPv4-only name asked for AAAA gets an empty answer and does not leak to the network, so `strategy: ipv6_only` on such a name yields no address, as with the OS hosts file. Anything else is a miss, and the query takes the network path unchanged in every mode.
- `hosts` members carry no health records, never join a fan or survival mode, never become current and are absent from `GetDNSGroups`. In the DNS query stream a hit shows the `hosts` server as the one that answered, with one `answered` probe; the connection test gets a `dns_member` stage for it. A miss leaves no trace. Cache unchanged.
- Limits: `servers` is still required and non-empty; `hosts` or `fakeip` inside `servers` is still rejected at start, and the error now names the `hosts` key; the key accepts only `hosts`-type tags, no duplicates, no overlap with `servers`. Configs without the key behave as before. Works wherever the group tag is accepted: `domain_resolver`, `dns.final`, rules.
- Unit-tested in every mode, including the real `hosts` transport; not yet checked on a device. (issue #60, SPEC 143)

## 🐛 Fixes

### 📏 MTU alignment: a tunnel over a group with a proxy member lost IPv6 inside

- Field case: a WireGuard endpoint to WARP (`mtu` 1280, IPv4 and IPv6 inside) with a `detour` to a selector of ~150 nodes — IPv4 inside worked, IPv6 hung without an error, URL tests timed out. One vless member of the selector went through another group with a WireGuard of `mtu` 1280; the alignment treated the vless as passing that limit upwards and clamped the tunnel to 1220. There is no such limit: the tunnel's packets ride vless as a TCP stream. And below 1280 the user-space stack silently refuses to bring IPv6 up.
- Now only IP tunnels and groups carry a limit upwards; any proxy (vless, trojan, shadowsocks, hysteria2, tuic, …) is a boundary, whatever lies under its own `detour`. A tunnel that carries IPv6 inside is never aligned below 1280; when the path leaves less, the tunnel keeps 1280 and the log warns that outer packets will be fragmented. AmneziaWG `s4` padding now counts in the overhead.
- One case is no longer aligned: a tunnel over shadowsocks or socks **UDP** whose own `detour` is a tunnel — set `mtu` on the upper tunnel by hand there. Unit-tested; not yet checked on a device. (SPEC 144)

## 🆕 Что нового

### 🏠 DNS-группа: сервер `hosts` перед сетевыми участниками

- Адреса серверов outbound и endpoint резолвятся через `domain_resolver`, который идёт в сервер напрямую, минуя DNS-правила: ни действие `predefined`, ни правило `server: hosts` до них не доходят. Сервер `hosts` в роли резолвера отвечает NXDOMAIN на любое имя не из списка, а `hosts` внутри `servers` группы отвергался на старте.
- Новый необязательный ключ группы `hosts`: теги серверов типа `hosts`, которых группа спрашивает до выбора цели, в порядке ключа. Попадание — запрос A или AAAA на имя, которое сервер знает, с ответом NOERROR: ответ отдаётся как есть, сетевые участники не опрашиваются. Запись только с другим семейством адресов — тоже попадание: имя только с IPv4 на запрос AAAA получает пустой ответ и в сеть не уходит, поэтому `strategy: ipv6_only` на таком имени адреса не даёт, как и hosts-файл ОС. Всё остальное — промах, и запрос идёт сетевым путём без изменений в любом режиме.
- Участники `hosts` без записей здоровья, не входят в веер и режим выживания, не становятся текущими, в `GetDNSGroups` отсутствуют. В потоке DNS-запросов попадание показывает сервер `hosts` ответившим, с одной пробой `answered`; проверка соединения получает для него стадию `dns_member`. Промах следа не оставляет. Кеш без изменений.
- Границы: `servers` по-прежнему обязателен и непуст; `hosts` или `fakeip` внутри `servers` по-прежнему отвергаются на старте, ошибка теперь называет ключ `hosts`; ключ принимает только теги типа `hosts`, без дубликатов и пересечений с `servers`. Конфиги без ключа ведут себя как раньше. Работает везде, где принимается тег группы: `domain_resolver`, `dns.final`, правила.
- Юнит-тесты во всех режимах, включая реальный транспорт `hosts`; на устройстве пока не проверялось. (issue #60, SPEC 143)

## 🐛 Исправления

### 📏 Выравнивание MTU: туннель над группой с прокси-участником терял IPv6 внутри

- Полевой случай: WireGuard-endpoint к WARP (`mtu` 1280, IPv4 и IPv6 внутри) с `detour` на селектор из ~150 узлов — IPv4 внутри работал, IPv6 висел без ошибки, URL-тесты уходили в таймаут. Один vless-участник селектора ходил через другую группу с WireGuard `mtu` 1280; выравнивание считало, что vless передаёт это ограничение наверх, и зажимало туннель до 1220. Такого ограничения нет: пакеты туннеля идут через vless потоком TCP. А ниже 1280 пользовательский стек молча не поднимает IPv6.
- Теперь ограничение наверх несут только IP-туннели и группы; любой прокси (vless, trojan, shadowsocks, hysteria2, tuic, …) — граница, что бы ни лежало под его собственным `detour`. Туннель, несущий IPv6 внутри, никогда не выравнивается ниже 1280; если путь оставляет меньше, туннель держит 1280, а лог предупреждает, что внешние пакеты будут фрагментироваться. Паддинг `s4` AmneziaWG теперь входит в накладные.
- Один случай больше не выравнивается: туннель над shadowsocks или socks по **UDP**, у которых свой `detour` на туннель, — там `mtu` верхнему туннелю задаётся руками. Юнит-тесты; на устройстве пока не проверялось. (SPEC 144)
