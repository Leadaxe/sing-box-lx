Hotfix for `sing-box lxd update` on routers. Restarting the service under procd could start the new daemon before the old one had released the TUN interface: the core failed with `TUNSETIFF: device or resource busy`, the daemon stayed up without a VPN, and the updater still reported `done`. Now the daemon retries a busy TUN at boot for up to 10 s, and the updater waits up to 20 s for the core itself to report `started`, rolling back otherwise.

Хотфикс `sing-box lxd update` на роутерах. Рестарт службы под procd мог запустить новый демон раньше, чем старый освободил TUN-интерфейс: ядро падало с `TUNSETIFF: device or resource busy`, демон оставался без VPN, а апдейтер всё равно сообщал `done`. Теперь демон при загрузке повторяет открытие занятого TUN до 10 с, а апдейтер ждёт до 20 с, пока само ядро не сообщит `started`, иначе откатывается.

## 🐛 Fixed

### 🔁 The core did not start after a service restart under procd

- Symptom: after `lxd update` (or a plain `/etc/init.d/sing-box-lxd restart`) the daemon's log said `boot from last-good; staying up — … open tun: TUNSETIFF: device or resource busy`, the launcher got `service is not started`, and the VPN stayed down until a manual restart (about 80 s in the live run).
- Cause: procd starts the new process a few seconds before the old one has torn down its TUN, and the kernel keeps the interface until the old descriptor closes.
- Now: at boot the daemon retries the whole core start every 500 ms for up to 10 s while the error is `EBUSY`. Any other error is still final at once. Only the boot path is affected; `POST /admin/apply` is unchanged. (SPEC 129)

### ✅ `lxd update` no longer reports `done` when the daemon is up but the core is not

- Before: the health step only asked the init whether the service was running, which is true for a daemon that lost the TUN race.
- Now, after the init says running, the updater polls the new daemon's `GET /admin/status` once a second for up to 20 s:
  - `started` → `core started`, `done`, exit 0;
  - `fatal`, or still `idle` after 20 s → the old binary is restored and the service restarted, `ERROR: <ver> is up but the core did not start: <last_error>, rolled back to <old>`, exit 2;
  - no answer at all (daemon unreachable, wrong secret) → `core status unknown (…); the service is running, not rolling back`, exit 0;
  - no probe possible (no `daemon.json`, `listen` only on LAN addresses, core stopped by the operator) → `core status not checked: <why>`, exit 0.
- The address, secret and `tls` come from `daemon.json` in the state directory, as for `lxd client`. (SPEC 129)

## 🔧 Changed

### 🔑 `GET /admin/status` is also readable from the host without a client certificate

- A request from a loopback peer without a certificate is served on the operator path with the Bearer secret from `daemon.json` — this is how `lxd update` learns whether the core came up.
- A trusted certificate, or any non-loopback peer, takes the pinned path exactly as before; a remote client without a certificate still gets `401 client certificate not trusted`.

## 🧰 Under the hood

- Base: sing-box `v1.14.3`, zero drift from `upstream/stable`; submodules and dependencies unchanged since lx.16. Go 1.26.8.
- Unit tests for the retry, the operator route and the core wait. The fix itself has not yet been exercised on a router: the next `lxd update` (lx.16 → lx.17) runs on the old lx.16 updater, so the new health step takes effect from the update after that; the boot retry is in lx.17 and applies to that restart already.

## 🐛 Исправлено

### 🔁 Ядро не запускалось после рестарта службы под procd

- Симптом: после `lxd update` (или обычного `/etc/init.d/sing-box-lxd restart`) в логе демона `boot from last-good; staying up — … open tun: TUNSETIFF: device or resource busy`, лаунчер получал `service is not started`, VPN лежал до ручного рестарта (в живом прогоне — около 80 с).
- Причина: procd запускает новый процесс на несколько секунд раньше, чем старый разобрал свой TUN, а ядро держит интерфейс, пока не закрыт старый дескриптор.
- Теперь: при загрузке демон повторяет весь старт ядра каждые 500 мс до 10 с, пока ошибка — `EBUSY`. Любая другая ошибка по-прежнему окончательна сразу. Затронута только загрузка; `POST /admin/apply` не изменился. (SPEC 129)

### ✅ `lxd update` больше не сообщает `done`, когда демон жив, а ядро нет

- Было: шаг здоровья спрашивал только init, работает ли служба, а для демона, проигравшего гонку за TUN, это правда.
- Стало: после «running» от init апдейтер опрашивает `GET /admin/status` нового демона раз в секунду до 20 с:
  - `started` → `core started`, `done`, код 0;
  - `fatal` или всё ещё `idle` через 20 с → старый бинарь возвращается, служба перезапускается, `ERROR: <ver> is up but the core did not start: <last_error>, rolled back to <old>`, код 2;
  - ни одного ответа (демон недостижим, неверный секрет) → `core status unknown (…); the service is running, not rolling back`, код 0;
  - проба невозможна (нет `daemon.json`, `listen` только на LAN-адресах, ядро остановлено оператором) → `core status not checked: <почему>`, код 0.
- Адрес, секрет и `tls` берутся из `daemon.json` в state-каталоге, как у `lxd client`. (SPEC 129)

## 🔧 Изменено

### 🔑 `GET /admin/status` читается с хоста и без клиентского сертификата

- Запрос с loopback-пира без сертификата обслуживается операторским путём с Bearer-секретом из `daemon.json` — так `lxd update` узнаёт, поднялось ли ядро.
- Доверенный сертификат и любой не-loopback пир идут прежним пином; удалённый клиент без сертификата по-прежнему получает `401 client certificate not trusted`.

## 🧰 Под капотом

- База: sing-box `v1.14.3`, дрейф от `upstream/stable` 0; сабмодули и зависимости с lx.16 не менялись. Go 1.26.8.
- Юнит-тесты на ретрай, операторский маршрут и ожидание ядра. На роутере сам фикс ещё не прогонялся: ближайший `lxd update` (lx.16 → lx.17) выполняет старый апдейтер lx.16, поэтому новый шаг здоровья заработает со следующего обновления; ретрай на загрузке уже в lx.17 и действует на этом же рестарте.
