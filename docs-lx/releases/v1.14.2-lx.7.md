Three cases where a `masque` node hung without reporting an error are fixed: `vhttp: auto` stuck on h2 until restart, closing an h2 tunnel behind a stalled write, and an h3 endpoint that accepts the connection but never answers CONNECT-IP. Configs are unchanged.

Исправлены три случая, когда узел `masque` зависал без ошибки: `vhttp: auto`, застрявший на h2 до рестарта, закрытие h2-туннеля за зависшей записью и h3-эндпоинт, который принял соединение и не ответил на CONNECT-IP. Конфиги не меняются.

## 🐛 Fixed

### 🔁 `vhttp: auto` returns to h3 when the remembered h2 stops working

- Was: once a tunnel came up on h2, `auto` remembered h2 and tried only h2 from then on. If h2 stopped coming up (for example after moving to a network where TCP to the endpoint is closed and UDP is open), every dial failed until the process was restarted.
- Now: a failed remembered h2 drops the memory and h3 is tried within the same dial. If h3 comes up it is remembered; if both fail the error carries both causes and the next dial starts from h3.
- Not affected: an explicit `vhttp: h2` never turns into h3; a dial cancelled by the caller changes nothing.

### 🔌 Closing an h2 tunnel no longer waits for a stalled write

- Was: on a path that stopped accepting data, closing the tunnel queued behind the stalled write and waited for the TCP timeout of the OS (minutes). Until then the node kept handing out the dead tunnel, and shutdown of the core waited too.
- Now: the socket is closed at once and the stalled write fails. The farewell `RST_STREAM` is sent only when no write is in progress, bounded by 1 s.

### ⏱️ h3: a silent endpoint no longer holds the dial

- Was: if the endpoint completed the QUIC handshake and never answered the CONNECT-IP request, the wait lasted as long as the connection lived. With `vhttp: h3` every dial of the node queued behind it; with `auto` the fallback to h2 worked, but the abandoned h3 attempt stayed alive together with its connection.
- Now: waiting for the response ends when the dial is cancelled or times out. ([SPEC 108](https://github.com/Leadaxe/sing-box-lx/blob/lx/SPECS/TASKS/108-MASQUE_UNBOUNDED_WAITS/SPEC.md))

## 🐛 Исправлено

### 🔁 `vhttp: auto` возвращается к h3, когда запомненный h2 перестал работать

- Было: после того как туннель поднялся по h2, `auto` запоминал h2 и дальше пробовал только его. Если h2 переставал подниматься (например, после перехода в сеть, где TCP до эндпоинта закрыт, а UDP открыт), каждый dial отказывал до рестарта процесса.
- Стало: отказ запомненного h2 сбрасывает память, и в том же dial пробуется h3. Поднялся h3 — запоминается он; отказали оба — ошибка несёт обе причины, следующий dial начинает с h3.
- Не затронуто: явный `vhttp: h2` в h3 не превращается; dial, отменённый вызывающим, ничего не меняет.

### 🔌 Закрытие h2-туннеля больше не ждёт зависшую запись

- Было: на пути, который перестал принимать данные, закрытие туннеля вставало в очередь за зависшей записью и ждало TCP-таймаута ОС (минуты). Всё это время узел раздавал мёртвый туннель, а остановка ядра тоже ждала.
- Стало: сокет закрывается сразу, зависшая запись получает ошибку. Прощальный `RST_STREAM` уходит, только если запись не идёт, и ограничен 1 с.

### ⏱️ h3: молчащий эндпоинт больше не держит dial

- Было: если эндпоинт завершил QUIC-хендшейк и не ответил на запрос CONNECT-IP, ожидание длилось, пока живо соединение. При `vhttp: h3` за ним в очередь вставали все dial узла; при `auto` фолбэк на h2 срабатывал, но брошенная попытка h3 оставалась жить вместе со своим соединением.
- Стало: ожидание ответа заканчивается, когда dial отменён или истёк его срок. ([SPEC 108](https://github.com/Leadaxe/sing-box-lx/blob/lx/SPECS/TASKS/108-MASQUE_UNBOUNDED_WAITS/SPEC.md))
