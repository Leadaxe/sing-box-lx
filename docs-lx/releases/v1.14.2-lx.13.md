The QUIC decoy of AmneziaWG (`ip=quic`) is now generated fresh before every WireGuard handshake instead of being baked once for the endpoint's lifetime, and the `ib=chrome` / `ib=firefox` profiles now send a real QUIC ClientHello of the browser rather than a TCP-shaped one. Verified on a phone over LTE: `chrome`, `firefox` and the generic form all bring a WARP tunnel up where plain WireGuard does not. `ip=sip` sends only the INVITE; `ip=dns` carries no EDNS options.

## 🆕 What's new

### 🧪 `ib=chrome-full` — Chrome 155 with ML-KEM in one oversized Initial (experimental)

- Same Chrome profile, but the hybrid `X25519MLKEM768` key share is kept: a ~1.75 KB ClientHello sent whole in a single ~2 KB Initial that is IP-fragmented on the wire.
- For test benches only: it does **not** pass over LTE (fragments are dropped on the path). Client UIs (LxBox, launcher) do not expose it.

## 🔧 Changed

### 🌐 `ib=chrome` and `ib=firefox` — the browser's QUIC ClientHello, laid out like the browser

- `chrome`: Chrome 155 without post-quantum key share (~470 bytes), Chrome's QUIC extension set and transport parameters (`initial_rtt` always present, shuffled order, GREASE parameter), frames split the way Chrome's chaos protector does — 2–10 CRYPTO pieces, 2–10 PING, padding spread, shuffled. One 1250-byte Initial, packet number 1.
- `firefox`: Firefox 148 without post-quantum (~665 bytes) matched against a Firefox 149 capture: NSS cipher order, 15 extensions in capture order, Firefox transport parameters, 3-byte source connection ID, 2-byte packet number, zeros after the packet up to 1252 bytes.
- `""` / `curl`: generic ~294-byte ClientHello, one CRYPTO plus PADDING, unchanged.
- Device-verified over LTE (09.10.2026, control: plain WireGuard does not come up): `chrome`, `firefox`, `curl` all bring the tunnel up. What matters on the path is a valid Initial with the whole ClientHello in one packet under MTU; the ClientHello contents do not change the outcome.

### 📞 `ip=sip` — INVITE only

- The second packet, `SIP/2.0 100 Trying`, is gone: it is a server reply and a client never sends it. An explicit `i2` next to `ip=sip` is no longer a conflict and is sent as given.

### 🔍 `ip=dns` — EDNS without options

- The unknown EDNS option `0xFDE9` with 40 random bytes (a leftover of WireSock's server-side tail) is removed; the query is header, HTTPS question and an empty OPT, ~43 bytes.
- Over LTE neither `dns` nor `sip` brings a WARP tunnel up — only the QUIC decoy does. Use them against servers that answer such a decoy (WireSock proxy).

### 🧭 Picking `id`

- The decoy's domain must be routed the same way as the WireGuard endpoint: a router that routes by the first UDP packet's SNI moves the whole flow, decoy and WireGuard alike. (SPEC 009)

## 🐛 Fixed

### 🔁 The QUIC decoy was byte-identical for the endpoint's lifetime

- The decoy datagram was baked into the AmneziaWG blob when the endpoint was created and resent unchanged before every handshake initiation — start, rekey every 120 s, wake-up, reconnect — with the same connection ID: a hash signature for DPI and a stable device identifier.
- Now the engine asks for a fresh Initial before every handshake: new connection IDs, random, key share, frame layout and ciphertext each time. `dns` / `stun` / `sip` stay static templates with the `<r>` entropy they had.

### 🧩 `ib=chrome` / `ib=firefox` sent a TCP ClientHello inside QUIC

- Since 18.06.2026 every release sent the browser's TCP-shaped ClientHello in the decoy: TLS 1.2 ciphers, GREASE cipher, TCP-only extensions and no `quic_transport_parameters`. A real QUIC server rejects that. Fixed by the profiles above.

## 🧰 Under the hood

- Base: sing-box `v1.14.2`, same upstream `stable` commit as lx.12. Upstream `v1.14.3` (network reset on DNS server changes on macOS, legacy macOS build fix, a sing-tun bump) landed after the release candidate and is deliberately deferred to the next sync: this stable is the exact code run on the device.
- The wireguard-go fork gains one hook for per-handshake decoy generation; capture files Chrome 147 / Firefox 149 (BSD-3, from wiresock-boringtun) back a parity test that decrypts them and compares extensions and transport parameters.

### 🔍 `ip=dns` — EDNS без опций

- Убрана неизвестная EDNS-опция `0xFDE9` с 40 случайными байтами (наследие серверного хвоста WireSock); запрос — заголовок, вопрос HTTPS и пустой OPT, ~43 байта.
- В LTE ни `dns`, ни `sip` туннель к WARP не поднимают — только QUIC-decoy. Использовать против серверов, отвечающих на такой decoy (WireSock proxy).

### 🧭 Выбор `id`

- Домен decoy должен роутиться туда же, куда WireGuard-endpoint: роутер, ведущий трафик по SNI первого UDP-пакета, уводит весь поток, и decoy, и WireGuard. (SPEC 009)

## 🐛 Исправлено

### 🔁 QUIC-decoy был байт-в-байт одинаковым весь срок жизни endpoint'а

- Датаграмма decoy запекалась в блоб AmneziaWG при создании endpoint'а и уходила без изменений перед каждым handshake initiation — старт, rekey каждые 120 с, пробуждение, реконнект — с тем же connection ID: хеш-сигнатура для DPI и постоянный идентификатор устройства.
- Теперь движок запрашивает свежий Initial перед каждым хендшейком: новые connection ID, random, key share, раскладка фреймов и шифртекст. `dns` / `stun` / `sip` остаются статичными шаблонами с прежней `<r>`-энтропией.

### 🧩 `ib=chrome` / `ib=firefox` слали TCP-ClientHello внутри QUIC

- С 18.06.2026 все релизы отправляли в decoy TCP-форму ClientHello браузера: шифры TLS 1.2, GREASE-шифр, TCP-only расширения и без `quic_transport_parameters`. Настоящий QUIC-сервер такое отвергает. Исправлено профилями выше.
