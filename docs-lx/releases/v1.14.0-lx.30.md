## 🐛 Fixed

### 🧵 DNS over an XHTTP detour: `write request: context canceled` on every query

A DNS server of type `udp`, `tcp` or `tls` with `detour` pointing at a VLESS+XHTTP node failed on the first query. Symptoms:

- URL tests of `masque` and `wireguard` nodes against a domain URL went red with `lookup …: write request: context canceled`, while the same node tested by IP URL was green — the tunnel was fine, the name was not resolving.
- System DNS through TUN returned nothing for uncached names; the DNS query stream reported `source: failed`.
- DoH (`https`) through the same node kept working, because it uses its own HTTP client and no connection pool.

Cause: the DNS transport pool cancels its dial context immediately after `dial` returns — the standard `net.Dialer` contract every other transport relies on. The XHTTP dial handed the connection up before the stream was raised and kept watching that context until the download response, which in `stream-one` only arrives after the first write. The cancellation therefore always landed after the dial had returned, and the first DNS write was killed by the client's own error.

This never worked, and `auto` with REALITY resolves to `stream-one`, so a default configuration was affected.

Fix: `DialContext` for `stream-one` and `stream-up` now returns only once the HTTP layer has accepted the request body. The download response is still not awaited, so a server that withholds it until the first uplink byte does not deadlock the dial. After the dial returns, the dial context no longer affects the connection at all.

- A raise that fails before the body is accepted now fails the **dial**, carrying the real cause instead of `context canceled`.
- A half-alive node on a cold pool fails the dial within the caller's own deadline, with the pipe broken and the pooled slot returned.
- `packet-up` is unchanged: it has no upload pipe, and each of its uploads is a separately bounded POST.

Trade-off: a warm pooled connection to a peer that died silently accepts the body instantly, so such a node is now caught by `xmux.h_keep_alive_period`, by the WireGuard handshake give-up, or by the caller's read deadline, rather than by the 15-second dial deadline. (SPEC 077)

### 🔁 Pooled XHTTP connection could be released twice on a failed dial

The raise-failure path already returned the pooled connection to the xmux pool, and the dial's error path returned it a second time. Before this release a dial could not fail after creating the connection, so the double release was unreachable; with the new contract it becomes reachable and would drive the pool's live-stream counter negative, leaving a retired connection alive forever. One release handle now covers the whole dial. (SPEC 077)

## 🐛 Исправлено

### 🧵 DNS через XHTTP-detour: `write request: context canceled` на каждом запросе

DNS-сервер типа `udp`, `tcp` или `tls` с `detour` на узел VLESS+XHTTP падал с первого запроса. Симптомы:

- URL-тесты `masque`- и `wireguard`-узлов по доменному адресу краснели с `lookup …: write request: context canceled`, при этом тот же узел по IP-адресу давал зелёный отклик — туннель был исправен, не резолвилось имя.
- Системный DNS через TUN не отвечал на некэшированные имена, в потоке DNS-запросов стояло `source: failed`.
- DoH (`https`) через тот же узел работал: у него свой HTTP-клиент и нет пула соединений.

Причина: пул DNS-транспорта отменяет dial-контекст сразу после возврата из `dial` — это штатный контракт `net.Dialer`, на который рассчитывают все остальные транспорты. XHTTP-дайл отдавал соединение наверх до подъёма стрима и продолжал слушать этот контекст до download-ответа, а в режиме `stream-one` ответ приходит только после первой записи. Отмена поэтому всегда наступала уже после возврата, и первая же запись DNS-запроса умирала от нашей собственной ошибки.

Не работало никогда, а режим `auto` при включённом REALITY выбирает именно `stream-one` — то есть задет был конфиг по умолчанию.

Что стало: `DialContext` для `stream-one` и `stream-up` возвращает соединение только после того, как HTTP-слой принял тело запроса. Download-ответ по-прежнему не ждётся, поэтому сервер, придерживающий его до первого байта uplink, не вешает дайл. После возврата dial-контекст на соединение не влияет.

- Провал подъёма стрима до принятия тела теперь валит **сам дайл** и несёт настоящую причину вместо `context canceled`.
- Полуживой узел на холодном пуле даёт ошибку в пределах дедлайна вызывающего, pipe разорван, слот пула возвращён.
- Режим `packet-up` не менялся: у него нет upload-пайпа, а каждая отправка — отдельный POST со своим бюджетом.

Цена решения: тёплое соединение пула к молча умершему узлу принимает тело мгновенно, поэтому такой узел теперь отлавливается через `xmux.h_keep_alive_period`, через give-up рукопожатия WireGuard или через read-deadline вызывающего, а не 15-секундным дедлайном дайла. (SPEC 077)

### 🔁 Слот пула XHTTP мог освободиться дважды на ошибочном дайле

Путь провала подъёма стрима уже возвращал соединение в пул xmux, и путь ошибки дайла возвращал его второй раз. До этого релиза дайл не мог упасть после создания соединения, поэтому двойной возврат был недостижим; с новым контрактом он достижим и увёл бы счётчик живых стримов в минус, а снятое с ротации соединение не закрылось бы никогда. Теперь на весь дайл один хэндл освобождения. (SPEC 077)
