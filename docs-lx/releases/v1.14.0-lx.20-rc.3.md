## 🐛 Fixed

### 📶 Switching WiFi↔mobile while the tunnel was starting killed the app

Reported from the field: the app simply crashed. The crash bundle pointed at
the routine "reset network" action the app performs whenever the default
network changes — normally harmless, and exactly what keeps connections alive
when you walk out of WiFi range.

The problem was timing. That action was allowed to run as soon as the core
object existed, but a tunnel needs a moment to finish assembling itself, and
during that moment the parts the action reaches for are not there yet. If the
network happened to change inside that window — a few hundred milliseconds
around tunnel start, wider when the core was busy opening its cache file — the
process died instead of ignoring the request. Switching networks right as you
tap connect was enough to hit it.

Such commands now wait until the tunnel is actually up, and are quietly
ignored before that. Once running, behaviour is unchanged: a network switch
still drops stale sockets as before. The bug is older than this release.
(SPEC 047)

### 💥 A connection to a dead node could take down the whole tunnel

Also reported from the field, from a second crash bundle. A TCP connection
that never completes — the server stays silent, refuses, or times out — is an
everyday event: subscriptions accumulate dead nodes, latency tests probe them,
and a reconnect after a network change retries them all at once. Such a
connection is supposed to fail on its own and leave everything else alone.

Instead, under a narrow race it could crash the entire process. When a failed
connection was being cleaned up, part of its state was released a fraction of
a second before the connection was formally closed; a network packet arriving
in that gap was handed to code that assumed the state was still there. The
result was not a dropped connection but a dead VPN. It struck rarely and
unpredictably, which is why it looked like a random crash — but it grew more
likely exactly when many connections were failing at once.

The gap is now closed: a packet arriving too late is ignored instead of
crashing. This lives in the network stack the tunnel is built on, so the fix
ships as a patched copy of that component. (SPEC 048)

## 🔧 Build

### The Go toolchain version is now stated in the source tree

Anyone rebuilding this core from source — F-Droid in particular, which compiles
it in its own sandbox — previously had no way to learn which Go version the
official builds use. The obvious candidate, `go.mod`, names an older version
that is known to break every QUIC-based protocol on some Android devices, so
reading it would have produced a subtly broken build.

A `go.version` file in the repository root now states that version, and our own
build jobs read it from there instead of repeating it in a dozen places. For
users this changes nothing directly; it makes builds from source reproducible
and unblocks packaging by third parties. (SPEC 049)

## 🐛 Исправлено

### 📶 Смена WiFi↔мобильной сети в момент запуска туннеля роняла приложение

Жалоба с поля: приложение просто крашилось. Крашбандл указал на штатное
действие «сброс сети», которое приложение выполняет при каждой смене сети по
умолчанию — обычно безобидное и именно оно сохраняет соединения живыми, когда
вы выходите из зоны WiFi.

Дело было в моменте. Этому действию разрешалось выполняться, как только
появлялся объект ядра, — но туннелю нужно время, чтобы собраться до конца, и в
эти мгновения тех частей, к которым действие обращается, ещё не существует.
Если смена сети попадала ровно в это окно — несколько сотен миллисекунд вокруг
старта туннеля, шире, когда ядро занято открытием своего файла кеша, — процесс
умирал вместо того, чтобы проигнорировать запрос. Достаточно было переключить
сеть ровно в момент подключения.

Теперь такие команды дожидаются, пока туннель действительно поднимется, а до
того тихо игнорируются. На работающем туннеле поведение прежнее: смена сети
по-прежнему закрывает протухшие сокеты. Баг старше этого релиза. (SPEC 047)

### 💥 Соединение с мёртвой нодой могло уронить весь туннель

Тоже жалоба с поля, из второго крашбандла. TCP-соединение, которое так и не
устанавливается — сервер молчит, отвечает отказом или отваливается по
таймауту, — событие ежедневное: в подписках копятся мёртвые ноды, их
простукивают тесты задержки, а переподключение после смены сети пробует их все
разом. Такое соединение должно тихо отвалиться само, не задев остальное.

Вместо этого в узкой гонке оно могло уронить процесс целиком. Когда неудачное
соединение убиралось, часть его состояния освобождалась на доли секунды
раньше, чем соединение формально закрывалось; пришедший в этот зазор сетевой
пакет попадал в код, считавший, что состояние ещё на месте. Итогом был не
разрыв одного соединения, а мёртвый VPN. Срабатывало редко и непредсказуемо,
оттого и выглядело случайным крашем, — но вероятность росла ровно тогда, когда
неудачных соединений было много сразу.

Зазор закрыт: опоздавший пакет теперь игнорируется, а не роняет ядро.
Проблема находится в сетевом стеке, на котором построен туннель, поэтому фикс
поставляется в виде исправленной копии этого компонента. (SPEC 048)

## 🔧 Сборка

### Версия Go-тулчейна теперь записана в исходниках

Тем, кто пересобирает ядро из исходников — прежде всего F-Droid, который
компилирует его в своей песочнице, — раньше неоткуда было узнать, какой версией
Go собираются официальные сборки. Очевидный кандидат, `go.mod`, называет более
старую версию, на которой на части Android-устройств отказывают все протоколы
на базе QUIC, — то есть чтение оттуда давало бы незаметно сломанную сборку.

Теперь версия записана в файле `go.version` в корне репозитория, и наши
сборочные задачи читают её оттуда, а не повторяют в десятке мест. Для
пользователей напрямую не меняется ничего; это делает сборку из исходников
воспроизводимой и открывает дорогу к упаковке сторонними каталогами. (SPEC 049)
