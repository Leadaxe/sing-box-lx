XHTTP nodes no longer get evicted from the `xmux` pool or fill the log with `ERROR` lines just because the client closed a connection itself. Under `urltest` inside a `selector` with `interrupt_exist_connections: true`, every switch closed a batch of XHTTP connections; the pool's breaker counted our own cancellations as stream failures and retired healthy connections, and the relay logged each normal close as `connection download closed: http2: response body closed`. Genuine failures — timeouts, resets, HTTP/2 stream errors, non-200 answers — are classified exactly as before.

XHTTP-узлы больше не вытесняются из пула `xmux` и не засоряют лог строками `ERROR` только потому, что клиент сам закрыл соединение. Под `urltest` внутри `selector` с `interrupt_exist_connections: true` каждое переключение закрывало пачку XHTTP-соединений; брейкер пула считал наши же отмены сбоями и списывал здоровые соединения, а релей писал каждое нормальное закрытие как `connection download closed: http2: response body closed`. Настоящие сбои — таймауты, сбросы, ошибки стримов HTTP/2, не-200 ответы — классифицируются как раньше.

## 🐛 Fixed

### 🧯 XHTTP: a connection closed by the client is not a failure

- Was: with `interrupt_exist_connections: true` on a `selector` or `urltest` group, every switch closed the group's live XHTTP connections. The pooled `xmux` connection saw the cancelled upload/download requests as stream failures; three in a row marked it `failing`, evicted it and armed a backoff on opening a replacement (`xhttp: xmux: evicted connection (cause=failing)`). Six variants of the same server under one `urltest` flap constantly, so this fired all the time. ([LxBox#148](https://github.com/Leadaxe/LxBox/issues/148))
- Now: a cancellation (`context.Canceled`) is neutral for the breaker — only the client itself or the caller can cancel a request context, so it says nothing about the pooled connection's health. Deadline expiry, connection resets, HTTP/2 stream errors and non-200 answers still count as failures, so the protection from issue #14 (a CDN resetting every stream) is unchanged.
- Also: closing an XHTTP connection made its blocked download read wake with `http2: response body closed`, which the relay does not recognise as a normal close and logged at ERROR on every successful request. That read now returns the standard closed-connection error (or a timeout error when it was the read deadline that closed the body), and the relay logs it at trace level like any other close. `io.EOF` from the server is passed through untouched.
- Applies to all XHTTP modes and to `dl=h1`/`h2`/`h3` download transports. Nothing to configure. ([SPEC 094](https://github.com/Leadaxe/sing-box-lx/blob/lx/SPECS/TASKS/094-XHTTP_LOCAL_CLOSE_NOT_FAILURE/SPEC.md))

- Unchanged: configuration (no new keys), the wire format, pool rotation limits (`xmux` section), other transports, Clash API, gRPC/lxd and the libbox signatures, the tag sets of desktop, router and AAR builds, the Go toolchain (1.26.8), the four submodules.
- Upstream base is unchanged — sing-box `v1.14.1`. Known drift at the cut: `upstream/stable` is 34 commits ahead, with bumps of `sing`, `sing-tun` and `wireguard-go` (v0.0.7) — two of them are fork submodules, so the whole set is deliberately left for a separate sync.
