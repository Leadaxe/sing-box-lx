Two long-standing ways the client could look "stuck" are gone. Connections
through a WireGuard node no longer hang for two silent minutes when the path
dies — they fail in fifteen seconds. And an auto-selecting group no longer keeps
sending traffic through a node that stopped answering: it now moves to a working
one on the spot, instead of waiting for its next scheduled test. REALITY nodes on
freshly updated Xray servers work again.

Ушли два давних сценария, в которых клиент выглядел «зависшим». Соединения через
WireGuard-узел больше не висят две молчаливые минуты, когда путь умер, — они

## 🐛 Fixed

### 🕳️ Two silent minutes on a dead WireGuard path

When the path to a node went quiet — the Wi-Fi network dropping the tunnel's
UDP, a node going down, a radio falling asleep — every connection through that
node hung for about two minutes before failing, with nothing in the log. Apps
gave up on their own timeouts first and retried into the same dead node, so the
whole client read as frozen. For domain destinations it could be worse: each
resolved address waited its own two minutes in turn.

The cause is old and inherited from upstream sing-box, not specific to this
fork: the five-second connect timeout only ever applied to ordinary system
sockets, and connections made inside a WireGuard tunnel take a different path
that no layer bounded. What was left was the network stack's own retry ladder,
which gives up only after 127 seconds.

Those connections now fail in fifteen seconds. That number is deliberate: it
matches the budget node health-checks already use, so a slow-but-alive node
cannot pass its checks while every real connection through it dies. Legitimate
slow connects were measured before choosing it — a cold node that has to rebuild
its device and redo a handshake needs about five seconds locally and eight to ten
on a real mobile network, so fifteen leaves room. The limit applies only while
the connection is being established and is released the moment it succeeds; it
can never cut a working download. UDP is untouched. The same fix covers OpenVPN,
OpenConnect and Tailscale endpoints, which had the identical flaw. (SPEC 052)

### 🎯 An auto group staying on a node that stopped working

Groups in the default automatic mode picked their node from the last health-check
and only reconsidered at the end of the next scheduled run — up to three minutes
later, longer with passive checking enabled. A failed connection changed nothing.
So when a node died, traffic kept being aimed at it: with the fix above the user
now got an error every fifteen seconds instead of a two-minute hang, but still
through the same dead node.

Now a failure that means "this path is dead" — a connect timeout, an unreachable
network — marks the node and immediately retries the same request through the
next best one. Two attempts at most; if the retry succeeds the group moves its
selection there, without disturbing connections that are already running.
A connection refused or reset by the destination does not count: the node
delivered the packet and the site answered, so another node would be refused
too. Neither does a request the app itself cancelled.

If the node that was fastest collects three such marks, the group switches its
ranking: fewest marks first, then speed among those tied — usually all the
healthy ones, which then compete on speed exactly as before. A mark is only ever
cleared by proof of life: a successful connection or an answered health-check
probe, never by time passing. If every candidate ends up marked — the network
itself is down, not the nodes — the group forces a fresh round of checks, at most
once every two minutes. Nothing here runs on a timer, so device sleep and
system-level app freezing cannot desynchronise it. Round-robin groups are
unaffected. (SPEC 054)

### 🔒 REALITY nodes rejected by updated Xray servers

Xray v26.7.11 began requiring a minimum client version by default, and sing-box
still announced a version from 2023 — below the new threshold. The failure is
invisible by design: rather than refusing, the server quietly serves its cover
website, so the node looks broken with a clean log, indistinguishable from a
wrong key or a clock skew. The announced version now matches the required
minimum; older servers are unaffected. (SPEC 053)

## 🐛 Исправлено

### 🕳️ Две молчаливые минуты на мёртвом WireGuard-пути

Когда путь до узла замолкал — Wi-Fi-сеть резала UDP туннеля, узел выключался,
радио засыпало — каждое соединение через этот узел висело около двух минут и
только потом отваливалось, ничего не написав в лог. Приложения сдавались раньше
по своим таймаутам и повторяли попытку через тот же мёртвый узел, поэтому
клиент целиком выглядел зависшим. Для доменных назначений бывало хуже: каждый
разрезолвленный адрес отстаивал свои две минуты по очереди.

Причина давняя и унаследована от апстримного sing-box, а не своя: пятисекундный
таймаут соединения всегда применялся только к обычным системным сокетам, а
соединения внутри WireGuard-туннеля идут другим путём, который никто не
ограничивал. Оставалась лишь собственная лестница повторов сетевого стека — она
сдаётся через 127 секунд.

Теперь такие соединения отваливаются за пятнадцать секунд. Число выбрано не
наугад: столько же отведено проверкам здоровья узлов, и если бы пользовательский
бюджет был меньше, появилась бы вилка — медленный, но живой узел проходит
проверки, а все реальные соединения через него падают. Перед выбором замерили
честные медленные соединения: холодному узлу, которому надо пересобрать
устройство и заново сделать рукопожатие, нужно около пяти секунд локально и
восемь-десять на реальной мобильной сети, так что пятнадцать оставляют запас.
Ограничение действует только на время установки соединения и снимается сразу
после успеха — оборвать работающую загрузку оно не может. UDP не затронут. Та же
правка закрывает эндпоинты OpenVPN, OpenConnect и Tailscale — у них был ровно
тот же изъян. (SPEC 052)

### 🎯 Группа с автовыбором, застрявшая на переставшем работать узле

Группы в автоматическом режиме брали узел из последней проверки здоровья и
пересматривали выбор только в конце следующего планового прогона — до трёх минут
спустя, а с пассивной проверкой и дольше. Неудачное соединение не меняло ничего.
Поэтому когда узел умирал, трафик продолжал идти в него: с правкой выше
пользователь стал получать ошибку каждые пятнадцать секунд вместо двухминутного
зависания, но всё через тот же мёртвый узел.

Теперь отказ, означающий «этот путь мёртв» — таймаут соединения, недоступная
сеть, — помечает узел и тут же повторяет тот же запрос через следующий по
качеству. Попыток не больше двух; если повтор удался, группа переносит туда свой
выбор, не трогая уже работающие соединения. Отказ или сброс со стороны
назначения не считается: узел донёс пакет и сайт ответил, значит через другой
узел будет тот же отказ. Не считается и запрос, который отменило само
приложение.

Если самый быстрый узел набирает три такие пометки, группа меняет правило
выбора: сначала меньше пометок, затем скорость среди равных — а равных обычно
все здоровые, и они соревнуются по скорости ровно как раньше. Пометка снимается
только доказательством жизни: успешным соединением или ответом на пробу, но
никогда — просто по времени. Если помеченными оказались все кандидаты (значит,
умерла сама сеть, а не узлы) — группа принудительно запускает новый круг
проверок, не чаще раза в две минуты. Ничего из этого не работает на таймерах,
поэтому ни сон устройства, ни системная заморозка приложения не собьют логику.
Групп в режиме round_robin изменения не касаются. (SPEC 054)

### 🔒 REALITY-узлы, отвергаемые обновлёнными серверами Xray

Xray v26.7.11 стал по умолчанию требовать минимальную версию клиента, а sing-box
всё ещё объявлял версию 2023 года — ниже нового порога. Отказ невидим по
задумке: вместо отказа сервер тихо отдаёт свой камуфляжный сайт, поэтому узел
выглядит сломанным при чистом логе и неотличим от неверного ключа или
разъехавшихся часов. Объявляемая версия теперь совпадает с требуемым минимумом;
на старые серверы это не влияет. (SPEC 053)
