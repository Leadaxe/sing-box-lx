`lxd` runs the admin's own scripts at the core's lifecycle boundaries (`pre_start`, `post_start`, `post_reload`, `post_stop`) with the facts of the core in the environment, so system DNS and similar host policy can follow the TUN. Two fixes from field dumps: the core no longer waits 10–16 s on start for an unrelated mux handshake, and a masque `vhttp: auto` goroutine no longer pins the previous core instance after every in-process reload — on a router this ate both CPU cores within days.

## 🆕 What's new

### 🪝 lxd hooks: your scripts at the core's lifecycle boundaries

- Four scripts in `<state_dir>/hooks/`: `pre_start`, `post_start`, `post_reload`, `post_stop`. The daemon creates the directory and a stub for every missing script at each start; a stub left as created is "not configured" and the event is skipped with a Warn.
- `daemon.json`: `hooks.enabled` (default `false`), `hooks.timeout_seconds` (default 15), `hooks.unsafe_skip_owner_check`.
- Facts in the environment: `LXD_EVENT`, `LXD_REASON`, `LXD_CLIENT`, `LXD_CONFIG_SHA`, `LXD_TUN_ADDRESS` / `LXD_TUN_INTERFACE` / `LXD_TUN_MTU` / `LXD_TUN_AUTO_ROUTE` and their `_PREV` twins, `LXD_ERROR`.
- `pre_start` is fail-closed; `post_*` must be idempotent. `post_stop(fatal)` after a failed start, `post_reload(rollback)` after a rollback, `post_stop(recover)` at boot when `hooks/core_snapshot.json` says the previous process never reached `post_stop`.
- Synchronous, output in `<log dir>/hooks/<event>.log`, timeout → `SIGKILL` to the process group, `flock` across daemon processes, root-owned gate before every run; `hooks` state in `GET /admin/status`. The OpenWrt installer sets `term_timeout 30` so procd does not kill `post_stop` mid-way.
- Unix only; on Windows the key is ignored with a Warn. Main use: system DNS onto the TUN and back, the policy stays with the admin. (FEATURE 014)

## 🐛 Fixed

### 🧠 masque `vhttp: auto`: the previous core instance stayed in memory after every reload

- When the h3 leg failed before the fallback timer and h2 then came up, a "drain" goroutine waited forever on a result that was already taken. Its closure kept the outbound and, through the core context, the whole closed instance: TUN with its GRO tables, WireGuard devices with their receive pools, NAT tables.
- Every in-process reload (`lxd` apply, Stop/Start from the launcher, a profile switch in the app) left one more dead instance behind. On a router with `GOMEMLIMIT=200MiB` the heap hit the limit within days and the GC ran continuously: 94 % on both cores at zero traffic, ~40 TUN instances in the heap with one live read loop. Removing nodes from the config or restarting the core inside the daemon did not help; only a process restart did.
- Now the drain runs only for a leg that has not answered yet. Affected since `v1.14.0-lx.27`. The installer's `GOMEMLIMIT` is unchanged. (SPEC 137)

### ⏱️ Core start waited 10–16 s for an unrelated mux handshake

- `ReferenceManager.Start` called `update()` synchronously, which asked every unreferenced mux outbound to close idle connections — under a sing-mux lock that a URL test started at `PostStart` holds for the whole network dial. Start waited for that handshake to finish or time out.
- The first `update()` now runs off the start path; `update` itself stays single-threaded. Seen on Android with 55 outbounds, 13 groups and two `vless` + ws + `multiplex` nodes. (SPEC 136)

## 🆕 Что нового

### 🪝 Хуки lxd: ваши скрипты на границах жизненного цикла ядра

- Четыре скрипта в `<state_dir>/hooks/`: `pre_start`, `post_start`, `post_reload`, `post_stop`. Демон создаёт каталог и заготовку для каждого отсутствующего скрипта на каждом старте; нетронутая заготовка = «не настроено», событие пропускается с Warn.
- `daemon.json`: `hooks.enabled` (по умолчанию `false`), `hooks.timeout_seconds` (по умолчанию 15), `hooks.unsafe_skip_owner_check`.
- Факты в окружении: `LXD_EVENT`, `LXD_REASON`, `LXD_CLIENT`, `LXD_CONFIG_SHA`, `LXD_TUN_ADDRESS` / `LXD_TUN_INTERFACE` / `LXD_TUN_MTU` / `LXD_TUN_AUTO_ROUTE` и их пары `_PREV`, `LXD_ERROR`.
- `pre_start` — fail-closed; `post_*` должны быть идемпотентными. `post_stop(fatal)` после провального старта, `post_reload(rollback)` после отката, `post_stop(recover)` при загрузке, если `hooks/core_snapshot.json` говорит, что прошлый процесс до `post_stop` не дошёл.
- Синхронно, вывод в `<каталог лога>/hooks/<event>.log`, таймаут → `SIGKILL` группе процессов, `flock` между процессами демона, проверка владельца root перед каждым запуском; состояние `hooks` в `GET /admin/status`. Инсталлятор OpenWrt ставит `term_timeout 30`, чтобы procd не убивал `post_stop` на полпути.
- Только Unix; на Windows ключ игнорируется с Warn. Главный сценарий — системный DNS на TUN и обратно, политика остаётся у администратора. (FEATURE 014)

## 🐛 Исправлено

### 🧠 masque `vhttp: auto`: предыдущий экземпляр ядра оставался в памяти после каждой пересборки

- Когда h3 отказывал до таймера фолбэка, а h2 поднимался, «дренажная» горутина вечно ждала результат, который уже был забран. Её замыкание держало outbound, а через контекст ядра — весь закрытый экземпляр: TUN с GRO-таблицами, WireGuard-устройства с приёмными пулами, NAT-таблицы.
- Каждая пересборка внутри процесса (apply в `lxd`, Stop/Start из лаунчера, смена профиля в приложении) оставляла ещё один мёртвый экземпляр. На роутере с `GOMEMLIMIT=200MiB` куча упиралась в лимит за несколько дней, и GC работал непрерывно: 94 % на обоих ядрах при нулевом трафике, ~40 TUN-экземпляров в куче при одном живом read-loop. Снятие узлов из конфига и рестарт ядра внутри демона не помогали, помогал только рестарт процесса.
- Теперь дренаж запускается только для ноги, которая ещё не отвечала. Затронуты версии с `v1.14.0-lx.27`. `GOMEMLIMIT` инсталлятора не меняется. (SPEC 137)

### ⏱️ Старт ядра ждал 10–16 с чужой mux-handshake

- `ReferenceManager.Start` синхронно вызывал `update()`, который просил каждый неиспользуемый mux-outbound закрыть простаивающие соединения — под замком sing-mux, который URL-тест с `PostStart` держит на весь сетевой dial. Старт ждал, пока этот handshake закончится или отвалится по таймауту.
- Первый `update()` теперь выполняется вне стартового пути; сам `update` остаётся однопоточным. Снято на Android: 55 outbound'ов, 13 групп, два узла `vless` + ws + `multiplex`. (SPEC 136)
