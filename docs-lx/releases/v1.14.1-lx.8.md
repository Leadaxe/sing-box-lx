The gRPC transport now understands Xray's custom-path form of `service_name`. A value with a leading `/` — `"/xxx/something/Tun"` — is sent as that exact path, the way Xray itself builds it; before, the whole value was escaped as one segment and the server answered `v2ray-grpc: unexpected status: 404 Not Found`. Values without a leading `/` behave byte for byte as before. Not yet verified against a live Xray server — the wire path was checked against Xray's and grpc-go's source.

## 🔧 Changed

### 🔗 gRPC `service_name`: a leading `/` means Xray's custom path

- Was: a server configured the Xray way, `serviceName: "/xxx/something/Tun"` (typically behind nginx with the same `location`), could not be reached — `v2ray-grpc: unexpected status: 404 Not Found`. The client escaped the whole value as a single segment and sent `/%2Fxxx%2Fsomething%2FTun/Tun`. ([singbox-launcher#130](https://github.com/Leadaxe/singbox-launcher/issues/130))
- Now: a leading `/` switches to Xray's convention — each segment is escaped on its own, the last segment is the stream name, a `|…` multi-stream tail is dropped. `"/a/b/Tun"` goes on the wire as `/a/b/Tun`, `"/a/b/Stream"` as `/a/b/Stream`.
- Without a leading `/` nothing changed: `"TunService"` → `/TunService/Tun`, `"a/b"` → `/a%2Fb/Tun` (which is also what Xray sends for that form). A guard test pins this byte for byte.
- Applies to the client and to the server (inbound). The lite server still compares the decoded path, so it is more lenient than Xray: a server with `"a/b"` accepts both `/a%2Fb/Tun` and `/a/b/Tun`. The `with_grpc` client still sends the old form unescaped — upstream behaviour, not changed.
- Verification: the `:path` the client sends is captured by a bare HTTP/2 listener and compared with what Xray computes; the convention was checked against the source of Xray (`getServiceName`/`getTunStreamName`, `TunCustomName`) and grpc-go (raw `:path`, split at the last `/`). ⚠️ Not run against a live Xray server yet. ([SPEC 093](https://github.com/Leadaxe/sing-box-lx/blob/lx/SPECS/TASKS/093-GRPC_SERVICE_NAME_CUSTOM_PATH/SPEC.md), [docs §4.1](https://github.com/Leadaxe/sing-box-lx/blob/lx/docs-lx/protocols-transports.md))

- Unchanged: configuration (no new keys, no new validation), the wire format for every existing `service_name` without a leading `/`, all other transports, Clash API, gRPC/lxd and the libbox signatures, the tag sets of desktop, router and AAR builds, the Go toolchain (1.26.8), the four submodules.
- Upstream base is unchanged — sing-box `v1.14.1`. Known drift at the cut: `upstream/stable` is 10 commits ahead, together with a `wireguard-go` bump to v0.0.7. The WireGuard changes require re-basing the `wireguard-go` fork submodule first, so the whole set is still deliberately left for a separate sync.
