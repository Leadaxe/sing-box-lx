## 🐛 Fixed

### 🔁 `lxd update` from the launcher rolled back with `TUNSETIFF: device or resource busy`

- Before: a command started through `commands` (the launcher's Update button) ran as a child of the daemon and inherited the daemon's open descriptors, among them the TUN fd. The interface lives while any copy of that fd is open: the detached updater held `lxd-tun0` through the service restart, longer than the new core's 10 s busy retry; the core went `fatal`, the updater saw it and restored the previous binary (`… is up but the core did not start: … TUNSETIFF: device or resource busy, rolled back`).
- Now: before spawning any command (and before the `check` child of apply) the daemon sets `FD_CLOEXEC` on every descriptor above stderr that lacks it. Nothing is closed in the daemon; the child simply does not get the copies. The core's own busy retry and the updater's health step are unchanged.
- Not affected: commands' output, exit code and detachment (a service restart still does not kill a running command); Windows (no `commands` there).
- **Upgrading from lx.17 / lx.18:** the daemon that spawns the updater is still the old one, so the Update button will roll back once more. Either stop the core in the launcher, press Update, then start the core (the updater skips the core check while the core is stopped by the operator; `start` brings the new core up), or run `sing-box lxd update` over SSH once. Every later update works with the core running. (SPEC 128)

## 🧰 Under the hood

- Base: sing-box `v1.14.3`, zero drift from `upstream/stable`; submodules and dependencies unchanged since lx.18. Go 1.26.8.
- Verified by the lxd unit tests (`TestMarkInheritableCloseOnExec`, `TestCommandDoesNotInheritDescriptors`: a real `/bin/sh` child no longer sees the daemon's descriptor). The live confirmation on the router is the next update after the manual step.
