## 🆕 What's new

### 🧮 `lx.wg.buffers`: fewer receive buffers on small machines

- A tunnel without `detour` keeps one 64 KiB buffer per datagram it may read at once, in each of its two receive routines, for as long as it is up: 16.4 MiB per tunnel.
- `read_datagram_count` (1–128, default 128 as upstream) sets how many datagrams one read takes. At `8` the tunnel keeps about 1 MiB. Linux and Android; accepted and ignored on macOS and Windows.
- Below 128 the socket is created without kernel receive coalescing (UDP GRO). Send coalescing (UDP GSO) stays.
- Measured on a 4-core Cortex-A55 board, 8 against the default: speed within the spread (download 124.1 vs 118.9 Mbit/s, upload 142.3 vs 140.0), receive buffers in the heap 12–15 → about 1 MiB, client peak memory during download 73.6 → 62.3 MiB.
- The default is unchanged: over loopback at 100–150 Mbit/s the batch and GRO give nothing; on a real NIC and a fast link they may.
- Many tunnels: a hundred idle tunnels without `detour` keep 1740 MiB of Go heap at the default, 138 MiB at `8`, 44 MiB at `1`. Little of it is backed by physical memory while they idle (94 against 74 MiB), but the heap counts toward memory limits, has to fit a 32-bit address space, and moves the garbage collection threshold. For tens and hundreds of tunnels use `1` or `2`.
- `send_by_mtu: false` is a diagnostic switch: it puts the buffers read from the tunnel stack back at 64 KiB, as before this release.
- Android: the effect of `read_datagram_count` is derived from the code, not measured on a device. (SPEC 158 §9)

### 🔌 `lx.wg.connected_socket`: more upload on a tunnel with one server, off by default

- For a tunnel with one peer, a fixed server address and no `listen_port`, on Linux and Android. The tunnel socket is connected to the server, so the system keeps the route instead of looking it up for every datagram.
- Measured on the same board: upload 140.0 → 146.4 Mbit/s, 149.8 together with `read_datagram_count: 8`. No gain on download.
- The connection is never relied on. A send that fails because of it disconnects the socket and goes out the ordinary way; an unanswered handshake or a route change disconnects it, lets it hear any address for three seconds, and connects it again.
- The price: a connected socket hears only the server's address. A server that answers from a new address is heard after the next handshake retry, not at once.
- Verified on the board: after a server restart under load traffic is back in 5 s, the same as without the key. Not verified: a phone that changes between Wi-Fi and LTE, a real NIC. That is why it is off by default. (SPEC 160)

### 💾 `lxd update` on a router whose flash holds one binary

- Before: the update wrote the new binary next to the running one, so a flash partition smaller than two copies could never update (a 70.8 MB ubifs partition and a 76 MB binary).
- Now, when there is no room, or with `--low-space`, the new binary and a compressed copy of the old one are staged in RAM, the service is stopped, the old binary is replaced and the service is started again.
- A failed write, a service that does not come up or a core that does not start puts the old binary back from the copy. If even that fails, the update exits with code 3, keeps both copies and logs the manual restore command.
- Not verified on a router yet. ([#79](https://github.com/Leadaxe/sing-box-lx/issues/79), SPEC 129)

## 🔧 Changed

### ⚠️ The WireGuard sleep keys moved into `lx.wg.idle` — old names are a load error

- `lx.wg` now has keys that work in any build, so the layout got one rule: the `idle` block needs a mobile build, the rest of `lx.wg` works everywhere.
- `lx.wg.idle_suspend` → `lx.wg.idle.suspend`, `idle_suspend_reachable` → `idle.suspend_reachable`, `idle_teardown` → `idle.teardown`, `lazy_build` → `idle.lazy_build`, `build_max` → `idle.build_max`, `build_overflow` → `idle.build_overflow`.
- A config with an old key does not load; the error names the new one (`lx.wg.idle_suspend is moved to lx.wg.idle.suspend`). There is no period with both.
- Meaning, defaults and mutual conditions of the keys are unchanged. (SPEC 098)

### ⚡ WireGuard / AmneziaWG without `detour`: faster send and receive, no setting

- Before: after every datagram the socket layer reset all 128 messages it prepares for a batch, although the tunnel stack hands packets over one at a time. That was about 7 % of the CPU of a tunnel endpoint.
- Now it resets the ones it used.
- Measured on a 4-core Cortex-A55 board, two instances of the core over loopback, against the previous build: download 103.1 → 118.9 Mbit/s, upload 127.0 → 140.0; client CPU per byte −13 % and −8 %.
- Also fixed: when the system refused UDP segmentation offload, the retry sent the first datagram with the coalesced segments attached, and the peer dropped it. Once per socket, on a NIC without hardware checksums, when more than one datagram goes out per call (an AmneziaWG handshake).
- Not measured on a real NIC. (SPEC 160)

### 🧮 WireGuard / AmneziaWG: a queued packet holds ~2 KiB instead of 64 KiB

- Before: every packet waiting inside the tunnel kept a 64 KiB buffer, on receive and on send. A thousand queued packets cost 64 MiB in each direction; this shows when the link is faster than the CPU (routers, phones).
- Now: the send side allocates for the tunnel MTU; the receive side queues a 2 KiB copy.
- Measured on a 4-core Cortex-A55 board, two instances of the core over loopback, 8 TCP streams: peak memory of the client 137 → 92 MiB, of the server 150 → 117 MiB, at the same 97–128 Mbit/s. A queue of ~1000 packets: 66 → 4 MiB on receive, 64 → 2 MiB on send.
- On Linux and Android each tunnel without `detour` also keeps 8 MiB less heap while idle.
- Android: the queue is capped at 8 MiB instead of 256 MiB. Not verified on a device.
- Not changed: on Linux with a TUN inbound that has GSO, the receive side works as before (the packets are merged on their way back to the TUN and need the large buffers). Send-side savings apply there too.
- Cost per packet of this change alone is within −3.7…+0.9 % of the previous build. (SPEC 158)

### 🔄 Upstream fixes up to 2026-11-23 are in

- ECH: the config is fetched through the node's `domain_resolver`, and from DNS for QUIC as well.
- Rule sets: a data race between an update and matching.
- `direct`: ICMP sockets no longer accumulate without bound.
- auto-redirect on Linux: DNS from link-local sources, replies of TUN flows, traffic marked by other programs.
- systemd-resolved: the D-Bus connection lifecycle.
- v2ray-plugin mux: reads into short buffers.
- OpenConnect: Fortinet login through SAML.

## 🐛 Fixed

### 🧵 DNS over a proxied stream lost queries in bursts

- Symptom: a `tcp` DNS server reached through VLESS or shadowsocks + h2mux logged `dns: short read` in bursts (210 lines in an hour and a half on a router, up to 82 in one second); a page opened on the first try in about five seconds.
- Cause: concurrent writes to one proxied connection sent the protocol header twice — on the client for queries, on the server (`hijack-dns`, `dns` outbound, `resolved`) for responses.
- Now writes are serialized on both sides. The server half takes effect on exit nodes running this build. (SPEC 157)

### 🔌 AmneziaWG with small junk took the uplink down on some routers

- Symptom: on a board with a Synopsys DesignWare Ethernet MAC (`stmmac`, e.g. RK3568) an AmneziaWG tunnel without `detour` and with junk of a few bytes (Proton VPN profiles: `Jc = 3`, `Jmin = 1`, `Jmax = 3`) stopped all outgoing traffic of the machine after the first handshake. The kernel logged `NETDEV WATCHDOG … transmit queue 0 timed out` and reset the adapter, often more than a minute later; sing-box showed only `network: missing default interface`.
- Cause: the junk and decoy datagrams ahead of a handshake went to the socket in one call and were merged into one UDP segmentation request with a 1–3-byte segment size, which such a NIC cannot handle.
- Now each of these datagrams is sent on its own. The wire is unchanged, and so is the data path.
- On an older build the workaround is `ethtool -K eth0 tx-udp-segmentation off`. ([#82](https://github.com/Leadaxe/sing-box-lx/issues/82), SPEC 101)

### 📦 lxd: a rule set that a config points at can now be updated

- Before: `PUT /admin/resources/{name}` answered 409 for any file the active or last-good config references, so an updated rule set never reached the machine.
- Now a referenced `.srs` / `.json` is replaced in place. It is first loaded the way the core loads it; a set the core cannot load is rejected with 422 and never reaches the disk.
- The previous copy is kept until the core has reloaded the new one or started with it, and is put back if the core refuses the set or the start fails. The response carries `"replace": "confirmed"` or `"pending"`; the request may take up to 10 s.
- Windows: a config that names a resource with backslashes is now recognized as referencing it; before, the 409 guard did not see such a path.
- Not changed: other files and `DELETE` of a referenced name still answer 409. (SPEC 159)

### 🌐 HTTP outbound: a proxy that never answers no longer holds goroutines and sockets

- Symptom: when an HTTP proxy accepted TCP and the CONNECT request but did not answer, every dial waited forever, and closing the client connection did not stop it. 768 attempts left 780 goroutines and 1546 file descriptors, and they were not freed when the proxy came back.
- Now the CONNECT exchange after the underlying dial is limited to 15 s. On timeout the socket is closed and the dial returns `CONNECT handshake timeout`.
- `detour` sessions and `connect_timeout` are unchanged; there is no config key.
- Checked against Squid 6.12 with a stalled ACL helper: 24 hung CONNECTs before, none after. Thanks to Alex01d. ([#74](https://github.com/Leadaxe/sing-box-lx/issues/74), [PR #73](https://github.com/Leadaxe/sing-box-lx/pull/73), SPEC 161)

### 🧵 WireGuard: stopping a tunnel while it dials

- Symptom: when an embedding app closed or rebuilt a WireGuard endpoint while connections were being opened through it, a dial could read the device just as it was cleared (a data race, possibly a crash), and an attached return path could be lost. Stopping the core could also wait up to 15 s for a TCP connect started inside the tunnel.
- Now the swappable device fields are read and replaced under a short lock, and a TCP connect inside the tunnel ends together with the device.
- Pinned by tests under `-race`. Thanks to dqzaexxpess. ([#75](https://github.com/Leadaxe/sing-box-lx/issues/75))

## 🐛 Исправлено

### 🧵 DNS через потоковое прокси-соединение терял запросы пачками

- Симптом: DNS-сервер `tcp` через VLESS или shadowsocks + h2mux писал `dns: short read` пачками (210 строк за полтора часа на роутере, до 82 в одну секунду); страница открывалась с первого раза секунд за пять.
- Причина: параллельные записи в одно прокси-соединение отправляли заголовок протокола дважды — на клиенте для запросов, на сервере (`hijack-dns`, `dns`-outbound, `resolved`) для ответов.
- Теперь запись сериализована с обеих сторон. Серверная половина действует на выходных узлах с этой сборкой. (SPEC 157)

### 🔌 AmneziaWG с коротким junk ронял аплинк на некоторых роутерах

- Симптом: на плате с Ethernet-контроллером Synopsys DesignWare (`stmmac`, например RK3568) туннель AmneziaWG без `detour` с junk в несколько байт (профили Proton VPN: `Jc = 3`, `Jmin = 1`, `Jmax = 3`) после первого рукопожатия останавливал весь исходящий трафик машины. Ядро писало `NETDEV WATCHDOG … transmit queue 0 timed out` и сбрасывало адаптер, часто больше чем через минуту; в sing-box было видно только `network: missing default interface`.
- Причина: junk и декои перед рукопожатием уходили в сокет одним вызовом и склеивались в один запрос на сегментацию UDP с размером сегмента 1–3 байта, с которым такая карта не справляется.
- Теперь каждая из этих датаграмм отправляется отдельно. На проводе ничего не изменилось, data-путь тоже прежний.
- На старой сборке обходится командой `ethtool -K eth0 tx-udp-segmentation off`. ([#82](https://github.com/Leadaxe/sing-box-lx/issues/82), SPEC 101)

### 📦 lxd: набор правил, на который ссылается конфиг, теперь можно обновить

- Было: `PUT /admin/resources/{имя}` отвечал 409 для любого файла, на который ссылается активный или last-good конфиг, и обновлённый набор не доезжал до машины.
- Стало: занятый `.srs` / `.json` заменяется на месте. Сначала он загружается тем же путём, что в ядре; набор, который ядро не загрузит, отвергается с 422 и на диск не попадает.
- Прежняя копия хранится, пока ядро не перечитало новую или не стартовало с ней, и возвращается, если ядро набор не приняло или старт не удался. В ответе — `"replace": "confirmed"` или `"pending"`; запрос может длиться до 10 с.
- Windows: конфиг, в котором ресурс назван путём с обратными слэшами, теперь распознаётся как ссылающийся на него; раньше отказ 409 такой путь не видел.
- Не изменилось: прочие файлы и `DELETE` занятого имени по-прежнему отвечают 409. (SPEC 159)

### 🌐 HTTP outbound: прокси, который не отвечает, больше не держит горутины и сокеты

- Симптом: если HTTP-прокси принимал TCP и запрос CONNECT, но не отвечал, каждый дозвон ждал бесконечно, и закрытие клиентского соединения его не останавливало. 768 попыток оставляли 780 горутин и 1546 файловых дескрипторов, и после восстановления прокси они не освобождались.
- Теперь обмен CONNECT после нижележащего дозвона ограничен 15 с. По истечении сокет закрывается, дозвон возвращает `CONNECT handshake timeout`.
- Сессии `detour` и `connect_timeout` не меняются; ключа конфига нет.
- Проверено на Squid 6.12 с остановленным ACL-помощником: было 24 зависших CONNECT, стало ни одного. Спасибо Alex01d. ([#74](https://github.com/Leadaxe/sing-box-lx/issues/74), [PR #73](https://github.com/Leadaxe/sing-box-lx/pull/73), SPEC 161)

### 🧵 WireGuard: остановка туннеля во время дозвонов

- Симптом: когда встраивающее приложение закрывало или пересобирало endpoint WireGuard, пока через него открывались соединения, дозвон мог прочитать устройство в момент его обнуления (гонка данных, возможно падение), а прикреплённый обратный путь — потеряться. Остановка ядра к тому же могла ждать до 15 с TCP-соединение, начатое внутри туннеля.
- Теперь подменяемые поля устройства читаются и меняются под коротким замком, а TCP-соединение внутри туннеля завершается вместе с устройством.
- Закреплено тестами под `-race`. Спасибо dqzaexxpess. ([#75](https://github.com/Leadaxe/sing-box-lx/issues/75))
