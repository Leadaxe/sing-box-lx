`lxd` installs as a Windows service: the SCM runs a protected copy of the binary set from Program Files under LocalSystem, starts before login, and the launcher pairs through an invite file. XHTTP now picks HTTP/1.1, HTTP/2 or HTTP/3 from `tls.alpn` the way Xray does, so h3-only servers work. Client names are bounded and a named re-pair replaces the old record instead of adding one.

`lxd` ставится службой Windows: SCM исполняет защищённую копию набора файлов из Program Files под LocalSystem, стартует до входа пользователя, лаунчер сопрягается через файл приглашения. XHTTP выбирает HTTP/1.1, HTTP/2 или HTTP/3 по `tls.alpn`, как Xray, поэтому серверы только с h3 работают. Имена клиентов ограничены, повторное сопряжение под тем же именем заменяет старую запись, а не добавляет новую.

## 🆕 What's new

### 🪟 `lxd` as a Windows service

- `sing-box lxd --service=install` (elevated) registers the SCM service `sing-box-lxd`: LocalSystem, automatic start after `Tcpip`, restart on failure. The service executes a protected copy `<ProgramFiles>\sing-box-lxd\sing-box-lxd.exe` (plus `libcronet.dll` when it lies beside the source), never the binary install was run from. Updating replaces the image through a temporary file and `rename`; a failed update starts the previous image back.
- State and logs live in `<ProgramData>\sing-box-lxd\state\` and `logs\lxd.log`; install takes ownership of that tree and replaces its DACL before writing the secret. The copy directory is readable by Authenticated Users and writable by nobody else; a service pointed at another binary, a foreign owner or a writable ancestor is refused at start.
- `--service=copy` (protected copy without a service), `--service=status` without elevation (exit 0 OK, 2 MISMATCH/UNSAFE, 3 NOT INSTALLED, 4 COPY ONLY, 5 NOT RUNNING), `--service=uninstall [--keep-copy] [--purge]`, `--dry-run`, `--exec-dir`. `install-user` is not available on Windows.
- Sidecar `sing-box-lxd.install.json` lists the file set with hashes, the bound service and install warnings; the macOS sidecar is unchanged.
- Windows 7 (386) build has no service. macOS, Linux and Android behaviour is unchanged except the items below. ([SPEC 103](https://github.com/Leadaxe/sing-box-lx/blob/lx/SPECS/TASKS/103-LXD_WINDOWS_SERVICE/SPEC.md))

### 🎫 Pairing invite into a file, client name rules (all platforms)

- `lxd --service=install --invite-out <file> [--invite-name <name>]` and `lxd client add --invite-out <file>` write the invite into a new file (created exclusively, refused if it exists) instead of stdout; the client name defaults to `singbox-launcher` with `--invite-out`. A failed mint with `--invite-out` exits 1.
- A client name is 1 to 64 printable characters after trimming; anything else is rejected at mint. Enrolling with a named invite replaces the client of that name (the old certificate is revoked); an unnamed invite adds, as before.
- A passed start-up self-check inside the service logs one INFO line on macOS and Windows.

### 🌐 XHTTP: HTTP version from `tls.alpn`, like Xray

- `tls.alpn: ["h3"]` → HTTP/3 over QUIC/UDP through the same `detour` (servers listening only on QUIC now work); `["http/1.1"]` and configs without TLS → HTTP/1.1 (cleartext was h2c before); REALITY → always HTTP/2, an `alpn` without `h2` is replaced with a warning; otherwise HTTP/2 as before. No new keys.
- HTTP/3: `MaxIdleTimeout` 300 s, keep-alive from `xmux.h_keep_alive_period` (`0` → 10 s), Chrome-like QUIC handshake; `utls.fingerprint` is not applied on HTTP/3 (warning). Without `with_quic` a config with `["h3"]` is rejected at load.
- HTTP/1.1: download and streaming requests each on their own connection with `Connection: close`; `packet-up` POSTs are keep-alive. ([SPEC 104](https://github.com/Leadaxe/sing-box-lx/blob/lx/SPECS/TASKS/104-XHTTP_HTTP_VERSION_PARITY/SPEC.md))

## 🔧 Changed

### 🪵 Daemon log on Windows

- The service owns `logs\lxd.log` and rotates it by copy-and-truncate (an open file cannot be renamed there); panics of the admin REST and gRPC handlers land in the log as JSON 500 / `codes.Internal` with a stack trace, on every platform.

## 🆕 Что нового

### 🪟 `lxd` как служба Windows

- `sing-box lxd --service=install` (от администратора) регистрирует службу SCM `sing-box-lxd`: LocalSystem, автозапуск после `Tcpip`, рестарт при сбое. Служба исполняет защищённую копию `<ProgramFiles>\sing-box-lxd\sing-box-lxd.exe` (плюс `libcronet.dll`, если лежит рядом с источником), а не файл, из которого её поставили. Обновление заменяет образ через временный файл и `rename`; неудачное обновление возвращает прежний образ.
- Состояние и логи — в `<ProgramData>\sing-box-lxd\state\` и `logs\lxd.log`; install забирает владение этим деревом и заменяет DACL до записи секрета. Каталог копии читаем для Authenticated Users и никому не доступен на запись; служба, указывающая на другой бинарь, чужой владелец или записываемый предок — отказ старта.
- `--service=copy` (защищённая копия без службы), `--service=status` без повышения (выход 0 OK, 2 MISMATCH/UNSAFE, 3 NOT INSTALLED, 4 COPY ONLY, 5 NOT RUNNING), `--service=uninstall [--keep-copy] [--purge]`, `--dry-run`, `--exec-dir`. `install-user` на Windows нет.
- Сайдкар `sing-box-lxd.install.json` перечисляет набор файлов с хешами, привязанную службу и предупреждения install; сайдкар macOS не изменился.
- Сборка Windows 7 (386) без службы. Поведение macOS, Linux и Android не изменилось, кроме пунктов ниже. ([SPEC 103](https://github.com/Leadaxe/sing-box-lx/blob/lx/SPECS/TASKS/103-LXD_WINDOWS_SERVICE/SPEC.md))

### 🎫 Приглашение в файл, правила имени клиента (все платформы)

- `lxd --service=install --invite-out <файл> [--invite-name <имя>]` и `lxd client add --invite-out <файл>` пишут приглашение в новый файл (создаётся эксклюзивно, существующий — отказ), а не в stdout; имя клиента с `--invite-out` по умолчанию `singbox-launcher`. Провал минта при `--invite-out` — код выхода 1.
- Имя клиента — от 1 до 64 печатных символов после обрезки пробелов, иначе отказ на минте. Сопряжение по именованному приглашению заменяет клиента с этим именем (старый сертификат отзывается); безымянное добавляет, как раньше.
- Пройденная самопроверка при старте внутри службы пишет одну строку INFO на macOS и Windows.

### 🌐 XHTTP: версия HTTP по `tls.alpn`, как у Xray

- `tls.alpn: ["h3"]` → HTTP/3 по QUIC/UDP через тот же `detour` (серверы, слушающие только QUIC, теперь работают); `["http/1.1"]` и конфиг без TLS → HTTP/1.1 (без TLS раньше был h2c); REALITY → всегда HTTP/2, `alpn` без `h2` заменяется с предупреждением; иначе HTTP/2 как раньше. Новых ключей нет.
- HTTP/3: `MaxIdleTimeout` 300 с, keep-alive из `xmux.h_keep_alive_period` (`0` → 10 с), Chrome-подобное QUIC-рукопожатие; `utls.fingerprint` на HTTP/3 не применяется (предупреждение). Без `with_quic` конфиг с `["h3"]` отвергается при загрузке.
- HTTP/1.1: download и потоковые запросы — каждый по своему соединению с `Connection: close`; POST'ы `packet-up` — keep-alive. ([SPEC 104](https://github.com/Leadaxe/sing-box-lx/blob/lx/SPECS/TASKS/104-XHTTP_HTTP_VERSION_PARITY/SPEC.md))

## 🔧 Изменено

### 🪵 Лог демона на Windows

- Служба владеет `logs\lxd.log` и ротирует его копированием с усечением (открытый файл там не переименовать); паники обработчиков admin REST и gRPC попадают в лог как JSON 500 / `codes.Internal` со стеком, на всех платформах.
