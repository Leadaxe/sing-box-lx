## 🆕 What's new

### 🧩 `sing-box lxd` — headless daemon with an admin plane

The core runs in-process behind a long-lived gRPC control channel, modelled on
upstream's desktop daemon (`experimental/boxdd`) but headless and shipped as a
subcommand of the existing binary — one artifact, no separate extractor path, no
version skew.

- The control channel **survives reload and a broken config**: if the core fails
  to start or reload, the daemon logs it and keeps listening in FATAL state
  instead of exiting.
- `POST /admin/apply` validates the candidate config with `sing-box check` and
  rolls back to last-good if the start fails. `rollback`, `start`, `stop`,
  `config` and `status` complete the plane; run state and an interrupted apply
  survive restarts.
- A validator infrastructure failure is never reported as a verdict on your
  config: a cancelled parent request returns 500, not 422. The validator's own
  10 s timeout is a verdict.
- `GET /admin/info` returns the daemon passport — version, state dir, listen
  address, certificate fingerprint, pid, uptime, log path — so clients do not
  hardcode paths.
- `SIGHUP` re-reads the config file and swaps the instance under the live server.
  `SIGINT`/`SIGTERM` shut down in order: service → gRPC server → close.
- Requires the `with_lx_command` build tag; without it the subcommand does not
  exist and the package is an empty stub. No upstream files are touched — the
  subcommand self-registers via `init()`. (SPEC 055, SPEC 056, FEATURE 014)

### 🔐 mTLS enrollment: the certificate is the full mandate

The daemon is its own CA. A client enrolls with a one-time invite of the form
`address#fingerprint#code` and is identified by its certificate from then on — no
Bearer token on top, since clients never learn the secret and requiring both
would lock out every launcher.

Bearer is the operator mandate for the **loopback-only** `client add`, `list` and
`remove` routes: minting an invite code grants trust, so it is unreachable from
the network by construction. (SPEC 057)

### 🪵 The daemon owns and rotates its log

Under a service manager (stdout is not a terminal) the daemon redirects
stdout/stderr to `<support>/lxd.log` — core logs and runtime panics included —
and rotates by age and size. Defaults are roughly a day of history: 24 h, 1
backup, 20 MB as a safety ceiling; `log_max_size_mb`, `log_max_backups` and
`log_max_age_hours` in `daemon.json` override them. In a terminal the log stays
on screen.

The reason is concrete: launchd's `StandardOutPath` is never rotated — a run grew
to 39 MB in about a day and a half on info-level core logs, and `newsyslog`
handles neither paths with spaces nor user scope.

### ⚙️ Service installation on macOS, a printed recipe on Linux

`--service=install` (system LaunchDaemon) and `install-user` (LaunchAgent, no
sudo) install for real: they materialize `daemon.json` themselves — scanning for
a free port from 19091, generating the secret and the mTLS material — write the
plist, bootstrap the job and print a summary with a one-time invite.

Linux only **prints a recipe**, on the principle that anything touching disk is
the operator's action: init detection via `/proc/1/comm` with fallbacks, a link
to the right section of the manual, a ready-to-paste `daemon.json`, a systemd
unit or procd init script, and the enable commands. The secret never reaches the
screen — the recipe substitutes `$(head -c 32 /dev/urandom | xxd -p -c 64)` so
the value is born on the host. `uninstall --purge` likewise prints `rm -rf`
rather than running it. `--dry-run` works with both install and uninstall.
Windows remains a stub. (SPEC 057, operator manual: `docs-lx/lxd-daemon.md`)

## 🔧 Changed

### ⚠️ `lxd run` → `lxd`, connection flags replaced by `daemon.json`

The subcommand is now bare `lxd`, and the connection flags (`--listen`, `--tls`,
`--secret`, `--secret-file`) are gone entirely. Daemon settings live in
`<state-dir>/daemon.json` (mode 0600), which makes "does the file or the flag
win?" unanswerable by construction.

Without that file a dev run gets fixed defaults — plain h2c on `127.0.0.1:9091`,
no secret. The file is never created implicitly.

### 🧰 Build toolchain moved to go1.26.5

The fork ships on the same toolchain as upstream: `go.version` is bumped and the
win7 build takes upstream's patched go1.26.5 script. Verified green locally on
1.26.5 — the full `LX_TAGS` binary including badtls linking, both fork
submodules, and the core test suite.

## 🐛 Fixed

### 💥 Startup crash with a domain-addressed node in a WireGuard detour chain

Endpoints start before DNS transports do. An early WireGuard bind dial through a
detour chain containing a domain-addressed node resolved through a `dns_group`
that had not started yet: the member list was empty and the survival branch
picked `best[rand.IntN(0)]` — a panic on a zero argument, so the core never came
up at all.

An empty member list is now read as "not started" and returns a typed error; the
caller retries once the transports are up. Field crash on 1.14.0-lx.22
(android/arm64). (SPEC 033)

### 💥 `GetRules` killed the core under the `api` service

With `services: [{"type": "api"}]` the core attaches to an already-running box
from the outside and has no `*box.Box` of its own — only the owning start path
builds one. `GetRules` reached for the routing table through that missing object,
so the first call to the RPC brought the whole process down.

The router is now resolved from the service context (where it is registered
anyway, and where the Clash API already reads it) and stored on the instance, so
both start paths have it. If it is genuinely absent, the RPC degrades to
`Unavailable` instead of panicking — the same discipline `GetRunningConfig`
already followed. No other lx RPC had this pattern. (FEATURE 006)

### 🌐 Upstream fixes carried in

Merged from upstream through 2026-08-11: local DNS transport caches are
partitioned by interface signature, so a network change no longer serves another
network's cache; the WireGuard handshake resolves **all** addresses of a
domain-addressed peer and races them; daemon endpoint subscriptions survive a
service restart; hijacked DNS queries carry process info again. Also fixed:
network reset, FakeIP async metadata save, the Android process finder, and
unbounded allocations when reading an untrusted rule-set.

<summary><h2>🇷🇺 Русский</h2></summary>

## 🆕 Что нового

### 🧩 `sing-box lxd` — headless-демон с админ-плоскостью

Ядро работает in-process за долгоживущим управляющим каналом gRPC — по модели
десктопного демона апстрима (`experimental/boxdd`), но headless и в форме
сабкоманды существующего бинаря: один артефакт, отдельный путь распаковки не
нужен, рассинхрон версий невозможен.

- Управляющий канал **переживает reload и битый конфиг**: если ядро не смогло
  стартовать или перезагрузиться, демон пишет это в лог и остаётся слушать в
  состоянии FATAL, а не завершается.
- `POST /admin/apply` валидирует кандидата собственным `sing-box check` и при
  провале старта откатывается на last-good. Плоскость дополняют `rollback`,
  `start`, `stop`, `config` и `status`; состояние запуска и прерванный apply
  переживают рестарты.
- Инфраструктурный сбой валидатора не выдаётся за вердикт по конфигу: отмена
  родительского запроса — 500, а не 422. Собственный таймаут валидатора в 10 с —
  вердикт.
- `GET /admin/info` отдаёт паспорт демона: версия, state-каталог, адрес
  прослушивания, отпечаток сертификата, pid, uptime, путь к логу — клиенту не
  нужно хардкодить пути.
- `SIGHUP` перечитывает файл конфига и подменяет инстанс под живым сервером.
  `SIGINT`/`SIGTERM` гасят по порядку: сервис → gRPC-сервер → закрытие.
- Требуется тег сборки `with_lx_command`; без него сабкоманды нет, а пакет —
  пустой стаб. Апстримные файлы не затронуты: сабкоманда самонавешивается через
  `init()`. (SPEC 055, SPEC 056, FEATURE 014)

### 🔐 mTLS-регистрация: сертификат — полный мандат

Демон сам себе CA. Клиент регистрируется одноразовым инвайтом вида
`адрес#отпечаток#код` и дальше опознаётся по сертификату — Bearer поверх не
нужен: клиенты секрета не знают, а требование обоих запирало бы каждый лаунчер.

Bearer — операторский мандат **loopback-only** маршрутов `client add`, `list` и
`remove`: минт кода это выдача доверия, поэтому из сети он недоступен в принципе.
(SPEC 057)

### 🪵 Демон владеет своим логом и ротирует его

Под службой (stdout не терминал) демон перехватывает stdout/stderr на
`<support>/lxd.log` — туда попадает всё, включая лог ядра и паники рантайма — и
ротирует по возрасту и размеру. Дефолты — примерно сутки истории: 24 ч, 1 бэкап,
20 МБ как страховочный потолок; переопределяются ключами `log_max_size_mb`,
`log_max_backups` и `log_max_age_hours` в `daemon.json`. В терминале лог остаётся
на экране.

Повод конкретный: launchd `StandardOutPath` не ротируется — наблюдался рост до
39 МБ примерно за полтора суток на info-логах ядра, а `newsyslog` не умеет ни
пути с пробелами, ни user-scope.

### ⚙️ Установка службы на macOS, печать рецепта на Linux

`--service=install` (системный LaunchDaemon) и `install-user` (LaunchAgent без
sudo) ставят по-настоящему: сами материализуют `daemon.json` — скан свободного
порта начиная с 19091, генерация секрета и mTLS-материала, — пишут plist,
бутстрапят задание и печатают сводку с одноразовым инвайтом.

Linux **только печатает рецепт**, по принципу «всё, что меняет диск, делает
оператор»: детект init по `/proc/1/comm` с фолбэками, ссылка на нужный раздел
руководства, готовый к вставке `daemon.json`, unit systemd или init-скрипт procd
и команды включения. Секрет на экран не попадает — в рецепте стоит подстановка
`$(head -c 32 /dev/urandom | xxd -p -c 64)`, значение рождается на хосте.
`uninstall --purge` там тоже печатает `rm -rf`, а не выполняет. Флаг `--dry-run`
работает и с install, и с uninstall. Windows — по-прежнему заглушка.
(SPEC 057, руководство оператора: `docs-lx/lxd-daemon.md`)

## 🔧 Изменено

### ⚠️ `lxd run` → `lxd`, connection-флаги заменены на `daemon.json`

Сабкоманда теперь голое `lxd`, а connection-флагов (`--listen`, `--tls`,
`--secret`, `--secret-file`) больше нет вовсе. Настройки демона живут в
`<state-dir>/daemon.json` (права 0600) — вопрос «кто побеждает, файл или флаг»
становится невозможен по построению.

Без этого файла dev-запуск получает фиксированные дефолты: plain h2c на
`127.0.0.1:9091`, без секрета. Неявно файл не создаётся.

### 🧰 Сборочный тулчейн переехал на go1.26.5

Форк отгружается тем же тулчейном, что и апстрим: `go.version` бампнут,
win7-сборка берёт апстримовый патченный скрипт go1.26.5. Локально на 1.26.5
зелёные: полный `LX_TAGS`-бинарь, включая badtls-линковку, оба форк-сабмодуля и
тесты ядра.

## 🐛 Исправлено

### 💥 Краш на старте с доменным узлом в detour-цепи WireGuard

Эндпоинты стартуют раньше DNS-транспортов. Ранний дайл WG-bind через detour-цепь
с доменным узлом уходил резолвиться в группу `dns_group`, которая ещё не
стартовала: список членов пуст, и survival-ветка выбирала `best[rand.IntN(0)]` —
паника на нулевом аргументе, ядро не поднималось вовсе.

Пустой список членов теперь читается как «не стартована» и возвращает
типизированную ошибку; вызывающий повторяет попытку, когда транспорты поднимутся.
Полевой краш на 1.14.0-lx.22 (android/arm64). (SPEC 033)

### 💥 `GetRules` убивал ядро под сервисом `api`

С `services: [{"type": "api"}]` ядро прицепляется снаружи к уже поднятому box и
собственного `*box.Box` не имеет — его строит только владеющий путь запуска.
`GetRules` тянулся за таблицей маршрутизации через этот отсутствующий объект,
поэтому первый же вызов RPC ронял весь процесс.

Теперь роутер резолвится из сервисного контекста (где он и так зарегистрирован и
откуда его уже берёт Clash API) и хранится в инстансе, так что он есть у обоих
путей запуска. Если роутера действительно нет, RPC деградирует в `Unavailable`
вместо паники — та же дисциплина, что уже была у `GetRunningConfig`. У остальных
lx-RPC этого паттерна не было. (FEATURE 006)

### 🌐 Апстримные исправления в составе релиза

Влито из апстрима по 2026-08-11: кеши локального DNS-транспорта партиционируются
по сигнатуре интерфейса — смена сети больше не отдаёт кеш чужой сети;
WireGuard-хендшейк резолвит **все** адреса домен-пира и гонит их наперегонки;
подписки эндпоинтов в `daemon` переживают перезапуск сервиса; hijacked-DNS снова
несёт process info. Также исправлены: reset network, async-сохранение метаданных
FakeIP, поиск процессов на Android и неограниченные аллокации при чтении
недоверенного rule-set.
