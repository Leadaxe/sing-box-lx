## 🐛 Fixed

### 🧊 One dead node behind a DNS server froze the whole tunnel

Reported from the field on Android: the first page loads, then everything
hangs — new sites fail with "unknown host", pings stop, the profiler shows
zero connections. A few minutes later it recovers on its own, and dies again.
The config was perfectly legal: a DNS server with a `detour` to a proxy group,
and the node selected in that group was being silently dropped by the network.

The cause was not DNS-specific. Hijacked DNS queries were resolved directly on
the tunnel's packet loop, and the resolver call blocks the caller while it
waits for the transport to dial. Dialing through a black-holed node never
completes, so every unique query held the packet loop for the full DNS timeout
— and nothing else moved through the tunnel meanwhile: other DNS servers,
ICMP, new connections of every protocol. A background trickle of app queries
was enough to keep it frozen almost continuously.

Those exchanges now run off the packet loop, with concurrency capped at 256 in
flight; beyond that a query is dropped and the client retries, which is normal
for UDP. Queries aimed at the dead server still fail on their own timeout —
that part is expected — but the tunnel keeps forwarding. The bug is older than
this release and affects both tun stacks. (SPEC 046)

<summary><h2>🇷🇺 Русский</h2></summary>

## 🐛 Исправлено

### 🧊 Одна мёртвая нода за DNS-сервером морозила весь туннель

Жалоба с поля, Android: первая страница грузится, дальше всё висит — свежие
домены отваливаются с «unknown host», пинги не проходят, в профайлере ноль
соединений. Через несколько минут само оживает и умирает снова. Конфиг при
этом абсолютно легальный: DNS-сервер с `detour` на группу прокси, а выбранную
в группе ноду сеть молча дропала.

Причина оказалась не в DNS. Перехваченные DNS-запросы резолвились прямо в
пакетном цикле туннеля, а вызов резолвера держит вызывающего, пока транспорт
дозванивается до сервера. Через ноду-чёрную-дыру дозвон не завершается
никогда, поэтому каждый уникальный запрос занимал пакетный цикл на полный
DNS-таймаут — и всё это время через туннель не шло ничего: ни другие
DNS-серверы, ни ICMP, ни новые соединения любых протоколов. Фонового ручейка
запросов от приложений хватало, чтобы цикл стоял почти непрерывно.

Теперь такие обмены выполняются вне пакетного цикла, с ограничением в 256
одновременных; сверх лимита запрос дропается, и клиент повторяет — для UDP это
штатно. Запросы в мёртвый сервер по-прежнему падают по своему таймауту, так и
задумано, но форвардинг туннеля при этом жив. Баг старше этого релиза и
проявлялся на обоих tun-стеках. (SPEC 046)
