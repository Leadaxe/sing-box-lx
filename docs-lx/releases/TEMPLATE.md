# Шаблон релиз-нот (`docs-lx/releases/v<версия>.md`)

Имя файла — **`v<версия>.md`**, где `<версия>` = тег без ведущей `v`: для тега
`v1.14.0-lx.19` это `v1.14.0-lx.19.md`. Если файл существует,
`lx-release.yml` берёт его как тело «what's new» релиза целиком (вместо секции changelog)
и оборачивает служебным каркасом: заголовок с upstream-базой сверху, свёрнутые
`<details>` про бинарники/AAR/теги и ссылка на предыдущий релиз снизу — их писать не нужно.

- **Stable-тег обязан иметь этот файл** (без него CI кинет warning и уедет сырой changelog).
- Для rc/alpha/beta файл опционален — фолбэк на `#### v…`-секцию changelog остаётся.
- `docs-lx/lx-changelog.md` при этом никуда не девается: это инженерный лог (SPEC-ссылки,
  детали реализации), он по-прежнему ведётся на каждый тег. Релиз-файл — «человеческая»
  надстройка над ним, не замена.

## Правила текста (формат LxBox)

**Тон — сухой технический, не рассказ.** Что было → что стало → числа, пороги,
границы. Не пересказывать ход расследования, не объяснять «по-человечески» то,
что точнее выражается термином, не писать вводных абзацев и метафор. Разбор
причин, история и обоснование решений — в `SPECS/` и `lx-changelog.md`; сюда
попадает только результат.

1. **Сверху — TL;DR**: 2–4 сухих предложения EN + столько же RU. Что изменилось
   для пользователя, с ключевыми числами; без номеров SPEC и версий.
2. Дальше — два блока `<details open>`: 🇬🇧 English и 🇷🇺 Русский. Набор пунктов в обоих
   языках одинаковый; это не пословный перевод, а тот же смысл.
3. Внутри каждого языка — секции в этом порядке (пустые опускать):
   `## 🆕 What's new / Что нового` · `## 🔧 Changed / Изменено` ·
   `## 🐛 Fixed / Исправлено` · `## 🧰 Tools / Инструменты`.
4. Пункт = `### <эмодзи> <заголовок>` + минимум текста, достаточный по существу.
   - Заголовок — **факт**: симптом или изменившееся поведение с числом, если оно
     есть: «Таймаут соединения через WireGuard — 15 с (было ~127 с)».
   - Текст: старое поведение → новое → числа/пороги/дефолты → границы (что НЕ
     затронуто). Списком, если пунктов больше двух-трёх — читается лучше абзаца.
   - Идентификаторы (`ECONNREFUSED`, `passive_check`, `interval`) писать как
     есть — они точнее описания словами.
   - Ссылки — максимум одна в конце пункта, на SPEC/FEATURE (`(SPEC 044)`); никаких
     хешей коммитов в тексте.
5. Промоут rc-линии в stable — файл **сводит** содержимое rc.1–rc.N: одна запись на тему,
   а не хроника «в rc.2 добавили, в rc.3 починили».
6. Файл — живой черновик до среза тега: пиши его по ходу rc-линии, правь при новых rc.

## Скелет

```markdown
One-paragraph English TL;DR: what a user gets from this release.

Абзац русского TL;DR: что получает пользователь от этого релиза.

---

<details open>
<summary><h2>🇬🇧 English</h2></summary>

## 🆕 What's new

### 🧪 Headline in user terms

Prose.

## 🔧 Changed

## 🐛 Fixed

## 🧰 Tools

</details>

<details open>
<summary><h2>🇷🇺 Русский</h2></summary>

## 🆕 Что нового

### 🧪 Заголовок глазами пользователя

Текст.

## 🔧 Изменено

## 🐛 Исправлено

## 🧰 Инструменты

</details>
```

Проверка перед тегом: отрендерить файл (например, `gh api markdown`) или просто вычитать
на GitHub — блоки `<details>` требуют пустую строку после `<summary>…</summary>`, иначе
markdown внутри не отрендерится.
