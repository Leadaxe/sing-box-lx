## Фичи и build-теги

`sing-box-lx` — это upstream [sing-box](https://github.com/SagerNet/sing-box) плюс небольшой набор клиентских фич, каждая за своим build-тегом:

| Фича | Build-тег | Где живёт в конфиге | Входит в |
|------|-----------|---------------------|----------|
| **XHTTP** транспорт (совместим с Xray) | `with_xhttp` | `transport.type: "xhttp"` на VLESS / VMess / Trojan outbound | desktop + mobile |
| **AmneziaWG 2.0/3.x** (AWG2, AWG3) | `with_awg` | доп. поля на `wireguard` endpoint | desktop + mobile |
| **MASQUE** outbound (CONNECT-IP / WARP) | `with_quic`+`with_gvisor` | `outbounds[].type: "masque"` | desktop + mobile |
| **TrustTunnel** outbound и inbound | `with_trusttunnel` (+ `with_quic` для HTTP/3) | `outbounds[].type` / `inbounds[].type: "trusttunnel"`; поля — [protocols-transports.ru.md §6](protocols-transports.ru.md#6-trusttunnel-outbound-и-inbound), глобальный `lx.trusttunnel.idle_timeout` — [§13](#lxtrusttunnel--trusttunnel-outboundы) | desktop + mobile |
| **Idle-suspend** | `with_lx_idle_suspend` | `lx.wg.idle.suspend` (+ `suspend_reachable`, `teardown`) | только mobile (AAR) |
| **Корневой блок `lx`** | — (разбирается всегда) | `lx.wg`, `lx.masque`, `lx.trusttunnel`, `lx.mtu_align`, `lx.sniff_guard` — глобальные ручки форка, [§13](#13-корневой-блок-lx) | desktop + mobile |
| **Группа DNS-серверов** | — (всегда в сборке) | `dns.servers[].type: "group"` | desktop + mobile |
| **VLESS `encryption`** | — (всегда в сборке) | `encryption` на `vless`-outbound | desktop + mobile |
| **Демон `lxd`** | `with_lxd` | не ключ конфига — подкоманда `sing-box lxd` + `<state-dir>/daemon.json`; см. [lxd-daemon.ru.md](lxd-daemon.ru.md) | desktop / сервер (не Win7, не AAR) |
| **Outbound `chain`** | `with_lx_chain` | `outbounds[].type: "chain"` — многохоповый путь из групп и узлов | desktop + mobile |

Desktop/CLI-бинарь собирает `make -f Makefile.lx lx-build`: на выходе `sing-box` с версией `…-lx.N`.
В сборку входят `with_xhttp` и `with_awg` (плюс `with_lx_command` и `with_lxd`), но не `with_lx_idle_suspend`.
Без тега фичи нет: `xhttp`-транспорт или AWG-поле отклоняются при загрузке с явной ошибкой, молчаливого отката нет.

Тег `with_lx_idle_suspend` входит только в мобильный AAR (`cmd/internal/build_libbox`), не в
desktop `LX_TAGS`. Он усыпляет простаивающие WireGuard/AmneziaWG-эндпоинты и освобождает их
приёмные буферы: на устройстве 8 усыплённых эндпоинтов освободили 134 МБ. Ключи `lx.wg.idle` и
отказ десктоп-бинаря на них — в [§13](#lxwg--endpointы-wireguard--amneziawg), энергомодель и
рекомендованный мобильный конфиг — в [lx-energy.ru.md](lx-energy.ru.md).

> ⚠️ Все ключи/UUID ниже — заглушки. Никогда не коммитьте реальные приватные ключи / pre-shared-ключи в репозиторий.

## 0. Все поля разом (исчерпывающий пример)

Один конфиг несёт все поля outbound-фич: XHTTP-транспорт, AmneziaWG 2.0 endpoint,
masquerade-сахар `id`/`ip`/`ib`, VLESS `encryption`, `round_robin`-балансировщик `urltest`
и корневой блок `lx` со всеми ключами. У MASQUE и DNS-группы свои примеры — в [§4](#4-masque-outbound--cloudflare-warp)
и [§5](#5-группа-dns-серверов). Блок `lx` описан в [§13](#13-корневой-блок-lx), его энергоключи — в [lx-energy.ru.md](lx-energy.ru.md).

Это справочник «всё сразу», а не рекомендуемый конфиг. Многие поля взаимоисключающие
(сахар `id`/`ip`/`ib` и написанный вручную `i1`) либо серверные и клиентом игнорируются;
такие поля помечены в комментариях. Для рабочей настройки скопируйте только нужный
блок и прочитайте его раздел ниже. В каждом комментарии — значение по умолчанию и допустимые значения.

```jsonc
{
  // ─────────────────────────────────────────────────────────────────────────
  // Корневой блок `lx` (§13) — глобальные ручки форка по подсистемам.
  // lx.wg.idle действует только с build-тегом with_lx_idle_suspend (мобильный AAR);
  // десктоп-бинарь отвергает его на старте. Остальное в lx.wg работает в любой сборке.
  // ─────────────────────────────────────────────────────────────────────────
  "lx": {
    "wg": {
      "idle": {                                 // только сборки с with_lx_idle_suspend
        "suspend": "30s",                       // дефолт: выкл. Endpoint вне дерева маршрутизации → Down после простоя
        "suspend_reachable": "5m",              // дефолт: выкл. То же для endpoint'ов в дереве; >= suspend, требует его
        "teardown": "10m",                      // дефолт: = suspend_reachable. Сон до полной разборки; "0" = никогда
        "lazy_build": true,                     // дефолт: false. Сборка устройства при первом дайле (SPEC 097)
        "build_max": 4,                         // дефолт: 0 (без потолка). Не больше N собранных устройств (SPEC 097)
        "build_overflow": "wait"                // дефолт: wait. wait | build (SPEC 097)
      },
      "buffers": {                              // любая сборка (SPEC 158)
        "read_datagram_count": 8,               // дефолт: 128. 1–128 датаграмм на одно чтение из сокета
        "send_by_mtu": true                     // дефолт: true. false = буферы чтения из стека по 64 КБ (диагностика)
      },
      "connected_socket": true                  // дефолт: false. Подключённый сокет туннеля в режиме одного пира (SPEC 160)
    },
    "masque": {
      "idle_timeout": "5m"                      // дефолт: выкл. Глобальное окно простоя masque-узлов без своего ключа
    },
    "trusttunnel": {
      "idle_timeout": "5m"                      // дефолт: 5m. Глобальное окно простоя trusttunnel-узлов без своего ключа; выключается только "0" в узле (SPEC 133)
    },
    "mtu_align": "clamp",                       // дефолт: clamp. off | fill | clamp, либо объект {"mode", "except": [теги]} (§13)
    "sniff_guard": {                            // дефолт: нет блока = поведение апстрима. Защита рукопожатия от перенаправления по SNI на релее или роутере (§13, SPEC 060)
      "nodes": {
        "sni_mismatch": true,                   // дефолт: true — только узлы, у которых SNI не совпадает с server. false — фильтра нет
        "outbound_type": ["vless", "masque"]    // дефолт: фильтра нет. Список типов или false; true, [] и неизвестный тип — ошибка загрузки
      },
      "detour_type": {                          // дефолт: {"direct": "clean", "ssh": "clean", "socks": "clean", "*": "suspect"}
        "direct": "clean",                      //   тип носителя → never | clean | suspect; "*" — остальные типы; группы ключами нельзя
        "*": "suspect"
      },
      "override": false,                        // дефолт: false. true — блок сильнее узловых fragment / record_fragment
      "tls": {
        "method": "record_fragment",            // дефолт: off. record_fragment | fragment | delay | off
        "delay": "300ms",                       // дефолт: 300ms. Пауза метода delay; > 0
        "persist": true,                        // дефолт: false. Лейблы релеев в experimental.cache_file
        "detour_type": { "ssh": "suspect" }     // дефолт: общая карта. Перекрытие для TLS
      },
      "quic": {
        "method": "decoy_first_byte",           // дефолт: off. decoy_first_byte | delay | off
        "delay": "300ms",                       // дефолт: 300ms
        "persist": true,                        // дефолт: false
        "detour_type": { "socks": "never" }     // дефолт: общая карта. Перекрытие для QUIC
      }
    }
    // "quic_sniff_decoy" удалён: любое значение — ошибка загрузки, замена — sniff_guard.quic (§13)
    // "awg_masquerade" удалён в lx.33: любое значение — ошибка загрузки, пачка AWG идёт на любом пути (§13)
  },

  "outbounds": [
    // ─────────────────────────────────────────────────────────────────────────
    // XHTTP-транспорт (§1) — крепится к VLESS / VMess / Trojan outbound.
    // Требует build-тег with_xhttp.
    // ─────────────────────────────────────────────────────────────────────────
    {
      "type": "vless",
      "tag": "xhttp-out",
      "server": "example.com",
      "server_port": 443,
      "uuid": "00000000-0000-0000-0000-000000000000",
      "encryption": "",                         // по умолчанию: "" (выкл). PQ-слой VLESS (§6):
                                                //   "mlkem768x25519plus.<native|xorpub|random>.<0rtt|1rtt>….<ключ>"
      "tls": {
        "enabled": true,
        "server_name": "example.com",
        "utls": { "enabled": true, "fingerprint": "chrome" },
        "reality": {
          "enabled": true, "public_key": "<reality-public-key-base64>", "short_id": "0123abcd",
          "key_share": ""                       // дефолт: "" (как несёт отпечаток). §7:
                                                //   "classical" = вырезать X25519MLKEM768 (только Xray < v26.9.8)
                                                //   "hybrid"    = требовать его (ошибка на edge/ios/…)
        }
      },
      "transport": {
        "type": "xhttp",                        // селектор — должно быть "xhttp"

        // ── базовые (v1) ──
        "mode": "auto",                         // auto | packet-up | stream-up | stream-one.
                                                //   auto → stream-one на Reality, иначе packet-up
        "host": "example.com",                  // по умолчанию: TLS SNI / сервер. Переопределяет заголовок Host
        "path": "/xhttp",                       // по умолчанию: "" (корень). Session id / seq дописываются сегментами пути
        "headers": { "X-Foo": "bar" },          // по умолчанию: нет. Доп. заголовки на каждый запрос
        "x_padding_bytes": "100-1000",          // по умолчанию: "100-1000". "min-max" или одно число — длина паддинга
        "no_grpc_header": false,                // по умолчанию: false. Не слать Content-Type: application/grpc в stream-one/stream-up

        // ── размещение session / seq (v2) ──
        "session_placement": "path",            // по умолчанию: path. path | query | header | cookie
        "session_key": "",                      // по умолчанию: X-Session (header) / x_session (query|cookie); для path не нужен
        "seq_placement": "path",                // по умолчанию: path. path | query | header | cookie (packet-up)
        "seq_key": "",                          // по умолчанию: X-Seq (header) / x_seq (query|cookie); для path не нужен
        "session_table": "",                    // по умолчанию: не задан (id = дашед-UUID). Имя алфавита или свой ASCII-набор
        "session_length": "",                   // по умолчанию: не задан. "min-max" или "n"; задаётся вместе с session_table

        // ── размещение uplink-данных (v2, packet-up) ──
        "uplink_data_placement": "auto",        // по умолчанию: auto (== body). body | auto | header | cookie.
                                                //   header/cookie допустимы ТОЛЬКО в packet-up
        "uplink_data_key": "",                  // по умолчанию: X-Data (header) / x_data (cookie); "" для body
        "uplink_chunk_size": "",                // по умолчанию: cookie 2048-3072 / header 3000-4000 / иначе = sc_max_each_post_bytes.
                                                //   "min-max" в base64-символах, min не ниже 64
        "uplink_http_method": "POST",           // по умолчанию: POST. Приводится к верхнему регистру. GET только в packet-up

        // ── обфускация X-Padding (v2) — всё ниже работает только при obfs_mode=true ──
        "x_padding_obfs_mode": false,           // по умолчанию: false. Главный переключатель. false → legacy x_padding в Referer
        "x_padding_placement": "queryInHeader", // по умолчанию: queryInHeader. cookie | header | query | queryInHeader
        "x_padding_key": "x_padding",           // по умолчанию: x_padding. Имя cookie/query-параметра
        "x_padding_header": "X-Padding",         // по умолчанию: X-Padding. Имя заголовка (placement header / queryInHeader)
        "x_padding_method": "repeat-x",         // по умолчанию: repeat-x. repeat-x ('X'*N) | tokenish (base62, длина под HPACK)

        // ── тюнинг packet-up (v2) ──
        "sc_max_each_post_bytes": "1000000-1000000", // по умолчанию: "1000000-1000000". Порог дробления POST ("min-max")
        "sc_min_posts_interval_ms": "30-30",    // по умолчанию: "30-30". Анти-burst задержка между POST, мс ("min-max")

        // ── принимаются, но ИГНОРИРУЮТСЯ клиентом (только для симметрии конфига/ссылки) ──
        "sc_max_concurrent_posts": 0,           // ИГНОР — legacy-ручка Xray; клиент держит один POST в полёте
        "server_max_header_bytes": 0,           // ИГНОР — только сервер (http.Server.MaxHeaderBytes)
        "no_sse_header": false,                 // ИГНОР — только сервер (SSE Content-Type на downlink)
        "sc_max_buffered_posts": 0,             // ИГНОР — только сервер (глубина буфера переупорядочивания upload)
        "sc_stream_up_server_secs": ""          // ИГНОР — только сервер (интервал keepalive на stream-up)
      }
    },

    // ─────────────────────────────────────────────────────────────────────────
    // AmneziaWG 2.0 endpoint (§2) — wireguard endpoint с обфускацией.
    // Требует build-тег with_awg. Все AWG-поля на КОРНЕ endpoint
    // (ни одного на peer), повторяя секцию [Interface] файла awg-quick .conf.
    // ─────────────────────────────────────────────────────────────────────────
    {
      "type": "wireguard",
      "tag": "awg-out",
      "system": false,
      "mtu": 1280,                              // ниже обычного WG (transport junk s4); ядро ставит 1280 по умолчанию, если задан s4
      "address": ["10.0.0.2/32"],
      "private_key": "<client-private-key-base64>",

      // ── junk-пакеты перед handshake ──
      "jc": 10,                                 // по умолчанию: 0 (не задано). Количество junk-пакетов
      "jmin": 50,                               // по умолчанию: 0. Мин. размер каждого junk-пакета
      "jmax": 100,                              // по умолчанию: 0. Макс. размер каждого junk-пакета (держать ниже path MTU)

      // ── junk в handshake-сообщениях (s1/s2) + junk-size AWG 2.0 (s3/s4) ──
      "s1": 20,                                 // по умолчанию: 0. Junk перед handshake-сообщением INIT
      "s2": 20,                                 // по умолчанию: 0. Junk перед handshake-сообщением RESPONSE
      "s3": 60,                                 // по умолчанию: 0. Параметр junk-size AWG 2.0
      "s4": 60,                                 // по умолчанию: 0. Параметр junk-size AWG 2.0

      // ── magic headers: одно uint32 (AWG 1.x) ЛИБО диапазон "min-max" (AWG 2.0) ──
      // диапазоны НЕ должны пересекаться; 0 / "" = не задано (считается WG-дефолтом 1/2/3/4)
      "h1": 1234567890,                         // или "43613244-384550127"   — WG-сообщение тип 1
      "h2": 1234567891,                         // или "826869626-2105069164" — тип 2
      "h3": 1234567892,                         // или "2124774725-2141151992" — тип 3
      "h4": 1234567893,                         // или "2144594503-2146278491" — тип 4

      // ── CPS-приманки i1..i5 (регистрозависимы; шлются по порядку до handshake) ──
      // теги: <b 0xHEX> байты, <c> счётчик, <t> таймстамп, <r N> случайные байты,
      //       <rc N> случайные символы, <rd N> случайные цифры.
      // i1 ВЗАИМОИСКЛЮЧАЕТСЯ с сахаром id/ip/ib ниже — используйте что-то одно.
      "i1": "<b 0x000100002112a442><r 12>",     // по умолчанию: "". CPS-пакет 1
      "i2": "<b 0x010100002112a442><r 12>",     // по умолчанию: "". CPS-пакет 2
      "i3": "<r 24>",                            // по умолчанию: "". CPS-пакет 3
      "i4": "",                                  // по умолчанию: "". CPS-пакет 4
      "i5": "",                                  // по умолчанию: "". CPS-пакет 5

      // ── masquerade-сахар (§2 → id/ip/ib) — генерирует i1 за вас.
      //    ВЗАИМОИСКЛЮЧАЕТСЯ с явным i1 выше. Показан для справки;
      //    в реальном конфиге используйте ЛИБО i1..i5, ЛИБО id/ip/ib, не оба. ──
      "id": "www.google.com",                   // по умолчанию: "". Masquerade-домен (SNI/QNAME/SIP-host). Обязателен для ip=quic

      // ── AmneziaWG 3.x (контейнер amnezia-awg2, protocol_version 3.x; SPEC 080) ──
      // header_protection_key — СЕРВЕРНЫЙ (обязан совпасть с сервером); при нём
      // каждый s1..s4 должен быть >= 12 (в паддинге лежит nonce шифра заголовка).
      "header_protection_key": "<base64-32-bytes>", // по умолчанию: "" (выкл). Вывод `awg genkey`; маскирует тип/receiver/счётчик каждого пакета

      "peers": [
        {
          "address": "server.example.com",
          "port": 51821,
          "public_key": "<server-public-key-base64>",
          "pre_shared_key": "<preshared-key-base64>",
          "allowed_ips": ["0.0.0.0/0", "::/0"],
          "persistent_keepalive_interval": "25-35" // число (WireGuard) или "min-max" секунд (AWG 3.x)
        }
      ]
    },

    // Балансировка urltest round_robin (§3). Поля конфига всегда доступны;

      "interval": "15m",
      "mode": "round_robin",                    // по умолчанию: least_test. least_test | round_robin | failover

        "pool_tolerance": 0,                    // по умолчанию: 0 (мс). 0 = держать живой пул; >0 = топ-N по задержке с гистерезисом

                                                //   process | domain | source_ip | dest_ip | dest_port.
                                                //   ОТКЛЮЧИТЬ через sentinel ["none"] — никогда не пустой []
      }
    }
  ]
}
```

## 1. XHTTP-транспорт

XHTTP (в Xray — «splithttp»/«xhttp») — v2ray-транспорт: он туннелирует прокси поверх обычных
HTTP/2-запросов. XHTTP крепится к VLESS / VMess / Trojan через общий блок `transport` и сочетается
с TLS, включая Reality. С XTLS-Vision XHTTP несовместим; это ограничение протокола, а не
форка. Дефолтная форма на проводе байт-в-байт совпадает с v1-клиентом, проверенным вживую.
Каждое v2-поле включается явно (opt-in): размещение session/seq, обфускация uplink, семейство
`x_padding_*`, переиспользование соединений `xmux`.

Минимальный блок `transport` — просто `"type": "xhttp"` (режим `auto`). [Пример
ниже](#пример--vless--xhttp--reality) добавляет Reality-узел с `stream-one`.

> семантика пула `xmux`, формы записи диапазонов и таблица диагностики.

## 2. AmneziaWG 2.0/3.x (AWG2, AWG3)

AWG — это WireGuard + обфускация против DPI. Настраивается как обычный sing-box `wireguard` endpoint с дополнительными полями. С `with_awg` они передаются на устройство. Конфиг без единого AWG-поля — обычный WireGuard endpoint, поведение байт-в-байт как в upstream.

AWG2 = поля AWG1 плюс CPS-пакеты `I1`–`I5`. И клиент, и сервер должны работать на AmneziaWG с совпадающими параметрами: I-пакеты — это конфигурация, они не согласуются. Первую приманку проще задать WireSock-style сахаром `id`/`ip`/`ib`: он генерирует `i1` сам. Сахар описан в [полном справочнике](protocols-transports.ru.md#25-сахар-маскировки-id--ip--ib).

AWG3 — это amneziawg-go v3.0/v3.1, контейнер Amnezia `amnezia-awg2` с `protocol_version` 3.x. Он добавляет защиту заголовка, паддинг содержимого, случайные хвосты, отключённые cookie, диапазонные тайминги и диапазонный `persistent_keepalive_interval`. Ключ защиты заголовка `header_protection_key` серверный и обязан совпасть с сервером. Все поля AWG3, как и AWG2, лежат на корне endpoint — [справочник §2.10](protocols-transports.ru.md#210-awg-3x-защита-заголовка-паддинг-хвосты-тайминги).

AWG-поля лежат на корне endpoint, ни одно не на peer, как в секции `[Interface]`
файла `awg-quick` `.conf`: junk (`jc`/`jmin`/`jmax`), паддинг handshake (`s1`–`s4`),
magic-заголовки (`h1`–`h4`, одно значение или диапазон `"min-max"`) и CPS-приманки
(`i1`–`i5`). AWG-endpoint нужен `mtu` ниже, чем у обычного WireGuard, потому что `s4`
паддит каждый data-пакет. Если `s4` задан, а `mtu` нет, ядро ставит `1280`.

## 3. Режимы выбора узла в urltest

Upstream `urltest` всегда выбирает единственный узел с наименьшей задержкой. sing-box-lx добавляет
к нему два режима:

| `mode` | Выбор | Переключение | Что пробуется каждый `interval` |
|---|---|---|---|
| `least_test` (по умолчанию) | самый быстрый | как только кто-то быстрее на `tolerance` | все узлы |
| `round_robin` | пул живых | ротация по пулу | члены пула (лениво) |
| `failover` | самый быстрый на момент выбора | только при отказе или деградации текущего (больше 2× медленнее остальных, с подтверждением); следующий — снова самый быстрый | только текущий узел |

Общие upstream-поля (`url`, `interval`, `idle_timeout`, `interrupt_exist_connections`) не меняются.
Поля `mode` и `balancer` доступны без build-тега. Метод CommandClient `GetPool` требует тега
`with_lx_command`; он описан в [§8](#8-наблюдаемость-расширения-commandclient).

### 3.1 Общие поля

| Ключ | Тип | По умолчанию | Значение |
|------|-----|--------------|----------|
| `mode` | string | `least_test` | `least_test` (поведение upstream) \| `round_robin` (ротация по пулу) \| `failover` (держаться за рабочий узел до его отказа). `least_connection` отклоняется (round_robin статистически равномерен) |
| `balancer` | object | — | параметры round_robin; допустим только с `mode: round_robin`, иначе ошибка старта. Поля — в [§3.3](#33-round_robin--пул-со-sticky-привязкой) |

### 3.2 least_test — самый быстрый узел

Поведение upstream: каждый `interval` пробуются все узлы, группа переключается, как только другой
узел быстрее текущего больше чем на `tolerance` мс (по умолчанию `50`). С опущенным `mode` outbound
ведёт себя так же. Штрафной failover на ошибках дайла класса «путь мёртв» действует и здесь
([SPEC 054](../SPECS/TASKS/054-URLTEST_PENALTY_FAILOVER/SPEC.md)).

### 3.3 round_robin — пул со sticky-привязкой

`round_robin` ротирует трафик по пулу узлов фиксированного размера. Health-check проходит только
пул, а не каждый узел, поэтому режим масштабируется на большие списки. Выбор происходит один раз на
соединение; UDP/QUIC-сессия остаётся на своём узле. Upstream-поле `tolerance` в round_robin
игнорируется, вместо него — `pool_tolerance`. Пока `pool_tolerance` не задан, об этом
напоминает предупреждение при старте.

#### Поля `balancer`

| Ключ | Тип | По умолчанию | Значение |
|------|-----|--------------|----------|
| `pool` | int | `3` | размер пула ротации. `0`/опущено → `3`; отрицательное — ошибка. Эффективный размер — `min(pool, число outbounds)`. Каждый `interval` URL-тестируется только пул, поэтому список из сотен узлов не означает сотни тестов |
| `pool_tolerance` | int (мс) | `0` | `0` — пул всегда полон живых узлов, задержка не ранжируется, тестов не больше нужного; дешёвый режим для больших списков. `> 0` — тестируются все узлы, в пуле держатся `pool` самых быстрых. Член пула заменяется, только когда узел вне пула обгоняет его больше чем на `pool_tolerance` мс (гистерезис). Мёртвый узел пула держит свой слот, пока не найдётся живая замена, поэтому пул никогда не пустеет. Пока в пуле есть живой узел, новые соединения мёртвый обходят: sticky-ключи мёртвых слотов поровну расходятся по живым слотам, простая ротация идёт по живым слотам. Узел в карантине обходится так же. Отказ соединения сам по себе не меняет ни пул, ни историю; он запускает [самовосстановление](#самовосстановление-пула). Живость — общая история URL-тестов узла. Поэтому из ротации до ближайшего health-check пула (не дольше `interval` плюс время пробы) узел выводят и ручной тест задержки с коротким таймаутом, который не успел (Clash API `/proxies/{name}/delay`, `URLTestOutbound`), и неудачный dial группы `least_test` с тем же узлом |
| `sticky_hash` | string[] | `["process","domain"]` | компоненты sticky-ключа потока (см. [Привязка по слот-хешу](#привязка-по-слот-хешу)). Опущено/`[]` → дефолт. Чтобы отключить sticky-привязку, укажите sentinel `["none"]`, никогда не пустой `[]`. Компоненты: `process` \| `domain` \| `source_ip` \| `dest_ip` \| `dest_port` |

> ⚠️ `"sticky_hash": []` не отключает sticky-привязку. Декодер конфига sing-box (badjson)
> ре-маршалит каждый outbound, и пустой JSON-массив не переживает round-trip: он схлопывается
> в «опущено», то есть в дефолт `["process","domain"]` с включённой привязкой. Отключает её явный
> sentinel `["none"]`. Если он есть, он единственный допустимый элемент: смешивание `none`
> с реальным компонентом — ошибка.

#### Привязка по слот-хешу

`sticky_hash` привязывает поток к фиксированному индексу слота `slot[hash(key) % pool]`, а не
к позиции узла; хеш — FNV-64a по конкатенированным компонентам. Слоты никогда не двигаются, и
узел-замена занимает тот же слот, который вытеснил. Поэтому узел, оставшийся в своём слоте,
держит все свои ключи, когда другие слоты меняются: ни лишних реконнектов, ни per-key состояния.

Дефолт `["process","domain"]` привязывает поток по процессу и по домену назначения. `domain`
читает исходный снифнутый домен. Он переживает резолв роутера домен→IP, поэтому заполнен для
обычного доменного трафика, а не только для назначений с литеральным IP. Для доменного трафика
держите `domain` в ключе: ключ только из `source_ip`/`dest_ip`/`dest_port` может схлопнуться
в `""` для нерезолвленного назначения и приклеить все потоки одного источника к одному слоту.

#### Самовосстановление пула

Пул восстанавливается после сбоя узла, не дожидаясь `interval`.

Плановая проверка обходит узлы раз в `interval`, и на большом списке это долгий процесс: между
двумя проверками часто проходит 10–15 минут. Для живого трафика это слишком редко: узел, умерший
сразу после проверки, получал бы свою долю новых соединений до следующей. Поэтому у группы
`round_robin` есть механизмы восстановления, которые работают от самих соединений. О мёртвом
узле, о сайте, закрытом для одного узла, и о пропавшей своей сети группа узнаёт по отказам
соединений и отвечает на каждый случай за секунды.

Настраивать нечего. Скорость загрузки и отдачи не меняется; добавочная работа на каждое соединение
в обычном трафике не видна.

##### Что видит приложение при сбое узла

| Что случилось | Что делает группа | Что видит приложение |
|---|---|---|
| Узел пула умер между проверками: процесс сервера остановлен, машина недоступна | Соединение, не открывшееся через узел, повторяется через следующий слот. Узел вычёркивается, слот получает замену вне пула | Ни одного упавшего соединения |
| Узел принимает соединение и молчит | Через 5 с новые соединения обходят его слот. Через 20 с (5 с ожидания и 15 с таймаута пробы) узел вычёркивается и заменяется. Соединения, ещё открывающиеся через него, повторяются через другой узел; открытые соединения, ждущие первого байта, закрываются | Соединения, попавшие в узел за первые 5 с, ждут, пока его вычеркнут или приложение сдастся; закрытое соединение приложение повторяет |
| Сайт недоступен через один узел: гео-ограничение, сайт не пускает адрес узла | После первого отказа группа проверяет, что сам узел отвечает, и переводит этот сайт на следующий слот. Остальные сайты остаются на своих узлах | Первый запрос может упасть (см. ограничения); следующие идут через другой узел |
| Узел отвечает на пробу, но рвёт заметную долю соединений | Узел с долей отказов от 5 % и больше удвоенной медианы пула уходит в карантин: его слот обходится и получает замену до следующей плановой проверки | Меньше упавших соединений |
| Пропала своя сеть: сон устройства, смена Wi-Fi или мобильной сети, обрыв у провайдера | Не отвечает никто, поэтому группа никого не вычёркивает и замирает на 15 с | После возврата сети пул тот же, что до обрыва |

Цифры — со стенда на роутере NanoPi: пять узлов, `pool: 3`, `interval: 10m`, все серверы на
loopback. С одним убитым узлом пула прошли 30 запросов из 30, слот получил замену за 0,13 с.
Релиз 1.14.4-lx.36 на том же стенде потерял 10 запросов из 30. Когда все серверы остановлены на
20 с под нагрузкой, группа не вычеркнула ни одного узла, не сдвинула ни одного ключа и никого не
отправила в карантин.

Больше всего это дают три сценария:

- пул из нескольких серверов с редкой проверкой (`interval` от 10 минут): сервер, упавший между
  проверками, стоит доли секунды, а не своей доли соединений до следующей проверки;
- подписка с узлами в разных странах: сайт, закрытый для узла одной страны, открывается через
  другой узел пула, а остальной трафик остаётся на своих узлах;
- телефоны и ноутбуки: сон и смена сети не вычёркивают узлы, и после пробуждения пул тот же,
  что работал до него.

Восемь ограничений:

- Так восстанавливается только `mode: round_robin`. У `least_test` и `failover` остаются штраф и
  запасное подключение по ошибкам «путь мёртв» ([§3.2](#32-least_test--самый-быстрый-узел)).
- Первый запрос к сайту, закрытому для узла, может упасть. Через VLESS, Trojan, VMess и
  Shadowsocks отказ виден только после открытия соединения, поэтому группа его не повторяет —
  повторяет приложение. Через `direct` и WireGuard такой запрос ждёт два таймаута подряд.
- Молчащий узел заменяется за 20 с, не сразу.
- Сайт остаётся на новом слоте до перезапуска ядра. Таблица держит 1024 ключа, при переполнении
  вытесняется самый старый. Сайт, закрытый через все узлы пула, возвращается на свой слот до
  следующей проверки.
- Без sticky-привязки (`sticky_hash: ["none"]`) сайты не сдвигаются; мёртвые и карантинные узлы
  обходятся и так.
- UDP покрыт частично: мёртвый узел вычёркивается и для UDP, но отказы UDP не сдвигают ключи и
  не идут в счёт карантина.
- Ключей конфига нет: поведение включено всегда и не настраивается.
- На открытии каждого соединения есть небольшая добавочная работа. Скорость загрузки и отдачи —
  на уровне сборки без самовосстановления; разница видна только в синтетическом прогоне из тысяч
  очень коротких соединений подряд ([замеры](../SPECS/TASKS/138-URLTEST_RR_SKIP_DEAD_SLOT/IMPLEMENTATION_REPORT.md)).

Состояние показывает `sing-box api group pool <tag>` (сборка с `with_lx_command`): таблица слотов
со `STATE` (`live`/`dead`/`quarantined`), `CONNECTIONS` и `FAILURES`, а также сдвинутые ключи,
проблемы в адресе и заморозка. То же несёт `GetPool` демона: по слоту `quarantined`,
`connections` и `confirmedFailures`, по группе `shiftedKeys`, `markedKeys`, `frozen` и
`frozenSeconds`. В libbox поля группы приходят через `GetPoolState`
([§8](#8-наблюдаемость-расширения-commandclient)). Как группа различает эти случаи — в
[следующей части](#как-группа-отличает-мёртвый-узел-от-закрытого-сайта-и-пропавшей-сети).

##### Как группа отличает мёртвый узел от закрытого сайта и пропавшей сети

Одна ошибка соединения не отличает мёртвый узел от сайта, недоступного через него, и от
пропавшей своей сети. Поэтому группа действует по тому, что узнаёт об узле после отказа. Ключей
конфига нет.

- **Повтор.** Соединение, не открывшееся через узел пула, один раз повторяется через следующий
  живой слот, чей узел не вложенный `urltest`. Соединение, закрывшееся без байта от назначения
  после того, как клиент что-то отправил, — тоже отказ, но без повтора.
- **Вердикт по узлу.** Отказ ждёт вердикта по своему узлу: не больше 64 ждущих отказов на узел
  и не дольше 60 с. Вердиктов три:
  - жив — первый байт соединения, начатого после отказа, или ответ пробы, начатой после него.
    Дело в сайте, и sticky-ключ сдвигается на слот после того, где упал. Ключ, упавший на всех
    живых узлах пула, помечается «проблема в адресе»: он возвращается на свой слот и до
    планового или ручного прогона или смены сети не получает ни повторов, ни проверок, ни
    сдвигов;
  - мёртв — проба узла молчит, а контрольный узел (следующий слот) отвечает. История узла
    стирается, его дайлы в полёте отменяются и уходят в повтор, соединения, ждущие первого
    байта, закрываются. Слот сразу получает замену вне пула: при `pool_tolerance: 0` — первый
    живой кандидат в порядке конфига, пробы пачками размером с пул; при `> 0` — самый быстрый
    по истории;
  - не ответил никто — легла своя сеть. Ничего не меняется, самовосстановление замирает.
- **С чего начинается вердикт.** Отказ открытия через прокси-узел бросает подозрение на сам
  узел, и проверка с контролем запускается сразу. Закрытие без байта, отказ открытия через лист
  `direct` или endpoint (WireGuard, AWG, Tailscale и другие туннели) и отказ повтора бросают
  подозрение на сайт. Тогда сразу запускается проба одного этого узла, вне проверки и её паузы,
  не чаще раза в 3 с на узел. Её ответ — вердикт «жив», и ключ сдвигается сразу; её молчание
  запускает проверку с контролем.
- **Пробы** идут на URL группы с таймаутом 15 с, и сама проба не пишет историю. Узел и контроль
  всегда пробуются вживую. Группа ведёт одну проверку за раз, между проверками по отказам — не
  меньше 15 с.
- **Зависший узел.** Узел, который принимает соединение и молчит, отказа не даёт. Проверка
  запускается, когда выбор его слота застаёт соединение через него без ответа дольше 5 с или
  когда клиент сдаётся после 5 с. Проверка идёт не чаще раза в минуту на группу; когда она
  стартовать не может, вместо неё идёт проба одного этого узла. Пока узел не доказал, что жив
  после начала такого соединения, выбор обходит его слот как мёртвый, если в пуле есть слот ни
  мёртвый, ни с таким соединением. Обход не меняет ни историю, ни сдвиги, ни счётчики.
- **Карантин.** Узел от 8 соединений и 3 подтверждённых отказов уходит в карантин, когда его
  доля отказов не меньше 5 % и больше удвоенной медианы остального пула. Выбор его обходит, а
  слот получает замену до планового или ручного прогона или смены сети. История узла остаётся.
- **Заморозка.** 15 с после вердикта «не ответил никто», пробуждения устройства или сети и
  смены сети группа не делает ни повторов, ни проб, ни сдвигов, ни счёта. После смены сети
  заморозка длится ещё и весь прогон.
- **UDP** делит те же слоты. Ошибка открытия UDP — повтор и проверка, как в TCP. Поток,
  отправивший пакеты и не получивший ответа, только запускает проверку. UDP ключи не сдвигает и
  в счёт не идёт.
- **Не трогают состояние.** Тест соединения
  ([SPEC 139](../SPECS/TASKS/139-CONNECTION_TEST/SPEC.ru.md)) получает повтор, но ничего не
  меняет. Замер задержки через группу (проба внешней группы, Clash API) не получает ни повтора,
  ни проверки.

`sing-box api group pool <tag>` (сборка с `with_lx_command`) печатает сдвинутые ключи, проблемы
в адресе, заморозку и таблицу слотов с `DELAY`, `STATE` (`live`/`dead`/`quarantined`),
`CONNECTIONS` и `FAILURES`. Те же поля несут `GetPool` и `GetPoolState` демона
([§8](#8-наблюдаемость-расширения-commandclient)). Список соединений показывает узел, через
который соединение пошло, в том числе после повтора. Все правила — в
[SPEC 138 §3](../SPECS/TASKS/138-URLTEST_RR_SKIP_DEAD_SLOT/SPEC.md#3-самовосстановление-по-отказу-соединения).

#### Пример — urltest с round_robin

```jsonc
{
  "type": "urltest",
  "tag": "auto",
  "outbounds": ["proxy-a", "proxy-b", "proxy-c", "proxy-d", "proxy-e"],
  "interval": "15m",
  "mode": "round_robin",
  "balancer": {
    "pool": 3,
    "pool_tolerance": 0,
    "sticky_hash": ["process", "domain"]   // ["none"] чтобы отключить sticky-привязку
  }
}
```

Для большого списка узлов рекомендуемая настройка с минимальными накладными расходами —
`pool_tolerance: 0`, малый `pool` и бóльший `interval`.

Статус: равномерная ротация проверена локально (10/10/10 с выключенной sticky-привязкой) и
end-to-end на устройстве, на реальном многоузловом пуле. Фикс `domain` из rc.15 поднимает
на устройстве per-domain равномерность с ~0.27 до 0.95+.

📖 [Полный справочник](../docs/configuration/outbound/urltest.md): каждое поле, семантика
sticky по компонентам, правила наполнения и поддержки пула, советы по тюнингу.

### 3.4 failover — держаться до отказа

**Выбор.** Группа берёт самый быстрый узел на момент выбора, без `tolerance`; порядок в списке
`outbounds` роли не играет.

**Удержание.** Пока узел работает, группа остаётся на нём, даже если другой стал быстрее. Каждый
`interval` пробуется только удерживаемый узел: одна проба вместо N, остальные узлы спят.

**Деградация.** Если удерживаемый узел ответил больше чем вдвое медленнее самого
быстрого из остальных узлов той же сети (по их последней задержке), он сразу пробуется ещё раз.
Если снова больше 2×, идёт полный прогон. Группа переезжает на самый быстрый узел, только если
тот больше чем в 1,5 раза быстрее; иначе остаётся: просела сеть, а не узел. Ключа конфига нет.

**Отказ.** Два вида:

- проба удерживаемого узла не ответила → полный прогон по всем узлам → самый быстрый из живых;
- дайл через него упал с ошибкой «путь мёртв» → штраф и fallback-дайл, как в [least_test](#32-least_test--самый-быстрый-узел) → выбор переезжает
  без `Interrupt`.

После переезда новый узел становится удерживаемым. Деградировавший узел (выше) уходит так же.

**Ручной тест.** Тест группы из UI, CLI (`sing-box api group urltest <tag>`) или Clash API всегда
`force`: пробует все узлы и перевыбирает самый быстрый. Это единственный способ вернуться на
лучший узел, пока удерживаемый жив.

**Что не действует.** `tolerance` игнорируется, при старте выводится предупреждение. `balancer`
даёт ошибку старта.

В UI задержки невыбранных узлов показаны на момент последнего полного прогона.

#### Пример — urltest с failover

```jsonc
{
  "type": "urltest",
  "tag": "auto",
  "outbounds": ["proxy-a", "proxy-b", "proxy-c", "proxy-d", "proxy-e"],
  "url": "https://www.gstatic.com/generate_204",
  "interval": "15m",
  "mode": "failover"
  // tolerance не задаётся: переключений «по скорости» нет (ненулевое значение — предупреждение)
  // balancer не задаётся: с failover это ошибка старта
}
```

Когда выбирать: мобильные профили и случаи, где стабильность узла важнее всегда актуального самого
быстрого. Сколько проб это экономит — в [lx-energy.ru.md §6](lx-energy.ru.md#6-пробы-urltest-будят-спящих-поэтому-их-ограничивают-пять-механизмов).

### 3.5 Сравнение и выбор режима

| Что важнее | Режим |
|---|---|
| минимум переключений и одна проба в `interval` | `failover` |
| распределение нагрузки по нескольким узлам | `round_robin` |
| всегда самый быстрый узел любой ценой проб | `least_test` |

По энергии: `least_test` будит все узлы каждый `interval`, `round_robin` — только пул (при `pool_tolerance: 0`), `failover` —
один узел; подробнее в [lx-energy.ru.md §6](lx-energy.ru.md#6-пробы-urltest-будят-спящих-поэтому-их-ограничивают-пять-механизмов).

## 4. MASQUE outbound — Cloudflare WARP

Outbound `masque` туннелирует целые IP-пакеты поверх HTTP/3 или HTTP/2 через CONNECT-IP (RFC
9484). Основное назначение — подключение к Cloudflare WARP. Это CONNECT-IP, а не CONNECT-UDP
(RFC 9298). С AWG-сахаром *masquerade* `id/ip/ib` из §2 у него общее только слово. Ядро
поднимает на туннель userspace gVisor-стек и гонит трафик через него, как через
WireGuard-endpoint. Outbound собирается с тегами `with_quic` и `with_gvisor`, оба входят в
дефолтный `LX_TAGS`. Ключи берутся готовыми из конфига: регистрацию устройства (ECDSA-ключи,
WARP enroll) делает клиент, не ядро.

> ⚠️ Версия HTTP задаётся полем `vhttp`, а не `network`. В старых конфигах `h3`/`h2`
> задавались в `network`, хотя на всех остальных outbound `network` значит другое. Ключ
> снят в `v1.14.3-lx.18`: masque-outbound с `network` не разбирается
> (`unknown field "network"`), переименуйте ключ в `vhttp`. Плоские TLS-поля пока
> принимаются с deprecation; таблица миграции — в полном справочнике (ссылка ниже).

Обязательные поля — `server`/`server_port`, пара ключей (`private_key`/`public_key`, для
дефолтного профиля `cloudflare`) и хотя бы один из `ip`/`ipv6`. `ip`/`ipv6` — локальный адрес
клиента *внутри* туннеля, не выходной IP. TLS задаётся в стандартном блоке `tls` outbound'а. У
остальных полей есть дефолт:

| Поле | По умолчанию |
|------|--------------|
| `profile` | `cloudflare` |
| `vhttp` | `auto` |
| `tls.server_name` | `www.cloudflare.com` |
| `mtu` | `1280` |
| `idle_timeout` | выключен или глобальный `lx.masque.idle_timeout` ([§13](#13-корневой-блок-lx)); ключ узла сильнее глобального, `"0"` тоже |
| `keep_alive_period` | `30s` |
| `network_list` | `tcp+udp` |

SNI по умолчанию — `www.cloudflare.com`, а не имя эндпоинта: по имени MASQUE-эндпоинта в
ClientHello его режет DPI. Эндпоинт аутентифицируется пиннингом `public_key`, поэтому SNI может
отличаться.

> 📖 Полный справочник — в
> [protocols-transports.ru.md §3](protocols-transports.ru.md#3-masque-outbound-connect-ip--warp)
> ([EN](protocols-transports.md#3-masque-outbound-connect-ip--warp)): каждое поле с типом и
> дефолтом, матрица профилей (`cloudflare` и `standard`), формат ключей, выбор `vhttp`
> между h3 и h2, поведение idle-suspend и keepalive, валидация при старте, таблица
> миграции со схемы с `network` и частые грабли.

### Пример — WARP (дефолты: `vhttp: auto`)

```jsonc
{
  "type": "masque",
  "tag": "warp",
  "server": "162.159.198.2",
  "server_port": 443,
  "profile": "cloudflare",
  "tls": {
    "server_name": "www.microsoft.com"   // любой нейтральный популярный хост (domain-fronting)
  },
  "private_key": "<base64 DER EC private key>",
  "public_key":  "<base64 DER PKIX public key>",
  "ip":   "172.16.0.2/32",
  "ipv6": "2606:4700:110:...::/128",
  "mtu":  1280
}
```

`"vhttp": "auto"` — значение по умолчанию. Оно сначала пробует h3 и переходит на h2, если
QUIC-хендшейк не уложился в 3 с. Победа h3 запоминается. Победа h2 запоминается на окно, которое
растёт по лестнице 1 с → 10 с → 30 с → 5 мин → 10 мин: каждая следующая победа h2 поднимает
ступень, победа h3 возвращает на первую. Когда окно истекает, h3 снова пробуется первым. Если
запомненный режим перестал подниматься, память сбрасывается, и в той же попытке пробуется
другой.

`auto` нужен для отказа, при котором эндпоинт молча игнорирует QUIC: ошибки нет, есть зависание.
Так же ведёт себя TCP-only-хоп перед эндпоинтом — HTTP CONNECT в `detour` или звено VLESS/Trojan
в цепочке. Случай пойман в поле на проксированном хопе: Cloudflare отвечал по TCP:443 и не
отвечал по QUIC. На профиле `standard` ноги h2 нет, поэтому дефолт там означает h3; явный
`"vhttp": "auto"` на `standard` даёт предупреждение.

> ⚠️ Профиль `"standard"` требует `uri`. У `cloudflare` есть дефолт
> (`https://cloudflareaccess.com`), у `standard` его нет, и без `uri` outbound не поднимается:
> `masque: uri is required for the standard profile — set it to the server's CONNECT-IP
> request URI, e.g. https://<host>/.well-known/masque/ip/*/*/`. Значение уходит в запрос
> Extended CONNECT как есть, ядро ничего в нём не подставляет. Поэтому пишите шаблон,
> который публикует сервер. RFC 9484 описывает форму полного туннеля с `*` на местах
> хоста и порта.

Для `h2` (CONNECT-IP поверх TCP:443) меняется одно поле: `"vhttp": "h2"`. Путь `h2` гонит свой
TLS через общий слой `common/tls`, поэтому ClientHello режется так же, как у любого другого
TLS-outbound: узловыми `fragment` / `record_fragment` и секцией `tls` блока
[`lx.sniff_guard`](#lxsniff_guard--защита-от-перенаправления-по-sni). Ногу `h3` защищает секция
`quic` того же блока; в `auto` у ног отдельные лейблы пути. Без блока ClientHello через `detour`
не режется ([§9](#9-clienthello-под-detour--без-дефолта)).

> ⚠️ Нужен блок `dns` верхнего уровня. Userspace-стек работает на L3 и сам домены не
> резолвит: outbound резолвит их через DNS-роутер перед dial.

Внешний QUIC к серверу стартует с `InitialPacketSize` = `mtu + 51` (кламп 1200…1452; при `mtu`
1280 — 1331). Так внутренний пакет размером `mtu` помещается в датаграмму с первого пакета, а не
после первой пробы PMTUD.

> ⚠️ WARP пропускает внутренние IPv4-фрагменты и теряет IPv6-фрагменты. Узел над masque,
> чей пакет не влезает в `mtu`, по IPv6 молчит, по IPv4 работает: так ведёт себя QUIC-прокси
> с payload 1280, это 1328 байт по IPv6. Узел над masque — через `detour`, группу или как
> звено `chain` — получает размер пакета под `mtu` автоматически
> ([§13, `lx.mtu_align`](#lxmtu_align--выравнивание-mtu-и-размера-пакета-по-пути)). Вручную —
> `initial_packet_size: 1232` у QUIC-узла или `mtu: 1340` у masque; второе требует внешнего
> пути ≈ 1440 байт до WARP.

`h3` (QUIC) стоит по умолчанию и быстрее. В сетях, где режется входящий UDP:443, QUIC-хендшейк
виснет и `h3` не поднимается. Такой узел переключите на `h2` (TCP:443): там он проверен на
устройстве. Первый dial `h3` медленный, потому что холодный CONNECT-IP — это QUIC-хендшейк,
Extended CONNECT, анонс маршрута и стек. Короткий таймаут urltest может пометить свежий h3-узел
`-1` на первой пробе, хотя дальше узел работает.

Outbound проверен на устройстве от начала до конца, на Wi-Fi и LTE: `warp=on`, трафик идёт и на
`h3`, и на `h2`, idle-suspend и самовосстановление подтверждены.

## 5. Группа DNS-серверов

Тип `group` объединяет несколько DNS-серверов под одним тегом и выбирает между ними по
стратегии. Он нужен, чтобы один мёртвый DNS-сервер не ронял резолв целиком. В апстриме
`dns.final` — сервер *по умолчанию*, а не резерв, и запрос, который правило направило в сервер,
при любой сетевой ошибке, таймауте или SERVFAIL падает без повтора. Build-тега нет, тип доступен
всегда; конфиг без `group`-сервера ведёт себя как upstream. Разбор — в [фиче
DNS_GROUP](../SPECS/FEATURES/013-DNS_GROUP/FEATURE.md).

У серверов нет состояний: down и backoff не существуют. Вместо них группа ведёт две таблицы
записей с TTL. Запись об ошибке пишет любой сбойный обмен, и она стирает живые победы сервера.
Запись о победе пишет только первый успех веера; любой успех стирает живые ошибки сервера.
Чистый сервер — сервер с нулём живых ошибок. Смена сети очищает обе таблицы.

### Поля (запись в `dns.servers[]`)

```jsonc
{
  "type": "group",                  // селектор — строго "group"
  "tag": "public",
  "hosts": ["local"],               // необязательное: только теги серверов hosts.
                                    //   Опрашиваются первыми, в этом порядке;
                                    //   серверами группы не считаются (без здоровья и веера)
  "servers": ["google", "cloudflare", "quad9"], // обязательное, ≥1 тегов.
                                    //   Порядок не значим ни в одном режиме
  "mode": "stable",                 // stable (дефолт) | fastest | parallel
  "error_ttl": "2m",                // дефолт 2m: сколько живёт запись об ошибке
  "win_ttl": "5m"                   // дефолт 5m: сколько живёт победа.
                                    //   Только fastest; вне него — предупреждение
}
```

Сбой — это транспортная ошибка, таймаут или `SERVFAIL`. `NXDOMAIN` и пустой ответ — валидные
ответы; если такой ответ пришёл в веере первым, он засчитывается победой.

Три режима выбирают цель среди чистых серверов:

- `stable` — sticky прежде случайности: группа остаётся на текущем сервере, пока он чист.
  Случайный перевыбор среди чистых — только когда чистого текущего нет. На выздоровевший
  бывший текущий группа не возвращается: он просто возвращается в пул.
- `fastest` — чистый сервер с максимумом живых побед. Когда живых побед нет ни у кого,
  запрос становится веером-выборами по всем чистым. Выборы идут по одному за раз
  (single-flight), конкурентные запросы в это время идут к случайному чистому. Переизбрание
  наступает, когда истекает `win_ttl`.
- `parallel` — каждый запрос идёт веером по всем чистым, победы не пишутся. Трафика по
  определению в N раз больше.

Если чистых нет, любой режим делает одну попытку к наименее грязному серверу и не уходит в веер.
Это режим выживания: он защищает от шторма запросов.

Одиночная цель получает под-дедлайн — половину остатка бюджета запроса; остаток гарантирован
вееру-спасению. При сбое цели запрос уходит веером по оставшимся чистым. Первый успех отвечает и
становится текущим. Опоздавшие отбрасываются: в кеш они не идут, но их успех лечит записи ошибок
своего сервера. Сбой участника веера после завершения контекста запроса — артефакт, он никуда не
записывается.

Поток DNS-запросов показывает участника, который фактически ответил; при попадании в кеш и
полном сбое там тег группы. В потоке есть трасса проб и флаги `fanned` / `survival`. Трасса —
это путь групп изнутри наружу, исходы проб `answered`/`timeout`/`network_error`/`servfail` и
rtt. `GetDNSGroups` ([§8](#8-наблюдаемость-расширения-commandclient), `with_lx_command`) отдаёт
живые записи по каждому участнику: чистота, живые ошибки (счёт и возраст последней), живые
победы, последний rtt, флаг текущего.

> ⚠️ При сбое любой режим шлёт имя запроса всем чистым участникам, `parallel` — с каждым
> запросом. Не смешивайте внутренние и публичные резолверы в одной группе.

### Локальные имена первыми: `hosts`

Необязательный ключ `hosts` перечисляет серверы типа `hosts`, которые группа опрашивает до
выбора цели, в порядке ключа:

- **Попадание** — запрос A или AAAA, участник знает имя и отвечает NOERROR. Этот ответ
  отдаётся как есть, сетевые участники не опрашиваются. Попаданием считается и пустой
  NOERROR, когда в записи есть только другое семейство адресов: имя только с IPv4 на
  запрос AAAA получает пустой ответ, и в сеть запрос не уходит. Поэтому
  `strategy: ipv6_only` на таком имени адреса не даёт — так же, как `hosts`-файл ОС.
- **Промах** — имя неизвестно, другой тип запроса или ответ не NOERROR: запрос
  уходит в `servers` по режиму группы без изменений.
- У участников `hosts` нет записей здоровья. Они не входят в веер и режим выживания, не
  становятся текущими и отсутствуют в `GetDNSGroups`. Попадание видно как ответ участника
  `hosts` с одной пробой `answered`; промах следа не оставляет.
- `servers` остаётся обязательным и непустым. Сервер `hosts` (или `fakeip`) внутри
  `servers` отвергается при загрузке, и ошибка указывает на ключ `hosts`. Ключ принимает
  только теги типа `hosts`, без дубликатов и без пересечения с `servers`.

Ключ работает везде, где принимается тег группы: `domain_resolver` (у узла или
`route.default_domain_resolver`), `dns.final`, правила. Он нужен, потому что адреса серверов
outbound и endpoint резолвятся через `domain_resolver`. Этот резолвер идёт в сервер напрямую,
минуя DNS-правила, поэтому до этих адресов не доходят ни действие правила `predefined`, ни
правило `server: hosts`. Сам `hosts` таким резолвером быть не может: на любое другое имя он
отвечает NXDOMAIN.

### Пример — отказоустойчивый публичный DNS по умолчанию

```jsonc
{
  "dns": {
    "servers": [
      { "type": "udp", "tag": "google",     "server": "8.8.8.8" },
      { "type": "udp", "tag": "cloudflare", "server": "1.1.1.1" },
      { "type": "group", "tag": "public",
        "servers": ["google", "cloudflare"],
        "mode": "fastest", "error_ttl": "2m", "win_ttl": "5m" }
    ],
    "final": "public"
  }
}
```

### Пример — одно локальное имя для WireGuard-сервера с IPv4 и IPv6

Свой WireGuard-сервер (или WARP), доступный по IPv4 и IPv6 под одним локальным
именем (issue #60):

```jsonc
{
  "dns": {
    "servers": [
      { "type": "hosts", "tag": "local",
        "predefined": { "wg.home": ["203.0.113.10", "2001:db8::10"] } },
      { "type": "udp", "tag": "google",     "server": "8.8.8.8" },
      { "type": "udp", "tag": "cloudflare", "server": "1.1.1.1" },
      { "type": "group", "tag": "resolver",
        "hosts": ["local"],
        "servers": ["google", "cloudflare"],
        "mode": "stable" }
    ],
    "final": "resolver"
  },
  "route": { "default_domain_resolver": { "server": "resolver", "strategy": "prefer_ipv6" } }
}
```

`wg.home` в адресе сервера endpoint'а получает оба адреса из `local`, семейство выбирает
`strategy`. Любое другое имя идёт в `google` / `cloudflare` по режиму `stable`.

> ⚠️ Контракт v1 (`mode: failover|race`, `interval`, `down_time`) вышел в
> `v1.14.0-lx.16-rc.1` и удалён: конфиги с ним не загружаются.

## 6. VLESS `encryption` — пост-квантовый слой

Плоское поле `encryption` на `vless`-outbound включает рукопожатие `mlkem768x25519plus` внутри
VLESS. Этот слой лежит над транспортом и TLS, под VLESS-клиентом. От key exchange REALITY он не
зависит: это другой слой. Серверы, которые требуют его (в Xray настроен `decryption`), молча
рвут обычный VLESS. Транспорт поднимается: WS отвечает `101`, gRPC — на SETTINGS. После этого
пир закрывает соединение без единой строки в логе ядра; этот симптом поле и лечит. В форке
только клиентская половина: форк клиентский, серверная половина не портирована. Поле всегда в
сборке, build-тега нет.

### Поле (на `vless`-outbound)

| Ключ | Тип | По умолчанию | Значение |
|------|-----|--------------|----------|
| `encryption` | string | `""` | `""`/`"none"` = слой выключен (поведение upstream байт-в-байт). Иначе — spec-строка; `check` и старт проверяют её, ошибка называет конкретный сегмент |

Грамматика spec-строки (сегменты через точку):

```
mlkem768x25519plus.<native|xorpub|random>.<0rtt|1rtt>[.<padding>…].<ключ>[.<ключ>…]
```

- **appearance** — как слой выглядит на проводе: `native` (AEAD-заголовки в форме
  TLSv1.3), `xorpub` (XOR по публичному ключу), `random`.
- **rtt** — `0rtt` или `1rtt`.
- **padding** — опциональные короткие блоки вида `100-111-1111`. Сегмент короче
  20 символов до первого ключа читается как padding.
- **ключ** — base64url публичного ключа X25519 (32 байта) или ML-KEM-768
  (1184 байта); ключей может быть несколько. Рабочий ключ ML-KEM-768 — ~1579
  символов; заметно более короткий — обрезанный ключ, а не другой формат.

### Пример

```jsonc
{
  "type": "vless",
  "tag": "pq-node",
  "server": "example.com",
  "server_port": 443,
  "uuid": "00000000-0000-0000-0000-000000000000",
  "encryption": "mlkem768x25519plus.native.0rtt.<base64url ключ ML-KEM-768>",
  "transport": { "type": "ws", "path": "/ws" }
}
```

Поле вышло в `v1.14.0-lx.18` и проверено на устройстве на подписке, из-за которой появилось:
заработали 10 узлов, мёртвых без него (6 из 8 WS, 4 из 4 gRPC), в остальных группах транспортов
ничего не изменилось. В поле встречается форма `native.0rtt`. `1rtt` с padding и
`xorpub`/`random` парсятся и собираются, но живого сервера с ними ещё не встречали.

> ⚠️ В подписке значение приходит как `settings.vnext[0].users[0].encryption`. На
> sing-box-outbound это плоское поле `encryption` рядом с `uuid`. Если билдер конфига его
> теряет, ядру нечего включать.

## 7. REALITY `key_share` — гибридный или классический ClientHello

Поле `key_share` — строка в `tls.reality`, задаётся на каждом узле:

```json
"reality": { "enabled": true, "public_key": "…", "short_id": "0123abcd", "key_share": "classical" }
```

| Значение | ClientHello | Работает против |
|---|---|---|
| `""` (не задано) | Как несёт отпечаток: `chrome` / `firefox` / `safari` шлют гибридный шар `X25519MLKEM768`, `edge` / `ios` / `android` / `360` / `qq` — только X25519. Ядро ничего не меняет. | любой Xray, если отпечаток несёт гибрид; иначе только Xray < v26.9.8 |
| `"classical"` | `X25519MLKEM768` вырезан из `key_share` и `supported_groups`. Приветствие как у апстрима, на ~1,2 КБ короче (`chrome`: 594 байта вместо 1720, один TCP-сегмент вместо двух). | Только Xray < v26.9.8. Новые серверы молча отвергают приветствие без гибрида (`reality verification failed`). |
| `"hybrid"` | Гибрид обязателен. На отпечатке без него рукопожатие сразу падает с `reality key_share "hybrid": fingerprint Edge 85 carries no X25519MLKEM768 key share`. Без этого значения сервер отказал бы молча, и отказ не отличить от чужого ключа. На `chrome` / `firefox` / `safari` ничего не меняет. | как `""` |

Любое другое значение — ошибка конфига при загрузке: опечатка не должна молча становиться
дефолтом.

В некоторых сетях двухсегментное гибридное приветствие теряется, а односегментное классическое
проходит (LxBox #142). Клиент самого Xray упирается в ту же проблему (XTLS#6256). Новые
Xray-серверы гибрид требуют. Ядро не может выбрать за пользователя между «сервер отвергнет» и
«сеть потеряет», поэтому выбор задаётся на узле. `classical` снижает постквантовую защиту и
годится только для старых серверов. Для нового сервера в такой сети остаются `record_fragment`
([§9](#9-clienthello-под-detour--без-дефолта)) и `detour`.

## 8. Наблюдаемость (расширения CommandClient)

Это дополнения клиентского API, а не конфига: методы на `CommandClient` libbox (нативный
gRPC-канал управления). Все они за тегом `with_lx_command`, их вызывает LxBox. В конфиг-файл
sing-box они ничего не добавляют: методы появляются в сборке с тегом, а вызывает их клиент. Без
тега методов нет, и демон обслуживает только апстримный набор команд. Разбор — в [фиче
OBSERVABILITY](../SPECS/FEATURES/006-OBSERVABILITY/FEATURE.md).

Методы, которые форк добавляет в `CommandClient`:

- **`URLTestOutbound(tag, link, timeout)`** — синхронно измеряет задержку одного outbound
  или endpoint по требованию, вне периодического теста группы.
- **`GetRules()`** — отдаёт снимок таблицы маршрутных правил: route-правила и DNS-правила.
- **`GetGroups()`** — отдаёт снимок outbound-групп; те же данные пушит поток групп.
- **`GetOutbounds()`** — отдаёт плоский список outbound и endpoint. Он нужен рядом с
  `GetGroups`, потому что отдельно стоящие outbound не входят ни в одну группу. Элемент
  WG/AWG-endpoint'а ещё несёт `EndpointState` (`never_built` / `building` / `up` / `asleep`
  / `torn_down` / `down` / `disabled`) и `IdleSinceSeconds` — время с последнего дайла. У
  прочих outbound оба поля пусты или 0
  ([lx-energy.ru.md §11](lx-energy.ru.md#11-ленивая-сборка-и-бюджет-не-дают-собирать-устройства-впустую)).
  Состояние `disabled` выставляет `SetEndpointEnabled` (ниже;
  [lx-energy.ru.md §12](lx-energy.ru.md#12-ручной-переключатель-выключает-endpoint-без-правки-конфига)).
- **`GetPool(groupTag)`** — отдаёт текущий пул ротации round_robin группы `urltest`, слот
  за слотом ([§3](#3-режимы-выбора-узла-в-urltest)). По каждому слоту ещё отдаёт
  `Quarantined`, `Connections` и `ConfirmedFailures`.
- **`GetPoolState(groupTag)`** — отдаёт те же слоты и состояние группы: `ShiftedKeys`,
  `MarkedKeys`, `Frozen` и `FrozenSeconds`
  ([самовосстановление](#самовосстановление-пула)).
- **`GetDNSGroups()`** — отдаёт живое состояние каждого DNS-сервера `group`
  ([§5](#5-группа-dns-серверов)): по каждому участнику `clean` / `liveErrors` /
  `lastErrorAgeMs` / `liveWins` / `current`.
- **`GetRunningConfig()`** — отдаёт канонический JSON options, из которых построен
  работающий box, после override. Результат — объект с аксессором `Content()`: голый
  `string`-возврат ронял бы gomobile на android/arm64.
- **`SubscribeDNSQueries(includeAnswers, handler)`** — подписывает на структурный живой
  поток DNS-запросов. По каждому запросу приходят `domain`, `qtype`, `rcode`, CNAME-цепочка
  и ответы (при `includeAnswers`), привязка к процессу, `dnsServer` / `dnsServerType` /
  `outbound`. `rcode` `-1` означает ошибку резолва — это полноправное состояние. Пустой
  `outbound` означает direct/system — тоже валидное состояние, не баг.
- **`GetChains()`** — отдаёт состояние каждого outbound `chain`
  ([§10](#10-outbound-chain--виртуальная-цепочка-хопов-из-групп-и-узлов)): по позициям
  разрешённый узел, а для позиций ≥ 1 — звено (`starting|active|idle`, живые соединения,
  эффективный MTU и причина, что снял `strip`, применён ли `rewrite`, последняя ошибка).
  Метод отдаёт и счётчики дозвонов, ошибок и звеньев.
- **`SetEndpointEnabled(tag, enabled)`** — выключает или включает WG/AWG-endpoint на ходу
  ([lx-energy.ru.md §12](lx-energy.ru.md#12-ручной-переключатель-выключает-endpoint-без-правки-конфига)). Возвращает
  объект `EndpointToggleResult`; его поле `State` — состояние endpoint'а после вызова.

Поток соединений тоже расширен: отслеживаемое `Connection` несёт отдельное поле **`detourList`**
— хвост transport-detour'а финального outbound. Он отдаётся отдельно от прокси-`chain`, потому
что `chain` не включает detour.

Методы появляются в сборке с тегом:


## 9. ClientHello под `detour` — без дефолта

> ⚠️ Без блока `lx.sniff_guard` ядро режет ClientHello как апстрим: только там, где у узла
> задан `fragment` или `record_fragment`, через `detour` тоже. В прежних релизах
> TLS-over-TCP outbound (VLESS, trojan, vmess, anytls, shadowtls, http, masque `h2`, …),
> который диалит через `detour`, по умолчанию резал ClientHello на TLS-записи
> (`record_fragment`). Конфиг без блока загружается без ошибки, а TLS-узлы через релеи,
> которые перенаправляют соединение по SNI, перестают подниматься.

Разрез защищает от релея, который читает SNI из ClientHello и отправляет соединение на это имя
вместо назначения узла. Так работает Xray `sniffing` с `destOverride` без `routeOnly`. Узел, у
которого SNI — маскировка (WARP с чужим именем, REALITY), получает соединение не туда: хендшейк
висит и падает с `tls handshake: EOF` через 12–17 с, либо приходит чужой ключ. ClientHello,
разрезанный на TLS-записи, TLS-сниффер Xray не разбирает. Замер через сниффящее плечо: без
разреза ❌ отказ за 12 с; `fragment` ✅ 0.6 с; `record_fragment` ✅ 0.1 с.

Защиту включает блок [`lx.sniff_guard`](#lxsniff_guard--защита-от-перенаправления-по-sni) (§13).
Минимальный блок:

```json
"lx": { "sniff_guard": { "tls": { "method": "record_fragment" } } }
```

С ним путь через любой релей, кроме `ssh` и `socks`, стартует с разрезом, прямой путь — без.
Путь через `ssh` и `socks` стартует без разреза. Разрез на нём включается, если узел на этом
пути упал без разреза и прошёл с ним. Чтобы с разрезом стартовали все релеи, как при прежнем
дефолте, добавьте `"detour_type": {"ssh": "suspect", "socks": "suspect"}`. Карта накладывается
поверх дефолтов, поэтому перечислять нужно только то, что меняется. Узлы, у которых SNI
совпадает с `server`, блок по умолчанию не защищает (`nodes.sni_mismatch`). Прежний дефолт резал
и их; чтобы резать их тоже, добавьте `"nodes": {"sni_mismatch": false}`. В отличие от прежнего
дефолта, блок учится по исходу подключений и может снять разрез с пути, где он мешает.

Узловые ключи апстрима:

- **`fragment` / `record_fragment`** у узла действуют как в апстриме, с блоком и без него.
  Блок перекрывает их только при `"override": true`.
- **`"record_fragment": false`** — узел просит ClientHello одной записью. Под блоком без
  `override` такой узел идёт без разреза на любом пути.
- **REALITY-узлы** — `fragment` / `record_fragment` действуют и на них. В апстриме
  REALITY-клиент строит uTLS-соединение на голом сокете, и эти ключи там молча не
  действуют. Гибридный ClientHello занимает 1,5–1,9 КБ, это два TCP-сегмента. Поможет ли
  разрез в сети, которая теряет такой первый пакет, — свойство той сети. Второй способ —
  `key_share` ([§7](#7-reality-key_share--гибридный-или-классический-clienthello)).
- Разрезается только хендшейк, трафик после него не трогается.

## 10. Outbound `chain` — виртуальная цепочка хопов из групп и узлов

Build-тег `with_lx_chain` входит в десктопные `LX_TAGS` и в AAR. Без него `"type": "chain"`
отвергается при чтении конфига. Разбор — в [фиче CHAIN](../SPECS/FEATURES/015-CHAIN/FEATURE.md).

```json
{
  "type": "chain",
  "tag": "virtualisation",
  "outbounds": ["selector-in", "selector-mid", "selector-exit"],
  "idle_timeout": "5m",
  "strip_evasion": true,
  "strip": { "multiplex.padding": false, "tls.utls": true },
  "rewrite": { "wireguard": { "mtu": 1200 } }
}
```

Позиции в `outbounds` идут в порядке пакета. `outbounds[0]` — первый хоп от клиента: он касается
реальной сети и используется как есть, с его dial-полями. Последняя позиция — узел, чей адрес
видит цель. Запись через `detour` читается наоборот: там узел с `detour` — выход. Любая позиция
— узел, endpoint или группа любой вложенности. Все три формы работают одинаково, длина любая (≥
2):

```
["selector-in", "selector-mid", "selector-exit"]   // все группы
["node-in",     "node-mid",     "node-exit"]       // все узлы
["node-in",     "selector-mid", "node-exit"]       // смешанно
```

| Ключ | Тип | Дефолт | Смысл |
|------|-----|--------|-------|
| `outbounds` | список тегов, ≥ 2, все различны | обязательное | позиции в порядке пакета; повтор тега — ошибка старта, см. ниже |
| `idle_timeout` | длительность | `5m` | простаивающее звено (см. ниже) без живых соединений удаляется через это время; `0` — жить до остановки |
| `strip_evasion` | bool | `true` | снимать односторонние DPI-приёмы у звеньев на позициях ≥ 1 (каталог ниже) |
| `strip` | карта ключ → bool | `{}` | патч к каталогу: `false` — оставить, `true` — снимать дополнительно; неизвестный ключ — ошибка старта |
| `rewrite` | карта тип → JSON-объект | `{}` | merge-patch (RFC 7396) к конфигу каждого звена этого типа на позициях ≥ 1 |

Теги в `outbounds` должны различаться: повтор валит старт с `duplicate outbound in chain`,
потому что в списке, который читается как путь, это почти всегда описка. Чтобы поставить один
узел на несколько позиций намеренно, объявите его отдельным тегом на каждую позицию; учётные
данные в объявлениях могут совпадать. Так строится «сэндвич» `WARP → чужой узел → WARP`: внешние
слои прячут середину от вашего адреса, а цель — от середины. Каждая позиция получает своё звено
со своим detour (звено ключуется парой «позиция, узел»), и экземпляры независимы.

Группы не копируются: цепочка зовёт оригинальную группу, и та выбирает со всей своей логикой
(ручной выбор, health-check, sticky, штрафы, `interrupt_exist_connections`). Узел, выбранный на
позиции ≥ 1, работает через своё звено — рантайм-экземпляр этого узла, который дозванивается до
своего сервера через предыдущую позицию. Звенья создаются при первом использовании. На старте
прогреваются позиции с известным выбором — узлы и селекторы; позиции с urltest остаются
ленивыми. Звено несёт тег узла, поэтому история и штрафы группы продолжают работать. Звено
удаляется, только когда у него ноль живых соединений и его не выбирали дольше `idle_timeout`.
Переключение группы не убивает старое звено, пока через него идёт поток. WireGuard-звенья
засыпают по правилам idle-suspend, как любой endpoint.

- **`direct` на позиции ≥ 1 прозрачен**: хопа нет. Положите `direct` в селектор, чтобы
  выключать позицию на лету. `block` отвергает. Если все позиции ≥ 1 — `direct`, цепочка
  равна позиции 0.
- **MTU и размер пакета звеньев выравниваются автоматически** общим механизмом
  `lx.mtu_align` ([§13](#lxmtu_align--выравнивание-mtu-и-размера-пакета-по-пути)), тем же,
  что под обычным `detour`. `mtu` в конфиге узла означает «как у самостоятельного узла».
  Цепочка вычитает точные накладные IP-туннелей *под* звеном и берёт худший случай по
  участникам группы: WG внутри IP-туннеля −60/−80 по семейству адреса сервера, MASQUE
  −79/−99. QUIC-звенья (hysteria2, tuic, hysteria) на позициях ≥ 1 получают
  `initial_packet_size` под ёмкость хопа ниже и `disable_path_mtu_discovery: true`. Над
  любым прокси (vless/trojan/ss/hysteria2/…) ничего не меняется. Режим (`clamp` по
  умолчанию, `fill`, `off`) и `except` действуют на звенья так же.
- **Каталог `strip`** — односторонние приёмы, сервер их не видит:
  - `tls.fragment` — пакетная фрагментация ClientHello и `fragment_fallback_delay`.
    `record_fragment` каталог не трогает: защиту пути от перенаправления по SNI задаёт
    `lx.sniff_guard` (§9, §13);
  - `multiplex.padding`;
  - `xhttp.padding` — `x_padding_bytes` фиксируется на нижней границе диапазона узла, без
    явного диапазона — на `100`; размещение и obfs-режим не меняются;
  - `tls.utls` — только явным `"tls.utls": true`; на узле с `reality` это ошибка старта.
- Контракты с сервером — `flow`, `obfs`, `shadowtls`, `plugin`, `udp_over_tcp`, `ech`,
  пути транспортов — не снимаются никогда.
- Порядок преобразований звена: `strip` → `rewrite` → MTU. Все патчи прогоняются всухую на
  старте по каждому узлу, достижимому на позициях ≥ 1: `rewrite` с неизвестным полем валит
  старт, а не первый дозвон.

> ⚠️ По умолчанию цепочка снимает фрагментацию ClientHello на позициях ≥ 1: обычный DPI
> стоит между вами и первым хопом. Если позиция 0 — домашний relay, а DPI стоит на границе
> (`["relay", "foreign-node"]`), фрагментация нужна на позиции 1. Для этого поставьте
> `"strip": {"tls.fragment": false}`.

`detourList` соединения ([§8](#8-наблюдаемость-расширения-commandclient)) показывает разрешённый
путь. `GetChains` (CommandClient) и Clash API `/proxies/<tag>` → `chain` отдают состояние по
позициям и счётчики. Состояние позиции — выбранный узел, состояние звена `starting|active|idle`,
живые соединения, эффективный MTU и причина, что снято или переписано, последняя ошибка. Ошибки
дозвона называют позицию и хоп под ней: `chain[virtualisation] #2 (warp-exit) via #1 (node-m):
…`. Задержку по слоям меряет URLTest по внутренним тегам `<tag>#0`, `<tag>#1`, …; каждый тег
меряет путь до своей позиции.

Известные границы: группа на позиции ≥ 1 ранжирует узлы по *прямым* замерам; туннель над хопом
без UDP падает при дозвоне, и ошибка называет обе позиции; вложенный `chain` допустим только на
позиции 0.

## 11. Снифферы протоколов для трафика из LAN

Форк добавляет имена протоколов для списка `sniffer` действия `sniff` и матчера `protocol` в
правилах: `wireguard`, `openvpn`, `ike`, `tailscale`, `sip`. `sip` ещё ставит `domain` из
Request-URI. Снифферы узнают VPN-туннели и звонки других устройств за роутером по форме первого
пакета. Они стоят перед апстримным uTP-сниффером, потому что тот помечает plain WireGuard как
`bittorrent`. Считается только первый пакет потока, поэтому junk и decoy насквозь не видны.
Порядок снифферов, ограничения и пример для роутера — в [lx-sniff.ru.md](lx-sniff.ru.md).

## 13. Корневой блок `lx`

Глобальные ручки форка живут в одном корневом блоке `lx`, сгруппированные по подсистеме. Всё, что
описывает конкретный узел, остаётся в его объекте, как в апстриме: поля AWG — в endpoint'е, `xhttp` —
в `transport`, собственный `idle_timeout` masque-узла — в узле. Все подблоки и ключи опциональны;
пустой `lx` и отсутствующий равнозначны. Опечатка в имени ключа — ошибка загрузки, не тихий дефолт.

```jsonc
"lx": {
  "wg": {
    "idle": {
      "suspend": "30s",
      "suspend_reachable": "5m",
      "teardown": "10m",
      "lazy_build": true,
      "build_max": 4,
      "build_overflow": "wait"
    },
    "buffers": {
      "read_datagram_count": 8,
      "send_by_mtu": true
    },
    "connected_socket": true
  },
  "masque": {
    "idle_timeout": "5m"
  },
  "trusttunnel": {
    "idle_timeout": "5m"
  },
  "mtu_align": "clamp",
  "sniff_guard": {
    "tls": { "method": "record_fragment" },
    "quic": { "method": "decoy_first_byte" }
  }
}
```

### `lx.wg` — endpoint'ы WireGuard / AmneziaWG

Подблок `idle` работает только в мобильной сборке (`with_lx_idle_suspend`), остальные ключи
`lx.wg` — в любой сборке.

| Ключ | Тип | Дефолт | Значение |
|---|---|---|---|
| `idle.suspend` | длительность | выкл | Порог простоя endpoint'а вне активного дерева маршрутизации: после него устройство уводится в Down (сокеты закрыты, приёмные буферы свободны), следующий дайл будит. Отсутствие или `0` выключает механизм, тик не стартует |
| `idle.suspend_reachable` | длительность | выкл | Второй, более длинный порог для endpoint'ов в дереве (член urltest-пула, выбранный узел, final); без него они не спят. Обязан быть ≥ `idle.suspend`, требует его |
| `idle.teardown` | длительность, явный `"0"` допустим | наследует `idle.suspend_reachable` | Сколько уже спящий endpoint спит до разборки устройства и netstack'а; считается от засыпания. `"0"` запрещает разборку. Требует `idle.suspend` |
| `idle.lazy_build` | bool | `false` | Endpoint'ы стартуют разобранными, устройство собирается при первом дайле. Требует `idle.suspend` |
| `idle.build_max` | целое ≥ 0 | `0` = без потолка | Не больше N собранных устройств одновременно |
| `idle.build_overflow` | `wait` \| `build` | `wait` | Когда все `build_max` устройств держат живые соединения: ждать в пределах дедлайна дайла или собрать сверх потолка с предупреждением |
| `buffers.read_datagram_count` | целое 1–128 | `128`, как в апстриме | Сколько датаграмм резервируется на одно чтение из сокета. Для слабых машин — `8`. Linux и Android, туннели без `detour` |
| `buffers.send_by_mtu` | bool | `true` | Брать буфер чтения из стека по MTU туннеля, а не 64 КБ. `false` — для диагностики |
| `connected_socket` | bool | `false` | Подключать сокет туннеля к адресу сервера в режиме одного пира. Linux и Android |

Таймлайны трёх ключей сна и рекомендованный мобильный конфиг — в
[lx-energy.ru.md](lx-energy.ru.md). Порядок выбора жертвы и состояния для `lazy_build`,
`build_max` и `build_overflow` — в
[lx-energy.ru.md §11](lx-energy.ru.md#11-ленивая-сборка-и-бюджет-не-дают-собирать-устройства-впустую). Как ведут себя
эти три ключа:

- `lazy_build` не действует на endpoint с `listen_port` (его никто не дайлит).
- `build_max` без `lazy_build` допустим: устройства собираются на старте, а потолок действует с
  первой пересборки (пробуждения после `idle.teardown`).
- `wait` из `build_overflow` длится до дедлайна самого дайла, не дольше 15 с.
- `build_max` ниже числа одновременно используемых узлов заставляет их разбирать друг друга при
  каждом переключении, и каждый дайл платит сборку устройства. Ставить для сессий с массовыми
  пробами, а не как общую ручку памяти.

`buffers` и `connected_socket` относятся к сокету туннеля без `detour`; у туннеля через
`detour` своего сокета нет, и на него они не действуют.

- `buffers.read_datagram_count`: туннель держит по одному буферу на 64 KiB на каждую датаграмму,
  которую может прочитать за раз, в каждой из двух приёмных рутин (IPv4 и IPv6), всё время,
  пока жив: 16,4 MiB при значении по умолчанию 128, около 1 MiB при 8. При значении меньше 128
  сокет создаётся без склейки ядра на приём (UDP GRO); склейка на отправку (UDP GSO) остаётся.
  На плате с четырьмя ядрами Cortex-A55 на 100–150 Мбит/с значение не влияло ни на скорость,
  ни на процессор. На настоящей сетевой карте и на быстрых каналах пачки и GRO могут давать
  выигрыш, поэтому значение по умолчанию оставлено апстримным. На macOS и Windows ключ
  принимается и ничего не меняет.
  Замер на 100 простаивающих туннелях без `detour` в одном экземпляре (та же плата):

  | `read_datagram_count` | Куча Go | Занято физически (RSS) |
  |---|---:|---:|
  | 128 (по умолчанию) | 1740 MiB | 94 MiB |
  | 8 | 138 MiB | 77 MiB |
  | 2 | 58 MiB | 75 MiB |
  | 1 | 44 MiB | 74 MiB |

  Простаивающий туннель при любом значении занимает мало физической памяти: буфер, в который
  ни разу не читали, страницами не подкреплён. Куча при этом важна. Она входит в лимит памяти
  рантайма, сдвигает порог сборки мусора (при 1,74 GiB живой кучи следующая сборка — на 3,5 GiB),
  а буфер становится физическим, как только через туннель пошёл трафик. Поэтому чем больше
  туннелей, тем меньше значение: `8` для одного-двух туннелей на слабой машине, `1` или `2`
  для десятков и сотен. Скорость при `1` на релизной сборке не мерилась; измерительная сборка
  показала на 3 % меньше отдачи, чем при `8`.
- `buffers.send_by_mtu: false` ставит буферы чтения из стека туннеля по 64 КБ, как в версиях до
  lx.36. Он нужен при разборе проблемы, чтобы исключить буферы по MTU из подозреваемых. В
  остальных случаях ставить его незачем.
- `connected_socket` действует на туннель с одним пиром, фиксированным адресом сервера и без
  `listen_port`. Сокет подключается к серверу, и система хранит маршрут, а не ищет его на
  каждую датаграмму. На той же плате это около 5 % отдачи, вместе с
  `buffers.read_datagram_count: 8` — 7 %; замер через loopback. Цена: подключённый
  сокет слышит только адрес сервера, а его исходный адрес фиксируется при подключении. Ядро
  отключает сокет при любой ошибке отправки и когда рукопожатие остаётся без ответа, затем
  подключает снова. Сервер, ответивший с нового адреса, будет услышан после ближайшего повтора
  рукопожатия, а не сразу. По умолчанию ключ выключен: он не проверен на телефоне, который
  меняет сеть. Ключ действует на Linux и Android; на macOS сокет в этом режиме подключён всегда.

Ключи `lx.wg.idle` действуют только в сборках с `with_lx_idle_suspend` (мобильный AAR).
Десктоп/CLI-бинарь отвергает их на старте — любое окно простоя, явный `idle.teardown` (включая `"0"`),
`lazy_build`, ненулевой `build_max` или `build_overflow: "build"`:
`lx.wg.idle.* is set but this build lacks idle-suspend support; rebuild with -tags with_lx_idle_suspend (mobile-only feature)`.
`lx.wg.buffers` и `lx.wg.connected_socket` в этом отказе не участвуют.
`sing-box check` проверяет ключи, но роутер не запускает, поэтому на десктопе принимает их.

Каноническая форма отбрасывает явно записанные значения по умолчанию:
`read_datagram_count: 128`, `send_by_mtu: true`, `connected_socket: false`, пустые блоки `idle` и
`buffers`.

Ошибки валидации называют полный путь ключа:

- `lx.wg.idle.suspend_reachable must be >= lx.wg.idle.suspend`
- `lx.wg.idle.suspend_reachable requires lx.wg.idle.suspend`, так же для `idle.teardown`, `idle.lazy_build`
- `lx.wg.idle.<ключ> must be >= 0` для отрицательной длительности, `lx.wg.idle.build_max must be >= 0`
- `lx.wg.idle.build_overflow must be "wait" or "build"`
- `lx.wg.buffers.read_datagram_count must be between 1 and 128` для `0`, отрицательного значения и больше 128
- `lx.wg.<старый ключ> is moved to lx.wg.idle.<новый ключ>` для плоского ключа прежней раскладки; соответствие ключей — в разделе [Переехали: плоские ключи сна в `lx.wg`](#переехали-плоские-ключи-сна-в-lxwg)

### `lx.mtu_align` — выравнивание MTU и размера пакета по пути

Узел может стоять прямо над IP-туннелем: через `detour`, через группу под `detour` или как звено
`chain` ([§10](#10-outbound-chain--виртуальная-цепочка-хопов-из-групп-и-узлов)). Такой
узел получает размер пакета, который влезает в туннель: `mtu` у туннелей (`wireguard`,
`masque`), `initial_packet_size` плюс `disable_path_mtu_discovery: true` у QUIC-прокси
(`hysteria2`, `tuic`, `hysteria`). Размер считается один раз на старте по конфигу, до создания
узлов, и апстримные конструкторы читают уже поправленные опции. Значения только понижаются;
каждое изменённое поле видно в логе старта вместе с причиной. Исходный случай — issue #37:
hysteria2 через `detour` на WARP работал с IPv4-сервером и молчал с IPv6-сервером.

Один ключ в корневом блоке `lx`, две формы записи:

```jsonc
"lx": { "mtu_align": "clamp" }                                        // строка — режим
"lx": { "mtu_align": { "mode": "clamp", "except": ["my-wg"] } }       // объект — режим + исключения
```

| Режим | Поле не задано | Задано явно и больше предела | Задано явно и влезает |
|---|---|---|---|
| `off` | не трогается | не трогается | не трогается |
| `fill` | дописывается предел | не трогается; предупреждение «не влезет под `<tag>`» | не трогается |
| `clamp` (дефолт) | дописывается предел | понижается до предела; в лог: configured → effective и причина | не трогается |

Ни один режим не повышает значения. `except` — теги узлов, которые не трогаются ни в одном режиме.
Неизвестный режим отвергается при разборе конфига, неизвестный тег — позже, при сборке
экземпляра, когда известны все узлы. Без ключа действует `clamp`. Это контракт `chain` («`mtu` в
конфиге = как самостоятельного, цепочка только понижает»), и он действует и под обычным `detour`.

Ошибки валидации (все три ловит и `sing-box check`):

- `lx.mtu_align.mode must be "off", "fill" or "clamp"` — неизвестный режим, в строковой и в
  объектной форме; при разборе конфига
- `lx.mtu_align.except: empty tag` — пустая строка в `except`
- `lx.mtu_align.except: unknown outbound/endpoint tag: <теги>` — тега нет ни среди outbound'ов, ни
  среди endpoint'ов; проверяется перед выравниванием, до создания узлов

**Ёмкость узла** — сколько байт IP-пакета он пронесёт для узла над собой:

| Узел снизу | Ёмкость |
|---|---|
| `masque`, `wireguard` (endpoint и legacy outbound), `openvpn-client`, `openconnect` | его эффективный `mtu` (после собственного выравнивания, рекурсивно вниз) |
| `tailscale` endpoint | `system_interface_mtu`, иначе 1280 |
| `selector`, `urltest` | min по всем достижимым членам, рекурсивно |
| `chain` как цель `detour` | без предела + предупреждение (цепочка выравнивает себя сама) |
| любой другой узел — `direct` и любой прокси (vless, trojan, ss, socks, hysteria2, tuic, …), с `detour` или без | без предела: прокси доставляет пакет узла над собой целиком (потоком TCP или своей нарезкой), и то, что лежит под его `detour`, верхний узел не ограничивает |

Ёмкость наверх несут только туннели и группы. Это правило не покрывает один случай: туннель над
`shadowsocks` или `socks` по UDP, у которых свой `detour` на туннель. Они пропускают датаграммы
как есть, и ограничение под ними действует; верхнему туннелю там `mtu` задаётся руками.

**Что получает узел сверху** (`ipudp` = 28 для IPv4-сервера, 48 для IPv6; домен или неразобранный
адрес считаются IPv6; у WG-endpoint семейство берётся из `peers[0].address`):

| Узел сверху | Поле | Предел | Накладные v4 / v6 |
|---|---|---|---|
| `wireguard` | `mtu` | `ёмкость − 32 − s4 − ipudp` (`s4` — транспортный паддинг AmneziaWG, 0 у обычного WG) | 60 / 80 (+ `s4`) |
| `masque` | `mtu` | `ёмкость − 51 − ipudp` | 79 / 99 |
| `hysteria2`, `tuic`, `hysteria` | `initial_packet_size` (+ `disable_path_mtu_discovery: true`) | `ёмкость − ipudp`, кламп 1200…1452 | — |
| `openvpn-client`, `openconnect` | — | не выводится; одно предупреждение, если под узлом есть ёмкость | неизвестны |

**Пол IPv6.** Туннель, который несёт IPv6 внутри, никогда не выравнивается ниже 1280. Это
`wireguard`-endpoint с IPv6-префиксом в `address` и `masque` всегда. gvisor молча не поднимает IPv6 на
канале с меньшим MTU, а мёртвый IPv6 внутри туннеля хуже фрагментов. Если путь оставляет меньше
1280, туннель получает 1280 и строку Warn (`… is above the path: … leaves 1220 bytes, below the IPv6
minimum 1280; outer packets will be fragmented`). Туннель только с IPv4 внутри выравнивается и ниже
1280; явный `mtu` ниже 1280 никогда не повышается.

Если предел QUIC-узла ниже 1200 (туннель с `mtu` < 1248 под IPv6-сервером), ставится 1200 с
предупреждением: ниже минимума QUIC опуститься нельзя. PMTUD выключается вместе с выведенным
`initial_packet_size`, потому что quic-go умеет только искать размер вверх до 1452: по IPv6 пробы
теряются вместе с фрагментами, по IPv4 «проходят» фрагментацией, и каждый пакет едет двумя. Узел с
явным `initial_packet_size` не трогается целиком, включая PMTUD.

**Пример — WARP по умолчанию** (`masque` с `mtu` 1280) и hysteria2 с `detour` на него:

```jsonc
{ "type": "masque", "tag": "warp", "mtu": 1280, /* … */ },
{ "type": "hysteria2", "tag": "hy2", "server": "2001:db8::1", "detour": "warp", /* … */ }
```

`hy2` получает `initial_packet_size: 1232` (1280 − 48) и `disable_path_mtu_discovery: true`; с
IPv4-сервером — 1252 (1280 − 28). Без выравнивания quic-go шлёт пакеты с payload 1280, по IPv6 это
1328 байт. Туннель режет их на фрагменты, и WARP их теряет ([§4](#4-masque-outbound--cloudflare-warp)).

**Группы.** Под группой берётся min по всем членам на старте; при переключении селектора/urltest
значение не пересчитывается. Размер QUIC-пакета фиксируется при создании клиента, MTU
WG-устройства — при создании устройства, и живое соединение на новый путь не переезжает. Цена на
широком члене группы: до 200 байт на пакет (1452 → 1252) и выключенный PMTUD. Если эта цена
мешает, есть три выхода: явное значение в режиме `fill`, тег в `except` или режим `off`.

**Лог старта** — одна Info-строка на изменённое поле, предупреждения — Warn:

```
mtu_align: hy2 initial_packet_size → 1232 (detour warp[masque] mtu 1280 − 48 ipv6; pmtud off)
mtu_align: wg-exit mtu 1420 → 1200 clamped (limited by warp[masque] mtu 1280 via sel −80 ipv6)
```

У `chain` то же решение видно в `ChainInfo` (`mtu_configured` / `mtu_effective` / `mtu_reason`
с префиксом режима `clamped:` / `filled:`). Решения по `detour` lx RPC не отдаёт.

**Не выравниваются:**

- xhttp по h3 и naive (cronet) — у них свой QUIC-транспорт;
- `openvpn-client` и `openconnect` как верхние узлы — только предупреждение;
- направление «сервер → клиент» — им управляет сервер.

Чем masque отвечает на это снизу (внешний `InitialPacketSize` = `mtu + 51`, ICMP Packet Too Big с
фактическим бюджетом) — в [§4](#4-masque-outbound--cloudflare-warp).

### `lx.sniff_guard` — защита от перенаправления по SNI

Между клиентом и сервером может стоять узел, который читает имя из первого пакета рукопожатия и
отправляет соединение на это имя, а не на набранный адрес. Так работает Xray-инбаунд с
`sniffing.destOverride` без `routeOnly`. Он встречается на релее под `detour` и на роутере с VPN
или прозрачным прокси в локальной сети. Пока SNI — собственное имя сервера, подмена приводит туда
же. Когда SNI — маскировка (REALITY, WARP, hysteria2 или tuic с подставным SNI, QUIC-маскировка
AmneziaWG), соединение уходит на чужой хост, и узел выглядит мёртвым. Блок делает первый пакет
рукопожатия нечитаемым для сниффера и не меняет того, что получает сервер. По исходам подключений
блок учится, на каких путях это нужно.

Без блока, как и без `method` в секции, защиты нет: рукопожатие уходит как в апстриме. Блок, в
котором ни у одной секции нет метода, равнозначен отсутствию блока. Сам себя блок не включает:
дефолты защиты выставляет приложение, которое пишет конфиг.

```jsonc
"lx": {
  "sniff_guard": {
    "nodes": {
      "sni_mismatch": true,                 // нет ключа = true; false — фильтра нет
      "outbound_type": ["vless", "masque"]  // false | нет ключа — фильтра нет
    },
    "detour_type": {                        // нет detour = "direct"
      "direct": "clean",
      "ssh":    "clean",
      "socks":  "clean",
      "*":      "suspect"
    },
    "override": false,
    "tls": {
      "method": "record_fragment",          // record_fragment | fragment | delay | off
      "delay": "300ms",
      "persist": true
    },
    "quic": {
      "method": "decoy_first_byte",         // decoy_first_byte | delay | off
      "detour_type": { "socks": "never" },
      "persist": true
    }
  }
}
```

**Кого защищать — `nodes`.** Два фильтра; узел защищается, если проходит оба. Узел, не прошедший
фильтры, работает как без блока. Без блока `nodes` действует `sni_mismatch: true`: узел с
собственным именем проходит сниффящий релей и без защиты. Защиту всем узлам, которые её умеют,
даёт `sni_mismatch: false`.

| Ключ | Значения | Без ключа | Смысл |
|---|---|---|---|
| `sni_mismatch` | `true`, `false` | `true` | `true` — только узлы, у которых SNI не совпадает с адресом `server`; `false` — фильтра нет |
| `outbound_type` | список типов, `false` | фильтра нет | Только узлы перечисленных типов. `true`, пустой список и неизвестный тип — ошибка загрузки; известный тип, который защиту не умеет, допустим и пропускается |

Совпадение SNI с `server` проверяется при загрузке сравнением строк, без DNS: без учёта регистра
и завершающей точки, поддомен — другое имя. Сравнивается имя, которое фактически уйдёт в ClientHello
или Initial; при ECH — внешнее, публичное. Внешнее имя берётся только из конфига ECH, заданного
в самом узле (`ech.config`); при `ech.config_path` и ECH из DNS сравнивается обычный
`server_name`.

| `server` | SNI | Результат |
|---|---|---|
| домен | не задан или тот же домен | совпадает |
| домен | другое имя | не совпадает |
| IP | имя | не совпадает |
| IP | не задан | совпадает — снифферу нечего читать |
| любой | SNI не отправляется (`disable_sni`) | совпадает |
| hysteria2 с обфускацией Salamander | любое | совпадает — Initial снифферу не прочитать |
| REALITY, masque (WARP), QUIC-маскировка AWG | любое | не совпадает всегда |

Узел за CDN (`server` — IP CDN, SNI — свой домен) попадает под фильтр без нужды, защита ему не
мешает. Узел, для имени которого DNS релея отдаёт другой адрес, фильтр `sni_mismatch` не
пройдёт. Для него ставят `sni_mismatch: false`, при нужде вместе с `outbound_type`.

**Стартовое состояние пути — `detour_type`.** Карта «тип носителя → состояние, с которого путь
начинает». Носитель — ближайший не-групповой outbound, через который фактически идёт
подключение: группа (`selector`, `urltest`) разворачивается в выбранного участника. Узел без
`detour`, с `detour` в `direct` или в группу, где сейчас выбран `direct`, идёт по пути типа
`direct`. Если носитель определить не удалось, путь считается неизвестным: защиты нет, лейбл не
ведётся.

| Значение | Смысл |
|---|---|
| `never` | На этом пути защиты нет никогда: лейбл не ведётся, повторов нет, узловые ключи работают как в апстриме |
| `clean` | Старт без защиты |
| `suspect` | Старт с защитой |

Ключ `"*"` — все типы, которых нет в карте. Группы ключами быть не могут. Дефолт карты: `direct`,
`ssh`, `socks` — `clean`; `"*"` — `suspect`. Секция `tls` или `quic` может перекрыть отдельные
типы своей картой `detour_type`, остальные берутся из общей. `"socks": "never"` в секции `quic`
примера взят из полевого случая: через `socks` с UDP-over-TCP байт-приманка ломала туннель, хотя
сниффера на пути не было.

**Секции `tls` и `quic`, `override`.**

| Ключ | Значения | Без ключа | Смысл |
|---|---|---|---|
| `tls.method` | `record_fragment`, `fragment`, `delay`, `off` | `off` | Метод для TLS поверх TCP (таблица ниже) |
| `quic.method` | `decoy_first_byte`, `delay`, `off` | `off` | Метод для QUIC |
| `delay` (в секции) | положительная длительность | `300ms` | Пауза метода `delay` этой секции. Против Xray нужна больше 200 мс; меньшее значение допустимо для сниффера с более коротким ожиданием. Ноль и отрицательное — ошибка загрузки |
| `persist` (в секции) | `true`, `false` | `false` | Сохранять лейблы зашифрованных релеев в `experimental.cache_file`. `true` без включённого `cache_file` — ошибка загрузки |
| `detour_type` (в секции) | карта, как выше | общая карта | Перекрытие стартовых состояний для протокола |
| `override` (общий) | `true`, `false` | `false` | `false` — узловые `fragment` / `record_fragment` сильнее блока, узел с явным значением идёт по нему. `true` — для узла, прошедшего `nodes`, форму ClientHello определяет лейбл пути: на `suspect` — метод блока, на `clean` — без разреза, даже если узел просил разрез. На пути `never` блок не действует. У QUIC узловых ключей нет, там `override` ни на что не влияет |

Узловые `tls.fragment`, `tls.record_fragment` (явный `false` — отказ от разреза) и
`tls.fragment_fallback_delay` работают при любом состоянии блока, как в апстриме.

**Методы.** Сервер в каждом случае получает корректное рукопожатие. После рукопожатия трафик не
трогается.

| Метод | Что уходит в сеть | Против сниффера Xray | Цена |
|---|---|---|---|
| `tls.record_fragment` | ClientHello разрезан на несколько TLS-записей, точки разреза внутри имени SNI | Сниффер разбирает только первую запись, она обрывается посреди расширений — «не ClientHello» с первой попытки | Нет |
| `tls.fragment` | ClientHello одной записью, кусками по TCP-сегментам с ожиданием ACK (на сокете устройства) или паузой (через релей) | Защищает, пока пауза между кусками больше 200 мс: через релей это `fragment_fallback_delay` (500 мс), на прямом пути за прозрачным прокси ядро выдерживает ту же паузу | Пауза `fragment_fallback_delay` через релей и на прямом пути за прозрачным прокси |
| `tls.delay` | ClientHello одной записью, двумя кусками с разрезом внутри SNI и паузой `delay` между ними | Первый кусок неполон, сниффер ждёт продолжения 200 мс и сдаётся | Пауза `delay` на каждом защищённом рукопожатии |
| `quic.decoy_first_byte` | Датаграмма из одного байта `0x00` перед первым Initial; сервер её отбрасывает | QUIC-сниффер решает по первой датаграмме: «не QUIC» | Нет |
| `quic.delay` | Второй Initial задерживается на `delay` | Сниффер собирает ClientHello из Initial-пакетов в пределах 200 мс и не успевает | Пауза `delay` на каждом защищённом рукопожатии |

**Какие узлы умеют защиту.** TLS поверх TCP: vless, trojan, vmess, anytls, shadowtls, http с TLS,
masque `h2`, trusttunnel `h2`, XHTTP на `h2`. QUIC: masque `h3`, hysteria2, tuic, trusttunnel с
QUIC, XHTTP на `h3`, wireguard с QUIC-образной маскировкой AmneziaWG. Не умеют и пропускаются
молча: naive и узлы с системным TLS-движком (`engine: apple`, `windows`).

| Метод | Применим | Не применим |
|---|---|---|
| `tls.record_fragment`, `tls.fragment`, `tls.delay` | все TLS-узлы из списка выше | naive, системные TLS-движки |
| `quic.decoy_first_byte` | все QUIC-узлы из списка, включая AmneziaWG | — |
| `quic.delay` | QUIC-узлы, у которых ClientHello занимает два Initial-пакета | AmneziaWG; узел, чей ClientHello уместился в один Initial; hysteria2 с обфускацией Salamander. На таком узле метод ничего не делает |

Узел, к которому метод секции не применим, идёт как без блока и лейбл пути не двигает.

**Как учится лейбл пути.** Лейбл ведётся на пару «путь + протокол»: путь — `direct` или тег
ближайшего релея, протокол — `tls` или `quic`. Ключ — тег, а не тип: два VLESS-релея с разной
настройкой сниффинга различаются. Лейбл общий для всех узлов, которые идут этим путём; TLS и QUIC
друг на друга не влияют. На `clean` узел идёт без защиты, на `suspect` — с защитой.

Лейбл меняется только парой исходов на одном узле:

- узел упал без защиты, затем прошёл с ней → путь становится `suspect`;
- узел упал с защитой, затем прошёл без неё → путь становится `clean`;
- любой другой исход лейбл не трогает. Мёртвый узел, который падает в обоих случаях, ничего не
  меняет, поэтому массовая проверка узлов, часть которых мертва, защиту с пути не снимает.

Быстрая ошибка (не таймаут) повторяется в том же дайле с противоположным решением. Таймаут
отдаёт ошибку, а противоположное решение достаётся следующему дайлу этого узла на этом пути
(в пределах 10 минут). На пути `suspect` попытка без защиты после неудачи допускается не чаще раза
в 10 минут на путь; в остальное время неудача на `suspect` ничего за собой не тянет.

В пару идут только попытки, в которых рукопожатие действительно состоялось и решение блока к
нему применено. Дайл, севший на уже поднятую сессию (mux, пул anytls, XHTTP, долгая QUIC-сессия
masque, hysteria2, tuic, trusttunnel), и узел с собственным выбором при `override: false` в пару
не идут.

Лейбл двигают только узлы, у которых SNI не совпадает с `server` (по таблице выше), независимо
от фильтра `sni_mismatch`. Узел с собственным именем проходит сниффящий релей и без защиты, поэтому
его исходы о сниффере ничего не говорят. Такой узел защиту по лейблу получает только при
`sni_mismatch: false`. На пути `clean` он повторов не делает. На пути `suspect`, если он упал с
защитой и прошёл без неё, узел запоминает личный отказ: дальше на этом пути он идёт без защиты, а
лейбл пути и остальные узлы не меняются. Обратная пара на этом узле (упал без защиты, прошёл с ней) отказ снимает. Повтор для
такого узла — не чаще раза в 10 минут. Личный отказ живёт, пока жив экземпляр ядра, и не
сохраняется.

Особенности протоколов:

- **hysteria2, tuic** — рукопожатие идёт внутри библиотеки QUIC, исход оценивается по сроку жизни
  соединения: закрытое раньше 30 с после дозвона — неудача, прожившее дольше — успех. Успех
  засчитывается, как только соединение прожило 30 с; неудача — при следующем новом соединении
  узла. Повтора в том же дайле нет, пара складывается через следующий дайл. При порт-хопе hysteria2 сокеты следующих
  хопов рукопожатия не несут и не защищаются; режим realm у hysteria2 не защищается вовсе.
- **masque `auto`** — ноги живут по разным лейблам: h3 по `quic`, h2 по `tls`. Быстро упавший h3
  повторяется с противоположным решением до отката на h2. Молчащий h3 через 3 с без
  хендшейка уступает h2, а противоположное решение достаётся следующей ноге h3.
- **AmneziaWG** — endpoint `wireguard` под блок попадает, если его маскировка `ip: "quic"` или у
  него непустой `i1`; байт уходит только перед QUIC-образной пачкой. Решение берётся из лейбла на
  момент создания сокета. Исход рукопожатия лейбл не двигает, поэтому AmneziaWG никогда не
  двигает лейбл пути. Если других QUIC-узлов на пути нет, лейбл остаётся стартовым. Узлу AWG на
  пути со стартом `clean` (прямой, `socks`) защиту задают явно: `suspect` для этого типа носителя
  в `quic.detour_type`.

Каждая смена лейбла и каждая постановка или снятие личного отказа пишут строку в лог на уровне
info: путь, протокол, старое и новое состояние, узел и исходы обеих попыток. Отдельного API нет.

**Цена обучения.**

- Первая неудача на пути `clean` — таймаут, а не ошибка: сниффер уводит соединение на имя, где
  никто не отвечает. Первый дайл узла висит до дедлайна, первый URL-тест узла падает, защита
  приходит со второго дайла.
- Узел с быстрым отказом стоит двух рукопожатий вместо одного.
- Случайный сбой на чистом пути (неудача без защиты, следом успех с ней) ставит `suspect`, и снять
  его может только обратная пара. Для `record_fragment` и `decoy_first_byte` это бесплатно; для
  `delay` и `fragment` — пауза на каждом рукопожатии, с `persist` и после перезапуска.

**Смена сети и `persist`.** Смена сети сбрасывает в стартовое состояние лейблы пути `direct` и
незашифрованных носителей (`socks`, `http` без TLS) вместе с личными отказами и ожидающими
повторами на них. Лейблы зашифрованных релеев смену сети переживают. Если под тем же тегом
оказался другой релей (тип, адрес или порт), его лейблы и отказы сбрасываются. Без `persist` лейблы
живут, пока жив экземпляр ядра: перезапуск и применение нового конфига начинают со стартовых
состояний. С `persist` лейблы зашифрованных релеев пишутся в `experimental.cache_file` и
поднимаются при старте, если под тем же тегом тот же релей. Запись для пути, который карта в
текущем конфиге объявляет `never`, не применяется. Лейблы `direct` и незашифрованных носителей не
сохраняются.

**Ошибки загрузки.** Все их ловит `sing-box check`. `<key>` — полный путь ключа, например
`lx.sniff_guard.quic.detour_type`.

| Причина | Сообщение |
|---|---|
| Неизвестный метод | `lx.sniff_guard.tls.method must be one of "record_fragment", "fragment", "delay", "off"`; `lx.sniff_guard.quic.method must be one of "decoy_first_byte", "delay", "off"` |
| `nodes.outbound_type: true` | `lx.sniff_guard.nodes.outbound_type: true is not a filter; list the types, or use false for no filter` |
| `nodes.outbound_type: []` | `lx.sniff_guard.nodes.outbound_type: empty list; list the types, or use false for no filter` |
| Тип, которого не знает ни один outbound или endpoint этой сборки, в `nodes.outbound_type` или ключом `detour_type` | `<key>: unknown outbound type "<t>"` |
| Группа в `nodes.outbound_type` | `lx.sniff_guard.nodes.outbound_type: "<t>" is a group; a group is never dialled itself, name the member types` |
| Группа ключом `detour_type` | `<key>: "<t>" is a group; name the member types, a group is resolved to the member it picks` |
| Неизвестное значение в карте `detour_type` | `<key>.<type> must be "never", "clean" or "suspect"` |
| `delay` ноль или отрицательный | `<key>.delay must be > 0` (`<key>` — `lx.sniff_guard.tls` или `lx.sniff_guard.quic`) |
| `persist: true` без включённого `experimental.cache_file` | `lx.sniff_guard.tls.persist: requires experimental.cache_file to be enabled`; то же с `.quic` |
| Неизвестный ключ или значение, которое не объект | сообщение начинается с ключа: `lx.sniff_guard`, `lx.sniff_guard.nodes`, `lx.sniff_guard.tls`, `lx.sniff_guard.quic` |
| Удалённый ключ `lx.quic_sniff_decoy` | `lx.quic_sniff_decoy is removed: the QUIC sniff decoy is configured by lx.sniff_guard.quic` |

Проверки неизвестного типа и `persist` выполняются, только если хотя бы у одной секции задан
метод; `persist` проверяется у секции, у которой метод есть.

**Границы.**

- Сниффер напрямую не обнаруживается и от других причин отказа не отличается. Признак один —
  пара исходов на одном узле, и случайный сбой может сложиться в ложную пару.
- Рукопожатие, которое без ошибки завершилось не там, успехом и считается: `tuic` с `insecure` и
  SNI, который резолвится в живой QUIC-хост. masque защищён пином ключа, hysteria2 —
  аутентификацией, TLS-узлы — проверкой сертификата (без `insecure`).
- Полный gRPC-транспорт (`grpc`, не lite) не защищается: его рукопожатие идёт вне дайла узла.
  Такой узел идёт как без блока.
- На прямом пути не защищаются shadowtls v2/v3 и любой узел с `tcp_fast_open`: путь для них
  определить нельзя. Через `detour` они защищаются как все.
- shadowtls v3 без uTLS не защищается ни на каком пути: его рукопожатие идёт мимо TLS-слоя ядра.
  С uTLS — как остальные.
- Релей блок не лечит; на стороне релея лечение — `"routeOnly": true` в `sniffing`.
- Против снифферов, кроме Xray, не проверено. sing-box как релей назначение по сниффингу не
  подменяет, защита через него не нужна. Ожидание 200 мс — константа Xray; для другого сниффера
  `delay` подбирается ключом.
- DPI, который дропает защищённое рукопожатие (разрез на записи как сигнатура), блок не обходит:
  лейбл такого пути по паре уходит в `clean`.

### `lx.quic_sniff_decoy` — удалён

Заменён блоком `lx.sniff_guard`. Любое значение ключа — ошибка загрузки:
`lx.quic_sniff_decoy is removed: the QUIC sniff decoy is configured by lx.sniff_guard.quic`;
обратной совместимости нет. Байт `0x00` перед QUIC Initial задаёт
метод `"decoy_first_byte"` в секции `quic`:

```json
"lx": { "sniff_guard": { "quic": { "method": "decoy_first_byte" } } }
```

| Было | Стало |
|---|---|
| `mode`, `detour_type` | карта `detour_type` (общая или `quic.detour_type`): `never` для путей, где байт не нужен |
| `send: "always"` | стартовое состояние `suspect` |
| `send: "retry"` | стартовое состояние `clean`; защита включается по паре исходов |
| `outbound_type` | `nodes.outbound_type`; фильтр общий для секций `tls` и `quic` |

Память `clean → armed → decoy` на outbound заменена общим лейблом на тег релея и протокол. История —
[SPEC 060](../SPECS/TASKS/060-TLS_FRAGMENT_AUTO_ON_DETOUR/HISTORY.md).

### `lx.awg_masquerade` — удалён

Удалён в lx.33 (владелец 2026-11-07). Любое значение — ошибка загрузки:
`lx.awg_masquerade is removed: the AmneziaWG masquerade burst is sent on every path`. Маскировочная
пачка AmneziaWG (приманка `ip`/`id`/`ib`, `i1`…`i5`, junk `jc`) шлётся на любом пути, в том числе
через `detour`, как при дефолте `all` в lx.32. Ключ уберите из конфига. Случай релея со
сниффингом (issue #64) закрывает секция `quic` блока `lx.sniff_guard` (`decoy_first_byte`). История —
[SPEC 153](../SPECS/TASKS/153-AWG_MASQUERADE_OVER_DETOUR/SPEC.md).

## 14. Tailscale: выключить Taildrop

Ключ `disable_taildrop` на endpoint'е `tailscale`. Без ключа Taildrop работает как в апстриме.

```json
{ "type": "tailscale", "tag": "ts", "disable_taildrop": true }
```

С `true` узел не принимает файлы: отправитель получает ошибку 403 `Taildrop is disabled on this node`. Отправка с узла тоже отвергается, в статусе `canShareFiles = false`. Файлы, полученные раньше, остаются в `taildrop_directory`, их можно открыть и удалить. Другие устройства tailnet всё равно видят узел получателем: это задаёт админка Tailscale, а не узел.
