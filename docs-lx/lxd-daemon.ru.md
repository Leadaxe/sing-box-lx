## 1. lxd — ядро sing-box внутри демона с постоянным каналом управления

`sing-box lxd` — демон, который запускает ядро sing-box в своём процессе и держит
долгоживущий канал управления. Отличия от `sing-box run`:

- **Канал переживает reload.** У `run` смена конфига = рестарт процесса: клиент
  (лаунчер) теряет соединение, стримы статусов и наблюдаемости рвутся. У lxd
  слушающий порт принадлежит демону, а не box-инстансу. Apply подменяет ядро
  под живым сервером, и клиент видит переходы STARTED/STOPPING/… в одном стриме
  без переподключения.
- **Демон на связи, когда трафик не идёт.** Канал управления поднимается до
  ядра, поэтому битый или отсутствующий конфиг не отключает демон. Конфиг
  чинится по тому же каналу, пока data-plane лежит.
- **Конфиг с гарантиями.** `POST /admin/apply` проверяет кандидата
  (`sing-box check` собственным бинарником). Если старт провалился, демон
  откатывается на последний рабочий конфиг (**last-good**). Прерванный apply и
  run-намерение (`was_running`) демон помнит через рестарты и ребуты.
- **Удалённое управление по mTLS.** Демон — сам себе CA; клиенты регистрируются
  одноразовым инвайтом и дальше опознаются по сертификату.

Типовые роли: локальный движок для лаунчера на том же маке (канал переживает
reload'ы) и удалённый узел — например, ядро на роутере или сервере, которым
лаунчер управляет по сети.

Один порт несёт две плоскости:

| Плоскость | Протокол | Что даёт |
|---|---|---|
| наблюдаемость | gRPC `daemon.StartedService` | статусы, логи, группы/urltest, DNS-поток, соединения — общий протокол с Android-линейкой |
| администрирование | REST `/admin/*` | apply / rollback / start / stop / config / status / info, enrollment клиентов |

## 2. Быстрый старт (dev, без установки)

```bash
sing-box lxd --state-dir lxd-state -c config.json
```

Без `daemon.json` действуют dev-дефолты: plain h2c на `127.0.0.1:9091`, без
секрета, без mTLS и без реестра клиентов. Лог — на экран. `-c` — необязательный
seed: он используется, только пока нет last-good. Без него демон стартует пустым
(IDLE) и ждёт первый apply.

Проверка:

```bash
curl -s http://127.0.0.1:9091/admin/status
```

## 3. daemon.json — настройки демона

Файл лежит в `<state-dir>/daemon.json` (0600) и остаётся единственным источником
настроек канала: флагов `--listen/--tls/--secret` у команды нет. Без файла
действуют dev-дефолты. Неявно файл не создаётся: его пишет `--service=install`
на macOS и Windows или оператор в редакторе.

| Ключ | Дефолт | Значение |
|---|---|---|
| `listen` | `127.0.0.1:9091` | адрес канала (обе плоскости); строка `"host:port"` либо `{"address": [...], "port": N}` для нескольких адресов — [3.1](#31-listen-один-адрес-или-несколько) |
| `tls` | `false` | mTLS с регистрацией клиентов; `false` = plain h2c, только loopback/dev |
| `secret` | пусто | Bearer для операторских маршрутов; при `tls: false` — единственная защита (пусто = аутентификации нет) |
| `log_file` | `<родитель state-dir>/lxd.log` | абсолютный путь ротируемого лога вместо дефолтного: `/tmp/lxd.log` для tmpfs на роутере. На Windows install пишет `<ProgramData>\sing-box-lxd\logs\lxd.log`, если ключа нет. Фактический путь отдаёт `/admin/info` |
| `log_max_size_mb` | `1` | ротация лога: страховочный потолок размера |
| `log_max_backups` | `1` | сколько старых поколений (`lxd.log.1…N`) хранить |
| `log_max_age_hours` | `24` | ротация по возрасту файла |
| `commands` | нет | именованные root-команды, которые клиент запускает по имени через `/admin/commands`: `{"update": "/usr/bin/sing-box lxd update"}`. Имя — `[a-z0-9][a-z0-9_-]{0,31}`; с плохим именем или пустой командой демон не стартует; нет ключа — нет маршрутов. Команда исполняется от пользователя демона (root) без входа от клиента — [8.5](#85-обслуживание-из-лаунчера-именованные-команды) |
| `hooks` | нет | скрипты админа в `<state_dir>/hooks/`, которые демон вызывает при смене состояния ядра: `{"enabled": true, "timeout_seconds": 15, "unsafe_skip_owner_check": false}`. Нет ключа или `enabled: false` — хуков нет, но каталог и заготовки всё равно создаются. С отрицательным таймаутом демон не стартует. Подробно — [6a](#6a-хуки-демон-вызывает-скрипты-админа-при-смене-состояния-ядра) |

Дефолты ротации хранят ≈сутки истории. 0 или отсутствующий ключ — дефолт;
значения «без лимита» нет намеренно. Любая настройка меняется правкой файла и
рестартом службы, без переустановки.

### 3.1. listen: один адрес или несколько

У `listen` две формы с одним смыслом: адреса, на которых поднимается
управляющий канал. Обе плоскости (gRPC и admin REST) доступны на каждом адресе
одинаково.

```jsonc
"listen": "127.0.0.1:19091"                                  // один адрес
"listen": {"address": ["192.168.10.1", "127.0.0.1"], "port": 19091}  // несколько
```

Вторая форма нужна, когда демон должен быть доступен и с LAN-интерфейса, и с
loopback: одним биндом это не выразить. `0.0.0.0` не подходит: он открывает
наружу и все остальные интерфейсы хоста, включая те, на которых слушать не
планировали.

Правила для списка адресов:

- **Всё или ничего.** Если хоть один адрес не поднялся (опечатка или интерфейс
  ещё не сконфигурен), демон завершается с ошибкой и называет адрес. Так демон
  не поднимается наполовину: здоровый снаружи, но недоступный там, где нужен.
  Если адрес появляется поздно (мост или туннель настраивается после загрузки),
  запускайте службу после этого интерфейса.
- **Первый адрес — рекламируемый.** Инвайты регистрации, локальный клиент и
  сводка установки указывают на первую запись. Ставьте первым адрес, на который
  должны ходить лаунчеры.
- **Маски не поддерживаются.** `192.168.10.1/32` отвергается: ядро биндит один
  адрес, а не диапазон, и маска обещала бы в файле то, чего демон не делает.
  Ограничивать, кто может подключаться, — задача файрвола.
- **Строковая форма остаётся рабочей.** Существующие `daemon.json` со строкой
  править не нужно, и одиночный адрес записывается строкой.

## 4. Ключи командной строки

| Ключ | Значение |
|---|---|
| `--state-dir <dir>` | дом демона: daemon.json, last-good, run-state, реестр клиентов, ключи (дефолт `lxd-state`) |
| `-c <файл>` | seed-конфиг (строго один файл; каталоги `-C` не поддерживаются) |
| `--config-force <файл>` | всегда бутиться с этого файла, поверх last-good |
| `--run` | поднять ядро независимо от записанного run-состояния |
| `--service install\|install-user\|copy\|uninstall\|status` | установка службой, защищённая копия без службы, снятие, отчёт (см. разделы ОС, [7.1](#71-root-owned-копия-бинаря) и [7a](#7a-windows--автоматическая-установка)); на Windows `install`/`copy`/`uninstall` требуют повышенного токена, `install-user` — отказ |
| `--exec-dir <dir>` | с `install`/`copy`/`uninstall`/`status` — каталог защищённой копии и её сайдкара. macOS: `sing-box-lxd`, дефолт `/Library/PrivilegedHelperTools`, при отсутствии создаётся `root:wheel 0755`; заданный здесь создаётся вместе с недостающими родителями. Windows: `sing-box-lxd.exe` (с `libcronet.dll`, если она лежит рядом с источником), дефолт `<ProgramFiles>\sing-box-lxd`, создаётся, если его нет |
| `--allow-unsafe-exec` | только для отладки: служба (root-job launchd, служба SCM на Windows) стартует и с бинаря, который не защищённая копия (WARN вместо отказа) |
| `--purge` | с `uninstall` — снести и state-каталог (Windows: весь `<ProgramData>\sing-box-lxd`, state и логи) |
| `--keep-copy` | с `uninstall` — снять службу, защищённую копию оставить для запуска без службы ([7.1](#71-root-owned-копия-бинаря), [7a](#7a-windows--автоматическая-установка)) |
| `--dry-run` | с `--service` (кроме `status`) — показать, что было бы сделано, ничего не меняя |
| `--invite-out <файл>` | с `--service=install` (macOS, Windows) — записать инвайт сопряжения в этот новый файл вместо stdout; существующий файл — отказ всей команды, провал минта — выход 1 ([9](#9-сопряжение-клиента-одинаково-на-всех-ос)) |
| `--invite-name <имя>` | с `--service=install` — имя клиента, которого сопрягает инвайт (дефолт `singbox-launcher` при `--invite-out`, без него — без имени) |
| `client add [--name <метка>] [--invite-out <файл>]` | сминтить одноразовый инвайт для нового клиента; `--invite-out` пишет его в новый файл вместо печати |
| `client list` / `client remove <имя-или-отпечаток>` | просмотр / отзыв доверенных клиентов |
| `update [--dry-run] [--prerelease] [--no-restart] [--low-space] [--service <name>]` | самообновление из последнего релиза под платформу этого бинаря и рестарт службы через init (linux, root; [8.6](#86-обновление-sing-box-lxd-update)) |

Сабкоманда существует только в сборках с тегом `with_lxd`.

## 5. Клиент входит по сертификату, оператор — по секрету

- **Клиент (лаунчер)** входит доверенным сертификатом, полученным при
  enrollment. Сертификат даёт полный доступ к обеим плоскостям; Bearer клиенту
  не нужен, секрета он не знает.
- **Оператор (человек с шеллом на хосте)** входит Bearer-секретом из daemon.json
  на маршрутах только для loopback (`client add/list/remove`). Минт инвайта
  выдаёт доверие, поэтому из сети эти маршруты недоступны.
- **Enrollment** — единственный путь к доверию: одноразовый код
  (`адрес#отпечаток-сервера#код`) сгорает при первом использовании, клиент пинит
  сервер по отпечатку.
- **При `tls: false` (dev)** защищает только Bearer, а без секрета аутентификации
  нет. Поэтому plain-режим — только на loopback.

## 6. Логи

Под службой (stdout — не терминал) демон сам владеет файлом
`<support>/lxd.log`. Он перехватывает stdout/stderr процесса, поэтому в файл
попадает всё, включая лог ядра и паники. Ротация идёт по возрасту и размеру с
лимитами из daemon.json. При ручном запуске в терминале лог остаётся на экране,
файл не трогается. Путь к логу и state-dir клиент узнаёт из `GET /admin/info` и
ничего не хардкодит. Там же демон называет платформу и релизный ассет бинаря,
init-систему хоста и запущен ли он под ней службой. Поэтому клиенту не нужна
таблица uname → GOARCH и не нужно спрашивать пользователя про init.
Работает на macOS, Linux и Windows.

**Windows.** Лог службы — `<ProgramData>\sing-box-lxd\logs\lxd.log`: install пишет
этот `log_file` в daemon.json. Файл лежит рядом с `classic.log` лаунчера. Живой файл
на Windows нельзя переименовать (Go открывает файлы без `FILE_SHARE_DELETE`), а
писатель, который его держит, остался бы на старом файле. Поэтому демон держит один
дескриптор всю жизнь процесса. Стандартные дескрипторы вывода и ошибок процесса
указывают на него, паники рантайма тоже идут туда. Ротация копирует содержимое в
`lxd.log.1` и усекает `lxd.log`; строки, записанные между копированием и усечением,
теряются. Удалить файл, пока демон жив, нельзя.
`/admin/logs` читает `lxd.log` и `lxd.log.1`, как и на других платформах.

**Каналов лога два, и несут они разное.** gRPC-поток `SubscribeLog` несёт лог
ядра — то, что пишет работающий инстанс. Строки самого демона (`lxd: …`,
ошибки бутстрапа, паники) идут в stdout/stderr, то есть в `lxd.log`. Если ядро
не поднялось, стримить нечего, и причина лежит в файле. `GET /admin/logs?tail=N`
отдаёт хвост файла по сети, так что удалённому клиенту shell на хосте не нужен:

```bash
curl -s --cert client.pem --key client.key -k \
  "https://server:9091/admin/logs?tail=500"
```

## 6a. Хуки: демон вызывает скрипты админа при смене состояния ядра

Ядро на хосте с TUN меняет маршруты, но системный DNS не трогает: на macOS, на
Linux без `systemd-resolved` и на роутерах резолвер продолжает смотреть на
провайдера. Переключение DNS внутри ядра отвергнуто (issue #12): ядро не
знает всех сетевых служб и порядка их восстановления, а провальный откат
оставляет хост без DNS. Поэтому политика живёт у админа, в четырёх скриптах.
Демон только вызывает их в нужный момент и передаёт факты о ядре
([SPEC 135](../SPECS/TASKS/135-LXD_HOOKS/SPEC.ru.md)).

**Файлы.** На каждом старте демон создаёт `<state_dir>/hooks/` (root-owned,
`0755`) и кладёт заготовку для каждого отсутствующего скрипта:

| Файл | Кто пишет | Назначение |
|---|---|---|
| `hooks/pre_start`, `post_start`, `post_reload`, `post_stop` | вы | скрипты (исполняемые файлы, запускаются напрямую; ваш shell — в строке `#!`) |
| `hooks/core_snapshot.json` | демон | факты последнего живого ядра; есть при загрузке = предыдущий процесс не дошёл до `post_stop` |
| `hooks/.lock` | демон | `flock` вокруг каждого запуска, между процессами |
| `<каталог лога>/hooks/<event>.log` | скрипт (перенаправление) | вывод последнего запуска; без файла лога — `hooks/log/` |
| всё остальное в `hooks/` | вы | ваш снимок состояния системы, в вашем формате |

Заготовка, оставленная байт в байт как создана, или отсутствующий файл
означает «не настроено»: событие пропускается с Warn. Комментарий заготовки
перечисляет переменные своего события, так что документация лежит там, где вы
пишете скрипт.

**daemon.json:**

```jsonc
"hooks": {
  "enabled": true,                 // по умолчанию false: нет ключа = нет хуков (заготовки всё равно создаются)
  "timeout_seconds": 15,           // на хук; 0/нет = 15; отрицательное — демон не стартует
  "unsafe_skip_owner_check": false // true = гейт владельца выключен; WARN на каждом старте
}
```

**События.** «Текущее» ядро — то, что есть после события, `_PREV` — то, чего
больше нет.

| Событие | Когда | `LXD_REASON` | Если скрипт провалился (ненулевой код, таймаут, гейт) |
|---|---|---|---|
| `pre_start` | до старта ядра | `boot` (загрузка демона), `start` (`POST /admin/start`), `apply` / `sighup` (apply, поднимающий ядро из ничего) | fail-closed: ядро не стартует, `status: fatal`, `last_error` называет хук |
| `post_start` | после подъёма ядра — tun и маршруты есть | `boot`, `start`, `apply` / `sighup` (тот же случай) | ядро работает; Error в логе, лейбл в `/admin/status` |
| `post_reload` | после подмены инстанса в живом процессе | `apply`, `sighup`, `rollback` (новый конфиг не поднялся, last-good поднят; также `POST /admin/rollback` при живом ядре) | ядро работает; Error, лейбл в статусе |
| `post_stop` | когда ядра нет | `stop`, `shutdown` (SIGTERM, `update`, рестарт службы), `fatal` (старт провалился после пройденного `pre_start`, или откат тоже провалился), `recover` (см. ниже) | только лог; остановку ничто не блокирует |

Каждый старт заканчивается либо `post_start`, либо `post_stop(fatal)`. Откат
внутри apply — это `post_reload(rollback)`, и в `LXD_ERROR` лежит причина, по
которой отвергнут новый конфиг. `pre_stop` и `pre_reload` нет: паника процесса
демона уносит ядро с собой, и на событие «до» положиться нельзя. Отсюда
контракт для `post_*`: скрипты идемпотентны и восстанавливают состояние.
Читайте свой снимок в `$LXD_HOOK_DIR`, действуйте по нему и не считайте, что
перед этим `post_stop` был `post_start`. `pre_start` — проверка предусловий
(аплинк есть, диск не полон) без побочных эффектов.

**`recover`.** После каждого успешного старта демон пишет
`hooks/core_snapshot.json`, после `post_stop` удаляет его. Если демон находит
файл при загрузке, предыдущий процесс умер без `post_stop` (паника ядра,
`kill -9`, потеря питания). Тогда демон до своего `pre_start` вызывает
`post_stop` с `LXD_REASON=recover` и `_PREV` из файла. Для скрипта это обычная
остановка. Только так покрывается паника ядра: ядро живёт в процессе демона,
дочернего надзора нет.

**Окружение.** Переменные заполняет демон, вход клиента в них не попадает;
пусто — неизвестно или неприменимо. Общие переменные: `LXD_EVENT`,
`LXD_REASON`, `LXD_PLATFORM`, `LXD_VERSION`, `LXD_INIT_SYSTEM`,
`LXD_STATE_DIR`, `LXD_BIN`, `LXD_HOOK_DIR`, а также:

- `LXD_CLIENT` — имя клиента, если переход вызван REST-запросом: по
  сертификату или `operator` через Bearer. Пусто для `boot`, `sighup`,
  `shutdown`, `fatal`, `recover`;
- `PATH` — как у `commands`;
- `LXD_LOG_FILE` — пусто при запуске в терминале;
- `LXD_HOOK_TIMEOUT` — таймаут в секундах.

Факты о ядре: текущие — без суффикса, прежние — с `_PREV`:

| Переменная | Значение |
|---|---|
| `LXD_CONFIG_SHA` / `_PREV` | sha256 конфига, как в `/admin/status` |
| `LXD_TUN_ADDRESS` / `_PREV` | адреса всех tun-inbound через запятую, v4 и v6 вместе, в порядке конфига |
| `LXD_TUN_INTERFACE` / `_PREV` | фактические имена интерфейсов (`utunN`, `tunN`), тот же порядок; в `pre_start` и в `post_stop(fatal)` — только явный `interface_name`, иначе пусто |
| `LXD_TUN_MTU` / `_PREV` | mtu на каждый tun-inbound (9000, если не задан) |
| `LXD_TUN_AUTO_ROUTE` / `_PREV` | `1`/`0` на каждый tun-inbound — при `0` направлять системный DNS на tun бессмысленно |
| `LXD_ERROR` | ошибка ядра при `rollback` и `fatal` |

У `pre_start` только текущие факты, у `post_stop` только `_PREV`, у
`post_reload` оба; нет tun-inbound — все `LXD_TUN_*` пусты.

**Исполнение.** Хук исполняется синхронно, в процессе демона. Файл запускается
напрямую (без shell), cwd `/`, stdin `/dev/null`, stdout и stderr перенаправлены
в `<event>.log`, который перезаписывается на каждом запуске. Хук работает в
собственной группе процессов; по таймауту вся группа получает `SIGKILL`.
Фоновый потомок (`nohup … &`) демон не ждёт, но потомок без `setsid` умирает
вместе с демоном под SIGTERM службы. Поэтому всё, от чего зависит DNS, должно
завершиться до `exit`.

Перед каждым запуском демон проверяет путь: каждый компонент от `/` до скрипта
принадлежит root, без записи для group/other и не симлинк, а файл — обычный и
исполняемый. Нарушение — провал хука. Переход ждёт хук, поэтому
`POST /admin/apply` может занять до `timeout_seconds` дольше. Между процессами
запуски сериализованы `flock` на `hooks/.lock`. При `update` procd стартует
новый демон раньше, чем старый закончил; без замка новый `post_start` снял бы
снимок системного DNS, в котором ещё стоит DNS VPN.

**Бюджет остановки.** Под SIGTERM `post_stop` выполняется до закрытия плоскостей
управления. Окно задаёт init-система: procd убивает по `term_timeout` (по
умолчанию 5 с, инсталлятор OpenWrt ставит 30), launchd — по `ExitTimeOut`
(20 с). `SIGKILL` посреди `post_stop` оставляет DNS на мёртвом tun, поэтому
держите скрипт внутри этого окна.

**Windows:** ключ `hooks` принимается с Warn и игнорируется (только unix).

**Пример для macOS.** `post_start` направляет DNS службы Wi-Fi на tun,
`post_stop` возвращает DNS из снимка:

```sh
#!/bin/sh
# post_start
set -e
SERVICE="Wi-Fi"
case "$LXD_TUN_AUTO_ROUTE" in 1*) ;; *) exit 0 ;; esac
[ -f "$LXD_HOOK_DIR/dns.snapshot" ] || networksetup -getdnsservers "$SERVICE" > "$LXD_HOOK_DIR/dns.snapshot"
DNS=$(printf '%s' "$LXD_TUN_ADDRESS" | cut -d, -f1 | cut -d/ -f1)
networksetup -setdnsservers "$SERVICE" "$DNS"
```

```sh
#!/bin/sh
# post_stop — идемпотентен: без снимка восстанавливать нечего
SERVICE="Wi-Fi"
[ -f "$LXD_HOOK_DIR/dns.snapshot" ] || exit 0
if grep -q "aren't any" "$LXD_HOOK_DIR/dns.snapshot"; then
  networksetup -setdnsservers "$SERVICE" empty
else
  networksetup -setdnsservers "$SERVICE" $(cat "$LXD_HOOK_DIR/dns.snapshot")
fi
rm -f "$LXD_HOOK_DIR/dns.snapshot"
```

**Пример для Linux с `systemd-resolved`.** DNS ставится на интерфейс, и
восстанавливать нечего: настройка умирает вместе с интерфейсом:

```sh
#!/bin/sh
# post_start
IFACE=$(printf '%s' "$LXD_TUN_INTERFACE" | cut -d, -f1)
DNS=$(printf '%s' "$LXD_TUN_ADDRESS" | cut -d, -f1 | cut -d/ -f1)
[ -n "$IFACE" ] && resolvectl dns "$IFACE" "$DNS" && resolvectl domain "$IFACE" '~.'
```

`GET /admin/status` отдаёт объект `hooks` с последним исходом каждого события
(`ok` / `failed` / `timeout` / `skipped` / `never`, `reason`, `exit_code`,
`finished_at`, `detail`), чтобы клиент мог показать лейбл рядом с состоянием
ядра.

## 7. macOS — автоматическая установка

Полный `--service` есть на macOS и Windows ([7a](#7a-windows--автоматическая-установка));
этот раздел — про macOS. Областей установки две:

```bash
sudo sing-box lxd --service=install    # системный LaunchDaemon: root, старт до логина, TUN
sing-box lxd --service=install-user    # LaunchAgent: без sudo, старт при логине, десктоп-UX
```

`install-user` работает от имени залогиненного пользователя и поэтому не может
владеть TUN. Создание интерфейса на macOS требует root, так что конфиг с
inbound'ом `tun` под пользовательской областью упадёт с ошибкой прав. Настройка
`tls` в daemon.json на это не влияет; для TUN ставится системная область
(`sudo … --service=install`).

Install делает всё сам, в пять шагов:

1. системная область: копирует бинарь в
   `/Library/PrivilegedHelperTools/sing-box-lxd` с владельцем root,
   и служба исполняет эту копию, а не файл, из которого её поставили
   ([7.1](#71-root-owned-копия-бинаря));
2. создаёт `…/Application Support/sing-box-lxd/` (0700; системная область — `root:wheel`)
   и `state/` внутри;
3. записывает daemon.json: существующий адрес сохраняется, чтобы реинсталл не
   сдвинул канал из-под сопряжённых клиентов; иначе берётся первый свободный
   loopback-порт от 19091. `tls` включается всегда; секрет сохраняется или
   генерируется;
4. пишет plist (`com.leadaxe.sing-box-lxd`) и бутстрапит службу. После bootout
   ждёт, пока старый job исчезнет (до 10 с, `waiting for the old service to
   unload (Ns)`), и повторяет bootstrap, который ответил «already in progress»:
   живое ядро выходит несколько секунд. plist сводится к
   `sing-box lxd --state-dir <dir>`, все настройки — в daemon.json;
5. печатает отчёт status ([7.1](#71-root-owned-копия-бинаря)) и сводку: адрес
   канала, админ-секрет, путь daemon.json, команду рестарта и одноразовый инвайт
   для сопряжения лаунчера. С `--invite-out` инвайт уходит в файл
   ([9](#9-сопряжение-клиента-одинаково-на-всех-ос)).

Пути: system — `/Library/Application Support/sing-box-lxd/`, user —
`~/Library/Application Support/sing-box-lxd/`. Лог — `lxd.log` рядом со `state/`.

Остальные действия:

```bash
sing-box lxd --service=install --dry-run  # показать план копии, plist и что произойдёт, ничего не трогая
sing-box lxd --service=status             # что установлено; выход 0/2/3/4 (см. 7.1), root не нужен
sudo sing-box lxd --service=copy          # только root-owned копия, без службы (7.1)
sing-box lxd --service=uninstall          # снять службу; state сохраняется
sing-box lxd --service=uninstall --purge  # снять службу и снести state (клиенты, ключи, last-good)
sing-box lxd --service=uninstall --dry-run --purge   # показать, что было бы удалено
sudo sing-box lxd client add --name mac-book   # новый инвайт на живом демоне (state-dir найдётся сам)
```

### 7.1. Root-owned копия бинаря

LaunchDaemon исполняется от root при каждой загрузке и каждом KeepAlive-рестарте.
Бинарь в бандле лаунчера может заменить залогиненный пользователь. Если бы plist
указывал на этот файл, любой процесс пользователя получил бы исполнение кода от
root. Поэтому системная служба никогда не исполняет файл, из которого её
поставили; `--service=install` сначала копирует его:

| Что | Путь | Владелец / режим |
|---|---|---|
| бинарь | `/Library/PrivilegedHelperTools/sing-box-lxd` | `root:wheel 0755` |
| сайдкар | `/Library/PrivilegedHelperTools/sing-box-lxd.install.json` | `root:wheel 0644` |

Соглашение Apple для привилегированных помощников: плоский файл, без своего каталога.
Имя — `sing-box-lxd`, а не лейбл службы: macOS усекает имя процесса до 16 символов.
`sing-box-lxd` влезает целиком и содержит `sing-box`, так что `pgrep sing-box`, `pkill` и
`ps -c` находят демон без `-f`. Лейбл службы, plist и `XPC_SERVICE_NAME` остаются
`com.leadaxe.sing-box-lxd`.

На чистой macOS каталога `/Library/PrivilegedHelperTools` нет, пока SMJobBless не
поставит первый привилегированный помощник. Тогда `install` и `copy` создают его
`root:wheel 0755`, как `sudo mkdir -m 0755` (`lxd: created … (root:wheel 0755)`;
`--dry-run` пишет `would create`). Создаётся только этот последний компонент:
`/Library` должен существовать и проходить инвариант. Существующий каталог
проверяется и не «чинится», а `status` и `uninstall` каталог не создают.

- **Инвариант.** Каждый компонент пути от `/` до бинаря — настоящий каталог или файл
  (не симлинк), принадлежит uid 0 и не имеет записи для group и other. Сам
  `/Applications` — `root:admin 0775`, поэтому бинарь из бандла инвариант не проходит.
- **Как встаёт копия.** Временный файл с уникальным именем в том же каталоге, fsync,
  `chown root:wheel`, `chmod 0755`, сверка sha256 с источником, затем `rename` поверх
  старой копии. Копия никогда не переписывается на месте: работающий демон держит
  старый файл, а macOS убивает процесс, у которого меняются подписанные страницы.
  xattr и переподписи нет. Одинаковая копия не трогается:
  `lxd: binary unchanged (sha256 …), copy skipped`.
- **В plist** меняется только `ProgramArguments[0]`; daemon.json, адрес, секрет и
  сопряжённые клиенты остаются как были.
- **Сайдкар** `sing-box-lxd.install.json` читается без root:
  ```json
  {
    "source": "/Applications/singbox-launcher.app/Contents/MacOS/bin/sing-box",
    "sha256": "…",
    "version": "1.14.1-lx.11",
    "installed_at": "2026-09-24T12:00:00Z",
    "plist_path": "/Library/LaunchDaemons/com.leadaxe.sing-box-lxd.plist",
    "label": "com.leadaxe.sing-box-lxd"
  }
  ```
  `version` — версия ядра копии, видна без её запуска; `plist_path` пуст у копии без
  службы.
- **`--exec-dir <dir>`** кладёт оба файла с теми же именами в другой каталог; если его
  нет, он создаётся `root:wheel 0755`. Тот же инвариант распространяется на каждый
  компонент `<dir>` и на сам файл; иначе install отказывает:
  `<путь>: owned by uid N, mode NNNN, must be root-owned and not group/world-writable`.
- **Каталог на месте файла** останавливает install и copy:
  `target is a directory (legacy layout); remove it: sudo rm -rf <путь>`. Ни одна
  команда его не удаляет: status показывает его (выход 2), uninstall оставляет с той же
  подсказкой.
- **Файлы прежних сборок ядро не трогает.** `v1.14.1-lx.11` называл копию лейблом
  (`/Library/PrivilegedHelperTools/com.leadaxe.sing-box-lxd` и её `.install.json`), ранние
  пре-релизы оставляли каталог с тем же именем. Текущее ядро их не читает, не переписывает
  и не удаляет; plist, исполняющий такой файл, виден как `MISMATCH` (выход 2), пока
  `sudo sing-box lxd --service=install` не переведёт службу на `sing-box-lxd`. Остатки
  удалить руками: `sudo rm -rf /Library/PrivilegedHelperTools/com.leadaxe.sing-box-lxd*`.

**Копия без службы.** `sudo sing-box lxd --service=copy` кладёт ту же копию и сайдкар,
без plist и launchd. Она нужна лаунчеру, который сам запускает ядро от root
(classic TUN). Повтор с тем же бинарём ничего не меняет (`lxd: already up to date <sha256>`);
последующий `--service=install` привязывает эту копию к plist без повторного копирования.
Чтобы обновить ядро, снова запустите `--service=copy` (и `--service=install`, если служба
есть) из нового бинаря: ядро само обновлений не отслеживает.

**Status** не требует root и ничего не меняет:

```bash
sing-box lxd --service=status; echo "exit $?"
```

Для LaunchDaemon (а без него — для копии) и для user-агента status печатает plist,
программу, которую он исполняет, владельца и режим, проходит ли инвариант, sha256 программы против
sha256 этого бинаря, сайдкар и состояние и pid из `launchctl print`. Последняя строка —
вердикт:

| Вердикт | Значение | Выход |
|---|---|---|
| `OK` | служба исполняет root-owned копию этого же бинаря | 0 |
| `MISMATCH` | нужна переустановка: другой бинарь, сайдкара нет или он чужой, копию поменяли в обход сайдкара, сайдкар без копии | 2 |
| `UNSAFE` | программа или каталог над ней не проходит инвариант | 2 |
| `NOT INSTALLED` | нет ни plist, ни копии | 3 |
| `COPY ONLY` | исправная копия этого бинаря, службы нет | 4 |
| `NOT RUNNING` | на диске всё исправно, но у launchd нет работающего job'а с этим лейблом (bootstrap упал или был только bootout); в причине — команда `launchctl bootstrap` | 5 |

**Uninstall** удаляет копию и сайдкар при двух условиях: сайдкар относится к этой службе
(или ни к какому plist), и sha256 файла равен записанному. Иначе файл остаётся, а
причина печатается (`lxd: copy left in place: …`). Произвольный `ProgramArguments[0]`
uninstall не удаляет никогда.

`sudo sing-box lxd --service=uninstall --keep-copy` снимает plist и job launchd, но оставляет
копию и сайдкар и очищает в нём `plist_path`. Получается состояние «только копия» (status
`COPY ONLY`, выход 4):
`lxd: copy kept for non-service use: <путь>; remove with --service=uninstall without --keep-copy`.
`--purge` и здесь касается только state. Если службы нет и копия уже отвязана, команда
ничего не меняет, печатает ту же строку и выходит с 0.

**Самопроверка при старте.** Ядро, запущенное от root (`lxd` или `run`), проверяет
собственный бинарь инвариантом. Проверка есть только на macOS и Windows, где службу
ставит само ядро; на Linux и других ОС самопроверки нет и в лог ничего не пишется. Job
launchd (родитель — pid 1, `XPC_SERVICE_NAME=com.leadaxe.sing-box-lxd`) отказывается
стартовать с бинаря, который не проходит инвариант, и пишет причину в `lxd.log`:

```
lxd: refusing to run as a root service from /Applications/…/sing-box (uid 501, mode 0755): /Applications: owned by uid 0, mode 0775, must be root-owned and not group/world-writable; run `sing-box lxd --service=install` to reinstall from a root-owned copy
```

Любой другой запуск от root только пишет WARN с тем же путём, владельцем и режимом:
sudo из терминала, nohup, лаунчер, который поднимает ядро с правами.
`lxd --allow-unsafe-exec` превращает отказ в WARN для отладки. Пройденная проверка в
job'е launchd пишет одну строку INFO:
`lxd: self-check ok: root-owned /Library/PrivilegedHelperTools/sing-box-lxd, launchd service com.leadaxe.sing-box-lxd`.

> ⚠️ Системная установка, сделанная старым ядром, перестаёт стартовать после
> обновления бинаря. Её plist исполняет бинарь из бандла. Как только этот бинарь
> обновится до этой версии, ближайший рестарт службы откажет в старте из-за
> самопроверки. Переустановите службу один раз: `sudo sing-box lxd --service=install`;
> daemon.json, клиенты и ключи сохраняются.

**Ручная проверка:**

```bash
ls -ld / /Library /Library/PrivilegedHelperTools
ls -l /Library/PrivilegedHelperTools/sing-box-lxd*                         # root wheel -rwxr-xr-x бинарь, -rw-r--r-- .install.json
plutil -p /Library/LaunchDaemons/com.leadaxe.sing-box-lxd.plist            # ProgramArguments[0] = копия
shasum -a 256 /Library/PrivilegedHelperTools/sing-box-lxd
cat /Library/PrivilegedHelperTools/sing-box-lxd.install.json               # тот же sha256
pgrep -l sing-box                                                          # демон виден как sing-box-lxd
launchctl print system/com.leadaxe.sing-box-lxd | grep -E '^[[:space:]](state|pid|program) ='
sing-box lxd --service=status
```

## 7a. Windows — автоматическая установка

На Windows `--service` ставит службу диспетчера служб (SCM) с именем `sing-box-lxd`:
учётная запись `LocalSystem`, автозапуск при загрузке (до входа пользователя), зависимость
от `Tcpip`. Модель та же, что на macOS ([7.1](#71-root-owned-копия-бинаря)): служба никогда
не исполняет файл, из которого её поставили, — только защищённую копию.

```powershell
# PowerShell «Запуск от имени администратора» для всего, кроме status и --dry-run
sing-box lxd --service=install                  # служба, защищённая копия, daemon.json, инвайт
sing-box lxd --service=install --dry-run        # план: каталог данных, копия, BinaryPathName; ничего не трогает
sing-box lxd --service=status                   # без повышения; выход 0/2/3/4/5, 1 при ошибке (см. ниже)
sing-box lxd --service=copy                     # только защищённая копия, SCM не трогается (7a.1)
sing-box lxd --service=uninstall                # снять службу и её копию; state и логи сохраняются
sing-box lxd --service=uninstall --keep-copy    # снять службу, копию оставить (status COPY ONLY)
sing-box lxd --service=uninstall --purge        # снести и <ProgramData>\sing-box-lxd (state и логи)
sing-box lxd --service=install --invite-out C:\Users\me\invite.txt   # инвайт в новый файл (9)
sing-box lxd client add --name office-pc        # новый инвайт на живом демоне (state-dir найдётся сам)
```

`install`, `copy` и `uninstall` требуют повышенного токена; без него отказывают до любых
изменений (`--service=install needs an elevated token (run as administrator)`). `status` и
`--dry-run` работают из обычной консоли. `--service=install-user` здесь нет:
`--service=install-user is not supported on Windows; use --service=install`. `--exec-dir <dir>`
переносит копию в другой каталог, как на macOS; `status` и `uninstall` такой установки
нужно запускать с тем же флагом.

Пути (корни берутся из известных папок `ProgramFiles` и `ProgramData`; `C:\` — только
обычное значение):

| Что | Путь | Владелец / DACL |
|---|---|---|
| каталог копии | `<ProgramFiles>\sing-box-lxd\` | Administrators; `D:P(A;OICI;FA;;;SY)(A;OICI;FA;;;BA)(A;OICI;FRFX;;;AU)` |
| бинарь | `…\sing-box-lxd\sing-box-lxd.exe` | Administrators; `D:P(A;;FA;;;SY)(A;;FA;;;BA)(A;;FRFX;;;AU)` |
| библиотека | `…\sing-box-lxd\libcronet.dll` — только если лежит рядом с исходным бинарём | как у бинаря |
| сайдкар | `…\sing-box-lxd\sing-box-lxd.install.json` | как у бинаря |
| каталог данных | `<ProgramData>\sing-box-lxd\` | Administrators; `D:P(A;OICI;FA;;;SY)(A;OICI;FA;;;BA)` |
| state | `<ProgramData>\sing-box-lxd\state\` — daemon.json, TLS-пара, клиенты, `resources`, `tailscale` | SYSTEM или Administrators, доступ только SYSTEM и Administrators |
| логи | `<ProgramData>\sing-box-lxd\logs\` — `lxd.log`, `lxd.log.1`; туда же лаунчер пишет свой `classic.log` | как у state |

Authenticated Users могут читать и исполнять копию, но не писать в неё: лаунчер без
прав считает её хеш и читает сайдкар. Каталог данных закрыт для всех, кроме SYSTEM и
Administrators. `wintun.dll` в копию не входит: `sing-tun` встраивает его и загружает из
памяти.

Что делает `--service=install`, по шагам:

1. Проверяет токен; с `--invite-out` существующий файл отменяет всю команду до любых
   изменений.
2. **Забирает каталог данных** до любой записи в него. daemon.json несёт секрет, а файл,
   созданный под чужим владельцем, унаследовал бы чужой DACL. Install включает
   `SeTakeOwnershipPrivilege` и `SeRestorePrivilege` и обходит `<ProgramData>\sing-box-lxd`
   сверху вниз; каждое звено открывается через дескриптор без следования ссылкам. Корень
   получает владельца Administrators и защищённый DACL из таблицы. Узел ниже, выбившийся из
   нормы, получает владельца Administrators и собственный явный защищённый DACL: каталоги —
   наследуемый, файлы — `D:P(A;;FA;;;SY)(A;;FA;;;BA)`. Файлы, созданные демоном под SYSTEM
   с унаследованными записями, в норме и остаются как есть. На каждое изменённое звено
   пишется строка `lxd: took ownership of <путь> (was <имя> (<SID>))` или
   `lxd: replaced DACL on <путь>`, либо одна строка на весь каталог —
   `lxd: data dir <путь> is protected`. `state\` и `logs\` создаются, если их нет. `classic.log` лаунчера получает тот же DACL; своё чтение лаунчер восстанавливает
   на ближайшем повышенном старте. Reparse point или файл с несколькими жёсткими ссылками
   внутри — отказ (`<путь> is a reparse point; remove it: Remove-Item <путь>`): смена ACL
   через ссылку поменяла бы чужой объект. Сам install такое не удаляет.
3. **daemon.json** — как на macOS: существующий адрес сохраняется, иначе первый свободный
   loopback-порт от 19091; `tls: true`; секрет сохраняется или генерируется. Если в файле нет
   `log_file`, install пишет `<ProgramData>\sing-box-lxd\logs\lxd.log`.
4. Работающая служба останавливается с ожиданием `STOPPED` до 30 с
   (`lxd: stopping service sing-box-lxd (Ns)`); не остановилась — install падает, ничего не
   изменено.
5. Набор файлов и сайдкар встают в каталог копии ([7a.1](#7a1-защищённая-копия-набора)).
6. Служба создаётся или обновляется: `BinaryPathName` — путь копии в кавычках плюс
   `lxd --state-dir <abs>` (и `-c`/`--config-force`/`--run`, если заданы, как на macOS);
   `LocalSystem`, автозапуск, зависимость `Tcpip`; восстановление — три рестарта через 5 с,
   сброс счётчика через 86400 с; восстановление срабатывает и когда служба останавливается
   с ненулевым кодом.
   DACL службы — `D:P(A;;GA;;;SY)(A;;GA;;;BA)(A;;0x2008d;;;AU)`: Authenticated Users могут
   читать конфигурацию и состояние, но не запускать, не останавливать, не перенастраивать и
   не забирать службу.
7. Запуск с ожиданием `RUNNING` до 30 с. Служба, остановившаяся при запуске, — ошибка с её
   кодами выхода; причина — в `lxd.log`.
8. Отчёт status; вердикт не `OK` — install завершается ошибкой (выход 1).
9. Сводка: адрес канала, админ-секрет, путь daemon.json,
   `restart command: Restart-Service sing-box-lxd (PowerShell as administrator)` и
   одноразовый инвайт — в stdout или в файл `--invite-out`.

Если после остановки на шаге 4 не удались копия или конфигурация службы, install
возвращает прежний образ, запускает службу на нём и только потом отдаёт ошибку
(`lxd: install failed, previous service image restarted`): неудачное обновление не оставляет
хост без VPN. Повторный install с тем же бинарём файлы не трогает
(`lxd: binary set unchanged (…), copy skipped`), daemon.json, секрет и клиентов сохраняет и
перезапускает службу, и VPN ненадолго прерывается.

Службу перезапускает `Restart-Service`, а не `sc.exe stop` + `sc.exe start`: `sc.exe stop`
не ждёт остановки, и `start` падает с ошибкой 1056, пока служба в `STOP_PENDING`. Install
сразу после uninstall при открытой оснастке «Службы» (`services.msc`) может получить
`ERROR_SERVICE_MARKED_FOR_DELETE` (1072). Закройте оснастку или перезагрузитесь и повторите
install.

Install мог забрать владение у учётной записи вне SYSTEM, Administrators и TrustedInstaller,
или такая запись могла читать `state\`. Если daemon.json при этом уже был, секрет и
серверная пара не перегенерируются: лаунчер хранит секрет, а новая пара рассопрягла бы всех
клиентов. Вместо этого install печатает `WARN: <путь> was readable by <имя> (<SID>) before this install; rotate the admin
secret in daemon.json and re-pair clients if the host is shared` и кладёт тот же текст в
сайдкар (`warnings`): у лаунчера, запускающего install через `runas`, консоли нет.

**Status** не требует повышения и ничего не меняет. Он открывает SCM с `SC_MANAGER_CONNECT`,
а службу — только с правами запроса, и печатает три блока:

- `[service]` — имя, `BinaryPathName` и его argv[0], тип старта, учётная запись, состояние,
  pid, защищён ли DACL службы;
- `[copy]` — каталог, инвариант цепочки, владелец и sha256 каждого файла против набора
  вызывающего, лишние файлы, остатки, сайдкар с предупреждениями;
- `[data dir]` — владелец и защищён ли DACL. Без прав администратора блок обычно не
  читается, это норма: он только для сведения.

Последняя строка — вердикт:

| Вердикт | Значение | Выход |
|---|---|---|
| `OK` | служба исполняет каноническую копию, DACL службы и инвариант в порядке, сайдкар привязан к `sing-box-lxd`, файлы = сайдкар = набор вызывающего бинаря, лишних файлов нет, состояние `RUNNING` | 0 |
| `MISMATCH` | инвариант соблюдён, но: набор отличается от набора вызывающего (в том числе `libcronet.dll` есть только с одной стороны); сайдкара нет или он чужой; файл не совпадает с сайдкаром; сайдкар называет отсутствующий файл; сайдкар привязан к несуществующей службе; лишний файл в каталоге копии | 2 |
| `UNSAFE` | конфигурация службы не читается (в том числе отказ в доступе); `BinaryPathName` не разбирается; argv[0] — не каноническая копия; путь с пробелом без кавычек; DACL службы даёт чужой учётной записи `SERVICE_CHANGE_CONFIG`, `WRITE_DAC`, `WRITE_OWNER`, `DELETE`, `GENERIC_WRITE` или `GENERIC_ALL`; цепочка или набор нарушают инвариант | 2 |
| `NOT INSTALLED` | нет ни службы, ни копии, ни сайдкара | 3 |
| `COPY ONLY` | службы нет; копия проходит инвариант, её сайдкар с `service: ""`, файлы = сайдкар = набор вызывающего | 4 |
| `NOT RUNNING` | всё как у `OK`, но состояние не `RUNNING` (включая `START_PENDING`); в причине — `sc.exe start sing-box-lxd` (от администратора) или `--service=install` | 5 |
| ошибка | SCM не открылся, вызывающий бинарь не читается | 1 |

В отличие от macOS, служба, чей argv[0] — не каноническая копия, получает `UNSAFE`, а не
`MISMATCH`. Набор вызывающего — его `.exe` и `libcronet.dll` рядом, если есть; пути
сравниваются без учёта регистра.

**Uninstall** останавливает и удаляет службу (`lxd: uninstalled service sing-box-lxd`), затем
смотрит в два места: каталог argv[0] службы (если файл называется `sing-box-lxd.exe`) и
каталог копии. Набор там удаляется, только если сайдкар есть, его `service` — `sing-box-lxd`
или пусто, и sha256 каждого файла равен сайдкару; одно расхождение — не удаляется ничего, с
причиной (`lxd: copy left in place: …`). Остатки уходят вместе с набором; дефолтный
`<ProgramFiles>\sing-box-lxd` удаляется, если опустел, каталог из `--exec-dir` остаётся.
`--keep-copy` снимает только службу и переписывает сайдкар с `service: ""`
(`lxd: copy kept for non-service use: <путь>; remove with --service=uninstall without --keep-copy`).
`--purge` удаляет и весь `<ProgramData>\sing-box-lxd`, включая `classic.log` лаунчера.
`--dry-run` печатает те же решения со словом `would`.

**Логи.** Демон пишет `logs\lxd.log` и ротирует его копированием, как описано в
разделе [6](#6-логи). События
самой службы (старт, остановка, код выхода) — в системном журнале событий, их пишет SCM;
демон Event Log не использует. Ошибка до открытия лога (не читается daemon.json) видна там
только как код выхода 1.

**Под SCM** демон сообщает `START_PENDING`, читает daemon.json, забирает лог, выполняет
самопроверку и переходит рабочим каталогом в state-каталог: относительные пути конфига вроде
`cache.db` разрешаются там, а не в `System32`. Затем он сразу сообщает `RUNNING`: управляющий
канал и так поднимается первым, а бутстрап ядра может идти дольше таймаута старта SCM. Остановка
или выключение отменяют демон и ждут его 10 с; дальше процесс пишет строку в лог и выходит
с кодом 1. Канал — тот же TCP loopback + mTLS, что и на других платформах; named pipe нет.

Служба запускает демон на контексте ядра, как и консольный запуск; паника в обработчике
admin REST или gRPC пишется в `lxd.log` со стеком. Нужна версия `v1.14.2-lx.2` или новее: в
пререлизах `v1.14.2-lx.2-rc.1`/`rc.2` первый `/admin/apply` под SCM падал в панику, клиент
видел EOF.

Сборки для Windows 7 (`windows-386-legacy-windows-7`) идут без `with_lxd`: там нет ни `lxd`,
ни службы.

### 7a.1. Защищённая копия набора

- **Инвариант.** Каждый компонент от корня тома до родителя каталога копии принадлежит
  SYSTEM, Administrators или TrustedInstaller, и никакая другая учётная запись не имеет на
  нём `DELETE`, `WRITE_DAC`, `WRITE_OWNER`, `GENERIC_WRITE`, `GENERIC_ALL` или
  `FILE_DELETE_CHILD`. Создавать папки в `C:\` при этом можно: подменить наш путь это не
  даёт. Каталог копии и каждый файл набора принадлежат SYSTEM или Administrators, и никакая
  другая учётная запись не имеет на них прав записи. Каждый компонент открывается без следования ссылкам, владелец и DACL читаются с
  этого дескриптора; reparse point в любом звене, NULL DACL или разрешающая запись
  неизвестного типа (object, callback) — нарушение. Том — фиксированный диск NTFS. Сообщения
  называют путь и учётную запись: `<путь>: owner <имя> (<SID>) is not SYSTEM, Administrators
  or TrustedInstaller` (для самой копии — `is not SYSTEM or Administrators`),
  `<путь>: <имя> (<SID>) is granted <права>, must not be writable by a non-administrative
  principal`, `<путь>: is a reparse point, must be a real file or directory`,
  `<путь>: not on a fixed NTFS volume`.
- **Набор.** `os.Executable()` с разрешёнными ссылками (обычный файл, не больше 512 МиБ)
  плюс `libcronet.dll` из того же каталога, если он есть. Копия всегда называется
  `sing-box-lxd.exe`.
- **Как встаёт набор.** Сначала проверяются предки (нарушение — отказ до любых изменений);
  каталог копии создаётся со своим DACL или приводится к нему. Остатки прошлого прогона
  (`<член набора>.old`, `.<член набора>.tmp-<hex>`) удаляются; занятый остаток ждёт
  следующего install (`lxd: <путь> is still in use, left for the next install`). Файл,
  названный в прошлом сайдкаре и выпавший из набора (`libcronet.dll` прежней сборки),
  удаляется; незнакомый файл — отказ:
  `<путь>: unknown file in the copy directory; remove it: Remove-Item <путь>`. Каждый
  изменившийся член набора идёт через временный файл в том же каталоге: запись, сброс на
  диск, DACL, сверка sha256 с источником; затем старый файл переименовывается в
  `<имя>.old`, временный встаёт на место, `.old` удаляется. Перезаписи на месте нет:
  исполняемый образ нельзя открыть на запись, но можно переименовать. Одинаковый набор не
  трогается: `lxd: binary set unchanged (sha256 <exe>[, libcronet.dll <hex>]), copy skipped`.
- **Сайдкар** `sing-box-lxd.install.json` пишется после набора, временным файлом и
  `rename`, читается без повышения. Структура отличается от macOS:
  ```json
  {
    "source": "C:\\Users\\u\\AppData\\Local\\singbox-launcher\\bin\\sing-box.exe",
    "version": "1.14.2-lx.2",
    "installed_at": "2026-09-24T12:00:00Z",
    "service": "sing-box-lxd",
    "files": [
      {"name": "sing-box-lxd.exe", "sha256": "…"},
      {"name": "libcronet.dll", "sha256": "…"}
    ],
    "warnings": [
      {"code": "state_dir_foreign_before_install", "text": "WARN: … before this install; …"}
    ]
  }
  ```
  `service` — служба SCM, к которой привязана копия, `""` — копия без службы. `files` —
  весь набор с sha256 каждой копии. `warnings` — то, о чём предупредили последние install
  или copy; нет поля или пустой массив — предупреждений нет, каждый прогон переписывает
  поле. Код предупреждения один — `state_dir_foreign_before_install`. Если файлы, привязка и
  предупреждения не изменились, сайдкар не переписывается (`lxd: already up to date <sha256>`).
  При установке из самой копии `source` сохраняется прежний.
- **Копия без службы.** `--service=copy` забирает каталог данных и кладёт набор и сайдкар;
  SCM не трогается. Сайдкар получает `service: ""`, если только он не был привязан к
  существующей службе `sing-box-lxd` — тогда привязка сохраняется. Работающая служба
  исполняет старый образ до рестарта (`lxd: the service still runs the previous image until
  restarted`). Повтор с тем же бинарём ничего не меняет. Режим нужен лаунчеру, который сам
  запускает ядро с правами.
- **Самопроверка при старте.** Ядро с повышенным токеном (`lxd` или `run`) проверяет
  собственный бинарь инвариантом: цепочку над его каталогом, каталог, бинарь и
  `libcronet.dll` рядом. `lxd`, запущенный SCM, при нарушении отказывается стартовать,
  причина — в `lxd.log`, код выхода 1:
  ```
  lxd: refusing to run as a Windows service from <бинарь> (owner <имя> (<SID>)): <нарушение>; run `sing-box lxd --service=install` to reinstall from a protected copy
  ```
  Любой другой повышенный запуск — `lxd` вне SCM, `run` (в том числе classic лаунчера) — и
  `lxd --allow-unsafe-exec` только пишут WARN; процесс без повышения не проверяется.
  Пройденная проверка под SCM — одна строка INFO:
  `lxd: self-check ok: protected <путь>, windows service sing-box-lxd`.
- **Поиск DLL.** Любая сборка с `with_lxd` на Windows ограничивает поиск DLL, загружаемых
  без полного пути, каталогом приложения и `System32` (`SetDefaultDllDirectories`). Так
  привилегированное ядро не подхватит библиотеку, подложенную в рабочий каталог или в
  доступный пользователю на запись каталог `PATH`. Сама `libcronet.dll` грузится лениво по
  полному пути: из каталога exe, затем из каталогов `PATH`. Если в наборе нет
  `libcronet.dll`, служба и повышенный `run` на старте пинят загрузку на каталог exe, и
  naive-outbound получает ошибку загрузки вместо поиска по `PATH` под SYSTEM.

Что защита не покрывает:

- подпись Authenticode копии не проверяется и не ставится;
- одновременные install/copy с разными бинарями друг от друга не блокируются: status покажет
  `MISMATCH`, повтор команды чинит;
- предков `<ProgramData>` ядро не проверяет.

### 7a.2. Ручная проверка

Из PowerShell (`icacls` и `Get-Acl` каталога данных требуют прав администратора):

```powershell
sc.exe qc sing-box-lxd                     # BINARY_PATH_NAME = "C:\Program Files\sing-box-lxd\sing-box-lxd.exe" lxd --state-dir …, AUTO_START, LocalSystem, DEPENDENCIES Tcpip
sc.exe qfailure sing-box-lxd               # RESTART -- Delay = 5000 milliseconds (три раза), RESET_PERIOD 86400
sc.exe sdshow sing-box-lxd                 # D:P(A;;GA;;;SY)(A;;GA;;;BA)(A;;0x2008d;;;AU)
sc.exe query sing-box-lxd                  # STATE 4 RUNNING
icacls "C:\Program Files\sing-box-lxd"     # SYSTEM:(OI)(CI)(F), Administrators:(OI)(CI)(F), Authenticated Users:(OI)(CI)(RX); без унаследованных записей
icacls "C:\Program Files\sing-box-lxd\sing-box-lxd.exe"
(Get-Acl "C:\Program Files\sing-box-lxd\sing-box-lxd.exe").Owner   # BUILTIN\Administrators
icacls C:\ProgramData\sing-box-lxd /t      # только SYSTEM и Administrators (плюс собственная запись лаунчера на classic.log)
Get-FileHash "C:\Program Files\sing-box-lxd\sing-box-lxd.exe"      # SHA256, сверить с сайдкаром
Get-Content "C:\Program Files\sing-box-lxd\sing-box-lxd.install.json"
Get-Content C:\ProgramData\sing-box-lxd\logs\lxd.log -Tail 50
sing-box lxd --service=status; "exit $LASTEXITCODE"
```

## 8. Linux — подходы к настройке

На Linux `--service` только печатает. Всё, что меняет диск, — unit/init-скрипт,
`daemon.json`, удаление state — оператор выполняет своими руками. У launchd один
вендор и один API, а на Linux init-системы разные: серверы с systemd, роутеры на
OpenWrt/procd, контейнеры без того и другого. Неверная догадка, которая меняет
`/etc`, хуже точной распечатки. Печать не оставляет и полусостояний: рецепт не
применяется частично и не может оставить хост между двумя конфигурациями.

Поэтому `--service=install` определяет init-систему и печатает готовый к
вставке рецепт — дом демона, `daemon.json`, unit/init-скрипт, команды включения
и шаг сопряжения — со ссылкой на соответствующий раздел этого документа.
`--service=uninstall` так же печатает шаги снятия; `--purge` печатает команду
`rm -rf`, а не выполняет её. `--dry-run` принимается и ничего не меняет — на
Linux любое действие и так лишь печать.

Сам демон на Linux работает полностью: mTLS, apply/rollback, ротация лога.
Кросс-сборка `GOOS=linux GOARCH=arm64` (статический бинарник, musl-совместим)
проверена. Секрет на экран не попадает никогда: рецепт
генерирует его на месте через `$(head -c 32 /dev/urandom | xxd -p -c 64)`, так
что он существует только внутри `daemon.json` на хосте.

Ниже — то, что этот рецепт печатает, если удобнее делать руками.

### 8.1. Общая часть (любой init)

```bash
mkdir -p /var/lib/sing-box-lxd/state        # OpenWrt: /etc/sing-box-lxd/state — см. 8.3
cat > /var/lib/sing-box-lxd/state/daemon.json <<EOF
{
  "listen": "127.0.0.1:19091",
  "tls": true,
  "secret": "$(head -c 32 /dev/urandom | xxd -p -c 64)"
}
EOF
chmod 700 /var/lib/sing-box-lxd /var/lib/sing-box-lxd/state
chmod 600 /var/lib/sing-box-lxd/state/daemon.json
```

> ⚠️ На OpenWrt/busybox нет `xxd`. Подстановка выше даст пустой секрет без
> единой ошибки, а `"secret": ""` при `tls: true` — это канал управления без
> аутентификации. Там секрет генерируйте через `$(openssl rand -hex 32)`: openssl
> на OpenWrt почти всегда есть. Затем проверьте записанное (`grep secret
> daemon.json`), а не выход команды. Рецепт `--service=install` уже печатает
> правильный генератор под каждый init.

Чтобы управлять демоном с другой машины, укажите в `listen` LAN-адрес:
`192.168.10.1:19091`. Если рядом нужен и loopback, подойдёт объектная форма
`{"address": ["192.168.10.1", "127.0.0.1"], "port": 19091}`; оба формата описаны в
разделе [3.1](#31-listen-один-адрес-или-несколько). mTLS обязателен; без
необходимости не открывайте порт наружу в файрволе. Операторские команды
(`client add`) всё равно выполняются только на самом хосте.

### 8.2. systemd (обычный сервер/десктоп)

`/etc/systemd/system/sing-box-lxd.service`:

```ini
[Unit]
Description=sing-box-lx daemon
After=network-online.target
Wants=network-online.target

[Service]
ExecStart=/usr/local/bin/sing-box lxd --state-dir /var/lib/sing-box-lxd/state
Restart=always
RestartSec=2

[Install]
WantedBy=multi-user.target
```

```bash
systemctl daemon-reload
systemctl enable --now sing-box-lxd
```

stdout под systemd — не терминал, поэтому демон сам заберёт лог в
`/var/lib/sing-box-lxd/lxd.log` и будет ротировать; journald получит только
ранний вывод до перехвата.

### 8.3. OpenWrt / procd (роутеры)

Особенности платформы:

- `/var` — tmpfs и очищается при перезагрузке, поэтому state-каталог держите в
  персистентном месте: `/etc/sing-box-lxd/state` (overlay) или extroot (`/root/…`).
- Лог рядом со state писался бы в NAND-overlay и изнашивал бы флеш. Поэтому
  инсталлятор прописывает в daemon.json `"log_file": "/tmp/lxd.log"`. Лог живёт
  на tmpfs и теряется при перезагрузке; для роутера это оправданная цена. Лимиты
  ротации (1 МБ × 2 файла) ограничивают занятую RAM.

**Заливка бинарника.** На OpenWrt часто нет sftp-server, поэтому `scp`/`rsync`
не работают. Рабочий способ — поток через ssh. Архив качайте и распаковывайте на
рабочей машине, не на роутере: там может не хватить места под tar.

```bash
ssh root@HOST 'cat > /root/sing-box' < sing-box            # распакованный бинарь
ssh root@HOST 'chmod +x /root/sing-box && /root/sing-box version'
```

Берите статическую сборку (`GOOS=linux`, musl-совместима) и проверьте это до
запуска: `file sing-box` должен показать `statically linked` под нужную
архитектуру. Динамический бинарь под glibc на musl-роутере не стартует. В выводе
`version` проверьте тег `with_lxd`: без него нет ни `lxd`, ни `client`.

`/etc/init.d/sing-box-lxd`:

```sh
#!/bin/sh /etc/rc.common
START=95
USE_PROCD=1

start_service() {
    procd_open_instance
    procd_set_param command /root/sing-box lxd --state-dir /etc/sing-box-lxd/state
    procd_set_param respawn
    procd_set_param stdout 1
    procd_set_param stderr 1
    procd_close_instance
}
```

```bash
chmod +x /etc/init.d/sing-box-lxd
/etc/init.d/sing-box-lxd enable
/etc/init.d/sing-box-lxd start
```

`sysupgrade -b` не забирает ни init-скрипт, ни state, ни бинарник — дописать
пути в `/etc/sysupgrade.conf`, иначе обновление прошивки удалит установку.

Как поднять поверх демона отдельный VPN-Wi-Fi (Wi-Fi → мост → tun → firewall с
fail-closed) — [openwrt-vpn-ssid.ru.md](openwrt-vpn-ssid.ru.md).

### 8.4. На Linux нет автоустановки и self-update через init

- Автоматической установки нет намеренно: рецепт печатается, выполняет его
  оператор. Причины — в начале [раздела 8](#8-linux--подходы-к-настройке).
- Self-update средствами init — бинарь обновляет себя сам: `sing-box lxd update`
  ([8.6](#86-обновление-sing-box-lxd-update)).

### 8.5. Обслуживание из лаунчера: именованные команды

Демон работает под root, поэтому клиент не может передать ему код на исполнение:
клиент настраивает сеть и ничего больше. Клиент только выбирает команду из
списка, который оператор написал на хосте, — как в `sudoers`. `daemon.json`:

```json
"commands": {
  "update":  "/usr/bin/sing-box lxd update",
  "restart": "/etc/init.d/sing-box-lxd restart"
}
```

Клиент видит список с текстом команд и последним исходом (`GET /admin/commands`)
и запускает команду по имени (`POST /admin/commands/update`). Передать он ничего
не может: запрос с телом получает `400`. Команда исполняется detached в своей
сессии, поэтому рестарт службы убивает демон, но не команду. Дескрипторов демона
у команды нет: перед порождением на все ставится `FD_CLOEXEC`. Иначе
detached-команда с копией fd TUN держала бы интерфейс через рестарт, и новое ядро
не смогло бы его открыть.

Вывод и код выхода пишутся в `<каталог лог-файла>/commands/`, а если лог-файла у
демона нет — в state-dir. На роутере это tmpfs, и запуск не изнашивает flash.
Записи переживают рестарт демона: `GET /admin/commands/update` после него
показывает `done`, код выхода и хвост лога. `lost` значит, что процесс умер, не
успев записать код выхода.

В окружении команды — факты от демона, не от клиента: `LXD_PLATFORM` (релизный
ассет, напр. `linux-arm64`), `LXD_VERSION`, `LXD_INIT_SYSTEM`, `LXD_STATE_DIR`,
`LXD_BIN` (работающий бинарь), `LXD_CLIENT` (кто нажал); `PATH` выставляется в
обычный `/usr/sbin:/usr/bin:/sbin:/bin`, если init его не дал. Каждый запуск
пишется в лог с именем клиента.

Каждая команда выполняется от root. `wget http://…` без проверки checksum отдаёт
root тому, кто сидит на пути трафика. Вместо самодельного скачивания используйте
`sing-box lxd update` ([8.6](#86-обновление-sing-box-lxd-update)). Доступ к
командам проверяется так же, как у всех admin-маршрутов: клиентский сертификат под
mTLS, Bearer без него. Ключ `commands` работает только на unix (Linux, macOS); на
Windows он игнорируется с предупреждением.

### 8.6. Обновление: `sing-box lxd update`

```bash
sing-box lxd update            # последний stable, рестарт через init, откат, если не поднялся
sing-box lxd update --dry-run  # установлено / доступно / ассет — ничего не меняет
```

Бинарь знает то, что самодельный скрипт вынужден угадывать: свой путь
(`os.Executable` с раскрытыми симлинками — это и есть файл для замены), версию,
свой релизный ассет (`Platform:` в `sing-box version`, напр. `linux-armv7`,
`linux-mipsle-softfloat`) и init хоста. Шаги:

1. `SHA256SUMS` последнего stable-релиза (`--prerelease` — новейший релиз,
   включая rc, через GitHub API) даёт имя ассета, версию и сумму одним запросом.
   Версия та же → `already up to date`, выход 0. Установленная новее доступной —
   отказ: даунгрейда нет. Бинарь, упакованный UPX (`UPX!` в первых 4 КиБ), берёт
   упакованную копию `sing-box-<ver>-<platform>.upx.tar.gz`: роутер, на overlay
   которого помещается только сжатое ядро, его и сохраняет. Нет такой копии в
   релизе — ставится обычный архив, об этом пишется строка в вывод.
2. Свободное место рядом с бинарём ≥ его размер + 10 %; если его меньше,
   вместо шагов 3–7 идёт режим малого места (ниже).
3. Архив льётся потоком прямо в `<бинарь>.new` на той же файловой системе: sha256
   по сжатым байтам, gunzip, tar, пишется только запись `sing-box` — в `/tmp`
   (RAM роутера) ничего не попадает. Перед записью место проверяется ещё раз — по
   размеру из tar-заголовка записи (+ 10 %): обычный бинарь вместо упакованного в
   4–5 раз больше, и обновление останавливается здесь, на первых килобайтах архива.
   Прогресс пишется в вывод не чаще раза в секунду (`downloading <asset>: 3.2 / 14.1 MiB (23%)`; без длины от сервера —
   только байты). Несовпадение суммы удаляет `.new`.
4. `<бинарь>.new version` должен запуститься; при применённом конфиге
   (`<state>/last_good.json`) `<бинарь>.new check -c` должен его принять.
5. Подмена: `link(бинарь, бинарь.old)` сохраняет старый inode бесплатно,
   `rename(new, бинарь)` атомарен — без `ETXTBSY`, работающий демон живёт на
   старом inode.
6. Рестарт через init: `/etc/init.d/<service> restart` (procd), `systemctl
   restart <service>` (systemd), `rc-service <service> restart` (openrc);
   `--service` — для юнита с другим именем. Нераспознанный init, `--no-restart`
   или провал самой команды restart оставляют новый бинарь и просят перезапустить
   руками — откатывать нечего.
7. Здоровье: init должен считать службу работающей в течение 15 с и через 3 с
   после этого (crash-loop под procd мигает). Иначе `бинарь.old` возвращается,
   служба перезапускается снова — выход 2.
8. Ядро, а не только процесс. «Running» у init — это демон. Демон, проигравший
   старому процессу гонку за TUN на рестарте, работает с управляющим каналом, но
   без VPN. Поэтому апдейтер спрашивает у нового демона `GET /admin/status`
   (loopback, секрет из `daemon.json`) раз в секунду до 20 с:
   - `started` → `core started`, обновление завершено;
   - `fatal` → откат как в шаге 7 с `ERROR: <ver> is up but the core did not
     start: <last_error>`, выход 2; всё ещё `idle` через 20 с → то же;
   - проба без единого ответа — не вердикт: `core status unknown (…); the service
     is running, not rolling back`, выход 0;
   - `core status not checked: <почему>` — пробы нет вовсе: нет `daemon.json`,
     `listen` не на loopback или ядро остановлено оператором.

   Сам демон при загрузке повторяет открытие занятого TUN до 10 с (каждые 500 мс),
   поэтому обычный `restart` под procd эту гонку тоже не проигрывает.

**Режим малого места.** На роутере, где `/usr/bin` лежит на маленьком
flash-оверлее, вторая копия рядом с бинарём не помещается (обычный linux-arm64
весит ~76 МБ). Когда проверка места шага 2 или 3 не прошла или задан флаг
`--low-space`, копии держатся во временном каталоге (`/tmp`, на роутере это
RAM), а на флешке в каждый момент лежит один бинарь:

1. Подготовка, флешка не тронута: архив распаковывается в
   `/tmp/sing-box-lxd-update/`, сумма, `version` и `check` проверяются как выше,
   работающий бинарь сжимается туда же gzip'ом — это копия для отката. Во
   временном каталоге должно хватить места на обе (statfs, ограниченный
   `MemAvailable`); любой сбой здесь ничего не меняет.
2. Апдейтер передаёт управление новому бинарю из временного каталога: процесс,
   запущенный из `/usr/bin/sing-box`, держит этот файл, и его удаление не
   освободило бы места.
3. `stop` службы, ожидание её выхода, удаление старого бинаря, запись нового
   (`.new`, fsync, rename), `start`. VPN не работает 10–20 с, и питание отключать
   нельзя: между удалением и концом записи бинаря на флешке нет, а копия лежит в
   RAM.
4. Здоровье — как в шагах 7–8. Ошибка записи (в том числе нехватка места: на
   ubifs и jffs2 проверкой служит сама запись, statfs сжатия не видит), служба
   не поднялась или ядро не `started` — старый бинарь восстанавливается из
   копии и запускается, выход 2. Не удалось и это — выход 3: обе копии остаются
   во временном каталоге, в логе команда ручного восстановления.

`--no-restart` в этом режиме отклоняется. На роутере с релизом без этого режима
новый бинарь один раз нужно запустить руками: апдейтер старого релиза
останавливается на проверке места.

| Код выхода | Значение |
|---|---|
| `0` | обновлено или уже актуально |
| `1` | ничего не изменено |
| `2` | откат |
| `3` | откат в режиме малого места не удался |

Скачивание учитывает `HTTPS_PROXY` / `ALL_PROXY` / `NO_PROXY`. Где GitHub
недоступен, команда идёт через собственный inbound ядра:
`"update": "HTTPS_PROXY=socks5://127.0.0.1:2080 /usr/bin/sing-box lxd update"`.
Корневые сертификаты — системные: на OpenWrt это `ca-bundle`, его требует
инсталлятор. `lxd update` есть только на Linux; у macOS и Windows свои пути
установки ([7](#7-macos--автоматическая-установка), [7a](#7a-windows--автоматическая-установка)).
Инсталлятор OpenWrt пишет `"commands": {"update": "/usr/bin/sing-box lxd update"}`
в `daemon.json`, и кнопка Update лаунчера запускает именно эту команду.

## 9. Сопряжение клиента (одинаково на всех ОС)

1. На хосте демона выполните `sing-box lxd client add --name <метка>`. На macOS
   с системной службой команда нужна под sudo. На Windows — от администратора:
   без повышения прав она отвечает `cannot read <путь>: access denied — run as administrator`.
   Команда печатает одноразовый инвайт `адрес#отпечаток#код`.
2. Вставьте инвайт в лаунчер. Лаунчер пинит сервер по отпечатку и регистрируется
   кодом (`POST /admin/enroll`). Дальше демон доверяет ему по его сертификату, а
   код сгорает.
3. Проверка и отзыв: `client list`, `client remove <имя-или-отпечаток>`.

**Имя клиента.** `--name`, `--invite-name` и поле `name` в `POST /admin/client-code`
обрезаются от пробелов по краям. После этого имя либо пустое (клиент без имени), либо
от 1 до 64 печатных символов. Иначе команда отказывает, а маршрут отвечает 400
`client name: …`. Инвайт с именем при погашении заменяет сопряжённого клиента с тем же
именем: старый сертификат отзывается, новый занимает его место. Поэтому лаунчер, который
сопрягается заново на каждом install, не копит записи. Инвайт без имени добавляет клиента.

**Инвайт в файл.** `client add --invite-out <файл>` и `--service=install --invite-out <файл>`
пишут строку инвайта (`адрес#отпечаток#код` и перевод строки) в новый файл вместо печати и
печатают `lxd: invite written to <файл>`.

- Файл создаётся до минта и эксклюзивно. На Unix — `O_CREAT|O_EXCL|O_NOFOLLOW`, режим 0600.
  На Windows — `CREATE_NEW`, после чего итоговый путь открытого файла обязан совпасть с
  запрошенным. Короткое имя 8.3 в запросе допустимо; junction на пути — отказ, файл удаляется.
- Если файл уже существует, команда отказывает до любых изменений.
- Install ждёт минта от демона до 15 с. Если не дождался, install с `--invite-out` выходит
  с кодом 1: служба остаётся установленной, файл удаляется. Лаунчер судит по коду выхода.
- С `--invite-out` install называет клиента `singbox-launcher`, если `--invite-name` не
  задаёт другое имя. Без `--invite-out` имя берётся из `--invite-name`, иначе его нет.
- `--service=install --invite-out` работает там, где install ставит службу (macOS, Windows).
  На Linux install печатает рецепт, и команда отказывает. `client add --invite-out`
  работает везде.

Сопряжение по сети подчиняется трём правилам. Они проверены на роутере, где три попытки
сопряжения не удались:

- **Операторские команды (`client add/list/remove`) работают только с
  loopback.** По сети демон отвечает `403 operator routes are loopback-only`:
  минт инвайта равен выдаче доверия, поэтому снаружи этот маршрут закрыт. Если
  `listen` указывает на один LAN-адрес, демон не слушает loopback, и команда не
  выполнится ни с какого адреса. Решение — объектная форма listen с обоими
  адресами: `{"address": ["192.168.10.1", "127.0.0.1"], "port": 19091}`. Формат
  описан в разделе [3.1](#31-listen-один-адрес-или-несколько). Держать `0.0.0.0`
  ради этого не нужно и небезопасно.
- **Код живёт в памяти процесса, не в state-dir.** Рестарт демона между
  `client add` и вводом кода в лаунчере сбрасывает enrollment: клиент получит
  `enroll: no active enrollment code`. Порядок такой: выставить listen →
  рестарт службы → выпустить код → ввести его в лаунчере → только потом менять
  что-либо ещё.
- **Адрес в инвайте берётся из `listen`.** Если listen — loopback или
  объектная форма, замените в лаунчере адрес на достижимый
  (`192.168.10.1:19091`); отпечаток и код оставьте как есть. После успеха
  доверие лежит в `clients.json` и переживает рестарт демона и ребут хоста.

### 9.1 Свой клиент проходит enrollment за четыре шага

Лаунчер делает всё это сам. Этот раздел — контракт для сторонних клиентов и
для отладки через curl.

Инвайт — три сегмента через `#`: `адрес#отпечаток#код`:

| Сегмент | Смысл |
|---|---|
| `адрес` | куда подключаться (`host:port`) |
| `отпечаток` | SHA-256 от DER серверного сертификата, hex в нижнем регистре; по нему клиент пинит сервер |
| `код` | одноразовый код (`XXXX-XXXX-XXXX`); только этот сегмент идёт в поле `code` |

1. **Сгенерировать клиентскую идентичность.** Подходит любой разбираемый
   X.509-сертификат: демон пинит его SHA-256-отпечаток и цепочку не проверяет,
   поэтому self-signed — норма. Приватный ключ не покидает клиента. Модель та
   же, что у пиров WireGuard: стороны обмениваются только публичными
   сертификатами (отпечатками). Собственные идентичности демона — ECDSA P-256
   на 10 лет:

   ```bash
   openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes \
     -keyout client_key.pem -out client_cert.pem -days 3650 \
     -subj "/CN=my-client" -addext "extendedKeyUsage=clientAuth"
   ```

2. **Подключиться по TLS, пиня сервер.** Серверный сертификат self-signed,
   поэтому клиент заменяет проверку цепочки пином: sha256 от DER листового
   сертификата обязан совпасть с сегментом `отпечаток` из инвайта. curl такой
   пин выразить не умеет: `--pinnedpubkey` хеширует публичный ключ, а не
   сертификат. Для опытов с curl — `-k` и сверка отпечатка вручную:

   ```bash
   openssl s_client -connect 127.0.0.1:19091 </dev/null 2>/dev/null \
     | openssl x509 -outform DER | openssl dgst -sha256
   ```

3. **`POST /admin/enroll`** — без заголовка `Authorization`. Код здесь —
   единственная защита, и это единственный маршрут, достижимый до доверия. Тело —
   JSON с тремя полями. `cert_pem` — клиентский сертификат из шага 1; без него
   или с не-PEM демон отвечает `invalid client certificate PEM`:

   ```bash
   curl -sk https://127.0.0.1:19091/admin/enroll \
     -H 'Content-Type: application/json' \
     -d "$(jq -n --rawfile cert client_cert.pem --arg code XXXX-XXXX-XXXX \
           '{code: $code, name: "my-client", cert_pem: $cert}')"
   ```

   Успех — `{"enrolled":true,"name":…,"fingerprint":…}`. Метка из
   `client add --name` побеждает `name` из запроса. Такой именной код заменяет
   сопряжённого клиента с тем же именем (правило — в разделе
   [9](#9-сопряжение-клиента-одинаково-на-всех-ос), абзац «Имя клиента»).
   Код сгорает при успехе. Активен всегда только один код: новый минт заменяет старый.

4. **Всё после enrollment — mTLS этим сертификатом.** Сертификат — полный
   credential для обеих плоскостей (админ-REST и gRPC), Bearer поверх не нужен:

   ```bash
   curl -sk --cert client_cert.pem --key client_key.pem \
     https://127.0.0.1:19091/admin/status
   ```

Карта ошибок:

| Ответ | Причина |
|---|---|
| `invalid client certificate PEM` | нет `cert_pem`, или это не PEM-блок `CERTIFICATE` |
| `invalid enrollment code` | опечатка, уже сгоревший код, или в `code` вставлен весь инвайт вместо последнего сегмента |
| `no active enrollment code` | демон рестартовал после `client add` (код живёт в памяти процесса), или код уже погашен |
| `client certificate not trusted` (любой другой маршрут) | сертификат не проходил enrollment, или state демона снесён |

## 10. Админ-REST (справочно)

| Маршрут | Что делает |
|---|---|
| `POST /admin/apply` | тело = конфиг; 200 применён / 422 невалиден / 500 сбой (+`rolled_back`) |
| `POST /admin/rollback` | откат на last-good (404 — нечего) |
| `POST /admin/start` · `POST /admin/stop` | жизнь ядра отдельно от конфига (stop запоминается) |
| `GET /admin/config` | активный конфиг |
| `GET /admin/status` | `idle\|started\|fatal`, sha активного/last-good, `last_error`, `interrupted_apply`, `hooks` (`enabled` и последний исход каждого события: `state` `ok\|failed\|timeout\|skipped\|never`, `reason`, `exit_code`, `finished_at`, `detail`; хуки описаны в [6a](#6a-хуки-демон-вызывает-скрипты-админа-при-смене-состояния-ядра)) |
| `GET /admin/info` | паспорт: версия, state_dir, listen, tls, отпечаток, pid, uptime, log_path, `executable` и `executable_sha256` — работающий бинарь. Ядра сравниваются по хешу, не по пути; хеш считается один раз при старте, в первые мгновения он `""`. Платформенная карточка: `goos`, `goarch`; `platform` — релизный ассет для платформы бинаря, то есть что качать для этой машины (`linux-armv7`, `linux-mipsle-softfloat`); `init_system` — init на хосте: `procd` / `systemd` / `openrc` / `launchd` / `scm`, `""` — не распознан; `service` — `true`, если этот процесс запущен под ним как служба; `packed` — `true`, если работающий бинарь сжат UPX: для него качать ассет `<platform>.upx.tar.gz`, как это делает `lxd update` |
| `POST /admin/enroll` | регистрация клиента по одноразовому коду |
| `GET /admin/resources` · `PUT`/`GET`/`DELETE /admin/resources/{имя}` | файлы, на которые ссылается конфиг (`.srs`, geo-базы): список с sha256, заливка, выгрузка, удаление. Пока на имя ссылается активный или last-good конфиг, `DELETE` отвечает 409. `PUT` в этом случае заменяет только набор правил (`.srs`/`.json`), который ядро способно загрузить: 422, если не способно или работающее ядро его отвергло; 409 для любого другого файла. Прежняя копия хранится, пока ядро не перечитало новую или не стартовало с ней (`"replace": "confirmed"` / `"pending"` в ответе), и возвращается при неудавшемся старте |
| `GET /admin/memory` | память процесса: heap/stack/sys, горутины, GC и два числа RSS — `rss_current_bytes` и `rss_peak_bytes` (сырые байты). Пик не убывает, поэтому отдаётся отдельно от текущего |
| `GET /admin/stats` | uptime ядра, `uplink_total`/`downlink_total`, активные соединения; когда ядра нет — всё `null`, статус всё равно 200 |
| `GET /admin/logs?tail=N` | хвост `lxd.log` — лог самого демона. В gRPC-потоке его нет: тот несёт лог ядра |
| `GET /admin/pprof` | профили со счётчиками; `block`/`mutex` показывают `enabled:false`, пока не задан rate |
| `GET /admin/pprof/{имя}` | `heap`, `allocs`, `goroutine`, `threadcreate`, `block`, `mutex` — отдаются мгновенно из того, что рантайм копит и так; `?debug=2` у `goroutine` = дамп стеков |
| `GET /admin/pprof/profile?seconds=N` | CPU-профиль; этот маршрут пишет N секунд (дефолт 30, максимум 120), параллельный запрос получает 409 |
| `GET /admin/pprof/trace?seconds=N` | runtime trace, правила записи те же |
| `POST /admin/pprof/block?rate=N` · `POST /admin/pprof/mutex?fraction=N` | включение/выключение двух lock-профилей (`0` = выкл); не сохраняется, после рестарта сброшено |
| `GET /admin/clients-info` | справочник IP → устройство: `name`, `mac`, `ssid`, `iface`, `port`, `source` по каждому клиенту, о котором знает хост; отвечает и когда ядро не поднято |
| `PUT`/`DELETE /admin/clients-info/labels/{ключ}` | собственное имя клиента от оператора; ключ — IP или MAC (иначе 400) |
| `GET /admin/host` | машина, на которой работает демон: CPU (по ядрам), память, термозоны, диски, дескрипторы. `/admin/memory`, в отличие от него, — про процесс |
| `GET /admin/host/interfaces` | все сетевые интерфейсы с сырыми счётчиками и посчитанными скоростями |
| `GET /admin/commands` | именованные команды оператора: имя, текст, состояние последнего запуска (`idle` / `running` / `done` / `lost`), `started_at`, `finished_at`, `exit_code`, `client` |
| `POST /admin/commands/{name}` | запустить команду по имени, без тела: `202` + вид `running`; `404` — не настроена; `409` — уже выполняется; `400` — непустое тело |
| `GET /admin/commands/{name}` | тот же вид плюс `log` — последние 64 КиБ вывода |

**Операторские маршруты** — `GET /admin/clients`, `POST /admin/client-code`,
`POST /admin/client-remove`. Через них работают подкоманды `client list / add /
remove`, и в удалённую поверхность они не входят. Они слушают только loopback и
требуют Bearer-секрет. Это единственные маршруты, которые не требуют клиентского
сертификата: у оператора на самом хосте его нет. Выпуск кода-приглашения равен
выдаче доверия, поэтому из сети он недостижим. `GET /admin/status` доступен обоими
путями. Запрос без сертификата с loopback-пира идёт операторским путём (секрет):
так `lxd update` узнаёт, поднялось ли ядро. Запрос с доверенным сертификатом или
с любого не-loopback пира идёт путём пина.

SIGHUP демону = перечитать файл конфига (`--config-force`/`-c`) и применить через
тот же apply-пайплайн с валидацией и откатом.

## 10a. `GET /admin/clients-info` превращает адреса в LAN в имена устройств

Инспектор соединений с записью `192.168.20.238:50558` читается, пока устройство
одно, и бесполезен, когда их пятнадцать. `GET /admin/clients-info` — таблица,
которая превращает адреса в устройства. Это справочник, а не поле в соединении:
имена меняются раз в часы, поэтому клиент тянет карту раз в минуту и сам сшивает
её с адресами источников. Поток соединений не меняется.

```bash
curl -s .../admin/clients-info
```

```json
{
  "clients": {
    "192.168.20.238": {"name": "iPhone-Vasya", "mac": "be:ab:bd:ec:70:40",
                       "ssid": "LexVPN2G", "iface": "phy0-ap1", "port": "",
                       "source": "lease+arp+wireless"},
    "192.168.20.51":  {"name": "NAS", "mac": "dc:a6:32:de:ad:be", "ssid": "",
                       "iface": "br-lan", "port": "lan2",
                       "source": "lease+arp+bridge"}
  },
  "sources": ["lease", "arp", "bridge", "wireless"],
  "updated_unix": 1755087234
}
```

Карту наполняют пять провайдеров, каждый следующий уточняет предыдущего:

| Провайдер | Заполняет | Откуда |
|---|---|---|
| `lease` | `name`, `mac` | DHCP-лизы (`/tmp/dhcp.leases` и обычные пути дистрибутивов) |
| `arp` | `mac`, `iface` | `/proc/net/arp`; покрывает и клиентов со статическим IP, которых нет в лизах |
| `bridge` | `port` | `bridge fdb show`: в какой порт включён проводной клиент |
| `wireless` | `ssid`, `iface` | `ubus call hostapd.*` на OpenWrt; уточняет `br-lan` до конкретной точки доступа |
| `label` | `name` | ваши собственные лейблы; перекрывают остальные провайдеры |

`source` есть в каждой записи, чтобы по нему находить, какой провайдер замолчал,
когда устройство теряет имя. Одинокое `"source": "label"` означает, что DHCP-лиз
протух. Пустое поле — состояние, а не ошибка: у проводного клиента нет `ssid`, а
вне Linux последние три провайдера молчат целиком. Маршрут всё равно отвечает —
лизами и лейблами.

`processInfo` эту задачу не решает: он ищет процесс в локальной таблице
сокетов, а соединение клиента из сети открыл другой хост.

Лейблы принадлежат вам и переживают рестарт (`<state_dir>/client-labels.json`):

```bash
curl -X PUT -d '{"name":"Телевизор"}'   .../admin/clients-info/labels/192.168.20.77
curl -X PUT -d '{"name":"Рабочий ноут"}' .../admin/clients-info/labels/be:ab:bd:ec:70:40
curl -X DELETE .../admin/clients-info/labels/192.168.20.77
```

Лейбл по MAC переезжает вместе с устройством на другой адрес. Современные
телефоны подставляют случайный MAC на каждую сеть и меняют его при
переподключении. Для них устойчивее лейбл по IP вместе с DHCP-резервацией.

Карта кешируется на 60 секунд; запись лейбла видна сразу. Лизы ищутся в обычных
местах, переопределяются в `daemon.json`:

```json
{"dhcp_lease_files": ["/etc/custom/leases"]}
```

## 10b. `GET /admin/host` описывает машину, а не процесс

`/admin/memory` описывает процесс демона. Когда тормозит сам роутер, этого
мало. `GET /admin/host` описывает машину:

```bash
curl -s .../admin/host
curl -s .../admin/host/interfaces
```

На что отвечает:

| Секция | Что говорит |
|---|---|
| `cpu` | `usage_percent` и `per_core_percent`: одно ядро на 100 % при трёх свободных среднее прячет. `load_1/5/15` ядро ОС отдаёт готовыми |
| `memory` | `used_percent` считается от `available_bytes`, а не от `free_bytes`. Роутер держит почти всю память в page cache, и процент от free показывает «занято», когда свободно 120 МБ |
| `thermal` | все датчики массивом `zones[]` плюс `max_celsius` для одного индикатора. `null`, когда датчиков нет |
| `disk` | `mounts[]` с флагами `read_only` и `holds_state_dir`. `max_used_percent` игнорирует read-only ФС: корень squashfs на OpenWrt всегда занят на 100 %, а всегда красный индикатор перестают замечать |
| `fd` | открытые дескрипторы демона и лимит, плюс системные. Если упереться в любой из них, новые соединения не открываются, и в логе нет ни одной понятной строки |

**Проценты требуют двух замеров.** `usage_percent` — это дельта между двумя
чтениями `/proc/stat`, поэтому первый запрос после старта отдаёт `null` и
`interval_seconds: 0`. Ноль читался бы как «простаивает», а это другое
утверждение. `interval_seconds` говорит, за какое окно посчитан процент:
12.4% за пять секунд и за час значат разное.

**Кеш 500 мс.** Маршрут можно опрашивать до 2 раз в секунду, и каждый ответ
будет свежим. При более частом опросе вернётся тот же снимок с тем же
`updated_unix`. Проценты — дельта между двумя замерами, поэтому короткое окно
делает число шумнее, а не точнее. Для гладкого графика усредняйте на клиенте,
а не опрашивайте чаще.

**Счётчики и скорости вместе.** У интерфейсов есть и сырой `rx_bytes`, и
`rx_bytes_per_second`. Счётчик переживает рестарты и разрывы; скорость удобна,
но на разрывах неверна. Графики стройте по счётчику, глазами читайте скорость.

Отдаются все интерфейсы, включая `lo` и лежачие: «wan лёг» — то, что
нужно увидеть. Фильтрация — задача UI.

**Платформу определяют машиночитаемые поля, а не строка `os`.** Строка `os` —
для человека, её формат задаёт дистрибутив:

| Поле | Пример | Отвечает на |
|---|---|---|
| `os_family` | `linux` | есть ли тут `/proc` (ядро, сисколлы) |
| `os_id` | `openwrt` | есть ли тут `ubus` (дистрибутив) |
| `os_id_like` | `["lede","openwrt"]` | форк чего-то знакомого? |

Роутер RouteRich называет себя `RouteRich`, но `ID` в `/etc/os-release` у него
`openwrt`: сопоставление по строке для человека платформу бы не опознало.
`os_id_like` нужен для форков, которые ставят собственный `ID` и называют базу
только там. Вне Linux `os_id` — константа (`macos`, `windows`), а `os_id_like` —
пустой массив, не `null`.

**Вне Linux форма ответа та же, недоступные поля — `null`.** На macOS это
термодатчики (нужен CGO) и проценты CPU (Mach API); память, диски,
дескрипторы и load average работают. Клиент проверяет `null`, а не разбирает
поле `os`.

## 11. Демон диагностируется через тот же управляющий порт

Все запросы ниже идут через обычный управляющий порт с обычным клиентским
сертификатом. Второй debug-порт без аутентификации открывать не нужно.
Собственный `experimental.debug.listen` ядра поднимает именно такой порт, без
аутентификации; на сервере, доступном из сети, им пользоваться нельзя.

**Есть ли проблема** — эти запросы дёшевы, их можно слать регулярно:

```bash
curl -s .../admin/memory   # горутины и heap во времени говорят об утечках
curl -s .../admin/stats    # uptime ядра, трафик, живые соединения
```

Неуклонно растущие `goroutines` или `heap_inuse_bytes` — признак утечки.
Смотреть надо на `rss_current_bytes`, а не на `rss_peak_bytes`: пик — максимум
за всю жизнь процесса, вниз он не возвращается.

**Демон завис** — самый быстрый ответ, дамп стеков отдаётся мгновенно:

```bash
curl -s ".../admin/pprof/goroutine?debug=2" > stacks.txt
```

В ответе все горутины со стеками, как в дампе при панике; то, что застряло,
там видно.

**Демон ест CPU** — этот маршрут записывает профиль и отвечает через столько
секунд, сколько задано в `seconds`:

```bash
curl -s ".../admin/pprof/profile?seconds=30" > cpu.pb.gz
go tool pprof -top sing-box cpu.pb.gz
```

**Растёт память** — снять heap дважды с интервалом в час и сравнить:

```bash
curl -s .../admin/pprof/heap > heap-1.pb.gz
# … через час …
curl -s .../admin/pprof/heap > heap-2.pb.gz
go tool pprof -base heap-1.pb.gz sing-box heap-2.pb.gz
```

`heap`, `allocs`, `goroutine` и `threadcreate` — снимки. Рантайм ведёт их
непрерывно, поэтому GET возвращается за миллисекунды и уже покрывает всю
жизнь процесса. Включать заранее ничего не надо, и доступность этих маршрутов
не создаёт фоновой нагрузки.

**Конкуренция за локи** — единственный случай, который нужно сперва включить:
профили `mutex` и `block` стоят ресурсов.

```bash
curl -s -X POST ".../admin/pprof/mutex?fraction=100"
# … дать поработать под нагрузкой …
curl -s .../admin/pprof/mutex > mutex.pb.gz
curl -s -X POST ".../admin/pprof/mutex?fraction=0"     # выключить обратно
```

Аргументом `go tool pprof` укажите тот же бинарь, что работает на хосте.
Символизация происходит на вашей машине, поэтому демон не отдаёт `/symbol`.
